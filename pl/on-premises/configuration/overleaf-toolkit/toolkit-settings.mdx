Ta strona opisuje zmienne środowiskowe obsługiwane w pliku `config/overleaf.rc` we wdrożeniach Toolkit.

Plik `config/overleaf.rc` składa się z definicji zmiennych w postaci `NAME=value`. Wiersze zaczynające się od `#` są traktowane jako komentarze.

<Info>

Po każdej zmianie w `overleaf.rc` lub `variables.env` konieczne jest odtworzenie kontenerów Docker poprzez uruchomienie `bin/up`.

</Info>

## Kontener

### `sharelatex`

| Nazwa | Opis |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PROJECT_NAME` | <p>Ustawia wartość flagi `--project-name` przekazywanej do `docker-compose`. Jest to przydatne przy uruchamianiu wielu instancji Overleaf na jednym hoście, ponieważ każda instancja może mieć inną nazwę projektu.<br /><br />- <strong>Domyślnie</strong>: `overleaf`</p> |
| `OVERLEAF_IMAGE_NAME` | <p>Obraz Docker używany przez kontener aplikacji Server Pro/CE. Jest to tylko nazwa obrazu Docker; tag obrazu Docker jest pobierany z `config/version`.<br /><br />- <strong>Domyślnie:</strong><br />- Server Pro: `ghcr.io/ayaka-notes/overleaf-pro`<br />- Community Edition: `sharelatex/sharelatex`</p> |
| `SERVER_PRO` | <p>Gdy ustawiono `true`, Toolkit używa obrazu Server Pro (`ghcr.io/ayaka-notes/overleaf-pro`) zamiast domyślnego obrazu Server CE (`sharelatex/sharelatex`).<br /><br />- <strong>Domyślnie</strong>: `false`</p> |
| `GIT_BRIDGE_ENABLED` | <p>Ustaw `true`, aby włączyć funkcję git-bridge (tylko Server Pro). Więcej informacji znajdziesz w dokumentacji użytkownika <a href="https://www.overleaf.com/learn/how-to/Git_integration">https://www.overleaf.com/learn/how-to/Git_integration</a>.<br /><br />- <strong>Domyślnie:</strong> `false`</p> |
| `GIT_BRIDGE_IMAGE` | <p>Obraz Docker używany przez kontener git-bridge (tylko Server Pro). Jest to tylko nazwa obrazu Docker; tag obrazu Docker jest pobierany z `config/version`.<br /><br />- <strong>Domyślnie:</strong> `ghcr.io/ayaka-notes/overleaf-pro/git-bridge`</p> |
| `GIT_BRIDGE_DATA_PATH` | Ustawia ścieżkę do katalogu, który zostanie zamontowany w kontenerze `git-bridge` (tylko Server Pro) i będzie używany do przechowywania repozytoriów git. Może to być pełna ścieżka (zaczynająca się od `/`) lub ścieżka względna wobec katalogu bazowego Toolkit. |
| `GIT_BRIDGE_LOG_LEVEL` | <p>Konfiguruje poziom logowania kontenera `git-bridge`. Dostępne poziomy: `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`.<br /><br />- <strong>Domyślnie:</strong> `INFO`</p> |
| `SIBLING_CONTAINERS_ENABLED` | <p>Gdy ustawiono `true`, Toolkit używa techniki <strong>Sibling Containers</strong> do kompilowania projektów w oddzielnych piaskownicach, z osobnym kontenerem Docker dla każdego projektu. Więcej informacji znajdziesz w dokumentacji &#x3C;server-pro-only-configuration/sandboxed-compiles>.<br /><br />- <strong>Wymaga:</strong> `SERVER_PRO=true`<br />- <strong>Domyślnie:</strong> `true`</p> |
| `SIBLING_CONTAINERS_PULL` | <p>Gdy ustawiono `true`, Toolkit przy użyciu polecenia `bin/up` automatycznie pobiera wszystkie obrazy TeX Live ustawione za pomocą `ALL_TEX_LIVE_DOCKER_IMAGES` w pliku <strong>config/variables.env</strong>.<br /><br />- <strong>Domyślnie:</strong> `true`</p> |
| `DOCKER_SOCKET_PATH` | <p>Ustawia ścieżkę do gniazda Docker na maszynie hosta (maszynie, na której działa Toolkit). Gdy `SIBLING_CONTAINERS_ENABLED` ma wartość `true`, gniazdo zostanie zamontowane w kontenerze, aby usługa kompilatora mogła uruchamiać nowe kontenery Docker na hoście.<br /><br />- <strong>Wymaga:</strong> `SIBLING_CONTAINERS_ENABLED=true`<br />- <strong>Domyślnie:</strong> `/var/run/docker.sock`</p> |
| `OVERLEAF_DATA_PATH` | <p>Ustawia ścieżkę do katalogu, który zostanie zamontowany w głównym kontenerze `sharelatex` i będzie używany do przechowywania danych kompilacji. Może to być pełna ścieżka (zaczynająca się od `/`) lub ścieżka względna wobec katalogu bazowego Toolkit.<br /><br />- <strong>Domyślnie:</strong> `data/overleaf`</p> |
| `OVERLEAF_LISTEN_IP` | <p>Ustawia adres(y) IP hosta, na których kontener będzie nasłuchiwał. Na przykład, jeśli ustawiono `0.0.0.0`, interfejs webowy będzie dostępny pod dowolnym adresem IP hosta. Przy bezpośrednim dostępie do kontenera wartość `OVERLEAF_LISTEN_IP` musi być ustawiona na Twój publiczny adres IP. Ustawienie `OVERLEAF_LISTEN_IP` na `0.0.0.0` lub na zewnętrzny adres IP hosta zazwyczaj powoduje błędy przy jednoczesnym użyciu z .<br /><br />- <strong>Domyślnie:</strong> `127.0.0.1`</p> |
| `OVERLEAF_PORT` | <p>Ustawia port hosta, na którym kontener będzie nasłuchiwał. Na przykład, jeśli ustawiono `8099`, a `OVERLEAF_LISTEN_IP` ma wartość `127.0.0.1`, interfejs webowy będzie dostępny pod adresem `http://localhost:8099`.<br /><br />- <strong>Domyślnie:</strong> `80`</p> |
| `OVERLEAF_LOG_PATH` | <p>Ustawia ścieżkę do katalogu, który zostanie zamontowany w głównym kontenerze `sharelatex` i będzie używany do udostępniania logów aplikacji na hoście Docker. Może to być pełna ścieżka (zaczynająca się od `/`) lub ścieżka względna wobec katalogu bazowego Toolkit. Usuń ten wpis konfiguracji, aby wyłączyć montowanie (bind-mount). Jeśli nie jest ustawiony, logi zostaną utracone przy odtwarzaniu kontenera.<br /><br />Zobacz , aby uzyskać informacje o logowaniu.<br /><br />- <strong>Domyślnie:</strong> nieustawione</p> |

### `mongo`

| Nazwa | Opis |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MONGO_ENABLED` | <p>Gdy ustawiono `true`, Toolkit tworzy kontener MongoDB, w którym działa baza danych. Gdy ustawiono `false`, ten kontener nie zostanie utworzony, a system użyje zamiast tego bazy danych MongoDB określonej przez `MONGO_URL`.<br /><br />- <strong>Domyślnie</strong>: `true`</p> |
| `MONGO_URL` | <p>Określa adres URL połączenia z MongoDB używany, gdy `MONGO_ENABLED` ma wartość `false`.<br /><br />- <strong>Domyślnie</strong>: nieustawione</p> |
| `MONGO_DATA_PATH` | <p>Ustawia ścieżkę do katalogu, który zostanie zamontowany w kontenerze `mongo` i będzie używany do przechowywania bazy danych MongoDB. Może to być pełna ścieżka (zaczynająca się od `/`) lub ścieżka względna wobec katalogu bazowego Toolkit. Ta opcja dotyczy tylko lokalnego kontenera `mongo`, tworzonego, gdy `MONGO_ENABLED` ma wartość `true`.<br /><br />- <strong>Domyślnie</strong>: `data/mongo`</p> |
| `MONGO_IMAGE` | <p>Obraz Docker używany przez kontener MongoDB. Jest to tylko nazwa obrazu Docker; tag obrazu Docker należy podać w `MONGO_VERSION` (patrz niżej).<br /><br />- <strong>Domyślnie:</strong> `mongo`</p> |
| `MONGO_VERSION` | <p>Wersja MongoDB używana przez kontener MongoDB. Wartość musi zaczynać się od głównej wersji MongoDB i kropki, np. `6.0` lub `6.0-with-suffix`.<br /><br />- <strong>Domyślnie:</strong> `6.0`</p> |

| `REDIS_PORT` | <p>Określa port Redis używany, gdy `REDIS_ENABLED` ma wartość `false`.<br /><br />- <strong>Domyślnie</strong>: nieustawione</p> |
| `REDIS_DATA_PATH` | <p>Ustawia ścieżkę do katalogu, który zostanie zamontowany w kontenerze `redis` i będzie używany do przechowywania bazy danych Redis. Może to być pełna ścieżka (zaczynająca się od `/`) lub ścieżka względna wobec katalogu bazowego Toolkit. ### `nginx`

| Nazwa | Opis |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NGINX_ENABLED` | <p>Gdy ustawiono `true`, Toolkit tworzy kontener NGINX pełniący funkcję proxy TLS.<br /><br />- <strong>Domyślnie</strong>: `false`</p> |
| `NGINX_CONFIG_PATH` | <p>Ścieżka do pliku konfiguracyjnego NGINX używanego przez proxy TLS.<br /><br />- <strong>Domyślnie</strong>: `config/nginx/nginx.conf`</p> |
| `NGINX_TLS_LISTEN_IP` | <p>Ustawia adres(y) IP hosta, na których kontener proxy TLS będzie nasłuchiwał połączeń HTTPS. Na przykład, jeśli ustawiono `0.0.0.0`, interfejs webowy HTTPS będzie dostępny pod dowolnym adresem IP hosta. Zazwyczaj należy tu ustawić zewnętrzny adres IP hosta.<br /><br />- <strong>Domyślnie</strong>: `127.0.1.1`</p> |
| `NGINX_HTTP_LISTEN_IP` | <p>Ustawia adres(y) IP hosta, na których kontener proxy TLS będzie nasłuchiwał w celu przekierowania HTTP. Na przykład, jeśli ustawiono `127.0.1.1`, połączenia HTTP do `127.0.1.1` będą przekierowywane do interfejsu webowego HTTPS. Zazwyczaj należy tu ustawić zewnętrzny adres IP hosta. Nie ustawiaj `0.0.0.0`, ponieważ zazwyczaj powoduje to konflikt z `OVERLEAF_LISTEN_IP`.<br /><br />- <strong>Domyślnie</strong>: `127.0.1.1`</p> |
| `NGINX_HTTP_PORT` | <p>Ustawia port hosta, na którym kontener proxy TLS będzie nasłuchiwał połączeń HTTP.<br /><br />- <strong>Domyślnie</strong>: `80`</p> |
| `TLS_PORT` | <p>Ustawia port hosta, na którym kontener proxy TLS będzie nasłuchiwał połączeń HTTPS.<br /><br />- <strong>Domyślnie</strong>: `443`</p> |
| `TLS_PRIVATE_KEY_PATH` | <p>Ścieżka do klucza prywatnego używanego przez proxy TLS.<br /><br />- <strong>Domyślnie</strong>: `config/nginx/certs/overleaf_key.pem`</p> |
| `TLS_CERTIFICATE_PATH` | <p>Ścieżka do publicznego certyfikatu używanego przez proxy TLS.<br /><br />- <strong>Domyślnie</strong>: `config/nginx/certs/overleaf_certificate.pem`</p> |
