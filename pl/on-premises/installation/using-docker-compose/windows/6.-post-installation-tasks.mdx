### Tworzenie administratora i pierwszego projektu {#create-the-administrator-and-a-first-project}

Otwórz [http://localhost:8080/launchpad](http://localhost:8080/launchpad) w **przeglądarce w systemie Windows**, utwórz pierwsze konto administratora i zaloguj się. Następnie postępuj zgodnie z krokiem [6. Zadania poinstalacyjne](/pl/on-premises/installation/using-docker-compose/linux/6.-post-installation-tasks) przewodnika dla systemu Linux, używając portu `8080` w przykładowych adresach URL.

### Weryfikacja kompilacji {#verify-compilation}

Działająca strona logowania nie dowodzi, że osobne kontenery kompilatora mają dostęp do katalogu danych WSL. Utwórz pusty projekt i skompiluj ten `main.tex` za pomocą **pdfLaTeX**:

```latex
\documentclass{article}
\begin{document}
Ayakaleaf Pro on Windows WSL 2.
\end{document}
```

Podgląd PDF powinien pokazać ten tekst. W przypadku obrazu basic w razie potrzeby wybierz **TeX Live 2026 Basic** w ustawieniach projektu.

Wybierz **XeLaTeX** i przetestuj:

```latex
\documentclass{article}
\usepackage{fontspec}
\begin{document}
Ayakaleaf WSL XeLaTeX sandbox.
\end{document}
```

Oba przykłady działają z obrazem basic. W przypadku dokumentów chińskich, zanim przetestujesz poniższy przykład z **XeLaTeX**, użyj obrazu zawierającego `ctex` i wymagane fonty, takiego jak full. Obraz basic ich nie zawiera:

```latex
\documentclass{ctexart}
\begin{document}
你好，Ayakaleaf Pro。
\end{document}
```

Aby potwierdzić użycie piaskownicy, uruchom w **Ubuntu** podczas kompilacji:

```bash
docker ps -a --filter ancestor=ghcr.io/ayaka-notes/texlive-basic:2026.1
bin/logs -f clsi
```

W filtrze użyj nazwy wybranego obrazu. Krótkie kompilacje mogą się zakończyć, zanim uruchomi się `docker ps`; `-a` pokazuje również zatrzymane kontenery, dopóki nie zostaną usunięte. Kontener kompilatora powinien używać tego obrazu i bind mountu `/compile` z katalogu danych Toolkit w WSL. Same logi aplikacji nie zastępują sprawdzenia pliku PDF.

### Weryfikacja trwałości danych {#verify-persistence}

W **Ubuntu**, w katalogu Toolkit:

```bash
bin/stop
bin/start
```

Poczekaj na aplikację, otwórz ponownie projekt z systemu Windows i skompiluj go jeszcze raz. Twoje konto, źródło i pliki projektu powinny nadal być na miejscu. Domyślnie bieżące dane znajdują się w `~/ayakaleaf-toolkit/data/` w Ubuntu. Zachowaj zarówno `config/`, jak i `data/`; odinstalowanie lub wyrejestrowanie dystrybucji Ubuntu może je usunąć.

### Utrzymywanie dostępności instancji {#keep-the-instance-available}

Utrzymanie działania instancji składa się z trzech elementów: Windows nie przechodzi w stan uśpienia, Docker Desktop działa, a kontenery uruchamiają się ponownie wraz z silnikiem.

W **Settings → General** Docker Desktop włącz **Start Docker Desktop when you sign in to your computer**, zobacz [ustawienia Docker Desktop](https://docs.docker.com/desktop/settings-and-maintenance/settings/). Uruchamia to Dockera po zalogowaniu, a nie przed nim. Po ponownym uruchomieniu systemu Windows zaloguj się, poczekaj, aż Docker Desktop zakończy uruchamianie, otwórz Ubuntu i sprawdź `docker ps` oraz witrynę.

**Resource Saver** w Docker Desktop to coś innego niż uśpienie systemu Windows. Zwykle włącza się tylko wtedy, gdy nie działają żadne kontenery; działająca aplikacja, MongoDB i Redis zapobiegają temu stanowi bezczynności. W WSL 2 wstrzymuje on silnik Dockera, zamiast wyłączać współdzieloną maszynę wirtualną WSL. Nie wstrzymuj ręcznie (**Pause**) Docker Desktop, gdy obsługujesz użytkowników. Nie musisz wyłączać Resource Saver tylko po to, aby ten stos działał; zobacz [dokumentację Resource Saver Dockera](https://docs.docker.com/desktop/use-desktop/resource-saver/).

Usługi Toolkit używają `restart: always`. Sprawdź rzeczywiste ustawienie w **Ubuntu**:

```bash
docker inspect sharelatex mongo redis --format '{{.Name}} restart={{.HostConfig.RestartPolicy.Name}}'
```

Każda usługa powinna zgłaszać `always`. Gdy Docker działa, może ponownie uruchomić te istniejące kontenery bez nowego `bin/up`. Ręcznie zatrzymany kontener pozostaje zatrzymany, dopóki go nie uruchomisz lub nie uruchomisz ponownie silnika; przy `always` ponowne uruchomienie silnika może go znowu uruchomić. Zobacz [działanie zasad restartu w Dockerze](https://docs.docker.com/engine/containers/start-containers-automatically/).

| Działanie | Wpływ na Ayakaleaf |
| --- | --- |
| Zamknięcie terminala Ubuntu po `bin/up -d` | Kontenery działają w trybie odłączonym; terminal nie jest ich nadzorcą. Docker Desktop i środowisko WSL muszą pozostać dostępne |
| Zamknięcie okna Docker Dashboard | Okno można zamknąć, a Docker Desktop nadal działa w zasobniku systemowym |
| Wybranie **Quit Docker Desktop** | Zatrzymuje silnik i sprawia, że witryna jest niedostępna; aby przywrócić działanie, otwórz ponownie Docker Desktop |
| Uruchomienie `wsl --shutdown` | Zatrzymuje wszystkie dystrybucje WSL i przerywa działanie backendu Docker WSL; uruchom ponownie Docker Desktop i otwórz ponownie Ubuntu |
| Uśpienie, hibernacja lub zamknięcie systemu Windows | Usługa jest niedostępna; samo pozostawienie włączonego lub wyłączonego ekranu tego nie zmienia |
| Uruchomienie `bin/stop` | Zatrzymuje instancję z zachowaniem danych; aby wznowić, użyj `bin/start` |

Do długotrwałego działania przy zasilaniu sieciowym otwórz w systemie Windows 11 **Settings → System → Power & battery → Screen, sleep & hibernate timeouts** (niektóre wersje pokazują **Power** lub **Screen and sleep**). Ustaw limit czasu uśpienia przy podłączonym zasilaniu na **Never** i wyłącz automatyczną hibernację, jeśli jest skonfigurowana. Ekran nadal może się wyłączać. Działanie po zamknięciu pokrywy laptopa to osobne ustawienie; zamknięcie pokrywy może uśpić komputer nawet przy limicie czasu bezczynności ustawionym na Never. Zobacz [ustawienia zasilania systemu Windows](https://support.microsoft.com/en-us/windows/experience/power-battery/power-settings-in-windows-11).

Nie uruchamiaj `wsl --shutdown` w ramach rutynowego porządkowania, gdy witryna jest używana. Jeśli wymaga tego zmiana ustawień WSL, najpierw zatrzymaj instancję i zaplanuj przerwę. Przy tych ustawieniach Windows może uruchamiać instancję w sposób ciągły. Dla usługi współdzielonej, która musi przetrwać wylogowania i nienadzorowane ponowne uruchomienia, zalecamy [przewodnik dla systemu Linux](/pl/on-premises/installation/using-docker-compose/linux).

### Sprawdzanie przywracania po ponownym uruchomieniu Docker Desktop {#check-recovery-after-restarting-docker-desktop}

Po zapisaniu pracy i zakończeniu aktywnych kompilacji wybierz **Restart Docker Desktop** z menu rozwiązywania problemów Docker Desktop. Poczekaj na silnik, a następnie sprawdź w **Ubuntu**:

```bash
docker ps
curl -I http://localhost:8080/launchpad
```

Otwórz istniejący projekt w systemie Windows i skompiluj go ponownie. Potwierdź, że konto i źródło nadal istnieją.

Jeśli celowo zatrzymałeś instancję poleceniem `bin/stop`, użyj `bin/start`. Jeśli Docker działa, ale usługa zawodzi, przeczytaj jej logi, zamiast odtwarzać konfigurację. Aktualizacje systemu Windows, aktualizacje Dockera i utrata zasilania nadal mogą przerwać działanie instalacji pracującej przez całą dobę; twórz kopie zapasowe i sprawdzaj przywracanie po planowanej konserwacji.

### Codzienne użytkowanie {#daily-use}

Uruchom Docker Desktop w systemie Windows. Otwórz **Ubuntu**:

```bash
cd "$HOME/ayakaleaf-toolkit"
```

| Zadanie | Polecenie |
| --- | --- |
| Uruchomienie istniejących kontenerów | `bin/start` |
| Zatrzymanie kontenerów z zachowaniem danych | `bin/stop` |
| Zastosowanie zmian konfiguracji | `bin/up -d` |
| Sprawdzenie stanu | `bin/docker-compose ps` |
| Odczyt logów uruchamiania | `bin/docker-compose logs --tail=100 sharelatex` |
| Odczyt logów MongoDB | `bin/docker-compose logs --tail=100 mongo` |
| Odczyt logów kompilatora | `bin/logs -f clsi` |

`bin/start` nie stosuje zmian konfiguracji: po zmianie `config/` użyj `bin/up -d`. Przed aktualizacją, przeniesieniem lub usunięciem dystrybucji WSL postępuj zgodnie z instrukcją [Dane i kopie zapasowe](/pl/on-premises/maintenance/data-and-backups). Kopiowanie bieżących plików MongoDB w trakcie zapisu przez bazę danych nie daje spójnej kopii zapasowej.

Do użytku lokalnego pozostaw `127.0.0.1`. Obsługa innych komputerów wymaga też świadomie ustawionego adresu nasłuchiwania, adresu URL witryny, konfiguracji zapory/sieci systemu Windows oraz HTTPS; sama zmiana `OVERLEAF_SITE_URL` nie publikuje portu.

Jeśli coś nie działa, zobacz [Rozwiązywanie problemów](/pl/on-premises/installation/using-docker-compose/windows/troubleshooting).
