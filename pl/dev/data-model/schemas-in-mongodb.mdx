W tej sekcji omówimy model danych Overleaf. Overleaf używa MongoDB do trwałego przechowywania danych; jedyna baza danych nosi nazwę `sharelatex`, czyli nazwę poprzednika Overleaf.

Środowisko deweloperskie już uruchamia Mongo Express obok Mongo (zobacz [setup-develop-tools.md](/pl/dev/environment/setup-develop-tools  "mention")). Otwórz [http://localhost:8081/](http://localhost:8081/) i zaloguj się danymi `admin:pass`.

</Frame>

Możesz też otworzyć powłokę w kontenerze Mongo z katalogu `develop`:

```bash
bin/docker-compose exec mongo mongosh sharelatex
```

#### Jak zbudowane są strony {#how-the-pages-are-written}

* Każda strona wymienia pola, które zapisuje kod, z ich typem, znaczeniem i wierszem kodu, który to pokazuje: wierszem schematu Mongoose lub miejscem, które zapisuje pole. Pola zapisywane tylko przez migrację, skrypt lub jeden z modułów web są tak oznaczone.
* Wiele kolekcji nie ma schematu Mongoose: usługi zapisują je za pomocą sterownika MongoDB.
* Indeksy tworzą tylko migracje z `tools/migrations/`. CE przy każdym starcie uruchamia te z tagiem `server-ce` (`server-ce/init_scripts/900_run_web_migrations.sh`); `autoIndex` w Mongoose jest wyłączone (`services/web/app/src/infrastructure/Mongoose.mjs:7`). Tabele indeksów wymieniają tylko to, co ostatecznie ma instancja CE.
* Tekst docs jest w Mongo, ale inna zawartość nie. Zawartość plików jest przechowywana jako bloby, a historia jako chunki w bucketach history-v1 (lokalne foldery lub S3 / RustFS); otwarte docs są w Redis, dopóki document-updater nie wykona flushu.

Na przykład nic w CE ani w naszych modułach nie zapisuje przy normalnym użyciu `splittests`, `samlLogs`, `notificationsPreferences`, `onboardingDataCollection` ani `userfeatureusages`, więc nie mają one strony.
