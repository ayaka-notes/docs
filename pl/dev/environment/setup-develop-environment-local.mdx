## Wymagania wstępne {#prerequisites}

Overleaf to typowy projekt open source oparty na architekturze mikroserwisów, w którym wszystkie usługi działają w Dockerze.

* Kod źródłowy oficjalnej edycji Community Edition znajduje się na [GitHub Overleaf Official](https://github.com/overleaf/overleaf/tree).
* Kod źródłowy Overleaf-CEP jest dostępny na [GitHub Yu-i-i/Overleaf](https://github.com/yu-i-i/overleaf-cep).
* Ayakaleaf Pro jest dostępny na [GitHub ayaka-notes/ayakaleaf-pro](https://github.com/ayaka-notes/ayakaleaf-pro).

Do skonfigurowania środowiska deweloperskiego Overleaf potrzebny jest wydajny serwer; zalecana jest konfiguracja z co najmniej 8 rdzeniami i 16 GB RAM, ponieważ jednocześnie trzeba uruchomić ponad 20 kontenerów.

<Info>

Ponieważ serwery z 8 lub więcej rdzeniami CPU są zazwyczaj drogie, zdecydowanie zalecamy prowadzenie prac deweloperskich na komputerze lokalnym.

</Info>

Zakładamy też, że jako programista znasz już [instalację Dockera](https://docs.docker.com/engine/install/ubuntu/). Do prac deweloperskich zdecydowanie zalecamy używanie aktualnej i stabilnej wersji Ubuntu LTS (np. Ubuntu 24.04 w latach 2025–2026) oraz najnowszej wersji Dockera, co zmniejsza ryzyko wystąpienia nieoczekiwanych błędów.

Podsumowując, będziesz potrzebować:

* [x] Wydajnego serwera/komputera stacjonarnego do prac deweloperskich
* [x] Aktualnej i stabilnej wersji Ubuntu LTS (np. Ubuntu 24.04)
* [x] Środowiska Docker i Git

## Samouczek konfiguracji {#configuration-tutorial}

Tutaj na przykładzie Ayakaleaf Pro pokazujemy, jak skonfigurować środowisko deweloperskie Overleaf. Wszystkie poniższe polecenia są uruchamiane w katalogu `develop`, chyba że zaznaczono inaczej.

<Steps>
<Step title="Pobierz kod źródłowy">
Najpierw sklonuj repozytorium:

```bash title="bash"
git clone https://github.com/ayaka-notes/ayakaleaf-pro.git
cd ayakaleaf-pro/develop
```
</Step>

<Step title="Synchronizacja `yarn.lock`">
Repozytorium używa Yarn 4 (`packageManager` w głównym `package.json`), a jego `yarn.lock` może być niezsynchronizowany z plikami `package.json`. Zsynchronizuj go po pierwszym sklonowaniu i po każdej zmianie w `package.json`:

```bash title="bash"
bin/sync
```

`bin/sync` uruchamia `yarn install --mode=update-lockfile` w kontenerze `node:24.18.1`, więc nie potrzebujesz Node.js na hoście. Nie commituj zmienionego `yarn.lock`.
</Step>

<Step title="Zbuduj obraz deweloperski">
Zbuduj usługi:

```bash title="bash"
bin/build
```

<Info>

Jeśli Dockerowi zabraknie pamięci RAM podczas równoległego budowania usług, utwórz w tym katalogu plik `.env` zawierający `COMPOSE_PARALLEL_LIMIT=1`.

</Info>
</Step>

<Step title="Nałożenie tłumaczeń">
Moduły Ayakaleaf Pro przechowują swoje tłumaczenia w `services/web/locales/locales_patches/`, których nie zawierają zatwierdzone pliki lokalizacji. Nałóż je raz przed pierwszym uruchomieniem, w przeciwnym razie strony tych modułów pokażą klucze takie jak `about_to_permanently_delete_accounts` zamiast tekstu:

```bash title="bash"
bin/i18n
```

Wymaga `jq` na hoście. Uruchom go ponownie po dodaniu tłumaczenia lub zmianie gałęzi, zobacz [Aktualizacja tłumaczeń i18n](/pl/dev/environment/update-i18n-translations).
</Step>

<Step title="Uruchom wszystkie mikroserwisy">
Następnie uruchom usługi:

```bash title="bash"
bin/up
```

Gdy usługi będą działać, otwórz [http://localhost/launchpad](http://localhost/launchpad), aby utworzyć pierwsze konto administratora. Dodaj port, jeśli zmieniłeś `OVERLEAF_PORT` (zobacz niżej).

<Info>

LDAP jest domyślnie włączony (`LDAP_ENABLED=true` w `dev.rc`). Launchpad pokazuje wtedy formularz administratora LDAP: pyta tylko o adres e-mail, a ten administrator loguje się potem przez LDAP, na przykład jako `professor` / `professor` (`professor@planetexpress.com`). Użytkownicy testowi są wymienieni w `develop/authentication/README.md`. Ustaw `LDAP_ENABLED=false` i `SAML_ENABLED=false`, aby zamiast tego utworzyć lokalnego administratora z hasłem.

</Info>
</Step>
</Steps>

<Info>

`develop/dev.env` ustawia już `ADMIN_PRIVILEGE_AVAILABLE=true`, więc administratorzy mogą otworzyć panel administracyjny bez dodatkowej konfiguracji.

</Info>

### Konfiguracja (`dev.rc`) {#configuration-dev-rc}

`develop/dev.rc`, obok `dev.env`, zawiera przełączniki środowiska deweloperskiego, podobnie jak `overleaf.rc` w Overleaf Toolkit. Zmień wartość i ponownie uruchom `bin/dev`, aby ją zastosować; wyłączona funkcja zatrzymuje też swoje kontenery.

| Zmienna | Domyślnie | Co robi |
| --- | --- | --- |
| `OVERLEAF_PORT` | `80` | Port hosta dla witryny. |
| `LDAP_ENABLED` | `true` | Logowanie LDAP z użytkownikami testowymi. |
| `SAML_ENABLED` | `true` | Logowanie SAML z użytkownikami testowymi. |
| `MAILPIT_ENABLED` | `true` | Przechwytuje w Mailpit każdy e-mail z `web`. Włącza też potwierdzanie adresów e-mail (`EMAIL_CONFIRMATION_DISABLED=false`). |
| `S3_ENABLED` | `true` | Przechowuje pliki historii i szablonów w RustFS (S3) zamiast w lokalnych woluminach. |
| `HOPPSCOTCH_ENABLED` | `true` | Hoppscotch z proxy do sieci Dockera, zobacz [Konfiguracja narzędzi deweloperskich](/pl/dev/environment/setup-develop-tools). |
| `HOPPSCOTCH_PORT` | `9170` | Port hosta dla Hoppscotch. |
| `GRAFANA_ENABLED` | `true` | Grafana pod `/grafana/` witryny, ze stanem, metrykami i logami każdej usługi, zobacz [Konfiguracja narzędzi deweloperskich](/pl/dev/environment/setup-develop-tools). |

Każda funkcja trzyma swój `docker-compose.yml` i inne pliki we własnym folderze: `authentication/ldap`, `authentication/saml`, `mail`, `s3`, `hoppscotch` i `grafana`. Funkcja, która potrzebuje ustawienia `web` bez zmiennej środowiskowej, montuje plik w `/etc/overleaf/settings.d/`, a `develop/settings.dev-env.cjs` scala je wszystkie. Wszystkie skrypty `bin/*` działają przez `bin/docker-compose`, który dodaje pliki włączonych funkcji. Używaj `bin/docker-compose` zamiast `docker compose`, gdy potrzebujesz własnego polecenia compose.

<Warning>

Lokalne woluminy i RustFS to osobne magazyny: projekt utworzony przy `S3_ENABLED=true` nie ma historii ani plików binarnych po przełączeniu na `false`, i odwrotnie. Aby skopiować do RustFS pliki środowiska działającego przed pojawieniem się `S3_ENABLED`, postępuj zgodnie z „Moving existing data into RustFS” w [develop/README.md](https://github.com/ayaka-notes/ayakaleaf-pro/blob/server-pro/develop/README.md).

</Warning>

### Porty {#ports}

Witryna, konsola RustFS i Hoppscotch nasłuchują na `127.0.0.1` hosta; na zdalnej maszynie najpierw przekieruj ich porty, na przykład `ssh -L 9001:localhost:9001 <host>`. Witryna używa `OVERLEAF_PORT` z `dev.rc`, więc dodaj port do poniższych adresów, jeśli go zmieniłeś.

| Strona | Adres | Logowanie |
| --- | --- | --- |
| Witryna | [http://localhost](http://localhost) | Konta witryny lub użytkownicy testowi |
| Skrzynka e-mail (Mailpit) | [http://localhost/mailpit/](http://localhost/mailpit/) | Brak |
| Grafana | [http://localhost/grafana/](http://localhost/grafana/) | Brak, anonimowi użytkownicy są administratorami |
| Mongo Express | [http://localhost/mongo-express/](http://localhost/mongo-express/) | Brak |
| RedisInsight | [http://localhost/redis-insight/](http://localhost/redis-insight/) | Brak |
| Konsola S3 (RustFS) | [http://localhost:9001/rustfs/console/](http://localhost:9001/rustfs/console/) | `rustfsadmin` / `rustfsadmin` |
| Hoppscotch | [http://localhost:9170](http://localhost:9170) (`HOPPSCOTCH_PORT`) | Brak |

Mailpit, Grafana, Mongo Express i RedisInsight są udostępniane przez witrynę pod własnymi ścieżkami przez webpack-dev-server, więc nie potrzebują własnych portów. Po zalogowaniu menu **Dev tools** na pasku nawigacji witryny prowadzi do nich; strona, której funkcja jest wyłączona w `dev.rc`, jest pomijana. [Konfiguracja narzędzi deweloperskich](/pl/dev/environment/setup-develop-tools) pokazuje, do czego służy każde z nich.

API S3 (port 9000) i SMTP (port 1025) są dostępne tylko w sieci Dockera. Mongo (27017), Redis (6379), Mongo Express (8081), RedisInsight (5540) i git-bridge (8000) są publikowane tylko na `127.0.0.1` hosta.

### TeX Live {#tex-live}

Kompilacje w piaskownicy są domyślnie włączone: `develop/dev.env` ustawia `SANDBOXED_COMPILES=true` oraz obrazy `ghcr.io/ayaka-notes/texlive-full:2026.1` i `ghcr.io/ayaka-notes/texlive-full:2025.1`. clsi nie pobiera obrazów samodzielnie, więc pobierz je raz:

```bash
docker pull ghcr.io/ayaka-notes/texlive-full:2026.1
docker pull ghcr.io/ayaka-notes/texlive-full:2025.1
```

Szczegóły znajdziesz w [Konfiguracja Sandbox Compiles](/pl/dev/environment/setup-sandbox-compiles).

<Warning>

Projekt utworzony, gdy `SANDBOXED_COMPILES` był wyłączony, nie ma obrazu TeX Live. Nadal kompiluje się z domyślnym obrazem, ale przechodzenie między kodem a PDF kończy się błędem „That didn't work. Recompile and try again.” Przypisz takim projektom raz obraz z `TEX_LIVE_DOCKER_IMAGE`; bez `--commit` skrypt tylko pokazuje, co by zmienił:

```bash
bin/docker-compose exec web sh -c 'cd /overleaf/services/web && node scripts/backfill_project_image_name.mjs --commit'
```

</Warning>

`dev.env` włącza też konwersje Pandoc z `PANDOC_IMAGE=overleaf-pandoc:local`. Zbuduj ten obraz raz, z katalogu głównego repozytorium:

```bash
docker build -t overleaf-pandoc:local develop/pandoc
```

Aby kompilować na hoście macOS, może być konieczne nadpisanie ścieżki do gniazda Dockera przez utworzenie w katalogu `develop` pliku `.env` zawierającego `DOCKER_SOCKET_PATH=/var/run/docker.sock.raw`

### Rozwój {#development}

Aby uniknąć uruchamiania `bin/build && bin/up` po każdej zmianie kodu, możesz uruchomić Overleaf Community Edition w _trybie deweloperskim_, w którym usługi automatycznie aktualizują się po zmianach w kodzie.

W tym celu użyj dołączonego skryptu `bin/dev`:

```text
bin/dev
```

Spowoduje to uruchomienie wszystkich usług za pomocą `node --watch`, który automatycznie monitoruje kod i w razie potrzeby restartuje usługi. Uruchom go ponownie po zmianie `dev.rc`.

Aby poprawić wydajność, możesz uruchomić w trybie deweloperskim tylko część usług, przekazując do skryptu `bin/dev` listę rozdzieloną spacjami:

```text
bin/dev [service1] [service2] ... [serviceN]
```

<Info>

Uruchomienie usługi `web` w _trybie deweloperskim_ spowoduje aktualizację usługi `web` tylko przy zmianach kodu backendu. Aby automatycznie aktualizować również kod frontendu, uruchom także usługę `webpack` w _trybie deweloperskim_.

</Info>

Jeśli nie podasz nazw usług, wszystkie usługi zostaną uruchomione w trybie deweloperskim.

Po dodaniu tłumaczenia lub zmianie gałęzi uruchom `bin/i18n`, zobacz [Aktualizacja tłumaczeń i18n](/pl/dev/environment/update-i18n-translations).

### Debugowanie {#debugging}

W _trybie deweloperskim_ większość usług udostępnia port debugowania, do którego możesz podłączyć debuger, na przykład inspektor w Chrome Dev Tools lub debuger zintegrowany z IDE. Poniższa tabela pokazuje port udostępniony na `127.0.0.1` **maszyny hosta** dla każdej usługi:

| Usługa             | Port |
| ------------------ | ---- |
| `web`                   | 9229 |
| `clsi`                  | 9230 |
| `chat`                  | 9231 |
| `docstore`              | 9233 |
| `document-updater`      | 9234 |
| `filestore`             | 9235 |
| `notifications`         | 9236 |
| `real-time`             | 9237 |
| `history-v1`            | 9239 |
| `project-history`       | 9240 |
| `linked-url-proxy`      | 9241 |
| `third-party-datastore` | 9242 |

Aby podłączyć się do usługi za pomocą _zdalnego debugowania_ Chrome, przejdź do chrome://inspect/ i upewnij się, że opcja _Discover network targets_ jest zaznaczona. Następnie kliknij _Configure..._ i dodaj wpis `localhost:[service port]` dla każdej usługi, do której chcesz podłączyć debugger.

Po dodaniu wpisu usługa pojawi się jako _Remote Target_, który można inspekcjonować i debugować.

### Logowanie {#logging}

Skrypt `bin/logs` śledzi logi i formatuje je za pomocą `bunyan`. Potrzebuje też `ggrep`, czyli nazwy GNU grep zainstalowanego przez Homebrew w macOS; Ubuntu nie ma polecenia `ggrep`.

```bash
sudo npm install -g bunyan
# Or sudo apt install node-bunyan 
```

Możesz też uruchomić bezpośrednio:

```text
bin/docker-compose logs -f [service name]
```

Używaj `bin/docker-compose` zamiast `docker compose`, aby znajdowane były także usługi funkcji z `dev.rc` (`mailpit`, `rustfs`, `ldap`, `saml`, `hoppscotch` oraz `grafana` z Prometheusem, Loki i eksporterami).

Przy `GRAFANA_ENABLED=true` logi każdego kontenera są też w Grafanie, gdzie można je filtrować według usługi, poziomu i tekstu, zobacz [Konfiguracja narzędzi deweloperskich](/pl/dev/environment/setup-develop-tools#grafana).
