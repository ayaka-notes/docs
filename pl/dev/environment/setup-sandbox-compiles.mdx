Kompilacje w piaskownicy działają w środowisku deweloperskim nieco inaczej niż w obrazie produkcyjnym. Środowisko deweloperskie ma je już skonfigurowane; ta strona wyjaśnia ustawienia i trzy kwestie, o których warto pamiętać:

* Problem z uprawnieniami do plików
* Współdzielenie wolumenu między history-v1 a filestore
* Problem z podkatalogami

### Włączanie Sandbox Compiles {#enable-sandbox-compiles}

Kompilacje w piaskownicy są domyślnie włączone. `develop/docker-compose.yml` ustawia `SANDBOXED_COMPILES=true` dla `clsi`, a `develop/dev.env` zawiera resztę:

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

clsi nie pobiera obrazów samodzielnie, więc pobierz je raz poleceniem `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1` (oraz `:2025.1`).

LaTeX działa w kontenerach siostrzanych jako `TEXLIVE_IMAGE_USER`. W środowisku deweloperskim jest to `tex`, który jest też domyślną wartością clsi (`services/clsi/config/settings.defaults.cjs:154`). Obraz produkcyjny używa zamiast tego `www-data`, gdy `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` (`server-ce/config/env.sh:15-21`), ponieważ tam pliki tworzy użytkownik `www-data` kontenera Overleaf.

<Warning>

Nie używaj własnoręcznie zbudowanego obrazu — możesz napotkać szereg błędów.

</Warning>

### Naprawa uprawnień do plików {#fix-file-permissions}

Kontener clsi uruchamia się jako root, przekazuje foldery `compiles`, `output` i `cache` użytkownikowi `node` (uid `1000`), a następnie uruchamia clsi jako `node` (`services/clsi/entrypoint.sh`). Dlatego `develop/compiles` na hoście należy do uid `1000`, tego samego uid co `tex` w środowisku deweloperskim (zobacz komentarz w `develop/pandoc/Dockerfile`). Przy powyższych ustawieniach środowisko deweloperskie kompiluje bez żadnej zmiany uprawnień.

Jeśli zamiast tego ustawisz `TEXLIVE_IMAGE_USER=root`, root (uid `0`) nie ma uprawnień do zapisu w podfolderach `compiles`. W takim przypadku nadaj grupie `root` własność i prawo zapisu do `compiles`, z ustawionym `setgid`, aby nowe podfoldery dziedziczyły tę własność:

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

Szczegółową dokumentację znajdziesz w pliku `services/clsi/README.md`.

### Współdzielenie wolumenu między history-v1 a filestore {#volume-share-between-history-v1-and-filestore}

<Info>

Ustawienia z tej i następnej sekcji są już w `develop/docker-compose.yml` i `develop/dev.env`. Mają znaczenie tylko przy `S3_ENABLED=false` w `develop/dev.rc`. Przy domyślnym `S3_ENABLED=true` filestore i history-v1 przechowują te pliki w bucketach RustFS (`develop/s3/docker-compose.yml`).

</Info>

Domyślnie filestore pełni rolę pomostu między S3 a innymi usługami w Overleaf. Jednak w Overleaf CE lub Server Pro wszystkie pliki są domyślnie przechowywane lokalnie. Dlatego Overleaf wprowadził dość nietypowe rozwiązanie.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

Jednocześnie `data/history` jest też używany przez usługę historii. Dzięki temu różne mikrousługi mogą współdzielić te same dane. Dlatego usługa filestore w develop montuje wolumin `history-v1-buckets` z history-v1. Bez niego **clsi nie będzie mógł pobierać plików blob z usługi filestore**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

filestore znajduje buckety dzięki tym ustawieniom w `dev.env`:

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### Używanie podkatalogów {#use-subdirectories}

filestore zawsze odczytuje bloby historii z podkatalogami (`services/filestore/app/js/KeyBuilder.js:58`, `:70`). Obraz produkcyjny włącza `useSubdirectories` dla history-v1 (`server-ce/config/production.json`), ale domyślna konfiguracja history-v1 tego nie robi, więc w środowisku deweloperskim history-v1 <strong>spłaszczyłby wszystkie dane.</strong> Dlatego `dev.env` ustawia `NODE_CONFIG` dla history-v1:&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

Bez tego history-v1 zapisuje pliki `project_blobs` w ten sposób:

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

Gdy `useSubdirectories` ma wartość `true`, znak `_` w tych nazwach zmienia się w `/`, więc każdy blob jest zapisywany w podfolderach.
