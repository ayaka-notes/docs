### Wprowadzenie

Zanim zagłębisz się w rozwój projektu, prosimy o zapoznanie się z następującymi kwestiami:

* Overleaf jest oficjalnie rozwijany w [wewnętrznym repozytorium](http://github.com/overleaf/internal), a wersja społecznościowa (Community Edition) jest publikowana w [overleaf/overleaf](https://github.com/overleaf/overleaf). Za synchronizację kodu między repozytorium wewnętrznym a publicznym odpowiada copybot.
* [Ayaka-notes/overleaf-pro](https://github.com/ayaka-notes/ayakaleaf-pro) to fork wersji społecznościowej Overleaf. Chcemy, aby ten projekt był rozwijany długoterminowo, dlatego przed wniesieniem wkładu prosimy o przestrzeganie poniższych zasad.

### Zasady dotyczące commitów

* Prosimy nie wprowadzać rozległych modyfikacji w istniejącym kodzie Overleaf. Skupiaj jak najwięcej funkcjonalności w katalogu `services/web/modules`. Zminimalizuje to nakład pracy przy późniejszym scalaniu i aktualizowaniu kodu.
* Vibe coding to rzeczywiście bardzo wygodna metoda, ale łatwo może wprowadzić bałagan w projekcie i sprawić, że później stanie się on trudny w utrzymaniu, dlatego korzystaj z niego ostrożnie.
* Prosimy nie dodawać podczas rozwoju żadnych treści związanych z tłumaczeniami; w miarę możliwości korzystaj z istniejących tłumaczeń.
* Unikaj wprowadzania zmiennych środowiskowych, o ile nie jest to absolutnie konieczne. Jeśli są wymagane, zadbaj o to, aby były jak najbardziej spójne z tymi z Overleaf Toolkit lub [docs.overleaf.com](https://docs.overleaf.com/).

### Zasady dotyczące gałęzi

Do rozwoju overleaf-pro używamy następujących gałęzi:

* `main`: Ta gałąź służy wyłącznie do synchronizacji kodu z upstreamu, prosimy **NIE** commitować do niej żadnych zewnętrznych zmian. W tej gałęzi ustawiamy tagi takie jak `ce-v[X.x.x]`, które oznaczają, że dany stan odpowiada wersji `v[X.x.x]` oficjalnej wersji Overleaf Community Edition. Uwaga: te tagi są niezmienne!
* `server-pro`: Domyślna gałąź do codziennego rozwoju.
* `feature-X`: Gałąź służąca do rozwoju konkretnej funkcji.
* `release-vX.0.0`: Gałąź przeznaczona dla wydania; przed wydaniem wprowadzamy w niej poprawki typu hot-fix.

### GitHub Action

[GitHub Action](https://github.com/ayaka-notes/ayakaleaf-pro/actions) odpowiada za automatyczne CI/CD. Nie musisz budować obrazów na własnym komputerze: każdy z poniższych obrazów jest budowany przez workflow, a te z ręcznym wyzwalaczem można zbudować jednym kliknięciem.

| Workflow | Wyzwalacz | Źródło | Obraz |
| --- | --- | --- | --- |
| Sync Upstream Code | Codziennie, ręcznie | `overleaf/overleaf` → `main` | — |
| Build Development Image | Codziennie, ręcznie | `server-pro` | `ghcr.io/ayaka-notes/overleaf-pro/dev:<service>` |
| Build Operations Image | Push / PR do `server-pro`, ręcznie | Wypchnięty commit lub HEAD PR | `ghcr.io/ayaka-notes/overleaf-pro/ops:<YYYYMMDDHHMM>-<sha>`, `ops:latest` |
| Build Release Image | Ręcznie | Najnowsza gałąź `release-v*` | `ghcr.io/ayaka-notes/overleaf-pro:<version>`, `:latest` oraz `overleaf-pro/git-bridge` |

* **Obrazy deweloperskie** zawierają po jednej mikrousłudze (`web`, `webpack`, `clsi`, ...) dla `linux/amd64` i `linux/arm64`. Konfiguracja Codespace pobiera je za pomocą `develop/docker-compose.image.yml` zamiast uruchamiać `bin/build`.
* **Obrazy operacyjne** to pełne obrazy jednokontenerowe (jak `sharelatex/sharelatex`) służące do kompleksowego testowania zmian. `ops:latest` jest przesuwany tylko przy pushach do `server-pro`; PR otrzymuje wyłącznie tag z sygnaturą czasową. Obrazy te są przechowywane przez 7 dni i służą wyłącznie do testów.
* **Obrazy wydań** to obrazy wdrażane przez użytkowników. Wersja pochodzi z nazwy gałęzi, więc `release-v6.3.0` publikuje `overleaf-pro:6.3.0`.

<Steps>
<Step title="Ręczne uruchamianie workflow">
Otwórz kartę [Actions](https://github.com/ayaka-notes/ayakaleaf-pro/actions), wybierz workflow po lewej stronie, kliknij **Run workflow** i potwierdź. Build Operations Image ma również opcję **Build without cache** na wypadek, gdy warstwa w pamięci podręcznej jest nieaktualna.
</Step>

<Step title="Budowanie we własnym forku">
Te same workflow działają w forku: włącz Actions w swoim forku, a następnie uruchamiaj je z jego karty Actions. Obrazy są wypychane do `ghcr.io/<your-name>/overleaf-pro/...` za pomocą wbudowanego `GITHUB_TOKEN`, więc żadne sekrety nie są potrzebne. Sync Upstream Code oraz czyszczenie starych obrazów działają tylko w `ayaka-notes`.

Build Release Image wymaga gałęzi `release-v*` w Twoim forku.
</Step>
</Steps>

<Info>

Aby sprawdzić, z którego commitu zbudowano obraz: tag obrazu operacyjnego kończy się skróconym hashem commitu, a obraz wydania zawiera go w etykiecie `com.overleaf.pro.revision` (zobacz `docker inspect` w sekcji Pytania i odpowiedzi poniżej).

</Info>

### Pytania i odpowiedzi

<Accordion title="Jak znaleźć hash commitu dla Overleaf Community Edition `X.0.0`?">

Najpierw pobierz obraz Docker i uruchom poniższe polecenie, aby sprawdzić etykiety tego obrazu:

```shellscript title="bash" wrap
docker inspect --format='{{json .Config.Labels}}' sharelatex/sharelatex:6.0.0
{"com.overleaf.ce.revision":"b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f","org.opencontainers.image.ref.name":"ubuntu","org.opencontainers.image.version":"24.04"}
```

Następnie możesz sprawdzić, czy [commit (b0d05c0)](https://github.com/overleaf/overleaf/commit/b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f) znajduje się w gałęzi master upstreamu.

</Accordion>

<Accordion title="Dlaczego hash commitu w obrazie CE jest taki sam dla wersji `6.0.0` i `6.0.1`?">

To zamierzone zachowanie. Wydanie 6.0.1 jest drobnym wydaniem poprawkowym zbudowanym na bazie obrazu 6.0.0. Zmiany są nakładane poprzez łatanie istniejącego obrazu 6.0.0, a nie przez przebudowanie obrazu z nowego commitu. Dlatego hash commitu wewnątrz obrazu jest identyczny w wersjach 6.0.0 i 6.0.1.

Szczegółowe informacje znajdziesz w [hotfix](https://github.com/overleaf/overleaf/tree/main/server-ce/hotfix).

</Accordion>
