## المتطلبات المسبقة {#prerequisites}

يُعد Overleaf مشروعًا نموذجيًا مفتوح المصدر قائمًا على بنية الخدمات المصغّرة (microservices)، حيث تعمل جميع الخدمات داخل Docker.

* الشيفرة المصدرية الرسمية لإصدار Community Edition موجودة على [GitHub Overleaf Official](https://github.com/overleaf/overleaf/tree).
* الشيفرة المصدرية لـ Overleaf-CEP متاحة على [GitHub Yu-i-i/Overleaf](https://github.com/yu-i-i/overleaf-cep).
* يتوفر Ayakaleaf Pro على [GitHub ayaka-notes/ayakaleaf-pro](https://github.com/ayaka-notes/ayakaleaf-pro).

لإعداد بيئة تطوير Overleaf، ستحتاج إلى خادم قوي؛ يُوصى بتكوين لا يقل عن 8 أنوية و16 جيجابايت من ذاكرة RAM، لأنك ستحتاج إلى تشغيل أكثر من 20 حاوية في الوقت نفسه.

<Info>

نظرًا لأن الخوادم التي تحتوي على 8 أنوية معالج أو أكثر تكون عادةً باهظة الثمن، يُوصى بشدة باستخدام حاسوبك المحلي للتطوير.

</Info>

في الوقت نفسه، وبصفتك مطورًا، نعتقد أنك على دراية مسبقة بـ [تثبيت Docker](https://docs.docker.com/engine/install/ubuntu/). ننصح بشدة باستخدام إصدار حديث ومستقر من Ubuntu LTS (مثل Ubuntu 24.04 في 2025–2026) وأحدث إصدار من Docker للتطوير، لأن ذلك يقلل من احتمال مواجهة أخطاء غير متوقعة.

باختصار، ستحتاج إلى:

* [x] خادم أو حاسوب مكتبي قوي للتطوير
* [x] إصدار حديث ومستقر من Ubuntu LTS (مثل Ubuntu 24.04)
* [x] بيئة Docker وGit

## دليل الإعداد {#configuration-tutorial}

نستخدم هنا Ayakaleaf Pro لنوضح كيفية إعداد بيئة تطوير Overleaf. تُشغَّل جميع الأوامر أدناه في المجلد `develop` ما لم يُذكر خلاف ذلك.

<Steps>
<Step title="سحب الشيفرة المصدرية">
أولًا، لنقم باستنساخ المستودع:

```bash title="bash"
git clone https://github.com/ayaka-notes/ayakaleaf-pro.git
cd ayakaleaf-pro/develop
```
</Step>

<Step title="مزامنة `yarn.lock`">
يستخدم المستودع Yarn 4 (`packageManager` في ملف `package.json` الجذري)، وقد يكون ملف `yarn.lock` غير متزامن مع ملفات `package.json`. زامنه بعد الاستنساخ الأول وبعد أي تغيير في `package.json`:

```bash title="bash"
bin/sync
```

يشغّل `bin/sync` الأمر `yarn install --mode=update-lockfile` داخل حاوية `node:24.18.1`، لذا لا تحتاج إلى Node.js على المضيف. لا تلتزم بملف `yarn.lock` المعدَّل.
</Step>

<Step title="بناء صورة التطوير">
ابنِ الخدمات:

```bash title="bash"
bin/build
```

<Info>

إذا نفدت ذاكرة RAM لدى Docker أثناء بناء الخدمات بالتوازي، فأنشئ ملف `.env` في هذا المجلد يحتوي على `COMPOSE_PARALLEL_LIMIT=1`.

</Info>
</Step>

<Step title="تطبيق الترجمات">
تحتفظ وحدات Ayakaleaf Pro بترجماتها في `services/web/locales/locales_patches/`، وهي غير موجودة في ملفات اللغات الملتزَم بها. طبّقها مرة واحدة قبل التشغيل الأول، وإلا فستعرض صفحات هذه الوحدات مفاتيح مثل `about_to_permanently_delete_accounts` بدلًا من النص:

```bash title="bash"
bin/i18n
```

يحتاج إلى `jq` على المضيف. شغّله مجددًا بعد إضافة ترجمة أو تغيير الفرع، راجع [تحديث ترجمات i18n](/ar/dev/environment/update-i18n-translations).
</Step>

<Step title="تشغيل جميع الخدمات المصغّرة">
ثم شغّل الخدمات:

```bash title="bash"
bin/up
```

بمجرد تشغيل الخدمات، افتح [http://localhost/launchpad](http://localhost/launchpad) لإنشاء أول حساب مسؤول. أضف المنفذ إذا غيّرت `OVERLEAF_PORT` (انظر أدناه).

<Info>

يكون LDAP مفعّلًا افتراضيًا (`LDAP_ENABLED=true` في `dev.rc`). عندها يعرض launchpad نموذج مسؤول LDAP: يطلب بريدًا إلكترونيًا فقط، ثم يسجّل هذا المسؤول الدخول عبر LDAP، مثلًا باسم `professor` / `professor` (`professor@planetexpress.com`). المستخدمون التجريبيون مدرجون في `develop/authentication/README.md`. اضبط `LDAP_ENABLED=false` و`SAML_ENABLED=false` لإنشاء مسؤول محلي بكلمة مرور بدلًا من ذلك.

</Info>
</Step>
</Steps>

<Info>

يضبط `develop/dev.env` بالفعل `ADMIN_PRIVILEGE_AVAILABLE=true`، لذا يمكن للمسؤولين فتح لوحة الإدارة دون إعداد إضافي.

</Info>

### الإعداد (`dev.rc`) {#configuration-dev-rc}

يحتوي `develop/dev.rc` بجوار `dev.env` على مفاتيح بيئة التطوير، مثل `overleaf.rc` في Overleaf Toolkit. غيّر قيمة وشغّل `bin/dev` مجددًا لتطبيقها؛ والميزة المعطّلة توقف حاوياتها أيضًا.

| المتغير | الافتراضي | ما يفعله |
| --- | --- | --- |
| `OVERLEAF_PORT` | `80` | منفذ الموقع على المضيف. |
| `LDAP_ENABLED` | `true` | تسجيل الدخول عبر LDAP بمستخدمين تجريبيين. |
| `SAML_ENABLED` | `true` | تسجيل الدخول عبر SAML بمستخدمين تجريبيين. |
| `MAILPIT_ENABLED` | `true` | يلتقط في Mailpit كل بريد إلكتروني يرسله `web`. كما يفعّل تأكيد البريد الإلكتروني (`EMAIL_CONFIRMATION_DISABLED=false`). |
| `S3_ENABLED` | `true` | يحتفظ بملفات السجل والقوالب في RustFS (S3) بدلًا من وحدات التخزين المحلية. |
| `HOPPSCOTCH_ENABLED` | `true` | Hoppscotch مع وكيل إلى شبكة Docker، راجع [إعداد أدوات التطوير](/ar/dev/environment/setup-develop-tools). |
| `HOPPSCOTCH_PORT` | `9170` | منفذ Hoppscotch على المضيف. |
| `GRAFANA_ENABLED` | `true` | Grafana على `/grafana/` في الموقع، مع حالة كل خدمة ومقاييسها وسجلاتها، راجع [إعداد أدوات التطوير](/ar/dev/environment/setup-develop-tools). |

تحتفظ كل ميزة بملف `docker-compose.yml` وملفاتها الأخرى في مجلد خاص بها: `authentication/ldap` و`authentication/saml` و`mail` و`s3` و`hoppscotch` و`grafana`. والميزة التي تحتاج إلى إعداد في `web` بلا متغير بيئة تربط ملفًا في `/etc/overleaf/settings.d/`، ويدمجها `develop/settings.dev-env.cjs` جميعًا. تمر جميع سكربتات `bin/*` عبر `bin/docker-compose` الذي يضيف ملفات الميزات المفعّلة. استدعِ `bin/docker-compose` بدلًا من `docker compose` عندما تحتاج إلى أمر compose بنفسك.

<Warning>

وحدات التخزين المحلية وRustFS مخزنان منفصلان: المشروع الذي أُنشئ مع `S3_ENABLED=true` لا يحتوي على سجل أو ملفات ثنائية بعد التبديل إلى `false`، والعكس صحيح. لنسخ ملفات بيئة كانت تعمل قبل وجود `S3_ENABLED` إلى RustFS، اتبع «Moving existing data into RustFS» في [develop/README.md](https://github.com/ayaka-notes/ayakaleaf-pro/blob/server-pro/develop/README.md).

</Warning>

### المنافذ {#ports}

يستمع الموقع ووحدة تحكم RustFS وHoppscotch على `127.0.0.1` للمضيف؛ وعلى جهاز بعيد، أعِد توجيه منافذها أولًا، مثلًا `ssh -L 9001:localhost:9001 <host>`. يستخدم الموقع `OVERLEAF_PORT` من `dev.rc`، لذا أضف المنفذ إلى العناوين أدناه إذا غيّرته.

| الصفحة | العنوان | تسجيل الدخول |
| --- | --- | --- |
| الموقع | [http://localhost](http://localhost) | حسابات الموقع أو المستخدمون التجريبيون |
| صندوق البريد (Mailpit) | [http://localhost/mailpit/](http://localhost/mailpit/) | لا يوجد |
| Grafana | [http://localhost/grafana/](http://localhost/grafana/) | لا يوجد، المستخدمون المجهولون مسؤولون |
| Mongo Express | [http://localhost/mongo-express/](http://localhost/mongo-express/) | لا يوجد |
| RedisInsight | [http://localhost/redis-insight/](http://localhost/redis-insight/) | لا يوجد |
| وحدة تحكم S3 (RustFS) | [http://localhost:9001/rustfs/console/](http://localhost:9001/rustfs/console/) | `rustfsadmin` / `rustfsadmin` |
| Hoppscotch | [http://localhost:9170](http://localhost:9170) (`HOPPSCOTCH_PORT`) | لا يوجد |

يقدّم الموقع Mailpit وGrafana وMongo Express وRedisInsight على مساراتها الخاصة عبر webpack-dev-server، لذا لا تحتاج إلى منافذ خاصة بها. بعد تسجيل الدخول، تشير إليها قائمة **Dev tools** في شريط التنقل بالموقع؛ وتُستبعد الصفحة التي تكون ميزتها معطّلة في `dev.rc`. يوضح [إعداد أدوات التطوير](/ar/dev/environment/setup-develop-tools) ما تفعله كل منها.

لا يمكن الوصول إلى واجهة S3 API (المنفذ 9000) وSMTP (المنفذ 1025) إلا داخل شبكة Docker. تُنشر Mongo (27017) وRedis (6379) وMongo Express (8081) وRedisInsight (5540) وgit-bridge (8000) على `127.0.0.1` للمضيف فقط.

### TeX Live {#tex-live}

الترجمة في بيئة معزولة مفعّلة افتراضيًا: يضبط `develop/dev.env` القيمة `SANDBOXED_COMPILES=true` والصورتين `ghcr.io/ayaka-notes/texlive-full:2026.1` و`ghcr.io/ayaka-notes/texlive-full:2025.1`. لا يسحب clsi الصور بنفسه، لذا اسحبها مرة واحدة:

```bash
docker pull ghcr.io/ayaka-notes/texlive-full:2026.1
docker pull ghcr.io/ayaka-notes/texlive-full:2025.1
```

راجع [إعداد Sandbox Compiles](/ar/dev/environment/setup-sandbox-compiles) للتفاصيل.

<Warning>

المشروع الذي أُنشئ بينما كان `SANDBOXED_COMPILES` معطّلًا لا يملك صورة TeX Live. يظل يُترجم بالصورة الافتراضية، لكن الانتقال بين الكود وملف PDF يفشل بالرسالة «That didn't work. Recompile and try again.» امنح هذه المشاريع صورة `TEX_LIVE_DOCKER_IMAGE` مرة واحدة؛ وبدون `--commit` يعرض السكربت ما سيغيّره فقط:

```bash
bin/docker-compose exec web sh -c 'cd /overleaf/services/web && node scripts/backfill_project_image_name.mjs --commit'
```

</Warning>

يفعّل `dev.env` أيضًا تحويلات Pandoc باستخدام `PANDOC_IMAGE=overleaf-pandoc:local`. ابنِ هذه الصورة مرة واحدة من جذر المستودع:

```bash
docker build -t overleaf-pandoc:local develop/pandoc
```

للترجمة على مضيف macOS، قد تحتاج إلى تجاوز مسار مقبس Docker بإنشاء ملف `.env` في المجلد `develop` يحتوي على `DOCKER_SOCKET_PATH=/var/run/docker.sock.raw`

### التطوير {#development}

لتجنب تشغيل `bin/build && bin/up` بعد كل تغيير في الشيفرة، يمكنك تشغيل Overleaf Community Edition في _وضع التطوير_، حيث تُحدَّث الخدمات تلقائيًا عند تغيير الشيفرة.

للقيام بذلك، استخدم السكربت المضمّن `bin/dev`:

```text
bin/dev
```

سيؤدي ذلك إلى تشغيل جميع الخدمات باستخدام `node --watch`، الذي يراقب الشيفرة تلقائيًا ويعيد تشغيل الخدمات عند الحاجة. شغّله مجددًا بعد تغيير `dev.rc`.

لتحسين الأداء، يمكنك تشغيل مجموعة فرعية فقط من الخدمات في وضع التطوير عن طريق تمرير قائمة مفصولة بمسافات إلى السكربت `bin/dev`:

```text
bin/dev [service1] [service2] ... [serviceN]
```

<Info>

سيؤدي تشغيل خدمة `web` في _وضع التطوير_ إلى تحديث خدمة `web` فقط عند تغيير شيفرة الواجهة الخلفية. ولتحديث شيفرة الواجهة الأمامية تلقائيًا أيضًا، تأكد من تشغيل خدمة `webpack` في _وضع التطوير_ كذلك.

</Info>

إذا لم تُحدَّد أي خدمات، فستعمل جميع الخدمات في وضع التطوير.

بعد إضافة ترجمة أو تغيير الفرع، شغّل `bin/i18n`، راجع [تحديث ترجمات i18n](/ar/dev/environment/update-i18n-translations).

### تصحيح الأخطاء {#debugging}

عند التشغيل في _وضع التطوير_ تكشف معظم الخدمات منفذ تصحيح يمكنك ربط مصحّح به، مثل أداة الفحص في Chrome Dev Tools أو مصحّح مدمج في بيئة تطوير. يعرض الجدول التالي المنفذ المكشوف على `127.0.0.1` في **الجهاز المضيف** لكل خدمة:

| الخدمة             | المنفذ |
| ------------------ | ---- |
| `web`                   | 9229 |
| `clsi`                  | 9230 |
| `chat`                  | 9231 |
| `docstore`              | 9233 |
| `document-updater`      | 9234 |
| `filestore`             | 9235 |
| `notifications`         | 9236 |
| `real-time`             | 9237 |
| `history-v1`            | 9239 |
| `project-history`       | 9240 |
| `linked-url-proxy`      | 9241 |
| `third-party-datastore` | 9242 |

للاتصال بخدمة باستخدام _التصحيح عن بُعد_ في Chrome، انتقل إلى chrome://inspect/ وتأكد من تحديد _Discover network targets_. ثم انقر على _Configure..._ وأضف إدخالًا `localhost:[service port]` لكل خدمة تريد ربط مصحح الأخطاء بها.

بعد إضافة الإدخال، ستظهر الخدمة كـ _Remote Target_ يمكنك فحصها وتصحيح أخطائها.

### السجلات {#logging}

يتابع السكربت `bin/logs` السجلات وينسّقها باستخدام `bunyan`. كما يحتاج إلى `ggrep`، وهو اسم GNU grep عند تثبيته عبر Homebrew على macOS؛ ولا يحتوي Ubuntu على الأمر `ggrep`.

```bash
sudo npm install -g bunyan
# Or sudo apt install node-bunyan 
```

أو يمكنك التشغيل مباشرةً باستخدام:

```text
bin/docker-compose logs -f [service name]
```

استخدم `bin/docker-compose` بدلًا من `docker compose` حتى يُعثر أيضًا على خدمات الميزات في `dev.rc` (`mailpit` و`rustfs` و`ldap` و`saml` و`hoppscotch` و`grafana` مع Prometheus وLoki والمصدّرات).

مع `GRAFANA_ENABLED=true` تكون سجلات كل حاوية موجودة أيضًا في Grafana، حيث يمكن تصفيتها حسب الخدمة والمستوى والنص، راجع [إعداد أدوات التطوير](/ar/dev/environment/setup-develop-tools#grafana).

### أدوات أخرى {#other-tools}

بعد الانتهاء من كل ما سبق، يمكنك الرجوع إلى [القسم التالي](/ar/dev/environment/setup-develop-tools) لإضافة بعض أدوات تصحيح الأخطاء إلى بيئة تطوير overleaf الخاصة بك.
