تعمل الترجمة في بيئة معزولة بشكل مختلف قليلًا في بيئة التطوير عنها في صورة الإنتاج. بيئة التطوير مُعدّة لها مسبقًا؛ وتشرح هذه الصفحة الإعدادات وثلاثة أمور يجب مراعاتها:

* مشكلة أذونات الملفات
* مشاركة وحدة التخزين (Volume) بين history-v1 و filestore
* مشكلة المجلدات الفرعية

### تفعيل Sandbox Compiles {#enable-sandbox-compiles}

الترجمة في بيئة معزولة مفعّلة افتراضيًا. يضبط `develop/docker-compose.yml` القيمة `SANDBOXED_COMPILES=true` للخدمة `clsi`، ويحتوي `develop/dev.env` على الباقي:

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

لا يسحب clsi الصور بنفسه، لذا اسحب الصور مرة واحدة باستخدام `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1` (و`:2025.1`).

يعمل LaTeX في الحاويات الشقيقة بصفته `TEXLIVE_IMAGE_USER`. وفي بيئة التطوير يكون هذا المستخدم `tex`، وهو أيضًا القيمة الافتراضية لـ clsi (`services/clsi/config/settings.defaults.cjs:154`). أما صورة الإنتاج فتستخدم `www-data` بدلًا منه عندما يكون `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` (`server-ce/config/env.sh:15-21`)، لأن الملفات هناك يُنشئها المستخدم `www-data` في حاوية Overleaf.

<Warning>

يُرجى عدم استخدام صورة قمت ببنائها بنفسك، فقد تواجه سلسلة من الأخطاء.

</Warning>

### إصلاح أذونات الملفات {#fix-file-permissions}

تبدأ حاوية clsi بصفة root، وتمنح المجلدات `compiles` و`output` و`cache` للمستخدم `node` (uid `1000`)، ثم تشغّل clsi بصفة `node` (`services/clsi/entrypoint.sh`). لذلك يعود `develop/compiles` على المضيف إلى uid `1000`، وهو uid نفسه الخاص بـ `tex` في بيئة التطوير (راجع التعليق في `develop/pandoc/Dockerfile`). ومع الإعدادات أعلاه، تُترجم بيئة التطوير دون أي تغيير في الأذونات.

إذا ضبطت `TEXLIVE_IMAGE_USER=root` بدلًا من ذلك، فلن يكون لدى root (uid `0`) إذن الكتابة في المجلدات الفرعية لـ `compiles`. في هذه الحالة امنح المجموعة `root` ملكية `compiles` وإذن الكتابة فيه، مع ضبط `setgid` حتى ترث المجلدات الفرعية الجديدة هذه الملكية:

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

للاطلاع على التوثيق التفصيلي، يمكنك مراجعة `services/clsi/README.md`.

### مشاركة وحدة التخزين (Volume) بين history-v1 و filestore {#volume-share-between-history-v1-and-filestore}

<Info>

الإعدادات في هذا القسم والقسم التالي موجودة بالفعل في `develop/docker-compose.yml` و`develop/dev.env`. ولا تهم إلا مع `S3_ENABLED=false` في `develop/dev.rc`. ومع القيمة الافتراضية `S3_ENABLED=true` يحتفظ filestore وhistory-v1 بهذه الملفات في حاويات RustFS بدلًا من ذلك (`develop/s3/docker-compose.yml`).

</Info>

افتراضيًا، تعمل filestore كجسر بين s3 والخدمات الأخرى في overleaf. لكن في overleaf ce أو server pro، تُخزَّن جميع الملفات محليًا بشكل افتراضي. ولذلك اعتمدت overleaf طريقة ملتوية جدًا.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

وفي الوقت نفسه، تستخدم خدمة السجل أيضًا `data/history`. وبهذه الطريقة يمكن للخدمات المصغرة المختلفة مشاركة البيانات نفسها. ولهذا تربط خدمة filestore في develop وحدة التخزين `history-v1-buckets` الخاصة بـ history-v1. وبدونها **لن يتمكن clsi من سحب ملفات blob من خدمة filestore**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

يعثر filestore على الحاويات عبر هذه الإعدادات في `dev.env`:

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### استخدام المجلدات الفرعية {#use-subdirectories}

يقرأ filestore دائمًا كائنات blob الخاصة بالسجل باستخدام مجلدات فرعية (`services/filestore/app/js/KeyBuilder.js:58`، `:70`). تفعّل صورة الإنتاج `useSubdirectories` لـ history-v1 (`server-ce/config/production.json`)، لكن الإعداد الافتراضي لـ history-v1 لا يفعل ذلك، لذا في التطوير كان history-v1 <strong>سيُسطّح جميع البيانات.</strong> لهذا يضبط `dev.env` القيمة `NODE_CONFIG` لـ history-v1:&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

وبدونها يخزّن history-v1 ملفات `project_blobs` هكذا:

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

عند ضبط `useSubdirectories` على `true` يصبح `_` في هذه الأسماء `/`، فيُخزَّن كل blob في مجلدات فرعية.
