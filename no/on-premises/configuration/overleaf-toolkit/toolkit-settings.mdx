Denne siden beskriver miljøvariablene som støttes i `config/overleaf.rc`-filen for Toolkit-distribusjoner.

`config/overleaf.rc`-filen består av variabeldefinisjoner på formen `NAME=value`. Linjer som begynner med `#`, behandles som kommentarer.

<Info>

Du må gjenopprette Docker-containerne etter at du har endret noe i `overleaf.rc` eller `variables.env`, ved å kjøre `bin/up`.

</Info>

## Container

### `sharelatex`

| Navn                         | Beskrivelse |
| ---------------------------- | ----------- |
| `PROJECT_NAME`               | <p>Angir verdien til `--project-name`-flagget som sendes til `docker-compose`. Dette er nyttig når du kjører flere Overleaf-instanser på én vert, siden hver instans kan ha et eget prosjektnavn.<br /><br />- <strong>Standard</strong>: `overleaf`</p> |
| `OVERLEAF_IMAGE_NAME`        | <p>Docker-imaget som brukes av applikasjonscontaineren for Server Pro/CE. Dette er bare navnet på Docker-imaget; taggen til Docker-imaget hentes fra `config/version`.<br /><br />- <strong>Standard:</strong><br />- Server Pro: `quay.io/sharelatex/sharelatex-pro`<br />- Community Edition: `sharelatex/sharelatex`</p> |
| `SERVER_PRO`                 | <p>Når denne er satt til `true`, bruker Toolkit Server Pro-imaget (`quay.io/sharelatex/sharelatex-pro`) i stedet for standardimaget for Server CE (`sharelatex/sharelatex`).<br /><br />- <strong>Standard</strong>: `false`</p> |
| `GIT_BRIDGE_ENABLED`         | <p>Sett til `true` for å aktivere git-bridge-funksjonen (kun Server Pro). For mer informasjon, se brukerdokumentasjonen på <a href="https://www.overleaf.com/learn/how-to/Git_integration">https://www.overleaf.com/learn/how-to/Git_integration</a>.<br /><br />- <strong>Standard:</strong> `false`</p> |
| `GIT_BRIDGE_IMAGE`           | <p>Docker-imaget som brukes av git-bridge-containeren (kun Server Pro). Dette er bare navnet på Docker-imaget; taggen til Docker-imaget hentes fra `config/version`.<br /><br />- <strong>Standard:</strong> `quay.io/sharelatex/git-bridge`</p> |
| `GIT_BRIDGE_DATA_PATH`       | Angir stien til katalogen som monteres inn i `git-bridge`-containeren (kun Server Pro) og brukes til å lagre git-repositoriene. Dette kan være enten en fullstendig sti (som begynner med `/`) eller en sti relativt til Toolkits basiskatalog. |
| `GIT_BRIDGE_LOG_LEVEL`       | <p>Konfigurerer loggnivået for `git-bridge`-containeren. Tilgjengelige nivåer: `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`.<br /><br />- <strong>Standard:</strong> `INFO`</p> |
| `SIBLING_CONTAINERS_ENABLED` | <p>Når denne er satt til `true`, bruker Toolkit teknikken <strong>Sibling Containers</strong> for å kompilere prosjekter i separate sandkasser, med en egen Docker-container for hvert prosjekt. Se dokumentasjonen &#x3C;server-pro-only-configuration/sandboxed-compiles> for mer informasjon.<br /><br />- <strong>Krever:</strong> `SERVER_PRO=true`<br />- <strong>Standard:</strong> `true`</p> |
| `SIBLING_CONTAINERS_PULL`    | <p>Når denne er satt til `true`, henter Toolkit automatisk alle TeX Live-imager som er angitt med `ALL_TEX_LIVE_DOCKER_IMAGES` i <strong>config/variables.env</strong>-filen, når kommandoen `bin/up` brukes.<br /><br />- <strong>Standard:</strong> `true`</p> |
| `DOCKER_SOCKET_PATH`         | <p>Angir stien til Docker-socketen på vertsmaskinen (maskinen som kjører Toolkit). Når `SIBLING_CONTAINERS_ENABLED` er `true`, monteres socketen inn i containeren slik at kompilatortjenesten kan starte nye Docker-containere på verten.<br /><br />- <strong>Krever:</strong> `SIBLING_CONTAINERS_ENABLED=true`<br />- <strong>Standard:</strong> `/var/run/docker.sock`</p> |
| `OVERLEAF_DATA_PATH`         | <p>Angir stien til katalogen som monteres inn i hovedcontaineren `sharelatex` og brukes til å lagre kompileringsdata. Dette kan være enten en fullstendig sti (som begynner med `/`) eller en sti relativt til Toolkits basiskatalog.<br /><br />- <strong>Standard:</strong> `data/overleaf`</p> |
| `OVERLEAF_LISTEN_IP`         | <p>Angir IP-adressen(e) på verten som containeren skal binde seg til. Hvis denne for eksempel er satt til `0.0.0.0`, blir nettgrensesnittet tilgjengelig på alle vertens IP-adresser. For direkte tilgang til containeren må verdien av `OVERLEAF_LISTEN_IP` settes til den offentlige IP-adressen din. Å sette `OVERLEAF_LISTEN_IP` til enten `0.0.0.0` eller vertens eksterne IP vil vanligvis føre til feil når det brukes sammen med .<br /><br />- <strong>Standard:</strong> `127.0.0.1`</p> |
| `OVERLEAF_PORT`              | <p>Angir porten på verten som containeren skal binde seg til. Hvis denne for eksempel er satt til `8099` og `OVERLEAF_LISTEN_IP` er satt til `127.0.0.1`, blir nettgrensesnittet tilgjengelig på `http://localhost:8099`.<br /><br />- <strong>Standard:</strong> `80`</p> |
| `OVERLEAF_LOG_PATH`          | <p>Angir stien til katalogen som monteres inn i hovedcontaineren `sharelatex` og brukes til å gjøre applikasjonslogger tilgjengelige på Docker-verten. Dette kan være enten en fullstendig sti (som begynner med `/`) eller en sti relativt til Toolkits basiskatalog. Fjern konfigurasjonsoppføringen for å deaktivere bind-monteringen. Når den ikke er satt, forkastes loggene når containeren gjenopprettes.<br /><br />Se for informasjon om logging.<br /><br />- <strong>Standard:</strong> ikke satt</p> |

### `mongo`

| Navn              | Beskrivelse |
| ----------------- | ----------- |
| `MONGO_ENABLED`   | <p>Når denne er satt til `true`, oppretter Toolkit en MongoDB-container som er vert for databasen. Når den er satt til `false`, opprettes ikke denne containeren, og systemet bruker i stedet MongoDB-databasen som er angitt med `MONGO_URL`.<br /><br />- <strong>Standard</strong>: `true`</p> |
| `MONGO_URL`       | <p>Angir tilkoblings-URL-en til MongoDB som skal brukes når `MONGO_ENABLED` er `false`.<br /><br />- <strong>Standard</strong>: ikke satt</p> |
| `MONGO_DATA_PATH` | <p>Angir stien til katalogen som monteres inn i `mongo`-containeren og brukes til å lagre MongoDB-databasen. Dette kan være enten en fullstendig sti (som begynner med `/`) eller en sti relativt til Toolkits basiskatalog. Dette alternativet påvirker bare den lokale `mongo`-containeren som opprettes når `MONGO_ENABLED` er `true`.<br /><br />- <strong>Standard</strong>: `data/mongo`</p> |
| `MONGO_IMAGE`     | <p>Docker-imaget som brukes av MongoDB-containeren. Dette er bare navnet på Docker-imaget; taggen til Docker-imaget skal settes i `MONGO_VERSION` (se nedenfor).<br /><br />- <strong>Standard:</strong> `mongo`</p> |
| `MONGO_VERSION`   | <p>MongoDB-versjonen som brukes av MongoDB-containeren. Verdien må begynne med hovedversjonen av MongoDB og et punktum, f.eks. `6.0` eller `6.0-with-suffix`.<br /><br />- <strong>Standard:</strong> `6.0`</p> |

### `redis`

| Navn                    | Beskrivelse |
| ----------------------- | ----------- |
| `REDIS_ENABLED`         | <p>Når denne er satt til `true`, oppretter Toolkit en Redis-container som er vert for Redis-databasen. Når den er satt til `false`, opprettes ikke denne containeren, og systemet bruker i stedet Redis-databasen som er angitt med `REDIS_HOST` og `REDIS_PORT`.<br /><br />- <strong>Standard</strong>: `true`</p> |
| `REDIS_HOST`            | <p>Angir Redis-verten som skal brukes når `REDIS_ENABLED` er `false`.<br /><br />- <strong>Standard</strong>: ikke satt</p> |
| `REDIS_PORT`            | <p>Angir Redis-porten som skal brukes når `REDIS_ENABLED` er `false`.<br /><br />- <strong>Standard</strong>: ikke satt</p> |
| `REDIS_DATA_PATH`       | <p>Angir stien til katalogen som monteres inn i `redis`-containeren og brukes til å lagre Redis-databasen. Dette kan være enten en fullstendig sti (som begynner med `/`) eller en sti relativt til Toolkits basiskatalog. Dette alternativet påvirker bare den lokale `redis`-containeren som opprettes når `REDIS_ENABLED` er `true`.<br /><br />- <strong>Standard</strong>: `data/redis`</p> |
| `REDIS_AOF_PERSISTENCE` | <p>Slår på AOF-persistens (Append Only File) for Redis. Dette er den <strong>anbefalte</strong> konfigurasjonen for Redis-persistens.<br /><br />For mer informasjon, se avsnittet &#x3C;../../../maintenance/data-and-backups#aof-append-only-file> i &#x3C;../../maintenance/data-and-backups>.<br /><br />- <strong>Standard:</strong> `true`</p> |

***

### `nginx`

| Navn                   | Beskrivelse |
| ---------------------- | ----------- |
| `NGINX_ENABLED`        | <p>Når denne er satt til `true`, oppretter Toolkit en NGINX-container som fungerer som TLS-proxy.<br /><br />- <strong>Standard</strong>: `false`</p> |
| `NGINX_CONFIG_PATH`    | <p>Sti til NGINX-konfigurasjonsfilen som skal brukes for TLS-proxyen.<br /><br />- <strong>Standard</strong>: `config/nginx/nginx.conf`</p> |
| `NGINX_TLS_LISTEN_IP`  | <p>Angir IP-adressen(e) på verten som TLS-proxycontaineren skal binde seg til for HTTPS. Hvis denne for eksempel er satt til `0.0.0.0`, blir HTTPS-nettgrensesnittet tilgjengelig på alle vertens IP-adresser. Vanligvis bør denne settes til vertens eksterne IP.<br /><br />- <strong>Standard</strong>: `127.0.1.1`</p> |
| `NGINX_HTTP_LISTEN_IP` | <p>Angir IP-adressen(e) på verten som TLS-proxycontaineren skal binde seg til for HTTP-omdirigering. Hvis denne for eksempel er satt til `127.0.1.1`, blir HTTP-tilkoblinger til `127.0.1.1` omdirigert til HTTPS-nettgrensesnittet. Vanligvis bør denne settes til vertens eksterne IP. Ikke sett den til `0.0.0.0`, da dette vanligvis vil føre til konflikt med `OVERLEAF_LISTEN_IP`.<br /><br />- <strong>Standard</strong>: `127.0.1.1`</p> |
| `NGINX_HTTP_PORT`      | <p>Angir porten på verten som TLS-proxycontaineren skal binde seg til for HTTP.<br /><br />- <strong>Standard</strong>: `80`</p> |
| `TLS_PORT`             | <p>Angir porten på verten som TLS-proxycontaineren skal binde seg til for HTTPS.<br /><br />- <strong>Standard</strong>: `443`</p> |
| `TLS_PRIVATE_KEY_PATH` | <p>Sti til den private nøkkelen som skal brukes for TLS-proxyen.<br /><br />- <strong>Standard</strong>: `config/nginx/certs/overleaf_key.pem`</p> |
| `TLS_CERTIFICATE_PATH` | <p>Sti til det offentlige sertifikatet som skal brukes for TLS-proxyen.<br /><br />- <strong>Standard</strong>: `config/nginx/certs/overleaf_certificate.pem`</p> |
