### Opprett administratoren og et første prosjekt {#create-the-administrator-and-a-first-project}

Åpne [http://localhost:8080/launchpad](http://localhost:8080/launchpad) i **nettleseren i Windows**, opprett den første administratorkontoen og logg inn. Følg deretter [6. Oppgaver etter installasjon](/no/on-premises/installation/using-docker-compose/linux/6.-post-installation-tasks) i Linux-veiledningen, og bruk port `8080` i eksempel-URL-ene der.

### Bekreft kompilering {#verify-compilation}

At en påloggingsside fungerer, beviser ikke at de separate kompilatorcontainerne har tilgang til WSL-datamappen. Opprett et tomt prosjekt og kompiler denne `main.tex` med **pdfLaTeX**:

```latex
\documentclass{article}
\begin{document}
Ayakaleaf Pro on Windows WSL 2.
\end{document}
```

PDF-forhåndsvisningen skal vise teksten. For basic-imaget velger du om nødvendig **TeX Live 2026 Basic** i prosjektinnstillingene.

Velg **XeLaTeX** og test:

```latex
\documentclass{article}
\usepackage{fontspec}
\begin{document}
Ayakaleaf WSL XeLaTeX sandbox.
\end{document}
```

Begge eksemplene fungerer med basic. For kinesiske dokumenter bruker du et image som inneholder `ctex` og de nødvendige skriftene, for eksempel full, før du tester følgende med **XeLaTeX**. Basic inneholder dem ikke:

```latex
\documentclass{ctexart}
\begin{document}
你好，Ayakaleaf Pro。
\end{document}
```

For å bekrefte at sandkassen brukes, kjører du dette i **Ubuntu** mens du kompilerer:

```bash
docker ps -a --filter ancestor=ghcr.io/ayaka-notes/texlive-basic:2026.1
bin/logs -f clsi
```

Bruk navnet på imaget du valgte, i filteret. Korte kompileringer kan bli ferdige før `docker ps` kjører; `-a` viser også stoppede containere inntil de ryddes bort. En kompilatorcontainer skal bruke det imaget og en `/compile`-bind-montering fra Toolkits WSL-datamappe. Applikasjonslogger alene erstatter ikke en sjekk av PDF-en.

### Bekreft varig lagring {#verify-persistence}

I **Ubuntu**, fra Toolkit-mappen:

```bash
bin/stop
bin/start
```

Vent på applikasjonen, åpne prosjektet igjen fra Windows og kompiler på nytt. Kontoen din, kildekoden og prosjektfilene skal fortsatt være der. De aktive dataene ligger som standard i `~/ayakaleaf-toolkit/data/` i Ubuntu. Ta vare på både `config/` og `data/`; avinstallering eller avregistrering av Ubuntu-distribusjonen kan slette dem.

### Hold instansen tilgjengelig {#keep-the-instance-available}

Det er tre deler ved å holde instansen i gang: Windows holdes våken, Docker Desktop kjører, og containerne starter på nytt sammen med motoren.

I **Settings → General** i Docker Desktop slår du på **Start Docker Desktop when you sign in to your computer**, se [Docker Desktop-innstillinger](https://docs.docker.com/desktop/settings-and-maintenance/settings/). Dette starter Docker etter pålogging, ikke før pålogging. Etter en omstart av Windows logger du inn, venter til Docker Desktop har startet ferdig, åpner Ubuntu og sjekker `docker ps` og nettstedet.

**Resource Saver** i Docker Desktop er atskilt fra dvale i Windows. Den aktiveres normalt bare når ingen containere kjører; den kjørende applikasjonen, MongoDB og Redis forhindrer denne inaktive tilstanden. På WSL 2 setter den Docker-motoren på pause i stedet for å slå av den delte WSL-VM-en. Ikke sett Docker Desktop på **Pause** manuelt mens du betjener brukere. Du trenger ikke å deaktivere Resource Saver bare for å holde denne stakken i gang; se [Dockers dokumentasjon om Resource Saver](https://docs.docker.com/desktop/use-desktop/resource-saver/).

Toolkit-tjenestene bruker `restart: always`. Bekreft den faktiske innstillingen i **Ubuntu**:

```bash
docker inspect sharelatex mongo redis --format '{{.Name}} restart={{.HostConfig.RestartPolicy.Name}}'
```

Hver tjeneste skal rapportere `always`. Når Docker kjører, kan den starte disse eksisterende containerne på nytt uten en ny `bin/up`. En container som er stoppet manuelt, forblir stoppet til du starter den eller starter motoren på nytt; med `always` kan en omstart av motoren starte den igjen. Se [Dockers virkemåte for omstartspolicyer](https://docs.docker.com/engine/containers/start-containers-automatically/).

| Handling | Virkning på Ayakaleaf |
| --- | --- |
| Lukk Ubuntu-terminalen etter `bin/up -d` | Containerne kjører frakoblet; terminalen er ikke det som holder dem i gang. Sørg for at Docker Desktop og WSL-miljøet forblir tilgjengelige |
| Lukk vinduet Docker Dashboard | Vinduet kan lukkes mens Docker Desktop fortsetter i systemstatusfeltet |
| Velg **Quit Docker Desktop** | Stopper motoren og gjør nettstedet utilgjengelig; åpne Docker Desktop igjen for å gjenopprette |
| Kjør `wsl --shutdown` | Stopper alle WSL-distribusjoner og avbryter Docker WSL-backenden; start Docker Desktop på nytt og åpne Ubuntu igjen |
| Sett Windows i dvale, dvalemodus eller slå det av | Tjenesten er utilgjengelig; å bare la skjermen være på eller av endrer ikke dette |
| Kjør `bin/stop` | Stopper instansen og beholder dataene; bruk `bin/start` for å fortsette |

For langvarig bruk på strømnettet åpner du **Settings → System → Power & battery → Screen, sleep & hibernate timeouts** i Windows 11 (noen versjoner viser **Power** eller **Screen and sleep**). Sett tidsavbruddet for dvale ved tilkoblet strøm til **Never**, og deaktiver automatisk dvalemodus hvis det er konfigurert. Skjermen kan fortsatt slå seg av. Hva som skjer når du lukker lokket på en bærbar PC, er en egen innstilling; å lukke lokket kan sette den i dvale selv med tidsavbrudd for dvale satt til Never. Se [Strøminnstillinger i Windows](https://support.microsoft.com/en-us/windows/experience/power-battery/power-settings-in-windows-11).

Ikke kjør `wsl --shutdown` som rutinemessig opprydding mens nettstedet er i bruk. Hvis en endring av WSL-innstillinger krever det, stopper du instansen først og planlegger et avbrudd. Windows kan kjøre instansen kontinuerlig med disse innstillingene. For en delt tjeneste som må overleve utlogginger og omstarter uten tilsyn, anbefaler vi [Linux-veiledningen](/no/on-premises/installation/using-docker-compose/linux).

### Sjekk gjenoppretting etter omstart av Docker Desktop {#check-recovery-after-restarting-docker-desktop}

Etter at du har lagret arbeidet og latt aktive kompileringer bli ferdige, velger du **Restart Docker Desktop** fra feilsøkingsmenyen i Docker Desktop. Vent på motoren, og sjekk deretter i **Ubuntu**:

```bash
docker ps
curl -I http://localhost:8080/launchpad
```

Åpne det eksisterende prosjektet i Windows og kompiler det på nytt. Bekreft at kontoen og kildekoden fortsatt finnes.

Hvis du med vilje stoppet instansen med `bin/stop`, bruker du `bin/start`. Hvis Docker kjører, men en tjeneste feiler, leser du loggene i stedet for å gjenopprette konfigurasjonen. Windows Update, Docker-oppdateringer og strømbrudd kan fortsatt avbryte en installasjon som kjører døgnet rundt; ta sikkerhetskopier og sjekk gjenopprettingen etter planlagt vedlikehold.

### Daglig bruk {#daily-use}

Start Docker Desktop i Windows. Åpne **Ubuntu**:

```bash
cd "$HOME/ayakaleaf-toolkit"
```

| Oppgave | Kommando |
| --- | --- |
| Start eksisterende containere | `bin/start` |
| Stopp containere og behold data | `bin/stop` |
| Ta i bruk konfigurasjonsendringer | `bin/up -d` |
| Sjekk status | `bin/docker-compose ps` |
| Les oppstartslogger | `bin/docker-compose logs --tail=100 sharelatex` |
| Les MongoDB-logger | `bin/docker-compose logs --tail=100 mongo` |
| Les kompilatorlogger | `bin/logs -f clsi` |

`bin/start` tar ikke i bruk konfigurasjonsendringer: bruk `bin/up -d` etter at du har endret `config/`. Følg [Data og sikkerhetskopier](/no/on-premises/maintenance/data-and-backups) før du oppgraderer, flytter eller fjerner WSL-distribusjonen. Å kopiere aktive MongoDB-filer mens databasen skriver, gir ikke en konsistent sikkerhetskopi.

Behold `127.0.0.1` for lokal bruk. For å betjene andre datamaskiner kreves det også en bevisst valgt lytteadresse, nettstedets URL, konfigurasjon av Windows-brannmur/nettverk og HTTPS; å endre bare `OVERLEAF_SITE_URL` publiserer ikke en port.

Hvis noe ikke fungerer, se [Feilsøking](/no/on-premises/installation/using-docker-compose/windows/troubleshooting).
