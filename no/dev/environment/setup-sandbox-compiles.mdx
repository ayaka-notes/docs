Sandkassekompileringer fungerer litt annerledes i utviklingsmiljøet enn i produksjonsimaget. Utviklingsmiljøet har dem allerede satt opp; denne siden forklarer innstillingene og tre ting du bør være oppmerksom på:

* Problem med filtillatelser
* Delt volum mellom history-v1 og filestore
* Problem med underkataloger

### Aktiver Sandbox Compiles {#enable-sandbox-compiles}

Sandkassekompileringer er på som standard. `develop/docker-compose.yml` setter `SANDBOXED_COMPILES=true` for `clsi`, og `develop/dev.env` inneholder resten:

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

clsi henter ikke images selv, så hent imagene én gang med `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1` (og `:2025.1`).

LaTeX kjører i søskencontainerne som `TEXLIVE_IMAGE_USER`. I utviklingsmiljøet er dette `tex`, som også er standard for clsi (`services/clsi/config/settings.defaults.cjs:154`). Produksjonsimaget bruker i stedet `www-data` når `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` (`server-ce/config/env.sh:15-21`), fordi filene der opprettes av brukeren `www-data` i Overleaf-containeren.

<Warning>

Ikke bruk et image du har bygget selv, da kan du støte på en rekke feil.

</Warning>

### Rett opp filtillatelser {#fix-file-permissions}

clsi-containeren starter som root, gir mappene `compiles`, `output` og `cache` til brukeren `node` (uid `1000`) og kjører deretter clsi som `node` (`services/clsi/entrypoint.sh`). Derfor tilhører `develop/compiles` på verten uid `1000`, samme uid som `tex` i utviklingsmiljøet (se kommentaren i `develop/pandoc/Dockerfile`). Med innstillingene over kompilerer utviklingsmiljøet uten noen endring av tillatelser.

Hvis du i stedet setter `TEXLIVE_IMAGE_USER=root`, har root (uid `0`) ikke tillatelse til å skrive til undermappene i `compiles`. Gi i så fall gruppen `root` eierskap og skrivetilgang til `compiles`, med `setgid` satt slik at nye undermapper arver dette eierskapet:

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

For mer detaljert dokumentasjon, se `services/clsi/README.md`.

### Delt volum mellom history-v1 og filestore {#volume-share-between-history-v1-and-filestore}

<Info>

Innstillingene i denne og neste del finnes allerede i `develop/docker-compose.yml` og `develop/dev.env`. De har bare betydning med `S3_ENABLED=false` i `develop/dev.rc`. Med standardverdien `S3_ENABLED=true` lagrer filestore og history-v1 i stedet disse filene i RustFS-buckets (`develop/s3/docker-compose.yml`).

</Info>

Som standard fungerer filestore som en bro mellom S3 og andre tjenester i Overleaf. I Overleaf CE eller Server Pro lagres imidlertid alle filer lokalt som standard. Derfor har Overleaf innført en ganske innviklet metode.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

Samtidig brukes `data/history` også av historikktjenesten. På denne måten kan ulike mikrotjenester dele de samme dataene. Derfor monterer filestore-tjenesten i develop volumet `history-v1-buckets` fra history-v1. Uten det **kan ikke clsi hente blob-filer fra filestore-tjenesten**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

filestore finner bucketene gjennom disse innstillingene i `dev.env`:

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### Bruk underkataloger {#use-subdirectories}

filestore leser alltid historikkblobber med underkataloger (`services/filestore/app/js/KeyBuilder.js:58`, `:70`). Produksjonsimaget slår på `useSubdirectories` for history-v1 (`server-ce/config/production.json`), men standardkonfigurasjonen til history-v1 gjør det ikke, så i utvikling ville history-v1 <strong>flate ut alle dataene.</strong> Derfor setter `dev.env` `NODE_CONFIG` for history-v1:&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

Uten den lagrer history-v1 `project_blobs`-filene slik:

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

Når `useSubdirectories` er satt til `true`, blir `_` i disse navnene til `/`, slik at hver blob lagres i undermapper.
