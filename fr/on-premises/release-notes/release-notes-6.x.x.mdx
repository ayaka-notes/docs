## Ayakaleaf Pro 6.3.2

<strong>Date de sortie :</strong> 2026.10.23

Voir : [https://github.com/ayaka-notes/ayakaleaf-pro/releases/tag/pro-v6.3.2](https://github.com/ayaka-notes/ayakaleaf-pro/releases/tag/pro-v6.3.2)

Nous sommes très fiers d'annoncer la sortie d'Overleaf Pro 6.3.2. L'Overleaf 6.3.2 en amont est une version de sécurité qui met à jour Node.js, et nous la livrons avec la synchronisation Gitea et les corrections de bugs découverts depuis la 6.3.1.

<Info>

La synchronisation Gitea est livrée dans la 6.3.2 en **avant-première** pour des tests progressifs, et sera officiellement publiée dans la v6.4.0. Sa configuration et son comportement peuvent encore évoluer d'ici là. Elle est désactivée par défaut. Veuillez signaler tout problème sur [GitHub](https://github.com/ayaka-notes/ayakaleaf-pro/issues).

</Info>

### Modifications

* Synchronisation Gitea bidirectionnelle (avant-première), pour gitea.com et Gitea autogéré 1.23+.
* Node.js 24.22.1, la mise à jour de sécurité de l'Overleaf 6.3.2 en amont.
* Corrections de bugs détectés par notre système de tests E2E et par l'Internal Horizon Issue Investigation.

#### Fonctionnalité 01 : synchronisation Gitea (avant-première)

Synchronisation bidirectionnelle avec Gitea, de la même manière que la synchronisation GitHub et la synchronisation GitLab : liez votre compte, importez un dépôt depuis le menu de nouveau projet, exportez un projet, poussez et récupérez les modifications, et fusionnez via des pull requests. Overleaf ne contourne jamais la protection de branche du dépôt. Consultez [Synchronisation Gitea](/fr/on-premises/configuration/overleaf-toolkit/gitea-synchronisation).

### Corrections de bugs

* Synchronisation GitHub, GitLab et Gitea : lorsqu'un fichier supprimé dans le dépôt ne peut pas être supprimé dans Overleaf, la synchronisation échoue et peut être relancée, au lieu de signaler un succès et de laisser le fichier dans le projet. Un `git push` qui supprime un fichier échoue de la même manière ([#121](https://github.com/ayaka-notes/ayakaleaf-pro/issues/121)).
* Git bridge : un document créé dans l'éditeur avec une extension non textuelle (comme `.csv`) reste un document modifiable lorsqu'un `git push` le modifie.
* Suivi des modifications : les éditeurs non connectés d'un projet partagé par lien peuvent supprimer des fils de commentaires, mais ne peuvent plus les résoudre ni les rouvrir. Les relecteurs peuvent supprimer leurs propres réponses.
* Galerie de modèles : la publication d'un modèle nécessite un accès au projet.
* Learn : les pages d'aide en cache restent disponibles lorsque le wiki est inaccessible.

### Mise à niveau

* Depuis la 6.3.1 ou la 6.3.0 : aucune migration n'est nécessaire. Téléchargez la nouvelle image et redémarrez.
* Depuis la 6.2.x ou une version antérieure avec Zotero ou Mendeley en service : exécutez d'abord la migration Zotero / Mendeley de la [6.3.0](#ayakaleaf-pro-6.3.0).
* La synchronisation Gitea est désactivée par défaut et ne nécessite que de nouvelles variables d'environnement.

<strong>Date de sortie :</strong> 2026.10.18

#### Fonctionnalité 01 : synchronisation Dropbox (avant-première)

Chaque utilisateur lie son propre compte Dropbox, et les projets dont il est propriétaire ou qui sont partagés avec lui apparaissent sous `Apps/<DROPBOX_APP_NAME>/`. Les modifications effectuées dans Overleaf sont envoyées vers Dropbox, et celles effectuées dans Dropbox reviennent via un webhook signé. Le Git bridge doit être activé. Voir [Synchronisation Dropbox](/fr/on-premises/configuration/overleaf-toolkit/dropbox-synchronisation).

#### Fonctionnalité 02 : synchronisation GitLab (avant-première)

Synchronisation bidirectionnelle avec GitLab, sur le même principe que la synchronisation GitHub : liez votre compte, importez un dépôt depuis le menu de nouveau projet, exportez un projet, poussez et récupérez les modifications, et fusionnez via des merge requests. Voir [Synchronisation GitLab](/fr/on-premises/configuration/overleaf-toolkit/gitlab-synchronisation).

### Corrections de bugs

* Authentification : les comptes locaux peuvent définir et modifier leur mot de passe sur les instances SSO, et les utilisateurs OIDC ne peuvent plus modifier leur propre adresse e-mail ([#112](https://github.com/ayaka-notes/ayakaleaf-pro/pull/112)). Les méthodes de connexion LDAP, SAML et OIDC sont préservées, et la déconnexion SAML/OIDC fonctionne de nouveau. Voir [Comptes et mots de passe](/fr/on-premises/configuration/overleaf-toolkit/authentication#accounts-and-passwords).
* LDAP, SAML et OIDC : les attributs de nom à plusieurs valeurs (comme `cn`) ne font plus échouer la connexion, et les adresses e-mail OIDC sont converties en minuscules comme pour LDAP et SAML, de sorte qu'un compte dont l'IdP envoie l'adresse e-mail avec une casse différente est lié au lieu d'échouer.
* Utilisateurs suspendus : suspendre un utilisateur met fin à ses sessions et ferme ses éditeurs ouverts. Ses jetons Git et ses téléchargements MCP sont refusés.
* Synchronisation GitHub : seul le propriétaire peut exporter un projet, les modifications effectuées pendant une récupération restent en attente, les fichiers vides sont synchronisés, les fusions manuelles sont vérifiées sur GitHub, et un jeton remplacé est révoqué lors d'une nouvelle liaison.
* Zotero / Mendeley : un message invitant à refaire la liaison s'affiche lorsque les identifiants ne fonctionnent plus, et les références sont réindexées après un import.
* Les requêtes vers les API externes (Zotero, Mendeley, GitHub, GitLab, recherche web) bénéficient d'un délai de connexion de 3 s au lieu de 1 s ([#106](https://github.com/ayaka-notes/ayakaleaf-pro/pull/106)).
* Suivi des modifications : les données de relecture incluent les documents non chargés et les modifications non enregistrées (issu de [yu-i-i/overleaf-cep#262](https://github.com/yu-i-i/overleaf-cep/pull/262)).
* Assistant d'erreurs : ne propose des corrections que pour les documents du projet ([#103](https://github.com/ayaka-notes/ayakaleaf-pro/pull/103)).
* Panneau d'administration : la restauration d'un projet supprimé, le changement de propriétaire et la modification des utilisateurs fonctionnent correctement. La recherche utilise le texte littéral, et l'échec d'un e-mail n'empêche plus la création ou la suppression d'un compte.
* Galerie de modèles : un tri non valide renvoie 400 au lieu de 500, les identifiants de modèles sont validés, et la publication d'un projet sans fichier principal en demande un.
* Git bridge : nginx redirige `/git/` vers `GIT_BRIDGE_HOST` et `GIT_BRIDGE_PORT`, et les routes internes sont masquées.
* Compilations en sandbox : les conteneurs des projets récemment compilés sont conservés pour être réutilisés.

### Mise à niveau

* Depuis la 6.3.0 : aucune migration n'est nécessaire. Téléchargez la nouvelle image et redémarrez.
* Depuis la 6.2.x ou une version antérieure avec Zotero ou Mendeley en service : exécutez d'abord la migration Zotero / Mendeley de la [6.3.0](#ayakaleaf-pro-6.3.0).

La synchronisation Dropbox nécessite en outre que ses index MongoDB soient créés une fois, avant que les utilisateurs ne lient leurs comptes : voir [Créer les index de la base de données](/fr/on-premises/configuration/overleaf-toolkit/dropbox-synchronisation#create-the-database-indexes).

<Accordion title="Migration Zotero / Mendeley pour les installations existantes">

Lors de la mise à niveau vers l'image 6.3.0 republiée, migrez les métadonnées existantes des bibliographies liées à Zotero/Mendeley à l'aide du script ci-dessous. Cette migration accompagne le correctif `12031b8dfd`.

Elle renomme `zoteroGroupId` / `mendeleyGroupId` en `group_id`, renomme `importedByUserId` en `importer_id` et supprime `importedByName`.

Sauvegardez MongoDB et arrêtez l'application avant d'exécuter la migration. Laissez MongoDB en fonctionnement. Ouvrez son shell (remplacez `mongo` par le nom de votre conteneur) :

```bash
docker exec -it mongo mongosh
```

Exécutez ce qui suit dans `mongosh` (remplacez `sharelatex` par le nom de votre base de données) :

```javascript
use sharelatex

(async () => {
  let updated = 0
  await db.projects.find({}, { rootFolder: 1 }).forEach(async project => {
    const changes = {}
    function visit(folders, path) {
      for (const [i, folder] of (folders || []).entries()) {
        const folderPath = `${path}.${i}`
        for (const [j, file] of (folder.fileRefs || []).entries()) {
          const data = { ...file.linkedFileData }
          if (!["zotero", "mendeley"].includes(data.provider)) continue
          const groupKey = `${data.provider}GroupId`
          if (![groupKey, "importedByUserId", "importedByName"].some(key => key in data)) continue
          for (const [oldKey, newKey] of [[groupKey, "group_id"], ["importedByUserId", "importer_id"]]) {
            if (data[oldKey] != null && data[oldKey] !== "") {
              const value = String(data[oldKey])
              if (newKey in data && data[newKey] !== value) {
                throw new Error(`Conflicting ${newKey}: project ${project._id}, file ${file._id}`)
              }
              data[newKey] = value
            }
            delete data[oldKey]
          }
          delete data.importedByName
          changes[`${folderPath}.fileRefs.${j}.linkedFileData`] = data
        }
        visit(folder.folders, `${folderPath}.folders`)
      }
    }
    visit(project.rootFolder, "rootFolder")
    if (!Object.keys(changes).length) return
    const result = await db.projects.updateOne(
      { _id: project._id, rootFolder: { $eq: project.rootFolder } },
      { $set: changes }
    )
    if (!result.matchedCount) throw new Error(`Project changed during migration: ${project._id}`)
    updated += result.modifiedCount
  })
  print(`Updated ${updated} project(s).`)
})()
```

Le script prend en compte les dossiers imbriqués et ne modifie que les métadonnées Zotero/Mendeley. Il peut être réexécuté sans risque : une migration terminée affiche `Updated 0 project(s).` à l'exécution suivante. S'il s'arrête sur un conflit, examinez le projet/fichier signalé ; les projets précédents ont peut-être déjà été migrés.

Démarrez l'application mise à jour, rechargez l'éditeur et actualisez un fichier de bibliographie existant en tant qu'utilisateur l'ayant importé à l'origine. Les instantanés historiques ne sont pas réécrits. Pour revenir à l'ancienne application, restaurez la sauvegarde MongoDB.

</Accordion>

#### Fonctionnalité 04 : pagination des modèles

La galerie effectue désormais la pagination, le tri et la recherche dans MongoDB. Elle fonctionne sans aucune préparation ; avec des milliers de modèles, vous pouvez néanmoins ajouter ces index pour qu'elle reste rapide (réexécution sans risque, `mongo`/`sharelatex` = noms de votre conteneur et de votre base de données) :

```bash
docker exec mongo mongosh sharelatex --quiet --eval '
db.templates.createIndex({category:1,lastUpdated:-1},{name:"category_1_lastUpdated_-1",background:true});
db.templates.createIndex({lastUpdated:-1},{name:"lastUpdated_-1",background:true});
db.templates.createIndex({category:1,name:1},{name:"category_1_name_1_ci",collation:{locale:"en",strength:2},background:true});
db.templates.createIndex({name:1},{name:"name_1_ci",collation:{locale:"en",strength:2},background:true});
'
```

Conservez la `collation` des deux index `*_ci` telle qu'écrite — la galerie interroge avec la même collation, et MongoDB n'utilise qu'un index correspondant.
