<Accordion title="Exécuter Overleaf avec un système de fichiers NFS">

Monter un système de fichiers NFS dans un conteneur Overleaf est techniquement possible, mais ce n'est pas recommandé et cela peut entraîner différents types d'erreurs de performance.

Une erreur fréquente lors des compilations est la suivante :

```text
EBUSY: resource busy or locked, unlink '/var/lib/overleaf/data/compiles/62f3d57bef7cf9005c364e75-62f3d57bef7cf9005c364e7a/.nfs573663533034825247625441'
```

Nous déconseillons en particulier l'utilisation de systèmes de fichiers reposant sur NFS pour les données éphémères, comme les répertoires utilisés pour les données de compilation. Nous recommandons d'utiliser un disque de travail local, de préférence un SSD local, pour les répertoires suivants.

Pour les installations basées sur `docker-compose`, nous suggérons simplement de remplacer le montage depuis NFS, ce qui évite de modifier les chemins dans l'application. Voici un extrait de configuration `docker-compose` utilisant un disque de travail monté sur `/scratch` :

```yaml title="docker-compose excerpt"
services:
  sharelatex:
    environment:
      SANDBOXED_COMPILES_HOST_DIR: /scratch/compiles/
    volumes:
      - nfs:/var/lib/overleaf/data
      - /scratch/cache/:/var/lib/overleaf/data/cache
      - /scratch/compiles/:/var/lib/overleaf/data/compiles
      - /scratch/output/:/var/lib/overleaf/data/output
      - /scratch/tmp/:/var/lib/overleaf/tmp
```

Il n'est pas nécessaire de migrer les fichiers existants depuis le NFS vers leur nouvel emplacement après la mise à jour. Le compilateur LaTeX peut recréer tous les fichiers lors d'une nouvelle compilation complète.

Pour plus de détails, consultez : https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-with-an-nfs-filesystem

</Accordion>

<Accordion title="Le service `mongo` ne démarre pas lorsque Overleaf est exécuté sous Windows ou macOS">

Si vous exécutez Overleaf sous Windows ou macOS, le service `mongo` peut ne pas redémarrer, avec l'erreur suivante :

```text title="Example error"
Failed to start up WiredTiger under any compatibility version.
Reason: 1: Operation not permitted
```

Pour éviter cette erreur, les données doivent être stockées dans un volume plutôt que dans un répertoire monté par bind mount (consultez la documentation de l'image `mongo` pour plus de détails : https://github.com/docker-library/docs/blob/master/mongo/content.md#where-to-store-data). Pour stocker les données dans des volumes Docker montés dans les conteneurs MongoDB et Redis, ajoutez ce qui suit à `config/docker-compose.override.yml` (créez ce fichier s'il n'existe pas encore) :

```yaml title="config/docker-compose.override.yml"
volumes:
  mongo-data:
  redis-data:

services:
  mongo:
    volumes:
      - mongo-data:/data/db

  redis:
    volumes:
      - redis-data:/data
```

Pour plus d'informations, consultez : https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-on-windows-or-macos-results-in-the-mongoservice-not-starting

</Accordion>

<Accordion title="La mise à niveau vers Redis 6.2 provoque une boucle de redémarrage">

Utilisez la commande `docker logs redis` pour afficher une copie des journaux.

Si vous voyez la ligne `Fatal: Can't initialize Background Jobs`, la sortie complète ressemblera à ceci :

```text title="Redis log example"
1:M 11 Feb 2024 15:19:22.609 # Server initialized
1:M 11 Feb 2024 15:19:22.609 # Fatal: Can't initialize Background Jobs.
1:C 11 Feb 2024 15:19:26.055 # oO0OoO0OoO0Oo Redis is starting oO0OoO0OoO0Oo
```

Cela peut être lié à la version de Docker actuellement utilisée. Une mise à jour vers une version >= 20.10.10 devrait résoudre ce problème.

Pour plus d'informations, consultez le ticket correspondant dans le projet Redis : https://github.com/redis/redis/issues/12362

Référence : https://docs.overleaf.com/on-premises/support/troubleshooting#upgrading-to-redis-6.2-results-in-a-restart-loop

</Accordion>

<Accordion title="Orientation incorrecte des images d’aperçu/miniatures de la galerie de modèles">

Il arrive que les images d'aperçu/miniatures générées par Ayakaleaf Pro soient créées avec une mauvaise orientation et nécessitent une intervention manuelle pour être corrigées. Ces images sont stockées dans `/var/lib/overleaf/data/template_files/`.

Nous vous recommandons de sauvegarder ce dossier avant toute modification.

Vous devrez suivre les étapes ci-dessous pour chaque modèle concerné :

Trouver l'ID du modèleAccédez à la galerie de modèles de votre instance (/templates/all), ouvrez un modèle concerné et copiez l'ID depuis l'URL (par exemple : https://your-instance-url/templates/6645d346c224815e9460a695).Exécuter la commande de correctionExécutez la commande suivante depuis l'hôte Docker (remplacez l'ID du modèle par celui que vous avez copié et adaptez le chemin si nécessaire) :docker exec sharelatex /bin/bash -c "mogrify -rotate 90 /var/lib/overleaf/data/template\_files/6645d346c224815e9460a695\_\*\{thumbnail,preview\}"

Référence : https://docs.overleaf.com/on-premises/support/troubleshooting#incorrect-orientation-of-template-gallery-preview-thumbnail-images

</Accordion>

<Accordion title="Vérifiez que vous avez activé les appels système. Pour pdflatex, il s’agit de 'pdflatex -shell-escape'.">

La commande `\write18` est désactivée par défaut dans la Community Edition, car toutes les compilations s'effectuent dans le même conteneur `sharelatex` ; c'est le réglage par défaut le plus sûr.

Si vous souhaitez l'activer pour pdflatex, créez un fichier `latexmkrc` à la racine de votre projet avec le contenu suivant :

```perl title="latexmkrc"
$pdflatex = 'pdflatex --shell-escape';
```

Relancez ensuite la compilation.

Référence : https://docs.overleaf.com/on-premises/support/troubleshooting#please-verify-that-you-have-enabled-system-calls.-for-pdflatex-this-is-pdflatex-shell-escape

</Accordion>

<Accordion title="`bin/up` échoue avec `unable to upgrade to tcp, received 409` ou `OCI runtime exec failed` après « Initiating Mongo replica set... »">

Ces erreurs signifient que le conteneur `mongo` plante et redémarre en boucle. `bin/up` démarre MongoDB puis exécute une commande à l'intérieur, qui échoue pendant que le conteneur redémarre. `bin/docker-compose ps` affiche le service `mongo` avec l'état `Restarting`.

Pour trouver la cause réelle, consultez le journal de MongoDB :

```sh
bin/logs mongo
```

Causes fréquentes :

* <strong>Le processeur ne prend pas en charge AVX.</strong> MongoDB 5.0 et versions ultérieures nécessitent AVX sur x86-64, et le journal affiche `MongoDB 5.0+ requires a CPU with AVX support`. Dans une machine virtuelle, définissez le type de processeur sur `host` afin qu'AVX soit transmis.
* <strong>Noyau Linux 6.19 à 7.0.13.</strong> MongoDB refuse de démarrer sur ces noyaux. Voir [Prérequis logiciels](/fr/on-premises/installation/introduction#software-requirements) pour la solution de contournement.
* <strong>Les données ont été créées par une ancienne version de MongoDB.</strong> MongoDB 8.0 ne peut pas ouvrir directement des données de la 4.4 ou de la 5.0. Effectuez la mise à niveau une version majeure à la fois, voir [Mettre à jour MongoDB](/fr/on-premises/maintenance/updating-mongodb).

</Accordion>

<Accordion title="Le journal affiche « Running Overleaf Community Edition, skipping TexLive checks »">

C'est le comportement attendu avec Ayakaleaf Pro, et vous pouvez l'ignorer. Ce message s'affiche lorsque `OVERLEAF_IS_SERVER_PRO` ne vaut pas `true`, ce qui est le cas dans l'image Ayakaleaf Pro. Ayakaleaf Pro n'a pas besoin de cette variable ; laissez-la donc non définie.

</Accordion>
