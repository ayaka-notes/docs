<Accordion title="Exécuter Overleaf avec un système de fichiers NFS">

Monter un système de fichiers NFS dans un conteneur Overleaf est techniquement possible, mais ce n'est pas recommandé et cela peut entraîner différents types de problèmes de performances.

Une erreur fréquente rencontrée lors des compilations est :

```text
EBUSY: resource busy or locked, unlink '/var/lib/overleaf/data/compiles/62f3d57bef7cf9005c364e75-62f3d57bef7cf9005c364e7a/.nfs573663533034825247625441'
```

Nous déconseillons en particulier l'utilisation de systèmes de fichiers reposant sur NFS pour les données éphémères, comme les répertoires utilisés pour les données de compilation. Nous recommandons d'utiliser un disque de travail local, de préférence un SSD local, pour les répertoires suivants.

Pour les installations basées sur `docker-compose`, nous suggérons simplement de remplacer le bind mount NFS, ce qui évite de modifier les chemins dans l'application. Voici un extrait de configuration `docker-compose` utilisant un disque de travail monté sur `/scratch` :

```yaml title="docker-compose excerpt"
services:
  sharelatex:
    environment:
      SANDBOXED_COMPILES_HOST_DIR: /scratch/compiles/
    volumes:
      - nfs:/var/lib/overleaf/data
      - /scratch/cache/:/var/lib/overleaf/data/cache
      - /scratch/compiles/:/var/lib/overleaf/data/compiles
      - /scratch/output/:/var/lib/overleaf/data/output
      - /scratch/tmp/:/var/lib/overleaf/tmp
```

Il n'est pas nécessaire de migrer les fichiers existants du NFS vers leur nouvel emplacement après la mise à jour. Le compilateur LaTeX peut recréer tous les fichiers lors d'une nouvelle compilation complète.

Pour plus de détails, voir : https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-with-an-nfs-filesystem

</Accordion>

<Accordion title="Le service `mongo` ne démarre pas lors de l'exécution d'Overleaf sous Windows ou macOS">

Si vous exécutez Overleaf sous Windows ou macOS, le service `mongo` peut ne pas redémarrer et afficher l'erreur suivante :

```text title="Example error"
Failed to start up WiredTiger under any compatibility version.
Reason: 1: Operation not permitted
```

Pour éviter cette erreur, les données doivent être stockées dans un volume plutôt que dans un répertoire monté par bind mount (voir la documentation de l'image `mongo` pour plus de détails : https://github.com/docker-library/docs/blob/master/mongo/content.md#where-to-store-data). Pour stocker les données dans des volumes Docker montés dans les conteneurs MongoDB et Redis, ajoutez ce qui suit à `config/docker-compose.override.yml` (créez ce fichier s'il n'existe pas encore) :

```yaml title="config/docker-compose.override.yml"
volumes:
  mongo-data:
  redis-data:

services:
  mongo:
    volumes:
      - mongo-data:/data/db

  redis:
    volumes:
      - redis-data:/data
```

Pour plus d'informations, voir : https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-on-windows-or-macos-results-in-the-mongoservice-not-starting

</Accordion>

<Accordion title="La mise à niveau vers Redis 6.2 provoque une boucle de redémarrage">

Utilisez la commande `docker logs redis` pour afficher une copie des journaux.

Si vous voyez la ligne `Fatal: Can't initialize Background Jobs`, la sortie complète ressemblera à ceci :

```text title="Redis log example"
1:M 11 Feb 2024 15:19:22.609 # Server initialized
1:M 11 Feb 2024 15:19:22.609 # Fatal: Can't initialize Background Jobs.
1:C 11 Feb 2024 15:19:26.055 # oO0OoO0OoO0Oo Redis is starting oO0OoO0OoO0Oo
```

Cela peut être lié à la version de Docker actuellement utilisée. Une mise à jour vers une version >= 20.10.10 devrait résoudre ce problème.

Pour plus d'informations, consultez le ticket Redis en amont : https://github.com/redis/redis/issues/12362

Référence : https://docs.overleaf.com/on-premises/support/troubleshooting#upgrading-to-redis-6.2-results-in-a-restart-loop

</Accordion>

<Accordion title="Orientation incorrecte des images d'aperçu/miniatures de la galerie de modèles">

Il arrive que les images d'aperçu/miniatures générées par Server Pro soient créées avec une mauvaise orientation et nécessitent une intervention manuelle pour être corrigées. Ces images sont stockées dans `/var/lib/overleaf/data/template_files/` (>= 5.0.3) et `/var/lib/sharelatex/data/template_files/` (versions antérieures).

Nous recommandons de sauvegarder ce dossier avant toute modification.

Vous devrez suivre les étapes ci-dessous pour chaque modèle concerné :

Trouver l'ID du modèleAccédez à la galerie de modèles de votre instance (/templates/all), ouvrez un modèle concerné et copiez l'ID depuis l'URL (par exemple : https://your-instance-url/templates/6645d346c224815e9460a695).Exécuter la commande de correctionExécutez la commande suivante depuis l'hôte Docker (remplacez l'ID du modèle par celui que vous avez copié et adaptez le chemin si nécessaire) :docker exec sharelatex /bin/bash -c "mogrify -rotate 90 /var/lib/overleaf/data/template\_files/6645d346c224815e9460a695\_\*\{thumbnail,preview\}"

Référence : https://docs.overleaf.com/on-premises/support/troubleshooting#incorrect-orientation-of-template-gallery-preview-thumbnail-images

</Accordion>

<Accordion title="Please verify that you have enabled system calls. For pdflatex, this is 'pdflatex -shell-escape'.">

La commande `\write18` est désactivée par défaut dans la Community Edition, car toutes les compilations ont lieu dans le même conteneur `sharelatex` ; c'est le réglage par défaut le plus sûr.

Si vous souhaitez l'activer pour pdflatex, créez à la racine de votre projet un fichier `latexmkrc` avec le contenu suivant :

```perl title="latexmkrc"
$pdflatex = 'pdflatex --shell-escape';
```

Relancez ensuite la compilation.

Référence : https://docs.overleaf.com/on-premises/support/troubleshooting#please-verify-that-you-have-enabled-system-calls.-for-pdflatex-this-is-pdflatex-shell-escape

</Accordion>
