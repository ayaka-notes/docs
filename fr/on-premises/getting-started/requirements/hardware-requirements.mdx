## Exigences matérielles

Lors du dimensionnement du matériel destiné à Overleaf, le principal facteur à prendre en compte est le nombre d'utilisateurs simultanés qui lanceront des compilations.

Par exemple, si vous disposez d'une licence pour 100 utilisateurs au total, mais que vous ne prévoyez qu'environ \~5 utilisateurs travaillant en même temps, l'installation minimale suffira. Si vous prévoyez qu'une proportion plus importante d'utilisateurs travaillera (et compilera) simultanément, envisagez un serveur aux caractéristiques plus élevées.

### Installation minimale

Une configuration de base d'au moins 2 cœurs et 3 Go de mémoire est requise pour un fonctionnement normal avec environ 5 utilisateurs simultanés. Cette configuration minimale suffira également pour des groupes plus importants dont l'utilisation simultanée est moindre, ou pour lesquels des temps de compilation plus longs en période de forte charge sont acceptables.

<Danger>

Si vous envisagez d'utiliser un système de fichiers basé sur NFS (Network File System) pour votre petite instance, consultez la section correspondante de la page [Dépannage](/fr/on-premises/support/troubleshooting).

</Danger>

### Montée en charge

En règle générale, pour offrir un niveau de service élevé et constant, il convient d'ajouter 1 cœur de CPU et 1 Go de mémoire à l'installation minimale pour chaque tranche de 5 à 10 utilisateurs simultanés.

Ceci ne doit être considéré que comme une indication, car des facteurs tels que la taille des documents typiques (les documents volumineux consomment davantage de ressources de compilation), la fréquence de compilation des utilisateurs et la tolérance aux temps de compilation plus longs en période de forte charge influent tous sur le dimensionnement nécessaire.

Beaucoup de nos clients souhaitent déployer Server Pro à l'échelle de toute leur organisation ou pour de grandes équipes. Dans ces situations, il nous est difficile de recommander une configuration précise, car les cas d'usage et le matériel disponible peuvent être très variés.

| Exemple 1                                                                                                                                                                                                                                                                                                       | Exemple 2                                                                                                                                                                                                                                                                                                                |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Si vous exploitez une installation Server Pro pour 300 utilisateurs au total et que vous prévoyez régulièrement que 30 à 60 d'entre eux compilent des documents en même temps, 8 Go et 7 cœurs (5 cœurs + 5 Go + la base de 2 cœurs et 3 Go) devraient fournir des ressources suffisantes pour offrir à vos utilisateurs un niveau de service élevé et constant. | Pour donner un exemple des exigences matérielles d'un déploiement plus important, une installation Server Pro pour 1 000 utilisateurs au total a été mise en place avec succès sur un seul serveur équipé de deux processeurs à 4 cœurs et de 32 Go de mémoire système. Cette configuration a répondu aux besoins de l'équipe tout au long de l'année d'utilisation écoulée. |

Les clients qui dépassent les capacités d'un seul gros serveur peuvent consulter la page [Mise à l'échelle horizontale](/fr/on-premises/maintenance/horizontal-scaling) pour Server Pro.

### Stockage

Nous déconseillons l'utilisation de Network File System (NFS)/Amazon EFS/Amazon EBS pour le stockage des projets et de l'historique dans les installations de grande taille, et nous **ne le prenons explicitement pas en charge** pour la mise à l'échelle horizontale.

Ces systèmes de fichiers n'offrent pas les performances et la fiabilité dont Server Pro a besoin lorsqu'il fonctionne à grande échelle. Lorsque le système de fichiers ne parvient pas à suivre la charge, l'application se bloque à cause d'un trop grand nombre d'opérations d'E/S bloquantes. Ces blocages peuvent entraîner le dépassement des verrous basés sur Redis, ce qui peut à son tour corrompre les données des projets.

Nous recommandons plutôt d'utiliser un [stockage objet compatible S3](/fr/on-premises/getting-started/what-is-the-overleaf-toolkit). Des performances S3 médiocres n'affectent que le téléversement et le téléchargement des fichiers, ce qui se traduit uniquement par un nombre accru de connexions ouvertes vers votre fournisseur S3, sans affecter le comportement du reste de l'application. De plus, Server Pro peut définir des délais d'expiration raisonnables pour les requêtes S3, ce qui est impossible pour les opérations d'E/S sur le système de fichiers au niveau de l'application.

<Info>

À titre de référence, GitLab adopte une position similaire en [ne prenant pas en charge NFS/Amazon EFS](https://docs.gitlab.com/ee/administration/nfs.html) pour son offre auto-gérée.

</Info>

### Configuration spécifique à Nginx pour les déploiements de grande taille

Par défaut, une instance Overleaf Server limite le nombre de connexions à 768. Cela inclut les connexions Websocket persistantes, la navigation HTML de premier niveau et les requêtes ajax. Une fois cette limite atteinte, l'éditeur peut ne pas parvenir à se connecter, la page de l'éditeur peut ne pas se charger entièrement et les requêtes de compilation peuvent échouer. Nginx renverra des réponses avec le statut 500 et écrira `worker_connections are not enough while connecting to upstream` dans `var/log/nginx/error`.log à l'intérieur du conteneur `sharelatex`.

Le paramètre [`worker_connections`](https://nginx.org/en/docs/ngx_core_module.html#worker_connections) limite le nombre de connexions simultanées que nginx accepte par worker. Le nombre de workers est contrôlé par le paramètre [`worker_processes`](https://nginx.org/en/docs/ngx_core_module.html#worker_processes), défini à 4 par défaut dans notre configuration nginx.

Nginx effectue peu de travail comparé aux autres parties du système ; ces limites servent donc de garde-fou pour éviter qu'un trop grand nombre de connexions ne submerge le système. Il est préférable de rejeter rapidement quelques connexions excédentaires plutôt que de ralentir toutes les connexions.

Les instances Overleaf Server exposent des variables d'environnement pour ajuster ces paramètres nginx :

* `NGINX_WORKER_PROCESSES` pour [`worker_processes`](https://nginx.org/en/docs/ngx_core_module.html#worker_processes) (par défaut `4`)
* `NGINX_WORKER_CONNECTIONS` pour [`worker_connections`](https://nginx.org/en/docs/ngx_core_module.html#worker_connections) (par défaut `768`)
*   `NGINX_KEEPALIVE_TIMEOUT` pour [`keepalive_timeout`](https://nginx.org/en/docs/http/ngx_http_core_module.html#keepalive_timeout) (par défaut `65`)

    <Info>Lorsqu'un autre proxy est placé devant le conteneur `sharelatex` (par ex. pour la terminaison TLS), la valeur de `NGINX_KEEPALIVE_TIMEOUT` de l'instance Overleaf Server doit être supérieure à celle du proxy précédent. Par exemple, avec un autre processus nginx sur l'hôte Docker <strong>nginx-host</strong>, voici deux exemples :</Info>
* Valeur par défaut de `NGINX_KEEPALIVE_TIMEOUT` : utilisez [`keepalive_timeout 60s`](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#keepalive_timeout) (valeur par défaut dans upstream) dans **nginx-host**
* Valeur personnalisée `NGINX_KEEPALIVE_TIMEOUT=100s` : utilisez [`keepalive_timeout 90s`](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#keepalive_timeout) (valeur personnalisée dans upstream) dans **nginx-host**

### Vitesse du CPU

LaTeX est un programme monothread, ce qui signifie qu'il ne peut utiliser qu'un seul cœur de CPU à la fois. Le CPU est également le principal facteur limitant lors de la compilation d'un document. Par conséquent, plus les performances monocœur de votre CPU sont élevées, plus vous pourrez compiler rapidement un document. Davantage de cœurs ne sera utile que si vous tentez de compiler plus de documents que vous n'avez de cœurs de CPU libres.
