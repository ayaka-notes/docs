RHEL et ses recompilations (Rocky Linux, AlmaLinux) fournissent Podman au lieu de Docker, et certaines organisations n'autorisent pas Docker sur leurs serveurs. Le Toolkit peut exécuter Ayakaleaf Pro sur **Podman rootless** à la place : les conteneurs s'exécutent sous un utilisateur normal, les compilations s'exécutent toujours dans des conteneurs TeX Live isolés, et SELinux reste en mode enforcing. Le script `bin/podman-setup` vérifie l'hôte et corrige ce qu'il peut.

À la fin de cette section, vous disposez de la même instance qu'avec [Utiliser Docker Compose](/fr/on-premises/installation/using-docker-compose) : Ayakaleaf Pro avec compilations isolées, MongoDB et Redis, géré avec les commandes habituelles `bin/up`, `bin/doctor` et `bin/upgrade`.

<Info>

La prise en charge de Podman est expérimentale. Elle provient du Toolkit officiel d'Overleaf, qui ne la teste que sous RHEL 9 et versions ultérieures avec Podman rootless, les compilations isolées et SELinux en mode enforcing. Nous avons testé ces pages sous Rocky Linux 9.9 (Podman 5.8, SELinux enforcing) avec Ayakaleaf Pro 6.3.4. Docker reste l'environnement d'exécution de conteneurs recommandé.

</Info>

### Ce dont vous avez besoin {#what-you-need}

* **RHEL, Rocky Linux, AlmaLinux ou CentOS Stream 9 ou version ultérieure**, avec SELinux en mode enforcing. `bin/podman-setup` s'arrête sur toute autre distribution. Sous Ubuntu ou Debian, utilisez [Utiliser Docker Compose](/fr/on-premises/installation/using-docker-compose/linux).
* **Un utilisateur non root disposant de `sudo`** qui sera propriétaire des conteneurs. Exécutez chaque commande de cette section avec cet utilisateur ; `bin/podman-setup` refuse de s'exécuter en tant que `root`.
* **Un hôte propre** : pas de Docker Engine ni d'installation existante du Toolkit. La migration d'une instance existante basée sur Docker vers Podman n'est pas traitée.

### Différences avec Docker {#how-it-differs-from-docker}

|                                  | Docker                               | Podman rootless                                                                          |
| -------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------- |
| Qui exécute les conteneurs       | Le démon Docker, en tant que `root`  | Votre utilisateur                                                                        |
| Socket utilisé pour lancer les compilations | `/var/run/docker.sock`    | `/run/user/<uid>/podman/podman.sock`                                                     |
| Ports                            | N'importe lesquels, par exemple `80` et `443` | `1024` et plus, par exemple `8080`                                              |
| Pare-feu de l'hôte (`firewalld`) | Contourné par les ports publiés      | S'applique : ouvrez le port avec `firewall-cmd`                                          |
| Démarrage après un redémarrage   | Le démon Docker les redémarre        | Le service utilisateur `podman-restart`                                                  |
| SELinux                          | Non configuré par le Toolkit         | Module de politique `podman_socket_clsi` et `SELINUX_MODE=managed` dans `config/overleaf.rc` |
| Profil seccomp pour les compilations | Intégré à l'image                | Extrait dans `config/seccomp/<version>/` et défini comme `SECCOMP_PROFILE` par le Toolkit |

### Limitations connues {#known-limitations}

* <strong>Intégration Git.</strong> Dans Ayakaleaf Pro 6.3.4, `git clone` échoue avec `502` sur Podman : le NGINX de l'image recherche le conteneur `git-bridge` avec le serveur DNS de Docker (`127.0.0.11`), dont Podman ne dispose pas. Le correctif ([1b911d1092](https://github.com/ayaka-notes/ayakaleaf-pro/commit/1b911d1092c80f7b0ff77c5e3805b40503d49964)) arrivera avec la prochaine version ; d'ici là, laissez `GIT_BRIDGE_ENABLED=false`.
* <strong>Adresses IP des clients.</strong> Podman rootless transfère le port publié depuis l'intérieur du réseau du conteneur, si bien qu'Ayakaleaf Pro voit chaque visiteur avec une adresse interne comme `10.89.0.15`. Les [journaux d'audit](/fr/on-premises/user-guide/administrators/user-management#audit-logs) d'un utilisateur dans le panneau d'administration affichent cette adresse au lieu de son adresse IP.
