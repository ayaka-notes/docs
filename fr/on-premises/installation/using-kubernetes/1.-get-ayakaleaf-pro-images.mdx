title: 1. Obtenir les images Ayakaleaf Pro
description: Utilisez les mêmes images Ayakaleaf Pro que le Toolkit.
icon: split
---

Kubernetes exécute les mêmes images que le Toolkit. Il n'existe pas d'image distincte pour Kubernetes.

| Image                                                | Utilisée par                                                            |
| ---------------------------------------------------- | ----------------------------------------------------------------------- |
| `ghcr.io/ayaka-notes/overleaf-pro:6.3.2`             | le Deployment `overleaf`                                                |
| `ghcr.io/ayaka-notes/overleaf-pro/git-bridge:6.3.2`  | [Intégration Git](/fr/on-premises/configuration/kubernetes/integrations/git-integration) (facultatif), même tag que ci-dessus |
| `ghcr.io/ayaka-notes/texlive-*`                      | les compilations, récupérées dans Docker sur les nœuds à l'[étape 0](/fr/on-premises/installation/using-kubernetes/0.-prepare-the-nodes) |

Les images sont publiques sur [ghcr.io](https://github.com/ayaka-notes/ayakaleaf-pro/pkgs/container/overleaf-pro/) pour amd64 et arm64 ; le kubelet peut donc les récupérer sans identifiants.

<Warning>

Utilisez toujours un tag de version, comme `6.3.2`, et non `latest`. Les mises à niveau exécutent des migrations de base de données et doivent suivre [Mise à niveau sur Kubernetes](/fr/on-premises/maintenance/upgrading-on-kubernetes) ; un tag mobile mettrait à niveau un pod chaque fois qu'il est replanifié.

</Warning>

### Q\&A

<Accordion title="Nos nœuds ne peuvent pas joindre ghcr.io. Que faire ?">

<strong>Réponse :</strong> Copiez les images dans un registre accessible aux nœuds et utilisez ce nom dans les manifestes, par exemple :

```bash
docker pull ghcr.io/ayaka-notes/overleaf-pro:6.3.2
docker tag ghcr.io/ayaka-notes/overleaf-pro:6.3.2 registry.example.com/ayakaleaf/overleaf-pro:6.3.2
docker push registry.example.com/ayakaleaf/overleaf-pro:6.3.2
```

Pour un registre sans TLS, containerd a besoin d'un fichier `/etc/containerd/certs.d/<registry>/hosts.toml` contenant `server = "http://<registry>"` sur chaque nœud, et de `config_path` défini comme à l'[étape 0](/fr/on-premises/installation/using-kubernetes/0.-prepare-the-nodes). Docker lui-même ne pousse en HTTP simple que vers `localhost` ; poussez donc via `localhost:<port>` sur l'hôte du registre ou ajoutez-le à `insecure-registries`.

</Accordion>
