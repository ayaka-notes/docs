### Créer l'administrateur et un premier projet {#create-the-administrator-and-a-first-project}

Ouvrez [http://localhost:8080/launchpad](http://localhost:8080/launchpad) dans votre **navigateur Windows**, créez le premier compte administrateur et connectez-vous. Suivez ensuite [6. Tâches post-installation](/fr/on-premises/installation/using-docker-compose/linux/6.-post-installation-tasks) du guide Linux, en utilisant le port `8080` dans ses URL d'exemple.

### Vérifier la compilation {#verify-compilation}

Une page de connexion fonctionnelle ne prouve pas que les conteneurs de compilation distincts peuvent accéder au répertoire de données WSL. Créez un projet vide et compilez ce `main.tex` avec **pdfLaTeX** :

```latex
\documentclass{article}
\begin{document}
Ayakaleaf Pro on Windows WSL 2.
\end{document}
```

L'aperçu PDF doit afficher le texte. Pour l'image basic, sélectionnez si nécessaire **TeX Live 2026 Basic** dans les paramètres du projet.

Sélectionnez **XeLaTeX** et testez :

```latex
\documentclass{article}
\usepackage{fontspec}
\begin{document}
Ayakaleaf WSL XeLaTeX sandbox.
\end{document}
```

Les deux exemples fonctionnent avec basic. Pour les documents en chinois, utilisez une image contenant `ctex` et les polices requises, comme full, avant de tester ce qui suit avec **XeLaTeX**. Basic ne les inclut pas :

```latex
\documentclass{ctexart}
\begin{document}
你好，Ayakaleaf Pro。
\end{document}
```

Pour confirmer l'utilisation de la sandbox, exécutez dans **Ubuntu** pendant une compilation :

```bash
docker ps -a --filter ancestor=ghcr.io/ayaka-notes/texlive-basic:2026.1
bin/logs -f clsi
```

Utilisez le nom de l'image que vous avez choisie dans le filtre. Les compilations courtes peuvent se terminer avant l'exécution de `docker ps` ; `-a` affiche aussi les conteneurs arrêtés jusqu'à leur nettoyage. Un conteneur de compilation doit utiliser cette image et un bind mount `/compile` provenant du répertoire de données WSL du Toolkit. Les journaux de l'application seuls ne remplacent pas la vérification du PDF.

### Vérifier la persistance {#verify-persistence}

Dans **Ubuntu**, depuis le répertoire du Toolkit :

```bash
bin/stop
bin/start
```

Attendez l'application, rouvrez le projet depuis Windows et compilez-le à nouveau. Votre compte, la source et les fichiers du projet doivent toujours être présents. Par défaut, les données actives se trouvent dans `~/ayakaleaf-toolkit/data/` dans Ubuntu. Conservez à la fois `config/` et `data/` ; désinstaller ou désinscrire la distribution Ubuntu peut les supprimer.

### Garder l'instance disponible {#keep-the-instance-available}

Maintenir l'instance en fonctionnement repose sur trois éléments : Windows reste éveillé, Docker Desktop fonctionne, et les conteneurs redémarrent avec le moteur.

Dans **Settings → General** de Docker Desktop, activez **Start Docker Desktop when you sign in to your computer**, voir [Paramètres de Docker Desktop](https://docs.docker.com/desktop/settings-and-maintenance/settings/). Cela démarre Docker après l'ouverture de session, et non avant. Après un redémarrage de Windows, ouvrez une session, attendez que Docker Desktop ait fini de démarrer, ouvrez Ubuntu et vérifiez `docker ps` ainsi que le site.

Le **Resource Saver** de Docker Desktop est distinct de la mise en veille de Windows. Il ne s'active normalement que lorsqu'aucun conteneur n'est en cours d'exécution ; l'application, MongoDB et Redis en cours d'exécution empêchent cette condition d'inactivité. Sous WSL 2, il met en pause le moteur Docker au lieu d'arrêter la VM WSL partagée. Ne mettez pas manuellement Docker Desktop en **Pause** pendant que vous servez des utilisateurs. Vous n'avez pas besoin de désactiver Resource Saver simplement pour maintenir cette pile en fonctionnement ; consultez la [documentation de Docker sur Resource Saver](https://docs.docker.com/desktop/use-desktop/resource-saver/).

Les services du Toolkit utilisent `restart: always`. Vérifiez le paramètre effectif dans **Ubuntu** :

```bash
docker inspect sharelatex mongo redis --format '{{.Name}} restart={{.HostConfig.RestartPolicy.Name}}'
```

Chaque service doit indiquer `always`. Une fois Docker lancé, il peut redémarrer ces conteneurs existants sans nouveau `bin/up`. Un conteneur arrêté manuellement reste arrêté jusqu'à ce que vous le démarriez ou redémarriez le moteur ; avec `always`, un redémarrage du moteur peut le relancer. Consultez le [comportement des politiques de redémarrage de Docker](https://docs.docker.com/engine/containers/start-containers-automatically/).

| Action | Effet sur Ayakaleaf |
| --- | --- |
| Fermer le terminal Ubuntu après `bin/up -d` | Les conteneurs s'exécutent en mode détaché ; le terminal ne les supervise pas. Gardez Docker Desktop et l'environnement WSL disponibles |
| Fermer la fenêtre du Docker Dashboard | La fenêtre peut être fermée tandis que Docker Desktop continue de fonctionner dans la zone de notification |
| Choisir **Quit Docker Desktop** | Arrête le moteur et rend le site indisponible ; rouvrez Docker Desktop pour rétablir le service |
| Exécuter `wsl --shutdown` | Arrête toutes les distributions WSL et interrompt le backend WSL de Docker ; redémarrez Docker Desktop et rouvrez Ubuntu |
| Mettre Windows en veille, en veille prolongée ou l'arrêter | Le service est indisponible ; laisser seulement l'écran allumé ou éteint n'y change rien |
| Exécuter `bin/stop` | Arrête l'instance en conservant ses données ; utilisez `bin/start` pour reprendre |

Pour une utilisation prolongée sur secteur, ouvrez dans Windows 11 **Paramètres → Système → Alimentation et batterie → Délais d'expiration de l'écran, de la mise en veille et de la mise en veille prolongée** (certaines versions affichent **Alimentation** ou **Écran et veille**). Réglez le délai de mise en veille sur secteur sur **Jamais** et désactivez la mise en veille prolongée automatique si elle est configurée. L'écran peut toujours s'éteindre. L'action de fermeture du capot d'un ordinateur portable est un paramètre distinct ; fermer le capot peut mettre l'ordinateur en veille même si le délai de mise en veille pour inactivité est réglé sur Jamais. Consultez les [paramètres d'alimentation de Windows](https://support.microsoft.com/en-us/windows/experience/power-battery/power-settings-in-windows-11).

N'exécutez pas `wsl --shutdown` comme nettoyage de routine pendant que le site est utilisé. Si une modification des paramètres de WSL l'exige, arrêtez d'abord l'instance et planifiez une interruption. Windows peut exécuter l'instance en continu avec ces paramètres. Pour un service partagé qui doit survivre aux fermetures de session et aux redémarrages sans surveillance, nous recommandons le [guide Linux](/fr/on-premises/installation/using-docker-compose/linux).

### Vérifier la reprise après un redémarrage de Docker Desktop {#check-recovery-after-restarting-docker-desktop}

Après avoir enregistré votre travail et laissé les compilations en cours se terminer, choisissez **Restart Docker Desktop** dans le menu de dépannage de Docker Desktop. Attendez le moteur, puis vérifiez dans **Ubuntu** :

```bash
docker ps
curl -I http://localhost:8080/launchpad
```

Ouvrez le projet existant dans Windows et compilez-le à nouveau. Vérifiez que le compte et la source existent toujours.

Si vous avez volontairement arrêté l'instance avec `bin/stop`, utilisez `bin/start`. Si Docker fonctionne mais qu'un service échoue, lisez ses journaux plutôt que de recréer la configuration. Windows Update, les mises à jour de Docker et les coupures de courant peuvent tout de même interrompre une installation fonctionnant 24 heures sur 24 ; conservez des sauvegardes et vérifiez la reprise après une maintenance planifiée.

### Utilisation quotidienne {#daily-use}

Démarrez Docker Desktop dans Windows. Ouvrez **Ubuntu** :

```bash
cd "$HOME/ayakaleaf-toolkit"
```

| Tâche | Commande |
| --- | --- |
| Démarrer les conteneurs existants | `bin/start` |
| Arrêter les conteneurs en conservant les données | `bin/stop` |
| Appliquer les modifications de configuration | `bin/up -d` |
| Vérifier l'état | `bin/docker-compose ps` |
| Lire les journaux de démarrage | `bin/docker-compose logs --tail=100 sharelatex` |
| Lire les journaux de MongoDB | `bin/docker-compose logs --tail=100 mongo` |
| Lire les journaux du compilateur | `bin/logs -f clsi` |

`bin/start` n'applique pas les modifications de configuration : utilisez `bin/up -d` après avoir modifié `config/`. Suivez [Données et sauvegardes](/fr/on-premises/maintenance/data-and-backups) avant de mettre à niveau, de déplacer ou de supprimer la distribution WSL. Copier les fichiers MongoDB actifs pendant que la base de données écrit ne constitue pas une sauvegarde cohérente.

Conservez `127.0.0.1` pour un usage local. Servir d'autres ordinateurs nécessite également une adresse d'écoute, une URL de site, une configuration du pare-feu et du réseau Windows et HTTPS définis délibérément ; modifier uniquement `OVERLEAF_SITE_URL` ne publie pas de port.

Si quelque chose ne fonctionne pas, consultez [Dépannage](/fr/on-premises/installation/using-docker-compose/windows/troubleshooting).
