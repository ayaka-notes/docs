---
title: Configurer les compilations en sandbox
icon: box-archive
---

Les compilations en sandbox fonctionnent un peu différemment dans l'environnement de développement que dans l'image de production. L'environnement de développement les a déjà configurées ; cette page explique les paramètres et trois points à garder à l'esprit :

* Problème de permissions de fichiers
* Partage de volume entre history-v1 et filestore
* Problème des sous-répertoires

### Activer les compilations en sandbox {#enable-sandbox-compiles}

Les compilations en sandbox sont activées par défaut. `develop/docker-compose.yml` définit `SANDBOXED_COMPILES=true` pour `clsi`, et `develop/dev.env` contient le reste :

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

clsi ne récupère pas les images lui-même, alors récupérez-les une fois avec `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1` (et `:2025.1`).

LaTeX s'exécute dans les conteneurs frères sous `TEXLIVE_IMAGE_USER`. Dans l'environnement de développement, il s'agit de `tex`, qui est aussi la valeur par défaut de clsi (`services/clsi/config/settings.defaults.cjs:154`). L'image de production utilise `www-data` à la place lorsque `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` (`server-ce/config/env.sh:15-21`), car les fichiers y sont créés par l'utilisateur `www-data` du conteneur Overleaf.

<Warning>

N'utilisez pas votre propre image construite localement, vous risqueriez de rencontrer une série d'erreurs.

</Warning>

### Corriger les permissions de fichiers {#fix-file-permissions}

Le conteneur clsi démarre en root, attribue les dossiers `compiles`, `output` et `cache` à l'utilisateur `node` (uid `1000`), puis exécute clsi en tant que `node` (`services/clsi/entrypoint.sh`). Ainsi, `develop/compiles` sur l'hôte appartient à l'uid `1000`, le même uid que `tex` dans l'environnement de développement (voir le commentaire dans `develop/pandoc/Dockerfile`). Avec les paramètres ci-dessus, l'environnement de développement compile sans aucune modification des permissions.

Si vous définissez plutôt `TEXLIVE_IMAGE_USER=root`, root (uid `0`) n'a pas la permission d'écrire dans les sous-dossiers de `compiles`. Dans ce cas, donnez au groupe `root` la propriété et le droit d'écriture sur `compiles`, avec `setgid` activé pour que les nouveaux sous-dossiers héritent de cette propriété :

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

Pour une documentation détaillée, consultez `services/clsi/README.md`.

### Partage de volume entre history-v1 et filestore {#volume-share-between-history-v1-and-filestore}

<Info>

Les paramètres de cette section et de la suivante figurent déjà dans `develop/docker-compose.yml` et `develop/dev.env`. Ils ne comptent qu'avec `S3_ENABLED=false` dans `develop/dev.rc`. Avec la valeur par défaut `S3_ENABLED=true`, filestore et history-v1 conservent plutôt ces fichiers dans des buckets RustFS (`develop/s3/docker-compose.yml`).

</Info>

Par défaut, filestore sert de passerelle entre S3 et les autres services d'Overleaf. Cependant, dans Overleaf CE ou Server Pro, tous les fichiers sont stockés localement par défaut. Overleaf a donc introduit une méthode assez astucieuse.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

Parallèlement, `data/history` est aussi utilisé par le service d'historique. Ainsi, différents microservices peuvent partager les mêmes données. C'est pourquoi le service filestore de develop monte le volume `history-v1-buckets` de history-v1. Sans lui, **clsi ne pourra pas récupérer les fichiers blob depuis le service filestore**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

filestore trouve les buckets grâce à ces paramètres de `dev.env` :

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### Utiliser les sous-répertoires {#use-subdirectories}

filestore lit toujours les blobs d'historique avec des sous-répertoires (`services/filestore/app/js/KeyBuilder.js:58`, `:70`). L'image de production active `useSubdirectories` pour history-v1 (`server-ce/config/production.json`), mais pas la configuration par défaut de history-v1, donc en développement history-v1 <strong>aplatirait toutes les données.</strong> `dev.env` définit donc `NODE_CONFIG` pour history-v1 :&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

Sans cela, history-v1 stocke les fichiers `project_blobs` ainsi :

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

Avec `useSubdirectories` défini à `true`, le `_` de ces noms devient `/`, de sorte que chaque blob est stocké dans des sous-dossiers.
