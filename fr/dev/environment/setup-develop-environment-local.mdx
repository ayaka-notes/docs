## Prérequis {#prerequisites}

Overleaf est un projet open source typique reposant sur une architecture de microservices, dont tous les services s'exécutent dans Docker.&#x20;

* Le code source officiel de la Community Edition est disponible sur [GitHub Overleaf Official](https://github.com/overleaf/overleaf/tree).&#x20;
* Le code source d'Overleaf-CEP est disponible sur [GitHub Yu-i-i/Overleaf](https://github.com/yu-i-i/overleaf-cep).
* Ayakaleaf Pro est disponible sur [GitHub ayaka-notes/ayakaleaf-pro](https://github.com/ayaka-notes/ayakaleaf-pro).

Pour mettre en place un environnement de développement Overleaf, vous aurez besoin d'un serveur puissant ; une configuration d'au moins 8 cœurs et 16 Go de RAM est recommandée, car vous devrez exécuter plus de 20 conteneurs simultanément.

<Info>

Les serveurs dotés de 8 cœurs CPU ou plus étant généralement coûteux, nous vous recommandons vivement d'utiliser votre ordinateur local pour le développement.

</Info>

Par ailleurs, en tant que développeur, vous devriez déjà être familiarisé avec l'[installation de Docker](https://docs.docker.com/engine/install/ubuntu/). Nous vous conseillons fortement d'utiliser une version Ubuntu LTS récente et stable (par exemple Ubuntu 24.04 en 2025–2026) ainsi que la dernière version de Docker pour le développement, afin de réduire le risque de rencontrer des erreurs inattendues.

En résumé, vous aurez besoin de :

* [x] Un serveur ou un ordinateur de bureau puissant pour développer
* [x] Une version Ubuntu LTS récente et stable (par exemple Ubuntu 24.04)
* [x] Un environnement Docker et Git

## Tutoriel de configuration {#configuration-tutorial}

Ici, nous utilisons Ayakaleaf Pro pour montrer comment mettre en place un environnement de développement Overleaf. Toutes les commandes ci-dessous s'exécutent dans le répertoire `develop`, sauf indication contraire.

<Steps>
<Step title="Récupérer le code source">
Tout d'abord, clonons le dépôt :

```bash title="bash"
git clone https://github.com/ayaka-notes/ayakaleaf-pro.git
cd ayakaleaf-pro/develop
```
</Step>

<Step title="Synchroniser `yarn.lock`">
Le dépôt utilise Yarn 4 (`packageManager` dans le `package.json` racine), et son `yarn.lock` peut être désynchronisé des fichiers `package.json`. Synchronisez-le après le premier clonage et après toute modification d'un `package.json` :

```bash title="bash"
bin/sync
```

`bin/sync` exécute `yarn install --mode=update-lockfile` dans un conteneur `node:24.18.1`, vous n'avez donc pas besoin de Node.js sur l'hôte. Ne commitez pas le `yarn.lock` modifié.
</Step>

<Step title="Construire l'image de développement">
Construisez les services :

```bash title="bash"
bin/build
```

<Info>

Si Docker manque de RAM lors de la construction parallèle des services, créez un fichier `.env` dans ce répertoire contenant `COMPOSE_PARALLEL_LIMIT=1`.

</Info>
</Step>

<Step title="Appliquer les traductions">
Les modules d'Ayakaleaf Pro conservent leurs traductions dans `services/web/locales/locales_patches/`, que les fichiers de locales commités ne contiennent pas. Appliquez-les une fois avant le premier démarrage, sinon les pages de ces modules affichent des clés comme `about_to_permanently_delete_accounts` au lieu du texte :

```bash title="bash"
bin/i18n
```

Il nécessite `jq` sur l'hôte. Relancez-le après avoir ajouté une traduction ou changé de branche, voir [Mettre à jour les traductions i18n](/fr/dev/environment/update-i18n-translations).
</Step>

<Step title="Démarrer tous les microservices">
Démarrez ensuite les services :

```bash title="bash"
bin/up
```

Une fois les services lancés, ouvrez [http://localhost/launchpad](http://localhost/launchpad) pour créer le premier compte administrateur. Ajoutez le port si vous avez modifié `OVERLEAF_PORT` (voir ci-dessous).

<Info>

LDAP est activé par défaut (`LDAP_ENABLED=true` dans `dev.rc`). Le launchpad affiche alors le formulaire d'administrateur LDAP : il ne demande qu'une adresse e-mail, et cet administrateur se connecte ensuite via LDAP, par exemple en tant que `professor` / `professor` (`professor@planetexpress.com`). Les utilisateurs de test sont listés dans `develop/authentication/README.md`. Définissez `LDAP_ENABLED=false` et `SAML_ENABLED=false` pour créer plutôt un administrateur local avec un mot de passe.

</Info>
</Step>
</Steps>

<Info>

`develop/dev.env` définit déjà `ADMIN_PRIVILEGE_AVAILABLE=true`, donc les administrateurs peuvent ouvrir le panneau d'administration sans configuration supplémentaire.

</Info>

### Configuration (`dev.rc`) {#configuration-dev-rc}

`develop/dev.rc`, à côté de `dev.env`, contient les interrupteurs de l'environnement de développement, comme `overleaf.rc` dans l'Overleaf Toolkit. Modifiez une valeur et relancez `bin/dev` pour l'appliquer ; une fonctionnalité désactivée arrête aussi ses conteneurs.

| Variable | Par défaut | Rôle |
| --- | --- | --- |
| `OVERLEAF_PORT` | `80` | Port hôte du site. |
| `LDAP_ENABLED` | `true` | Connexion LDAP avec des utilisateurs de test. |
| `SAML_ENABLED` | `true` | Connexion SAML avec des utilisateurs de test. |
| `MAILPIT_ENABLED` | `true` | Capture chaque e-mail de `web` dans Mailpit. Active aussi la confirmation d'e-mail (`EMAIL_CONFIRMATION_DISABLED=false`). |
| `S3_ENABLED` | `true` | Conserve les fichiers d'historique et de modèles dans RustFS (S3) au lieu de volumes locaux. |
| `HOPPSCOTCH_ENABLED` | `true` | Hoppscotch avec un proxy vers le réseau Docker, voir [Installer les outils de développement](/fr/dev/environment/setup-develop-tools). |
| `HOPPSCOTCH_PORT` | `9170` | Port hôte de Hoppscotch. |
| `GRAFANA_ENABLED` | `true` | Grafana sur `/grafana/` du site, avec l'état, les métriques et les logs de chaque service, voir [Installer les outils de développement](/fr/dev/environment/setup-develop-tools). |

Chaque fonctionnalité garde son `docker-compose.yml` et ses autres fichiers dans son propre dossier : `authentication/ldap`, `authentication/saml`, `mail`, `s3`, `hoppscotch` et `grafana`. Une fonctionnalité qui a besoin d'un réglage de `web` sans variable d'environnement monte un fichier dans `/etc/overleaf/settings.d/`, et `develop/settings.dev-env.cjs` les fusionne tous. Tous les scripts `bin/*` passent par `bin/docker-compose`, qui ajoute les fichiers des fonctionnalités activées. Appelez `bin/docker-compose` au lieu de `docker compose` quand vous avez besoin vous-même d'une commande compose.

<Warning>

Les volumes locaux et RustFS sont des stockages séparés : un projet créé avec `S3_ENABLED=true` n'a ni historique ni fichiers binaires après le passage à `false`, et inversement. Pour copier dans RustFS les fichiers d'un environnement qui fonctionnait avant l'existence de `S3_ENABLED`, suivez « Moving existing data into RustFS » dans [develop/README.md](https://github.com/ayaka-notes/ayakaleaf-pro/blob/server-pro/develop/README.md).

</Warning>

### Ports {#ports}

Le site, la console RustFS et Hoppscotch écoutent sur `127.0.0.1` de l'hôte ; sur une machine distante, redirigez d'abord leurs ports, par exemple `ssh -L 9001:localhost:9001 <host>`. Le site utilise `OVERLEAF_PORT` de `dev.rc`, ajoutez donc le port aux adresses ci-dessous si vous l'avez modifié.

| Page | Adresse | Connexion |
| --- | --- | --- |
| Site | [http://localhost](http://localhost) | Les comptes du site, ou les utilisateurs de test |
| Boîte de réception (Mailpit) | [http://localhost/mailpit/](http://localhost/mailpit/) | Aucune |
| Grafana | [http://localhost/grafana/](http://localhost/grafana/) | Aucune, les utilisateurs anonymes sont administrateurs |
| Mongo Express | [http://localhost/mongo-express/](http://localhost/mongo-express/) | Aucune |
| RedisInsight | [http://localhost/redis-insight/](http://localhost/redis-insight/) | Aucune |
| Console S3 (RustFS) | [http://localhost:9001/rustfs/console/](http://localhost:9001/rustfs/console/) | `rustfsadmin` / `rustfsadmin` |
| Hoppscotch | [http://localhost:9170](http://localhost:9170) (`HOPPSCOTCH_PORT`) | Aucune |

Mailpit, Grafana, Mongo Express et RedisInsight sont servis par le site sur leurs propres chemins, via webpack-dev-server, ils n'ont donc pas besoin de port propre. Une fois connecté, le menu **Dev tools** de la barre de navigation du site y renvoie ; une page dont la fonctionnalité est désactivée dans `dev.rc` est omise. [Installer les outils de développement](/fr/dev/environment/setup-develop-tools) montre ce que fait chacun d'eux.

L'API S3 (port 9000) et SMTP (port 1025) ne sont accessibles qu'à l'intérieur du réseau Docker. Mongo (27017), Redis (6379), Mongo Express (8081), RedisInsight (5540) et git-bridge (8000) ne sont publiés que sur `127.0.0.1` de l'hôte.

### TeX Live {#tex-live}

Les compilations en sandbox sont activées par défaut : `develop/dev.env` définit `SANDBOXED_COMPILES=true` et les images `ghcr.io/ayaka-notes/texlive-full:2026.1` et `ghcr.io/ayaka-notes/texlive-full:2025.1`. clsi ne récupère pas les images lui-même, alors récupérez-les une fois :

```bash
docker pull ghcr.io/ayaka-notes/texlive-full:2026.1
docker pull ghcr.io/ayaka-notes/texlive-full:2025.1
```

Voir [Configurer les compilations en sandbox](/fr/dev/environment/setup-sandbox-compiles) pour les détails.

<Warning>

Un projet créé alors que `SANDBOXED_COMPILES` était désactivé n'a pas d'image TeX Live. Il compile toujours avec l'image par défaut, mais le passage entre le code et le PDF échoue avec « That didn't work. Recompile and try again. » Attribuez une fois à ces projets l'image de `TEX_LIVE_DOCKER_IMAGE` ; sans `--commit`, le script affiche seulement ce qu'il changerait :

```bash
bin/docker-compose exec web sh -c 'cd /overleaf/services/web && node scripts/backfill_project_image_name.mjs --commit'
```

</Warning>

`dev.env` active aussi les conversions Pandoc avec `PANDOC_IMAGE=overleaf-pandoc:local`. Construisez cette image une fois, depuis la racine du dépôt :

```bash
docker build -t overleaf-pandoc:local develop/pandoc
```

Pour compiler sur un hôte macOS, vous devrez peut-être remplacer le chemin du socket Docker en créant un fichier `.env` dans le répertoire `develop`, contenant `DOCKER_SOCKET_PATH=/var/run/docker.sock.raw`

### Développement {#development}

Pour éviter d'exécuter `bin/build && bin/up` après chaque modification du code, vous pouvez exécuter Overleaf Community Edition en _mode développement_, dans lequel les services se mettent automatiquement à jour lors des modifications du code.

Pour cela, utilisez le script `bin/dev` fourni :

```text
bin/dev
```

Cela démarre tous les services avec `node --watch`, qui surveille automatiquement le code et redémarre les services si nécessaire. Relancez-le après avoir modifié `dev.rc`.

Pour améliorer les performances, vous pouvez ne démarrer qu'une partie des services en mode développement en passant une liste séparée par des espaces au script `bin/dev` :

```text
bin/dev [service1] [service2] ... [serviceN]
```

<Info>

Démarrer le service `web` en _mode développement_ ne mettra à jour le service `web` que lors des modifications du code backend. Pour mettre également à jour automatiquement le code frontend, veillez à démarrer aussi le service `webpack` en _mode développement_.

</Info>

Si aucun service n'est indiqué, tous les services démarrent en mode développement.

Après avoir ajouté une traduction ou changé de branche, exécutez `bin/i18n`, voir [Mettre à jour les traductions i18n](/fr/dev/environment/update-i18n-translations).

### Débogage {#debugging}

En _mode développement_, la plupart des services exposent un port de débogage auquel vous pouvez attacher un débogueur, comme l'inspecteur des Dev Tools de Chrome ou celui intégré à un IDE. Le tableau suivant indique le port exposé sur `127.0.0.1` de la **machine hôte** pour chaque service :

| Service            | Port |
| ------------------ | ---- |
| `web`                   | 9229 |
| `clsi`                  | 9230 |
| `chat`                  | 9231 |
| `docstore`              | 9233 |
| `document-updater`      | 9234 |
| `filestore`             | 9235 |
| `notifications`         | 9236 |
| `real-time`             | 9237 |
| `history-v1`            | 9239 |
| `project-history`       | 9240 |
| `linked-url-proxy`      | 9241 |
| `third-party-datastore` | 9242 |

Pour vous attacher à un service via le _débogage à distance_ de Chrome, rendez-vous sur chrome://inspect/ et assurez-vous que l'option _Discover network targets_ est cochée. Cliquez ensuite sur _Configure..._ et ajoutez une entrée `localhost:[service port]` pour chacun des services auxquels vous souhaitez attacher un débogueur.

Après l'ajout d'une entrée, le service apparaît comme _Remote Target_, que vous pouvez inspecter et déboguer.

### Journalisation {#logging}

Le script `bin/logs` suit les logs et les formate avec `bunyan`. Il a aussi besoin de `ggrep`, le nom de GNU grep lorsqu'il est installé avec Homebrew sur macOS ; Ubuntu n'a pas de commande `ggrep`.

```bash
sudo npm install -g bunyan
# Or sudo apt install node-bunyan 
```

Vous pouvez aussi exécuter directement :

```text
bin/docker-compose logs -f [service name]
```

Utilisez `bin/docker-compose` plutôt que `docker compose`, afin que les services des fonctionnalités de `dev.rc` (`mailpit`, `rustfs`, `ldap`, `saml`, `hoppscotch`, et `grafana` avec Prometheus, Loki et les exporteurs) soient aussi trouvés.

Avec `GRAFANA_ENABLED=true`, les logs de chaque conteneur sont aussi dans Grafana, où ils peuvent être filtrés par service, niveau et texte, voir [Installer les outils de développement](/fr/dev/environment/setup-develop-tools#grafana).
