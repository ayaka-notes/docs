### Introduction

Avant de vous lancer dans le développement, nous vous invitons à prendre connaissance des points suivants :

* Overleaf est officiellement développé dans un [dépôt interne](http://github.com/overleaf/internal), et l'édition communautaire est publiée dans [overleaf/overleaf](https://github.com/overleaf/overleaf). Un copybot se charge de synchroniser le code entre le dépôt interne et le dépôt public.
* [Ayaka-notes/overleaf-pro](https://github.com/ayaka-notes/overleaf-pro) est un fork de l'édition communautaire d'Overleaf. Nous souhaitons que ce projet puisse durer sur le long terme : merci donc de respecter les règles ci-dessous avant de contribuer.

### Règles de commit

* Évitez de modifier en profondeur le code existant d'Overleaf. Concentrez autant que possible les fonctionnalités dans le dossier `services/web/modules`. Cela réduira au minimum notre charge de travail lors des futures fusions et mises à jour du code.
* Le vibe coding est certes très pratique, mais il peut facilement semer le désordre dans le projet et le rendre impossible à maintenir par la suite : utilisez-le avec prudence.
* N'ajoutez aucun contenu lié aux traductions pendant le développement ; réutilisez autant que possible les traductions existantes.
* Évitez d'introduire des variables d'environnement, sauf en cas de nécessité absolue. Si c'est indispensable, veillez à ce qu'elles soient aussi cohérentes que possible avec celles de l'Overleaf toolkit ou de [docs.overleaf.com](https://docs.overleaf.com/).

### Règles de branches

Nous utilisons les branches suivantes pour le développement d'overleaf-pro :

* `main` : cette branche sert uniquement à la synchronisation du code amont, **NE** commitez **AUCUNE** modification externe. Sur cette branche, nous posons des tags comme `ce-v[X.x.x]`, qui indiquent la correspondance avec la version `v[X.x.x]` de l'édition communautaire officielle d'Overleaf. Remarque : ces tags sont immuables !
* `server-pro` : branche par défaut pour le développement quotidien.
* `feature-X` : branche utilisée pour le développement d'une fonctionnalité spécifique.
* `release-vX.0.0` : branche dédiée à une version ; nous y appliquons des correctifs (hot-fix) avant la publication.

### GitHub Action

[GitHub Action](https://github.com/ayaka-notes/overleaf-pro/actions) se charge de la CI/CD automatique, qui comprend :

* La mise à jour nocturne de la branche main
* La construction de l'image Docker de développement
* La publication de l'image Docker

### Questions fréquentes

<Accordion title="Comment trouver le hash de commit de l'édition communautaire d'Overleaf `X.0.0` ?">

Commencez par récupérer l'image Docker, puis exécutez la commande suivante pour inspecter les labels de cette image :

```shellscript title="bash" wrap
docker inspect --format='{{json .Config.Labels}}' sharelatex/sharelatex:6.0.0
{"com.overleaf.ce.revision":"b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f","org.opencontainers.image.ref.name":"ubuntu","org.opencontainers.image.version":"24.04"}
```

Vous pouvez ensuite vérifier si le [commit (b0d05c0)](https://github.com/overleaf/overleaf/commit/b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f) est présent dans la branche master amont.

</Accordion>

<Accordion title="Pourquoi le hash de commit est-il identique dans l'image CE entre `6.0.0` et `6.0.1` ?">

C'est un comportement attendu. La version 6.0.1 est un correctif mineur construit à partir de l'image 6.0.0. Les modifications sont appliquées en patchant l'image 6.0.0 existante, au lieu de reconstruire l'image à partir d'un nouveau commit. Le hash de commit contenu dans l'image est donc identique entre 6.0.0 et 6.0.1.

Pour plus de détails, consultez [hotfix](https://github.com/overleaf/overleaf/tree/main/server-ce/hotfix).

</Accordion>
