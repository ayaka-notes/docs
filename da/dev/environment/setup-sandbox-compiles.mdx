Sandkassekompileringer fungerer lidt anderledes i udviklingsmiljøet end i produktionsimaget. Udviklingsmiljøet har dem allerede sat op; denne side forklarer indstillingerne og tre ting, du skal være opmærksom på:

* Problem med filrettigheder
* Delt volume mellem history-v1 og filestore
* Problem med undermapper

### Aktivér Sandbox Compiles {#enable-sandbox-compiles}

Sandkassekompileringer er slået til som standard. `develop/docker-compose.yml` sætter `SANDBOXED_COMPILES=true` for `clsi`, og `develop/dev.env` indeholder resten:

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

clsi henter ikke images selv, så hent imagene én gang med `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1` (og `:2025.1`).

LaTeX kører i søskendecontainerne som `TEXLIVE_IMAGE_USER`. I udviklingsmiljøet er det `tex`, som også er clsis standard (`services/clsi/config/settings.defaults.cjs:154`). Produktionsimaget bruger i stedet `www-data`, når `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` (`server-ce/config/env.sh:15-21`), fordi filerne dér oprettes af brugeren `www-data` i Overleaf-containeren.

<Warning>

Brug venligst ikke dit eget byggede image, da du kan støde på en række fejl.

</Warning>

### Ret filrettigheder {#fix-file-permissions}

clsi-containeren starter som root, giver mapperne `compiles`, `output` og `cache` til brugeren `node` (uid `1000`) og kører derefter clsi som `node` (`services/clsi/entrypoint.sh`). Derfor tilhører `develop/compiles` på værten uid `1000`, samme uid som `tex` i udviklingsmiljøet (se kommentaren i `develop/pandoc/Dockerfile`). Med indstillingerne ovenfor kompilerer udviklingsmiljøet uden nogen ændring af rettigheder.

Hvis du i stedet sætter `TEXLIVE_IMAGE_USER=root`, har root (uid `0`) ikke tilladelse til at skrive til undermapperne i `compiles`. Giv i så fald gruppen `root` ejerskab og skriverettighed til `compiles`, med `setgid` sat, så nye undermapper arver dette ejerskab:

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

For detaljeret dokumentation kan du se `services/clsi/README.md`.

### Delt volume mellem history-v1 og filestore {#volume-share-between-history-v1-and-filestore}

<Info>

Indstillingerne i dette og det næste afsnit findes allerede i `develop/docker-compose.yml` og `develop/dev.env`. De har kun betydning med `S3_ENABLED=false` i `develop/dev.rc`. Med standardværdien `S3_ENABLED=true` gemmer filestore og history-v1 i stedet disse filer i RustFS-buckets (`develop/s3/docker-compose.yml`).

</Info>

Som standard fungerer filestore som en bro mellem S3 og andre tjenester i Overleaf. I Overleaf CE eller Server Pro gemmes alle filer dog lokalt som standard. Derfor har Overleaf indført en meget snedig metode.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

Samtidig bruges `data/history` også af historiktjenesten. På den måde kan forskellige mikrotjenester dele de samme data. Derfor monterer filestore-tjenesten i develop volumet `history-v1-buckets` fra history-v1. Uden det **kan clsi ikke hente blob-filer fra filestore-tjenesten**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

filestore finder bucketsene via disse indstillinger i `dev.env`:

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### Brug undermapper {#use-subdirectories}

filestore læser altid historikblobs med undermapper (`services/filestore/app/js/KeyBuilder.js:58`, `:70`). Produktionsimaget slår `useSubdirectories` til for history-v1 (`server-ce/config/production.json`), men det gør standardkonfigurationen af history-v1 ikke, så i udvikling ville history-v1 <strong>gøre alle data flade.</strong> Derfor sætter `dev.env` `NODE_CONFIG` for history-v1:&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

Uden den gemmer history-v1 `project_blobs`-filerne sådan her:

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

Med `useSubdirectories` sat til `true` bliver `_` i disse navne til `/`, så hver blob gemmes i undermapper.
