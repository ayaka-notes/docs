Denne side beskriver de miljøvariabler, der understøttes i filen `config/overleaf.rc` ved Toolkit-udrulninger.

Filen `config/overleaf.rc` består af variabeldefinitioner i formen `NAME=value`. Linjer, der begynder med `#`, behandles som kommentarer.

<Info>

Det er nødvendigt at genoprette Docker-containerne ved at køre `bin/up`, efter at du har ændret noget i `overleaf.rc` eller `variables.env`.

</Info>

## Container

### `sharelatex`

| Navn                         | Beskrivelse |
| ---------------------------- | ----------- |
| `PROJECT_NAME`               | <p>Sætter værdien af flaget `--project-name`, der gives til `docker-compose`. Det er nyttigt, når der kører flere Overleaf-instanser på én vært, da hver instans kan have sit eget projektnavn.<br /><br />- <strong>Standard</strong>: `overleaf`</p> |
| `OVERLEAF_IMAGE_NAME`        | <p>Docker-image, der bruges af Server Pro/CE-applikationscontaineren. Dette er kun navnet på Docker-imaget; Docker-image-tagget hentes fra `config/version`.<br /><br />- <strong>Standard:</strong><br />- Server Pro: `ghcr.io/ayaka-notes/overleaf-pro`<br />- Community Edition: `sharelatex/sharelatex`</p> |
| `SERVER_PRO`                 | <p>Når den er sat til `true`, får Toolkit besked på at bruge Server Pro-imaget (`ghcr.io/ayaka-notes/overleaf-pro`) i stedet for standard-Server CE-imaget (`sharelatex/sharelatex`).<br /><br />- <strong>Standard</strong>: `false`</p> |
| `GIT_BRIDGE_ENABLED`         | <p>Sæt til `true` for at aktivere git-bridge-funktionen (kun Server Pro). Se brugerdokumentationen <a href="https://www.overleaf.com/learn/how-to/Git_integration">https://www.overleaf.com/learn/how-to/Git_integration</a> for flere oplysninger.<br /><br />- <strong>Standard:</strong> `false`</p> |
| `GIT_BRIDGE_IMAGE`           | <p>Docker-image, der bruges af git-bridge-containeren (kun Server Pro). Dette er kun navnet på Docker-imaget; Docker-image-tagget hentes fra `config/version`.<br /><br />- <strong>Standard:</strong> `ghcr.io/ayaka-notes/overleaf-pro/git-bridge`</p> |
| `GIT_BRIDGE_DATA_PATH`       | Sætter stien til den mappe, der monteres i `git-bridge`-containeren (kun Server Pro) og bruges til at gemme git-repositorierne. Det kan enten være en fuld sti (der begynder med `/`) eller en sti relativ til Toolkits basismappe. |
| `GIT_BRIDGE_LOG_LEVEL`       | <p>Konfigurerer logniveauet for `git-bridge`-containeren. Tilgængelige niveauer: `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`.<br /><br />- <strong>Standard:</strong> `INFO`</p> |
| `SIBLING_CONTAINERS_ENABLED` | <p>Når den er sat til `true`, får Toolkit besked på at bruge teknikken <strong>Sibling Containers</strong> til at kompilere projekter i separate sandboxes med en separat Docker-container for hvert projekt. Se dokumentationen &#x3C;server-pro-only-configuration/sandboxed-compiles> for flere oplysninger.<br /><br />- <strong>Kræver:</strong> `SERVER_PRO=true`<br />- <strong>Standard:</strong> `true`</p> |
| `SIBLING_CONTAINERS_PULL`    | <p>Når den er sat til `true`, får Toolkit besked på automatisk at hente alle TeX Live-images, der er angivet med `ALL_TEX_LIVE_DOCKER_IMAGES` i filen <strong>config/variables.env</strong>, når kommandoen `bin/up` bruges.<br /><br />- <strong>Standard:</strong> `true`</p> |
| `DOCKER_SOCKET_PATH`         | <p>Sætter stien til Docker-socket på værtsmaskinen (den maskine, der kører Toolkit). Når `SIBLING_CONTAINERS_ENABLED` er `true`, monteres socket i containeren, så kompileringstjenesten kan starte nye Docker-containere på værten.<br /><br />- <strong>Kræver:</strong> `SIBLING_CONTAINERS_ENABLED=true`<br />- <strong>Standard:</strong> `/var/run/docker.sock`</p> |
| `OVERLEAF_DATA_PATH`         | <p>Sætter stien til den mappe, der monteres i hovedcontaineren `sharelatex` og bruges til at gemme kompileringsdata. Det kan enten være en fuld sti (der begynder med `/`) eller en sti relativ til Toolkits basismappe.<br /><br />- <strong>Standard:</strong> `data/overleaf`</p> |
| `OVERLEAF_LISTEN_IP`         | <p>Sætter den eller de IP-adresser på værten, som containeren binder til. Hvis den f.eks. er sat til `0.0.0.0`, vil webgrænsefladen være tilgængelig på alle værtens IP-adresser. Ved direkte adgang til containeren skal værdien af `OVERLEAF_LISTEN_IP` sættes til din offentlige IP-adresse. Hvis `OVERLEAF_LISTEN_IP` sættes til enten `0.0.0.0` eller værtens eksterne IP, vil det typisk give fejl, når den bruges sammen med .<br /><br />- <strong>Standard:</strong> `127.0.0.1`</p> |
| `OVERLEAF_PORT`              | <p>Sætter den port på værten, som containeren binder til. Hvis den f.eks. er sat til `8099`, og `OVERLEAF_LISTEN_IP` er sat til `127.0.0.1`, vil webgrænsefladen være tilgængelig på `http://localhost:8099`.<br /><br />- <strong>Standard:</strong> `80`</p> |
| `OVERLEAF_LOG_PATH`          | <p>Sætter stien til den mappe, der monteres i hovedcontaineren `sharelatex` og bruges til at gøre applikationslogfiler tilgængelige på Docker-værten. Det kan enten være en fuld sti (der begynder med `/`) eller en sti relativ til Toolkits basismappe. Fjern konfigurationsposten for at deaktivere bind-mounten. Hvis den ikke er sat, kasseres logfilerne, når containeren genoprettes.<br /><br />Se for oplysninger om logning.<br /><br />- <strong>Standard:</strong> ikke sat</p> |

### `mongo`

| Navn              | Beskrivelse |
| ----------------- | ----------- |
| `MONGO_ENABLED`   | <p>Når den er sat til `true`, får Toolkit besked på at oprette en MongoDB-container til databasen. Når den er sat til `false`, oprettes denne container ikke, og systemet bruger i stedet den MongoDB-database, der er angivet med `MONGO_URL`.<br /><br />- <strong>Standard</strong>: `true`</p> |
| `MONGO_URL`       | <p>Angiver den MongoDB-forbindelses-URL, der skal bruges, når `MONGO_ENABLED` er `false`.<br /><br />- <strong>Standard</strong>: ikke sat</p> |
| `MONGO_DATA_PATH` | <p>Sætter stien til den mappe, der monteres i `mongo`-containeren og bruges til at gemme MongoDB-databasen. Det kan enten være en fuld sti (der begynder med `/`) eller en sti relativ til toolkittets basismappe. Denne indstilling påvirker kun den lokale `mongo`-container, der oprettes, når `MONGO_ENABLED` er `true`.<br /><br />- <strong>Standard</strong>: `data/mongo`</p> |
| `MONGO_IMAGE`     | <p>Docker-image, der bruges af MongoDB-containeren. Dette er kun navnet på Docker-imaget; Docker-image-tagget skal angives i `MONGO_VERSION` (se nedenfor).<br /><br />- <strong>Standard:</strong> `mongo`</p> |
| `MONGO_VERSION`   | <p>MongoDB-version, der bruges af MongoDB-containeren. Værdien skal begynde med MongoDB-hovedversionen og et punktum, f.eks. `6.0` eller `6.0-with-suffix`.<br /><br />- <strong>Standard:</strong> `6.0`</p> |

### `redis`

| Navn                    | Beskrivelse |
| ----------------------- | ----------- |
| `REDIS_ENABLED`         | <p>Når den er sat til `true`, får Toolkit besked på at oprette en Redis-container til Redis-databasen. Når den er sat til `false`, oprettes denne container ikke, og systemet bruger i stedet den Redis-database, der er angivet med `REDIS_HOST` og `REDIS_PORT`.<br /><br />- <strong>Standard</strong>: `true`</p> |
| `REDIS_HOST`            | <p>Angiver den Redis-vært, der skal bruges, når `REDIS_ENABLED` er `false`.<br /><br />- <strong>Standard</strong>: ikke sat</p> |
| `REDIS_PORT`            | <p>Angiver den Redis-port, der skal bruges, når `REDIS_ENABLED` er `false`.<br /><br />- <strong>Standard</strong>: ikke sat</p> |
| `REDIS_DATA_PATH`       | <p>Sætter stien til den mappe, der monteres i `redis`-containeren og bruges til at gemme Redis-databasen. Det kan enten være en fuld sti (der begynder med `/`) eller en sti relativ til Toolkits basismappe. Denne indstilling påvirker kun den lokale `redis`-container, der oprettes, når `REDIS_ENABLED` er `true`.<br /><br />- <strong>Standard</strong>: `data/redis`</p> |
| `REDIS_AOF_PERSISTENCE` | <p>Slår AOF-persistens (Append Only File) til for Redis. Dette er den <strong>anbefalede</strong> konfiguration for Redis-persistens.<br /><br />Se afsnittet &#x3C;../../../maintenance/data-and-backups#aof-append-only-file> i &#x3C;../../maintenance/data-and-backups> for flere detaljer.<br /><br />- <strong>Standard:</strong> `true`</p> |

### `nginx`

| Navn                   | Beskrivelse |
| ---------------------- | ----------- |
| `NGINX_ENABLED`        | <p>Når den er sat til `true`, får Toolkit besked på at oprette en NGINX-container, der fungerer som TLS-proxy.<br /><br />- <strong>Standard</strong>: `false`</p> |
| `NGINX_CONFIG_PATH`    | <p>Sti til den NGINX-konfigurationsfil, der skal bruges til TLS-proxyen.<br /><br />- <strong>Standard</strong>: `config/nginx/nginx.conf`</p> |
| `NGINX_TLS_LISTEN_IP`  | <p>Sætter den eller de IP-adresser på værten, som TLS-proxycontaineren binder til for HTTPS. Hvis den f.eks. er sat til `0.0.0.0`, vil HTTPS-webgrænsefladen være tilgængelig på alle værtens IP-adresser. Typisk bør den sættes til værtens eksterne IP.<br /><br />- <strong>Standard</strong>: `127.0.1.1`</p> |
| `NGINX_HTTP_LISTEN_IP` | <p>Sætter den eller de IP-adresser på værten, som TLS-proxycontaineren binder til for HTTP-omdirigering. Hvis den f.eks. er sat til `127.0.1.1`, vil HTTP-forbindelser til `127.0.1.1` blive omdirigeret til HTTPS-webgrænsefladen. Typisk bør den sættes til værtens eksterne IP. Sæt den ikke til `0.0.0.0`, da det typisk vil give en konflikt med `OVERLEAF_LISTEN_IP`.<br /><br />- <strong>Standard</strong>: `127.0.1.1`</p> |
| `NGINX_HTTP_PORT`      | <p>Sætter den port på værten, som TLS-proxycontaineren binder til for HTTP.<br /><br />- <strong>Standard</strong>: `80`</p> |
| `TLS_PORT`             | <p>Sætter den port på værten, som TLS-proxycontaineren binder til for HTTPS.<br /><br />- <strong>Standard</strong>: `443`</p> |
| `TLS_PRIVATE_KEY_PATH` | <p>Sti til den private nøgle, der skal bruges til TLS-proxyen.<br /><br />- <strong>Standard</strong>: `config/nginx/certs/overleaf_key.pem`</p> |
| `TLS_CERTIFICATE_PATH` | <p>Sti til det offentlige certifikat, der skal bruges til TLS-proxyen.<br /><br />- <strong>Standard</strong>: `config/nginx/certs/overleaf_certificate.pem`</p> |
