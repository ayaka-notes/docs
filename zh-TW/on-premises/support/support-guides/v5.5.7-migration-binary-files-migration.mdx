## 二進位檔案遷移

即將推出的 Server Pro 與 Community Edition 主要版本 `6.0` 會將二進位檔案的儲存空間用量減半。版本 `5.5.7` 包含線上遷移功能，讓升級過程中的停機時間降到最低。

自 Server Pro `4.x` 起，二進位檔案會儲存兩份：一份在「filestore」的作用中檔案儲存區，另一份在完整專案歷史記錄系統中。今後，每個檔案只會在完整專案歷史記錄系統中儲存一份。

遷移至整合儲存系統包含兩個部分：一個用於控制遷移階段的新旗標，以及一個處理所有作用中與軟刪除專案的指令碼。

階段：

* `OVERLEAF_FILESTORE_MIGRATION_LEVEL=0`（預設）：檔案從 filestore 讀取並寫入 filestore，並以非同步方式寫入歷史記錄。
* `OVERLEAF_FILESTORE_MIGRATION_LEVEL=1`：檔案從歷史記錄讀取，並以 filestore 作為備援，同時寫入 filestore 與歷史記錄。可以降級回 `OVERLEAF_FILESTORE_MIGRATION_LEVEL=0`。
* `OVERLEAF_FILESTORE_MIGRATION_LEVEL=2`：檔案僅從歷史記錄讀取並寫入歷史記錄。除非遷移是以「離線」方式執行，否則無法降級回 `OVERLEAF_FILESTORE_MIGRATION_LEVEL=1`。

若將資料儲存在 [S3](https://docs.overleaf.com/on-premises/configuration/overleaf-toolkit/s3)，且 filestore（`OVERLEAF_FILESTORE_S3_ACCESS_KEY_ID`）與歷史記錄（`OVERLEAF_HISTORY_S3_ACCESS_KEY_ID`）使用不同的服務帳號：請授予 filestore 使用者對歷史記錄 blob 儲存桶 `OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET` 的讀取權限。今後，filestore 服務將負責處理來自編譯服務的讀取請求。

<Warning>

強烈建議先在非正式／沙箱環境中執行二進位檔案遷移。

</Warning>

<Check>

標準的 Server Pro 授權允許您在一個正式環境以及一個非正式／沙箱環境中執行應用程式；強烈建議您配置一個非正式環境用於測試。

</Check>

<Info>

如果您升級至 Server Pro/CE 版本 `6.0` 後決定降級回較早的版本，則應從完整的系統備份還原。

</Info>

### 遷移程序

<Steps>
<Step title="建立備份">
為執行個體建立完整的[備份](https://docs.overleaf.com/on-premises/maintenance/data-and-backups#performing-a-consistent-backup)，包含 **mongo**、**redis** 與 **sharelatex** 目錄的一致性快照。
</Step>

<Step title="更新">
**Toolkit：**使用 `$ bin/upgrade` 指令碼將 **toolkit** 升級至最新版本。當出現提示 **Upgrade** image? 時，**請勿**確認，而是手動編輯 **config/version** 檔案，並將值設為 `5.5.7`。

**舊版 docker-compose.yml：**將 `sharelatex` 服務的版本更新為 `5.5.7`。
</Step>

#### 離線遷移

如果您想在二進位檔案遷移指令碼執行期間阻止使用者登入，請依照以下步驟操作：

* 使用管理員帳號登入您的 Overleaf 執行個體
* 點擊 **Admin** 按鈕並選擇 **Manage Site**
* 點擊 **Open/Close Editor** 分頁
* 點擊 **Close Editor** 按鈕
* 點擊 **Disconnect all users** 按鈕

完成後，任何已登入的使用者都會被重新導向至維護頁面，而造訪登入頁面的新使用者也會看到維護頁面，且**無法**登入。

重新啟動執行個體時，您需要重複這些步驟。若要重新開放網站，只需重新啟動執行個體即可。

#### 線上遷移

您可以在應用程式仍在執行時執行遷移指令碼。需要注意以下幾點：

* 遷移過程需要大量 I/O，指令碼執行期間應監控資源使用情況。
* 處理並行度較高時，`filestore` 服務的事件迴圈可能會出現阻塞，導致使用者體驗下降。我們建議從預設值 `--concurrency=10` 與 `--concurrent-batches=1` 開始。
* 您可以隨時停止指令碼。再次啟動時，會驗證先前的專案並略過已處理的檔案。如果您偏好在較不繁忙的時段（例如夜間）執行遷移，這會很有用。

當您的專案數量少於 1000 個時（請參閱以 `--report` 執行遷移指令碼的輸出），我們建議關閉網站，並在維護時段以離線方式執行遷移。如果專案數量很多，您可以先執行指令碼並監控進度，再依實際情況決定要繼續線上或離線執行。

#### 清除舊版二進位檔案資料

完成遷移並確認專案仍能存取所有檔案後，您可以移除 `/var/lib/overleaf/data/user_files` 中的舊檔案儲存區。我們強烈建議保留這些檔案一段時間；您可以先將資料夾重新命名，讓應用程式無法存取它們。

### 疑難排解

我們會在此處新增疑難排解建議。請注意，雖然我們通常只為 Server Pro 客戶提供支援，但考量到此次遷移的性質，我們也會盡力協助遇到二進位檔案遷移特定問題的 CE 客戶。

如果二進位檔案遷移指令碼失敗（亦即以錯誤結束，或印出的失敗專案數不為零），請以電子郵件將下列詳細資訊寄給我們的支援團隊 [support+filestoremigration@overleaf.com](mailto:support+filestoremigration@overleaf.com?subject=Binary%20file%20migration%20problem&body=Instance%20Type%3A%20CE%20or%20Server%20Pro%20%28delete%20as%20appropriate%29%0A%0AInstallation%20Type%3A%20Overleaf%20toolkit%20or%20docker-compose.yml%20or%20other%20%28delete%20as%20appropriate%29%0A%0AScript%20output%3A%0A%0Abin%2Fdoctor%20output%20%28if%20using%20toolkit%29%3A%0A），內容包括：

```bash

```

附加日誌檔案之前，請先遮蔽其中的任何敏感資訊。

#### 遺失的檔案

舊版的 Server Pro/CE 會在使用者上傳完成前就建立檔案樹項目，因此上傳失敗時，檔案可能會顯示為遺失。在處理所有檔案樹時，您可能會發現少數這類情況被回報為錯誤。

如果遺失的檔案數量不多，可以考慮手動檢查這些情況，並在瀏覽器的編輯器中將其刪除。

如果遺失的檔案數量很多，請考慮聯絡支援團隊，請參閱上方的電子郵件範本。

#### 找出損壞的檔案樹

對於檔案樹格式錯誤的專案（例如檔案名稱為空），遷移可能會失敗。您可以使用 `find_malformed_filetrees` 指令碼檢查資料庫中的所有專案，找出這些問題的清單：

```bash wrap
$ bin/docker-compose exec sharelatex /bin/bash -c "cd /overleaf/services/web && /sbin/setuser www-data node scripts/find_malformed_filetrees.mjs > /tmp/malformed-file-trees.json"
```

若要修正無效的路徑，請使用 `fix_malformed_filetree` 指令碼，針對每個有問題的路徑各執行一次指令：

```bash wrap
$ bin/docker-compose exec sharelatex /bin/bash -c "cd /overleaf/services/web && /sbin/setuser www-data node scripts/fix_malformed_filetree.mjs --logs=/tmp/malformed-file-trees.json"
```
