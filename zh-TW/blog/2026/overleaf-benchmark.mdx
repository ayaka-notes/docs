## 摘要

自行託管的 Overleaf 部署通常以一條經驗法則來估算規模：每五到十位並行使用者配置一個 CPU 核心與 1 GB 記憶體。我們證明這條法則不僅不夠精確，而且在結構上就是錯誤的：它假設容量由單一資源維度決定，但實際上是由兩道彼此獨立的「牆」所決定；此外，兩個軟體參數（而非硬體）對結果的影響可高達四倍。

我們在 QEMU/KVM 客體中，以 21 種 CPU／記憶體組態，測量了一個啟用沙箱編譯（TeX Live 2025）的標準 Ayakaleaf Pro v6.2.2 部署，主機核心時脈鎖定在 3.0 GHz。工作負載是一份真實的 63 頁 XeLaTeX 學位論文，由多達數百個不同使用者帳號同時編譯。我們發現，在客體記憶體低於 32 GiB 時，核心數量幾乎無關緊要——在 16 GiB 下，4、8 與 16 vCPU 客體的實測容量差異不到 8%——容量反而受制於一道超線性的記憶體牆，其成因是 TeX Live 目錄樹在共用頁面快取（page cache）上的競爭。

為了探討這些規律在規模放大一個數量級後是否依然成立，我們在一台 64 核心、995 GiB 的單一伺服器上重複了這組測試。它能以 100% 成功率承受 1024 個同時進行的冷編譯——是其執行緒數的八倍——而我們始終沒有觸及它的上限。真正有用的數字不是那個上限，而是其下方的拐點：尾端延遲在 $N=256$ 之前每倍增一次成長 20–40%，到 $N=512$ 時則成長 190%。因此，若以「不會失敗的最大並行數」來回報容量，將會把實際可用的運作點高估四倍。在那台機器上，記憶體從來不是瓶頸；限制來自 CPU，以及容器常駐程式（daemon）接納新沙箱的速率，無論請求多少編譯，該速率都會在約 200 附近飽和。

我們進一步找出兩個在容量規劃中看不見的實作層級效應。第一，CLSI 強制執行一個寫死的上限：最多 65 個同時編譯，且無法透過任何環境變數調整；超過此上限時，使用者會立即收到 HTTP 503，而不是被放入佇列。第二，Docker runner 中的每容器記憶體限制自 2018 年引入以來就一直無效，無論是數值大小還是設定位置都有問題，因此記憶體不足事件會拖垮整台主機，而不只是單一編譯。解除並行上限並將預設編譯逾時從 180 秒提高到 300 秒後，8 vCPU / 48 GiB 客體的實測容量從 64 個並行編譯提升到 268 個——在零硬體成本下提升了 4.2 倍。

最後，我們證明在此系統中，並行帶來的只有分時共享，而工作負載僅受時脈限制。擬合出的退化定律 $T(N)=T_1\max(1,N/C)^{b}$ 得到 $b=0.914$，接近完美的比例減速；而在機器完整的 1.0–5.5 GHz 範圍內進行的時脈掃描，將三十個測量值收斂到 $T=(k/f)\max(1,N/C)$，其中 $k=27.9 GHz·s$，殘差離散度為 5.1%。5.5 倍的時脈帶來 5.5 倍的加速，沒有邊際報酬遞減。這正是時脈與核心帶來不同效益的意義所在：時脈讓每位使用者的編譯都更快，核心只能接納更多使用者。

## 1. 簡介

Overleaf 是最主流的協作式 LaTeX 編輯器，其本地部署版本廣泛被無法將未發表稿件傳送至第三方雲端的大學與研究團隊採用。估算此類部署的規模是一個反覆出現的實務問題：在固定的硬體預算下，究竟有多少人能同時按下「Recompile」？

官方指引是一條線性法則——大約每五到十位並行使用者配置一個核心與 1 GB 記憶體——其前提是容量會在兩種資源上平滑且共同地擴展。我們的測量結果在三個方面與此相矛盾。

### 1.1 容量由兩道獨立的牆決定，而非一道

一個組態會失敗，若不是因為記憶體耗盡（此時 Overleaf 堆疊本身會當掉並回傳 HTTP 502），就是因為編譯超過伺服器端逾時（此時 CLSI 回報 `timedout`，而數 GB 的記憶體仍閒置未用）。這兩種狀態的擴展行為與補救方式完全不同。為受記憶體限制的組態增加核心不僅沒有效率，有時甚至適得其反：我們測量到某些組態中，增加核心數反而_降低_了容量，因為更多核心會讓並行編譯同步推進，使它們的記憶體需求高峰重疊，而不是彼此錯開。

### 1.2 軟體參數的影響大於硬體

編譯逾時是 MongoDB 中的一個每使用者欄位，其預設值 180 秒會默默地限制受 CPU 限制的組態。在硬體不變的情況下，將其提高到 300 秒可使實測容量提升高達 4.2 倍。另外，CLSI 會透過一個寫死的常數拒絕超過 65 個同時編譯。任何沒有同時考慮這兩點的容量研究——以及任何部署——測量的都是軟體，而不是機器。

### 1.3 並行是分時共享，而非平行運算

由於 LaTeX 編譯是單執行緒的，在 $C$ 個核心上服務 $N$ 位同時使用者並不會讓系統更快完成；它只會讓每位使用者按比例等待更久。因此，在確定使用者願意等待多久之前，「能支援多少並行使用者」這個問題本身就是不適定的。我們將這個相依關係明確化並加以量化。

### 1.4 貢獻

* 一份涵蓋 21 種 CPU／記憶體組態的容量矩陣，在時脈鎖定、經重複驗證的條件下測量，並依各組態的失敗特徵識別出其約束條件。
* 兩個擬合模型：一個將超線性記憶體牆與 CPU 上限分開的容量模型，以及一個確立純分時共享行為的延遲模型。
* 識別並以實驗證實已部署系統中的兩個實作問題，包括一個自 2018 年以來一直無效的容器記憶體限制。
* 量化編譯逾時與容量之間的取捨，我們認為任何並行數據都必須同時註明此取捨。

## 2. 背景

### 2.1 編譯路徑

Overleaf 的編譯請求依序經過 `web` $\rightarrow$ `clsi` $\rightarrow$ 編譯容器。在沙箱編譯部署中（`SIBLING_CONTAINERS_ENABLED=true`），CLSI 不會在行程內執行 `latexmk`；它會透過以 bind mount 掛載的 socket 請求主機的 Docker 常駐程式，從 TeX Live 映像檔啟動一個全新的容器，並將專案目錄以 bind mount 掛載到 `/compile`。因此，一次編譯就是一個執行單一 `latexmk` 行程的短暫容器。

由此產生三個結果，而這三者都影響了本文的測量。第一，工作單位是單執行緒行程：XeLaTeX 不會平行化。第二，每次編譯的資源隔離完全取決於 Docker runner 所請求的內容——我們在 §6.2 中證明它實際上什麼都沒請求。第三，工作集的主體不是文件，而是 TeX Live 目錄樹——一個約 32 GiB 的唯讀語料，每個並行編譯都會從中讀取，因而透過主機頁面快取共用。這種共用正是我們觀察到超線性記憶體擴展的根源。

### 2.2 啟用沙箱編譯

社群版 Overleaf 會在應用程式容器本身內執行 `latexmk`。Ayakaleaf Pro 與 Overleaf Server Pro 一樣，可以改為在_同層級（sibling）_容器中執行每次編譯——也就是由應用程式在_主機的_ Docker 常駐程式上啟動的容器，而非巢狀於應用程式容器內。兩個 toolkit 設定即可開啟此功能：

```ini
# config/overleaf.rc
SERVER_PRO=true
SIBLING_CONTAINERS_ENABLED=true
DOCKER_SOCKET_PATH=/var/run/docker.sock

# config/variables.env
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2025.1
```

toolkit 會將主機的 Docker socket 以 bind mount 掛載到應用程式容器中，並將這些設定轉換為 CLSI 讀取的環境變數：`SANDBOXED_COMPILES=true`、`SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` 與 `SANDBOXED_COMPILES_HOST_DIR`，最後一個是編譯目錄在_主機上_的路徑。這個路徑很重要：由於啟動編譯容器的是主機的常駐程式，提供給它的 bind mount 必須能在主機的命名空間中解析，而不是在應用程式容器的命名空間中。Server-Pro 的 `config/env.sh` 在此模式下還會強制設定 `TEXLIVE_IMAGE_USER=www-data`，使編譯容器寫入的檔案擁有者保持一致。

驗證方式很直接：編譯期間，主機上會出現一個名為 `project-{projectId}-{userId}-{hash}` 的容器，從 TeX Live 映像檔執行 `latexmk`，並以 0 結束。這就是本文自始至終所測量其數量的單位，我們也將在 §6.2 中報告它完全沒有資源限制的問題。

**為什麼這對本研究很重要。**

同層級容器讓測量變得乾淨——每次編譯都是一個可觀察、獨立排程的作業系統實體——但這也意味著在各編譯之間仲裁 CPU 與記憶體的是客體核心，而非 Overleaf。因此，本文中的每條擴展定律，都是 Linux 排程器套用於 $N$ 個單執行緒行程時的特性，這也是它們如此規律的原因。

### 2.3 兩種失敗模式

我們測量的每個組態都恰好以兩種方式之一失敗，而這個區別可以直接從回應狀態看出，而非推論而來：

* **記憶體耗盡**——Overleaf 堆疊本身失去回應，請求回傳 **HTTP 502**。在失敗等級時，客體的可用記憶體通常低於 500 MiB。
* **編譯逾時**——CLSI 在達到每使用者逾時時終止編譯，並回報狀態 `timedout`。在失敗等級時，可用記憶體通常還有數 GB。

我們依據這個特徵來分類每個組態，而非依據資源比例的經驗法則，這使得「我們撞上了哪道牆」這個問題能直接從資料本身得到解答。

## 3. 研究方法

### 3.1 測試平台與時脈控制

所有客體都在單一 Intel Core i9-14900K 主機上以 QEMU/KVM 執行，主機配備 62 GiB RAM 與 NVMe 儲存裝置。客體為 Ubuntu 24.04，搭配 Docker 29.7，並以 Overleaf Toolkit 部署 Ayakaleaf Pro v6.2.2，使用 `texlive-full:2025.1` 進行沙箱編譯。

除非控制時脈，否則一般桌上型 CPU 無法很好地代表伺服器。KVM 沒有提供設定虛擬時脈的機制：vCPU 是一個主機執行緒，以主機核心當下的頻率執行。因此我們直接限制主機：停用 turbo，並將每個核心的 `scaling_max_freq` 固定在 3.0 GHz，再以 `taskset` 將客體的 vCPU 綁定到實體 P-core。在混合核心 CPU 上這一點很重要：此型號的 E-core 基礎時脈為 2.4 GHz，停用 turbo 後_無法_達到 3.0 GHz，因此若執行過程跑到 E-core 上，就會在不知不覺中測量到一台較慢的機器。在滿載下，我們驗證所有十六個綁定的執行緒都精確地運行在 3000 MHz。一個防護指令碼會在每次基準測試前檢查此不變條件，否則拒絕啟動；它在研究期間抓到了一次 governor 被悄悄重設的情況。

### 3.2 第二個測試平台：一台大型 runner

QEMU 矩陣一次只隔離一個變數，但最多只能用到十六個綁定執行緒。為了探討相同的規律在高一個數量級時是否依然成立，我們在一台大型伺服器上重複了並行測試：一顆 AMD EPYC 7773X（Milan-X，64 核心／128 執行緒，768 MiB L3），配備 995 GiB RAM，執行相同的 Ayakaleaf Pro v6.2.2 映像檔與相同的 `texlive-full:2025.1`。與 QEMU 客體不同，這台機器沒有鎖定時脈：它是一台正式環境等級的伺服器，我們也以此身分來測量它。

有兩項操作上的預防措施是必要的，值得一提，因為少了它們，實驗測量的會是測試工具而不是伺服器。第一，每個容器都被限制在一個 `MemoryMax=940 GiB` 的 `systemd` slice 中，讓失控的測試耗盡的是 cgroup 而非主機。第二，沙箱編譯由主機常駐程式建立，每個都會弄髒自己的寫入時複製層——即使 20.6 GiB 的基礎映像檔是共用的，每個容器仍測得 116 MiB——因此 Docker 資料根目錄被移到一個專用的 NVMe 裝置上。在 $N=1024$ 時，一次測試會寫入約 119 GiB 的暫存層，這是一般根檔案系統放不下的。

### 3.3 工作負載

文件是一份真實的 63 頁碩士論文（SJTU 範本），透過 `latexmk` 以 XeLaTeX 編譯，包含 TikZ 圖、`biblatex` 參考書目處理以及內嵌的 PDF 資產——也就是說，這是一個真實而非合成的負載。在無負載的客體上，單次編譯在所有組態中需要 8.6–9.8 秒，我們將其作為自由運行的基準值 $T_1$。

### 3.4 負載產生

我們建立了 512 個真實使用者帳號，並為每個帳號提供一份專案副本，讓並行編譯的競爭情形與獨立使用者完全相同，而非共用一個專案鎖。請求從主機發送到客體的轉發連接埠，使負載產生不會消耗客體的 CPU。

並行是_同時_發生的，而非錯開的。每個工作階段都先建立完成——登入、CSRF 權杖、編譯器選擇——之後每個執行緒才會休眠到一個共同的時鐘時刻（只計算一次並共用），然後發出其 `POST /project/:id/compile`。這個區別並非吹毛求疵。錯開的漸進負載測量的是穩定佇列下的吞吐量；同時爆發測量的則是一整個教室的學生在同一個截止期限公告後按下同一個按鈕時會發生什麼事，而這正是維運人員真正擔心的情況。兩者的差異不只是一個常數倍數，因為後者填滿編譯佇列的速度比常駐程式清空它的速度還快。

在能夠忠實地送出這種爆發之前，必須先排除四個實務障礙。每一個都值得記錄，因為每一個都會在不知不覺中讓實驗退化成測量測試工具，而非測量伺服器。

#### 3.4.1 兩個速率限制器，而非一個

Overleaf 會依來源位址限制登入次數——每分鐘 20 次嘗試——而我們所有的流量都來自同一台主機。為每位模擬使用者指派不同的 `X-Forwarded-For` 位址可以解除此限制，但立即會碰上第二個較粗略的限制：每個子網路每分鐘約 200 次的配額。因此，將使用者分散在一個連續區塊中，會在第 201 個帳號時失敗。我們改為從使用者索引推導出合成位址，使連續的使用者落在不同的 `/24` 中，

$$
\texttt{203.}\;\big\lfloor i/250 \big\rfloor \bmod 100 + 1\texttt{.}\;
  i \bmod 250 + 1\texttt{.}\; i \bmod 200 + 10 ,
$$

這讓兩個限制器在全部 1024 位使用者下都保持寬鬆。

#### 3.4.2 注入的標頭預設會被丟棄

只設定標頭是不夠的。Express 只會對被告知要信任的對端採用 `X-Forwarded-For`，而 Overleaf 的 `trustedProxyIps` 預設為 `loopback`。由於負載產生器是透過容器的橋接網路而非迴路介面連到應用程式，標頭會被解析後丟棄，每位模擬使用者又都退回到同一個位址。症狀是在恰好第二十次登入時出現一波 `HTTP 429`，很容易被誤判為伺服器過載。必須明確將閘道網路加入信任鏈；在 §4.3 的叢集部署中，還必須加入 pod 與 service 的 CIDR。

#### 3.4.3 負載平衡器會覆寫它被要求保留的標頭

當執行個體位於代理伺服器後方時，慣用的 `option forwardfor` 會將真實用戶端位址_附加_到鏈上，這在正式環境中是正確的行為，但在這裡恰恰是錯的：合成位址會被負載產生器自己的位址取代。此指令必須限定為 `option forwardfor if-none`，讓代理伺服器只在用戶端未提供值時才加入。

#### 3.4.4 用戶端會比伺服器更早耗盡檔案描述元

在 $N=1024$ 時，產生器會同時持有超過一千個 socket，而預設 1024 個描述元的軟性限制會在工作階段建立期間就被觸及，而非在測量期間。這種失敗很安靜：三個工作階段無法建立，執行結果回報 1021 而非 1024，同時一個透過外部指令取得容器數量的取樣執行緒因 `EMFILE` 而終止，悄悄截斷了遙測資料。必須提高產生器上的軟性限制——我們主機上的硬性限制本來就是 1048576——然後重新執行。我們在 §4.3 中報告兩次執行結果：修正後的那次完成了 1024 個中的 1024 個，中位數與被截斷的那次相差在 1.2 秒以內，這也是我們將第一次視為可用但不具權威性的原因。

### 3.5 測量規程

為了可重現性，有幾項方法上的選擇被證明是必要的。

#### 3.5.1 暖機

在剛開機的客體上，頁面快取是空的，最初的編譯測量的是冷啟動 I/O，而非穩態容量：同樣的 2 vCPU / 2 GiB 組態，冷啟動為 36.5 秒，暖機後為 9.8 秒，相差 3.7 倍。因此每個組態在開機後都會執行兩次捨棄結果的單一編譯暖機。

#### 3.5.2 通過標準

一個並行等級只有在_每一個_編譯都成功、且重複執行後依然存活時才算通過。這比成功率門檻更嚴格，而且很重要：在 4 vCPU / 16 GiB 下，32 的等級第一次以 80.2 秒的中位數通過，但重複執行時 32 個編譯全部逾時，因此我們回報 31。

#### 3.5.3 搜尋

各等級的定位方式是：先從模型預測的種子值進行指數式夾擠，再進行精確的整數二分搜尋。由於標準是全有或全無，一個等級在第一次失敗時就已確定，因此只要有一個失敗，我們就放棄其餘仍在進行中的請求——但小等級除外，因為被放棄的編譯會嚴重拖住小型客體，使其再也無法恢復。

#### 3.5.4 等級之間的隔離

在下一個等級開始之前，會先清空編譯容器，並持續輪詢 web 應用程式直到它再次回應。若不這麼做，緊接在當機之後的等級會記錄到虛假的零工作階段失敗。

#### 3.5.5 主機清潔

主機上不相關的虛擬機器都已關閉：當有 24 GiB 的主機記憶體被分配到其他地方時，相同的客體組態在相同並行度下的平均負載為 11.7，而非 3.2。主機的記憶體壓力會傳導到客體中，使測量失效。

#### 4.3.2 退化是次線性的，因為接納速率受到限制

單純的分時共享預測：$8\times$ 的執行緒數會帶來 $8\times$ 的延遲。實測成本相對於單一編譯為 $9.7\times$，但相對於 $N=128$ 只有 $3.8\times$——而施加的負載增加了八倍。原因可以從圖 7(b) 與表 2 的最後一欄看出：雖然 1024 個請求是同時發出的，但實際存活的沙箱數量從未超過 205。常駐程式建立容器的速度跟不上用戶端請求的速度，因此請求在接納階段排隊，而不是在 CPU 內部爭用。正是排隊在這裡拯救了尾端延遲，而且這純屬偶然。

#### 4.3.3 拐點在 512，而不是在失敗點

在 $N=256$ 與 $N=512$ 之間，負載加倍使 $p_{95}$ 延遲上升 $2.9\times$；而之前每次加倍的代價都在 $1.2\times$ 到 $1.4\times$ 之間。若以「不會失敗的最大 $N$」來陳述容量，會回報 1024，而這對維運人員毫無用處：在那個點上，尾端等待時間將近八分鐘。

### 4.4 編譯時間與時脈成反比

由於工作負載受 CPU 限制，其成本應以 $1/f$ 擴展。我們直接驗證這一點：在其他條件不變的客體上，將主機時脈掃過機器的整個範圍，1.0–5.5 GHz，共十個級距（圖 8）。單一編譯時間從 26.5 秒降至 4.8 秒：5.5 倍的時脈帶來 5.5 倍的加速，在整個範圍內都沒有邊際報酬遞減。乘積 $T\!\cdot\!f$ 在全部十個時脈下的變化都在 2% 以內。

以核心配額進行正規化後，全部三十個測量值——十個時脈下的三個並行等級——都收斂到單一常數：

$$
T(N,f) \;=\; \frac{k}{f}\,\max\!\left(1,\frac{N}{C}\right),
  \qquad k = 27.9\ \mathrm{GHz\cdot s}
$$

在時脈本身變化達 5.5 倍的範圍內，殘差離散度為 5.1%。完全沒有曲率本身就是結果：如果工作負載受記憶體頻寬或 I/O 限制，當 CPU 跑得比其他資源快時，$T$ 會在高時脈處趨於平緩。

## 5. 分析

### 5.1 兩道牆，分別擬合

每個組態都依其失敗特徵（§2.3）分類，接著只用實際碰到記憶體牆與 CPU 上限的組態分別進行擬合：

$$
N_{\max} = \min\left(A R^{p},\; k_c C\right)
$$

其中 $R$ 以 GiB 為單位，$C$ 以 vCPU 為單位。

記憶體牆的指數始終是超線性的，$p>1$：每增加一個並行編譯的邊際記憶體成本，會隨著總記憶體增加而_下降_，從 3 GiB 客體上每次編譯約 312 MiB，降到 32 GiB 客體上約 194 MiB。其機制是 §2.1 中描述的 TeX Live 目錄樹共用頁面快取：並行編譯會讀取重疊的字型與巨集檔案，因此較大的快取能被更多編譯分攤。這就是為什麼單純的「每五位使用者 1 GB」法則會低估大型機器、高估小型機器。

### 5.2 更多核心反而更糟的情況

式 (2) 是兩項的最小值，因此對 $C$ 是單調的，但測量結果並非如此。我們觀察到兩次增加核心反而_降低_容量的反轉：在 16 GiB（54 對 45）與 32 GiB（145 對 135）。兩者都發生在受記憶體限制的狀態下，機制也相同：核心越多，並行編譯就越同步推進，並在同一時刻達到其常駐記憶體峰值；而核心較少時，排程器會將它們交錯執行，使峰值錯開。在記憶體餘裕本已捉襟見肘的客體上，正是這種錯開讓它得以存活。以平均資源使用量建構的容量模型無法表達這一點；這是峰值_同時發生_的特性。

第三個看似反轉的情況（在 2 GiB）我們現在不予採計。搜尋結果記錄在 2 vCPU 時容量為 2，但在 4 與 8 vCPU 時為 1，看起來像是相同的效應。重新檢視原始測試資料後，發現原因更簡單：在 2 GiB 時，$N=2$ 這個等級在三種核心數下第一次嘗試都成功了，但在三者之中有兩者的確認執行失敗。這個等級不是容量，而是擲硬幣，而 2 vCPU 那一格只是剛好擲中的那一次。因此我們在三種核心數下都回報可重現的值 1，並且不從這個差異中得出任何結論。我們在此記錄這項修正，而非悄悄地修改表格，因為被捨棄的那個讀數正是那種本來可以支持一個有趣論點的數據。

## 6. 實作層面的發現

### 6.1 寫死的並行上限

在足夠大的客體上，無論請求的並行數為何，容量都恰好停在 65 個同時編譯：在 $N=66,80,96,128$ 時，我們測得 $65$ 次成功，以及 $1,15,31,63$ 次立即的 `unavailable` 回應，容器數量固定在 65，數 GB 的記憶體未被使用，編譯時間中位數穩定在 77 秒——遠低於任何逾時。

原因是 CLSI 中的一個常數：

```javascript
// services/clsi/config/settings.defaults.cjs:110
compileConcurrencyLimit: isSpotInstance ? 32 : 64,

// services/clsi/app/js/LockManager.js
if (LOCKS.size <= Settings.compileConcurrencyLimit) return   // <= admits 64+1
throw new Errors.TooManyCompileRequestsError(...)
```

這個比較是非嚴格的，因此實際上限為 $64+1=65$，與測量結果完全吻合。多出的請求會收到 **HTTP 503**——它們是被_拒絕_，而不是被排入佇列，因此從使用者的角度來看，編譯按鈕就是直接失敗。與同一個檔案中的其他所有可調參數不同，這個參數不讀取任何環境變數；它是在 2024 年 8 月於上游引入的，只能透過修改映像檔來變更。提高此限制後，同一台 16 vCPU / 32 GiB 客體在 $N=80$ 時原本回報 `success=65, unavailable=15`，改為回報 `success=80`。

### 6.2 無效的容器記憶體限制

檢查一個運行中的編譯容器，會發現完全沒有任何資源隔離：

```text
Memory=0  NanoCpus=0  CpuShares=0  CpuQuota=0  CpusetCpus=[]
Ulimits=[{Name:cpu Soft:305 Hard:310}]
```

沒有任何 CPU 配額是刻意設計的，這也解釋了為什麼 §4.2 中的分時共享指數如此乾淨：沒有任何東西扭曲編譯之間的競爭。然而，沒有_記憶體_限制並非刻意設計。Docker runner 確實有請求一個限制：

```javascript
// services/clsi/app/js/DockerRunner.mjs:262
Memory: 1024 * 1024 * 1024 * 1024, // 1 Gb
```

這裡錯了兩次。數值為 $1024^4=1 tebiB$，而註解的本意是 $1024^3$；而且該欄位被放在建立選項的最上層，而不是 Docker API 預期的 `HostConfig` 內，因此會被丟棄——觀察到的 `Memory=0` 證實了這一點。這兩個錯誤都存在於引入該檔案的提交中（`9a519f0d3d`，2018 年 3 月），並且歷經從 CoffeeScript 的轉換、全儲存庫的重新格式化，以及 CJS 到 ESM 的遷移後依然存在，而這些都沒有重新檢視語意。值得注意的是，同一個提交中的 `MAX_OUTPUT = 1024 * 1024 // 1MB` 是正確的，這表示這是一時疏忽，而非誤解。

其後果可以在我們的低記憶體測量中看到。由於編譯沒有限制，記憶體耗盡並不會表現為 Docker 終止某個違規的容器；它會拖垮整個客體。在 2 vCPU / 2 GiB 組態上，我們觀察到監控用的 SSH 工作階段被阻塞 300 秒、兩個核心上的平均負載高達 68，最終客體自行重新開機。一個正常運作的每容器限制會讓退化過程平緩得多：過大的編譯會失敗，但服務會存活下來。

唯一真正生效的限制是 `RLIMIT_CPU`，設為 $\text{timeout}+5$ 秒。它限制的是 _CPU_ 時間，而非實際經過時間，而單次編譯只消耗約 9 秒的 CPU，因此在任何並行數下都不會觸及；它防範的是異常輸入，例如失控的巨集。不過，它是一個很有用的判斷依據：觀察到 `Soft:305` 即可確認 300 秒的逾時設定確實已傳遞到容器。

### 6.3 編譯逾時是影響最大的可調參數

每使用者欄位 `features.compileTimeout` 的預設值為 180 秒。對任何受 CPU 限制的組態而言，這不是安全餘裕，而是容量設定，因為一台仍在正確運算的機器會被判定為失敗。將其提高到 300 秒——只需一次 MongoDB 更新——就能使實測容量改變多達 4.2 倍（表 3）。上限為 600 秒，由 `RequestParser.MAX_TIMEOUT` 強制執行，超過此值會被悄悄截斷。

## 7. 相關研究

### 7.1 廠商指引

Overleaf 自己的硬體文件陳述了我們在此量化的定性事實：LaTeX 是單執行緒的，因此單核心效能決定編譯時間，而且「只有當您嘗試編譯的文件數多於可用的 CPU 核心數時，更多核心才會有幫助」\[1]。接著它給出了線性的規模估算法則——以 2 核心／3 GiB 為基礎，再為每五到十位並行使用者增加一個核心與 1 GB 記憶體——這正是本研究的動機。我們的貢獻是將這些陳述轉化為可測量的定律（式 (1) 與 (2)），並指出線性法則在何處失效：它沒有考慮使記憶體牆呈超線性的共用頁面快取，也沒有考慮主導結果的兩個軟體參數。

### 7.2 建置與 CI 容量研究

在 LaTeX 領域之外，並行條件下建置系統的測量已相當成熟。LightSys 報告指出，在 Docker 容器內編譯的傳統 CI 系統，其 I/O 會隨 pull request 到達率上升而退化，瓶頸約出現在十一個並行請求時 \[17]；TAOS-CI 觀察到編譯主導了 CI 的實際耗時，在大型專案中佔整體管線時間的 60–67% \[18]。我們的系統在一個方面有所不同，而這一點結果證明是決定性的：LaTeX 編譯是互動式的。一個花了兩倍時間的 CI 工作只是不方便；一個花了兩倍時間的編譯，則會被等待預覽窗格的使用者直接感受到，這就是為什麼我們不把逾時當作失敗門檻，而是當作容量參數。

### 7.3 容器開銷

近期研究將 Docker 容器啟動延遲依儲存層級進行拆解 \[19]，並描述邊緣環境中的容器效能 \[20]。在我們的情境中，每次編譯的容器啟動成本被分攤掉了：相對於 9 秒的編譯，它只是一個小常數，並被我們擬合的自由運行時間 $T_1$ 吸收。真正重要的容器特性是資源限制的_缺失_（§6.2），它將單次編譯的記憶體超用轉變為整台主機的故障。

### 7.4 將 LaTeX 視為不受信任的輸入

沙箱編譯之所以存在，是因為 TeX 是一種程式語言，而文件是不受信任的輸入 \[21, 22]。這個設計選擇使本研究成為可能——每次編譯都是一個具有可觀察資源行為的隔離容器——同時也使記憶體限制的缺失變得影響重大，因為部署它的維運人員會假設隔離是存在的。

### 7.5 以編譯器作為研究對象

TeX 本身作為一種語言已有完善的文件 \[16]，但它作為_建置目標_的行為直到最近才受到關注。Tan 與 Rigger \[8] 在不同引擎與發行版本之間編譯了大量 arXiv 原始檔，發現引擎的選擇無法互相替代：只有不到百分之一的文件在 XeTeX 與 pdfTeX 下產生位元組完全相同的輸出。這個結果直接影響我們的研究方法。容量是文件_與_引擎共同的特性，因此沒有同時固定兩者的基準測試是無法重現的；因此我們自始至終固定一份文件、一個引擎與一個發行版本（`texlive-full:2025.1`），並在每張圖的說明中註明引擎。這也限制了我們數據的普遍性，值得明白指出：它們描述的是 XeLaTeX 在這份文件上的表現，而不是抽象意義上的 TeX。

關於 LaTeX 建置_系統_的研究大多由實務工作者推動。LaTeX3 專案的 `l3build` \[13] 將回歸測試與封裝標準化，獨立的基準測試則比較各種包裝工具——一項針對 26 種建置系統的調查發現，預編譯的導言區比一般執行快約 20%，比 `latexmk` 快約 40% \[14]。這些最佳化的是_單次_編譯。它們與我們所測量的內容是正交的，且可以疊加：導言區快取會縮短 $T_1$，而本文中的每個容量數據都隨 $T_1$ 而縮放。

### 7.6 並行控制在編輯器中，而非編譯器中

Overleaf 的協作部分建立在一系列成熟的研究之上。操作轉換（operational transformation）源自 Ellis 與 Gibbs \[9]，並由 Jupiter 系統 \[10] 使其適用於高延遲用戶端，其設計在 `document-updater` 中清晰可辨：一個負責排序操作的伺服器，以及一個供用戶端同步的每文件緩衝區。無衝突複製資料型別（CRDT）\[11] 則在沒有中央排序器的情況下解決了相同問題。這個區別正是 §4.3 的拓撲能夠運作的關鍵：由於待處理更新緩衝區存在於共用的 Redis 中，而非某個執行個體的記憶體中，因此路由到任何複本的編譯都能看到最新的按鍵輸入，而編譯親和性可以依快取區域性來選擇，而不必考慮正確性。

### 7.7 容量模型

Amdahl 定律 \[24] 限制了平行化帶來的加速，Little 定律 \[23] 則將佔用量與到達率及服務時間關聯起來；上文兩者皆有使用。Gunther 的通用可擴展性定律 \[12] 在前者的基礎上加入了一個代表一致性延遲的逆行項，預測吞吐量會先達到高峰再下降。我們注意到，直到 $N=1024$，我們的系統都_沒有_出現那種逆行狀態：吞吐量飽和、延遲成長，但沒有任何崩潰。原因是結構性的而非僥倖——編譯之間沒有需要保持一致的共用狀態，因此該定律所加入的項接近於零，而 §4.3 的接納平台期會在爭用變得重要之前就將其封頂。

## 8. 給維運人員的建議

<Steps>
<Step title="在購買硬體之前，先調整兩個軟體參數">
兩者都是免費的，而且兩者的價值都高於我們測量過的任何單一硬體升級。將 `features.compileTimeout` 提高到使用者實際能容忍的值——CLSI 接受的最大值為 600 秒——並且，如果您預期會超過 65 個同時編譯，請在衍生映像檔中解除 `compileConcurrencyLimit`，或進行水平擴展。兩者都不做，就等於花錢買了軟體拒絕使用的核心。
</Step>

<Step title="依拐點而非上限來估算單一機器的規模">
大型 runner 的測試（§4.3）區分了兩個經常被混為一談的數字。_上限_——仍能回傳每一份 PDF 的最大並行數——在 64 核心伺服器上至少為 1024，而我們從未觸及它。_拐點_——尾端延遲不再緩慢成長、開始倍增的那個點——在 512，而其下方最後一個舒適的運作點是 256。在 $N=256$ 與 $N=512$ 之間，$p_{95}$ 等待時間從兩分鐘增加到將近六分鐘；在 512 與 1024 之間則達到八分鐘。依上限估算規模的維運人員，交付的是一個技術上可行、卻沒有人想用的系統。

因此，對於這台機器與這份文件，建議的運作點是 **256 個並行編譯**，即實體核心數的 $4\times$、執行緒數的 $2\times$，並可將 $p_{95}$ 維持在 120 秒左右。我們建議將 `compileConcurrencyLimit` 設為此值，而不是維持在高值：一次接納 1024 個編譯會讓每個人都等八分鐘，而接納 256 個並將其餘的排入佇列，則能讓大多數使用者在兩分鐘內得到服務。排隊只影響晚到的人；爭用則影響每一個人。
</Step>

<Step title="將這些數字視為最壞情況">
表 2 中的每個等級都是同時觸發的冷編譯。這兩個條件在正式環境中都不成立：同一份文件的暖編譯需要 8.6 秒，而冷編譯需要 28.3 秒，相差 $3.3$ 倍；而且真實使用者不會在同一秒按下按鈕。因此，一個每兩分鐘重新編譯一次、具有典型快取命中率的穩態使用者群體，所能支撐的寫作者會遠多於單看並行數所暗示的數量——在 256 的運作點上，約為一千名或更多活躍作者。並行數據是瞬間爆發的上限，而不是座位數。
</Step>

<Step title="先決定延遲預算，再據此得出規模">
式 (1) 可以直接反推。對於在時脈 $f$、$C$ 個核心上的目標等待時間 $T$，可容納的並行數為 $N \le C\,fT/k$，對這份文件而言 $k\approx28 GHz·s$。在 3 GHz 的 8 個核心上，60 秒的預算得出 $N\le51$；120 秒的預算則加倍。將預算與容量一起公布，是誠實陳述兩者的唯一方式。
</Step>

<Step title="先買記憶體，再買核心，並檢查您碰到的是哪道牆">
在 32 GiB 以下，我們幾乎沒有測量到額外核心帶來的效益。診斷方式很簡單：如果失敗以 HTTP 502 的形式出現且客體記憶體不足，就增加記憶體；如果失敗以 `timedout` 的形式出現且記憶體仍有剩餘，就增加核心或提高逾時。維運人員可以從我們用來分類組態的相同失敗特徵中讀出這一點。
</Step>

<Step title="體驗靠時脈，人數靠核心">
由於 $T\propto 1/f$ 在沒有曲率的情況下成立（在 1.0–5.5 GHz 範圍內誤差 2%），更快的時脈能讓每位使用者的每次編譯都更快。更多核心不會讓任何單次編譯變快；它們只能接納更多並行的編譯。抱怨「編譯很慢」的部署應該購買時脈；抱怨「截止期限時編譯失敗」的部署應該購買記憶體與核心。
</Step>

<Step title="超過上限後應水平擴展，而非垂直擴展">
超過 65 個並行編譯後，受支援的途徑是水平擴展（圖 2c 與圖 10，詳見 §9）：在具備 cookie 工作階段親和性的負載平衡器後方部署多個應用程式執行個體，共用集中式的 MongoDB、Redis 與 S3 相容儲存空間，並將 `git-bridge` 保留為單例。這會將每個執行個體的上限乘以執行個體數，而這正是 SaaS 部署達到其自身容量的方式。
</Step>

<Step title="不要依賴每次編譯的隔離">
在 Docker runner 的記憶體限制被修正之前（§6.2），單一異常文件可能會耗盡整台主機，而不是只有它自己被終止。需要這項保證的維運人員應該自行施加限制，而不是等待它。我們在大型主機上使用的機制，是一個帶有硬性上限的 systemd slice，再讓 Docker 常駐程式指向它，使其建立的每個容器都在其中計算用量：

```ini
[Slice]
MemoryMax=940G
```

這裡有一個細節，若是忽略就會浪費一整個下午。名為 `docker-capped.slice` 的 slice 並不位於 `docker.slice` 旁邊；它位於其_內部_，因為連字號是階層分隔符號，而不是名稱的一部分。一個看似沒有效果的上限，通常是被套用在與容器實際所在位置差了一層的地方。請在執行後從 `memory.max_usage_in_bytes` 讀回峰值來驗證，而不是相信設定檔——在我們的主機上，即使在 1024 個同時編譯下，編譯 cgroup 也從未超過其上限的五分之一，這本身就證明了瓶頸是常駐程式而非記憶體。
</Step>
</Steps>

## 9. 多機器參考部署

上述所有內容都是測量單一機器。本節以足以實際建置的細節說明分散式形式，並且——由於維運人員真正面對的問題不是_如何做_，而是_要不要做_——首先說明在什麼情況下它才值得投入。

### 9.1 何時需要分散式形式

單一機器在每個重要方面都更便宜：一個故障域、沒有需要保持一致的共用狀態、沒有可能出錯的路由。我們的資料為何時該離開單機設定了三個門檻。

#### 9.1.1 低於 65 個並行編譯時，不要這麼做

每個執行個體的上限是一個軟體常數，而非硬體常數（§6.1）。在施加的負載接近它之前，第二台機器只會增加故障模式，而沒有任何好處。64 核心主機是在解除 `compileConcurrencyLimit` 之後，才以完全成功服務了 256 個並行編譯；尚未變更這一個值的維運人員並不受硬體限制，也不該去採購硬體。

#### 9.1.2 介於 65 到約 500 之間，先垂直擴展

垂直擴展在我們的整個測試範圍內都保持線性，從未進入逆行狀態。一台大型主機以 100% 成功率達到 1024 個同時冷編譯（§4.3）；延遲拐點出現在 512，而非更早。在這個區間內，一台較大的機器嚴格來說比數台較小的機器更簡單，而且依據 §4.4，一台更快的機器能改善每位使用者的體驗，而不只是接納更多使用者。

#### 9.1.3 為了可用性而非吞吐量而採用分散式

在未達上限時執行多於一個應用程式複本的誠實理由是：一台機器只有一個電源供應器、一個核心、一個升級時段。這是一個正當的理由，也是我們會給出的理由；它只是不屬於容量論點，而將兩者混為一談，會讓維運人員在需要記憶體時去購買複本。

### 9.2 層級及其規模估算

圖 10 顯示了此拓撲。它有四個層級，各自依不同的量進行擴展——這正是將它們分開的意義所在。

#### 9.2.1 邊緣

一個負載平衡器，或為了可用性而使用兩個。它負責終止 TLS，不做任何昂貴的工作；它隨連線數而非編譯數擴展，對於本文研究的負載，一個小型執行個體就已足夠。重要的是它的設定，而不是它的規模（§9.3）。

#### 9.2.2 應用程式複本

這些承載編譯負載，也是唯一隨並行數擴展的層級。依 §8 的規則估算每一個的規模——先記憶體、後核心、再時脈——然後將複本數設定為足以涵蓋峰值並行數除以每個複本的上限。複本不保存任何持久性資料：其本機磁碟存放編譯暫存與輸出快取，兩者都可以重建。這就是它們可以安全地自由新增與移除的原因，而這值得驗證而非假設，因為只要一個 `filestore` 路徑設定錯誤，就會悄悄地把這個層級變成有狀態的。

#### 9.2.3 狀態

Redis、MongoDB 與 S3 相容的物件儲存空間，分別位於不同主機上。Redis 是承重的那一個，也是最不明顯的那一個：它保存工作階段儲存區與即時文件緩衝區，正是這一點讓路由到任何複本的編譯都能看到在另一個複本上輸入的按鍵。將 Redis 當作快取並依淘汰需求估算其規模的維運人員，會產生編譯過時文件的結果，而這極難診斷，因為沒有任何東西失敗——只是輸出是錯的。MongoDB 隨專案數量而非編譯速率擴展。物件儲存空間在只有一個複本時是選用的，超過一個時則是必要的。

#### 9.2.4 單例

`git-bridge` 將儲存庫保存在本機磁碟上、維護一個本機索引，且沒有複寫途徑。它必須恰好以一個執行個體執行，固定在一個指定的複本旁，它也是讓整個部署無法完全無狀態的元件。請據此規劃它的主機：它的磁碟才是需要備份的那一個。

| **層級**      | **數量**             | **擴展依據**             |
| ------------- | -------------------- | ------------------------ |
| 負載平衡器    | 1–2                  | 並行連線數               |
| 應用程式      | $\lceil N/C\rceil$ | 峰值並行編譯數           |
| Redis         | 1（+複本）           | 進行中的編輯工作階段     |

### 9.3 路由是最容易出錯的部分

三類請求必須到達三個不同的地方，而預設的單一規則設定最多只能滿足其中兩個。

`/project/` 底下的編譯流量應依專案識別碼以一致性雜湊分配，讓專案的編譯快取留在同一個複本上。我們使用 HAProxy 的 `balance hash path,field(3,/)` 搭配 `hash-type consistent` 與 `hash-balance-factor 150`。這個選擇在水平擴展時很重要：使用 cookie 親和性時，既有工作階段會無限期地固定在原本的複本上，新加入的複本只會接收新使用者，因此維運人員剛付錢買的機器完全分擔不到促使他購買的那些負載。在我們的設定中，一致性雜湊在水平擴展時重新分配了 35% 的專案，而 cookie 則為 0%。

工作階段流量則不同。當 WebSocket 升級失敗、`socket.io` 退回到 XHR 輪詢時，同一個工作階段的連續輪詢必須到達同一個複本，而路徑中沒有可供雜湊的專案識別碼。這類流量需要一個具備 cookie 親和性的獨立後端。我們設計了這種分流，但沒有實際部署；我們將其標示為缺口，而非宣稱已完成。

最後，`/git/` 必須到達 `git-bridge` 旁邊執行的那個複本。它被路由到該複本，而不是直接路由到 `git-bridge`，因為 bridge 會向應用程式的 OAuth 端點驗證其回呼，並透過應用程式解析 blob URL；繞過複本只會破壞驗證，而不會改善任何東西。

### 9.4 縮減規模需要排空緩衝

移除複本與新增複本並不對稱：進行中的編譯會遺失，使用者會看到一個並非由他們造成的失敗。可行的順序是先停止新流量、等待，然後才終止。我們將其實作為一個 pre-stop hook，在負載平衡器將後端標記為排空中時，讓 pod 保留一段可設定的時間——測試時短到只需幾分鐘，在正式環境中則長到足以讓工作階段自然結束，是以小時而非秒計。這段時間是決定彈性擴展是無感還是令人抓狂的調整旋鈕。

另一個我們透過測量而非設計發現的限制是：依 CPU 自動擴展不適用於此工作負載。應用程式 pod 本身的使用率只有 22 m core，而節點總計為 3997 m core，因為編譯工作發生在 pod 不會計算的同層級容器中。用來擴展此層級的任何訊號，都必須計算正在執行的編譯容器，而非 pod 的 CPU。

## 10. Overleaf 以外的意涵

§4.2 或 §4.3 中沒有任何內容是 Overleaf 程式碼所特有的。實測定律源自任何託管 LaTeX 服務都具備的三項特性：工作單位是單執行緒行程、它被隔離在容器中，而且其工作集是一個必須由頁面快取保存的大型唯讀目錄樹。有三個結果可以直接套用到任何建置此類服務的人身上。

### 10.1 先配置記憶體，再配置核心

矩陣中最強烈的結果是否定性的：在 16 GiB 以下，核心數幾乎無關緊要，只有在 48 GiB 時，4、8 與 16 vCPU 組態才有所區分（143、268、331）。將傳統法則理解為「每五位使用者增加一個核心」的維運人員，買錯了資源。其機制是發行版目錄樹上的共用頁面快取，這是 TeX Live 大小本身的特性，而非任何特定前端的特性。

### 10.2 接納速率是一種資源，而且通常被遺忘

在 $N=1024$ 時，即使每個請求都同時到達，我們的伺服器存活的沙箱數也從未超過 205 個（圖 7b）。限制因素是容器建立，而非編譯——這與將容器啟動成本歸因於執行階段開銷而非映像檔大小的測量研究一致 \[19, 20]。只估算 CPU 與記憶體的服務，會發現其爆發行為受制於一個它從未測量過的量。其實務形式就是 §8 的建議：刻意限制接納數量，因為自己選擇的佇列，好過事後才發現的佇列。

### 10.3 比編譯活得更久的沙箱會讓模型失效

此處的每個容量數據都假設容器被建立、執行一次編譯然後結束——生命週期為數十秒，且僅在執行期間工作週期接近一。近期有兩種設計模式打破了這個假設，而且是以相同的方式打破的。

第一種是每使用者的持久性沙箱。為每位使用者分配一個固定的私人環境，會將統計多工的資源池轉變為一組保留資源：一個原本可以靠分時共享以 64 個核心服務 256 個並行編譯的服務，如果為每個人提供四個專用核心，就只能服務 16 位使用者，在相同硬體下少了一個數量級。我們的資料量化了這個選擇的成本，而非反對它——保留資源換來的是可預測性，而在我們建議的運作點上，兌換率約為 $16\times$。

第二種、也是較新的一種，是與編譯器共用沙箱的 AI 代理。在代理輔助寫作平台中，執行 XeLaTeX 的同一個容器可能也承載一個長時間執行的程式設計代理，因此它是持續被佔用的，而非以爆發方式使用。實務工作者回報的症狀，恰好就是模型對此類部署的預測——在使用者人數不多時仍持續遲緩 \[15]。這種交互作用值得精確地陳述，因為它不只是「更多負載」。我們的三項發現會相互疊加。佔用不再是爆發性的，因此 §4.2 的分時共享定律會同時套用到整個使用者群體，而不只是當下正在編譯的那一部分。頁面快取——正是它帶來了 §4.1 的超線性記憶體報酬——現在要與代理自身的工作集共用，不再對 TeX 保持熱狀態。而 §6.2 中缺失的容器記憶體限制會變得危險得多，因為一個永不結束的容器永遠不會歸還其記憶體。

我們沒有測量過這類平台，也不對任何特定產品做出任何宣稱。我們能說的是我們的數據對設計的意涵：一個為每位使用者提供長期存在之多核心沙箱的架構，應該以保留資源系統的方式估算規模，而不是依據此處回報的並行數據，而它可預期的容量，更接近其核心數除以每位使用者的核心數，而非表 1 中的任何數字。

## 11. 有效性威脅

### 11.1 單一文件

所有測量都使用同一份 63 頁的 XeLaTeX 文件。其他文件的絕對容量會有所不同；而擴展定律是比例關係，應該不會改變。常駐記憶體大得多的文件會移動記憶體牆的位置，但不會改變其超線性的特性。

### 11.2 虛擬化主機

客體在一台實體機器上以 KVM 執行，因此絕對數字包含虛擬化開銷，且各客體共用主機的頁面快取與 NVMe 裝置。我們在觀察到主機記憶體壓力會使客體內的平均負載在相同並行數下膨脹超過 $3\times$ 之後，關閉了不相關的客體，以減輕最大的干擾因素。

### 11.3 同時到達

每次編譯都在同一瞬間發出，這是最壞情況。真實使用者的到達是一個隨機過程，因此依我們的數字估算規模的部署會有餘裕而非不足——但在提交截止期限結束時的峰值，比起卜瓦松模型更接近我們的模型。

### 11.4 邊界組態

在 2 GiB 時，系統已接近崩潰，相同組態的重複執行可能會相差一個編譯。我們回報保守值，並且不從該狀態下 $\pm 1$ 的差異得出結論。

## 13. 貢獻分工

Musicminion 設計了本研究、提供並操作測試平台、主導研究方向，並驗證了此處回報的每一項測量。Claude Opus 5（Anthropic）建置並操作基準測試工具、自動化部署、進行原始碼考據、製作圖表，並撰寫稿件初稿。兩位作者皆審閱了最終文本。凡被回報為受污染的執行——§4.3 的 1021 工作階段測試以及 §4.1 中異常的 $N=256$ 等級——其缺陷都是在審閱期間發現的，並在發表前重新執行，而非悄悄捨棄。

讀者應注意，ACM、IEEE 與 ICMJE 的作者資格政策目前將作者身分保留給能夠為作品負責的一方，並會要求將第二作者的貢獻記錄為揭露事項，而非署名。我們在此明確說明分工，使紀錄在任一慣例下都是正確的。

## 14. 結論

自行託管 Overleaf 的容量規劃，並不是擴展單一資源的問題。有三項發現應該改變規劃的方式。

第一，在客體記憶體低於 32 GiB 時，核心數幾乎無關緊要：在 16 GiB 時，4、8 與 16 vCPU 客體的容量差異不到 8%。透過 TeX Live 目錄樹上的共用頁面快取，記憶體決定了上限；只有在記憶體充裕之後，核心才開始發揮作用。

第二，兩個軟體參數的影響超過硬體。解除 CLSI 寫死的 65 個編譯上限並提高預設 180 秒的編譯逾時，讓一台 8 vCPU / 48 GiB 客體從 64 個並行編譯提升到 268 個——在沒有額外硬體的情況下提升了 4.2 倍。兩者都無法從設定文件中得知；其中一個甚至完全無法設定。

第三，「這台機器能支援多少並行使用者」這個問題的條件不足。此系統中的並行是純粹的分時共享，而容量就是逾時所允許的數量。誠實的答案形式會同時陳述兩者：_這台機器在使用者願意等待_ $T$ _秒的情況下，可服務_ $N$ _個同時編譯_，其中 $N$ 與 $T$ 由式 (1) 相關聯。

我們也回報一個潛在缺陷：Docker runner 中的每容器記憶體限制自 2018 年以來一直無效，無論是數值大小還是設定位置都有問題。其實際影響是，小型部署上的記憶體耗盡會拖垮整個服務，而不只是造成問題的那一次編譯。
