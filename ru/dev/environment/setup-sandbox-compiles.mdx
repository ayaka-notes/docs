Компиляция в песочнице в среде разработки работает немного иначе, чем в продакшен-образе. В среде разработки она уже настроена; на этой странице описаны настройки и три момента, о которых нужно помнить:

* Проблема с правами доступа к файлам
* Общий том для history-v1 и filestore
* Проблема с подкаталогами

### Включение изолированной компиляции {#enable-sandbox-compiles}

Компиляция в песочнице включена по умолчанию. `develop/docker-compose.yml` задаёт `SANDBOXED_COMPILES=true` для `clsi`, а `develop/dev.env` содержит остальное:

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

clsi не загружает образы сам, поэтому загрузите их один раз командой `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1` (и `:2025.1`).

LaTeX работает в соседних контейнерах от имени `TEXLIVE_IMAGE_USER`. В среде разработки это `tex`, что также является значением по умолчанию для clsi (`services/clsi/config/settings.defaults.cjs:154`). Продакшен-образ вместо этого использует `www-data`, когда `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` (`server-ce/config/env.sh:15-21`), потому что там файлы создаёт пользователь `www-data` контейнера Overleaf.

<Warning>

Не используйте собственноручно собранный образ: вы можете столкнуться с целым рядом ошибок.

</Warning>

### Исправление прав доступа к файлам {#fix-file-permissions}

Контейнер clsi запускается от root, передаёт папки `compiles`, `output` и `cache` пользователю `node` (uid `1000`), а затем запускает clsi от имени `node` (`services/clsi/entrypoint.sh`). Поэтому `develop/compiles` на хосте принадлежит uid `1000`, тому же uid, что и у `tex` в среде разработки (см. комментарий в `develop/pandoc/Dockerfile`). С приведёнными выше настройками среда разработки компилирует без каких-либо изменений прав.

Если вместо этого задать `TEXLIVE_IMAGE_USER=root`, у root (uid `0`) нет прав на запись в подпапки `compiles`. В этом случае передайте группе `root` владение и право записи на `compiles` и установите `setgid`, чтобы новые подпапки наследовали это владение:

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

Подробную документацию можно найти в `services/clsi/README.md`.

### Общий том для history-v1 и filestore {#volume-share-between-history-v1-and-filestore}

<Info>

Настройки из этого и следующего раздела уже есть в `develop/docker-compose.yml` и `develop/dev.env`. Они важны только при `S3_ENABLED=false` в `develop/dev.rc`. При значении по умолчанию `S3_ENABLED=true` filestore и history-v1 хранят эти файлы в бакетах RustFS (`develop/s3/docker-compose.yml`).

</Info>

По умолчанию filestore выступает посредником между S3 и другими сервисами Overleaf. Однако в Overleaf CE или Server Pro все файлы по умолчанию хранятся локально. Поэтому в Overleaf применён весьма хитрый приём.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

При этом `data/history` также используется сервисом истории. Так разные микросервисы могут совместно использовать одни и те же данные. Поэтому сервис filestore в develop монтирует том `history-v1-buckets` сервиса history-v1. Без него **clsi не сможет получать blob-файлы из сервиса filestore**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

filestore находит бакеты через эти настройки в `dev.env`:

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### Использование подкаталогов {#use-subdirectories}

filestore всегда читает blob-объекты истории с подкаталогами (`services/filestore/app/js/KeyBuilder.js:58`, `:70`). Продакшен-образ включает `useSubdirectories` для history-v1 (`server-ce/config/production.json`), а конфигурация history-v1 по умолчанию нет, поэтому в разработке history-v1 <strong>сделал бы все данные плоскими.</strong> Поэтому `dev.env` задаёт `NODE_CONFIG` для history-v1:&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

Без этого history-v1 хранит файлы `project_blobs` так:

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

Когда `useSubdirectories` равно `true`, символ `_` в этих именах становится `/`, поэтому каждый blob хранится во вложенных папках.
