### Введение

Прежде чем приступить к разработке, просим вас ознакомиться со следующим:

* Официально Overleaf разрабатывается во [внутреннем репозитории](http://github.com/overleaf/internal), а версия Community Edition публикуется в [overleaf/overleaf](https://github.com/overleaf/overleaf). За синхронизацию кода между внутренним и публичным репозиториями отвечает copybot.
* [Ayaka-notes/overleaf-pro](https://github.com/ayaka-notes/ayakaleaf-pro) — это форк Overleaf Community. Мы надеемся, что проект будет развиваться долгое время, поэтому, пожалуйста, соблюдайте правила, прежде чем вносить свой вклад.

### Правила коммитов

* Пожалуйста, не вносите масштабных изменений в существующий код Overleaf. Сосредоточьте как можно больше функциональности в папке `services/web/modules`. Это сведёт к минимуму объём работы при последующем слиянии и обновлении кода.
* Vibe coding действительно очень простой способ, но он легко может превратить проект в хаос и сделать его неподдерживаемым в будущем, поэтому используйте его с осторожностью.
* Пожалуйста, не добавляйте во время разработки ничего, связанного с переводами; по возможности используйте существующие переводы.
* Избегайте добавления переменных окружения без крайней необходимости. Если они всё же нужны, постарайтесь, чтобы они максимально соответствовали переменным из Overleaf toolkit или [docs.overleaf.com](https://docs.overleaf.com/).

### Правила ветвления

Для разработки overleaf-pro мы используем следующие ветки:

* `main`: эта ветка используется только для синхронизации с апстримом, пожалуйста, **НЕ** коммитьте в неё никаких сторонних изменений. В этой ветке мы ставим теги вида `ce-v[X.x.x]`, которые означают, что состояние соответствует версии `v[X.x.x]` официальной Overleaf Community Edition. Примечание: эти теги неизменяемы!
* `server-pro`: ветка по умолчанию для повседневной разработки.
* `feature-X`: ветка для разработки конкретной функции.
* `release-vX.0.0`: ветка для выпуска релиза, в ней перед релизом мы вносим срочные исправления.

### GitHub Action

[GitHub Action](https://github.com/ayaka-notes/ayakaleaf-pro/actions) отвечает за автоматический CI/CD. Вам не нужно собирать образы на своей машине: каждый образ ниже собирается workflow, а те, что поддерживают ручной запуск, можно собрать в один клик.

| Workflow | Запуск | Источник | Образ |
| --- | --- | --- | --- |
| Sync Upstream Code | Ежедневно, вручную | `overleaf/overleaf` → `main` | — |
| Build Development Image | Ежедневно, вручную | `server-pro` | `ghcr.io/ayaka-notes/overleaf-pro/dev:<service>` |
| Build Operations Image | Push / PR в `server-pro`, вручную | Отправленный коммит или head PR | `ghcr.io/ayaka-notes/overleaf-pro/ops:<YYYYMMDDHHMM>-<sha>`, `ops:latest` |
| Build Release Image | Вручную | Последняя ветка `release-v*` | `ghcr.io/ayaka-notes/overleaf-pro:<version>`, `:latest` и `overleaf-pro/git-bridge` |

* **Образы для разработки** содержат по одному микросервису (`web`, `webpack`, `clsi`, ...) для `linux/amd64` и `linux/arm64`. Конфигурация Codespace загружает их через `develop/docker-compose.image.yml` вместо запуска `bin/build`.
* **Операционные образы** — это полные одноконтейнерные образы (как `sharelatex/sharelatex`) для сквозного тестирования изменений. `ops:latest` обновляется только при push в `server-pro`; PR получает только тег с отметкой времени. Эти образы хранятся 7 дней и предназначены только для тестирования.
* **Релизные образы** — это то, что разворачивают пользователи. Версия берётся из имени ветки, поэтому `release-v6.3.0` публикует `overleaf-pro:6.3.0`.

<Steps>
<Step title="Запуск workflow вручную">
Откройте вкладку [Actions](https://github.com/ayaka-notes/ayakaleaf-pro/actions), выберите workflow слева, нажмите **Run workflow** и подтвердите. У Build Operations Image также есть опция **Build without cache** на случай, если кешированный слой устарел.
</Step>

<Step title="Сборка в вашем форке">
Те же workflow работают и в форке: включите Actions в своём форке, затем запускайте их с его вкладки Actions. Образы публикуются в `ghcr.io/<your-name>/overleaf-pro/...` с помощью встроенного `GITHUB_TOKEN`, поэтому секреты не нужны. Sync Upstream Code и очистка старых образов выполняются только в `ayaka-notes`.

Для Build Release Image в вашем форке нужна ветка `release-v*`.
</Step>
</Steps>

<Info>

Чтобы узнать, из какого коммита собран образ: тег операционного образа заканчивается коротким хешем коммита, а релизный образ содержит его в метке `com.overleaf.pro.revision` (см. `docker inspect` в разделе «Вопросы и ответы» ниже).

</Info>

### Вопросы и ответы

<Accordion title="Как найти хеш коммита для Overleaf Community Edition `X.0.0`?">

Прежде всего нужно скачать Docker-образ и выполнить следующую команду, чтобы просмотреть метки этого образа:

```shellscript title="bash" wrap
docker inspect --format='{{json .Config.Labels}}' sharelatex/sharelatex:6.0.0
{"com.overleaf.ce.revision":"b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f","org.opencontainers.image.ref.name":"ubuntu","org.opencontainers.image.version":"24.04"}
```

Затем можно проверить, присутствует ли [коммит (b0d05c0)](https://github.com/overleaf/overleaf/commit/b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f) в ветке master апстрима.

</Accordion>

<Accordion title="Почему хеш коммита в образах CE `6.0.0` и `6.0.1` одинаковый?">

Это ожидаемое поведение. Релиз 6.0.1 — это небольшой патч-релиз, собранный поверх образа 6.0.0. Изменения применяются путём патчинга существующего образа 6.0.0, а не пересборки образа из нового коммита. Поэтому хеш коммита внутри образа в версиях 6.0.0 и 6.0.1 совпадает.

Подробнее см. [hotfix](https://github.com/overleaf/overleaf/tree/main/server-ce/hotfix).

</Accordion>
