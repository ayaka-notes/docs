Рекомендуемый способ развёртывания экземпляров Overleaf Server CE и Overleaf Pro и управления ими — использование Toolkit.

Toolkit упрощает создание экземпляра Overleaf с помощью набора специальных скриптов, которые скрывают сложность оркестрации необходимых микросервисов. Достаточно запустить входящий в комплект скрипт инициализации и указать несколько параметров конфигурации, например пути к постоянному хранилищу, — и Toolkit сам развернёт и свяжет микросервисы, из которых состоит ваш экземпляр Overleaf Server CE или Pro.

Это позволяет вам сосредоточиться на настройке пользовательского опыта и реализации конкретных функций вашего локального экземпляра. Toolkit берёт на себя всю внутреннюю сложность, упрощая развёртывание вашего экземпляра Overleaf.

<Info>

По историческим причинам основной контейнер Overleaf называется `sharelatex` и основан на Docker-образе `sharelatex/sharelatex`. Это связано с тем, что технология построена на кодовой базе ShareLaTeX, которая была объединена с Overleaf. Подробнее см. в [этой записи блогаarrow-up-right](https://www.overleaf.com/blog/518-exciting-news-sharelatex-is-joining-overleaf). В будущем он будет переименован в соответствии со схемой именования Overleaf.

</Info>

#### Архитектура

Внутри контейнера Overleaf программное обеспечение работает как набор микросервисов под управлением `runit`. Наиболее интересные файлы внутри контейнера:

* `/etc/service/`: файлы инициализации микросервисов.
* `/var/log/overleaf/`: логи каждого микросервиса.
* `/overleaf/services/`: код различных микросервисов.
* `/var/lib/overleaf/`: точка монтирования постоянных данных (соответствует каталогу, указанному в `OVERLEAF_DATA_PATH` на хосте).

#### Контейнеры MongoDB и Redis

Overleaf зависит от двух внешних баз данных: MongoDB и Redis. По умолчанию Toolkit разворачивает по контейнеру для каждой из них в дополнение к контейнеру Overleaf — всего три Docker-контейнера.

<Info>

Если вы предпочитаете подключиться к существующему экземпляру MongoDB или Redis, это можно сделать, задав соответствующие параметры в конфигурационном файле [overleaf.rc](/ru/on-premises/configuration/overleaf-toolkit/files-and-locations#the-overleaf.rc-file).

</Info>

#### Редактор и процесс компиляции

В этом разделе приводится общий обзор обработки документов и процесса компиляции.

<Info>

На этой странице описан процесс компиляции с Sandboxed Compiles, доступный только в Overleaf Pro. В Server CE процесс компиляции использует простые подпроцессы — замените пункты, относящиеся к **контейнеру**, одним пунктом **запуск компиляции в подпроцессе**.

</Info>

Компоненты / участники:

* `user` — пользователь приложения
* `editor` — клиентское приложение, работающее в браузере
* `clsi` — микросервис, используемый для компиляции PDF
* `document-updater` — микросервис, используемый для обработки обновлений документов
* `filestore` — микросервис, работающий с бинарными файлами
* `real-time` — микросервис, используемый для работы с веб-сокетами
* `web` — (не такой уж) микросервис, используемый для обработки API-запросов

**Кеширование в Redis**

* **user**: загружает страницу редактора
* **editor**: открывает веб-сокет
* **editor**: отправляет через веб-сокет запрос на открытие документа
  * **real-time** -> **document-updater**: документ загружается из MongoDB в Redis
* **editor**: отправляет обновление документа через веб-сокет
  * **real-time** -> **document-updater**: документ обновляется в Redis
* **editor**: отправляет новые запросы на компиляцию
  * По прошествии 5 минут с момента последнего сброса (для каждого документа):
    * **document-updater**: сбрасывает документ из Redis в MongoDB
* **editor**: отправляет новые обновления
  * каждые 100 обновлений (для каждого документа):
    * **document-updater**: сбрасывает историю документа из Redis в MongoDB
* **user**: покидает редактор / закрывает вкладку браузера
  * через 5 минут
    * **real-time**: проверяет наличие других соавторов; если их нет:
      * **real-time** -> **document-updater**: сбрасывает документы из Redis в MongoDB

**Чтение из MongoDB в Redis**

* **document-updater** -> **web** -> **docstore**: чтение из MongoDB

**Сброс из Redis в MongoDB**

* **document-updater** -> **web** -> **docstore**: запись в MongoDB

**Компиляция — режим синхронизации «full»**

* **editor**: отправляет запрос на компиляцию с режимом синхронизации «full»
* **web** -> **document-updater**: все документы сбрасываются из Redis в MongoDB
* **web** -> **docstore**: все документы загружаются из MongoDB
* **web** -> **clsi**: запрос на компиляцию отправляется в `clsi` и включает:
  * режим синхронизации
  * хеш дерева файлов -> «состояние проекта»
  * все документы с их содержимым -> с ограничением тела запроса в 7 МБ
  * URL бинарных файлов для отдельной загрузки
* **clsi**: проверяет состояние на диске с учётом режима синхронизации и «состояния проекта»
  * это полная синхронизация, поэтому предыдущее состояние на диске можно игнорировать
* **clsi**: очищает каталог компиляции
* **clsi**: записывает все документы в каталог компиляции
* **clsi**: записывает все бинарные файлы в каталог компиляции
  * `clsi` копирует файлы из локального кеша проекта
  * при промахе кеша:
    * **clsi** -> **filestore**: загружает файлы
* **clsi**: записывает «состояние проекта»
* **clsi**: убеждается, что Docker-контейнер с нужной конфигурацией существует
  * формирует параметры контейнера, включая версию texlive
  * хеширует параметры
  * имя контейнера: `project-<project-id>-<user-id>-<hash>`
* **clsi**: запускает контейнер и передаёт stdout/stderr в память -> ограничение 2 МБ
* **clsi**: оставляет остановленный контейнер -> он удаляется через 24 часа
* **clsi**: записывает stdout/stderr на диск
* **clsi**: копирует выходные файлы в уникальный выходной каталог
  * build-id состоит из 8 случайных байтов и метки времени с точностью до мс
  * удаляет все каталоги сборки, кроме последних 3 (анонимный пользователь) / последнего 1 (вошедший пользователь)
* **clsi**: компиляция завершилась ошибкой/тайм-аутом
  * удаляет кеш компиляции — он может содержать неполные файлы или быть повреждён
* **editor**: загружает output.log и output.pdf

**Компиляция — режим синхронизации «incremental»**

* **editor**: отправляет запрос на компиляцию с режимом синхронизации «incremental»
* **web** -> **document-updater**: получает все документы из Redis
  * хеш «состояния проекта» также хранится в Redis
  * **web** отправляет хеш дерева файлов в `document-updater`, и при несовпадении `document-updater` может превратить инкрементальную компиляцию в полную
    * см. процесс компиляции, выполняемый при запросе редактором компиляции «full»
* **web** -> **clsi**: запрос на компиляцию отправляется в `clsi` и включает:
  * режим синхронизации
  * хеш дерева файлов -> «состояние проекта»
  * все документы из Redis с их содержимым -> с ограничением тела запроса в 7 МБ
  * без бинарных файлов
* **clsi**: проверяет состояние на диске с учётом режима синхронизации и «состояния проекта»
  * это инкрементальная синхронизация, поэтому «состояние проекта» должно совпадать
  * при несовпадении: отвечает кодом 409, после чего web повторяет запрос с синхронизацией «full»
    * см. процесс компиляции, выполняемый при запросе редактором компиляции «full»
* **clsi**: записывает обновлённые документы в каталог компиляции
* **clsi**: убеждается, что Docker-контейнер с нужной конфигурацией существует
  * формирует параметры контейнера, включая версию texlive
  * хеширует параметры
  * имя контейнера: `project-<project-id>-<user-id>-<hash>`
* **clsi**: запускает контейнер и передаёт stdout/stderr в память -> ограничение 2 МБ
* **clsi**: оставляет остановленный контейнер -> он удаляется через 24 часа
* **clsi**: записывает stdout/stderr на диск
* **clsi**: копирует выходные файлы в уникальный выходной каталог
  * build-id состоит из 8 случайных байтов и метки времени с точностью до мс
  * удаляет все каталоги сборки, кроме последних 3 (анонимный пользователь) / последнего 1 (вошедший пользователь)
* **clsi**: компиляция завершилась ошибкой/тайм-аутом
  * удаляет кеш компиляции — он может содержать неполные файлы или быть повреждён
* **editor**: загружает output.log и output.pdf

**Компиляция — переключение между режимами**

* **editor**: фиксирует ошибку компиляции — следующая компиляция будет «full»
* **editor**: фиксирует успешную компиляцию — следующая компиляция будет «incremental»
