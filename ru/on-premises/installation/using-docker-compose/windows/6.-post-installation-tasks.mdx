### Создание администратора и первого проекта {#create-the-administrator-and-a-first-project}

Откройте [http://localhost:8080/launchpad](http://localhost:8080/launchpad) в **браузере Windows**, создайте первую учётную запись администратора и войдите в систему. Затем следуйте разделу [6. Действия после установки](/ru/on-premises/installation/using-docker-compose/linux/6.-post-installation-tasks) руководства для Linux, используя порт `8080` в приведённых там примерах URL.

### Проверка компиляции {#verify-compilation}

Работающая страница входа ещё не доказывает, что отдельные контейнеры компилятора имеют доступ к каталогу данных WSL. Создайте пустой проект и скомпилируйте этот `main.tex` с помощью **pdfLaTeX**:

```latex
\documentclass{article}
\begin{document}
Ayakaleaf Pro on Windows WSL 2.
\end{document}
```

В предварительном просмотре PDF должен отобразиться текст. Для базового образа при необходимости выберите **TeX Live 2026 Basic** в настройках проекта.

Выберите **XeLaTeX** и проверьте:

```latex
\documentclass{article}
\usepackage{fontspec}
\begin{document}
Ayakaleaf WSL XeLaTeX sandbox.
\end{document}
```

Оба примера работают с базовым образом. Для документов на китайском языке используйте образ, содержащий `ctex` и нужные шрифты, например полный, прежде чем проверять следующий пример с **XeLaTeX**. В базовом образе их нет:

```latex
\documentclass{ctexart}
\begin{document}
你好，Ayakaleaf Pro。
\end{document}
```

Чтобы убедиться, что используется песочница, выполните в **Ubuntu** во время компиляции:

```bash
docker ps -a --filter ancestor=ghcr.io/ayaka-notes/texlive-basic:2026.1
bin/logs -f clsi
```

Укажите в фильтре имя выбранного вами образа. Короткие компиляции могут завершиться до запуска `docker ps`; параметр `-a` показывает и остановленные контейнеры, пока они не будут удалены. Контейнер компилятора должен использовать этот образ и bind-монтирование `/compile` из каталога данных Toolkit в WSL. Одни лишь журналы приложения не заменяют проверку PDF.

### Проверка сохранности данных {#verify-persistence}

В **Ubuntu**, в каталоге Toolkit:

```bash
bin/stop
bin/start
```

Дождитесь запуска приложения, снова откройте проект из Windows и скомпилируйте его. Ваша учётная запись, исходный код и файлы проекта должны остаться на месте. По умолчанию рабочие данные находятся в `~/ayakaleaf-toolkit/data/` внутри Ubuntu. Сохраняйте и `config/`, и `data/`; удаление или отмена регистрации дистрибутива Ubuntu может их удалить.

### Обеспечение доступности экземпляра {#keep-the-instance-available}

Чтобы экземпляр продолжал работать, нужны три условия: Windows не переходит в спящий режим, Docker Desktop запущен, а контейнеры перезапускаются вместе с движком.

В разделе **Settings → General** Docker Desktop включите **Start Docker Desktop when you sign in to your computer**, см. [настройки Docker Desktop](https://docs.docker.com/desktop/settings-and-maintenance/settings/). Docker при этом запускается после входа в систему, а не до него. После перезагрузки Windows войдите в систему, дождитесь окончания запуска Docker Desktop, откройте Ubuntu и проверьте `docker ps` и сайт.

**Resource Saver** в Docker Desktop не связан со спящим режимом Windows. Обычно он включается, только когда не запущено ни одного контейнера; работающие приложение, MongoDB и Redis не дают наступить этому состоянию простоя. В WSL 2 он приостанавливает движок Docker, а не выключает общую виртуальную машину WSL. Не приостанавливайте Docker Desktop вручную (**Pause**), пока он обслуживает пользователей. Отключать Resource Saver только ради того, чтобы этот стек продолжал работать, не нужно; см. [документацию Docker по Resource Saver](https://docs.docker.com/desktop/use-desktop/resource-saver/).

Сервисы Toolkit используют `restart: always`. Проверьте фактическую настройку в **Ubuntu**:

```bash
docker inspect sharelatex mongo redis --format '{{.Name}} restart={{.HostConfig.RestartPolicy.Name}}'
```

Каждый сервис должен сообщить `always`. Когда Docker работает, он может перезапускать эти существующие контейнеры без нового `bin/up`. Контейнер, остановленный вручную, остаётся остановленным, пока вы его не запустите или не перезапустите движок; при `always` перезапуск движка может снова запустить его. См. [поведение политик перезапуска Docker](https://docs.docker.com/engine/containers/start-containers-automatically/).

| Действие | Влияние на Ayakaleaf |
| --- | --- |
| Закрыть терминал Ubuntu после `bin/up -d` | Контейнеры работают в фоновом режиме; терминал ими не управляет. Docker Desktop и среда WSL должны оставаться доступными |
| Закрыть окно Docker Dashboard | Окно можно закрыть, при этом Docker Desktop продолжит работать в области уведомлений |
| Выбрать **Quit Docker Desktop** | Останавливает движок и делает сайт недоступным; чтобы восстановить работу, снова откройте Docker Desktop |
| Выполнить `wsl --shutdown` | Останавливает все дистрибутивы WSL и прерывает работу бэкенда Docker WSL; перезапустите Docker Desktop и снова откройте Ubuntu |
| Перевести Windows в спящий режим, гибернацию или выключить | Сервис недоступен; включённый или выключенный экран на это не влияет |
| Выполнить `bin/stop` | Останавливает экземпляр с сохранением данных; для возобновления используйте `bin/start` |

Для длительной работы от сети откройте в Windows 11 **Параметры → Система → Питание и батарея → Время ожидания экрана, спящего режима и гибернации** (в некоторых версиях отображается **Питание** или **Экран и спящий режим**). Установите для спящего режима при питании от сети значение **Никогда** и отключите автоматическую гибернацию, если она настроена. Дисплей по-прежнему может отключаться. Действие при закрытии крышки ноутбука — отдельная настройка; закрытие крышки может перевести его в спящий режим, даже если время ожидания перед сном равно «Никогда». См. [параметры питания Windows](https://support.microsoft.com/en-us/windows/experience/power-battery/power-settings-in-windows-11).

Не выполняйте `wsl --shutdown` для плановой очистки, пока сайт используется. Если это требуется для изменения настроек WSL, сначала остановите экземпляр и запланируйте перерыв в работе. С этими настройками Windows может обеспечивать непрерывную работу экземпляра. Для общего сервиса, который должен переживать выход из системы и перезагрузки без участия пользователя, мы рекомендуем [руководство для Linux](/ru/on-premises/installation/using-docker-compose/linux).

### Проверка восстановления после перезапуска Docker Desktop {#check-recovery-after-restarting-docker-desktop}

Сохранив работу и дождавшись завершения активных компиляций, выберите **Restart Docker Desktop** в меню устранения неполадок Docker Desktop. Дождитесь запуска движка, затем проверьте в **Ubuntu**:

```bash
docker ps
curl -I http://localhost:8080/launchpad
```

Откройте существующий проект в Windows и снова скомпилируйте его. Убедитесь, что учётная запись и исходный код по-прежнему на месте.

Если вы намеренно остановили экземпляр командой `bin/stop`, используйте `bin/start`. Если Docker работает, но какой-то сервис завершается ошибкой, прочитайте его журналы, а не пересоздавайте конфигурацию. Обновления Windows, обновления Docker и отключение питания всё равно могут прервать круглосуточную работу; делайте резервные копии и проверяйте восстановление после планового обслуживания.

### Повседневное использование {#daily-use}

Запустите Docker Desktop в Windows. Откройте **Ubuntu**:

```bash
cd "$HOME/ayakaleaf-toolkit"
```

| Задача | Команда |
| --- | --- |
| Запустить существующие контейнеры | `bin/start` |
| Остановить контейнеры, сохранив данные | `bin/stop` |
| Применить изменения конфигурации | `bin/up -d` |
| Проверить состояние | `bin/docker-compose ps` |
| Прочитать журналы запуска | `bin/docker-compose logs --tail=100 sharelatex` |
| Прочитать журналы MongoDB | `bin/docker-compose logs --tail=100 mongo` |
| Прочитать журналы компилятора | `bin/logs -f clsi` |

`bin/start` не применяет изменения конфигурации: после изменения `config/` используйте `bin/up -d`. Следуйте разделу [Данные и резервное копирование](/ru/on-premises/maintenance/data-and-backups) перед обновлением, переносом или удалением дистрибутива WSL. Копирование рабочих файлов MongoDB, пока база данных выполняет запись, не является согласованной резервной копией.

Для локального использования оставляйте `127.0.0.1`. Чтобы обслуживать другие компьютеры, также нужно осознанно настроить адрес прослушивания, URL сайта, брандмауэр и сеть Windows, а также HTTPS; одно лишь изменение `OVERLEAF_SITE_URL` не публикует порт.

Если что-то не работает, см. раздел [Устранение неполадок](/ru/on-premises/installation/using-docker-compose/windows/troubleshooting).
