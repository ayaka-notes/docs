<Accordion title="Запуск Overleaf с файловой системой NFS">

Монтирование файловой системы NFS в контейнере Overleaf технически возможно, но не рекомендуется и может приводить к различным проблемам с производительностью.

Одна из типичных ошибок при компиляции:

```text
EBUSY: resource busy or locked, unlink '/var/lib/overleaf/data/compiles/62f3d57bef7cf9005c364e75-62f3d57bef7cf9005c364e7a/.nfs573663533034825247625441'
```

В частности, мы не рекомендуем использовать файловые системы на базе NFS для временных данных, например каталогов, используемых для данных компиляции. Для следующих каталогов рекомендуем использовать локальный рабочий диск, предпочтительно локальный SSD.

Для установок на основе `docker-compose` мы предлагаем просто переопределить bind-монтирование из NFS, что позволяет не менять пути в приложении. Вот пример фрагмента конфигурации `docker-compose` с использованием рабочего диска, смонтированного в `/scratch`:

```yaml title="docker-compose excerpt"
services:
  sharelatex:
    environment:
      SANDBOXED_COMPILES_HOST_DIR: /scratch/compiles/
    volumes:
      - nfs:/var/lib/overleaf/data
      - /scratch/cache/:/var/lib/overleaf/data/cache
      - /scratch/compiles/:/var/lib/overleaf/data/compiles
      - /scratch/output/:/var/lib/overleaf/data/output
      - /scratch/tmp/:/var/lib/overleaf/tmp
```

После обновления переносить существующие файлы из NFS в новое расположение не нужно. Компилятор LaTeX может заново создать все файлы при полной повторной компиляции.

Подробнее см.: https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-with-an-nfs-filesystem

</Accordion>

<Accordion title="При запуске Overleaf в Windows или macOS не запускается сервис `mongo`">

Если вы запускаете Overleaf в Windows или macOS, сервис `mongo` может не перезапуститься с ошибкой:

```text title="Example error"
Failed to start up WiredTiger under any compatibility version.
Reason: 1: Operation not permitted
```

Это может произойти, когда данные MongoDB подключены через bind-монтирование из файловой системы, которая не обеспечивает необходимую ей семантику, например из каталога, смонтированного из Windows. Для [Windows с WSL 2](/ru/on-premises/installation/using-docker-compose/windows) храните Toolkit в домашнем каталоге Linux в Ubuntu и используйте bind-монтирования по умолчанию. См. [проверки MongoDB](/ru/on-premises/installation/using-docker-compose/windows/troubleshooting#mongodb-fails-to-start) в руководстве для этой платформы.

Для новой установки, которой требуется хранилище под управлением Docker, следующее переопределение использует именованные тома (см. [рекомендации по хранению данных для образа MongoDB](https://github.com/docker-library/docs/blob/master/mongo/content.md#where-to-store-data)). В существующей установке изменение точек монтирования не переносит данные: перед переключением создайте резервную копию базы данных и кэша и восстановите их, иначе сервис увидит пустые тома. Добавьте следующее в `config/docker-compose.override.yml`, объединив с уже имеющейся конфигурацией:

```yaml title="config/docker-compose.override.yml"
volumes:
  mongo-data:
  redis-data:

services:
  mongo:
    volumes:
      - mongo-data:/data/db

  redis:
    volumes:
      - redis-data:/data
```

Подробнее см.: https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-on-windows-or-macos-results-in-the-mongoservice-not-starting

</Accordion>

<Accordion title="Обновление до Redis 6.2 приводит к циклу перезапусков">

Используйте команду `docker logs redis`, чтобы вывести копию журналов.

Если вы видите строку `Fatal: Can't initialize Background Jobs`, полный вывод будет выглядеть примерно так:

```text title="Redis log example"
1:M 11 Feb 2024 15:19:22.609 # Server initialized
1:M 11 Feb 2024 15:19:22.609 # Fatal: Can't initialize Background Jobs.
1:C 11 Feb 2024 15:19:26.055 # oO0OoO0OoO0Oo Redis is starting oO0OoO0OoO0Oo
```

Это может быть связано с используемой в данный момент версией Docker. Обновление до версии >= 20.10.10 должно решить эту проблему.

Подробнее см. issue в апстриме Redis: https://github.com/redis/redis/issues/12362

Источник: https://docs.overleaf.com/on-premises/support/troubleshooting#upgrading-to-redis-6.2-results-in-a-restart-loop

</Accordion>

<Accordion title="Неправильная ориентация изображений предпросмотра/миниатюр в галерее шаблонов">

Иногда изображения предпросмотра/миниатюр, генерируемые Ayakaleaf Pro, создаются с неправильной ориентацией, и для их исправления требуется ручное вмешательство. Эти изображения хранятся в `/var/lib/overleaf/data/template_files/`.

Перед внесением изменений рекомендуем создать резервную копию этой папки.

Для каждого затронутого шаблона необходимо выполнить следующие шаги:

Найдите ID шаблонаПерейдите в галерею шаблонов вашего экземпляра (/templates/all), откройте затронутый шаблон и скопируйте ID из URL (например: https://your-instance-url/templates/6645d346c224815e9460a695).Выполните команду исправленияВыполните следующую команду на Docker-хосте (замените ID шаблона на скопированный и при необходимости измените путь):docker exec sharelatex /bin/bash -c "mogrify -rotate 90 /var/lib/overleaf/data/template\_files/6645d346c224815e9460a695\_\*\{thumbnail,preview\}"

Источник: https://docs.overleaf.com/on-premises/support/troubleshooting#incorrect-orientation-of-template-gallery-preview-thumbnail-images

</Accordion>

<Accordion title="Убедитесь, что системные вызовы включены. Для pdflatex это 'pdflatex -shell-escape'.">

Команда `\write18` по умолчанию отключена в Community Edition, поскольку все компиляции выполняются в одном контейнере `sharelatex`; это более безопасное значение по умолчанию.

Если вы хотите включить её для pdflatex, создайте в корне проекта файл `latexmkrc` со следующим содержимым:

```perl title="latexmkrc"
$pdflatex = 'pdflatex --shell-escape';
```

Затем попробуйте перекомпилировать.

Источник: https://docs.overleaf.com/on-premises/support/troubleshooting#please-verify-that-you-have-enabled-system-calls.-for-pdflatex-this-is-pdflatex-shell-escape

</Accordion>

<Accordion title="`bin/up` завершается ошибкой `unable to upgrade to tcp, received 409` или `OCI runtime exec failed` после «Initiating Mongo replica set...»">

Эти ошибки означают, что контейнер `mongo` постоянно падает и перезапускается. `bin/up` запускает MongoDB, а затем выполняет внутри него команду, которая завершается ошибкой, пока контейнер перезапускается. `bin/docker-compose ps` показывает сервис `mongo` в состоянии `Restarting`.

Чтобы найти настоящую причину, прочитайте журнал MongoDB:

```sh
bin/logs mongo
```

Частые причины:

* <strong>Процессор не поддерживает AVX.</strong> MongoDB 5.0 и новее требуют AVX на x86-64, и в журнале отображается `MongoDB 5.0+ requires a CPU with AVX support`. В виртуальной машине задайте тип процессора `host`, чтобы AVX передавался в гостевую систему.
* <strong>Ядро Linux с 6.19 по 7.0.13.</strong> MongoDB отказывается запускаться на этих ядрах. Обходное решение см. в разделе [Требования к программному обеспечению](/ru/on-premises/installation/introduction#software-requirements).
* <strong>Данные созданы более старой версией MongoDB.</strong> MongoDB 8.0 не может напрямую открыть данные версий 4.4 или 5.0. Обновляйтесь поэтапно, по одной мажорной версии за раз, см. [Обновление MongoDB](/ru/on-premises/maintenance/updating-mongodb).

</Accordion>

<Accordion title="В журнале отображается «Running Overleaf Community Edition, skipping TexLive checks»">

Это ожидаемое поведение для Ayakaleaf Pro, и его можно игнорировать. Сообщение выводится, когда `OVERLEAF_IS_SERVER_PRO` не равна `true`, что и имеет место в образе Ayakaleaf Pro. Ayakaleaf Pro не нуждается в этой переменной, поэтому оставьте её незаданной.

</Accordion>

<Accordion title="Контейнер `sharelatex` постоянно перезапускается">

Перед запуском Overleaf контейнер выполняет стартовые проверки и завершает работу, если одна из них не проходит. Toolkit запускает его с `restart: always`, поэтому Docker снова запускает контейнер, и та же проверка снова завершается ошибкой. В выводе при запуске указано, какая проверка не прошла:

```sh
bin/docker-compose logs --tail=100 sharelatex
```

Частые причины:

* **`Missing required secrets`**: задайте `OVERLEAF_INVITE_TOKEN_SECRET` в `config/variables.env`, см. [Переменные окружения](/ru/on-premises/configuration/overleaf-toolkit/environment-variables).
* **`ShareLaTeX to Overleaf rebranding`**: в конфигурации всё ещё используются переменные или пути `SHARELATEX_`; переименуйте их, как указано в сообщении.
* **Ошибка после `Checking can connect to mongo and redis`**: Overleaf не может подключиться к MongoDB или Redis. Проверьте `bin/logs mongo` и `bin/logs redis`.

Устранив причину, выполните `bin/up -d`.

</Accordion>

<Accordion title="Контейнер останавливается на `910_initiate_doc_version_recovery` или завершается с кодом 2">

При каждом запуске контейнер по очереди выполняет свои стартовые скрипты, а в журнале каждый из них указывается как `*** Running /etc/my_init.d/<script>...`. Скрипту `910_initiate_doc_version_recovery` есть что делать только на экземплярах, на которых когда-то работал Overleaf 5.0.1. На любом другом экземпляре он выводит `No recovery of doc versions needed.`, и запуск продолжается. Его вывод также записывается в `data/history/doc-version-recovery.log` в `OVERLEAF_DATA_PATH`.

Что произошло, можно понять по коду выхода и концу вывода `bin/docker-compose logs --tail=100 sharelatex`:

* **Код выхода 2**, и журнал заканчивается строкой `*** Init system aborted.`: контейнер был остановлен, например командой `bin/stop`, `docker stop` или нажатием Ctrl+C в `bin/up`. Скрипт в последней строке `Running` — лишь тот, который выполнялся в этот момент; он не завершился ошибкой. Снова запустите контейнер командой `bin/up -d` и дождитесь окончания запуска.
* **Код выхода 1**, и в журнале есть строка `*** /etc/my_init.d/<script> failed with status <n>`: этот скрипт завершился ошибкой, и сама ошибка находится в строках непосредственно выше. Если `910_initiate_doc_version_recovery` завершился ошибкой `Detected unflushed changes while recovering doc versions`, значит, на экземпляре работал 5.0.1 и в нём остались несброшенные правки; следуйте официальному руководству [Doc version recovery](https://docs.overleaf.com/on-premises/release-notes/release-notes-5.x.x/doc-version-recovery).

</Accordion>

<Accordion title="«Restricted, sorry you don’t have permission to load this page»">

Эта страница отображается, когда вы вошли в учётную запись, но вам не разрешено открывать страницу, например когда страница администратора открыта учётной записью, не являющейся администратором, или проект не предоставлен вам в общий доступ.

Чтобы открыть страницы администратора, войдите с учётной записью администратора. Существующий администратор может назначить администратором другую учётную запись, либо вы можете создать её командой `create-user --admin`, см. [Управление пользователями](/ru/on-premises/user-and-project-management/user-management). В среде разработки (`develop/`) для страниц администратора также требуется `ADMIN_PRIVILEGE_AVAILABLE=true` в `develop/dev.env`; в образе Ayakaleaf Pro это значение уже задано.

</Accordion>
