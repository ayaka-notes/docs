개발 환경의 샌드박스 컴파일은 프로덕션 이미지와 조금 다르게 동작합니다. 개발 환경에는 이미 설정되어 있으며, 이 페이지에서는 그 설정과 유의해야 할 세 가지를 설명합니다.

* 파일 권한 문제
* history-v1과 filestore 간 볼륨 공유
* 하위 디렉터리 문제

### 샌드박스 컴파일 활성화 {#enable-sandbox-compiles}

샌드박스 컴파일은 기본으로 켜져 있습니다. `develop/docker-compose.yml`이 `clsi`에 `SANDBOXED_COMPILES=true`를 설정하고, 나머지는 `develop/dev.env`에 있습니다.

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

clsi는 이미지를 직접 받지 않으므로 `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1`(및 `:2025.1`)로 이미지를 한 번 받으세요.

LaTeX는 형제 컨테이너에서 `TEXLIVE_IMAGE_USER`로 실행됩니다. 개발 환경에서는 `tex`이며, 이는 clsi의 기본값이기도 합니다(`services/clsi/config/settings.defaults.cjs:154`). 프로덕션 이미지는 `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true`일 때 대신 `www-data`를 사용합니다(`server-ce/config/env.sh:15-21`). 그곳에서는 Overleaf 컨테이너의 `www-data` 사용자가 파일을 만들기 때문입니다.

<Warning>

직접 빌드한 이미지는 사용하지 마세요. 여러 가지 오류가 발생할 수 있습니다.

</Warning>

### 파일 권한 수정 {#fix-file-permissions}

clsi 컨테이너는 root로 시작하여 `compiles`, `output`, `cache` 폴더를 `node` 사용자(uid `1000`)에게 넘긴 뒤 clsi를 `node`로 실행합니다(`services/clsi/entrypoint.sh`). 따라서 호스트의 `develop/compiles`는 uid `1000` 소유이며, 이는 개발 환경의 `tex`와 같은 uid입니다(`develop/pandoc/Dockerfile`의 주석 참고). 위 설정이면 개발 환경은 권한을 바꾸지 않아도 컴파일됩니다.

대신 `TEXLIVE_IMAGE_USER=root`를 설정하면 root(uid `0`)에는 `compiles` 하위 폴더에 쓸 권한이 없습니다. 이 경우 `compiles`의 소유 그룹을 `root`로 하고 쓰기 권한을 준 다음, 새 하위 폴더가 이 소유권을 상속하도록 `setgid`를 설정하세요.

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

자세한 문서는 `services/clsi/README.md`를 참고하세요.

### history-v1과 filestore 간 볼륨 공유 {#volume-share-between-history-v1-and-filestore}

<Info>

이 섹션과 다음 섹션의 설정은 이미 `develop/docker-compose.yml`과 `develop/dev.env`에 들어 있습니다. `develop/dev.rc`에서 `S3_ENABLED=false`일 때만 의미가 있습니다. 기본값인 `S3_ENABLED=true`에서는 filestore와 history-v1이 이 파일들을 대신 RustFS 버킷에 보관합니다(`develop/s3/docker-compose.yml`).

</Info>

기본적으로 filestore는 Overleaf에서 S3와 다른 서비스 사이의 다리 역할을 합니다. 하지만 Overleaf CE나 Server Pro에서는 기본적으로 모든 파일이 로컬에 저장됩니다. 그래서 Overleaf는 매우 까다로운 방법을 도입했습니다.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

동시에 `data/history`는 기록 서비스에서도 사용됩니다. 이렇게 하면 서로 다른 마이크로서비스가 같은 데이터를 공유할 수 있습니다. 그래서 develop의 filestore 서비스는 history-v1의 `history-v1-buckets` 볼륨을 마운트합니다. 이것이 없으면 **clsi가 filestore 서비스에서 blob 파일을 가져올 수 없습니다**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

filestore는 `dev.env`의 다음 설정으로 버킷을 찾습니다.

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### 하위 디렉터리 사용 {#use-subdirectories}

filestore는 기록 blob을 항상 하위 디렉터리와 함께 읽습니다(`services/filestore/app/js/KeyBuilder.js:58`, `:70`). 프로덕션 이미지는 history-v1에 `useSubdirectories`를 켜지만(`server-ce/config/production.json`) history-v1의 기본 설정은 그렇지 않으므로, 개발 환경에서는 history-v1이 <strong>모든 데이터를 평탄하게 저장하게 됩니다.</strong> 그래서 `dev.env`가 history-v1에 `NODE_CONFIG`를 설정합니다.&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

이 설정이 없으면 history-v1은 `project_blobs` 파일을 다음과 같이 저장합니다.

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

`useSubdirectories`를 `true`로 설정하면 이 이름들의 `_`가 `/`가 되어 각 blob이 하위 폴더에 저장됩니다.
