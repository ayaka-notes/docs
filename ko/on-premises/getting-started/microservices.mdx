Overleaf Server CE 및 Overleaf Pro 인스턴스를 배포하고 관리하는 권장 방법은 Toolkit을 사용하는 것입니다.

Toolkit은 필요한 마이크로서비스의 오케스트레이션을 추상화하는 몇 가지 사용자 정의 스크립트를 통해 Overleaf 인스턴스 생성을 간소화합니다. 번들로 제공되는 초기화 스크립트를 실행하고 영구 스토리지 경로 등 몇 가지 구성 옵션만 지정하면, Toolkit이 Overleaf Server CE 또는 Pro 인스턴스를 구성하는 마이크로서비스의 프로비저닝과 연결을 처리합니다.

따라서 사용자 경험을 맞춤화하고 온프레미스 인스턴스에 필요한 특정 기능을 구현하는 데 집중할 수 있습니다. Toolkit이 모든 복잡한 작업을 내부적으로 처리하므로 Overleaf 인스턴스를 간단하게 배포할 수 있습니다.

<Info>

역사적인 이유로 메인 Overleaf 컨테이너의 이름은 `sharelatex`이며, `sharelatex/sharelatex` Docker 이미지를 기반으로 합니다. 이는 이 기술이 Overleaf에 합병된 ShareLaTeX 코드베이스를 기반으로 하기 때문입니다. 자세한 내용은 [이 블로그 게시물](https://www.overleaf.com/blog/518-exciting-news-sharelatex-is-joining-overleaf)을 참조하세요. 향후 언젠가 Overleaf 명명 체계에 맞게 이름이 변경될 예정입니다.

</Info>

#### 아키텍처

Overleaf 컨테이너 내부에서 소프트웨어는 `runit`이 관리하는 마이크로서비스 집합으로 실행됩니다. 컨테이너 내부의 주요 파일은 다음과 같습니다.

* `/etc/service/`: 마이크로서비스 초기화 파일
* `/var/log/overleaf/`: 각 마이크로서비스의 로그
* `/overleaf/services/`: 각종 마이크로서비스의 코드
* `/var/lib/overleaf/`: 영구 데이터의 마운트 지점(호스트에서 `OVERLEAF_DATA_PATH`로 지정한 디렉터리에 해당)

#### MongoDB 및 Redis 컨테이너

Overleaf는 MongoDB와 Redis라는 두 개의 외부 데이터베이스에 의존합니다. 기본적으로 Toolkit은 Overleaf 컨테이너 외에 이 데이터베이스 각각에 대한 컨테이너를 프로비저닝하므로, 총 세 개의 Docker 컨테이너가 실행됩니다.

<Info>

기존 MongoDB 또는 Redis 인스턴스에 연결하려면 [overleaf.rc](/ko/on-premises/configuration/overleaf-toolkit/files-and-locations#the-overleaf.rc-file) 구성 파일에서 해당 설정을 지정하면 됩니다.

</Info>

#### 편집기 및 컴파일 프로세스

이 섹션에서는 문서 처리와 컴파일 프로세스의 전반적인 개요를 설명합니다.

<Info>

이 페이지는 Overleaf Pro에서만 사용할 수 있는 샌드박스 컴파일(Sandboxed Compiles)을 사용하는 컴파일 프로세스를 설명합니다. Server CE에서는 컴파일 프로세스가 단순한 하위 프로세스를 사용합니다. **컨테이너**를 언급하는 항목을 **하위 프로세스에서 컴파일 실행**이라는 단일 항목으로 바꾸어 생각하면 됩니다.

</Info>

구성 요소 / 행위자:

* `user` — 애플리케이션 사용자
* `editor` — 브라우저에서 실행되는 클라이언트 애플리케이션
* `clsi` — PDF 컴파일에 사용되는 마이크로서비스
* `document-updater` — 문서 업데이트 처리에 사용되는 마이크로서비스
* `filestore` — 바이너리 파일을 처리하는 마이크로서비스
* `real-time` — 웹 소켓 처리에 사용되는 마이크로서비스
* `web` — API 요청 처리에 사용되는 (그다지 마이크로하지 않은) 서비스

**Redis 캐싱**

* **user**: 편집기 페이지를 로드합니다
* **editor**: 웹 소켓을 엽니다
* **editor**: 웹 소켓을 통해 문서 열기 요청을 보냅니다
  * **real-time** -> **document-updater**: 문서가 MongoDB에서 Redis로 로드됩니다
* **editor**: 웹 소켓을 통해 문서 업데이트를 보냅니다
  * **real-time** -> **document-updater**: Redis에서 문서가 업데이트됩니다
* **editor**: 추가 컴파일 요청을 보냅니다
  * 마지막 플러시 후 5분이 지나면(문서별):
    * **document-updater**: 문서를 Redis에서 MongoDB로 플러시합니다
* **editor**: 추가 업데이트를 보냅니다
  * 100개의 업데이트마다(문서별):
    * **document-updater**: 문서 기록을 Redis에서 MongoDB로 플러시합니다
* **user**: 편집기를 떠나거나 브라우저 탭을 닫습니다
  * 5분 후
    * **real-time**: 다른 공동 작업자가 있는지 확인하고, 없으면:
      * **real-time** -> **document-updater**: 문서를 Redis에서 MongoDB로 플러시합니다

**MongoDB에서 Redis로 읽기**

* **document-updater** -> **web** -> **docstore**: MongoDB에서 읽습니다

**Redis에서 MongoDB로 플러시**

* **document-updater** -> **web** -> **docstore**: MongoDB에 씁니다

**컴파일 — "full" 동기화 모드**

* **editor**: sync-mode를 "full"로 설정하여 컴파일 요청을 보냅니다
* **web** -> **document-updater**: 모든 문서를 Redis에서 MongoDB로 플러시합니다
* **web** -> **docstore**: MongoDB에서 모든 문서를 다운로드합니다
* **web** -> **clsi**: 다음을 포함한 컴파일 요청을 `clsi`로 보냅니다.
  * sync-mode
  * 파일 트리의 해시 -> "project state"
  * 모든 문서와 그 내용 -> 7MB 요청 본문 제한 적용
  * 별도 다운로드를 위한 바이너리 파일 URL
* **clsi**: sync-mode와 "project state"로 디스크상의 상태를 확인합니다
  * 전체 동기화이므로 이전 디스크 상태는 무시할 수 있습니다
* **clsi**: 컴파일 디렉터리를 정리합니다
* **clsi**: 모든 문서를 컴파일 디렉터리에 씁니다
* **clsi**: 모든 바이너리 파일을 컴파일 디렉터리에 씁니다
  * `clsi`는 프로젝트별 로컬 캐시에서 파일을 복사합니다
  * 캐시 미스 시:
    * **clsi** -> **filestore**: 파일을 다운로드합니다
* **clsi**: "project state"를 기록합니다
* **clsi**: 원하는 구성의 Docker 컨테이너가 존재하는지 확인합니다
  * TeX Live 버전을 포함한 컨테이너 옵션을 구성합니다
  * 옵션을 해시합니다
  * 컨테이너 이름: `project-<project-id>-<user-id>-<hash>`
* **clsi**: 컨테이너를 시작하고 stdout/stderr를 메모리로 스트리밍합니다 -> 2MB 제한
* **clsi**: 중지된 컨테이너를 남겨 둡니다 -> 24시간 후 정리됩니다
* **clsi**: stdout/stderr를 디스크에 씁니다
* **clsi**: 출력 파일을 고유한 출력 디렉터리로 복사합니다
  * build-id는 8바이트 난수와 밀리초 정밀도의 타임스탬프로 구성됩니다
  * 최근 3개(익명 사용자) / 최근 1개(로그인 사용자) 빌드 폴더를 제외한 나머지를 모두 삭제합니다
* **clsi**: 컴파일이 실패하거나 시간 초과된 경우
  * 컴파일 캐시를 삭제합니다 — 일부 파일만 있거나 손상된 캐시일 수 있습니다
* **editor**: output.log와 output.pdf를 다운로드합니다

**컴파일 — "incremental" 동기화 모드**

* **editor**: sync-mode를 "incremental"로 설정하여 컴파일 요청을 보냅니다
* **web** -> **document-updater**: Redis에서 문서를 가져옵니다
  * "project state" 해시도 Redis에 저장됩니다
  * **web**은 파일 트리의 해시를 `document-updater`에 보내며, 불일치하는 경우 `document-updater`는 증분 컴파일을 전체 컴파일로 전환할 수 있습니다
    * 편집기가 "full" 컴파일을 요청했을 때 수행되는 컴파일 프로세스를 참조하세요
* **web** -> **clsi**: 다음을 포함한 컴파일 요청을 `clsi`로 보냅니다.
  * sync-mode
  * 파일 트리의 해시 -> "project state"
  * Redis의 모든 문서와 그 내용 -> 7MB 요청 본문 제한 적용
  * 바이너리 파일 없음
* **clsi**: sync-mode와 "project state"로 디스크상의 상태를 확인합니다
  * 증분 동기화이므로 "project state"가 일치해야 합니다
  * 불일치 시: 409로 응답하여 web이 "full" 동기화로 재시도하도록 합니다
    * 편집기가 "full" 컴파일을 요청했을 때 수행되는 컴파일 프로세스를 참조하세요
* **clsi**: 업데이트된 문서를 컴파일 디렉터리에 씁니다
* **clsi**: 원하는 구성의 Docker 컨테이너가 존재하는지 확인합니다
  * TeX Live 버전을 포함한 컨테이너 옵션을 구성합니다
  * 옵션을 해시합니다
  * 컨테이너 이름: `project-<project-id>-<user-id>-<hash>`
* **clsi**: 컨테이너를 시작하고 stdout/stderr를 메모리로 스트리밍합니다 -> 2MB 제한
* **clsi**: 중지된 컨테이너를 남겨 둡니다 -> 24시간 후 정리됩니다
* **clsi**: stdout/stderr를 디스크에 씁니다
* **clsi**: 출력 파일을 고유한 출력 디렉터리로 복사합니다
  * build-id는 8바이트 난수와 밀리초 정밀도의 타임스탬프로 구성됩니다
  * 최근 3개(익명 사용자) / 최근 1개(로그인 사용자) 빌드 폴더를 제외한 나머지를 모두 삭제합니다
* **clsi**: 컴파일이 실패하거나 시간 초과된 경우
  * 컴파일 캐시를 삭제합니다 — 일부 파일만 있거나 손상된 캐시일 수 있습니다
* **editor**: output.log와 output.pdf를 다운로드합니다

**컴파일 — 모드 간 전환**

* **editor**: 컴파일 실패를 감지하면 다음 컴파일은 "full" 컴파일이 됩니다
* **editor**: 컴파일 성공을 감지하면 다음 컴파일은 "incremental" 컴파일이 됩니다
