### 초기화가 invalid command code로 실패합니다 {#initialization-fails-with-invalid-command-code}

`bin/init`은 macOS의 BSD sed를 발견하면 `sed: ... invalid command code`를 보고합니다. [1. Toolkit 다운로드](/ko/on-premises/installation/using-docker-compose/macos/1.-download-the-toolkit)에 설명된 대로 GNU sed를 `PATH`에 추가하고 `sed --version`을 확인하세요.

초기화에 실패하면 `config/`에 세 파일이 모두 남으면서 `OVERLEAF_INVITE_TOKEN_SECRET`이 비어 있을 수 있습니다. 그 후 `bin/init`을 다시 실행하면 `Config files already exist`가 표시됩니다. 한 번도 시작한 적이 없는 새 설치라면 세 파일을 백업 디렉터리로 옮기고 `bin/init`을 다시 실행하세요. 기존 인스턴스라면 구성과 비밀 값을 유지하고, `bin/init`을 다시 실행하기 위해 파일을 삭제하지 마세요.

### MongoDB가 계속 재시작됩니다 {#mongodb-keeps-restarting}

MongoDB 로그와 Docker VM의 커널 버전을 확인하세요.

```bash
bin/docker-compose logs --tail=100 mongo
docker info --format '{{.KernelVersion}}'
```

로그에 Linux 커널 비호환성이 언급되어 있다면 [Docker VM의 Linux 커널 확인](/ko/on-premises/installation/using-docker-compose/macos/5.-personalizing-your-instance#check-the-docker-vms-linux-kernel)을 따르고 `bin/up -d`를 다시 실행하세요. 종료 코드 `137`만으로는 MongoDB의 메모리가 부족했다는 것이 증명되지 않습니다. 컨테이너 상태와 로그를 확인하세요. Docker Desktop의 오래된 MongoDB 문제에 대해서는 [문제 해결](/ko/on-premises/support/troubleshooting)도 참조하세요.

### Docker 데몬에 연결할 수 없습니다 {#cannot-connect-to-the-docker-daemon}

Docker Desktop을 시작하고 선택된 Docker 컨텍스트를 확인하세요. [0. Docker Desktop 설정](/ko/on-premises/installation/using-docker-compose/macos/0.-setup-docker-desktop)을 참조하세요. `docker info`는 작동하지만 컴파일이 Docker에 접근하지 못한다면 `config/overleaf.rc`의 소켓 설정을 확인하고 `clsi` 로그를 읽어 보세요. Mac에서 Docker CLI가 작동한다고 해서 애플리케이션의 소켓 마운트가 올바르다는 것이 증명되지는 않습니다.

### 페이지는 열리지만 컴파일이 실패합니다 {#the-page-opens-but-compiles-fail}

TeX Live 이미지가 로컬에 있고 Docker 엔진의 아키텍처와 일치하는지 확인하세요.

```bash
docker image inspect ghcr.io/ayaka-notes/texlive-full:2026.1 \
  --format '{{.Os}}/{{.Architecture}}'
bin/logs -f clsi
```

Apple silicon에서는 이미지가 `linux/arm64`여야 합니다. `SERVER_PRO`와 `SIBLING_CONTAINERS_ENABLED`가 모두 `true`인지 확인한 다음 `bin/up -d`로 변경 사항을 적용하세요. 로그에 컴파일 디렉터리가 없다고 표시되면 Docker Desktop의 파일 공유와 `OVERLEAF_DATA_PATH` 위치를 확인하세요. 마운트 실패를 숨기기 위해 Sandboxed Compiles를 끄지 마세요.

### Not a directory 오류가 나거나 바인드 마운트가 없습니다 {#not-a-directory-or-a-bind-mount-is-missing}

오버라이드가 마운트하는 호스트 파일이 삭제되었거나, 파일이 있어야 할 위치에 Docker가 디렉터리를 만들었을 수 있습니다. 호스트의 소스 경로를 확인하고, 마운트가 파일을 기대하는지 디렉터리를 기대하는지 확인하세요. 컨테이너를 다시 만들기 전에 구성 파일을 복원하세요. `/tmp` 아래에 설치한 경우 macOS가 임시 파일을 제거한 후 이 문제가 발생할 수 있습니다.

### 포트 또는 컨테이너 이름 충돌 {#port-or-container-name-conflicts}

포트 `8080`이 사용 중이라면 `config/overleaf.rc`에서 다른 포트를 선택하고, `OVERLEAF_SITE_URL`도 그에 맞게 설정한 다음 `bin/up -d`를 다시 실행하세요.

Toolkit은 컨테이너에 `sharelatex`, `mongo`, `redis` 같은 고정된 이름을 부여합니다. `PROJECT_NAME`만 변경해서는 두 Toolkit 설치가 서로 독립되지 않습니다. 두 번째 인스턴스를 시작하기 전에 `docker ps -a`를 확인하고, Compose 오버라이드에서 다른 컨테이너 이름, 다른 포트, 별도의 데이터 디렉터리를 사용하세요. 이름 충돌을 해결하기 위해 기존 배포의 컨테이너나 데이터를 제거하지 마세요.

### 얼마 후 인스턴스에 접근할 수 없습니다 {#the-instance-is-unreachable-after-a-while}

Mac이 잠자기 상태가 되었거나 Docker Desktop이 종료되었을 가능성이 높습니다. [인스턴스 가용성 유지](/ko/on-premises/installation/using-docker-compose/macos/6.-post-installation-tasks#keep-the-instance-available)를 참조하세요.

### `bin/doctor`가 Linux가 아니라고 하거나 Quay 로그인을 요구합니다 {#bin/doctor-says-this-is-not-linux-or-asks-for-a-quay-login}

공개 이미지를 사용하는 macOS에서는 두 경고 모두 정상입니다. [2. Toolkit 살펴보기](/ko/on-premises/installation/using-docker-compose/macos/2.-familiarize-yourself-with-the-toolkit)를 참조하세요. 대신 이미지 가져오기, 서비스 상태, 컴파일 결과를 확인하고, 보고서의 다른 오류는 무시하지 마세요.
