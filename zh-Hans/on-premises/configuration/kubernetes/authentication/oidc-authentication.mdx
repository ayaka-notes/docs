---
title: OIDC 身份验证
description: 在 Kubernetes 部署中让用户通过 OpenID Connect 提供方登录。
icon: id-card-clip
---

OIDC 登录由每个 Ayakaleaf Pro pod 中的 **web** 服务（`authentication` 模块）处理。它没有后台任务，也没有单独的 pod。提供方一侧（客户端、重定向 URI、管理员声明）与 Toolkit 上相同，因此请先按照 [OIDC 身份验证](/zh-Hans/on-premises/configuration/overleaf-toolkit/authentication/oidc-authentication)设置你的 OpenID 提供方（OP），然后按如下方式将这些值放入 Kubernetes。

### 各组件的运行位置

| | |
| --- | --- |
| 服务 | web，位于每个 Ayakaleaf Pro pod 中；设置在 web 启动时读取 |
| Pod → OP | `OVERLEAF_OIDC_TOKEN_URL` 和 `OVERLEAF_OIDC_USER_INFO_URL`，每次登录时访问 |
| 浏览器 → OP | `OVERLEAF_OIDC_AUTHORIZATION_URL`，退出登录时还有 `OVERLEAF_OIDC_LOGOUT_URL` |
| OP → Overleaf | 无：OP 只会将浏览器重定向回来 |
| 登录状态 | Redis 中的会话，由所有副本共享 |
| 定期任务 | 无 |

### 配置

<Steps>
<Step title="在 OP 中注册 Overleaf">
在你的 OP 中允许以下由 `OVERLEAF_SITE_URL` 构成的地址：

| 用途 | URI |
| --- | --- |
| 重定向 URI（登录） | `${OVERLEAF_SITE_URL}/oidc/login/callback` |
| 退出登录后的重定向 URI | `${OVERLEAF_SITE_URL}` |
| 关联现有账户后的退出登录重定向 URI | `${OVERLEAF_SITE_URL}/user/settings` |

按照[通过发现文档查找这些值](/zh-Hans/on-premises/configuration/overleaf-toolkit/authentication/oidc-authentication#finding-the-values-with-the-discovery-document)中的说明，在 OP 的发现文档中找到这五个 URL。
</Step>

<Step title="将设置添加到 ConfigMap">
添加到 `overleaf-env`（`30-config.yaml`，或在[多个副本](/zh-Hans/on-premises/configuration/kubernetes/horizontal-scaling)时为 `60-config.yaml`）：

```yaml title="30-config.yaml (additions)" wrap
  EXTERNAL_AUTH: oidc
  OVERLEAF_OIDC_PROVIDER_ID: authentik
  OVERLEAF_OIDC_PROVIDER_NAME: Authentik
  OVERLEAF_OIDC_IDENTITY_SERVICE_NAME: Log in with Authentik
  OVERLEAF_OIDC_ISSUER: https://authentik.example.com/application/o/overleaf/
  OVERLEAF_OIDC_AUTHORIZATION_URL: https://authentik.example.com/application/o/authorize/
  OVERLEAF_OIDC_TOKEN_URL: https://authentik.example.com/application/o/token/
  OVERLEAF_OIDC_USER_INFO_URL: https://authentik.example.com/application/o/userinfo/
  OVERLEAF_OIDC_LOGOUT_URL: https://authentik.example.com/application/o/overleaf/end-session/
  OVERLEAF_OIDC_CLIENT_ID: <Client ID>
  OVERLEAF_OIDC_USER_ID_FIELD: username
  OVERLEAF_OIDC_IS_ADMIN_FIELD: groups
  OVERLEAF_OIDC_IS_ADMIN_FIELD_VALUE: Admins
  OVERLEAF_OIDC_UPDATE_USER_DETAILS_ON_LOGIN: "true"
```

`EXTERNAL_AUTH` 接受以空格分隔的列表，例如 `ldap oidc`。所有 `OVERLEAF_OIDC_*` 设置请参见[环境变量](/zh-Hans/on-premises/configuration/overleaf-toolkit/authentication/oidc-authentication#environment-variables)；除客户端密钥外，它们都放入 ConfigMap。

<Warning>

请为 `"true"` 和 `"false"` 加上引号：ConfigMap 只能保存字符串。设为 `""` 的键与缺失的键并不相同：`OVERLEAF_OIDC_ALLOWED_EMAIL_DOMAINS: ""` 会关闭首次登录时的账户创建，而省略该键则允许所有域名。

</Warning>
</Step>

<Step title="将客户端密钥放入 Secret">
```bash
kubectl -n overleaf patch secret overleaf-secrets --type merge \
  -p '{"stringData":{"OVERLEAF_OIDC_CLIENT_SECRET":"<Client Secret>"}}'
```
</Step>

<Step title="信任私有 CA（可选）">
如果 OP 的证书由你自己的 CA 签发，请将该 CA 添加到挂载在 `/var/lib/overleaf/certs` 的 Secret `overleaf-certs` 中（参见[证书和其他文件](/zh-Hans/on-premises/configuration/kubernetes#证书和其他文件)），并让 Node.js 指向它：

```yaml
  NODE_EXTRA_CA_CERTS: /var/lib/overleaf/certs/ca.pem
```
</Step>

<Step title="应用并重启">
```bash
kubectl apply -f 30-config.yaml
kubectl -n overleaf rollout restart deployment/overleaf     # or statefulset/overleaf
kubectl -n overleaf rollout status deployment/overleaf
```

然后检查每个 pod 是否都能访问 token 端点。调用该端点的是 pod 而不是浏览器，因此防火墙或 DNS 问题只会在这里暴露出来：

```bash
for p in $(kubectl -n overleaf get pod -l app=overleaf -o name); do   # app=overleaf-ha for several replicas
  kubectl -n overleaf exec "$p" -- curl -sS -o /dev/null -w "$p %{http_code}\n" \
    https://authentik.example.com/application/o/token/
done
```

任何 HTTP 状态码（GET 请求返回 `405`）都表示端点可以访问；`000` 表示无法访问。
</Step>
</Steps>

### 多个副本

无需额外操作。登录的 `state` 值以及退出登录时使用的 ID token 都保存在会话中，而会话位于 Redis 中，因此无论回调由哪个副本接收都能正常工作。

### 在 Kubernetes 上的测试

以 goauthentik 作为 OP，在 Kubernetes 1.37 上，三个副本位于 HAProxy 之后，我们针对 OIDC 的端到端测试全部通过（35 个用例）：登录以及通过 OP 退出登录；按组、按邮箱、按单个值映射管理员以及不进行映射；每次登录时更新姓名和管理员标志；关联和取消关联账户；OIDC 账户的密码重置和密码更改；已停用的账户；`OVERLEAF_OIDC_ALLOWED_EMAIL_DOMAINS`；`OVERLEAF_DISABLE_LOCAL_LOGIN`；以及 OIDC 与公开访问同时使用。

### 问答

<Accordion title="登录失败并提示“Unable to verify authorization request state”">

<strong>答：</strong>浏览器在回调时没有将会话 cookie 发送回来。在 Kubernetes 上，常见原因有：

* 设置了 `OVERLEAF_SECURE_COOKIE`，但用户通过普通 HTTP 打开站点，因此浏览器从不保存该 cookie。`OVERLEAF_SECURE_COOKIE` 的任何值（即使是 `"false"`）都会开启安全 cookie；请改为删除该键。
* 站点是通过与 `OVERLEAF_SITE_URL` 不同的地址打开的。
* 在 HTTPS 之后，你的 ingress 或负载均衡器没有发送 `X-Forwarded-Proto: https`，或者其地址未包含在 `OVERLEAF_TRUSTED_PROXY_IPS` 中。

</Accordion>

<Accordion title="在哪里可以看到登录失败的原因？">

<strong>答：</strong>在处理该请求的 pod 的 web 日志中，而不是在 `kubectl logs` 中：

```bash
kubectl -n overleaf exec deploy/overleaf -- grep -i oidc /var/log/overleaf/web.log | tail
```

如果有多个副本，请逐一检查每个 `overleaf-N`。

</Accordion>
