### 简介

在开始开发之前，我们希望你先了解以下几点：

* Overleaf 官方在一个[内部仓库](http://github.com/overleaf/internal)中进行开发，社区版则发布在 [overleaf/overleaf](https://github.com/overleaf/overleaf)。由一个 copybot 负责在内部仓库和公共仓库之间同步代码。
* [Ayaka-notes/overleaf-pro](https://github.com/ayaka-notes/ayakaleaf-pro) 是 Overleaf 社区版的一个分支版本。我们希望这个项目能够长期维护，因此在贡献之前请遵守以下规则。

### 提交规则

* 请不要对现有的 Overleaf 代码进行大范围修改。尽可能将功能集中在 `services/web/modules` 文件夹中。这样可以最大限度地减少我们之后合并和更新代码时的工作量。
* Vibe coding 确实非常便捷，但很容易把项目弄得一团糟，导致之后难以维护，因此请谨慎使用。
* 开发过程中请不要添加任何与翻译相关的内容；尽可能使用现有的翻译。
* 除非绝对必要，否则避免引入新的环境变量。如果确实需要，请确保它们尽可能与 Overleaf Toolkit 或 [docs.overleaf.com](https://docs.overleaf.com/) 中的环境变量保持一致。

### 分支规则

我们在 overleaf-pro 开发中使用以下分支：

* `main`：此分支仅用于同步上游代码，请**不要**提交任何外部更改。在此分支中，我们会设置一些类似 `ce-v[X.x.x]` 的标签，表示其对应 Overleaf 官方社区版的 `v[X.x.x]`。注意：此标签不可变！
* `server-pro`：此分支是日常开发的默认分支。
* `feature-X`：此分支用于开发某个特定功能。
* `release-vX.0.0`：专用于发布的分支，我们会在发布前在此进行一些热修复。

### GitHub Action

[GitHub Action](https://github.com/ayaka-notes/ayakaleaf-pro/actions) 负责自动化 CI/CD。你无需在自己的机器上构建镜像：下面的每个镜像都由工作流构建，支持手动触发的工作流只需一键即可构建。

| 工作流 | 触发方式 | 来源 | 镜像 |
| --- | --- | --- | --- |
| Sync Upstream Code | 每日、手动 | `overleaf/overleaf` → `main` | — |
| Build Development Image | 每日、手动 | `server-pro` | `ghcr.io/ayaka-notes/overleaf-pro/dev:<service>` |
| Build Operations Image | 推送 / PR 到 `server-pro`、手动 | 推送的提交或 PR head | `ghcr.io/ayaka-notes/overleaf-pro/ops:<YYYYMMDDHHMM>-<sha>`、`ops:latest` |
| Build Release Image | 手动 | 最新的 `release-v*` 分支 | `ghcr.io/ayaka-notes/overleaf-pro:<version>`、`:latest` 以及 `overleaf-pro/git-bridge` |

* **开发镜像**每个只包含一个微服务（`web`、`webpack`、`clsi` 等），支持 `linux/amd64` 和 `linux/arm64`。Codespace 环境通过 `develop/docker-compose.image.yml` 拉取这些镜像，而不是运行 `bin/build`。
* **运维镜像**是完整的单容器镜像（类似 `sharelatex/sharelatex`），用于端到端测试某项更改。`ops:latest` 只会在推送到 `server-pro` 时更新；PR 只会得到带时间戳的标签。这些镜像保留 7 天，仅供测试使用。
* **发布镜像**是用户实际部署的镜像。版本号来自分支名称，因此 `release-v6.3.0` 会发布 `overleaf-pro:6.3.0`。

<Steps>
<Step title="手动运行工作流">
打开 [Actions](https://github.com/ayaka-notes/ayakaleaf-pro/actions) 选项卡，在左侧选择工作流，点击 **Run workflow** 并确认。Build Operations Image 还提供 **Build without cache** 选项，可在缓存层过期时使用。
</Step>

<Step title="在你的 Fork 中构建">
同样的工作流也可以在 fork 中运行：在你的 fork 中启用 Actions，然后从其 Actions 选项卡运行。镜像会使用内置的 `GITHUB_TOKEN` 推送到 `ghcr.io/<your-name>/overleaf-pro/...`，因此无需配置任何 secret。Sync Upstream Code 和旧镜像清理只会在 `ayaka-notes` 中运行。

Build Release Image 需要你的 fork 中存在 `release-v*` 分支。
</Step>
</Steps>

<Info>

要查看镜像是基于哪个提交构建的：运维镜像的标签以短提交哈希结尾，发布镜像则在 `com.overleaf.pro.revision` 标签中携带该哈希（参见下方问答中的 `docker inspect`）。

</Info>

### 问答

<Accordion title="如何找到 Overleaf 社区版 `X.0.0` 对应的提交哈希？">

首先，你需要拉取 Docker 镜像，并运行以下命令来查看该 Docker 镜像中的标签：

```shellscript title="bash" wrap
docker inspect --format='{{json .Config.Labels}}' sharelatex/sharelatex:6.0.0
{"com.overleaf.ce.revision":"b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f","org.opencontainers.image.ref.name":"ubuntu","org.opencontainers.image.version":"24.04"}
```

然后你可以检查该[提交（b0d05c0）](https://github.com/overleaf/overleaf/commit/b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f)是否存在于上游 master 分支中。

</Accordion>

<Accordion title="为什么 CE 镜像 `6.0.0` 和 `6.0.1` 中的提交哈希相同？">

这是预期行为。6.0.1 版本是基于 6.0.0 镜像构建的小型补丁版本。这些更改是通过对现有 6.0.0 镜像打补丁实现的，而不是基于新的提交重新构建镜像。因此，6.0.0 和 6.0.1 镜像中的提交哈希是相同的。

详细信息请参阅 [hotfix](https://github.com/overleaf/overleaf/tree/main/server-ce/hotfix)。

</Accordion>
