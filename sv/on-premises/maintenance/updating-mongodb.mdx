<Info>

Varje ny version av Server CE/Server Pro anger eventuella ändringar av vilken MongoDB-version som stöds i sina [versionsinformationer](https://docs.overleaf.com/on-premises/release-notes).

</Info>

### Bör jag uppdatera MongoDB?

Du bör **endast** överväga att uppdatera din MongoDB-version om du planerar att uppgradera din instans av Server CE/Server Pro.

Om du kör en MongoDB-version som är nyare än den som rekommenderas för din nuvarande (eller planerade) version behöver du inte göra några ändringar.

<Warning>

Du bör aldrig nedgradera din MongoDB-version.

</Warning>

Om du upplever ett specifikt problem som du tror kan bero på din nuvarande version av MongoDB får du gärna [skapa ett ärende](https://github.com/overleaf/overleaf/issues) om du använder Server CE, eller kontakta Overleaf Support om du använder Server Pro.

När du öppnar `mongo`-skalet bör den aktuella versionen skrivas ut direkt.

bin/docker-compose exec mongo mongod --version

### Uppdateringsprocess

Så här uppdaterar du MongoDB-versionen i samband med en uppgradering av din Server CE/Server Pro-instans:

1. Bestäm vilken version av Server CE/Server Pro du planerar att uppgradera till.
2. Ta reda på vilken MongoDB-version som rekommenderas för just den versionen av Overleaf Server CE/Server Pro.
3. Följ instruktionerna för att uppgradera MongoDB till målversionen.
4. Uppgradera avbildningsversionen av Server CE/Server Pro och starta om instansen.

Vår rekommendation är att alltid uppgradera **Server CE/Server Pro** till den senaste tillgängliga versionen, eftersom den alltid garanterat stöds (gäller endast Server Pro-användare).

<Danger>

När du uppgraderar Server CE/Pro rekommenderar vi att du uppgraderar till den senaste versionen av den installerade huvudversionen **innan** du uppgraderar till den senaste versionen av **nästa** huvudversion. Om din installation ligger mer än en huvudversion efter den senaste måste du utföra en uppgradering i flera steg.

Om du till exempel kör 3.5.10 behöver du uppgradera till 3.5.13 -> utföra migreringen av Full Project History -> 4.2.9 -> 5.5.4.

Du bör **aldrig** hoppa över huvudversioner (3.5.10 -> 5.5.4). Om du använder Toolkit och ligger mer än en huvudversion efter den senaste får du **inte** använda skriptet `bin/upgrade`, eftersom du måste utföra en manuell uppgradering i flera steg.

</Danger>

<Warning>

Det är viktigt att du tar en [konsekvent säkerhetskopia](/sv/on-premises/maintenance/data-and-backups#performing-a-consistent-backup) **före** varje uppgradering av huvudversion, så att du kan återgå om det skulle behövas.

</Warning>

#### Uppgradera MongoDB

MongoDB kräver **stegvisa uppgraderingar**. Det innebär att du inte kan gå direkt från, säg, `4.0` till `5.0`. Du måste först uppdatera från `4.2` till `4.4` och sedan till `5.0`.

<Info>

MongoDB använder jämna nummer för sina stabila versioner.

</Info>

#### **Uppdateringsinstruktioner när MongoDB körs utanför Docker**

Här är länkar till uppdateringsinstruktionerna från mongodb.com för uppgradering av MongoDB.

* [MongoDB versionsinformation - uppgradera MongoDB från `4.2` till `4.4`](https://www.mongodb.com/docs/v4.4/release-notes/4.4-upgrade-standalone/)
* [MongoDB versionsinformation - uppgradera MongoDB från `4.4` till `5.0`](https://www.mongodb.com/docs/v5.0/release-notes/5.0-upgrade-replica-set/)
* [MongoDB versionsinformation - uppgradera MongoDB från `5.0` till `6.0`](https://www.mongodb.com/docs/v6.0/release-notes/6.0-upgrade-replica-set/)
* [MongoDB versionsinformation - uppgradera MongoDB från `6.0` till `7.0`](https://www.mongodb.com/docs/manual/release-notes/7.0-upgrade-replica-set/#std-label-7.0-upgrade-replica-set)
* [MongoDB versionsinformation - uppgradera MongoDB från `7.0` till `8.0`](https://www.mongodb.com/docs/manual/release-notes/8.0-upgrade-replica-set/#std-label-8.0-upgrade-replica-set)

<Info>

Instruktionerna för `5.0` och senare avser en installation med replikuppsättning (replica set) i stället för en fristående installation. Eftersom Server Pro/CE 4.0.1+ använder transaktioner måste MongoDB köras som en replikuppsättning.

</Info>

<Warning>

Dokumentationen för MongoDB 3.2 till 4.2 finns nu tillgänglig via [https://www.mongodb.com/docs/legacy/](https://www.mongodb.com/docs/legacy/)

</Warning>

**Grundläggande instruktioner**

I de flesta fall kräver uppdateringen att en kompatibilitetsflagga sätts innan mongo-versionen faktiskt uppdateras. Stegen är följande:

1. Sätt kompatibilitetsflaggan enligt beskrivningen i MongoDB:s versionsinformation (se exemplen nedan).
2. Uppdatera sedan mongo-avbildningen:
   1. **Toolkit-användare** Uppdatera `MONGO_VERSION`, t.ex. `MONGO_VERSION=6.0`
   2. **Docker Compose-användare** Uppdatera versionen i taggen för avbildningen `mongo`,\
      t.ex. `services -> mongo -> image: mongo:6.0`;

**Exempel: Uppgradera MongoDB från `5.0` till `6.0`**

Vi börjar med att kontrollera att vi kör MongoDB `6.0`:

Användare av Overleaf Toolkit:

```bash
bin/docker-compose exec mongo mongod --version
# db version v5.0.24
```

Användare av Docker Compose:

```bash
docker compose exec mongo mongod --version
# db version v5.0.24
```

Enligt [uppgraderingsinstruktionerna](https://docs.mongodb.com/manual/release-notes/3.6-upgrade-standalone/#upgrade-version-path) är det enda kravet att `featureCompatibilityVersion` är satt till `5.0`. Det gör vi genom att öppna ett MongoDB-skal och köra det angivna kommandot:

Användare av Overleaf Toolkit:

```bash
bin/mongo
# MongoDB shell version v5.0.24
# ...
# overleaf:PRIMARY> db.adminCommand( { setFeatureCompatibilityVersion: "5.0" } )
# { 
# "ok" : 1,
# ...
# }
overleaf:PRIMARY> exit
# bye
```

<Info>

Docker Compose-användare kan köra `docker compose exec mongo mongosh` för att få ett skal och köra samma kommandon som Toolkit-användare.

</Info>

Användare av Overleaf Toolkit:

Därefter stoppar vi Server CE/Server Pro- och MongoDB-instanserna med kommandot `bin/stop`, sätter `MONGO_VERSION=6.0` i `config/overleaf.rc` och startar sedan om tjänsten `mongo` med `bin/up mongo`) för att kontrollera att uppdateringen gick smidigt.

Slutligen uppdaterar vi avbildningsversionen av Server CE/Server Pro till vår målversion och återskapar alla tjänster med kommandot `bin/up -d`.

Användare av Docker Compose:

Därefter stoppar vi Server CE/Server Pro- och MongoDB-instanserna med kommandot `docker compose stop`, uppdaterar filen [`docker-compose.yml`](https://github.com/overleaf/overleaf/blob/4b1babd4ea634ab12c54e9a9aea7db0e8a500941/docker-compose.yml) så att den använder `image: mongo:6.0` och startar sedan om tjänsten `mongo` med kommandot `docker compose up mongo` för att kontrollera att uppdateringen gick smidigt.

Slutligen uppdaterar vi avbildningsversionen av Server CE/Server Pro till vår målversion och återskapar alla tjänster med kommandot `docker compose up`.

Slutligen uppdaterar vi avbildningsversionen av Server CE/Server Pro till vår målversion och återskapar alla tjänster med kommandot `bin/up -d`.

#### Motsvarande kommandon för Docker Compose-användare

För Docker Compose-användare är motsvarande kommandon:

* `docker compose exec mongo mongod --version` för att visa mongo-versionen
* `docker compose exec mongo mongosh` för att starta ett mongo-skal för administrationskommandon
* kommandot `docker compose stop` för att stoppa servern

* Redigera filen [`docker-compose.yml`](https://github.com/overleaf/overleaf/blob/4b1babd4ea634ab12c54e9a9aea7db0e8a500941/docker-compose.yml) så att den använder `image: sharelatex:VERSION` för att uppgradera avbildningsversionen
* `docker compose up` för att återskapa alla tjänster.

### Skapa en anpassad roll

I version `5.5.1` införde vi en kontroll vid uppstart som verifierar funktionskompatibilitetsversionen för MongoDB. Om din MongoDB-databas använder autentisering (t.ex. grundläggande autentisering) kan det hända att containern `sharelatex` inte startar och visar behörighetsfelet "_not authorized on admin to execute command_".

För att lösa detta kan du antingen skapa en ny roll i MongoDB och tilldela den till användarkontot som används för att komma åt databasen enligt instruktionerna nedan, eller sätta `ALLOW_MONGO_ADMIN_CHECK_FAILURES=true` så att kontrollen kan misslyckas utan att installationen hindras från att starta.

<Check>

Den nya rollen ger **endast** behörighet att läsa klusteromfattande serverparametrar i MongoDB och kan även återanvändas för övervakningsändamål,

</Check>

```bash wrap
# Toolkit users
$ bin/docker-compose exec -it mongo mongosh -u {{YOUR-ADMIN-USERNAME}} -p

# Switch to the "admin" database using
overleaf [direct: primary] sharelatex> use admin
switched to db admin
overleaf [direct: primary] admin> 

# Create a new role with permission to use "getParamter". Copy and paste the function below into the shell and press the return key

db.createRole(
  {
    role: "clusterParameterReader",
    privileges: [
      {
        resource: { cluster: true },
        actions: ["getParameter"]    
      }
    ],
    roles: [] 
  }
);

# Switch back to the "sharelatex" database 
use sharelatex
switched to db sharelatex
overleaf [direct: primary] sharelatex> 

# Assign the new "clusterParameterReader" role to your database user by copy and pasting the function below into the shell and press the return key 
db.grantRolesToUser(
  "{{YOUR-DATABASE-USER}}",
  [
    { role: "clusterParameterReader", db: "admin" }
  ]
);

# Type exit then return to exit the MongoDB shell
# Run bin/up -d to start the deployment stack
$ bin/up -d
```
