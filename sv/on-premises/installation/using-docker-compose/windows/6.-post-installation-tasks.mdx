### Skapa administratören och ett första projekt {#create-the-administrator-and-a-first-project}

Öppna [http://localhost:8080/launchpad](http://localhost:8080/launchpad) i din **webbläsare i Windows**, skapa det första administratörskontot och logga in. Följ sedan [6. Uppgifter efter installationen](/sv/on-premises/installation/using-docker-compose/linux/6.-post-installation-tasks) i Linux-guiden och använd port `8080` i dess exempel-URL:er.

### Verifiera kompileringen {#verify-compilation}

En fungerande inloggningssida bevisar inte att de separata kompileringscontainrarna kan komma åt datakatalogen i WSL. Skapa ett tomt projekt och kompilera denna `main.tex` med **pdfLaTeX**:

```latex
\documentclass{article}
\begin{document}
Ayakaleaf Pro on Windows WSL 2.
\end{document}
```

PDF-förhandsvisningen ska visa texten. För basic-avbildningen väljer du vid behov **TeX Live 2026 Basic** i projektinställningarna.

Välj **XeLaTeX** och testa:

```latex
\documentclass{article}
\usepackage{fontspec}
\begin{document}
Ayakaleaf WSL XeLaTeX sandbox.
\end{document}
```

Båda exemplen fungerar med basic. För kinesiska dokument använder du en avbildning som innehåller `ctex` och de nödvändiga typsnitten, till exempel full, innan du testar följande med **XeLaTeX**. Basic innehåller dem inte:

```latex
\documentclass{ctexart}
\begin{document}
你好，Ayakaleaf Pro。
\end{document}
```

För att bekräfta att sandlådan används kör du följande i **Ubuntu** under kompileringen:

```bash
docker ps -a --filter ancestor=ghcr.io/ayaka-notes/texlive-basic:2026.1
bin/logs -f clsi
```

Använd namnet på den avbildning du valt i filtret. Korta kompileringar kan bli klara innan `docker ps` körs; `-a` visar även stoppade containrar fram till rensningen. En kompileringscontainer ska använda den avbildningen och en `/compile`-bind-montering från Toolkits datakatalog i WSL. Applikationsloggar ensamma ersätter inte en kontroll av PDF-filen.

### Verifiera beständigheten {#verify-persistence}

I **Ubuntu**, från Toolkit-katalogen:

```bash
bin/stop
bin/start
```

Vänta på applikationen, öppna projektet igen från Windows och kompilera på nytt. Ditt konto, källkoden och projektfilerna ska fortfarande finnas kvar. Som standard ligger de aktiva data i `~/ayakaleaf-toolkit/data/` i Ubuntu. Behåll både `config/` och `data/`; om du avinstallerar eller avregistrerar Ubuntu-distributionen kan de tas bort.

### Håll instansen tillgänglig {#keep-the-instance-available}

Att hålla instansen igång består av tre delar: Windows förblir vaket, Docker Desktop körs och containrarna startas om tillsammans med motorn.

I Docker Desktops **Settings → General** aktiverar du **Start Docker Desktop when you sign in to your computer**, se [Docker Desktop settings](https://docs.docker.com/desktop/settings-and-maintenance/settings/). Detta startar Docker efter inloggning, inte före. Efter en omstart av Windows loggar du in, väntar tills Docker Desktop har startat klart, öppnar Ubuntu och kontrollerar `docker ps` och webbplatsen.

Docker Desktops **Resource Saver** är skild från Windows viloläge. Den aktiveras normalt bara när inga containrar körs; den körande applikationen, MongoDB och Redis förhindrar det inaktiva tillståndet. På WSL 2 pausar den Docker-motorn i stället för att stänga av den delade WSL-VM:en. Använd inte **Pause** i Docker Desktop manuellt medan du betjänar användare. Du behöver inte inaktivera Resource Saver bara för att hålla den här stacken igång; se [Dockers dokumentation om Resource Saver](https://docs.docker.com/desktop/use-desktop/resource-saver/).

Toolkit-tjänsterna använder `restart: always`. Verifiera den faktiska inställningen i **Ubuntu**:

```bash
docker inspect sharelatex mongo redis --format '{{.Name}} restart={{.HostConfig.RestartPolicy.Name}}'
```

Varje tjänst ska rapportera `always`. När Docker körs kan den starta om dessa befintliga containrar utan en ny `bin/up`. En manuellt stoppad container förblir stoppad tills du startar den eller startar om motorn; med `always` kan en omstart av motorn starta den igen. Se [Dockers beteende för omstartspolicyer](https://docs.docker.com/engine/containers/start-containers-automatically/).

| Åtgärd | Effekt på Ayakaleaf |
| --- | --- |
| Stänga Ubuntu-terminalen efter `bin/up -d` | Containrarna körs frikopplade; terminalen övervakar dem inte. Se till att Docker Desktop och WSL-miljön förblir tillgängliga |
| Stänga fönstret Docker Dashboard | Fönstret kan stängas medan Docker Desktop fortsätter i systemfältet |
| Välja **Quit Docker Desktop** | Stoppar motorn och gör webbplatsen otillgänglig; öppna Docker Desktop igen för att återställa |
| Köra `wsl --shutdown` | Stoppar alla WSL-distributioner och avbryter Dockers WSL-backend; starta om Docker Desktop och öppna Ubuntu igen |
| Försätta Windows i vilo- eller viloläge (hibernation) eller stänga av det | Tjänsten är otillgänglig; att bara ha skärmen på eller av ändrar inte detta |
| Köra `bin/stop` | Stoppar instansen men behåller dess data; använd `bin/start` för att fortsätta |

För långvarig användning med nätström öppnar du **Settings → System → Power & battery → Screen, sleep & hibernate timeouts** i Windows 11 (vissa versioner visar **Power** eller **Screen and sleep**). Ställ in tidsgränsen för viloläge vid nätanslutning på **Never** och inaktivera automatisk viloläge (hibernation) om det är konfigurerat. Skärmen kan fortfarande stängas av. Vad som händer när en bärbar dators lock stängs är en separat inställning; om locket stängs kan datorn gå i viloläge även om tidsgränsen för inaktivitet är Never. Se [Energiinställningar i Windows](https://support.microsoft.com/en-us/windows/experience/power-battery/power-settings-in-windows-11).

Kör inte `wsl --shutdown` som rutinmässig rensning medan webbplatsen används. Om en ändring av WSL-inställningarna kräver det stoppar du instansen först och planerar ett avbrott. Windows kan köra instansen kontinuerligt med dessa inställningar. För en delad tjänst som måste klara utloggningar och obevakade omstarter rekommenderar vi [Linux-guiden](/sv/on-premises/installation/using-docker-compose/linux).

### Kontrollera återställningen efter omstart av Docker Desktop {#check-recovery-after-restarting-docker-desktop}

När du har sparat arbetet och låtit pågående kompileringar slutföras väljer du **Restart Docker Desktop** i Docker Desktops felsökningsmeny. Vänta på motorn och kontrollera sedan i **Ubuntu**:

```bash
docker ps
curl -I http://localhost:8080/launchpad
```

Öppna det befintliga projektet i Windows och kompilera det igen. Bekräfta att kontot och källkoden fortfarande finns.

Om du avsiktligt stoppade instansen med `bin/stop` använder du `bin/start`. Om Docker körs men en tjänst misslyckas läser du dess loggar i stället för att återskapa konfigurationen. Windows Update, Docker-uppdateringar och strömavbrott kan fortfarande avbryta en installation som körs dygnet runt; behåll säkerhetskopior och kontrollera återställningen efter planerat underhåll.

### Daglig användning {#daily-use}

Starta Docker Desktop i Windows. Öppna **Ubuntu**:

```bash
cd "$HOME/ayakaleaf-toolkit"
```

| Uppgift | Kommando |
| --- | --- |
| Starta befintliga containrar | `bin/start` |
| Stoppa containrar och behåll data | `bin/stop` |
| Tillämpa konfigurationsändringar | `bin/up -d` |
| Kontrollera status | `bin/docker-compose ps` |
| Läs startloggar | `bin/docker-compose logs --tail=100 sharelatex` |
| Läs MongoDB-loggar | `bin/docker-compose logs --tail=100 mongo` |
| Läs kompilatorloggar | `bin/logs -f clsi` |

`bin/start` tillämpar inte konfigurationsändringar: använd `bin/up -d` efter att du har ändrat `config/`. Följ [Data och säkerhetskopior](/sv/on-premises/maintenance/data-and-backups) innan du uppgraderar, flyttar eller tar bort WSL-distributionen. Att kopiera aktiva MongoDB-filer medan databasen skriver ger ingen konsekvent säkerhetskopia.

Behåll `127.0.0.1` för lokal användning. För att betjäna andra datorer krävs dessutom en medvetet vald lyssningsadress, webbplats-URL, Windows-brandvägg/nätverkskonfiguration och HTTPS; att bara ändra `OVERLEAF_SITE_URL` publicerar ingen port.

Om något inte fungerar, se [Felsökning](/sv/on-premises/installation/using-docker-compose/windows/troubleshooting).
