RHEL och dess ombyggen (Rocky Linux, AlmaLinux) levereras med Podman i stället för Docker, och vissa organisationer tillåter inte Docker på sina servrar. Toolkit kan i stället köra Ayakaleaf Pro på **rootless Podman**: containrarna körs som en vanlig användare, kompileringar körs fortfarande i sandlådade TeX Live-containrar och SELinux förblir i läget enforcing. Skriptet `bin/podman-setup` kontrollerar värden och åtgärdar det som går.

I slutet av det här avsnittet har du samma instans som med [Använda Docker Compose](/sv/on-premises/installation/using-docker-compose): Ayakaleaf Pro med sandlådade kompileringar, MongoDB och Redis, som du hanterar med de vanliga `bin/up`, `bin/doctor` och `bin/upgrade`.

<Info>

Stödet för Podman är experimentellt. Det kommer från den officiella Overleaf Toolkit, som bara testar det på RHEL 9 och senare med rootless Podman, sandlådade kompileringar och SELinux i läget enforcing. Vi har testat de här sidorna på Rocky Linux 9.9 (Podman 5.8, SELinux enforcing) med Ayakaleaf Pro 6.3.4. Docker är fortfarande den rekommenderade containerkörmiljön.

</Info>

### Vad du behöver {#what-you-need}

* **RHEL, Rocky Linux, AlmaLinux eller CentOS Stream 9 eller senare**, med SELinux i läget enforcing. `bin/podman-setup` avbryter på alla andra distributioner. På Ubuntu eller Debian använder du [Använda Docker Compose](/sv/on-premises/installation/using-docker-compose/linux).
* **En användare utan root-behörighet med `sudo`** som ska äga containrarna. Kör alla kommandon i det här avsnittet som den användaren; `bin/podman-setup` vägrar att köras som `root`.
* **En ren värd**: ingen Docker Engine och ingen befintlig Toolkit-installation. Att flytta en befintlig Docker-baserad instans till Podman beskrivs inte här.

### Hur det skiljer sig från Docker {#how-it-differs-from-docker}

|                                      | Docker                                     | Rootless Podman                                                                          |
| ------------------------------------ | ------------------------------------------ | ---------------------------------------------------------------------------------------- |
| Vem som kör containrarna             | Docker-daemonen, som `root`                | Din användare                                                                            |
| Socket som startar kompileringar     | `/var/run/docker.sock`                     | `/run/user/<uid>/podman/podman.sock`                                                     |
| Portar                               | Vilka som helst, till exempel `80` och `443` | `1024` och uppåt, till exempel `8080`                                                  |
| Värdens brandvägg (`firewalld`)      | Kringgås av publicerade portar             | Gäller: öppna porten med `firewall-cmd`                                                  |
| Start efter en omstart               | Docker-daemonen startar dem igen           | Användartjänsten `podman-restart`                                                        |
| SELinux                              | Konfigureras inte av Toolkit               | Policymodulen `podman_socket_clsi` och `SELINUX_MODE=managed` i `config/overleaf.rc`      |
| Seccomp-profil för kompileringar     | Inbyggd i avbildningen                     | Extraheras till `config/seccomp/<version>/` och anges som `SECCOMP_PROFILE` av Toolkit   |

### Kända begränsningar {#known-limitations}

* <strong>Git-integration.</strong> I Ayakaleaf Pro 6.3.4 misslyckas `git clone` med `502` på Podman: NGINX i avbildningen slår upp containern `git-bridge` med Dockers DNS-server (`127.0.0.11`), som Podman inte har. Korrigeringen ([1b911d1092](https://github.com/ayaka-notes/ayakaleaf-pro/commit/1b911d1092c80f7b0ff77c5e3805b40503d49964)) kommer i nästa version; låt `GIT_BRIDGE_ENABLED=false` stå kvar tills dess.
* <strong>Klienternas IP-adresser.</strong> Rootless Podman vidarebefordrar den publicerade porten inifrån containerns nätverk, så Ayakaleaf Pro ser varje besökare med en intern adress som `10.89.0.15`. En användares [granskningsloggar](/sv/on-premises/user-guide/administrators/user-management#audit-logs) i administratörspanelen visar den här adressen i stället för användarens IP-adress.
