## Förutsättningar {#prerequisites}

Overleaf är ett typiskt open source-projekt med mikrotjänstarkitektur, där alla tjänster körs i Docker.&#x20;

* Källkoden för den officiella Community Edition finns på [GitHub Overleaf Official](https://github.com/overleaf/overleaf/tree).&#x20;
* Källkoden för Overleaf-CEP finns på [GitHub Yu-i-i/Overleaf](https://github.com/yu-i-i/overleaf-cep).
* Ayakaleaf Pro finns på [GitHub ayaka-notes/ayakaleaf-pro](https://github.com/ayaka-notes/ayakaleaf-pro).

För att sätta upp en utvecklingsmiljö för Overleaf behöver du en kraftfull server; en konfiguration med minst 8 kärnor och 16 GB RAM rekommenderas, eftersom du behöver köra fler än 20 containrar samtidigt.

<Info>

Eftersom servrar med 8 eller fler CPU-kärnor vanligtvis är dyra rekommenderar vi starkt att du använder din lokala dator för utveckling.

</Info>

Som utvecklare förutsätter vi samtidigt att du redan är bekant med [installation av Docker](https://docs.docker.com/engine/install/ubuntu/). Vi rekommenderar starkt att du använder en aktuell och stabil Ubuntu LTS (t.ex. Ubuntu 24.04 under 2025–2026) och den senaste versionen av Docker för utveckling, eftersom det minskar risken för oväntade fel.

Sammanfattningsvis behöver du:

* [x] En kraftfull server/dator att utveckla på
* [x] En aktuell och stabil Ubuntu LTS (t.ex. Ubuntu 24.04)
* [x] En miljö med Docker och Git

## Konfigurationsguide {#configuration-tutorial}

Här använder vi Ayakaleaf Pro för att visa hur du sätter upp en utvecklingsmiljö för Overleaf. Alla kommandon nedan körs i katalogen `develop` om inget annat anges.

<Steps>
<Step title="Hämta källkoden">
Först klonar vi repot:

```bash title="bash"
git clone https://github.com/ayaka-notes/ayakaleaf-pro.git
cd ayakaleaf-pro/develop
```
</Step>

<Step title="Synkronisera `yarn.lock`">
Repot använder Yarn 4 (`packageManager` i rotens `package.json`), och dess `yarn.lock` kan vara osynkroniserad med `package.json`-filerna. Synkronisera den efter den första kloningen och efter varje ändring i en `package.json`:

```bash title="bash"
bin/sync
```

`bin/sync` kör `yarn install --mode=update-lockfile` i en `node:24.18.1`-container, så du behöver inte Node.js på värden. Checka inte in den ändrade `yarn.lock`.
</Step>

<Step title="Bygg utvecklingsavbildningen">
Bygg tjänsterna:

```bash title="bash"
bin/build
```

<Info>

Om Docker får slut på RAM när tjänsterna byggs parallellt skapar du en `.env`-fil i den här katalogen som innehåller `COMPOSE_PARALLEL_LIMIT=1`.

</Info>
</Step>

<Step title="Tillämpa översättningarna">
Modulerna i Ayakaleaf Pro har sina översättningar i `services/web/locales/locales_patches/`, som de incheckade språkfilerna inte innehåller. Tillämpa dem en gång före första starten, annars visar modulernas sidor nycklar som `about_to_permanently_delete_accounts` i stället för text:

```bash title="bash"
bin/i18n
```

Det kräver `jq` på värden. Kör det igen efter att du har lagt till en översättning eller bytt gren, se [Uppdatera i18n-översättningar](/sv/dev/environment/update-i18n-translations).
</Step>

<Step title="Starta alla mikrotjänster">
Starta sedan tjänsterna:

```bash title="bash"
bin/up
```

När tjänsterna körs öppnar du [http://localhost/launchpad](http://localhost/launchpad) för att skapa det första administratörskontot. Lägg till porten om du har ändrat `OVERLEAF_PORT` (se nedan).

<Info>

LDAP är på som standard (`LDAP_ENABLED=true` i `dev.rc`). Launchpad visar då LDAP-administratörsformuläret: det frågar bara efter en e-postadress, och den administratören loggar sedan in via LDAP, till exempel som `professor` / `professor` (`professor@planetexpress.com`). Testanvändarna listas i `develop/authentication/README.md`. Sätt `LDAP_ENABLED=false` och `SAML_ENABLED=false` för att i stället skapa en lokal administratör med lösenord.

</Info>
</Step>
</Steps>

<Info>

`develop/dev.env` sätter redan `ADMIN_PRIVILEGE_AVAILABLE=true`, så administratörer kan öppna administrationspanelen utan extra konfiguration.

</Info>

### Konfiguration (`dev.rc`) {#configuration-dev-rc}

`develop/dev.rc`, bredvid `dev.env`, innehåller utvecklingsmiljöns reglage, som `overleaf.rc` i Overleaf Toolkit. Ändra ett värde och kör `bin/dev` igen för att tillämpa det; en avstängd funktion stoppar även sina containrar.

| Variabel | Standard | Vad den gör |
| --- | --- | --- |
| `OVERLEAF_PORT` | `80` | Webbplatsens värdport. |
| `LDAP_ENABLED` | `true` | LDAP-inloggning med testanvändare. |
| `SAML_ENABLED` | `true` | SAML-inloggning med testanvändare. |
| `MAILPIT_ENABLED` | `true` | Fångar all e-post från `web` i Mailpit. Slår även på e-postbekräftelse (`EMAIL_CONFIRMATION_DISABLED=false`). |
| `S3_ENABLED` | `true` | Lagrar historik- och mallfiler i RustFS (S3) i stället för lokala volymer. |
| `HOPPSCOTCH_ENABLED` | `true` | Hoppscotch med en proxy in i Docker-nätverket, se [Konfigurera utvecklingsverktyg](/sv/dev/environment/setup-develop-tools). |
| `HOPPSCOTCH_PORT` | `9170` | Hoppscotchs värdport. |
| `GRAFANA_ENABLED` | `true` | Grafana på webbplatsens `/grafana/`, med tillstånd, mätvärden och loggar för varje tjänst, se [Konfigurera utvecklingsverktyg](/sv/dev/environment/setup-develop-tools). |

Varje funktion har sin `docker-compose.yml` och övriga filer i en egen mapp: `authentication/ldap`, `authentication/saml`, `mail`, `s3`, `hoppscotch` och `grafana`. En funktion som behöver en `web`-inställning utan miljövariabel monterar en fil i `/etc/overleaf/settings.d/`, och `develop/settings.dev-env.cjs` slår ihop dem alla. Alla `bin/*`-skript går via `bin/docker-compose`, som lägger till filerna för de påslagna funktionerna. Anropa `bin/docker-compose` i stället för `docker compose` när du själv behöver ett compose-kommando.

<Warning>

De lokala volymerna och RustFS är separata lagringar: ett projekt som skapats med `S3_ENABLED=true` saknar historik och binära filer efter byte till `false`, och tvärtom. För att kopiera filerna från en miljö som kördes innan `S3_ENABLED` fanns till RustFS, följ ”Moving existing data into RustFS” i [develop/README.md](https://github.com/ayaka-notes/ayakaleaf-pro/blob/server-pro/develop/README.md).

</Warning>

### Portar {#ports}

Webbplatsen, RustFS-konsolen och Hoppscotch lyssnar på värdens `127.0.0.1`; på en fjärrdator vidarebefordrar du först deras portar, till exempel `ssh -L 9001:localhost:9001 <host>`. Webbplatsen använder `OVERLEAF_PORT` från `dev.rc`, så lägg till porten i adresserna nedan om du har ändrat den.

| Sida | Adress | Inloggning |
| --- | --- | --- |
| Webbplats | [http://localhost](http://localhost) | Webbplatsens konton eller testanvändarna |
| E-postinkorg (Mailpit) | [http://localhost/mailpit/](http://localhost/mailpit/) | Ingen |
| Grafana | [http://localhost/grafana/](http://localhost/grafana/) | Ingen, anonyma användare är administratörer |
| Mongo Express | [http://localhost/mongo-express/](http://localhost/mongo-express/) | Ingen |
| RedisInsight | [http://localhost/redis-insight/](http://localhost/redis-insight/) | Ingen |
| S3-konsol (RustFS) | [http://localhost:9001/rustfs/console/](http://localhost:9001/rustfs/console/) | `rustfsadmin` / `rustfsadmin` |
| Hoppscotch | [http://localhost:9170](http://localhost:9170) (`HOPPSCOTCH_PORT`) | Ingen |

Mailpit, Grafana, Mongo Express och RedisInsight serveras av webbplatsen på egna sökvägar via webpack-dev-server, så de behöver ingen egen port. När du är inloggad länkar menyn **Dev tools** i webbplatsens navigeringsfält till dem; en sida vars funktion är avstängd i `dev.rc` utelämnas. [Konfigurera utvecklingsverktyg](/sv/dev/environment/setup-develop-tools) visar vad var och en gör.

S3-API:t (port 9000) och SMTP (port 1025) går bara att nå inuti Docker-nätverket. Mongo (27017), Redis (6379), Mongo Express (8081), RedisInsight (5540) och git-bridge (8000) publiceras bara på värdens `127.0.0.1`.

### TeX Live {#tex-live}

Sandlådekompileringar är på som standard: `develop/dev.env` sätter `SANDBOXED_COMPILES=true` och avbildningarna `ghcr.io/ayaka-notes/texlive-full:2026.1` och `ghcr.io/ayaka-notes/texlive-full:2025.1`. clsi hämtar inte avbildningar själv, så hämta dem en gång:

```bash
docker pull ghcr.io/ayaka-notes/texlive-full:2026.1
docker pull ghcr.io/ayaka-notes/texlive-full:2025.1
```

Se [Konfigurera kompilering i sandlåda](/sv/dev/environment/setup-sandbox-compiles) för detaljer.

<Warning>

Ett projekt som skapades medan `SANDBOXED_COMPILES` var avstängt har ingen TeX Live-avbildning. Det kompileras fortfarande med standardavbildningen, men att hoppa mellan koden och PDF:en misslyckas med ”That didn't work. Recompile and try again.” Ge sådana projekt avbildningen från `TEX_LIVE_DOCKER_IMAGE` en gång; utan `--commit` visar skriptet bara vad det skulle ändra:

```bash
bin/docker-compose exec web sh -c 'cd /overleaf/services/web && node scripts/backfill_project_image_name.mjs --commit'
```

</Warning>

`dev.env` slår även på Pandoc-konverteringar med `PANDOC_IMAGE=overleaf-pandoc:local`. Bygg den avbildningen en gång, från repots rot:

```bash
docker build -t overleaf-pandoc:local develop/pandoc
```

För att kompilera på en macOS-värd kan du behöva åsidosätta sökvägen till Docker-socketen genom att skapa en `.env`-fil i katalogen `develop` som innehåller `DOCKER_SOCKET_PATH=/var/run/docker.sock.raw`

### Utveckling {#development}

För att slippa köra `bin/build && bin/up` efter varje kodändring kan du köra Overleaf Community Edition i _utvecklingsläge_, där tjänsterna uppdateras automatiskt vid kodändringar.

Använd det medföljande skriptet `bin/dev` för detta:

```text
bin/dev
```

Detta startar alla tjänster med `node --watch`, som automatiskt övervakar koden och startar om tjänsterna vid behov. Kör det igen efter att du har ändrat `dev.rc`.

För bättre prestanda kan du starta endast en delmängd av tjänsterna i utvecklingsläge genom att ange en blankstegsseparerad lista till skriptet `bin/dev`:

```text
bin/dev [service1] [service2] ... [serviceN]
```

<Info>

Om tjänsten `web` startas i _utvecklingsläge_ uppdateras tjänsten `web` endast när backendkoden ändras. För att även frontendkoden ska uppdateras automatiskt ser du till att också starta tjänsten `webpack` i _utvecklingsläge_.

</Info>

Om inga tjänster anges startar alla tjänster i utvecklingsläge.

Kör `bin/i18n` efter att du har lagt till en översättning eller bytt gren, se [Uppdatera i18n-översättningar](/sv/dev/environment/update-i18n-translations).

### Felsökning {#debugging}

I _utvecklingsläge_ exponerar de flesta tjänster en felsökningsport som du kan koppla en debugger till, till exempel inspektören i Chromes Dev Tools eller en som är integrerad i en IDE. Följande tabell visar porten som exponeras på `127.0.0.1` på **värddatorn** för varje tjänst:

| Tjänst            | Port |
| ------------------ | ---- |
| `web`                   | 9229 |
| `clsi`                  | 9230 |
| `chat`                  | 9231 |
| `docstore`              | 9233 |
| `document-updater`      | 9234 |
| `filestore`             | 9235 |
| `notifications`         | 9236 |
| `real-time`             | 9237 |
| `history-v1`            | 9239 |
| `project-history`       | 9240 |
| `linked-url-proxy`      | 9241 |
| `third-party-datastore` | 9242 |

För att ansluta till en tjänst med Chromes _fjärrfelsökning_ går du till chrome://inspect/ och ser till att _Discover network targets_ är markerat. Klicka sedan på _Configure..._ och lägg till en post `localhost:[service port]` för var och en av de tjänster du vill ansluta en debugger till.

När du har lagt till en post visas tjänsten som ett _Remote Target_ som du kan inspektera och felsöka.

### Loggning {#logging}

Skriptet `bin/logs` följer loggarna och formaterar dem med `bunyan`. Det behöver även `ggrep`, vilket är namnet på GNU grep när det installeras med Homebrew på macOS; Ubuntu har inget `ggrep`-kommando.

```bash
sudo npm install -g bunyan
# Or sudo apt install node-bunyan 
```

Alternativt kan du köra direkt med:

```text
bin/docker-compose logs -f [service name]
```

Använd `bin/docker-compose` i stället för `docker compose`, så att även tjänsterna för funktionerna i `dev.rc` (`mailpit`, `rustfs`, `ldap`, `saml`, `hoppscotch` och `grafana` med Prometheus, Loki och exportörerna) hittas.

Med `GRAFANA_ENABLED=true` finns loggarna från varje container också i Grafana, där de kan filtreras efter tjänst, nivå och text, se [Konfigurera utvecklingsverktyg](/sv/dev/environment/setup-develop-tools#grafana).
