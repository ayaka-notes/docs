### 初期化が invalid command code で失敗する {#initialization-fails-with-invalid-command-code}

`bin/init` は macOS の BSD sed を検出すると `sed: ... invalid command code` と報告します。[1. Toolkit をダウンロードする](/ja/on-premises/installation/using-docker-compose/macos/1.-download-the-toolkit)のとおりに GNU sed を `PATH` に追加し、`sed --version` を確認してください。

初期化に失敗すると、`config/` に 3 つのファイルがすべて作成されたまま `OVERLEAF_INVITE_TOKEN_SECRET` が空になることがあります。その後 `bin/init` を再度実行すると `Config files already exist` と表示されます。一度も起動していない新規インストールの場合は、3 つのファイルをバックアップ用のディレクトリに移動してから `bin/init` を再度実行してください。既存のインスタンスの場合は、その設定とシークレットを保持し、`bin/init` を再実行するためにファイルを削除しないでください。

### MongoDB が再起動を繰り返す {#mongodb-keeps-restarting}

MongoDB のログと Docker VM のカーネルバージョンを確認します:

```bash
bin/docker-compose logs --tail=100 mongo
docker info --format '{{.KernelVersion}}'
```

ログに Linux カーネルの非互換性が示されている場合は、[Docker VM の Linux カーネルを確認する](/ja/on-premises/installation/using-docker-compose/macos/5.-personalizing-your-instance#check-the-docker-vms-linux-kernel)に従い、`bin/up -d` を再度実行してください。終了コード `137` だけでは MongoDB のメモリ不足の証明にはなりません。コンテナの状態とログを確認してください。Docker Desktop での以前の MongoDB の問題については、[トラブルシューティング](/ja/on-premises/support/troubleshooting)も参照してください。

### Docker デーモンに接続できない {#cannot-connect-to-the-docker-daemon}

Docker Desktop を起動し、選択されている Docker コンテキストを確認してください。[0. Docker Desktop のセットアップ](/ja/on-premises/installation/using-docker-compose/macos/0.-setup-docker-desktop)を参照してください。`docker info` は動作するのにコンパイルから Docker にアクセスできない場合は、`config/overleaf.rc` のソケット設定を確認し、`clsi` のログを読んでください。Mac 上で Docker CLI が動作していても、アプリケーションのソケットマウントが正しいことの証明にはなりません。

### ページは開くがコンパイルに失敗する {#the-page-opens-but-compiles-fail}

TeX Live イメージがローカルに存在し、Docker エンジンのアーキテクチャと一致していることを確認します:

```bash
docker image inspect ghcr.io/ayaka-notes/texlive-full:2026.1 \
  --format '{{.Os}}/{{.Architecture}}'
bin/logs -f clsi
```

Apple シリコンでは、イメージは `linux/arm64` である必要があります。`SERVER_PRO` と `SIBLING_CONTAINERS_ENABLED` の両方が `true` であることを確認してから、`bin/up -d` で変更を適用してください。ログにコンパイルディレクトリが見つからないと表示される場合は、Docker Desktop のファイル共有と `OVERLEAF_DATA_PATH` の場所を確認してください。マウントの失敗を隠すためにサンドボックスコンパイルを無効にしないでください。

### Not a directory、またはバインドマウントがない {#not-a-directory-or-a-bind-mount-is-missing}

オーバーライドでマウントしているホスト上のファイルが削除されたか、ファイルがあるべき場所に Docker がディレクトリを作成した可能性があります。ホスト上のソースパスと、マウントがファイルとディレクトリのどちらを想定しているかを確認してください。コンテナを再作成する前に設定ファイルを復元してください。`/tmp` 以下のインストールでは、macOS が一時ファイルを削除した後にこの問題が発生することがあります。

### ポートまたはコンテナ名の競合 {#port-or-container-name-conflicts}

ポート `8080` が使用中の場合は、`config/overleaf.rc` で別のポートを選び、それに合わせて `OVERLEAF_SITE_URL` を設定してから、`bin/up -d` を再度実行してください。

Toolkit はコンテナに `sharelatex`、`mongo`、`redis` などの固定名を付けます。`PROJECT_NAME` を変更するだけでは、2 つの Toolkit インストールは独立しません。2 つ目のインスタンスを起動する前に `docker ps -a` を確認し、Compose のオーバーライドで別のコンテナ名、別のポート、個別のデータディレクトリを使用してください。名前の競合を解決するために、既存のデプロイのコンテナやデータを削除しないでください。

### しばらくするとインスタンスにアクセスできなくなる {#the-instance-is-unreachable-after-a-while}

Mac がスリープしたか、Docker Desktop が終了した可能性があります。[インスタンスを利用可能な状態に保つ](/ja/on-premises/installation/using-docker-compose/macos/6.-post-installation-tasks#keep-the-instance-available)を参照してください。

### `bin/doctor` が Linux ではないと表示する、または Quay へのログインを求める {#bin/doctor-says-this-is-not-linux-or-asks-for-a-quay-login}

どちらの警告も、公開イメージを使用する macOS では想定どおりです。[2. Toolkit に慣れる](/ja/on-premises/installation/using-docker-compose/macos/2.-familiarize-yourself-with-the-toolkit)を参照してください。代わりにイメージのプル、サービスのステータス、コンパイル結果を確認し、レポート内のその他のエラーは無視しないでください。
