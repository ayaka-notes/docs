### 管理者と最初のプロジェクトを作成する {#create-the-administrator-and-a-first-project}

**Windows のブラウザー**で [http://localhost:8080/launchpad](http://localhost:8080/launchpad) を開き、最初の管理者アカウントを作成してログインします。その後、Linux ガイドの [6. インストール後のタスク](/ja/on-premises/installation/using-docker-compose/linux/6.-post-installation-tasks)に従ってください。その際、例の URL ではポート `8080` を使用してください。

### コンパイルを確認する {#verify-compilation}

ログインページが動作しても、個別のコンパイラーコンテナが WSL のデータディレクトリにアクセスできることの証明にはなりません。空のプロジェクトを作成し、次の `main.tex` を **pdfLaTeX** でコンパイルしてください:

```latex
\documentclass{article}
\begin{document}
Ayakaleaf Pro on Windows WSL 2.
\end{document}
```

PDF プレビューにテキストが表示されるはずです。basic イメージの場合は、必要に応じてプロジェクト設定で **TeX Live 2026 Basic** を選択してください。

**XeLaTeX** を選択して、次の内容でテストします:

```latex
\documentclass{article}
\usepackage{fontspec}
\begin{document}
Ayakaleaf WSL XeLaTeX sandbox.
\end{document}
```

どちらの例も basic で動作します。中国語のドキュメントの場合は、次の内容を **XeLaTeX** でテストする前に、full など `ctex` と必要なフォントを含むイメージを使用してください。basic にはこれらが含まれていません:

```latex
\documentclass{ctexart}
\begin{document}
你好，Ayakaleaf Pro。
\end{document}
```

サンドボックスが使用されていることを確認するには、コンパイル中に **Ubuntu** で次を実行します:

```bash
docker ps -a --filter ancestor=ghcr.io/ayaka-notes/texlive-basic:2026.1
bin/logs -f clsi
```

フィルターには選択したイメージ名を使用してください。短いコンパイルは `docker ps` の実行前に終了することがあります。`-a` を付けると、クリーンアップされるまでは停止したコンテナも表示されます。コンパイラーコンテナは、そのイメージと、Toolkit の WSL データディレクトリからの `/compile` バインドマウントを使用しているはずです。アプリケーションのログだけでは、PDF の確認の代わりにはなりません。

### 永続化を確認する {#verify-persistence}

**Ubuntu** で、Toolkit のディレクトリから次を実行します:

```bash
bin/stop
bin/start
```

アプリケーションの起動を待ち、Windows からプロジェクトを再度開いて、もう一度コンパイルしてください。アカウント、ソース、プロジェクトファイルが残っているはずです。デフォルトでは、稼働中のデータは Ubuntu 内の `~/ayakaleaf-toolkit/data/` にあります。`config/` と `data/` の両方を保持してください。Ubuntu ディストリビューションをアンインストールまたは登録解除すると、これらが削除される可能性があります。

### インスタンスを利用可能な状態に保つ {#keep-the-instance-available}

インスタンスを稼働させ続けるには、3 つの要素があります。Windows がスリープしないこと、Docker Desktop が実行されていること、そしてコンテナがエンジンとともに再起動することです。

Docker Desktop の **Settings → General** で **Start Docker Desktop when you sign in to your computer** をオンにしてください。[Docker Desktop の設定](https://docs.docker.com/desktop/settings-and-maintenance/settings/)を参照してください。これにより Docker はログイン後に起動しますが、ログイン前には起動しません。Windows を再起動した後は、サインインして Docker Desktop の起動が完了するまで待ち、Ubuntu を開いて `docker ps` とサイトを確認してください。

Docker Desktop の **Resource Saver** は Windows のスリープとは別のものです。通常はコンテナが 1 つも実行されていないときにのみ有効になり、実行中のアプリケーション、MongoDB、Redis がそのアイドル状態を防ぎます。WSL 2 では、共有の WSL VM をシャットダウンするのではなく、Docker エンジンを一時停止します。ユーザーにサービスを提供している間は、Docker Desktop を手動で **Pause** しないでください。このスタックを稼働させ続けるためだけに Resource Saver を無効にする必要はありません。[Docker の Resource Saver のドキュメント](https://docs.docker.com/desktop/use-desktop/resource-saver/)を参照してください。

Toolkit のサービスは `restart: always` を使用しています。**Ubuntu** で実際の設定を確認してください:

```bash
docker inspect sharelatex mongo redis --format '{{.Name}} restart={{.HostConfig.RestartPolicy.Name}}'
```

各サービスで `always` と表示されるはずです。Docker が実行されると、新たに `bin/up` を実行しなくても、既存のコンテナを再起動できます。手動で停止したコンテナは、起動するかエンジンを再起動するまで停止したままです。`always` の場合、エンジンを再起動するとコンテナが再び起動することがあります。[Docker の再起動ポリシーの動作](https://docs.docker.com/engine/containers/start-containers-automatically/)を参照してください。

| 操作 | Ayakaleaf への影響 |
| --- | --- |
| `bin/up -d` の後に Ubuntu のターミナルを閉じる | コンテナはデタッチされて実行されており、ターミナルはその管理元ではありません。Docker Desktop と WSL 環境を利用可能な状態に保ってください |
| Docker Dashboard のウィンドウを閉じる | ウィンドウを閉じても、Docker Desktop はシステムトレイで動作し続けます |
| **Quit Docker Desktop** を選択する | エンジンが停止し、サイトが利用できなくなります。復旧するには Docker Desktop を再度開いてください |
| `wsl --shutdown` を実行する | すべての WSL ディストリビューションが停止し、Docker の WSL バックエンドが中断されます。Docker Desktop を再起動し、Ubuntu を開き直してください |
| Windows をスリープ、休止状態、またはシャットダウンにする | サービスが利用できなくなります。画面をオンまたはオフにしておくだけでは、これは変わりません |
| `bin/stop` を実行する | データを保持したままインスタンスを停止します。再開するには `bin/start` を使用してください |

AC 電源で長時間使用する場合は、Windows 11 の **Settings → System → Power & battery → Screen, sleep & hibernate timeouts**（バージョンによっては **Power** または **Screen and sleep**）を開きます。電源接続時のスリープのタイムアウトを **Never** に設定し、自動休止状態が設定されている場合は無効にしてください。ディスプレイはオフになってもかまいません。ノート PC の蓋を閉じたときの動作は別の設定であり、アイドル時のスリープのタイムアウトが Never でも、蓋を閉じるとスリープすることがあります。[Windows の電源設定](https://support.microsoft.com/en-us/windows/experience/power-battery/power-settings-in-windows-11)を参照してください。

サイトの使用中に、日常的なクリーンアップとして `wsl --shutdown` を実行しないでください。WSL の設定変更でこれが必要な場合は、先にインスタンスを停止し、中断を計画してください。これらの設定により、Windows でインスタンスを継続的に実行できます。ログアウトや無人での再起動後も稼働し続ける必要がある共有サービスには、[Linux ガイド](/ja/on-premises/installation/using-docker-compose/linux)をおすすめします。

### Docker Desktop の再起動後の復旧を確認する {#check-recovery-after-restarting-docker-desktop}

作業を保存し、実行中のコンパイルが完了するのを待ってから、Docker Desktop のトラブルシューティングメニューで **Restart Docker Desktop** を選択します。エンジンの起動を待ってから、**Ubuntu** で次を確認します:

```bash
docker ps
curl -I http://localhost:8080/launchpad
```

Windows で既存のプロジェクトを開き、もう一度コンパイルします。アカウントとソースが残っていることを確認してください。

`bin/stop` で意図的にインスタンスを停止した場合は、`bin/start` を使用してください。Docker は起動しているのにサービスが失敗する場合は、設定を作り直すのではなく、そのログを読んでください。Windows Update、Docker のアップデート、停電によって 24 時間稼働のインストールが中断されることもあります。バックアップを保持し、計画的なメンテナンスの後には復旧を確認してください。

### 日常的な使用 {#daily-use}

Windows で Docker Desktop を起動します。**Ubuntu** を開きます:

```bash
cd "$HOME/ayakaleaf-toolkit"
```

| タスク | コマンド |
| --- | --- |
| 既存のコンテナを起動する | `bin/start` |
| データを保持したままコンテナを停止する | `bin/stop` |
| 設定の変更を適用する | `bin/up -d` |
| ステータスを確認する | `bin/docker-compose ps` |
| 起動ログを読む | `bin/docker-compose logs --tail=100 sharelatex` |
| MongoDB のログを読む | `bin/docker-compose logs --tail=100 mongo` |
| コンパイラーのログを読む | `bin/logs -f clsi` |

`bin/start` は設定の編集を適用しません。`config/` を変更した後は `bin/up -d` を使用してください。WSL ディストリビューションのアップグレード、移動、削除の前には、[データとバックアップ](/ja/on-premises/maintenance/data-and-backups)に従ってください。データベースが書き込んでいる最中に稼働中の MongoDB ファイルをコピーしても、一貫性のあるバックアップにはなりません。

ローカルで使用する場合は `127.0.0.1` のままにしてください。他のコンピューターに提供するには、待ち受けアドレス、サイト URL、Windows のファイアウォールとネットワークの設定、HTTPS を意図的に設定する必要もあります。`OVERLEAF_SITE_URL` を変更するだけでは、ポートは公開されません。

うまく動作しない場合は、[トラブルシューティング](/ja/on-premises/installation/using-docker-compose/windows/troubleshooting)を参照してください。
