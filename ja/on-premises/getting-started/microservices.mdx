Overleaf Server CE および Overleaf Pro のインスタンスをデプロイ・管理するには、Toolkit を使用する方法をおすすめします。

Toolkit は、必要なマイクロサービスのオーケストレーションを抽象化するカスタムスクリプトによって、Overleaf インスタンスの作成を簡素化します。同梱の初期化スクリプトを実行し、永続ストレージのパスなどいくつかの設定オプションを指定するだけで、Toolkit が Overleaf Server CE または Pro インスタンスを構成するマイクロサービスのプロビジョニングと接続を行います。

これにより、ユーザーエクスペリエンスのカスタマイズや、オンプレミスインスタンスに必要な特定の機能の実装に集中できます。Toolkit は内部の複雑な処理をすべて引き受け、Overleaf インスタンスのデプロイを簡素化します。

<Info>

歴史的な理由により、メインの Overleaf コンテナは `sharelatex` という名前で、`sharelatex/sharelatex` Docker イメージをベースにしています。これは、この技術が Overleaf に統合された ShareLaTeX のコードベースに基づいているためです。詳細については[このブログ記事](https://www.overleaf.com/blog/518-exciting-news-sharelatex-is-joining-overleaf)を参照してください。将来的には、Overleaf の命名規則に合わせて名前が変更される予定です。

</Info>

#### アーキテクチャ

Overleaf コンテナ内では、ソフトウェアは `runit` によって管理される一連のマイクロサービスとして動作します。コンテナ内の主なファイルは次のとおりです。

* `/etc/service/`: マイクロサービスの初期化ファイル。
* `/var/log/overleaf/`: 各マイクロサービスのログ。
* `/overleaf/services/`: 各種マイクロサービスのコード。
* `/var/lib/overleaf/`: 永続データのマウントポイント（ホスト上の `OVERLEAF_DATA_PATH` で指定されたディレクトリに対応）。

#### MongoDB と Redis のコンテナ

Overleaf は MongoDB と Redis という 2 つの外部データベースに依存しています。デフォルトでは、Toolkit は Overleaf コンテナに加えてこれらのデータベースごとにコンテナをプロビジョニングするため、Docker コンテナは合計 3 つになります。

<Info>

既存の MongoDB または Redis インスタンスに接続したい場合は、[overleaf.rc](/ja/on-premises/configuration/overleaf-toolkit/files-and-locations#the-overleaf.rc-file) 設定ファイルで適切な設定を行ってください。

</Info>

#### エディターとコンパイルプロセス

このセクションでは、ドキュメントの処理とコンパイルプロセスの概要を説明します。

<Info>

このページでは、Overleaf Pro でのみ利用可能な Sandboxed Compiles を使用したコンパイルプロセスについて説明します。Server CE では、コンパイルプロセスは単純なサブプロセスを使用します。**コンテナ**に関する項目は、**サブプロセスでコンパイルを実行する**という 1 つの項目に置き換えて読んでください。

</Info>

コンポーネント / アクター:

* `user` — アプリケーションのユーザー
* `editor` — ブラウザで動作するクライアントアプリケーション
* `clsi` — PDF のコンパイルに使用されるマイクロサービス
* `document-updater` — ドキュメントの更新処理に使用されるマイクロサービス
* `filestore` — バイナリファイルを扱うマイクロサービス
* `real-time` — WebSocket の処理に使用されるマイクロサービス
* `web` — API リクエストの処理に使用される（それほどマイクロではない）サービス

**Redis によるキャッシュ**

* **user**: エディターページを読み込む
* **editor**: WebSocket を開く
* **editor**: WebSocket 経由でドキュメントを開くリクエストを送信する
  * **real-time** -> **document-updater**: ドキュメントが MongoDB から Redis に読み込まれる
* **editor**: WebSocket 経由でドキュメントの更新を送信する
  * **real-time** -> **document-updater**: Redis 内のドキュメントが更新される
* **editor**: さらにコンパイルリクエストを送信する
  * 前回のフラッシュから 5 分経過後（ドキュメントごと）:
    * **document-updater**: ドキュメントを Redis から MongoDB にフラッシュする
* **editor**: さらに更新を送信する
  * 100 回の更新ごと（ドキュメントごと）:
    * **document-updater**: ドキュメントの履歴を Redis から MongoDB にフラッシュする
* **user**: エディターを離れる / ブラウザのタブを閉じる
  * 5 分後
    * **real-time**: 他の共同編集者がいるかを確認し、いなければ:
      * **real-time** -> **document-updater**: ドキュメントを Redis から MongoDB にフラッシュする

**MongoDB から Redis への読み込み**

* **document-updater** -> **web** -> **docstore**: MongoDB から読み込む

**Redis から MongoDB へのフラッシュ**

* **document-updater** -> **web** -> **docstore**: MongoDB に書き込む

**コンパイル — "full" 同期モード**

* **editor**: 同期モードを "full" に設定してコンパイルリクエストを送信する
* **web** -> **document-updater**: すべてのドキュメントが Redis から MongoDB にフラッシュされる
* **web** -> **docstore**: すべてのドキュメントが MongoDB からダウンロードされる
* **web** -> **clsi**: 次の内容を含むコンパイルリクエストが `clsi` に送信される:
  * 同期モード
  * ファイルツリーのハッシュ -> "プロジェクト状態"
  * すべてのドキュメントとその内容 -> 7MB のリクエストボディ制限の対象
  * 個別にダウンロードするためのバイナリファイルの URL
* **clsi**: 同期モードと "プロジェクト状態" を使ってディスク上の状態を確認する
  * これは完全同期なので、以前のディスク上の状態は無視できる
* **clsi**: コンパイルディレクトリをクリーンアップする
* **clsi**: すべてのドキュメントをコンパイルディレクトリに書き込む
* **clsi**: すべてのバイナリファイルをコンパイルディレクトリに書き込む
  * `clsi` はプロジェクトごとのローカルキャッシュからファイルをコピーする
  * キャッシュミスの場合:
    * **clsi** -> **filestore**: ファイルをダウンロードする
* **clsi**: "プロジェクト状態" を書き込む
* **clsi**: 目的の設定を持つ Docker コンテナが存在することを確認する
  * TeX Live のバージョンを含むコンテナオプションを構築する
  * オプションをハッシュ化する
  * コンテナ名: `project-<project-id>-<user-id>-<hash>`
* **clsi**: コンテナを起動し、stdout/stderr をメモリにストリーミングする -> 上限 2MB
* **clsi**: 停止したコンテナを残しておく -> 24 時間後にクリーンアップされる
* **clsi**: stdout/stderr をディスクに書き込む
* **clsi**: 出力ファイルを一意の出力ディレクトリにコピーする
  * build-id は 8 バイトのランダムなバイト列とミリ秒精度のタイムスタンプで構成される
  * 最新 3 つ（匿名ユーザー）/ 最新 1 つ（ログインユーザー）以外のビルドフォルダーを削除する
* **clsi**: コンパイルが失敗 / タイムアウトした場合
  * コンパイルキャッシュを削除する — 不完全なファイルや破損したキャッシュが含まれている可能性があるため
* **editor**: output.log と output.pdf をダウンロードする

**コンパイル — "incremental" 同期モード**

* **editor**: 同期モードを "incremental" に設定してコンパイルリクエストを送信する
* **web** -> **document-updater**: Redis からドキュメントを取得する
  * "プロジェクト状態" のハッシュも Redis に保存されている
  * **web** はファイルツリーのハッシュを `document-updater` に送信し、不一致の場合 `document-updater` はインクリメンタルコンパイルをフルコンパイルに切り替えることができる
    * エディターが "full" コンパイルを要求した場合のコンパイルプロセスを参照
* **web** -> **clsi**: 次の内容を含むコンパイルリクエストが `clsi` に送信される:
  * 同期モード
  * ファイルツリーのハッシュ -> "プロジェクト状態"
  * Redis 上のすべてのドキュメントとその内容 -> 7MB のリクエストボディ制限の対象
  * バイナリファイルは含まない
* **clsi**: 同期モードと "プロジェクト状態" を使ってディスク上の状態を確認する
  * これはインクリメンタル同期なので、"プロジェクト状態" が一致している必要がある
  * 不一致の場合: 409 を返し、web に "full" 同期で再試行させる
    * エディターが "full" コンパイルを要求した場合のコンパイルプロセスを参照
* **clsi**: 更新されたドキュメントをコンパイルディレクトリに書き込む
* **clsi**: 目的の設定を持つ Docker コンテナが存在することを確認する
  * TeX Live のバージョンを含むコンテナオプションを構築する
  * オプションをハッシュ化する
  * コンテナ名: `project-<project-id>-<user-id>-<hash>`
* **clsi**: コンテナを起動し、stdout/stderr をメモリにストリーミングする -> 上限 2MB
* **clsi**: 停止したコンテナを残しておく -> 24 時間後にクリーンアップされる
* **clsi**: stdout/stderr をディスクに書き込む
* **clsi**: 出力ファイルを一意の出力ディレクトリにコピーする
  * build-id は 8 バイトのランダムなバイト列とミリ秒精度のタイムスタンプで構成される
  * 最新 3 つ（匿名ユーザー）/ 最新 1 つ（ログインユーザー）以外のビルドフォルダーを削除する
* **clsi**: コンパイルが失敗 / タイムアウトした場合
  * コンパイルキャッシュを削除する — 不完全なファイルや破損したキャッシュが含まれている可能性があるため
* **editor**: output.log と output.pdf をダウンロードする

**コンパイル — モードの切り替え**

* **editor**: コンパイルの失敗を検知すると、次のコンパイルは "full" コンパイルになる
* **editor**: コンパイルの成功を検知すると、次のコンパイルは "incremental" コンパイルになる
