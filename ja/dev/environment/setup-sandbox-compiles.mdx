開発環境の Sandbox Compiles は、本番イメージとは少し異なる動作をします。開発環境ではすでに設定済みです。このページでは、その設定と注意すべき 3 つの点を説明します。

* ファイル権限の問題
* history-v1 と filestore 間のボリューム共有
* サブディレクトリの問題

### Sandbox Compiles を有効にする {#enable-sandbox-compiles}

Sandbox Compiles はデフォルトで有効です。`develop/docker-compose.yml` が `clsi` に `SANDBOXED_COMPILES=true` を設定し、残りは `develop/dev.env` にあります。

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

clsi は自分でイメージを pull しないため、`docker pull ghcr.io/ayaka-notes/texlive-full:2026.1`（および `:2025.1`）でイメージを一度 pull してください。

LaTeX は兄弟コンテナ内で `TEXLIVE_IMAGE_USER` として実行されます。開発環境ではこれは `tex` で、clsi のデフォルトでもあります（`services/clsi/config/settings.defaults.cjs:154`）。本番イメージでは、`SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` のときに代わりに `www-data` を使います（`server-ce/config/env.sh:15-21`）。本番ではファイルが Overleaf コンテナの `www-data` ユーザーによって作成されるためです。

<Warning>

自分でビルドしたイメージは使用しないでください。一連のエラーが発生する可能性があります。

</Warning>

### ファイル権限を修正する {#fix-file-permissions}

clsi コンテナは root として起動し、`compiles`、`output`、`cache` フォルダーを `node` ユーザー（uid `1000`）に渡してから、clsi を `node` として実行します（`services/clsi/entrypoint.sh`）。そのため、ホスト上の `develop/compiles` は uid `1000` の所有となり、開発環境の `tex` と同じ uid です（`develop/pandoc/Dockerfile` のコメントを参照）。上記の設定なら、開発環境は権限を変更しなくてもコンパイルできます。

代わりに `TEXLIVE_IMAGE_USER=root` を設定した場合、root（uid `0`）には `compiles` のサブフォルダーへの書き込み権限がありません。その場合は、`compiles` の所有グループを `root` にして書き込み権限を与え、新しいサブフォルダーがこの所有権を継承するように `setgid` を設定します。

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

詳細なドキュメントは `services/clsi/README.md` を参照してください。

### history-v1 と filestore 間のボリューム共有 {#volume-share-between-history-v1-and-filestore}

<Info>

このセクションと次のセクションの設定は、すでに `develop/docker-compose.yml` と `develop/dev.env` に含まれています。これらが関係するのは `develop/dev.rc` で `S3_ENABLED=false` の場合だけです。デフォルトの `S3_ENABLED=true` では、filestore と history-v1 はこれらのファイルを代わりに RustFS のバケットに保存します（`develop/s3/docker-compose.yml`）。

</Info>

デフォルトでは、filestore は S3 と Overleaf の他のサービスとの橋渡し役を担います。しかし Overleaf CE や Server Pro では、デフォルトですべてのファイルがローカルに保存されます。そのため、Overleaf は非常にトリッキーな方法を導入しています。

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

同時に、`data/history` は履歴サービスでも使われます。こうして異なるマイクロサービス間で同じデータを共有できます。そのため、develop の filestore サービスは history-v1 の `history-v1-buckets` ボリュームをマウントしています。これがないと、**clsi は filestore サービスから blob ファイルを取得できません**。

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

filestore は `dev.env` の次の設定でバケットを見つけます。

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### サブディレクトリを使用する {#use-subdirectories}

filestore は履歴の blob を常にサブディレクトリ付きで読み込みます（`services/filestore/app/js/KeyBuilder.js:58`、`:70`）。本番イメージは history-v1 の `useSubdirectories` を有効にしますが（`server-ce/config/production.json`）、history-v1 のデフォルト設定では有効にならないため、開発環境では history-v1 が<strong>すべてのデータをフラットにしてしまいます。</strong>そのため `dev.env` は history-v1 に `NODE_CONFIG` を設定しています。&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

これがないと、history-v1 は `project_blobs` のファイルを次のように保存します。

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

`useSubdirectories` を `true` にすると、これらの名前の `_` が `/` になり、各 blob がサブフォルダーに保存されます。
