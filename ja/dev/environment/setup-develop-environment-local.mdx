## 前提条件 {#prerequisites}

Overleaf はマイクロサービスアーキテクチャを採用した典型的なオープンソースプロジェクトで、すべてのサービスが Docker 上で動作します。

* 公式の Community Edition のソースコードは [GitHub Overleaf Official](https://github.com/overleaf/overleaf/tree) にあります。
* Overleaf-CEP のソースコードは [GitHub Yu-i-i/Overleaf](https://github.com/yu-i-i/overleaf-cep) で公開されています。
* Ayakaleaf Pro は [GitHub ayaka-notes/ayakaleaf-pro](https://github.com/ayaka-notes/ayakaleaf-pro) で公開されています。

Overleaf の開発環境を構築するには、高性能なサーバーが必要です。20 個以上のコンテナを同時に実行する必要があるため、少なくとも 8 コア・16GB RAM の構成を推奨します。

<Info>

8 コア以上の CPU を備えたサーバーは一般に高価なため、開発にはローカルのコンピューターを使用することを強くおすすめします。

</Info>

また、開発者であるあなたは [Docker のインストール](https://docs.docker.com/engine/install/ubuntu/) についてすでに理解しているものと想定します。予期しないエラーに遭遇する可能性を減らすため、開発には最新かつ安定した Ubuntu LTS（例：2025〜2026 年時点では Ubuntu 24.04）と最新の Docker を使用することを強く推奨します。

まとめると、次のものが必要です。

* [x] 開発用の高性能なサーバー／デスクトップ
* [x] 最新かつ安定した Ubuntu LTS（例：Ubuntu 24.04）
* [x] Docker と Git の環境

## 設定チュートリアル {#configuration-tutorial}

ここでは Ayakaleaf Pro を例に、Overleaf の開発環境をセットアップする方法を説明します。特に断りがない限り、以下のコマンドはすべて `develop` ディレクトリで実行します。

<Steps>
<Step title="ソースコードを取得する">
まず、リポジトリをクローンします。

```bash title="bash"
git clone https://github.com/ayaka-notes/ayakaleaf-pro.git
cd ayakaleaf-pro/develop
```
</Step>

<Step title="`yarn.lock` を同期する">
このリポジトリは Yarn 4 を使用しており（ルートの `package.json` の `packageManager`）、`yarn.lock` が `package.json` ファイルと同期していないことがあります。初回のクローン後と、`package.json` を変更した後に同期してください。

```bash title="bash"
bin/sync
```

`bin/sync` は `node:24.18.1` コンテナ内で `yarn install --mode=update-lockfile` を実行するため、ホストに Node.js は不要です。変更された `yarn.lock` はコミットしないでください。
</Step>

<Step title="開発用イメージをビルドする">
サービスをビルドします。

```bash title="bash"
bin/build
```

<Info>

サービスを並列でビルドしている間に Docker のメモリが不足する場合は、このディレクトリに `COMPOSE_PARALLEL_LIMIT=1` を含む `.env` ファイルを作成してください。

</Info>
</Step>

<Step title="翻訳を適用する">
Ayakaleaf Pro のモジュールは翻訳を `services/web/locales/locales_patches/` に保持しており、コミット済みのロケールファイルには含まれていません。初回起動前に一度適用してください。適用しないと、これらのモジュールのページにはテキストの代わりに `about_to_permanently_delete_accounts` のようなキーが表示されます。

```bash title="bash"
bin/i18n
```

ホストに `jq` が必要です。翻訳を追加したりブランチを切り替えたりした後は再度実行してください。[i18n 翻訳の更新](/ja/dev/environment/update-i18n-translations)を参照してください。
</Step>

<Step title="すべてのマイクロサービスを起動する">
次にサービスを起動します。

```bash title="bash"
bin/up
```

サービスが起動したら、[http://localhost/launchpad](http://localhost/launchpad) を開いて最初の管理者アカウントを作成します。 `OVERLEAF_PORT` を変更した場合はポートを追加してください（後述）。

<Info>

LDAP はデフォルトで有効です（`dev.rc` の `LDAP_ENABLED=true`）。この場合、Launchpad には LDAP 管理者フォームが表示されます。メールアドレスだけを入力し、その管理者はその後 LDAP でログインします。たとえば `professor` / `professor`（`professor@planetexpress.com`）です。テストユーザーは `develop/authentication/README.md` に記載されています。代わりにパスワード付きのローカル管理者を作成するには、`LDAP_ENABLED=false` と `SAML_ENABLED=false` を設定してください。

</Info>
</Step>
</Steps>

<Info>

`develop/dev.env` ではすでに `ADMIN_PRIVILEGE_AVAILABLE=true` が設定されているため、管理者は追加の設定なしで管理パネルを開けます。

</Info>

### 設定（`dev.rc`） {#configuration-dev-rc}

`dev.env` の隣にある `develop/dev.rc` には、Overleaf Toolkit の `overleaf.rc` のように開発環境のスイッチがまとめられています。値を変更したら `bin/dev` を再実行して反映してください。オフにした機能はそのコンテナも停止します。

| 変数 | デフォルト | 内容 |
| --- | --- | --- |
| `OVERLEAF_PORT` | `80` | サイトのホストポート。 |
| `LDAP_ENABLED` | `true` | テストユーザーによる LDAP ログイン。 |
| `SAML_ENABLED` | `true` | テストユーザーによる SAML ログイン。 |
| `MAILPIT_ENABLED` | `true` | `web` からのすべてのメールを Mailpit で受け取ります。メール確認も有効になります（`EMAIL_CONFIRMATION_DISABLED=false`）。 |
| `S3_ENABLED` | `true` | 履歴ファイルとテンプレートファイルをローカルボリュームではなく RustFS（S3）に保存します。 |
| `HOPPSCOTCH_ENABLED` | `true` | Docker ネットワークへのプロキシ付きの Hoppscotch。[開発ツールのセットアップ](/ja/dev/environment/setup-develop-tools)を参照してください。 |
| `HOPPSCOTCH_PORT` | `9170` | Hoppscotch のホストポート。 |
| `GRAFANA_ENABLED` | `true` | サイトの `/grafana/` で動作し、すべてのサービスの状態、メトリクス、ログを表示する Grafana。[開発ツールのセットアップ](/ja/dev/environment/setup-develop-tools)を参照してください。 |

各機能は `docker-compose.yml` などのファイルを専用のフォルダーに持っています：`authentication/ldap`、`authentication/saml`、`mail`、`s3`、`hoppscotch`、`grafana`。環境変数のない `web` の設定が必要な機能は `/etc/overleaf/settings.d/` にファイルをマウントし、`develop/settings.dev-env.cjs` がそれらをすべてマージします。すべての `bin/*` スクリプトは、有効な機能のファイルを追加する `bin/docker-compose` を経由します。自分で compose コマンドを実行する場合も、`docker compose` ではなく `bin/docker-compose` を使ってください。

<Warning>

ローカルボリュームと RustFS は別々のストアです。`S3_ENABLED=true` で作成したプロジェクトは、`false` に切り替えると履歴とバイナリファイルがなくなり、その逆も同様です。`S3_ENABLED` が存在する前から動いていた環境のファイルを RustFS にコピーするには、[develop/README.md](https://github.com/ayaka-notes/ayakaleaf-pro/blob/server-pro/develop/README.md) の「Moving existing data into RustFS」に従ってください。

</Warning>

### ポート {#ports}

サイト、RustFS コンソール、Hoppscotch はホストの `127.0.0.1` で待ち受けます。リモートマシンでは、まずそれらのポートを転送してください（例：`ssh -L 9001:localhost:9001 <host>`）。サイトは `dev.rc` の `OVERLEAF_PORT` を使うため、変更した場合は以下のアドレスにポートを追加してください。

| ページ | アドレス | ログイン |
| --- | --- | --- |
| サイト | [http://localhost](http://localhost) | サイトのアカウント、またはテストユーザー |
| メール受信箱（Mailpit） | [http://localhost/mailpit/](http://localhost/mailpit/) | なし |
| Grafana | [http://localhost/grafana/](http://localhost/grafana/) | なし（匿名ユーザーが管理者） |
| Mongo Express | [http://localhost/mongo-express/](http://localhost/mongo-express/) | なし |
| RedisInsight | [http://localhost/redis-insight/](http://localhost/redis-insight/) | なし |
| S3 コンソール（RustFS） | [http://localhost:9001/rustfs/console/](http://localhost:9001/rustfs/console/) | `rustfsadmin` / `rustfsadmin` |
| Hoppscotch | [http://localhost:9170](http://localhost:9170) (`HOPPSCOTCH_PORT`) | なし |

Mailpit、Grafana、Mongo Express、RedisInsight は webpack-dev-server を通じてサイトの専用パスで提供されるため、専用のポートは不要です。ログイン後は、サイトのナビゲーションバーにある **Dev tools** メニューからリンクされます。`dev.rc` で機能がオフになっているページは表示されません。各ツールの役割は[開発ツールのセットアップ](/ja/dev/environment/setup-develop-tools)を参照してください。

S3 API（ポート 9000）と SMTP（ポート 1025）には Docker ネットワーク内からしかアクセスできません。Mongo（27017）、Redis（6379）、Mongo Express（8081）、RedisInsight（5540）、git-bridge（8000）はホストの `127.0.0.1` にのみ公開されます。

### TeX Live {#tex-live}

Sandbox Compiles はデフォルトで有効です。`develop/dev.env` が `SANDBOXED_COMPILES=true` と、イメージ `ghcr.io/ayaka-notes/texlive-full:2026.1` および `ghcr.io/ayaka-notes/texlive-full:2025.1` を設定しています。clsi は自分でイメージを pull しないため、一度 pull してください。

```bash
docker pull ghcr.io/ayaka-notes/texlive-full:2026.1
docker pull ghcr.io/ayaka-notes/texlive-full:2025.1
```

詳しくは [Sandbox Compiles のセットアップ](/ja/dev/environment/setup-sandbox-compiles)を参照してください。

<Warning>

`SANDBOXED_COMPILES` がオフのときに作成されたプロジェクトには TeX Live イメージがありません。デフォルトのイメージでコンパイルはできますが、コードと PDF の間のジャンプが「That didn't work. Recompile and try again.」で失敗します。そのようなプロジェクトに一度 `TEX_LIVE_DOCKER_IMAGE` のイメージを設定してください。`--commit` を付けない場合、スクリプトは変更内容を表示するだけです。

```bash
bin/docker-compose exec web sh -c 'cd /overleaf/services/web && node scripts/backfill_project_image_name.mjs --commit'
```

</Warning>

`dev.env` は `PANDOC_IMAGE=overleaf-pandoc:local` で Pandoc 変換も有効にします。リポジトリのルートから、そのイメージを一度ビルドしてください。

```bash
docker build -t overleaf-pandoc:local develop/pandoc
```

macOS ホストでコンパイルするには、`develop` ディレクトリに `DOCKER_SOCKET_PATH=/var/run/docker.sock.raw` を含む `.env` ファイルを作成して、Docker ソケットのパスを上書きする必要がある場合があります。

### 開発 {#development}

コードを変更するたびに `bin/build && bin/up` を実行しなくて済むよう、Overleaf Community Edition を _開発モード_ で実行できます。このモードでは、コードの変更に応じてサービスが自動的に更新されます。

これを行うには、付属の `bin/dev` スクリプトを使用します。

```text
bin/dev
```

これにより、すべてのサービスが `node --watch` で起動され、コードが自動的に監視されて必要に応じてサービスが再起動されます。 `dev.rc` を変更した後は再度実行してください。

パフォーマンスを向上させるため、`bin/dev` スクリプトにスペース区切りのリストを渡して、一部のサービスのみを開発モードで起動することもできます。

```text
bin/dev [service1] [service2] ... [serviceN]
```

<Info>

`web` サービスを _開発モード_ で起動した場合、バックエンドのコードが変更されたときにのみ `web` サービスが更新されます。フロントエンドのコードも自動的に更新されるようにするには、`webpack` サービスも _開発モード_ で起動してください。

</Info>

サービス名を指定しない場合、すべてのサービスが開発モードで起動します。

翻訳を追加したりブランチを切り替えたりした後は、`bin/i18n` を実行してください。[i18n 翻訳の更新](/ja/dev/environment/update-i18n-translations)を参照してください。

### デバッグ {#debugging}

_開発モード_ で実行すると、ほとんどのサービスがデバッグポートを公開します。Chrome の Dev Tools のインスペクターや IDE に統合されたデバッガーをアタッチできます。次の表は、各サービスについて**ホストマシン** の `127.0.0.1` で公開されるポートです。

| サービス            | ポート |
| ------------------ | ---- |
| `web`                   | 9229 |
| `clsi`                  | 9230 |
| `chat`                  | 9231 |
| `docstore`              | 9233 |
| `document-updater`      | 9234 |
| `filestore`             | 9235 |
| `notifications`         | 9236 |
| `real-time`             | 9237 |
| `history-v1`            | 9239 |
| `project-history`       | 9240 |
| `linked-url-proxy`      | 9241 |
| `third-party-datastore` | 9242 |

Chrome の _リモートデバッグ_ を使ってサービスにアタッチするには、chrome://inspect/ にアクセスし、_Discover network targets_ にチェックが入っていることを確認します。次に _Configure..._ をクリックし、デバッガーをアタッチしたい各サービスについて `localhost:[service port]` のエントリを追加します。

エントリを追加すると、そのサービスが _Remote Target_ として表示され、検査やデバッグができるようになります。

### ログ {#logging}

スクリプト `bin/logs` はログを追跡し、`bunyan` で整形します。また `ggrep` も必要です。これは macOS で Homebrew からインストールした GNU grep の名前で、Ubuntu には `ggrep` コマンドはありません。

```bash
sudo npm install -g bunyan
# Or sudo apt install node-bunyan 
```

または、次のコマンドで直接実行することもできます。

```text
bin/docker-compose logs -f [service name]
```

`dev.rc` の機能のサービス（`mailpit`、`rustfs`、`ldap`、`saml`、`hoppscotch`、および Prometheus、Loki、エクスポーター付きの `grafana`）も見つかるように、`docker compose` ではなく `bin/docker-compose` を使ってください。

`GRAFANA_ENABLED=true` の場合、すべてのコンテナのログは Grafana にもあり、サービス、レベル、テキストで絞り込めます。[開発ツールのセットアップ](/ja/dev/environment/setup-develop-tools#grafana)を参照してください。
