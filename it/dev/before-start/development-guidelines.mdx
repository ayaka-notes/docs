### Introduzione

Prima di immergerti nello sviluppo, ci auguriamo che tu comprenda i seguenti aspetti:

* Overleaf viene sviluppato ufficialmente in un [repository interno](http://github.com/overleaf/internal), mentre la Community Edition viene pubblicata in [overleaf/overleaf](https://github.com/overleaf/overleaf). Un copybot si occupa di sincronizzare il codice tra il repository interno e quello pubblico.
* [Ayaka-notes/overleaf-pro](https://github.com/ayaka-notes/overleaf-pro) è un fork di Overleaf Community. Desideriamo che questo progetto duri nel tempo, quindi ti chiediamo di seguire queste regole prima di contribuire.

### Regole per i commit

* Non apportare modifiche estese al codice esistente di Overleaf. Concentra il più possibile le funzionalità nella cartella `services/web/modules`. In questo modo ridurremo al minimo il lavoro necessario per unire e aggiornare il codice in futuro.
* Il vibe coding è senza dubbio un approccio molto comodo, ma può facilmente creare disordine nel progetto e renderlo in seguito impossibile da mantenere: usalo con cautela.
* Non aggiungere contenuti relativi alle traduzioni durante lo sviluppo; usa le traduzioni esistenti ogni volta che è possibile.
* Evita di introdurre variabili d'ambiente se non strettamente necessario. Se servono, assicurati che siano il più possibile coerenti con quelle dell'Overleaf toolkit o di [docs.overleaf.com](https://docs.overleaf.com/).

### Regole per i branch

Per lo sviluppo di overleaf-pro usiamo i seguenti branch:

* `main`: questo branch serve solo per sincronizzare il codice upstream; **NON** effettuare commit di modifiche esterne. In questo branch impostiamo alcuni tag come `ce-v[X.x.x]`, che indicano la corrispondenza con la versione `v[X.x.x]` della Community Edition ufficiale di Overleaf. Nota: questi tag sono immutabili!
* `server-pro`: è il branch predefinito per lo sviluppo quotidiano.
* `feature-X`: questo branch serve per sviluppare una funzionalità specifica.
* `release-vX.0.0`: il branch dedicato al rilascio, su cui applichiamo eventuali hot-fix prima del rilascio.

### GitHub Action

[GitHub Action](https://github.com/ayaka-notes/overleaf-pro/actions) si occupa della CI/CD automatica, che comprende:

* Aggiornamento notturno del branch main
* Build dell'immagine Docker per lo sviluppo
* Rilascio dell'immagine Docker

### Domande e risposte

<Accordion title="Come trovo l'hash del commit per Overleaf Community Edition `X.0.0`?">

Innanzitutto devi scaricare l'immagine Docker ed eseguire il seguente comando per ispezionarne le label:

```shellscript title="bash" wrap
docker inspect --format='{{json .Config.Labels}}' sharelatex/sharelatex:6.0.0
{"com.overleaf.ce.revision":"b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f","org.opencontainers.image.ref.name":"ubuntu","org.opencontainers.image.version":"24.04"}
```

Poi puoi verificare se il [commit (b0d05c0)](https://github.com/overleaf/overleaf/commit/b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f) è presente nel branch master upstream.

</Accordion>

<Accordion title="Perché l'hash del commit nell'immagine CE è lo stesso tra `6.0.0` e `6.0.1`?">

È un comportamento previsto. La release 6.0.1 è una patch minore costruita sopra l'immagine 6.0.0. Le modifiche vengono applicate tramite patch all'immagine 6.0.0 esistente, invece di ricostruire l'immagine a partire da un nuovo commit. Per questo motivo l'hash del commit all'interno dell'immagine è identico tra 6.0.0 e 6.0.1.

Per informazioni dettagliate, consulta [hotfix](https://github.com/overleaf/overleaf/tree/main/server-ce/hotfix).

</Accordion>
