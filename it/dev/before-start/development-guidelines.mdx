### Introduzione

Prima di immergerti nello sviluppo, ci auguriamo che tu comprenda i seguenti aspetti:

* Ufficialmente Overleaf viene sviluppato in un [repository interno](http://github.com/overleaf/internal), mentre la community edition è pubblicata in [overleaf/overleaf](https://github.com/overleaf/overleaf). Un copybot si occupa di sincronizzare il codice tra il repository interno e quello pubblico.
* [Ayaka-notes/overleaf-pro](https://github.com/ayaka-notes/ayakaleaf-pro) è un fork della community edition di Overleaf. Speriamo che questo progetto possa durare a lungo, quindi ti chiediamo di seguire le regole prima di contribuire.

### Regole per i commit

* Non apportare modifiche estese al codice Overleaf esistente. Concentra il più possibile le funzionalità nella cartella `services/web/modules`. Questo ridurrà al minimo il nostro carico di lavoro quando in seguito dovremo unire e aggiornare il codice.
* Il vibe coding è davvero un approccio molto comodo, ma può facilmente creare disordine nel progetto, rendendolo in seguito impossibile da mantenere: usalo quindi con cautela.
* Non aggiungere contenuti relativi alle traduzioni durante lo sviluppo; usa le traduzioni esistenti ogni volta che è possibile.
* Evita di introdurre variabili d'ambiente se non strettamente necessario. Se servono, assicurati che siano il più possibile coerenti con quelle dell'Overleaf Toolkit o di [docs.overleaf.com](https://docs.overleaf.com/).

### Regole per i branch

Per lo sviluppo di overleaf-pro usiamo i seguenti branch:

* `main`: questo branch viene usato solo per la sincronizzazione del codice upstream, quindi **NON** eseguire commit di modifiche esterne. In questo branch impostiamo alcuni tag come `ce-v[X.x.x]`, che indicano la corrispondenza con la versione `v[X.x.x]` della Community Edition ufficiale di Overleaf. Nota: questi tag sono immutabili!
* `server-pro`: questo è il branch predefinito per lo sviluppo quotidiano.
* `feature-X`: questo branch viene usato per sviluppare una funzionalità specifica.
* `release-vX.0.0`: il branch dedicato al rilascio, in cui applichiamo eventuali hotfix prima della release.

### GitHub Action

[GitHub Action](https://github.com/ayaka-notes/ayakaleaf-pro/actions) si occupa della CI/CD automatica. Non è necessario compilare le immagini sulla propria macchina: ogni immagine qui sotto viene compilata da un workflow, e quelle con avvio manuale possono essere compilate con un clic.

| Workflow | Avvio | Sorgente | Immagine |
| --- | --- | --- | --- |
| Sync Upstream Code | Giornaliero, manuale | `overleaf/overleaf` → `main` | — |
| Build Development Image | Giornaliero, manuale | `server-pro` | `ghcr.io/ayaka-notes/overleaf-pro/dev:<service>` |
| Build Operations Image | Push / PR su `server-pro`, manuale | Commit inviato o head della PR | `ghcr.io/ayaka-notes/overleaf-pro/ops:<YYYYMMDDHHMM>-<sha>`, `ops:latest` |
| Build Release Image | Manuale | Branch `release-v*` più recente | `ghcr.io/ayaka-notes/overleaf-pro:<version>`, `:latest` e `overleaf-pro/git-bridge` |

* Le **immagini di sviluppo** contengono ciascuna un microservizio (`web`, `webpack`, `clsi`, ...) per `linux/amd64` e `linux/arm64`. La configurazione di Codespace le scarica tramite `develop/docker-compose.image.yml` invece di eseguire `bin/build`.
* Le **immagini operative** sono immagini complete a container singolo (come `sharelatex/sharelatex`) per testare una modifica end to end. `ops:latest` si aggiorna solo con i push su `server-pro`; una PR riceve solo un tag con data e ora. Queste immagini vengono conservate per 7 giorni e servono solo per i test.
* Le **immagini di rilascio** sono quelle che gli utenti distribuiscono. La versione deriva dal nome del branch, quindi `release-v6.3.0` pubblica `overleaf-pro:6.3.0`.

<Steps>
<Step title="Eseguire manualmente un workflow">
Apri la scheda [Actions](https://github.com/ayaka-notes/ayakaleaf-pro/actions), scegli il workflow a sinistra, fai clic su **Run workflow** e conferma. Build Operations Image offre anche l'opzione **Build without cache** per quando un layer in cache è obsoleto.
</Step>

<Step title="Compilare nel proprio fork">
Gli stessi workflow funzionano in un fork: abilita Actions nel tuo fork, quindi eseguili dalla relativa scheda Actions. Le immagini vengono inviate a `ghcr.io/<your-name>/overleaf-pro/...` con il `GITHUB_TOKEN` integrato, quindi non servono secret. Sync Upstream Code e la pulizia delle vecchie immagini vengono eseguiti solo in `ayaka-notes`.

Build Release Image richiede un branch `release-v*` nel tuo fork.
</Step>
</Steps>

<Info>

Per verificare da quale commit è stata compilata un'immagine: il tag di un'immagine operativa termina con l'hash breve del commit, mentre un'immagine di rilascio lo riporta nell'etichetta `com.overleaf.pro.revision` (vedi `docker inspect` nelle domande e risposte qui sotto).

</Info>

### Domande e risposte

<Accordion title="Come trovare l'hash del commit per Overleaf Community Edition `X.0.0`?">

Prima di tutto devi scaricare l'immagine Docker ed eseguire il seguente comando per ispezionarne le etichette:

```shellscript title="bash" wrap
docker inspect --format='{{json .Config.Labels}}' sharelatex/sharelatex:6.0.0
{"com.overleaf.ce.revision":"b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f","org.opencontainers.image.ref.name":"ubuntu","org.opencontainers.image.version":"24.04"}
```

Poi puoi verificare se il [commit (b0d05c0)](https://github.com/overleaf/overleaf/commit/b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f) è presente nel branch master upstream.

</Accordion>

<Accordion title="Perché l'hash del commit è lo stesso nelle immagini CE `6.0.0` e `6.0.1`?">

È un comportamento previsto. La release 6.0.1 è una patch minore costruita sopra l'immagine 6.0.0. Le modifiche vengono applicate applicando patch all'immagine 6.0.0 esistente, anziché ricostruire l'immagine da un nuovo commit. Per questo l'hash del commit all'interno dell'immagine è identico tra 6.0.0 e 6.0.1.

Per informazioni dettagliate, consulta [hotfix](https://github.com/overleaf/overleaf/tree/main/server-ce/hotfix).

</Accordion>
