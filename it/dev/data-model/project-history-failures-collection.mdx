---
title: Collezione Project History Failures
icon: triangle-exclamation
---

`projectHistoryFailures` contiene un documento per ogni progetto i cui aggiornamenti della cronologia project-history non è riuscito a elaborare, o per cui ha avviato una risincronizzazione. Il documento viene eliminato di nuovo non appena l’elaborazione funziona. project-history la scrive in `services/project-history/app/js/ErrorRecorder.js`; il suo tipo è in `services/project-history/app/js/mongo-types.ts:3-24`. Anche web ha uno schema Mongoose per essa (`services/web/app/src/models/ProjectHistoryFailure.mjs:5-19`), ma nessun codice web usa quel modello.

| `queueSize` | Number | Aggiornamenti in attesa nella coda Redis del progetto all’ultimo errore (`services/project-history/app/js/UpdatesProcessor.js:375`); `-1` quando l’errore è nato dall’avvio di una risincronizzazione (`services/project-history/app/js/SyncManager.js:75`, `96`). | `ErrorRecorder.js:36` |
| `ts` | Date | Ora dell’ultimo errore. | `ErrorRecorder.js:39` |
| `attempts` | Number | Numero di errori registrati dalla creazione del documento. | `ErrorRecorder.js:49` |
| `history` | Array of Object | Gli ultimi 10 eventi, dal più recente: record di errore `{ queueSize, error, stack, ts }` e avvii di risincronizzazione `{ resyncStartedAt }`. | `ErrorRecorder.js:50-56`, `92-98` |

#### Chi la scrive {#who-writes-it}

| Codice | Cosa fa |
| ---- | ------------ |
| `services/project-history/app/js/ErrorRecorder.js:34-66` | `record`: upsert dell’errore, `attempts` +1, voce aggiunta a `history`. Chiamato quando l’elaborazione degli aggiornamenti di un progetto fallisce (`UpdatesProcessor.js:91`, `169`, `242`, `293`, `345`) e quando una risincronizzazione non può partire (`SyncManager.js:75`, `96`). |
| `ErrorRecorder.js:86-102` | `recordSyncStart`: upsert, `resyncStartedAt`, `resyncAttempts` +1, voce aggiunta a `history`, a ogni avvio di risincronizzazione (`SyncManager.js:104`). |
| `ErrorRecorder.js:68-70` | `clearError`: elimina il documento dopo un flush riuscito (`UpdatesProcessor.js:101`, `194`, `259`, `355`), su project-history `DELETE /project/:project_id` (`services/project-history/app/js/HttpController.js:1386`) e per un id di progetto non valido durante un nuovo tentativo (`services/project-history/app/js/RetryManager.js:161`). |
| `ErrorRecorder.js:72-82` | `setForceDebug`: upsert di `forceDebug` (`HttpController.js:1016-1035`, route in `services/project-history/app/js/Router.js:82`). |
| `ErrorRecorder.js:109-119` | `cloneFailure`: copia il documento in un altro progetto, per project-history `POST /project/:project_id/clone` (`HttpController.js:135`), che nulla in web chiama. |

#### Chi la legge {#who-reads-it}

| Codice | Cosa fa |
| ---- | ------------ |

Il job soft rielabora la coda; il job hard risincronizza il progetto, con risincronizzazione hard quando `resyncAttempts` è almeno 1 e l’errore non è una risincronizzazione in corso (`RetryManager.js:30-31`, `35-56`, `106-111`). |
| `services/project-history/app/js/FlushManager.js:73-82` | Il flush di tutti i progetti salta quelli che hanno un fallimento. |
| `UpdatesProcessor.js:578-592` | Legge `forceDebug`. |
| `ErrorRecorder.js:124-129`, `140-145` | `getFailureRecord` e `getFailedProjects`: usati da `GET /project/:project_id/debug-info` (`HttpController.js:571`) e `GET /status/failures`, `GET /status/failures-full` (`Router.js:88-90`). |

#### Note {#notes}

* Un documento resta finché un flush del progetto non riesce o il progetto non viene eliminato (`clearError` sopra), quindi ogni documento segnala un progetto il cui ultimo flush o risincronizzazione non è ancora riuscito.
* Le stringhe di errore che iniziano con `OError:` vengono restituite come `Error:` (`ErrorRecorder.js:18-26`); il valore salvato resta invariato.
