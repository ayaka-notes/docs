Se vuoi configurare le compilazioni in sandbox per lo sviluppo, ci sono alcune piccole differenze tra l'ambiente di sviluppo e quello di produzione. Devi prestare attenzione a 3 aspetti:

* Problema dei permessi dei file
* Condivisione del volume tra history-v1 e filestore
* Problema delle sottodirectory

### Abilitare le compilazioni in sandbox

Qui basta abilitare le compilazioni in sandbox come si fa in Overleaf CE. Tuttavia, bisogna fare attenzione all'utente. In questo caso lo impostiamo su root.

In produzione usiamo www-data come utente condiviso tra il container di Overleaf e il container di compilazione TeX. Nell'ambiente di sviluppo, invece, l'utente predefinito nel container è node e non esiste alcun utente www-data a cui agganciarsi. Per questo usiamo root come soluzione alternativa.

<Warning>

Non usare un'immagine compilata da te: potresti incontrare una serie di errori.

</Warning>

```dotenv wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
TEXLIVE_IMAGE_USER=root
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2025.1, ghcr.io/ayaka-notes/texlive-full:2024.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2025, Texlive 2024
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2025.1
```

### Correggere i permessi dei file

LaTeX viene eseguito nei container fratelli con l'utente specificato nella variabile d'ambiente `TEXLIVE_IMAGE_USER`. Nell'esempio sopra è impostato su `root`, che ha uid `0`. Questo crea un problema con i permessi indicati sopra, poiché l'utente root non ha i permessi per scrivere nelle sottocartelle di `compiles`.

Una soluzione rapida è assegnare al gruppo `root` la proprietà e i permessi di lettura e scrittura su `compiles`, impostando `setgid` in modo che anche le nuove sottocartelle ereditino questa proprietà:

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

Per la documentazione dettagliata, consulta `services/clsi/README.md`.

### Condivisione del volume tra history-v1 e filestore

Per impostazione predefinita, filestore funge da ponte tra S3 e gli altri servizi di Overleaf. Tuttavia, in Overleaf CE o Server Pro tutti i file sono memorizzati localmente per impostazione predefinita. Per questo Overleaf ha introdotto un metodo piuttosto ingegnoso.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

Allo stesso tempo, `data/history` è usato anche dal servizio history. In questo modo i diversi microservizi possono condividere gli stessi dati. Devi aggiungere questo volume `history-v1-buckets` al servizio filestore nell'ambiente di sviluppo. Altrimenti **clsi non sarà in grado di recuperare i file blob dal servizio filestore**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

Devi inoltre aggiungere il nome del BUCKET alle impostazioni di `dev.env`:

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### Usare le sottodirectory

Filestore usa useSubdirectories impostato su true per impostazione predefinita; tuttavia, in sviluppo, history v1 **appiattisce tutti i dati.** Questo provoca alcuni conflitti. Per risolverli, devi aggiungere quanto segue:&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

In history v1, tutti i file di `project_blobs` sono originariamente memorizzati così:

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

Devi impostare useSubdirectories su `true` per passare alla modalità a sottodirectory. Ora, il carattere `_` originale nei blob verrà sostituito con `/`.
