Le compilazioni in sandbox funzionano in modo un po' diverso nell'ambiente di sviluppo rispetto all'immagine di produzione. L'ambiente di sviluppo le ha già configurate; questa pagina spiega le impostazioni e tre aspetti da tenere presenti:

* Problema dei permessi dei file
* Condivisione del volume tra history-v1 e filestore
* Problema delle sottodirectory

### Abilitare le Sandbox Compiles {#enable-sandbox-compiles}

Le compilazioni in sandbox sono attive per impostazione predefinita. `develop/docker-compose.yml` imposta `SANDBOXED_COMPILES=true` per `clsi`, e `develop/dev.env` contiene il resto:

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

clsi non scarica le immagini da solo, quindi scaricale una volta con `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1` (e `:2025.1`).

LaTeX viene eseguito nei container fratelli come `TEXLIVE_IMAGE_USER`. Nell'ambiente di sviluppo è `tex`, che è anche il valore predefinito di clsi (`services/clsi/config/settings.defaults.cjs:154`). L'immagine di produzione usa invece `www-data` quando `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` (`server-ce/config/env.sh:15-21`), perché lì i file vengono creati dall'utente `www-data` del container di Overleaf.

<Warning>

Non usare un'immagine costruita da te, altrimenti potresti incorrere in una serie di errori.

</Warning>

### Correggere i permessi dei file {#fix-file-permissions}

Il container di clsi si avvia come root, assegna le cartelle `compiles`, `output` e `cache` all'utente `node` (uid `1000`) e poi esegue clsi come `node` (`services/clsi/entrypoint.sh`). Quindi `develop/compiles` sull'host appartiene all'uid `1000`, lo stesso uid di `tex` nell'ambiente di sviluppo (vedi il commento in `develop/pandoc/Dockerfile`). Con le impostazioni sopra, l'ambiente di sviluppo compila senza alcuna modifica dei permessi.

Se invece imposti `TEXLIVE_IMAGE_USER=root`, root (uid `0`) non ha il permesso di scrivere nelle sottocartelle di `compiles`. In tal caso, assegna al gruppo `root` la proprietà e il permesso di scrittura su `compiles`, con `setgid` impostato in modo che le nuove sottocartelle ereditino questa proprietà:

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

Per la documentazione dettagliata, consulta `services/clsi/README.md`.

### Condivisione del volume tra history-v1 e filestore {#volume-share-between-history-v1-and-filestore}

<Info>

Le impostazioni di questa sezione e della successiva sono già in `develop/docker-compose.yml` e `develop/dev.env`. Contano solo con `S3_ENABLED=false` in `develop/dev.rc`. Con il valore predefinito `S3_ENABLED=true`, filestore e history-v1 conservano invece questi file in bucket RustFS (`develop/s3/docker-compose.yml`).

</Info>

Per impostazione predefinita, filestore funge da ponte tra S3 e gli altri servizi di Overleaf. Tuttavia, in Overleaf CE o Server Pro tutti i file sono memorizzati localmente per impostazione predefinita. Per questo Overleaf ha introdotto un metodo piuttosto ingegnoso.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

Nel frattempo, `data/history` è usato anche dal servizio della cronologia. In questo modo microservizi diversi possono condividere gli stessi dati. Per questo il servizio filestore in develop monta il volume `history-v1-buckets` di history-v1. Senza di esso, **clsi non potrà recuperare i file blob dal servizio filestore**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

filestore trova i bucket tramite queste impostazioni in `dev.env`:

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### Usare le sottodirectory {#use-subdirectories}

filestore legge sempre i blob della cronologia con sottodirectory (`services/filestore/app/js/KeyBuilder.js:58`, `:70`). L'immagine di produzione attiva `useSubdirectories` per history-v1 (`server-ce/config/production.json`), ma la configurazione predefinita di history-v1 no, quindi in sviluppo history-v1 <strong>appiattirebbe tutti i dati.</strong> Per questo `dev.env` imposta `NODE_CONFIG` per history-v1:&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

Senza di essa, history-v1 salva i file di `project_blobs` così:

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

Con `useSubdirectories` impostato a `true`, il `_` in questi nomi diventa `/`, così ogni blob viene salvato in sottocartelle.
