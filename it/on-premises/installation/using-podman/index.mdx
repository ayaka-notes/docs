RHEL e le sue ricompilazioni (Rocky Linux, AlmaLinux) includono Podman invece di Docker, e alcune organizzazioni non consentono Docker sui propri server. Il Toolkit può invece eseguire Ayakaleaf Pro su **Podman rootless**: i container vengono eseguiti con un utente normale, le compilazioni continuano a essere eseguite in container TeX Live isolati e SELinux resta in modalità enforcing. Lo script `bin/podman-setup` controlla l'host e corregge ciò che può.

Alla fine di questa sezione avrai la stessa istanza ottenuta con [Utilizzo di Docker Compose](/it/on-premises/installation/using-docker-compose): Ayakaleaf Pro con Sandboxed Compiles, MongoDB e Redis, gestito con i consueti `bin/up`, `bin/doctor` e `bin/upgrade`.

<Info>

Il supporto per Podman è sperimentale. Proviene dal Toolkit ufficiale di Overleaf, che lo testa solo su RHEL 9 e versioni successive con Podman rootless, Sandboxed Compiles e SELinux in modalità enforcing. Abbiamo testato queste pagine su Rocky Linux 9.9 (Podman 5.8, SELinux enforcing) con Ayakaleaf Pro 6.3.4. Docker resta il runtime per container consigliato.

</Info>

### Cosa ti serve {#what-you-need}

* **RHEL, Rocky Linux, AlmaLinux o CentOS Stream 9 o successivo**, con SELinux in modalità enforcing. `bin/podman-setup` si interrompe su qualsiasi altra distribuzione. Su Ubuntu o Debian, usa [Utilizzo di Docker Compose](/it/on-premises/installation/using-docker-compose/linux).
* **Un utente non root con `sudo`** che sarà proprietario dei container. Esegui ogni comando di questa sezione come questo utente; `bin/podman-setup` si rifiuta di essere eseguito come `root`.
* **Un host pulito**: nessun Docker Engine e nessuna installazione esistente del Toolkit. La migrazione di un'istanza esistente basata su Docker a Podman non è trattata.

### Differenze rispetto a Docker {#how-it-differs-from-docker}

|                                  | Docker                               | Podman rootless                                                                          |
| -------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------- |
| Chi esegue i container           | Il daemon Docker, come `root`        | Il tuo utente                                                                            |
| Socket usato per avviare le compilazioni | `/var/run/docker.sock`       | `/run/user/<uid>/podman/podman.sock`                                                     |
| Porte                            | Qualsiasi, ad esempio `80` e `443`   | `1024` e superiori, ad esempio `8080`                                                    |
| Firewall dell'host (`firewalld`) | Aggirato dalle porte pubblicate      | Si applica: apri la porta con `firewall-cmd`                                             |
| Avvio dopo un riavvio            | Il daemon Docker li riavvia          | Il servizio utente `podman-restart`                                                      |
| SELinux                          | Non configurato dal Toolkit          | Modulo di policy `podman_socket_clsi` e `SELINUX_MODE=managed` in `config/overleaf.rc`    |
| Profilo seccomp per le compilazioni | Integrato nell'immagine           | Estratto in `config/seccomp/<version>/` e impostato come `SECCOMP_PROFILE` dal Toolkit   |

### Limitazioni note {#known-limitations}

* <strong>Integrazione Git.</strong> In Ayakaleaf Pro 6.3.4, `git clone` fallisce con `502` su Podman: l'NGINX all'interno dell'immagine cerca il container `git-bridge` con il server DNS di Docker (`127.0.0.11`), che Podman non ha. La correzione ([1b911d1092](https://github.com/ayaka-notes/ayakaleaf-pro/commit/1b911d1092c80f7b0ff77c5e3805b40503d49964)) arriverà con la prossima release; fino ad allora, lascia `GIT_BRIDGE_ENABLED=false`.
* <strong>Indirizzi IP dei client.</strong> Podman rootless inoltra la porta pubblicata dall'interno della rete del container, quindi Ayakaleaf Pro vede ogni visitatore con un indirizzo interno come `10.89.0.15`. I [log di audit](/it/on-premises/user-guide/administrators/user-management#audit-logs) di un utente nel pannello di amministrazione mostrano questo indirizzo invece del suo indirizzo IP.
