### Creare l'amministratore e un primo progetto {#create-the-administrator-and-a-first-project}

Apri [http://localhost:8080/launchpad](http://localhost:8080/launchpad) nel tuo **browser di Windows**, crea il primo account amministratore ed effettua l'accesso. Poi segui [6. Attività post-installazione](/it/on-premises/installation/using-docker-compose/linux/6.-post-installation-tasks) della guida per Linux, usando la porta `8080` nei suoi URL di esempio.

### Verificare la compilazione {#verify-compilation}

Una pagina di accesso funzionante non dimostra che i container di compilazione separati possano accedere alla directory dei dati di WSL. Crea un progetto vuoto e compila questo `main.tex` con **pdfLaTeX**:

```latex
\documentclass{article}
\begin{document}
Ayakaleaf Pro on Windows WSL 2.
\end{document}
```

L'anteprima PDF dovrebbe mostrare il testo. Per l'immagine basic, seleziona **TeX Live 2026 Basic** nelle impostazioni del progetto, se necessario.

Seleziona **XeLaTeX** e prova:

```latex
\documentclass{article}
\usepackage{fontspec}
\begin{document}
Ayakaleaf WSL XeLaTeX sandbox.
\end{document}
```

Entrambi gli esempi funzionano con la basic. Per i documenti in cinese, usa un'immagine che contenga `ctex` e i font necessari, come la full, prima di provare quanto segue con **XeLaTeX**. La basic non li include:

```latex
\documentclass{ctexart}
\begin{document}
你好，Ayakaleaf Pro。
\end{document}
```

Per confermare l'uso della sandbox, esegui in **Ubuntu** durante la compilazione:

```bash
docker ps -a --filter ancestor=ghcr.io/ayaka-notes/texlive-basic:2026.1
bin/logs -f clsi
```

Usa nel filtro il nome dell'immagine che hai scelto. Le compilazioni brevi potrebbero terminare prima che `docker ps` venga eseguito; `-a` mostra anche i container arrestati fino alla pulizia. Un container di compilazione dovrebbe usare quell'immagine e un bind mount `/compile` dalla directory dei dati WSL del Toolkit. I soli log dell'applicazione non sostituiscono il controllo del PDF.

### Verificare la persistenza {#verify-persistence}

In **Ubuntu**, dalla directory del Toolkit:

```bash
bin/stop
bin/start
```

Attendi l'applicazione, riapri il progetto da Windows e compilalo di nuovo. Il tuo account, il sorgente e i file del progetto dovrebbero essere ancora presenti. I dati in uso predefiniti si trovano in `~/ayakaleaf-toolkit/data/` all'interno di Ubuntu. Conserva sia `config/` sia `data/`; disinstallare o annullare la registrazione della distribuzione Ubuntu può eliminarli.

### Mantenere l'istanza disponibile {#keep-the-instance-available}

Per mantenere l'istanza in esecuzione servono tre condizioni: Windows resta attivo, Docker Desktop è in esecuzione e i container si riavviano insieme al motore.

In **Settings → General** di Docker Desktop, attiva **Start Docker Desktop when you sign in to your computer**; vedi [Docker Desktop settings](https://docs.docker.com/desktop/settings-and-maintenance/settings/). Questo avvia Docker dopo l'accesso, non prima. Dopo un riavvio di Windows, accedi, attendi che Docker Desktop termini l'avvio, apri Ubuntu e controlla `docker ps` e il sito.

Il **Resource Saver** di Docker Desktop è distinto dalla sospensione di Windows. Normalmente si attiva solo quando non ci sono container in esecuzione; l'applicazione, MongoDB e Redis in esecuzione impediscono questa condizione di inattività. Su WSL 2 mette in pausa il motore Docker anziché arrestare la VM WSL condivisa. Non mettere manualmente in **Pause** Docker Desktop mentre servi gli utenti. Non è necessario disattivare Resource Saver solo per mantenere in esecuzione questo stack; vedi la [documentazione di Docker sul Resource Saver](https://docs.docker.com/desktop/use-desktop/resource-saver/).

I servizi del Toolkit usano `restart: always`. Verifica l'impostazione effettiva in **Ubuntu**:

```bash
docker inspect sharelatex mongo redis --format '{{.Name}} restart={{.HostConfig.RestartPolicy.Name}}'
```

Ogni servizio dovrebbe riportare `always`. Una volta che Docker è in esecuzione, può riavviare quei container esistenti senza un nuovo `bin/up`. Un container arrestato manualmente resta arrestato finché non lo avvii o non riavvii il motore; con `always`, un riavvio del motore può avviarlo di nuovo. Vedi il [comportamento dei criteri di riavvio di Docker](https://docs.docker.com/engine/containers/start-containers-automatically/).

| Azione | Effetto su Ayakaleaf |
| --- | --- |
| Chiudere il terminale Ubuntu dopo `bin/up -d` | I container sono eseguiti in modalità detached; il terminale non li supervisiona. Mantieni disponibili Docker Desktop e l'ambiente WSL |
| Chiudere la finestra della Docker Dashboard | La finestra può chiudersi mentre Docker Desktop continua nell'area di notifica |
| Scegliere **Quit Docker Desktop** | Arresta il motore e rende il sito non disponibile; apri di nuovo Docker Desktop per ripristinarlo |
| Eseguire `wsl --shutdown` | Arresta tutte le distribuzioni WSL e interrompe il backend WSL di Docker; riavvia Docker Desktop e riapri Ubuntu |
| Sospendere, ibernare o arrestare Windows | Il servizio non è disponibile; tenere solo lo schermo acceso o spento non cambia nulla |
| Eseguire `bin/stop` | Arresta l'istanza conservandone i dati; usa `bin/start` per riprendere |

Per un uso prolungato con alimentazione da rete, apri in Windows 11 **Settings → System → Power & battery → Screen, sleep & hibernate timeouts** (alcune versioni mostrano **Power** o **Screen and sleep**). Imposta il timeout di sospensione con alimentazione collegata su **Never** e disattiva l'ibernazione automatica, se configurata. Lo schermo può comunque spegnersi. L'azione alla chiusura del coperchio di un portatile è un'impostazione separata; chiudere il coperchio può mettere il portatile in sospensione anche con un timeout di inattività impostato su Never. Vedi le [impostazioni di alimentazione di Windows](https://support.microsoft.com/en-us/windows/experience/power-battery/power-settings-in-windows-11).

Non eseguire `wsl --shutdown` come pulizia di routine mentre il sito è in uso. Se una modifica alle impostazioni di WSL lo richiede, arresta prima l'istanza e pianifica un'interruzione. Con queste impostazioni Windows può eseguire l'istanza in modo continuo. Per un servizio condiviso che deve sopravvivere a disconnessioni e riavvii non presidiati, consigliamo la [guida per Linux](/it/on-premises/installation/using-docker-compose/linux).

### Verificare il ripristino dopo il riavvio di Docker Desktop {#check-recovery-after-restarting-docker-desktop}

Dopo aver salvato il lavoro e lasciato terminare le compilazioni in corso, scegli **Restart Docker Desktop** dal menu di risoluzione dei problemi di Docker Desktop. Attendi il motore, quindi controlla in **Ubuntu**:

```bash
docker ps
curl -I http://localhost:8080/launchpad
```

Apri il progetto esistente in Windows e compilalo di nuovo. Conferma che l'account e il sorgente esistano ancora.

Se hai arrestato intenzionalmente l'istanza con `bin/stop`, usa `bin/start`. Se Docker è attivo ma un servizio non funziona, leggi i suoi log anziché ricreare la configurazione. Windows Update, gli aggiornamenti di Docker e le interruzioni di corrente possono comunque interrompere un'installazione attiva 24 ore su 24; conserva i backup e verifica il ripristino dopo la manutenzione pianificata.

### Uso quotidiano {#daily-use}

Avvia Docker Desktop in Windows. Apri **Ubuntu**:

```bash
cd "$HOME/ayakaleaf-toolkit"
```

| Attività | Comando |
| --- | --- |
| Avviare i container esistenti | `bin/start` |
| Arrestare i container mantenendo i dati | `bin/stop` |
| Applicare le modifiche alla configurazione | `bin/up -d` |
| Controllare lo stato | `bin/docker-compose ps` |
| Leggere i log di avvio | `bin/docker-compose logs --tail=100 sharelatex` |
| Leggere i log di MongoDB | `bin/docker-compose logs --tail=100 mongo` |
| Leggere i log del compilatore | `bin/logs -f clsi` |

`bin/start` non applica le modifiche alla configurazione: usa `bin/up -d` dopo aver modificato `config/`. Segui [Dati e backup](/it/on-premises/maintenance/data-and-backups) prima di aggiornare, spostare o rimuovere la distribuzione WSL. Copiare i file di MongoDB in uso mentre il database vi scrive non costituisce un backup coerente.

Mantieni `127.0.0.1` per l'uso locale. Servire altri computer richiede anche di impostare deliberatamente l'indirizzo di ascolto, l'URL del sito, la configurazione del firewall/della rete di Windows e HTTPS; cambiare solo `OVERLEAF_SITE_URL` non pubblica una porta.

Se qualcosa non funziona, consulta [Risoluzione dei problemi](/it/on-premises/installation/using-docker-compose/windows/troubleshooting).
