### L'inizializzazione non riesce con invalid command code {#initialization-fails-with-invalid-command-code}

`bin/init` segnala `sed: ... invalid command code` quando trova il sed BSD di macOS. Metti GNU sed nel `PATH` come in [1. Scaricare il Toolkit](/it/on-premises/installation/using-docker-compose/macos/1.-download-the-toolkit) e controlla `sed --version`.

Un'inizializzazione fallita può lasciare tutti e tre i file in `config/` con un `OVERLEAF_INVITE_TOKEN_SECRET` vuoto. Rieseguire `bin/init` segnala quindi `Config files already exist`. Per una nuova installazione che non è mai stata avviata, sposta i tre file in una directory di backup ed esegui di nuovo `bin/init`. Per un'istanza esistente, conserva la sua configurazione e i suoi segreti e non eliminarne i file per far rieseguire `bin/init`.

### MongoDB continua a riavviarsi {#mongodb-keeps-restarting}

Leggi i log di MongoDB e la versione del kernel della VM di Docker:

```bash
bin/docker-compose logs --tail=100 mongo
docker info --format '{{.KernelVersion}}'
```

Se il log menziona l'incompatibilità con il kernel Linux, segui [Controllare il kernel Linux della VM di Docker](/it/on-premises/installation/using-docker-compose/macos/5.-personalizing-your-instance#check-the-docker-vms-linux-kernel) ed esegui di nuovo `bin/up -d`. Il solo codice di uscita `137` non dimostra che MongoDB abbia esaurito la memoria: controlla lo stato del container e i log. Per un problema più vecchio di MongoDB su Docker Desktop, vedi anche [Risoluzione dei problemi](/it/on-premises/support/troubleshooting).

### Impossibile connettersi al daemon Docker {#cannot-connect-to-the-docker-daemon}

Avvia Docker Desktop e controlla il contesto Docker selezionato; vedi [0. Configurare Docker Desktop](/it/on-premises/installation/using-docker-compose/macos/0.-setup-docker-desktop). Se `docker info` funziona ma le compilazioni non riescono a raggiungere Docker, controlla le impostazioni del socket in `config/overleaf.rc` e leggi i log di `clsi`. Una CLI di Docker funzionante sul Mac non dimostra che il mount del socket dell'applicazione sia corretto.

### La pagina si apre, ma le compilazioni non riescono {#the-page-opens-but-compiles-fail}

Controlla che l'immagine TeX Live esista in locale e corrisponda all'architettura del motore Docker:

```bash
docker image inspect ghcr.io/ayaka-notes/texlive-full:2026.1 \
  --format '{{.Os}}/{{.Architecture}}'
bin/logs -f clsi
```

Su Apple silicon, l'immagine dovrebbe essere `linux/arm64`. Controlla che `SERVER_PRO` e `SIBLING_CONTAINERS_ENABLED` siano entrambi `true`, quindi applica le modifiche con `bin/up -d`. Se i log segnalano una directory di compilazione mancante, controlla la condivisione dei file di Docker Desktop e la posizione di `OVERLEAF_DATA_PATH`. Non disattivare le sandboxed compiles per nascondere un errore di mount.

### Not a directory, oppure manca un bind mount {#not-a-directory-or-a-bind-mount-is-missing}

Un file dell'host montato da un override potrebbe essere stato eliminato, oppure Docker potrebbe aver creato una directory dove dovrebbe trovarsi il file. Controlla il percorso di origine sull'host e se il mount si aspetta un file o una directory. Ripristina il file di configurazione prima di ricreare il container. Un'installazione sotto `/tmp` può incorrere in questo problema dopo che macOS rimuove i file temporanei.

### Conflitti di porta o di nome dei container {#port-or-container-name-conflicts}

Se la porta `8080` è in uso, scegli un'altra porta in `config/overleaf.rc`, imposta `OVERLEAF_SITE_URL` di conseguenza ed esegui di nuovo `bin/up -d`.

Il Toolkit assegna ai suoi container nomi fissi come `sharelatex`, `mongo` e `redis`. Cambiare solo `PROJECT_NAME` non rende indipendenti due installazioni del Toolkit. Prima di avviare una seconda istanza, controlla `docker ps -a` e usa altri nomi di container in un override di Compose, un'altra porta e directory dei dati separate. Non rimuovere i container o i dati di una distribuzione esistente per risolvere un conflitto di nomi.

### L'istanza non è raggiungibile dopo un po' di tempo {#the-instance-is-unreachable-after-a-while}

Probabilmente il Mac è andato in sospensione, oppure Docker Desktop è stato chiuso. Vedi [Mantenere l'istanza disponibile](/it/on-premises/installation/using-docker-compose/macos/6.-post-installation-tasks#keep-the-instance-available).

### `bin/doctor` dice che non è Linux, o chiede un login a Quay {#bin/doctor-says-this-is-not-linux-or-asks-for-a-quay-login}

Entrambi gli avvisi sono previsti su macOS con l'immagine pubblica; vedi [2. Familiarizzare con il Toolkit](/it/on-premises/installation/using-docker-compose/macos/2.-familiarize-yourself-with-the-toolkit). Controlla invece il download delle immagini, lo stato dei servizi e i risultati delle compilazioni, e non ignorare gli altri errori del report.
