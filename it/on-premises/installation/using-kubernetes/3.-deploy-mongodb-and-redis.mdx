title: 3. Distribuire MongoDB e Redis
description: Esegui MongoDB come replica set e Redis con persistenza, oppure punta ai tuoi servizi.
icon: database
---

Ayakaleaf Pro richiede:

* **MongoDB 8** come **replica set** (usa le transazioni). Tre membri distribuiti su tre nodi sopravvivono alla perdita di un nodo; funziona anche un solo membro.
* **Redis 7**, un unico server con persistenza AOF. Redis contiene le modifiche non ancora scritte in MongoDB, le sessioni e i messaggi tra i servizi di Overleaf. Overleaf si collega a un unico server Redis: Sentinel e Redis Cluster non sono supportati.

<Info>

In alternativa puoi usare servizi gestiti, come MongoDB Atlas o il Redis del tuo cloud. Salta questa pagina e imposta `OVERLEAF_MONGO_URL` e `OVERLEAF_REDIS_HOST` su di essi al [passaggio 4](/it/on-premises/installation/using-kubernetes/4.-personalizing-your-instance).

</Info>

<Steps>
<Step title="MongoDB">
```yaml title="10-mongo.yaml" wrap
apiVersion: v1
kind: Service
metadata:
  name: mongo
  namespace: overleaf
spec:
  clusterIP: None                 # headless: gives mongo-0.mongo, mongo-1.mongo, ...
  publishNotReadyAddresses: true  # members must resolve each other before the set is initiated
  selector:
    app: mongo
  ports:
    - name: mongo
      port: 27017
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mongo
  namespace: overleaf
spec:
  serviceName: mongo
  replicas: 3
  selector:
    matchLabels:
      app: mongo
  template:
    metadata:
      labels:
        app: mongo
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app: mongo
              topologyKey: kubernetes.io/hostname
      containers:
        - name: mongo
          image: mongo:8.0
          args:
            - --replSet=overleaf
            - --bind_ip_all
            - --wiredTigerCacheSizeGB=0.25   # default is 50% of (RAM - 1 GB); size it for your nodes
          # env:
          #   - name: GLIBC_TUNABLES        # only on kernel 6.19+ (SERVER-121912)
          #     value: glibc.pthread.rseq=1
          ports:
            - containerPort: 27017
          readinessProbe:
            tcpSocket:
              port: 27017
          resources:
            requests:
              cpu: 100m
              memory: 384Mi
            limits:
              memory: 768Mi
          volumeMounts:
            - name: data
              mountPath: /data/db
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 5Gi
---
# Initiates the replica set once. Safe to re-run: it does nothing when the set exists.
apiVersion: batch/v1
kind: Job
metadata:
  name: mongo-init-replica-set
  namespace: overleaf
spec:
  backoffLimit: 20
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: init
          image: mongo:8.0
          command:
            - mongosh
            - --quiet
            - --host=mongo-0.mongo
            - --eval
            - |
              try {
                rs.status()
                print('replica set already initiated')
              } catch (e) {
                rs.initiate({
                  _id: 'overleaf',
                  members: [
                    { _id: 0, host: 'mongo-0.mongo.overleaf.svc.cluster.local:27017' },
                    { _id: 1, host: 'mongo-1.mongo.overleaf.svc.cluster.local:27017' },
                    { _id: 2, host: 'mongo-2.mongo.overleaf.svc.cluster.local:27017' },
                  ],
                })
              }
```

```bash
kubectl apply -f 10-mongo.yaml
kubectl -n overleaf rollout status statefulset/mongo
kubectl -n overleaf wait --for=condition=complete job/mongo-init-replica-set --timeout=5m
kubectl -n overleaf exec mongo-0 -- mongosh --quiet --eval 'rs.status().members.map(m => m.name + " " + m.stateStr)'
```

Dopo alcuni secondi un membro dovrebbe essere `PRIMARY` e gli altri `SECONDARY`. Il Job riprova finché tutti i membri non rispondono, quindi alcuni pod del Job falliti sono normali.

* Il Service headless richiede `publishNotReadyAddresses: true`: i membri devono trovarsi a vicenda per nome prima che il replica set esista.
* I membri vengono aggiunti con i loro nomi stabili (`mongo-0.mongo.overleaf.svc.cluster.local`), mai con gli IP dei pod, che cambiano a ogni riavvio.
* Per un solo membro, imposta `replicas: 1` e mantieni solo `mongo-0` nel Job.
</Step>

<Step title="Redis">
```yaml title="20-redis.yaml" wrap
apiVersion: v1
kind: Service
metadata:
  name: redis
  namespace: overleaf
spec:
  selector:
    app: redis
  ports:
    - name: redis
      port: 6379
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
  namespace: overleaf
spec:
  serviceName: redis
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis
          image: redis:7.4
          args: [--appendonly, "yes"]
          ports:
            - containerPort: 6379
          readinessProbe:
            tcpSocket:
              port: 6379
          resources:
            requests:
              cpu: 50m
              memory: 128Mi
            limits:
              memory: 512Mi
          volumeMounts:
            - name: data
              mountPath: /data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 2Gi
```

```bash
kubectl apply -f 20-redis.yaml
kubectl -n overleaf rollout status statefulset/redis
```
</Step>
</Steps>

### Q\&A

<Accordion title="MongoDB 8 si arresta in modo anomalo all'avvio su un kernel recente. Perché?">

<strong>Risposta:</strong> MongoDB 8 non funziona su kernel Linux 6.19 e successivi ([SERVER-121912](https://jira.mongodb.org/browse/SERVER-121912)). Rimuovi il commento dalla variabile d'ambiente `GLIBC_TUNABLES` in `10-mongo.yaml`.

</Accordion>

<Accordion title="Quanta memoria richiede MongoDB?">

<strong>Risposta:</strong> Per impostazione predefinita MongoDB usa per la sua cache metà della memoria del nodo meno 1 GB, e vede la memoria del nodo, non il limite del pod. Imposta `--wiredTigerCacheSizeGB` in base ai tuoi nodi; con `0.25` ogni membro è rimasto a circa 200-260 MiB sui nostri nodi di test da 4 GB.

</Accordion>
