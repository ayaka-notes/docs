<Accordion title="Eseguire Overleaf con un filesystem NFS">

Montare un filesystem NFS in un container Overleaf è tecnicamente possibile, ma non è consigliato e può causare diversi tipi di errori di prestazioni.

Un errore comune riscontrato durante le compilazioni è:

```text
EBUSY: resource busy or locked, unlink '/var/lib/overleaf/data/compiles/62f3d57bef7cf9005c364e75-62f3d57bef7cf9005c364e7a/.nfs573663533034825247625441'
```

In particolare sconsigliamo di usare filesystem basati su NFS per i dati temporanei, come le directory usate per i dati di compilazione. Per le directory seguenti consigliamo di usare un disco scratch locale, preferibilmente un SSD locale.

Per le configurazioni basate su `docker-compose`, suggeriamo semplicemente di sovrascrivere il bind mount da NFS, evitando così di modificare i percorsi nell'applicazione. Ecco un estratto di configurazione `docker-compose` che usa un disco scratch montato su `/scratch`:

```yaml title="docker-compose excerpt"
services:
  sharelatex:
    environment:
      SANDBOXED_COMPILES_HOST_DIR: /scratch/compiles/
    volumes:
      - nfs:/var/lib/overleaf/data
      - /scratch/cache/:/var/lib/overleaf/data/cache
      - /scratch/compiles/:/var/lib/overleaf/data/compiles
      - /scratch/output/:/var/lib/overleaf/data/output
      - /scratch/tmp/:/var/lib/overleaf/tmp
```

Dopo l'aggiornamento non è necessario migrare i file esistenti da NFS alla nuova posizione. Il compilatore LaTeX può ricreare tutti i file eseguendo di nuovo una compilazione completa.

Per maggiori dettagli vedi: https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-with-an-nfs-filesystem

</Accordion>

<Accordion title="Eseguendo Overleaf su Windows o macOS il servizio `mongo` non si avvia">

Se esegui Overleaf su Windows o macOS, il servizio `mongo` potrebbe non riuscire a riavviarsi, restituendo l'errore:

```text title="Example error"
Failed to start up WiredTiger under any compatibility version.
Reason: 1: Operation not permitted
```

Per evitare questo errore, i dati devono essere memorizzati in un volume anziché in una directory con bind mount (per maggiori dettagli consulta la documentazione dell'immagine `mongo`: https://github.com/docker-library/docs/blob/master/mongo/content.md#where-to-store-data). Per memorizzare i dati in volumi Docker montati nei container MongoDB e Redis, aggiungi quanto segue a `config/docker-compose.override.yml` (crea questo file se non esiste ancora):

```yaml title="config/docker-compose.override.yml"
volumes:
  mongo-data:
  redis-data:

services:
  mongo:
    volumes:
      - mongo-data:/data/db

  redis:
    volumes:
      - redis-data:/data
```

Per maggiori informazioni vedi: https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-on-windows-or-macos-results-in-the-mongoservice-not-starting

</Accordion>

<Accordion title="L'aggiornamento a Redis 6.2 causa un ciclo di riavvii">

Usa il comando `docker logs redis` per ottenere una copia dei log.

Se vedi la riga `Fatal: Can't initialize Background Jobs`, l'output completo sarà simile al seguente:

```text title="Redis log example"
1:M 11 Feb 2024 15:19:22.609 # Server initialized
1:M 11 Feb 2024 15:19:22.609 # Fatal: Can't initialize Background Jobs.
1:C 11 Feb 2024 15:19:26.055 # oO0OoO0OoO0Oo Redis is starting oO0OoO0OoO0Oo
```

Questo problema può essere legato alla versione di Docker attualmente in uso. L'aggiornamento a una versione >= 20.10.10 dovrebbe risolverlo.

Per maggiori informazioni, consulta la issue upstream di Redis: https://github.com/redis/redis/issues/12362

Riferimento: https://docs.overleaf.com/on-premises/support/troubleshooting#upgrading-to-redis-6.2-results-in-a-restart-loop

</Accordion>

<Accordion title="Orientamento errato delle immagini di anteprima/miniatura nella galleria dei template">

Occasionalmente, le immagini di anteprima/miniatura generate da Server Pro possono essere create con un orientamento errato e richiedere un intervento manuale per correggerle. Queste immagini sono memorizzate in `/var/lib/overleaf/data/template_files/` (>= 5.0.3) e in `/var/lib/sharelatex/data/template_files/` (versioni precedenti).

Consigliamo di eseguire un backup di questa cartella prima di apportare qualsiasi modifica.

Dovrai seguire i passaggi seguenti per ciascun template interessato:

Trova l'ID del template: vai alla galleria dei template della tua istanza (/templates/all), apri un template interessato e copia l'ID dall'URL (ad esempio: https://your-instance-url/templates/6645d346c224815e9460a695). Esegui il comando di correzione: esegui il comando seguente dall'host Docker (sostituisci l'ID del template con quello che hai copiato e aggiorna il percorso se necessario): docker exec sharelatex /bin/bash -c "mogrify -rotate 90 /var/lib/overleaf/data/template\_files/6645d346c224815e9460a695\_\*\{thumbnail,preview\}"

Riferimento: https://docs.overleaf.com/on-premises/support/troubleshooting#incorrect-orientation-of-template-gallery-preview-thumbnail-images

</Accordion>

<Accordion title="Verifica di aver abilitato le chiamate di sistema. Per pdflatex, si tratta di 'pdflatex -shell-escape'.">

Il comando `\write18` è disabilitato per impostazione predefinita nella Community Edition, poiché tutte le compilazioni avvengono all'interno dello stesso container `sharelatex`; questa è l'impostazione predefinita più sicura.

Se vuoi abilitarlo per pdflatex, crea un file `latexmkrc` nella radice del tuo progetto con il seguente contenuto:

```perl title="latexmkrc"
$pdflatex = 'pdflatex --shell-escape';
```

Quindi prova a ricompilare.

Riferimento: https://docs.overleaf.com/on-premises/support/troubleshooting#please-verify-that-you-have-enabled-system-calls.-for-pdflatex-this-is-pdflatex-shell-escape

</Accordion>
