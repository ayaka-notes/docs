## Migrazione alla cronologia completa dei progetti

La release `3.5.x` della Community Edition include la [funzionalità Full Project History](https://www.overleaf.com/learn/latex/Using_the_History_feature), già disponibile nella nostra offerta SaaS, [overleaf.com](http://overleaf.com/)

Dopo aver aggiornato la tua istanza a Overleaf CE `3.5.13`, tutti i nuovi progetti utilizzeranno Full Project History per impostazione predefinita. I progetti esistenti continueranno a utilizzare il sistema di cronologia legacy finché non verranno migrati.

<Info>

Se esegui l'aggiornamento alla `3.5.13` e decidi di tornare a una versione precedente, dovresti effettuare il ripristino da un backup completo del sistema. La cronologia dei progetti creati nella `3.5.13` non è compatibile con le versioni precedenti di Overleaf CE.

</Info>

La nuova Full Project History porta diversi miglioramenti per gli utenti:

* Tiene traccia delle modifiche ai file binari, cosa non supportata dal sistema legacy.
* Supporta le versioni etichettate.
* Il sistema è in generale più robusto, con minori probabilità di perdita di dati.

Consulta la [documentazione di Full Project History](https://www.overleaf.com/learn/latex/Using_the_History_feature) per ulteriori informazioni sulla cronologia completa dei progetti.

### Migrare i progetti esistenti

<Steps>
<Step title="Creare un backup">
Crea un [backup](https://docs.overleaf.com/on-premises/maintenance/data-and-backups#performing-a-consistent-backup) completo della tua istanza con uno snapshot coerente delle directory **mongo**, **redis** e **sharelatex**.
</Step>

<Step title="Aggiornare">
Aggiorna la versione dell'immagine sharelatex/sharelatex alla 3.5.13.

Toolkit: usa lo script `$ bin/upgrade` per aggiornare il toolkit all'ultima versione e imposta **config/version** su 3.5.13.
</Step>

<Step title="Avviare l'istanza">
Idealmente, dovresti impedire agli utenti di accedere alla tua istanza durante la migrazione, per evitare perdite di dati nel caso in cui tu debba ripristinare il backup. Consulta [Migrazione offline](https://github.com/overleaf/overleaf/wiki/Full-Project-History-Migration/#offline-migration) per ulteriori informazioni su come farlo.
</Step>

<Step title="Attendere che tutti i servizi siano attivi e in esecuzione">
Attendi che tutti i servizi siano attivi e in esecuzione (vedi il comando seguente)

```bash wrap
$ bin/docker-compose exec sharelatex /bin/bash -c "curl http://localhost:3000/status"
web sharelatex is alive (api)%
```
</Step>

<Step title="Eseguire lo script di migrazione">
```bash wrap
# Overleaf Toolkit users:
$ bin/docker-compose exec sharelatex /bin/bash -c "cd /overleaf/services/web; VERBOSE_LOGGING=true node scripts/history/migrate_history.js --force-clean --fix-invalid-characters --convert-large-docs-to-file"

# legacy docker-compose.yml users:
$ docker exec sharelatex /bin/bash -c "cd /overleaf/services/web; VERBOSE_LOGGING=true node scripts/history/migrate_history.js --force-clean --fix-invalid-characters --convert-large-docs-to-file"
```

`--force-clean` cancella i dati della cronologia dei progetti migrati parzialmente nel nuovo sistema; ciò consente di ritentare la migrazione dei singoli progetti non riusciti nei tentativi precedenti;

`--fix-invalid-characters` sostituisce i caratteri non stampabili non supportati dal nuovo sistema di cronologia;

`--convert-large-docs-to-file` converte i documenti che superano la soglia di 2MB di dimensione modificabile in file non modificabili)

L'output dovrebbe essere simile a questo:

```bash
Migrated Projects  :  1
Total Projects     :  51
Remaining Projects :  51
Total history records to migrate: 98
Starting migration...
Migrating project: 63d29b5772dd80015a81bffe
migration result { upgraded: true, historyType: 'NoneWithoutConversion' }
Migrating project: 63d29c2e72dd80015a81c0a2
migration result { upgraded: true, historyType: 'NoneWithoutConversion' }

// …

Migration complete
==================
Projects migrated:  51
Projects failed:  0
Done.
```

Se la migrazione riesce, otterrai un codice di uscita `0` e le ultime righe indicheranno l'assenza di errori:

```bash
Projects failed:  0
Done.
```

Puoi riaprire l'accesso agli utenti (vedi il passaggio successivo). In caso di errori, consulta la sezione sulla risoluzione dei problemi più avanti. Puoi comunque riaprire il sito anche se i problemi non vengono risolti immediatamente: i progetti non migrati resteranno sul sistema di cronologia legacy.
</Step>

<Step title="Riaprire il sito">
Se hai scelto di eseguire una migrazione offline, dovrai riaprire il sito. Se hai ancora effettuato l'accesso, dovrai:

1. Fare clic sul pulsante **Admin** e scegliere **Manage Site**
2. Fare clic sulla scheda **Open/Close Editor**
3. Fare clic sul pulsante **Reopen Editor**

Se hai chiuso il browser, dovrai riavviare il sito con `$ bin/up`.
</Step>
</Steps>

#### Migrazione offline

Per impedire agli utenti di accedere mentre lo script di migrazione della cronologia è in esecuzione, segui questi passaggi:

* Accedi alla tua istanza Overleaf con un account amministratore
* Fai clic sul pulsante **Admin** e scegli **Manage Site**
* Fai clic sulla scheda **Open/Close Editor**
* Fai clic sul pulsante **Close Editor**
* Fai clic sul pulsante **Disconnect all users**

Una volta fatto ciò, gli utenti che hanno effettuato l'accesso verranno reindirizzati alla pagina di manutenzione, e i nuovi utenti che visitano la pagina di accesso vedranno la pagina di manutenzione e **non** potranno accedere.

#### Migrazione online

È possibile eseguire gli script di migrazione mentre l'applicazione è ancora in esecuzione. Occorre tenere conto di alcune considerazioni:

* Il processo di migrazione richiede un uso intensivo della CPU: dovresti monitorare l'utilizzo delle risorse mentre lo script è in esecuzione.
* Con un valore di `--concurrency` elevato, l'event loop di alcuni servizi (in particolare `track-changes`) potrebbe subire dei blocchi, con conseguente peggioramento dell'esperienza utente. Consigliamo di iniziare con il valore predefinito `--concurrency=1`.
* Puoi interrompere lo script in qualsiasi momento. Riavviandolo, la migrazione riprenderà dal punto in cui l'avevi lasciata. Ciò è utile se preferisci eseguire la migrazione nelle ore meno trafficate (ad es. di notte).

Ti consigliamo di chiudere il sito ed eseguire la migrazione offline durante una finestra di manutenzione quando il numero di progetti è inferiore a 1000 (`db.projects.count()`). Se il numero di progetti è elevato, puoi eseguire lo script e monitorarne l'avanzamento, quindi decidere se continuare a eseguirlo online oppure offline in base al tuo caso specifico.

#### Pulizia dei dati della cronologia legacy

Uno script per la pulizia dei dati della cronologia legacy è stato aggiunto in Server Pro `3.5.6`, `4.0.6` e `4.1.0`.

```bash wrap
bin/docker-compose exec sharelatex /bin/bash -c "cd /overleaf/services/web; node scripts/history/clean_sl_history_data.js"
```

Lo script può essere eseguito dopo che tutti i progetti sono stati migrati. Può anche essere utilizzato per liberare spazio durante una migrazione online.

<Info>

In Server Pro prima della versione 3.5.13, lo script elimina il contenuto delle collection `docHistory` e `docHistoryIndex`. MongoDB non rilascia lo spazio su disco dopo l'eliminazione dei documenti, ma lo riutilizza per i documenti futuri della stessa collection. Dopo la migrazione della cronologia, nulla scriverà più in queste collection, quindi lo spazio su disco resterà inutilizzato.

Se vuoi rendere nuovamente disponibile lo spazio su disco, puoi eseguire l'aggiornamento a Server Pro 3.5.13 (se utilizzi ancora la release 3.x) o a Server Pro 4.2.5 (se utilizzi la release 4.x) ed eseguire di nuovo lo script di pulizia.

Lo script di pulizia incluso nelle ultime patch release di Server Pro `3.5.x` e nelle ultime `4.x.x` elimina le collection come passaggio finale.

È sicuro eseguire nuovamente lo script di pulizia.

</Info>

### Risoluzione dei problemi

Aggiungeremo qui dei consigli per la risoluzione dei problemi. Tieni presente che, sebbene normalmente offriamo supporto solo ai clienti Server Pro, data la natura di questa migrazione faremo del nostro meglio per supportare anche i clienti CE che riscontrano problemi specifici della migrazione alla cronologia completa dei progetti.

Se lo script di migrazione alla cronologia completa dei progetti non riesce (ovvero termina con un errore o riporta un numero di progetti non riusciti diverso da zero), invia i seguenti dettagli al nostro team di supporto via email a [support+historymigration@overleaf.com](mailto:support+historymigration@overleaf.com?subject=Full%20project%20history%20migration%20problem&body=Instance%20Type%3A%20CE%20or%20Server%20Pro%20%28delete%20as%20appropriate%29%0A%0AInstallation%20Type%3A%20Overleaf%20toolkit%20or%20docker-compose.yml%20or%20other%20%28delete%20as%20appropriate%29%0A%0AScript%20output%3A%0A%0Abin%2Fdoctor%20output%20%28if%20using%20toolkit%29%3A%0A), indicando:

Oggetto: Full project history migration problem

* Tipo di istanza: CE o Server Pro (eliminare la voce non pertinente)
* Tipo di installazione: Overleaf toolkit, `docker-compose.yml` o altro (eliminare le voci non pertinenti)
* Versione: 3.5.x (toolkit: `$ cat config/version`)
* Output dello script di migrazione (che dovrebbe trovarsi nel container in `/overleaf/services/web`)
* Migrated Projects: (secondo l'output dello script di migrazione)
* Total Projects: (secondo l'output dello script di migrazione)
* Remaining Projects: (secondo l'output dello script di migrazione)
* Durata della migrazione:
* Output di `bin/doctor` (se utilizzi il toolkit)
* Versione del Toolkit: `$ git rev-parse HEAD` (se utilizzi il Toolkit)

Valuta la possibilità di allegare all'email i file di log dei servizi `history-v1`, `project-history` e `track-changes`. Li trovi in `/var/log/sharelatex` all'interno del container `sharelatex` e puoi esportarli in questo modo:

```bash
$ docker cp sharelatex:/var/log/sharelatex/history-v1.log history-v1.log
$ docker cp sharelatex:/var/log/sharelatex/project-history.log project-history.log
$ docker cp sharelatex:/var/log/sharelatex/track-changes.log track-changes.log
```

Rimuovi qualsiasi informazione sensibile dai file di log prima di allegarli.

#### Individuare alberi di file danneggiati

La migrazione può non riuscire per i progetti con un albero di file malformato (ad esempio, con nomi di file vuoti). Puoi ottenere un elenco di questi problemi usando lo script `find_malformed_filetrees`, che controlla tutti i progetti nel database:

```bash wrap
$ bin/docker-compose exec sharelatex /bin/bash -c "cd /overleaf/services/web; node scripts/find_malformed_filetrees.js"
BAD PATH: 123456789012345678901234 rootFolder.0.1.2.3
BAD PATH: 123456789012345678901234 rootFolder.0.4.5.6
...
```

Per correggere i percorsi non validi, usa lo script `fix_malformed_filetree`, eseguendo il comando una volta per ciascun percorso errato:

```bash wrap
$ bin/docker-compose exec sharelatex /bin/bash -c "cd /overleaf/services/web; node scripts/fix_malformed_filetree.js 123456789012345678901234 rootFolder.0.1.2.3"
$ bin/docker-compose exec sharelatex /bin/bash -c "cd /overleaf/services/web; node scripts/fix_malformed_filetree.js 123456789012345678901234 rootFolder.0.4.5.6"
...
```
