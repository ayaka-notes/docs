<Accordion title="Overleaf mit einem NFS-Dateisystem betreiben">

Das Einhängen eines NFS-Dateisystems in einen Overleaf-Container ist technisch möglich, wird jedoch nicht empfohlen und kann zu verschiedenen Arten von Performance-Fehlern führen.

Ein häufiger Fehler bei Kompilierungen ist:

```text
EBUSY: resource busy or locked, unlink '/var/lib/overleaf/data/compiles/62f3d57bef7cf9005c364e75-62f3d57bef7cf9005c364e7a/.nfs573663533034825247625441'
```

Insbesondere raten wir davon ab, NFS-basierte Dateisysteme für flüchtige Daten zu verwenden, etwa für die Verzeichnisse mit Kompilierungsdaten. Wir empfehlen für die folgenden Verzeichnisse eine lokale Scratch-Disk, vorzugsweise eine lokale SSD.

Bei `docker-compose`-basierten Setups empfehlen wir, einfach den Bind-Mount von NFS zu überschreiben, sodass keine Pfade in der Anwendung geändert werden müssen. Hier ist ein Beispielausschnitt einer `docker-compose`-Konfiguration mit einer unter `/scratch` eingehängten Scratch-Disk:

```yaml title="docker-compose excerpt"
services:
  sharelatex:
    environment:
      SANDBOXED_COMPILES_HOST_DIR: /scratch/compiles/
    volumes:
      - nfs:/var/lib/overleaf/data
      - /scratch/cache/:/var/lib/overleaf/data/cache
      - /scratch/compiles/:/var/lib/overleaf/data/compiles
      - /scratch/output/:/var/lib/overleaf/data/output
      - /scratch/tmp/:/var/lib/overleaf/tmp
```

Nach dem Update müssen keine vorhandenen Dateien vom NFS an ihren neuen Speicherort migriert werden. Der LaTeX-Compiler kann alle Dateien mit einem erneuten vollständigen Kompilierungslauf wiederherstellen.

Weitere Details finden Sie unter: https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-with-an-nfs-filesystem

</Accordion>

<Accordion title="Unter Windows oder macOS startet der Dienst `mongo` nicht">

Wenn Sie Overleaf unter Windows oder macOS betreiben, kann der Neustart des Dienstes `mongo` mit folgendem Fehler fehlschlagen:

```text title="Example error"
Failed to start up WiredTiger under any compatibility version.
Reason: 1: Operation not permitted
```

Um diesen Fehler zu vermeiden, müssen die Daten in einem Volume statt in einem per Bind-Mount eingehängten Verzeichnis gespeichert werden (weitere Details in der Dokumentation des `mongo`-Images: https://github.com/docker-library/docs/blob/master/mongo/content.md#where-to-store-data). Um die Daten in Docker-Volumes zu speichern, die in die MongoDB- und Redis-Container eingehängt werden, fügen Sie Folgendes zu `config/docker-compose.override.yml` hinzu (erstellen Sie diese Datei, falls sie noch nicht existiert):

```yaml title="config/docker-compose.override.yml"
volumes:
  mongo-data:
  redis-data:

services:
  mongo:
    volumes:
      - mongo-data:/data/db

  redis:
    volumes:
      - redis-data:/data
```

Weitere Informationen finden Sie unter: https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-on-windows-or-macos-results-in-the-mongoservice-not-starting

</Accordion>

<Accordion title="Upgrade auf Redis 6.2 führt zu einer Neustartschleife">

Verwenden Sie den Befehl `docker logs redis`, um eine Kopie der Logs auszugeben.

Wenn Sie die Zeile `Fatal: Can't initialize Background Jobs` sehen, sieht die vollständige Ausgabe etwa so aus:

```text title="Redis log example"
1:M 11 Feb 2024 15:19:22.609 # Server initialized
1:M 11 Feb 2024 15:19:22.609 # Fatal: Can't initialize Background Jobs.
1:C 11 Feb 2024 15:19:26.055 # oO0OoO0OoO0Oo Redis is starting oO0OoO0OoO0Oo
```

Dies kann mit der aktuell verwendeten Docker-Version zusammenhängen. Ein Update auf eine Version >= 20.10.10 sollte das Problem beheben.

Weitere Informationen finden Sie im Upstream-Issue von Redis: https://github.com/redis/redis/issues/12362

Referenz: https://docs.overleaf.com/on-premises/support/troubleshooting#upgrading-to-redis-6.2-results-in-a-restart-loop

</Accordion>

<Accordion title="Falsche Ausrichtung von Vorschau-/Miniaturbildern in der Vorlagengalerie">

Gelegentlich werden die von Server Pro erzeugten Vorschau-/Miniaturbilder in der falschen Ausrichtung erstellt und müssen manuell korrigiert werden. Diese Bilder werden in `/var/lib/overleaf/data/template_files/` (>= 5.0.3) bzw. `/var/lib/sharelatex/data/template_files/` (ältere Versionen) gespeichert.

Wir empfehlen, diesen Ordner vor jeder Änderung zu sichern.

Für jede betroffene Vorlage müssen Sie die folgenden Schritte ausführen:

Vorlagen-ID ermittelnNavigieren Sie zur Vorlagengalerie Ihrer Instanz (/templates/all), öffnen Sie eine betroffene Vorlage und kopieren Sie die ID aus der URL (zum Beispiel: https://your-instance-url/templates/6645d346c224815e9460a695).Korrekturbefehl ausführenFühren Sie den folgenden Befehl auf dem Docker-Host aus (ersetzen Sie die Vorlagen-ID durch die kopierte ID und passen Sie gegebenenfalls den Pfad an):docker exec sharelatex /bin/bash -c "mogrify -rotate 90 /var/lib/overleaf/data/template\_files/6645d346c224815e9460a695\_\*\{thumbnail,preview\}"

Referenz: https://docs.overleaf.com/on-premises/support/troubleshooting#incorrect-orientation-of-template-gallery-preview-thumbnail-images

</Accordion>

<Accordion title="Bitte prüfen Sie, ob Systemaufrufe aktiviert sind. Für pdflatex ist dies 'pdflatex -shell-escape'.">

Der Befehl `\write18` ist in der Community Edition standardmäßig deaktiviert, da alle Kompilierungen im selben `sharelatex`-Container stattfinden; dies ist die sicherere Voreinstellung.

Wenn Sie ihn für pdflatex aktivieren möchten, erstellen Sie im Stammverzeichnis Ihres Projekts eine Datei `latexmkrc` mit folgendem Inhalt:

```perl title="latexmkrc"
$pdflatex = 'pdflatex --shell-escape';
```

Kompilieren Sie anschließend erneut.

Referenz: https://docs.overleaf.com/on-premises/support/troubleshooting#please-verify-that-you-have-enabled-system-calls.-for-pdflatex-this-is-pdflatex-shell-escape

</Accordion>
