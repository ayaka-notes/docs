<Accordion title="Overleaf mit einem NFS-Dateisystem betreiben">

Das Einbinden eines NFS-Dateisystems in einen Overleaf-Container ist technisch möglich, wird jedoch nicht empfohlen und kann zu verschiedenen Arten von Performance-Fehlern führen.

Ein häufiger Fehler beim Kompilieren ist:

```text
EBUSY: resource busy or locked, unlink '/var/lib/overleaf/data/compiles/62f3d57bef7cf9005c364e75-62f3d57bef7cf9005c364e7a/.nfs573663533034825247625441'
```

Insbesondere raten wir davon ab, NFS-basierte Dateisysteme für flüchtige Daten zu verwenden, etwa für die Verzeichnisse mit Kompilierungsdaten. Wir empfehlen für die folgenden Verzeichnisse eine lokale Scratch-Disk, vorzugsweise eine lokale SSD.

Bei `docker-compose`-basierten Setups empfehlen wir, einfach den Bind-Mount vom NFS zu überschreiben, sodass Pfade in der Anwendung nicht geändert werden müssen. Hier ein Beispiel für einen Auszug aus einer `docker-compose`-Konfiguration mit einer unter `/scratch` eingebundenen Scratch-Disk:

```yaml title="docker-compose excerpt"
services:
  sharelatex:
    environment:
      SANDBOXED_COMPILES_HOST_DIR: /scratch/compiles/
    volumes:
      - nfs:/var/lib/overleaf/data
      - /scratch/cache/:/var/lib/overleaf/data/cache
      - /scratch/compiles/:/var/lib/overleaf/data/compiles
      - /scratch/output/:/var/lib/overleaf/data/output
      - /scratch/tmp/:/var/lib/overleaf/tmp
```

Nach der Umstellung müssen keine vorhandenen Dateien vom NFS an ihren neuen Speicherort migriert werden. Der LaTeX-Compiler kann alle Dateien mit einem vollständigen Kompilierungsdurchlauf neu erzeugen.

Weitere Details finden Sie unter: https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-with-an-nfs-filesystem

</Accordion>

<Accordion title="Unter Windows oder macOS startet der Dienst `mongo` nicht">

Wenn Sie Overleaf unter Windows oder macOS betreiben, kann der Neustart des Dienstes `mongo` mit folgendem Fehler fehlschlagen:

```text title="Example error"
Failed to start up WiredTiger under any compatibility version.
Reason: 1: Operation not permitted
```

Dies kann auftreten, wenn MongoDB-Daten per Bind-Mount aus einem Dateisystem eingebunden werden, das die erforderliche Semantik nicht bietet, etwa aus einem unter Windows eingebundenen Verzeichnis. Für [Windows mit WSL 2](/de/on-premises/installation/using-docker-compose/windows) bewahren Sie das Toolkit im Linux-Home-Verzeichnis von Ubuntu auf und verwenden die Standard-Bind-Mounts. Siehe die [MongoDB-Prüfungen](/de/on-premises/installation/using-docker-compose/windows/troubleshooting#mongodb-fails-to-start) in der Plattformanleitung.

Für eine Neuinstallation, die von Docker verwalteten Speicher benötigt, verwendet die folgende Override-Datei benannte Volumes (siehe die [Speicherhinweise des MongoDB-Images](https://github.com/docker-library/docs/blob/master/mongo/content.md#where-to-store-data)). Bei einer bestehenden Installation migriert das Ändern der Mounts keine Daten: Sichern Sie die Datenbank bzw. den Cache und stellen Sie sie wieder her, bevor Sie umstellen, sonst sieht der Dienst leere Volumes. Fügen Sie Folgendes zu `config/docker-compose.override.yml` hinzu und führen Sie es mit einer eventuell vorhandenen Konfiguration zusammen:

```yaml title="config/docker-compose.override.yml"
volumes:
  mongo-data:
  redis-data:

services:
  mongo:
    volumes:
      - mongo-data:/data/db

  redis:
    volumes:
      - redis-data:/data
```

Weitere Informationen finden Sie unter: https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-on-windows-or-macos-results-in-the-mongoservice-not-starting

</Accordion>

<Accordion title="Upgrade auf Redis 6.2 führt zu einer Neustartschleife">

Verwenden Sie den Befehl `docker logs redis`, um eine Kopie der Logs auszugeben.

Wenn Sie die Zeile `Fatal: Can't initialize Background Jobs` sehen, sieht die vollständige Ausgabe etwa so aus:

```text title="Redis log example"
1:M 11 Feb 2024 15:19:22.609 # Server initialized
1:M 11 Feb 2024 15:19:22.609 # Fatal: Can't initialize Background Jobs.
1:C 11 Feb 2024 15:19:26.055 # oO0OoO0OoO0Oo Redis is starting oO0OoO0OoO0Oo
```

Dies kann mit der aktuell verwendeten Docker-Version zusammenhängen. Ein Update auf Version >= 20.10.10 sollte das Problem beheben.

Weitere Informationen finden Sie im Upstream-Issue von Redis: https://github.com/redis/redis/issues/12362

Referenz: https://docs.overleaf.com/on-premises/support/troubleshooting#upgrading-to-redis-6.2-results-in-a-restart-loop

</Accordion>

<Accordion title="Falsche Ausrichtung der Vorschau-/Miniaturbilder in der Vorlagengalerie">

Gelegentlich werden die von Ayakaleaf Pro erzeugten Vorschau-/Miniaturbilder falsch ausgerichtet und müssen manuell korrigiert werden. Diese Bilder werden in `/var/lib/overleaf/data/template_files/` gespeichert.

Wir empfehlen, diesen Ordner zu sichern, bevor Sie Änderungen vornehmen.

Führen Sie für jede betroffene Vorlage die folgenden Schritte aus:

Vorlagen-ID ermitteln: Navigieren Sie zur Vorlagengalerie Ihrer Instanz (/templates/all), öffnen Sie eine betroffene Vorlage und kopieren Sie die ID aus der URL (zum Beispiel: https://your-instance-url/templates/6645d346c224815e9460a695). Korrekturbefehl ausführen: Führen Sie den folgenden Befehl auf dem Docker-Host aus (ersetzen Sie die Vorlagen-ID durch die kopierte ID und passen Sie den Pfad bei Bedarf an): docker exec sharelatex /bin/bash -c "mogrify -rotate 90 /var/lib/overleaf/data/template\_files/6645d346c224815e9460a695\_\*\{thumbnail,preview\}"

Referenz: https://docs.overleaf.com/on-premises/support/troubleshooting#incorrect-orientation-of-template-gallery-preview-thumbnail-images

</Accordion>

<Accordion title="Bitte prüfen Sie, ob Systemaufrufe aktiviert sind. Für pdflatex lautet dies 'pdflatex -shell-escape'.">

Der Befehl `\write18` ist in der Community Edition standardmäßig deaktiviert, da alle Kompilierungen im selben Container `sharelatex` stattfinden; dies ist die sicherere Voreinstellung.

Wenn Sie ihn für pdflatex aktivieren möchten, erstellen Sie im Stammverzeichnis Ihres Projekts eine Datei `latexmkrc` mit folgendem Inhalt:

```perl title="latexmkrc"
$pdflatex = 'pdflatex --shell-escape';
```

Kompilieren Sie anschließend erneut.

Referenz: https://docs.overleaf.com/on-premises/support/troubleshooting#please-verify-that-you-have-enabled-system-calls.-for-pdflatex-this-is-pdflatex-shell-escape

</Accordion>

<Accordion title="`bin/up` schlägt nach „Initiating Mongo replica set...“ mit `unable to upgrade to tcp, received 409` oder `OCI runtime exec failed` fehl">

Diese Fehler bedeuten, dass der `mongo`-Container ständig abstürzt und neu startet. `bin/up` startet MongoDB und führt dann einen Befehl darin aus, der fehlschlägt, während der Container neu startet. `bin/docker-compose ps` zeigt den Dienst `mongo` als `Restarting` an.

Um die eigentliche Ursache zu finden, lesen Sie das MongoDB-Log:

```sh
bin/logs mongo
```

Häufige Ursachen sind:

* <strong>Die CPU unterstützt kein AVX.</strong> MongoDB 5.0 und neuer benötigen AVX auf x86-64, und das Log zeigt `MongoDB 5.0+ requires a CPU with AVX support`. Setzen Sie in einer virtuellen Maschine den CPU-Typ auf `host`, damit AVX durchgereicht wird.
* <strong>Linux-Kernel 6.19 bis 7.0.13.</strong> MongoDB startet auf diesen Kerneln nicht. Die Umgehungslösung finden Sie unter [Softwareanforderungen](/de/on-premises/installation/introduction#software-requirements).
* <strong>Die Daten wurden von einer älteren MongoDB-Version erstellt.</strong> MongoDB 8.0 kann Daten aus 4.4 oder 5.0 nicht direkt öffnen. Führen Sie das Upgrade jeweils um eine Hauptversion durch, siehe [MongoDB aktualisieren](/de/on-premises/maintenance/updating-mongodb).

</Accordion>

<Accordion title="Das Log zeigt „Running Overleaf Community Edition, skipping TexLive checks“">

Das ist bei Ayakaleaf Pro so vorgesehen und kann ignoriert werden. Die Meldung wird ausgegeben, wenn `OVERLEAF_IS_SERVER_PRO` nicht `true` ist, was im Ayakaleaf Pro-Image der Fall ist. Ayakaleaf Pro benötigt diese Variable nicht, lassen Sie sie daher ungesetzt.

</Accordion>

<Accordion title="Der Container `sharelatex` startet ständig neu">

Bevor Overleaf startet, führt der Container Startprüfungen aus und beendet sich, wenn eine davon fehlschlägt. Das Toolkit betreibt ihn mit `restart: always`, daher startet Docker ihn erneut, und dieselbe Prüfung schlägt wieder fehl. Die Startausgabe nennt die fehlgeschlagene Prüfung:

```sh
bin/docker-compose logs --tail=100 sharelatex
```

Häufige Ursachen sind:

* **`Missing required secrets`**: Setzen Sie `OVERLEAF_INVITE_TOKEN_SECRET` in `config/variables.env`, siehe [Umgebungsvariablen](/de/on-premises/configuration/overleaf-toolkit/environment-variables).
* **`ShareLaTeX to Overleaf rebranding`**: Die Konfiguration verwendet noch `SHARELATEX_`-Variablen oder -Pfade; benennen Sie sie wie in der Meldung angegeben um.
* **Ein Fehler nach `Checking can connect to mongo and redis`**: Overleaf kann MongoDB oder Redis nicht erreichen. Prüfen Sie `bin/logs mongo` und `bin/logs redis`.

Führen Sie nach Behebung der Ursache `bin/up -d` aus.

</Accordion>

<Accordion title="Der Container stoppt bei `910_initiate_doc_version_recovery` oder beendet sich mit Code 2">

Bei jedem Start führt der Container seine Startskripte nacheinander aus, und das Log nennt jedes davon als `*** Running /etc/my_init.d/<script>...`. `910_initiate_doc_version_recovery` hat nur auf Instanzen etwas zu tun, auf denen einmal Overleaf 5.0.1 lief. Auf jeder anderen Instanz gibt es `No recovery of doc versions needed.` aus, und der Start wird fortgesetzt. Seine Ausgabe landet außerdem in `data/history/doc-version-recovery.log` in `OVERLEAF_DATA_PATH`.

Der Exit-Code und das Ende von `bin/docker-compose logs --tail=100 sharelatex` zeigen, was passiert ist:

* **Exit-Code 2**, und das Log endet mit `*** Init system aborted.`: Der Container wurde gestoppt, zum Beispiel durch `bin/stop`, `docker stop` oder Strg+C bei `bin/up`. Das Skript in der letzten `Running`-Zeile ist nur dasjenige, das in diesem Moment lief; es ist nicht fehlgeschlagen. Starten Sie den Container mit `bin/up -d` erneut und lassen Sie den Start abschließen.
* **Exit-Code 1**, und das Log zeigt `*** /etc/my_init.d/<script> failed with status <n>`: Dieses Skript ist fehlgeschlagen, und sein Fehler steht in den Zeilen direkt darüber. Wenn `910_initiate_doc_version_recovery` mit `Detected unflushed changes while recovering doc versions` fehlgeschlagen ist, lief auf der Instanz 5.0.1 und sie hat noch nicht übertragene Änderungen; folgen Sie der offiziellen Anleitung [Doc version recovery](https://docs.overleaf.com/on-premises/release-notes/release-notes-5.x.x/doc-version-recovery).

</Accordion>

<Accordion title="„Restricted, sorry you don’t have permission to load this page“">

Diese Seite wird angezeigt, wenn Ihr Konto angemeldet ist, aber die Seite nicht öffnen darf, zum Beispiel eine Admin-Seite, die von einem Konto ohne Administratorrechte geöffnet wird, oder ein Projekt, das nicht mit Ihnen geteilt ist.

Um die Admin-Seiten zu öffnen, melden Sie sich mit einem Administratorkonto an. Ein bestehender Administrator kann ein anderes Konto zum Administrator machen, oder Sie erstellen eines mit dem Befehl `create-user --admin`, siehe [Benutzerverwaltung](/de/on-premises/user-and-project-management/user-management). In der Entwicklungsumgebung (`develop/`) benötigen die Admin-Seiten zusätzlich `ADMIN_PRIVILEGE_AVAILABLE=true` in `develop/dev.env`; das Ayakaleaf Pro-Image setzt dies bereits.

</Accordion>
