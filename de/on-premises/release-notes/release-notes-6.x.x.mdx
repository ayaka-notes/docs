## Ayakaleaf Pro 6.3.2

<strong>Veröffentlichungsdatum:</strong> 2026.10.23

Siehe: [https://github.com/ayaka-notes/ayakaleaf-pro/releases/tag/pro-v6.3.2](https://github.com/ayaka-notes/ayakaleaf-pro/releases/tag/pro-v6.3.2)

Wir sind sehr stolz, die Veröffentlichung von Overleaf Pro 6.3.2 bekannt zu geben. Das Upstream-Release Overleaf 6.3.2 ist ein Sicherheitsrelease, das Node.js aktualisiert, und wir liefern es zusammen mit der Gitea-Synchronisierung und den seit 6.3.1 gefundenen Fehlerbehebungen aus.

<Info>

Die Gitea-Synchronisierung wird in 6.3.2 als **Early Preview** für Graustufentests ausgeliefert und in v6.4.0 offiziell veröffentlicht. Ihre Konfiguration und ihr Verhalten können sich bis dahin noch ändern. Sie ist standardmäßig deaktiviert. Bitte melden Sie Probleme auf [GitHub](https://github.com/ayaka-notes/ayakaleaf-pro/issues).

</Info>

### Änderungen

* Bidirektionale Gitea-Synchronisierung (Early Preview) für gitea.com und selbst gehostetes Gitea 1.23+.
* Node.js 24.22.1, das Sicherheitsupdate aus dem Upstream-Release Overleaf 6.3.2.
* Fehlerbehebungen, die von unserem E2E-Testsystem und der internen Horizon-Fehleruntersuchung gefunden wurden.

#### Funktion 01: Gitea-Synchronisierung (Preview)

Bidirektionale Synchronisierung mit Gitea, genauso wie die GitHub- und die GitLab-Synchronisierung: Verknüpfen Sie Ihr Konto, importieren Sie ein Repository über das Menü für neue Projekte, exportieren Sie ein Projekt, pushen und pullen Sie und führen Sie Änderungen über Pull Requests zusammen. Overleaf umgeht niemals den Branch-Schutz des Repositorys. Siehe [Gitea-Synchronisierung](/de/on-premises/configuration/overleaf-toolkit/gitea-synchronisation).

### Fehlerbehebungen

* GitHub-, GitLab- und Gitea-Synchronisierung: Wenn eine im Repository gelöschte Datei in Overleaf nicht gelöscht werden kann, schlägt die Synchronisierung fehl und kann wiederholt werden, anstatt Erfolg zu melden und die Datei im Projekt zu belassen. Ein `git push`, der eine Datei löscht, schlägt auf die gleiche Weise fehl ([#121](https://github.com/ayaka-notes/ayakaleaf-pro/issues/121)).
* Git-Bridge: Ein im Editor erstelltes Dokument mit einer Nicht-Text-Erweiterung (z. B. `.csv`) bleibt ein bearbeitbares Dokument, wenn ein `git push` es ändert.
* Änderungsverfolgung: Nicht angemeldete Bearbeiter eines per Link geteilten Projekts können Kommentar-Threads löschen, sie aber nicht mehr auflösen oder wieder öffnen. Reviewer können ihre eigenen Antworten löschen.
* Vorlagengalerie: Das Veröffentlichen einer Vorlage erfordert Zugriff auf das Projekt.
* Learn: Zwischengespeicherte Hilfeseiten bleiben verfügbar, wenn das Wiki nicht erreichbar ist.

### Upgrade

* Von 6.3.1 oder 6.3.0: Es ist keine Migration erforderlich. Laden Sie das neue Image herunter und starten Sie neu.
* Von 6.2.x oder früher mit Zotero oder Mendeley im Einsatz: Führen Sie zuerst die Zotero-/Mendeley-Migration aus [6.3.0](#ayakaleaf-pro-6.3.0) aus.
* Die Gitea-Synchronisierung ist standardmäßig deaktiviert und benötigt nur neue Umgebungsvariablen.

## Ayakaleaf Pro 6.3.1

<strong>Veröffentlichungsdatum:</strong> 2026.10.18

Siehe: [https://github.com/ayaka-notes/ayakaleaf-pro/releases/tag/pro-v6.3.1](https://github.com/ayaka-notes/ayakaleaf-pro/releases/tag/pro-v6.3.1)

Wir sind sehr stolz, die Veröffentlichung von Overleaf Pro 6.3.1 bekannt zu geben. Während sich ein typisches Patch-Release auf kleinere Korrekturen an v6.3.0 beschränken würde, geht diese Version deutlich weiter: Neben zahlreichen Fehlerbehebungen führt sie fünf neue Funktionen ein.

<Info>

Ihre Konfiguration und ihr Verhalten können sich bis dahin noch ändern. Beide sind standardmäßig deaktiviert. ### Änderungen

* Bidirektionale Dropbox-Synchronisierung (Early Preview).
* Bidirektionale GitLab-Synchronisierung (Early Preview), einschließlich selbstverwaltetem GitLab 15.10+.
* MCP-Server pro Projekt für KI-Clients wie Claude Code, Codex, Cursor, VS Code und Gemini CLI.
* Unterstützung von GitHub Enterprise für die GitHub-Synchronisierung.
* Handschriftliche Symbolerkennung in der Symbolpalette, vollständig im Browser ausgeführt.

#### Funktion 01: Dropbox-Synchronisierung (Preview)

Jeder Benutzer verknüpft sein eigenes Dropbox-Konto, und seine eigenen sowie mit ihm geteilten Projekte erscheinen unter `Apps/<DROPBOX_APP_NAME>/`. Bearbeitungen in Overleaf werden an Dropbox übertragen, und Bearbeitungen in Dropbox gelangen über einen signierten Webhook zurück. Git-Bridge muss aktiviert sein. Siehe [Dropbox-Synchronisierung](/de/on-premises/configuration/overleaf-toolkit/dropbox-synchronisation).

### Fehlerbehebungen

* Authentifizierung: Lokale Konten können auf SSO-Instanzen ihr Passwort festlegen und ändern, und OIDC-Benutzer können ihre eigene E-Mail-Adresse nicht mehr ändern ([#112](https://github.com/ayaka-notes/ayakaleaf-pro/pull/112)). Die Anmeldemethoden LDAP, SAML und OIDC bleiben erhalten, und die Abmeldung über SAML/OIDC funktioniert wieder. Siehe [Konten und Passwörter](/de/on-premises/configuration/overleaf-toolkit/authentication#accounts-and-passwords).
* LDAP, SAML und OIDC: Namensattribute mit mehreren Werten (wie `cn`) lassen die Anmeldung nicht mehr fehlschlagen, und OIDC-E-Mail-Adressen werden wie bei LDAP und SAML in Kleinbuchstaben umgewandelt, sodass ein Konto, dessen E-Mail-Adresse der IdP in anderer Schreibweise sendet, verknüpft wird, statt fehlzuschlagen.
* Gesperrte Benutzer: Das Sperren eines Benutzers beendet seine Sitzungen und schließt seine geöffneten Editoren. Seine Git-Token und MCP-Downloads werden abgelehnt.
* GitHub-Synchronisierung: Nur der Eigentümer kann ein Projekt exportieren, während des Pullens vorgenommene Bearbeitungen bleiben ausstehend, leere Dateien werden synchronisiert, manuelle Merges werden auf GitHub überprüft, und ein ersetztes Token wird beim erneuten Verknüpfen widerrufen.
* Zotero / Mendeley: Eine Meldung zum erneuten Verknüpfen wird angezeigt, wenn die Zugangsdaten nicht mehr funktionieren, und Literaturangaben werden nach einem Import neu indiziert.
* Externe API-Anfragen (Zotero, Mendeley, GitHub, GitLab, Websuche) erhalten ein Verbindungs-Timeout von 3 s statt 1 s ([#106](https://github.com/ayaka-notes/ayakaleaf-pro/pull/106)).
* Änderungsverfolgung: Review-Daten umfassen nicht geladene Dokumente und nicht gespeicherte Änderungen (aus [yu-i-i/overleaf-cep#262](https://github.com/yu-i-i/overleaf-cep/pull/262)).
* Fehlerassistent: Bietet Korrekturen nur für Dokumente im Projekt an ([#103](https://github.com/ayaka-notes/ayakaleaf-pro/pull/103)).
* Admin-Panel: Das Wiederherstellen eines gelöschten Projekts, das Ändern von Eigentümern und das Bearbeiten von Benutzern funktionieren korrekt. Die Suche verwendet den wörtlichen Text, und eine fehlgeschlagene E-Mail verhindert nicht mehr das Erstellen oder Löschen von Konten.
* Vorlagengalerie: Eine ungültige Sortierung liefert 400 statt 500, Vorlagen-IDs werden validiert, und beim Veröffentlichen eines Projekts ohne Hauptdatei wird nach einer gefragt.
* Git-Bridge: nginx leitet `/git/` an `GIT_BRIDGE_HOST` und `GIT_BRIDGE_PORT` weiter, und interne Routen werden ausgeblendet.
* Sandboxed Compiles: Container kürzlich kompilierter Projekte werden zur Wiederverwendung beibehalten.

### Upgrade

* Von 6.3.0: Es ist keine Migration erforderlich. Laden Sie das neue Image herunter und starten Sie neu.
* Von 6.2.x oder früher mit Zotero oder Mendeley im Einsatz: Führen Sie zuerst die Zotero-/Mendeley-Migration aus [6.3.0](#ayakaleaf-pro-6.3.0) aus.

Für die Dropbox-Synchronisierung müssen außerdem einmalig ihre MongoDB-Indizes erstellt werden, bevor Benutzer ihre Konten verknüpfen: siehe [Datenbankindizes erstellen](/de/on-premises/configuration/overleaf-toolkit/dropbox-synchronisation#create-the-database-indexes).

<Accordion title="Zotero-/Mendeley-Migration für bestehende Installationen">

Migrieren Sie beim Upgrade auf das erneut veröffentlichte 6.3.0-Image die Metadaten bestehender verknüpfter Literaturdateien aus Zotero/Mendeley mit dem folgenden Skript. Diese Migration gehört zum Fix `12031b8dfd`.

Dabei wird `zoteroGroupId` / `mendeleyGroupId` in `group_id` und `importedByUserId` in `importer_id` umbenannt sowie `importedByName` entfernt.

Sichern Sie MongoDB und stoppen Sie die Anwendung, bevor Sie die Migration ausführen. Lassen Sie MongoDB weiterlaufen. Öffnen Sie dessen Shell (ersetzen Sie `mongo` durch den Namen Ihres Containers):

```bash
docker exec -it mongo mongosh
```

Führen Sie in `mongosh` Folgendes aus (ersetzen Sie `sharelatex` durch den Namen Ihrer Datenbank):

```javascript
use sharelatex

(async () => {
  let updated = 0
  await db.projects.find({}, { rootFolder: 1 }).forEach(async project => {
    const changes = {}
    function visit(folders, path) {
      for (const [i, folder] of (folders || []).entries()) {
        const folderPath = `${path}.${i}`
        for (const [j, file] of (folder.fileRefs || []).entries()) {
          const data = { ...file.linkedFileData }
          if (!["zotero", "mendeley"].includes(data.provider)) continue
          const groupKey = `${data.provider}GroupId`
          if (![groupKey, "importedByUserId", "importedByName"].some(key => key in data)) continue
          for (const [oldKey, newKey] of [[groupKey, "group_id"], ["importedByUserId", "importer_id"]]) {
            if (data[oldKey] != null && data[oldKey] !== "") {
              const value = String(data[oldKey])
              if (newKey in data && data[newKey] !== value) {
                throw new Error(`Conflicting ${newKey}: project ${project._id}, file ${file._id}`)
              }
              data[newKey] = value
            }
            delete data[oldKey]
          }
          delete data.importedByName
          changes[`${folderPath}.fileRefs.${j}.linkedFileData`] = data
        }
        visit(folder.folders, `${folderPath}.folders`)
      }
    }
    visit(project.rootFolder, "rootFolder")
    if (!Object.keys(changes).length) return
    const result = await db.projects.updateOne(
      { _id: project._id, rootFolder: { $eq: project.rootFolder } },
      { $set: changes }
    )
    if (!result.matchedCount) throw new Error(`Project changed during migration: ${project._id}`)
    updated += result.modifiedCount
  })
  print(`Updated ${updated} project(s).`)
})()
```

Das Skript berücksichtigt verschachtelte Ordner und ändert ausschließlich Metadaten von Zotero/Mendeley. Es kann bedenkenlos erneut ausgeführt werden: Eine abgeschlossene Migration meldet beim nächsten Lauf `Updated 0 project(s).`. Bricht es mit einem Konflikt ab, prüfen Sie das gemeldete Projekt bzw. die gemeldete Datei; frühere Projekte wurden möglicherweise bereits migriert.

Starten Sie die aktualisierte Anwendung, laden Sie den Editor neu und aktualisieren Sie eine bestehende Literaturdatei als deren ursprünglicher Importeur. Historische Snapshots werden nicht neu geschrieben. Um auf die alte Anwendung zurückzustufen, stellen Sie das MongoDB-Backup wieder her.

#### Funktion 04: Paginierung der Vorlagen

Die Galerie führt Paginierung, Sortierung und Suche jetzt in MongoDB durch. Das funktioniert ohne jede Vorbereitung; bei Tausenden von Vorlagen können Sie dennoch diese Indizes hinzufügen, um die Geschwindigkeit zu erhalten (kann bedenkenlos erneut ausgeführt werden, `mongo`/`sharelatex` = Namen Ihres Containers und Ihrer Datenbank):

```bash
docker exec mongo mongosh sharelatex --quiet --eval '
db.templates.createIndex({category:1,lastUpdated:-1},{name:"category_1_lastUpdated_-1",background:true});
db.templates.createIndex({lastUpdated:-1},{name:"lastUpdated_-1",background:true});
db.templates.createIndex({category:1,name:1},{name:"category_1_name_1_ci",collation:{locale:"en",strength:2},background:true});
db.templates.createIndex({name:1},{name:"name_1_ci",collation:{locale:"en",strength:2},background:true});
'
```

Behalten Sie die `collation` bei den beiden `*_ci`-Indizes genau wie angegeben bei – die Galerie fragt mit derselben Collation ab, und MongoDB verwendet nur einen passenden Index.
