## S3-Migration

<Info>

Diese Anleitung gilt für v5.x und neuer. Wenn Sie diese Anleitung für eine ältere Version verwenden, nutzen Sie bitte `sharelatex` statt `overleaf` in Pfadnamen und das Präfix `SHARELATEX_` statt `OVERLEAF_` für Umgebungsvariablen.

</Info>

<Check>

**Wir freuen uns auf Ihre Rückmeldung!** Wenn Sie uns mitteilen möchten, wie viele Dateien Sie migriert haben, wie groß ihr Gesamtvolumen war und wie lange die Migration gedauert hat, schreiben Sie eine E-Mail an [`ayaka-notes@outlook.com`](mailto:support@overleaf.com) .

</Check>

Diese Anleitung führt Sie durch die Migration von der Speicherung auf der Festplatte zu einem S3-kompatiblen Objektspeicher. Sie verweist auf Abschnitte des Einführungsdokuments zum [S3-Setup](/de/on-premises/configuration/overleaf-toolkit/s3).

### Voraussetzungen

* Ein S3-kompatibler Objektspeicher, mit dem kommuniziert werden kann; Optionen finden Sie unter [#s3-setup](/de/on-premises/configuration/overleaf-toolkit/s3#s3-setup  "mention")
* Freier Speicherplatz für die Migration der vorhandenen Daten, etwa in Höhe der aktuellen Größe auf der Festplatte
* Ein Wartungsfenster für die eigentliche Migration
* Ein vollständiges Backup einschließlich der Konfiguration, um eine Wiederherstellung zu ermöglichen

### Benötigten Speicherplatz für die Migration abschätzen

Mit `du` können wir die aktuelle Festplattennutzung berechnen:

```shell
docker exec sharelatex \
  du --human-readable --max-depth=0 /var/lib/overleaf/data/user_files

docker exec sharelatex \
  du --human-readable --max-depth=0 /var/lib/overleaf/data/template_files
```

Falls auf dem aktuellen Server nicht genügend Speicherplatz verfügbar ist, versuchen Sie, eine weitere Festplatte an den Server anzuschließen.

<Info>

Die History-Verzeichnisse haben bereits das richtige Layout. Sie können direkt aus dem per Bind-Mount eingebundenen Quellordner hochladen, wofür kein zusätzlicher Speicherplatz erforderlich ist.

</Info>

### Migrationsschritte

#### Schritt 0: Instanz herunterfahren

Wir müssen sicherstellen, dass alle Benutzer- und Vorlagendateien migriert werden. Am besten fahren Sie die Instanz herunter, um keine neu hochgeladenen Dateien zu verpassen.

Das Vorgehen zum Herunterfahren finden Sie in unserer Anleitung zum Erstellen eines konsistenten Backups.

#### Schritt 1: Verzeichnislayout umschreiben

Wir müssen das Verzeichnislayout der Projektdateien umschreiben, um sie in S3 hochzuladen. Das Verzeichnislayout für den lokalen Speicher im Filestore ist `<project-id>_<file-id>`, das Verzeichnislayout in S3 ist `<project-id>/<file-id>`.

Im Folgenden wird `/srv/overleaf-s3-migration` zum Speichern der Dateien im neuen Verzeichnislayout verwendet.

Zum Umschreiben des Layouts können wir `tar` verwenden:

```shell
mkdir -p /srv/overleaf-s3-migration/user_files \
         /srv/overleaf-s3-migration/template_files
docker exec sharelatex \
  tar --create --directory /var/lib/overleaf/data/user_files . \
| tar --extract --directory /srv/overleaf-s3-migration/user_files \
  --transform=sx_x/x
docker exec sharelatex \
  tar --create --directory /var/lib/overleaf/data/template_files . \
| tar --extract --directory /srv/overleaf-s3-migration/template_files \
  --transform=sx_x/xg
```

#### Schritt 2: Dateien hochladen

Je nach Vorliebe können Sie den S3-Client minio mc oder die aws cli verwenden, um die Dateien in Ihren S3-kompatiblen Objektspeicher hochzuladen.

**aws cli**

<Info>

* Ersetzen Sie hier `overleaf-user-files`, `overleaf-template-files`, `overleaf-project-blobs` und `overleaf-chunks` durch die Namen Ihrer S3-Buckets.
* Ersetzen Sie außerdem `/srv/overleaf-bind-mount` durch den lokalen Pfad des Bind-Mounts `/var/lib/overleaf`. Standardmäßig ist dies `~/overleaf_data` bei einem docker-compose.yml-Deployment und `<toolkit-checkout>/data/overleaf` bei Verwendung des Toolkits.

</Info>

```shell wrap
aws s3 sync /srv/overleaf-s3-migration/user_files s3://overleaf-user-files
aws s3 sync /srv/overleaf-s3-migration/template_files s3://overleaf-template-files

aws s3 sync /srv/overleaf-bind-mount/data/history/overleaf-project-blobs s3://overleaf-project-blobs
aws s3 sync /srv/overleaf-bind-mount/data/history/overleaf-chunks s3://overleaf-chunks
```

**minio mc**

Wir verwenden hier den Server-Alias "s3"; Sie haben möglicherweise einen anderen Namen gewählt.

```shell wrap
mc mirror /srv/overleaf-s3-migration/user_files s3/overleaf-user-files
mc mirror /srv/overleaf-s3-migration/template_files s3/overleaf-template-files

mc mirror /srv/overleaf-bind-mount/data/history/overleaf-project-blobs s3/overleaf-project-blobs
mc mirror /srv/overleaf-bind-mount/data/history/overleaf-chunks s3/overleaf-chunks
```

#### Schritt 3: Instanz mit S3 starten

Fügen Sie Ihrer Konfiguration alle S3-bezogenen Variablen hinzu, wie im Abschnitt [Übersicht der Variablen](/de/on-premises/configuration/overleaf-toolkit/s3#overview-of-variables) der Einrichtungsanleitung für [S3](https://docs.overleaf.com/on-premises/configuration/overleaf-toolkit/s3) beschrieben.

Bei Docker-Compose-Deployments können Sie außerdem den Bind-Mount für das Datenverzeichnis aus dem Abschnitt volumes entfernen.

<Check>

Bitte behalten Sie den [Bind-Mount einer Scratch-Disk für temporäre Dateien](/de/on-premises/support/troubleshooting#running-overleaf-with-an-nfs-filesystem) bei.

</Check>

Sie können die Instanz jetzt starten und die Migration überprüfen:

* Binärdateien können im Editor in der Vorschau angezeigt werden
* Ein PDF mit Bildern kann kompiliert werden
* Neue Dateien können hochgeladen werden

### Rollback

Sie können die Migration sauber rückgängig machen, indem Sie die Schritte umkehren:

1. Fahren Sie die Instanz herunter
2. Spiegeln Sie die Dateien zurück, indem Sie Quelle und Ziel vertauschen
3. Schreiben Sie die neuen Dateien mit einer umgekehrten `transform` zurück in das lokale Verzeichnis
4. Starten Sie die Instanz mit der alten Konfiguration neu

```shell wrap
# When using aws cli
aws s3 sync s3://overleaf-user-files /srv/overleaf-s3-migration/user_files
aws s3 sync s3://overleaf-template-files /srv/overleaf-s3-migration/template_files
aws s3 sync s3://overleaf-project-blobs /srv/overleaf-bind-mount/data/history/overleaf-project-blobs
aws s3 sync s3://overleaf-chunks /srv/overleaf-bind-mount/data/history/overleaf-chunks

# When using minio mc
mc mirror s3/overleaf-user-files /srv/overleaf-s3-migration/user_files
mc mirror s3/overleaf-template-files /srv/overleaf-s3-migration/template_files
mc mirror s3/overleaf-project-blobs /srv/overleaf-bind-mount/data/history/overleaf-project-blobs
mc mirror s3/overleaf-chunks /srv/overleaf-bind-mount/data/history/overleaf-chunks
```

```shell
# Write files into local Server CE/Server Pro
tar --create --directory /srv/overleaf-s3-migration/user_files . \
| docker exec --interactive sharelatex \
    tar \
      --extract \
      --keep-old-files \
      --directory /var/lib/overleaf/data/user_files \
      --transform=sx./xx --transform=sx/x_x \
      --wildcards '*/*/*'

tar --create --directory /srv/overleaf-s3-migration/template_files . \
| docker exec --interactive sharelatex \
    tar \
      --extract \
      --keep-old-files \
      --directory /var/lib/overleaf/data/template_files \
      --transform=sx./xx --transform=sx/x_xg \
      --wildcards '*/*/*/*/pdf-converted-cache/*' \
      --wildcards '*/*/*/*/pdf' \
      --wildcards '*/*/*/*/zip'
```

<Info>

Die erste Transformation entfernt den Ordner der obersten Ebene. Die zweite Transformation ändert das Verzeichnislayout in ein flaches Layout. Die Wildcards stellen sicher, dass nur Dateien extrahiert werden, nicht deren übergeordnete (Projekt-)Ordner.

</Info>
