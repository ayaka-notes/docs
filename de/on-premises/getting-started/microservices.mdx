Die empfohlene Methode zur Bereitstellung und Verwaltung von Overleaf Server CE- und Overleaf Pro-Instanzen ist die Verwendung des Toolkits.

Das Toolkit vereinfacht die Erstellung Ihrer Overleaf-Instanz durch einige eigene Skripte, die die Orchestrierung der benötigten Microservices abstrahieren. Führen Sie einfach das mitgelieferte Initialisierungsskript aus, geben Sie einige Konfigurationsoptionen wie Ihre Pfade für persistenten Speicher an, und das Toolkit kümmert sich um die Bereitstellung und Verbindung der Microservices, aus denen Ihre Overleaf Server CE- oder Pro-Instanz besteht.

So können Sie sich darauf konzentrieren, die Benutzererfahrung anzupassen und die spezifischen Funktionen Ihrer On-Premises-Instanz umzusetzen. Das Toolkit übernimmt die gesamte Komplexität im Hintergrund und ermöglicht eine vereinfachte Bereitstellung Ihrer Overleaf-Instanz.

<Info>

Aus historischen Gründen heißt der Overleaf-Hauptcontainer `sharelatex` und basiert auf dem Docker-Image `sharelatex/sharelatex`. Das liegt daran, dass die Technologie auf der Codebasis von ShareLaTeX beruht, das mit Overleaf zusammengeführt wurde. Weitere Details finden Sie in [diesem Blogbeitrag](https://www.overleaf.com/blog/518-exciting-news-sharelatex-is-joining-overleaf). Irgendwann in der Zukunft wird er umbenannt, um dem Namensschema von Overleaf zu entsprechen.

</Info>

#### Architektur

Im Overleaf-Container läuft die Software als eine Reihe von Microservices, die von `runit` verwaltet werden. Einige der interessanteren Dateien im Container sind:

* `/etc/service/`: Initialisierungsdateien für die Microservices.
* `/var/log/overleaf/`: Logs für jeden Microservice.
* `/overleaf/services/`: Code für die verschiedenen Microservices.
* `/var/lib/overleaf/`: der Mount-Point für persistente Daten (entspricht dem auf dem Host durch `OVERLEAF_DATA_PATH` angegebenen Verzeichnis).

#### Die MongoDB- und Redis-Container

Overleaf ist von zwei externen Datenbanken abhängig: MongoDB und Redis. Standardmäßig stellt das Toolkit zusätzlich zum Overleaf-Container für jede dieser Datenbanken einen Container bereit, also insgesamt drei Docker-Container.

<Info>

Wenn Sie sich lieber mit einer bestehenden MongoDB- oder Redis-Instanz verbinden möchten, können Sie dies über die entsprechenden Einstellungen in der Konfigurationsdatei [overleaf.rc](/de/on-premises/configuration/overleaf-toolkit/files-and-locations#the-overleaf.rc-file) tun.

</Info>

#### Editor und Kompiliervorgang

Dieser Abschnitt bietet einen groben Überblick über die Verarbeitung von Dokumenten und den Kompiliervorgang.

<Info>

Diese Seite beschreibt den Kompiliervorgang mit Sandboxed Compiles, wie er nur in Overleaf Pro verfügbar ist. In Server CE verwendet der Kompiliervorgang einfache Unterprozesse – ersetzen Sie die Punkte, die sich auf einen **Container** beziehen, durch einen einzigen Punkt **Kompilierung im Unterprozess ausführen**.

</Info>

Komponenten / Akteure:

* `user` — Eine Person, die die Anwendung nutzt
* `editor` — Die im Browser laufende Client-Anwendung
* `clsi` — Der Microservice zum Kompilieren von PDFs
* `document-updater` — Der Microservice zur Verarbeitung von Dokumentaktualisierungen
* `filestore` — Der Microservice für die Verwaltung von Binärdateien
* `real-time` — Der Microservice zur Verarbeitung von WebSockets
* `web` — Der (nicht ganz so) Micro-Service zur Verarbeitung von API-Anfragen

**Redis-Caching**

* **user**: lädt die Editor-Seite
* **editor**: öffnet einen WebSocket
* **editor**: sendet über den WebSocket eine Anfrage zum Öffnen eines Dokuments
  * **real-time** -> **document-updater**: Dokument wird aus MongoDB in Redis geladen
* **editor**: sendet eine Dokumentaktualisierung über den WebSocket
  * **real-time** -> **document-updater**: Dokument wird in Redis aktualisiert
* **editor**: sendet weitere Kompilieranfragen
  * Nach Ablauf von 5 Minuten seit dem letzten Flush (pro Dokument):
    * **document-updater**: schreibt das Dokument aus Redis in MongoDB
* **editor**: sendet weitere Aktualisierungen
  * alle 100 Aktualisierungen (pro Dokument):
    * **document-updater**: schreibt den Dokumentverlauf aus Redis in MongoDB
* **user**: verlässt den Editor/schließt den Browser-Tab
  * 5 Minuten später
    * **real-time**: prüft, ob andere Mitwirkende vorhanden sind; falls nicht:
      * **real-time** -> **document-updater**: schreibt die Dokumente aus Redis in MongoDB

**Lesen aus MongoDB in Redis**

* **document-updater** -> **web** -> **docstore**: Lesen aus MongoDB

**Schreiben aus Redis in MongoDB**

* **document-updater** -> **web** -> **docstore**: Schreiben in MongoDB

**Kompilieren — Sync-Modus "full"**

* **editor**: sendet eine Kompilieranfrage mit dem Sync-Modus "full"
* **web** -> **document-updater**: alle Dokumente werden aus Redis in MongoDB geschrieben
* **web** -> **docstore**: alle Dokumente werden aus MongoDB heruntergeladen
* **web** -> **clsi**: die Kompilieranfrage wird an `clsi` gesendet, einschließlich:
  * des Sync-Modus
  * eines Hashs des Dateibaums -> der "Projektzustand"
  * aller Dokumente mit ihrem Inhalt -> unterliegt der Grenze von 7 MB für den Request-Body
  * URLs der Binärdateien zum separaten Herunterladen
* **clsi**: prüft den Zustand auf der Festplatte anhand des Sync-Modus und des "Projektzustands"
  * es handelt sich um einen vollständigen Sync, daher kann der bisherige Zustand auf der Festplatte ignoriert werden
* **clsi**: bereinigt das Kompilierverzeichnis
* **clsi**: schreibt alle Dokumente in das Kompilierverzeichnis
* **clsi**: schreibt alle Binärdateien in das Kompilierverzeichnis
  * `clsi` kopiert die Dateien aus einem lokalen Cache pro Projekt
  * bei einem Cache-Miss:
    * **clsi** -> **filestore**: lädt die Dateien herunter
* **clsi**: schreibt den "Projektzustand"
* **clsi**: stellt sicher, dass ein Docker-Container mit der gewünschten Konfiguration existiert
  * erstellt die Container-Optionen, einschließlich der TeX Live-Version
  * bildet einen Hash der Optionen
  * Containername: `project-<project-id>-<user-id>-<hash>`
* **clsi**: startet den Container und streamt stdout/stderr in den Speicher -> Grenze 2 MB
* **clsi**: lässt den gestoppten Container bestehen -> wird nach 24 Stunden bereinigt
* **clsi**: schreibt stdout/stderr auf die Festplatte
* **clsi**: kopiert die Ausgabedateien in ein eindeutiges Ausgabeverzeichnis
  * die Build-ID besteht aus 8 zufälligen Bytes plus einem Zeitstempel mit Millisekunden-Genauigkeit
  * löscht alle Build-Ordner bis auf die letzten 3 (anonym) / den letzten 1 (angemeldeter Benutzer)
* **clsi**: Kompilierung fehlgeschlagen/Zeitüberschreitung
  * löscht den Kompilier-Cache – er könnte unvollständige Dateien enthalten bzw. beschädigt sein
* **editor**: lädt output.log und output.pdf herunter

**Kompilieren — Sync-Modus "incremental"**

* **editor**: sendet eine Kompilieranfrage mit dem Sync-Modus "incremental"
* **web** -> **document-updater**: holt alle Dokumente aus Redis
  * der Hash des "Projektzustands" wird ebenfalls in Redis gespeichert
  * **web** sendet den Hash des Dateibaums an `document-updater`, und `document-updater` kann die inkrementelle Kompilierung bei einer Abweichung in eine vollständige Kompilierung umwandeln
    * siehe den Kompiliervorgang bei einer vom Editor angeforderten "full"-Kompilierung
* **web** -> **clsi**: die Kompilieranfrage wird an `clsi` gesendet, einschließlich:
  * des Sync-Modus
  * eines Hashs des Dateibaums -> der "Projektzustand"
  * aller Dokumente aus Redis mit ihrem Inhalt -> unterliegt der Grenze von 7 MB für den Request-Body
  * keiner Binärdateien
* **clsi**: prüft den Zustand auf der Festplatte anhand des Sync-Modus und des "Projektzustands"
  * es handelt sich um einen inkrementellen Sync, daher muss der "Projektzustand" übereinstimmen
  * bei einer Abweichung: Antwort mit 409, web wiederholt den Vorgang mit "full"-Sync
    * siehe den Kompiliervorgang bei einer vom Editor angeforderten "full"-Kompilierung
* **clsi**: schreibt die aktualisierten Dokumente in das Kompilierverzeichnis
* **clsi**: stellt sicher, dass ein Docker-Container mit der gewünschten Konfiguration existiert
  * erstellt die Container-Optionen, einschließlich der TeX Live-Version
  * bildet einen Hash der Optionen
  * Containername: `project-<project-id>-<user-id>-<hash>`
* **clsi**: startet den Container und streamt stdout/stderr in den Speicher -> Grenze 2 MB
* **clsi**: lässt den gestoppten Container bestehen -> wird nach 24 Stunden bereinigt
* **clsi**: schreibt stdout/stderr auf die Festplatte
* **clsi**: kopiert die Ausgabedateien in ein eindeutiges Ausgabeverzeichnis
  * die Build-ID besteht aus 8 zufälligen Bytes plus einem Zeitstempel mit Millisekunden-Genauigkeit
  * löscht alle Build-Ordner bis auf die letzten 3 (anonym) / den letzten 1 (angemeldeter Benutzer)
* **clsi**: Kompilierung fehlgeschlagen/Zeitüberschreitung
  * löscht den Kompilier-Cache – er könnte unvollständige Dateien enthalten bzw. beschädigt sein
* **editor**: lädt output.log und output.pdf herunter

**Kompilieren — Wechsel zwischen den Modi**

* **editor**: stellt einen Kompilierfehler fest, die nächste Kompilierung ist eine "full"-Kompilierung
* **editor**: stellt eine erfolgreiche Kompilierung fest, die nächste Kompilierung ist eine "incremental"-Kompilierung
