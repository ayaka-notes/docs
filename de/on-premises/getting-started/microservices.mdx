Die empfohlene Methode zur Bereitstellung und Verwaltung von Overleaf-Server-CE- und Overleaf-Pro-Instanzen ist die Verwendung des Toolkits.

Das Toolkit vereinfacht die Erstellung Ihrer Overleaf-Instanz durch einige eigene Skripte, die die Orchestrierung der benötigten Microservices abstrahieren. Führen Sie einfach das mitgelieferte Initialisierungsskript aus, geben Sie einige Konfigurationsoptionen wie Ihre Pfade für persistenten Speicher an, und das Toolkit kümmert sich um die Bereitstellung und Verbindung der Microservices, aus denen Ihre Overleaf-Server-CE- oder Pro-Instanz besteht.

So können Sie sich darauf konzentrieren, die Benutzererfahrung anzupassen und die spezifischen Funktionen Ihrer On-Premises-Instanz umzusetzen. Das Toolkit übernimmt im Hintergrund die gesamte Komplexität und ermöglicht so eine vereinfachte Bereitstellung Ihrer Overleaf-Instanz.

<Info>

Aus historischen Gründen heißt der Haupt-Container von Overleaf `sharelatex` und basiert auf dem Docker-Image `sharelatex/sharelatex`. Das liegt daran, dass die Technologie auf der Codebasis von ShareLaTeX beruht, das mit Overleaf zusammengeführt wurde. Weitere Details finden Sie in [diesem Blogbeitrag](https://www.overleaf.com/blog/518-exciting-news-sharelatex-is-joining-overleaf). Zu einem späteren Zeitpunkt wird er umbenannt, um dem Namensschema von Overleaf zu entsprechen.

</Info>

#### Architektur

Innerhalb des Overleaf-Containers läuft die Software als eine Reihe von Microservices, die von `runit` verwaltet werden. Einige der interessanteren Dateien im Container sind:

* `/etc/service/`: Initialisierungsdateien für die Microservices.
* `/var/log/overleaf/`: Logs für jeden Microservice.
* `/overleaf/services/`: Code der verschiedenen Microservices.
* `/var/lib/overleaf/`: der Mount-Point für persistente Daten (entspricht dem durch `OVERLEAF_DATA_PATH` angegebenen Verzeichnis auf dem Host).

#### Die MongoDB- und Redis-Container

Overleaf ist von zwei externen Datenbanken abhängig: MongoDB und Redis. Standardmäßig stellt das Toolkit zusätzlich zum Overleaf-Container für jede dieser Datenbanken einen Container bereit, insgesamt also drei Docker-Container.

<Info>

Wenn Sie lieber eine Verbindung zu einer bestehenden MongoDB- oder Redis-Instanz herstellen möchten, können Sie dies über die entsprechenden Einstellungen in der Konfigurationsdatei [overleaf.rc](/de/on-premises/configuration/overleaf-toolkit/files-and-locations#the-overleaf.rc-file) tun.

</Info>

#### Editor und Kompiliervorgang

Dieser Abschnitt gibt einen groben Überblick über die Verarbeitung von Dokumenten und den Kompiliervorgang.

<Info>

Diese Seite beschreibt den Kompiliervorgang mit Sandboxed Compiles, wie er nur in Overleaf Pro verfügbar ist. In Server CE verwendet der Kompiliervorgang einfache Unterprozesse – ersetzen Sie die Punkte, die sich auf einen **Container** beziehen, durch einen einzigen Punkt **Kompilierung im Unterprozess ausführen**.

</Info>

Komponenten / Akteure:

* `user` — Ein Nutzer der Anwendung
* `editor` — Die im Browser laufende Client-Anwendung
* `clsi` — Der Microservice zum Kompilieren von PDFs
* `document-updater` — Der Microservice zur Verarbeitung von Dokumentaktualisierungen
* `filestore` — Der Microservice für Binärdateien
* `real-time` — Der Microservice für Web-Sockets
* `web` — Der (nicht ganz so) Micro-Service für API-Anfragen

**Redis-Caching**

* **user**: lädt die Editor-Seite
* **editor**: öffnet einen Web-Socket
* **editor**: sendet über den Web-Socket eine Anfrage zum Öffnen eines Dokuments
  * **real-time** -> **document-updater**: Dokument wird aus MongoDB in Redis geladen
* **editor**: sendet eine Dokumentaktualisierung über den Web-Socket
  * **real-time** -> **document-updater**: Dokument wird in Redis aktualisiert
* **editor**: sendet weitere Kompilieranfragen
  * Nach Ablauf von 5 Minuten seit dem letzten Flush (pro Dokument):
    * **document-updater**: schreibt das Dokument von Redis nach MongoDB zurück
* **editor**: sendet weitere Aktualisierungen
  * alle 100 Aktualisierungen (pro Dokument):
    * **document-updater**: schreibt den Dokumentverlauf von Redis nach MongoDB zurück
* **user**: verlässt den Editor/schließt den Browser-Tab
  * 5 Minuten später
    * **real-time**: prüft auf weitere Mitarbeitende; falls keine vorhanden sind:
      * **real-time** -> **document-updater**: schreibt die Dokumente von Redis nach MongoDB zurück

**Lesen aus MongoDB in Redis**

* **document-updater** -> **web** -> **docstore**: Lesen aus MongoDB

**Zurückschreiben von Redis nach MongoDB**

* **document-updater** -> **web** -> **docstore**: Schreiben in MongoDB

**Kompilierung — Sync-Modus „full“**

* **editor**: sendet eine Kompilieranfrage mit Sync-Modus "full"
* **web** -> **document-updater**: alle Dokumente werden von Redis nach MongoDB zurückgeschrieben
* **web** -> **docstore**: alle Dokumente werden aus MongoDB heruntergeladen
* **web** -> **clsi**: Kompilieranfrage wird an `clsi` gesendet, einschließlich:
  * des Sync-Modus
  * eines Hashs des Dateibaums -> der „Projektzustand“
  * aller Dokumente mit ihrem Inhalt -> unterliegt der Begrenzung des Request-Bodys auf 7 MB
  * der URLs der Binärdateien zum separaten Herunterladen
* **clsi**: prüft den Zustand auf der Festplatte anhand von Sync-Modus und „Projektzustand“
  * dies ist eine vollständige Synchronisierung, daher kann der vorherige Zustand auf der Festplatte ignoriert werden
* **clsi**: bereinigt das Kompilierverzeichnis
* **clsi**: schreibt alle Dokumente in das Kompilierverzeichnis
* **clsi**: schreibt alle Binärdateien in das Kompilierverzeichnis
  * `clsi` kopiert die Dateien aus einem lokalen Cache pro Projekt
  * bei einem Cache-Miss:
    * **clsi** -> **filestore**: lädt die Dateien herunter
* **clsi**: schreibt den „Projektzustand“
* **clsi**: stellt sicher, dass ein Docker-Container mit der gewünschten Konfiguration existiert
  * erstellt die Container-Optionen, einschließlich der TeX-Live-Version
  * hasht die Optionen
  * Container-Name: `project-<project-id>-<user-id>-<hash>`
* **clsi**: startet den Container und streamt stdout/stderr in den Speicher -> Limit 2 MB
* **clsi**: lässt den gestoppten Container bestehen -> wird nach 24 Stunden bereinigt
* **clsi**: schreibt stdout/stderr auf die Festplatte
* **clsi**: kopiert die Ausgabedateien in ein eindeutiges Ausgabeverzeichnis
  * Build-ID aus 8 Zufallsbytes plus Zeitstempel mit Millisekundengenauigkeit
  * löscht alle Build-Ordner außer den letzten 3 (anonym) / dem letzten (angemeldeter Nutzer)
* **clsi**: Kompilierung fehlgeschlagen/Timeout
  * löscht den Kompilier-Cache — er kann unvollständige Dateien/einen beschädigten Cache enthalten
* **editor**: lädt output.log und output.pdf herunter

**Kompilierung — Sync-Modus „incremental“**

* **editor**: sendet eine Kompilieranfrage mit Sync-Modus "incremental"
* **web** -> **document-updater**: holt alle Dokumente aus Redis
  * der Hash des „Projektzustands“ wird ebenfalls in Redis gespeichert
  * **web** sendet den Hash des Dateibaums an `document-updater`, und `document-updater` kann die inkrementelle Kompilierung bei einer Abweichung in eine vollständige Kompilierung umwandeln
    * siehe Kompiliervorgang bei einer vom Editor angeforderten „full“-Kompilierung
* **web** -> **clsi**: Kompilieranfrage wird an `clsi` gesendet, einschließlich:
  * des Sync-Modus
  * eines Hashs des Dateibaums -> der „Projektzustand“
  * aller Dokumente aus Redis mit ihrem Inhalt -> unterliegt der Begrenzung des Request-Bodys auf 7 MB
  * keiner Binärdateien
* **clsi**: prüft den Zustand auf der Festplatte anhand von Sync-Modus und „Projektzustand“
  * dies ist eine inkrementelle Synchronisierung, daher muss der „Projektzustand“ übereinstimmen
  * bei Abweichung: Antwort mit 409, web wiederholt den Vorgang mit „full“-Synchronisierung
    * siehe Kompiliervorgang bei einer vom Editor angeforderten „full“-Kompilierung
* **clsi**: schreibt die aktualisierten Dokumente in das Kompilierverzeichnis
* **clsi**: stellt sicher, dass ein Docker-Container mit der gewünschten Konfiguration existiert
  * erstellt die Container-Optionen, einschließlich der TeX-Live-Version
  * hasht die Optionen
  * Container-Name: `project-<project-id>-<user-id>-<hash>`
* **clsi**: startet den Container und streamt stdout/stderr in den Speicher -> Limit 2 MB
* **clsi**: lässt den gestoppten Container bestehen -> wird nach 24 Stunden bereinigt
* **clsi**: schreibt stdout/stderr auf die Festplatte
* **clsi**: kopiert die Ausgabedateien in ein eindeutiges Ausgabeverzeichnis
  * Build-ID aus 8 Zufallsbytes plus Zeitstempel mit Millisekundengenauigkeit
  * löscht alle Build-Ordner außer den letzten 3 (anonym) / dem letzten (angemeldeter Nutzer)
* **clsi**: Kompilierung fehlgeschlagen/Timeout
  * löscht den Kompilier-Cache — er kann unvollständige Dateien/einen beschädigten Cache enthalten
* **editor**: lädt output.log und output.pdf herunter

**Kompilierung — Wechsel zwischen den Modi**

* **editor**: stellt eine fehlgeschlagene Kompilierung fest, die nächste Kompilierung ist eine „full“-Kompilierung
* **editor**: stellt eine erfolgreiche Kompilierung fest, die nächste Kompilierung ist eine „incremental“-Kompilierung
