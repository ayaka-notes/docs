Ayakaleaf Pro benötigt:

* **MongoDB 8** als **Replikatset** (es verwendet Transaktionen). Drei auf drei Knoten verteilte Mitglieder überstehen den Ausfall eines Knotens; ein einzelnes Mitglied funktioniert ebenfalls.
* **Redis 7**, einen Server mit AOF-Persistenz. Redis enthält die noch nicht in MongoDB geschriebenen Bearbeitungen, die Sitzungen und die Nachrichten zwischen den Overleaf-Diensten. Overleaf verbindet sich mit einem einzelnen Redis-Server: Sentinel und Redis Cluster werden nicht unterstützt.

<Info>

Sie können stattdessen verwaltete Dienste verwenden, etwa MongoDB Atlas oder das Redis Ihrer Cloud. Überspringen Sie diese Seite und setzen Sie `OVERLEAF_MONGO_URL` und `OVERLEAF_REDIS_HOST` in [Schritt 4](/de/on-premises/installation/using-kubernetes/4.-personalizing-your-instance) auf diese Dienste.

</Info>

<Steps>
<Step title="MongoDB">
```yaml title="10-mongo.yaml" wrap
apiVersion: v1
kind: Service
metadata:
  name: mongo
  namespace: overleaf
spec:
  clusterIP: None                 # headless: gives mongo-0.mongo, mongo-1.mongo, ...
  publishNotReadyAddresses: true  # members must resolve each other before the set is initiated
  selector:
    app: mongo
  ports:
    - name: mongo
      port: 27017
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mongo
  namespace: overleaf
spec:
  serviceName: mongo
  replicas: 3
  selector:
    matchLabels:
      app: mongo
  template:
    metadata:
      labels:
        app: mongo
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app: mongo
              topologyKey: kubernetes.io/hostname
      containers:
        - name: mongo
          image: mongo:8.0
          args:
            - --replSet=overleaf
            - --bind_ip_all
            - --wiredTigerCacheSizeGB=0.25   # default is 50% of (RAM - 1 GB); size it for your nodes
          # env:
          #   - name: GLIBC_TUNABLES        # only on kernel 6.19+ (SERVER-121912)
          #     value: glibc.pthread.rseq=1
          ports:
            - containerPort: 27017
          readinessProbe:
            tcpSocket:
              port: 27017
          resources:
            requests:
              cpu: 100m
              memory: 384Mi
            limits:
              memory: 768Mi
          volumeMounts:
            - name: data
              mountPath: /data/db
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 5Gi
---
# Initiates the replica set once. Safe to re-run: it does nothing when the set exists.
apiVersion: batch/v1
kind: Job
metadata:
  name: mongo-init-replica-set
  namespace: overleaf
spec:
  backoffLimit: 20
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: init
          image: mongo:8.0
          command:
            - mongosh
            - --quiet
            - --host=mongo-0.mongo
            - --eval
            - |
              try {
                rs.status()
                print('replica set already initiated')
              } catch (e) {
                rs.initiate({
                  _id: 'overleaf',
                  members: [
                    { _id: 0, host: 'mongo-0.mongo.overleaf.svc.cluster.local:27017' },
                    { _id: 1, host: 'mongo-1.mongo.overleaf.svc.cluster.local:27017' },
                    { _id: 2, host: 'mongo-2.mongo.overleaf.svc.cluster.local:27017' },
                  ],
                })
              }
```

```bash
kubectl apply -f 10-mongo.yaml
kubectl -n overleaf rollout status statefulset/mongo
kubectl -n overleaf wait --for=condition=complete job/mongo-init-replica-set --timeout=5m
kubectl -n overleaf exec mongo-0 -- mongosh --quiet --eval 'rs.status().members.map(m => m.name + " " + m.stateStr)'
```

Nach einigen Sekunden sollte ein Mitglied `PRIMARY` und die anderen `SECONDARY` sein. Der Job versucht es erneut, bis alle Mitglieder antworten, daher sind einige fehlgeschlagene Job-Pods normal.

* Der Headless Service benötigt `publishNotReadyAddresses: true`: Die Mitglieder müssen sich gegenseitig über ihren Namen finden, bevor das Replikatset existiert.
* Die Mitglieder werden mit ihren stabilen Namen (`mongo-0.mongo.overleaf.svc.cluster.local`) hinzugefügt, nie mit Pod-IPs, die sich bei jedem Neustart ändern.
* Für ein einzelnes Mitglied setzen Sie `replicas: 1` und behalten im Job nur `mongo-0`.
</Step>

<Step title="Redis">
```yaml title="20-redis.yaml" wrap
apiVersion: v1
kind: Service
metadata:
  name: redis
  namespace: overleaf
spec:
  selector:
    app: redis
  ports:
    - name: redis
      port: 6379
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
  namespace: overleaf
spec:
  serviceName: redis
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis
          image: redis:7.4
          args: [--appendonly, "yes"]
          ports:
            - containerPort: 6379
          readinessProbe:
            tcpSocket:
              port: 6379
          resources:
            requests:
              cpu: 50m
              memory: 128Mi
            limits:
              memory: 512Mi
          volumeMounts:
            - name: data
              mountPath: /data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 2Gi
```

```bash
kubectl apply -f 20-redis.yaml
kubectl -n overleaf rollout status statefulset/redis
```
</Step>

### Q\&A

<Accordion title="MongoDB 8 stürzt auf einem aktuellen Kernel beim Start ab. Warum?">

<strong>Antwort:</strong> MongoDB 8 schlägt unter Linux-Kernel 6.19 und neuer fehl ([SERVER-121912](https://jira.mongodb.org/browse/SERVER-121912)). Kommentieren Sie die Umgebungsvariable `GLIBC_TUNABLES` in `10-mongo.yaml` ein.

</Accordion>

<Accordion title="Wie viel Arbeitsspeicher benötigt MongoDB?">

<strong>Antwort:</strong> Standardmäßig verwendet MongoDB die Hälfte des Knotenspeichers abzüglich 1 GB für seinen Cache, und es sieht den Speicher des Knotens, nicht das Limit des Pods. Setzen Sie `--wiredTigerCacheSizeGB` passend zu Ihren Knoten; mit `0.25` blieb jedes Mitglied auf unseren Testknoten mit 4 GB bei etwa 200 bis 260 MiB.

</Accordion>
