### Den Administrator und ein erstes Projekt erstellen {#create-the-administrator-and-a-first-project}

Öffnen Sie [http://localhost:8080/launchpad](http://localhost:8080/launchpad) in Ihrem **Windows-Browser**, erstellen Sie das erste Administratorkonto und melden Sie sich an. Folgen Sie dann [6. Aufgaben nach der Installation](/de/on-premises/installation/using-docker-compose/linux/6.-post-installation-tasks) der Linux-Anleitung und verwenden Sie in deren Beispiel-URLs den Port `8080`.

### Die Kompilierung prüfen {#verify-compilation}

Eine funktionierende Anmeldeseite beweist nicht, dass die separaten Compiler-Container auf das WSL-Datenverzeichnis zugreifen können. Erstellen Sie ein leeres Projekt und kompilieren Sie diese `main.tex` mit **pdfLaTeX**:

```latex
\documentclass{article}
\begin{document}
Ayakaleaf Pro on Windows WSL 2.
\end{document}
```

Die PDF-Vorschau sollte den Text anzeigen. Wählen Sie für das basic-Image bei Bedarf in den Projekteinstellungen **TeX Live 2026 Basic** aus.

Wählen Sie **XeLaTeX** und testen Sie:

```latex
\documentclass{article}
\usepackage{fontspec}
\begin{document}
Ayakaleaf WSL XeLaTeX sandbox.
\end{document}
```

Beide Beispiele funktionieren mit basic. Verwenden Sie für chinesische Dokumente ein Image, das `ctex` und die erforderlichen Schriften enthält, etwa full, bevor Sie Folgendes mit **XeLaTeX** testen. Basic enthält sie nicht:

```latex
\documentclass{ctexart}
\begin{document}
你好，Ayakaleaf Pro。
\end{document}
```

Um die Verwendung der Sandbox zu bestätigen, führen Sie während der Kompilierung in **Ubuntu** Folgendes aus:

```bash
docker ps -a --filter ancestor=ghcr.io/ayaka-notes/texlive-basic:2026.1
bin/logs -f clsi
```

Verwenden Sie im Filter den Namen Ihres gewählten Images. Kurze Kompilierungen können beendet sein, bevor `docker ps` läuft; `-a` zeigt bis zur Bereinigung auch gestoppte Container an. Ein Compiler-Container sollte dieses Image und einen `/compile`-Bind-Mount aus dem WSL-Datenverzeichnis des Toolkit verwenden. Anwendungslogs allein ersetzen nicht die Prüfung des PDFs.

### Die Persistenz prüfen {#verify-persistence}

In **Ubuntu**, im Toolkit-Verzeichnis:

```bash
bin/stop
bin/start
```

Warten Sie auf die Anwendung, öffnen Sie das Projekt in Windows erneut und kompilieren Sie es noch einmal. Ihr Konto, der Quelltext und die Projektdateien sollten noch vorhanden sein. Die Live-Daten liegen standardmäßig in `~/ayakaleaf-toolkit/data/` innerhalb von Ubuntu. Bewahren Sie sowohl `config/` als auch `data/` auf; das Deinstallieren oder Abmelden der Ubuntu-Distribution kann sie löschen.

### Die Instanz verfügbar halten {#keep-the-instance-available}

Damit die Instanz läuft, müssen drei Dinge gegeben sein: Windows bleibt wach, Docker Desktop läuft, und die Container starten mit der Engine neu.

Aktivieren Sie in Docker Desktop unter **Settings → General** die Option **Start Docker Desktop when you sign in to your computer**, siehe [Docker Desktop settings](https://docs.docker.com/desktop/settings-and-maintenance/settings/). Dadurch startet Docker nach der Anmeldung, nicht vor der Anmeldung. Melden Sie sich nach einem Windows-Neustart an, warten Sie, bis Docker Desktop vollständig gestartet ist, öffnen Sie Ubuntu und prüfen Sie `docker ps` und die Website.

Der **Resource Saver** von Docker Desktop ist vom Windows-Energiesparmodus unabhängig. Er wird normalerweise nur aktiv, wenn keine Container laufen; die laufende Anwendung, MongoDB und Redis verhindern diesen Leerlaufzustand. Unter WSL 2 pausiert er die Docker-Engine, statt die gemeinsam genutzte WSL-VM herunterzufahren. Pausieren Sie Docker Desktop nicht manuell mit **Pause**, während Sie Benutzer bedienen. Sie müssen den Resource Saver nicht deaktivieren, nur um diesen Stack am Laufen zu halten; siehe [Dockers Dokumentation zum Resource Saver](https://docs.docker.com/desktop/use-desktop/resource-saver/).

Die Dienste des Toolkit verwenden `restart: always`. Prüfen Sie die tatsächliche Einstellung in **Ubuntu**:

```bash
docker inspect sharelatex mongo redis --format '{{.Name}} restart={{.HostConfig.RestartPolicy.Name}}'
```

Jeder Dienst sollte `always` melden. Sobald Docker läuft, kann es diese vorhandenen Container ohne erneutes `bin/up` neu starten. Ein manuell gestoppter Container bleibt gestoppt, bis Sie ihn starten oder die Engine neu starten; mit `always` kann ein Neustart der Engine ihn wieder starten. Siehe [Dockers Verhalten bei Restart-Richtlinien](https://docs.docker.com/engine/containers/start-containers-automatically/).

| Aktion | Auswirkung auf Ayakaleaf |
| --- | --- |
| Das Ubuntu-Terminal nach `bin/up -d` schließen | Die Container laufen im Hintergrund; das Terminal überwacht sie nicht. Halten Sie Docker Desktop und die WSL-Umgebung verfügbar |
| Das Fenster des Docker Dashboard schließen | Das Fenster kann geschlossen werden, während Docker Desktop im Infobereich weiterläuft |
| **Quit Docker Desktop** wählen | Stoppt die Engine und macht die Website nicht verfügbar; öffnen Sie Docker Desktop erneut, um sie wiederherzustellen |
| `wsl --shutdown` ausführen | Stoppt alle WSL-Distributionen und unterbricht das Docker-WSL-Backend; starten Sie Docker Desktop neu und öffnen Sie Ubuntu erneut |
| Windows in den Energiesparmodus oder Ruhezustand versetzen oder herunterfahren | Der Dienst ist nicht verfügbar; ob nur der Bildschirm an- oder ausgeschaltet bleibt, ändert daran nichts |
| `bin/stop` ausführen | Stoppt die Instanz und behält ihre Daten; verwenden Sie `bin/start`, um fortzufahren |

Für den Dauerbetrieb im Netzbetrieb öffnen Sie in Windows 11 **Einstellungen → System → Energie & Akku → Timeouts für Bildschirm, Energiesparmodus und Ruhezustand** (manche Versionen zeigen **Energie** oder **Bildschirm und Energiesparmodus**). Setzen Sie das Timeout für den Energiesparmodus im Netzbetrieb auf **Nie** und deaktivieren Sie den automatischen Ruhezustand, falls konfiguriert. Der Bildschirm darf sich weiterhin ausschalten. Die Aktion beim Zuklappen eines Laptops ist eine separate Einstellung; das Zuklappen kann ihn auch bei einem Leerlauf-Timeout von „Nie“ in den Energiesparmodus versetzen. Siehe [Energieeinstellungen in Windows](https://support.microsoft.com/en-us/windows/experience/power-battery/power-settings-in-windows-11).

Führen Sie `wsl --shutdown` nicht als routinemäßige Bereinigung aus, während die Website genutzt wird. Wenn eine Änderung der WSL-Einstellungen es erfordert, stoppen Sie zuerst die Instanz und planen Sie eine Unterbrechung ein. Mit diesen Einstellungen kann Windows die Instanz dauerhaft betreiben. Für einen gemeinsam genutzten Dienst, der Abmeldungen und unbeaufsichtigte Neustarts überstehen muss, empfehlen wir die [Linux-Anleitung](/de/on-premises/installation/using-docker-compose/linux).

### Die Wiederherstellung nach einem Neustart von Docker Desktop prüfen {#check-recovery-after-restarting-docker-desktop}

Nachdem Sie Ihre Arbeit gespeichert und aktive Kompilierungen haben abschließen lassen, wählen Sie im Troubleshooting-Menü von Docker Desktop **Restart Docker Desktop**. Warten Sie auf die Engine und prüfen Sie dann in **Ubuntu**:

```bash
docker ps
curl -I http://localhost:8080/launchpad
```

Öffnen Sie das vorhandene Projekt in Windows und kompilieren Sie es erneut. Bestätigen Sie, dass das Konto und der Quelltext noch vorhanden sind.

Wenn Sie die Instanz absichtlich mit `bin/stop` gestoppt haben, verwenden Sie `bin/start`. Wenn Docker läuft, aber ein Dienst fehlschlägt, lesen Sie dessen Logs, statt die Konfiguration neu zu erstellen. Windows Update, Docker-Updates und Stromausfälle können eine Installation im 24-Stunden-Betrieb dennoch unterbrechen; erstellen Sie Backups und prüfen Sie die Wiederherstellung nach geplanten Wartungen.

### Tägliche Nutzung {#daily-use}

Starten Sie Docker Desktop in Windows. Öffnen Sie **Ubuntu**:

```bash
cd "$HOME/ayakaleaf-toolkit"
```

| Aufgabe | Befehl |
| --- | --- |
| Vorhandene Container starten | `bin/start` |
| Container stoppen und Daten behalten | `bin/stop` |
| Konfigurationsänderungen übernehmen | `bin/up -d` |
| Status prüfen | `bin/docker-compose ps` |
| Start-Logs lesen | `bin/docker-compose logs --tail=100 sharelatex` |
| MongoDB-Logs lesen | `bin/docker-compose logs --tail=100 mongo` |
| Compiler-Logs lesen | `bin/logs -f clsi` |

`bin/start` übernimmt keine Konfigurationsänderungen: Verwenden Sie `bin/up -d`, nachdem Sie `config/` geändert haben. Folgen Sie [Daten und Backups](/de/on-premises/maintenance/data-and-backups), bevor Sie die WSL-Distribution aktualisieren, verschieben oder entfernen. Das Kopieren laufender MongoDB-Dateien, während die Datenbank schreibt, ist kein konsistentes Backup.

Belassen Sie für die lokale Nutzung `127.0.0.1`. Um andere Computer zu bedienen, sind zusätzlich eine bewusst gewählte Listen-Adresse, Site-URL, Windows-Firewall-/Netzwerkkonfiguration und HTTPS erforderlich; das Ändern von `OVERLEAF_SITE_URL` allein veröffentlicht keinen Port.

Wenn etwas nicht funktioniert, siehe [Fehlerbehebung](/de/on-premises/installation/using-docker-compose/windows/troubleshooting).
