Diese Seite beschreibt die Umgebungsvariablen, die in der Datei `config/overleaf.rc` für Toolkit-Deployments unterstützt werden.

Die Datei `config/overleaf.rc` besteht aus Variablendefinitionen in der Form `NAME=value`. Zeilen, die mit `#` beginnen, werden als Kommentare behandelt.

<Info>

Nach jeder Änderung an `overleaf.rc` oder `variables.env` müssen Sie die Docker-Container neu erstellen, indem Sie `bin/up` ausführen.

</Info>

## Container

### `sharelatex`

| Name                         | Beschreibung |
| ---------------------------- | ------------ |
| `PROJECT_NAME`               | <p>Legt den Wert des Flags `--project-name` fest, das an `docker-compose` übergeben wird. Dies ist nützlich, wenn mehrere Overleaf-Instanzen auf einem Host laufen, da jede Instanz einen anderen Projektnamen haben kann.<br /><br />- <strong>Standard</strong>: `overleaf`</p> |
| `OVERLEAF_IMAGE_NAME`        | <p>Docker-Image, das vom Anwendungscontainer von Server Pro/CE verwendet wird. Dies ist nur der Name des Docker-Images; das Tag des Docker-Images wird aus `config/version` übernommen.<br /><br />- <strong>Standard:</strong><br />- Server Pro: `quay.io/sharelatex/sharelatex-pro`<br />- Community Edition: `sharelatex/sharelatex`</p> |
| `SERVER_PRO`                 | <p>Wenn auf `true` gesetzt, verwendet das Toolkit das Server-Pro-Image (`quay.io/sharelatex/sharelatex-pro`) anstelle des standardmäßigen Server-CE-Images (`sharelatex/sharelatex`).<br /><br />- <strong>Standard</strong>: `false`</p> |
| `GIT_BRIDGE_ENABLED`         | <p>Auf `true` setzen, um die git-bridge-Funktion zu aktivieren (nur Server Pro). Weitere Informationen finden Sie in der Benutzerdokumentation unter <a href="https://www.overleaf.com/learn/how-to/Git_integration">https://www.overleaf.com/learn/how-to/Git_integration</a>.<br /><br />- <strong>Standard:</strong> `false`</p> |
| `GIT_BRIDGE_IMAGE`           | <p>Docker-Image, das vom git-bridge-Container verwendet wird (nur Server Pro). Dies ist nur der Name des Docker-Images; das Tag des Docker-Images wird aus `config/version` übernommen.<br /><br />- <strong>Standard:</strong> `quay.io/sharelatex/git-bridge`</p> |
| `GIT_BRIDGE_DATA_PATH`       | Legt den Pfad zum Verzeichnis fest, das in den Container `git-bridge` (nur Server Pro) eingehängt und zum Speichern der Git-Repositories verwendet wird. Dies kann entweder ein vollständiger Pfad (beginnend mit `/`) oder ein Pfad relativ zum Basisverzeichnis des Toolkits sein. |
| `GIT_BRIDGE_LOG_LEVEL`       | <p>Konfiguriert die Log-Stufe des Containers `git-bridge`. Verfügbare Stufen: `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`.<br /><br />- <strong>Standard:</strong> `INFO`</p> |
| `SIBLING_CONTAINERS_ENABLED` | <p>Wenn auf `true` gesetzt, verwendet das Toolkit die Technik der <strong>Sibling Containers</strong>, um Projekte in separaten Sandboxes zu kompilieren, wobei für jedes Projekt ein eigener Docker-Container verwendet wird. Weitere Informationen finden Sie in der Dokumentation &#x3C;server-pro-only-configuration/sandboxed-compiles>.<br /><br />- <strong>Erfordert:</strong> `SERVER_PRO=true`<br />- <strong>Standard:</strong> `true`</p> |
| `SIBLING_CONTAINERS_PULL`    | <p>Wenn auf `true` gesetzt, lädt das Toolkit beim Befehl `bin/up` automatisch alle TeX-Live-Images herunter, die über `ALL_TEX_LIVE_DOCKER_IMAGES` in der Datei <strong>config/variables.env</strong> festgelegt sind.<br /><br />- <strong>Standard:</strong> `true`</p> |
| `DOCKER_SOCKET_PATH`         | <p>Legt den Pfad zum Docker-Socket auf dem Host-Rechner fest (dem Rechner, auf dem das Toolkit läuft). Wenn `SIBLING_CONTAINERS_ENABLED` auf `true` steht, wird der Socket in den Container eingehängt, damit der Compiler-Dienst neue Docker-Container auf dem Host starten kann.<br /><br />- <strong>Erfordert:</strong> `SIBLING_CONTAINERS_ENABLED=true`<br />- <strong>Standard:</strong> `/var/run/docker.sock`</p> |
| `OVERLEAF_DATA_PATH`         | <p>Legt den Pfad zum Verzeichnis fest, das in den Hauptcontainer `sharelatex` eingehängt und zum Speichern von Kompilierungsdaten verwendet wird. Dies kann entweder ein vollständiger Pfad (beginnend mit `/`) oder ein Pfad relativ zum Basisverzeichnis des Toolkits sein.<br /><br />- <strong>Standard:</strong> `data/overleaf`</p> |
| `OVERLEAF_LISTEN_IP`         | <p>Legt die Host-IP-Adresse(n) fest, an die der Container gebunden wird. Ist dies beispielsweise auf `0.0.0.0` gesetzt, ist die Weboberfläche unter jeder Host-IP-Adresse erreichbar. Für direkten Containerzugriff muss `OVERLEAF_LISTEN_IP` auf Ihre öffentliche IP-Adresse gesetzt werden. Wird `OVERLEAF_LISTEN_IP` entweder auf `0.0.0.0` oder auf die externe IP Ihres Hosts gesetzt, führt dies in Verbindung mit dem typischerweise zu Fehlern.<br /><br />- <strong>Standard:</strong> `127.0.0.1`</p> |
| `OVERLEAF_PORT`              | <p>Legt den Host-Port fest, an den der Container gebunden wird. Ist dies beispielsweise auf `8099` und `OVERLEAF_LISTEN_IP` auf `127.0.0.1` gesetzt, ist die Weboberfläche unter `http://localhost:8099` erreichbar.<br /><br />- <strong>Standard:</strong> `80`</p> |
| `OVERLEAF_LOG_PATH`          | <p>Legt den Pfad zum Verzeichnis fest, das in den Hauptcontainer `sharelatex` eingehängt und verwendet wird, um Anwendungslogs auf dem Docker-Host verfügbar zu machen. Dies kann entweder ein vollständiger Pfad (beginnend mit `/`) oder ein Pfad relativ zum Basisverzeichnis des Toolkits sein. Entfernen Sie den Konfigurationseintrag, um den Bind-Mount zu deaktivieren. Wenn nicht gesetzt, werden Logs beim Neuerstellen des Containers verworfen.<br /><br />Informationen zum Logging finden Sie unter.<br /><br />- <strong>Standard:</strong> nicht gesetzt</p> |

### `mongo`

| Name              | Beschreibung |
| ----------------- | ------------ |
| `MONGO_ENABLED`   | <p>Wenn auf `true` gesetzt, erstellt das Toolkit einen MongoDB-Container für die Datenbank. Wenn auf `false` gesetzt, wird dieser Container nicht erstellt, und das System verwendet stattdessen die über `MONGO_URL` angegebene MongoDB-Datenbank.<br /><br />- <strong>Standard</strong>: `true`</p> |
| `MONGO_URL`       | <p>Gibt die MongoDB-Verbindungs-URL an, die verwendet wird, wenn `MONGO_ENABLED` auf `false` steht.<br /><br />- <strong>Standard</strong>: nicht gesetzt</p> |
| `MONGO_DATA_PATH` | <p>Legt den Pfad zum Verzeichnis fest, das in den Container `mongo` eingehängt und zum Speichern der MongoDB-Datenbank verwendet wird. Dies kann entweder ein vollständiger Pfad (beginnend mit `/`) oder ein Pfad relativ zum Basisverzeichnis des Toolkits sein. Diese Option betrifft nur den lokalen Container `mongo`, der erstellt wird, wenn `MONGO_ENABLED` auf `true` steht.<br /><br />- <strong>Standard</strong>: `data/mongo`</p> |
| `MONGO_IMAGE`     | <p>Docker-Image, das vom MongoDB-Container verwendet wird. Dies ist nur der Name des Docker-Images; das Tag des Docker-Images gehört in `MONGO_VERSION` (siehe unten).<br /><br />- <strong>Standard:</strong> `mongo`</p> |
| `MONGO_VERSION`   | <p>MongoDB-Version, die vom MongoDB-Container verwendet wird. Der Wert muss mit der MongoDB-Hauptversion und einem Punkt beginnen, z. B. `6.0` oder `6.0-with-suffix`.<br /><br />- <strong>Standard:</strong> `6.0`</p> |

### `redis`

| Name                    | Beschreibung |
| ----------------------- | ------------ |
| `REDIS_ENABLED`         | <p>Wenn auf `true` gesetzt, erstellt das Toolkit einen Redis-Container für die Redis-Datenbank. Wenn auf `false` gesetzt, wird dieser Container nicht erstellt, und das System verwendet stattdessen die über `REDIS_HOST` und `REDIS_PORT` angegebene Redis-Datenbank.<br /><br />- <strong>Standard</strong>: `true`</p> |
| `REDIS_HOST`            | <p>Gibt den Redis-Host an, der verwendet wird, wenn `REDIS_ENABLED` auf `false` steht.<br /><br />- <strong>Standard</strong>: nicht gesetzt</p> |
| `REDIS_PORT`            | <p>Gibt den Redis-Port an, der verwendet wird, wenn `REDIS_ENABLED` auf `false` steht.<br /><br />- <strong>Standard</strong>: nicht gesetzt</p> |
| `REDIS_DATA_PATH`       | <p>Legt den Pfad zum Verzeichnis fest, das in den Container `redis` eingehängt und zum Speichern der Redis-Datenbank verwendet wird. Dies kann entweder ein vollständiger Pfad (beginnend mit `/`) oder ein Pfad relativ zum Basisverzeichnis des Toolkits sein. Diese Option betrifft nur den lokalen Container `redis`, der erstellt wird, wenn `REDIS_ENABLED` auf `true` steht.<br /><br />- <strong>Standard</strong>: `data/redis`</p> |
| `REDIS_AOF_PERSISTENCE` | <p>Aktiviert die AOF-Persistenz (Append Only File) für Redis. Dies ist die <strong>empfohlene</strong> Konfiguration für die Redis-Persistenz.<br /><br />Weitere Details finden Sie im Abschnitt &#x3C;../../../maintenance/data-and-backups#aof-append-only-file> in &#x3C;../../maintenance/data-and-backups>.<br /><br />- <strong>Standard:</strong> `true`</p> |

### `nginx`

| Name                   | Beschreibung |
| ---------------------- | ------------ |
| `NGINX_ENABLED`        | <p>Wenn auf `true` gesetzt, erstellt das Toolkit einen NGINX-Container, der als TLS-Proxy dient.<br /><br />- <strong>Standard</strong>: `false`</p> |
| `NGINX_CONFIG_PATH`    | <p>Pfad zur NGINX-Konfigurationsdatei für den TLS-Proxy.<br /><br />- <strong>Standard</strong>: `config/nginx/nginx.conf`</p> |
| `NGINX_TLS_LISTEN_IP`  | <p>Legt die Host-IP-Adresse(n) fest, an die der TLS-Proxy-Container für HTTPS gebunden wird. Ist dies beispielsweise auf `0.0.0.0` gesetzt, ist die HTTPS-Weboberfläche unter jeder Host-IP-Adresse erreichbar. Typischerweise sollte dies auf die externe IP Ihres Hosts gesetzt werden.<br /><br />- <strong>Standard</strong>: `127.0.1.1`</p> |
| `NGINX_HTTP_LISTEN_IP` | <p>Legt die Host-IP-Adresse(n) fest, an die der TLS-Proxy-Container für die HTTP-Weiterleitung gebunden wird. Ist dies beispielsweise auf `127.0.1.1` gesetzt, werden HTTP-Verbindungen zu `127.0.1.1` auf die HTTPS-Weboberfläche umgeleitet. Typischerweise sollte dies auf die externe IP Ihres Hosts gesetzt werden. Setzen Sie es nicht auf `0.0.0.0`, da dies typischerweise zu einem Konflikt mit `OVERLEAF_LISTEN_IP` führt.<br /><br />- <strong>Standard</strong>: `127.0.1.1`</p> |
| `NGINX_HTTP_PORT`      | <p>Legt den Host-Port fest, an den der TLS-Proxy-Container für HTTP gebunden wird.<br /><br />- <strong>Standard</strong>: `80`</p> |
| `TLS_PORT`             | <p>Legt den Host-Port fest, an den der TLS-Proxy-Container für HTTPS gebunden wird.<br /><br />- <strong>Standard</strong>: `443`</p> |
| `TLS_PRIVATE_KEY_PATH` | <p>Pfad zum privaten Schlüssel für den TLS-Proxy.<br /><br />- <strong>Standard</strong>: `config/nginx/certs/overleaf_key.pem`</p> |
| `TLS_CERTIFICATE_PATH` | <p>Pfad zum öffentlichen Zertifikat für den TLS-Proxy.<br /><br />- <strong>Standard</strong>: `config/nginx/certs/overleaf_certificate.pem`</p> |
