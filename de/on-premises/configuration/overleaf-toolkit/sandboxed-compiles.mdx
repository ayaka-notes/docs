Ayakaleaf Pro bietet die Möglichkeit, Kompilierungen für Sicherheit auf Unternehmensniveau in einer abgesicherten Sandbox-Umgebung auszuführen. Dazu wird jedes Projekt in seiner eigenen abgesicherten Docker-Umgebung ausgeführt.

### Verbesserte Sicherheit

Sandboxed Compiles sind der empfohlene Ansatz für Ayakaleaf Pro, da viele LaTeX-Dokumente im Rahmen der PDF-Kompilierung beliebige Shell-Befehle ausführen müssen bzw. können. Wenn Sie Sandboxed Compiles verwenden, läuft jede Kompilierung in einem separaten Docker-Container mit eingeschränkten Rechten, der mit keinem anderen Benutzer oder Projekt geteilt wird und keinen Zugriff auf externe Ressourcen wie das Host-Netzwerk hat.

<Warning>

Wenn Sie versuchen, Ayakaleaf Pro **ohne** Sandboxed Compiles zu betreiben, läuft die Kompilierung zusammen mit anderen gleichzeitigen Kompilierungen im Haupt-Docker-Container, und Benutzer haben beim Ausführen von LaTeX-Kompilierungen vollen Lese- und Schreibzugriff auf die Ressourcen des Containers `sharelatex` (Dateisystem, Netzwerk und Umgebungsvariablen).

</Warning>

### Einfachere Paketverwaltung

Um die manuelle Installation von Paketen zu vermeiden, empfehlen wir, Sandboxed Compiles zu aktivieren. Dies ist eine konfigurierbare Einstellung in Server Pro, die Ihren Benutzern Zugriff auf dieselbe TeX Live-Umgebung wie auf overleaf.com bietet, jedoch innerhalb Ihrer eigenen On-Premises-Installation. Die von Sandboxed Compiles verwendeten TeX Live-Images enthalten die beliebtesten Pakete und Schriftarten, die mit unseren Galerievorlagen getestet wurden, und gewährleisten so maximale Kompatibilität mit On-Premises-Projekten.

Durch die Aktivierung von Sandboxed Compiles können Sie festlegen, aus welchen TeX Live-Versionen Benutzer in ihrem Projekt wählen können, und eine Standardversion des TeX Live-Images für neue Projekte festlegen.

<Info>

Wenn Sie versuchen, Ayakaleaf Pro ohne Sandboxed Compiles zu betreiben, verwendet Ihre Instanz standardmäßig eine Basisschema-Version von TeX Live für Kompilierungen. Diese Basisversion ist schlank und enthält nur eine sehr begrenzte Auswahl an LaTeX-Paketen, was bei Ihren Benutzern höchstwahrscheinlich zu Fehlern wegen fehlender Pakete führt, insbesondere wenn sie vorgefertigte Vorlagen verwenden.

</Info>

Da Ayakaleaf Pro für den Offline-Betrieb konzipiert ist, gibt es keine automatisierte Möglichkeit, Galerievorlagen von overleaf.com in Ihre On-Premises-Installation zu integrieren; es ist jedoch möglich, dies manuell für jede einzelne Vorlage zu tun. Weitere Informationen dazu finden Sie in unserer Anleitung zum Übertragen von Vorlagen von overleaf.com: [#transferring-templates-from-overleaf.com](/de/on-premises/configuration/overleaf-toolkit/templates#transferring-templates-from-overleaf.com  "mention").

<Info>

Sandboxed Compiles setzt voraus, dass der Container `sharelatex` (über einen Bind-Mount) Zugriff auf den Docker-Socket des Hostsystems hat, damit er diese benachbarten Kompilierungscontainer verwalten kann.

</Info>

## Funktionsweise

Wenn Sandboxed Compiles aktiviert sind, wird der Docker-Socket vom Hostsystem in den Container `sharelatex` eingebunden, sodass der Compiler-Dienst im Container neue Docker-Container auf dem Host erstellen kann. Für jeden Compiler-Durchlauf in jedem Projekt führt der LaTeX-Compiler-Dienst (CLSI) dann Folgendes aus:

* Die Projektdateien an einen Speicherort innerhalb von `OVERLEAF_DATA_PATH` schreiben.
* Über den eingebundenen Docker-Socket einen neuen `texlive`-Container für den Kompilierungsdurchlauf erstellen.
* Den `texlive`-Container die Projektdaten vom Speicherort unter `OVERLEAF_DATA_PATH` lesen lassen.
* Das Projekt im `texlive`-Container kompilieren.

### Sandboxed Compiles aktivieren

#### Für Toolkit-Benutzer

Um Sandboxed Compiles (auch als Sibling-Container bezeichnet) zu aktivieren, setzen Sie die folgenden Konfigurationsoptionen in `overleaf-toolkit/config/overleaf.rc`:

```dotenv title="config/overleaf.rc"
SERVER_PRO=true
SIBLING_CONTAINERS_ENABLED=true
```

#### Für Docker Compose-Benutzer

<Danger>

Ab Overleaf CE/Server Pro `5.0.3` wurden die Umgebungsvariablen von `SHARELATEX_*` in `OVERLEAF_*` umbenannt.

</Danger>

Wenn Sie eine Version `4.x` (oder älter) verwenden, stellen Sie bitte sicher, dass die Variablen das entsprechende Präfix haben (z. B. `SHARELATEX_MONGO_URL` statt `OVERLEAF_MONGO_URL`).

```yml
version: '2'
services:
    sharelatex:
        #...
        volumes:
            - /data/overleaf_data:/var/lib/overleaf
            - /var/run/docker.sock:/var/run/docker.sock
        environment:
            #...
            DOCKER_RUNNER: "true"
            SANDBOXED_COMPILES: "true"
            SANDBOXED_COMPILES_HOST_DIR: "/data/overleaf_data/data/compiles"
            #...
        #...
```

### Das TeX Live-Image einrichten

<Info>

Benutzer in Festlandchina können `ghcr.io` durch `ghcr.nju.edu.cn` ersetzen, um den Download zu beschleunigen. Verwenden Sie `ghcr.nju.edu.cn` jedoch **NICHT** direkt in den Umgebungseinstellungen Ihres Toolkits. Behalten Sie dort ausschließlich `ghcr.io` bei.

</Info>

Ayakaleaf Pro verwendet drei Umgebungsvariablen, um festzulegen, welche TeX Live-Images für Sandboxed Compiles verwendet werden:

* `TEX_LIVE_DOCKER_IMAGE` **(erforderlich):** Das Standard-TeX Live-Image zum Kompilieren neuer Projekte. Dieses Image muss in `ALL_TEX_LIVE_DOCKER_IMAGES` enthalten sein.
* `ALL_TEX_LIVE_DOCKER_IMAGE_NAMES` **(erforderlich):** Eine kommagetrennte Liste von Anzeigenamen für die Images, die für die Auswahloptionen im Frontend verwendet werden.
* `ALL_TEX_LIVE_DOCKER_IMAGES` **(erforderlich):** Eine kommagetrennte Liste der zu verwendenden TeX Live-Images. Wenn das Overleaf Toolkit für die Bereitstellung verwendet wird, werden diese Images heruntergeladen oder aktualisiert. Um den Download zu überspringen, setzen Sie `SIBLING_CONTAINERS_PULL=false` in `config/overleaf.rc`.

Beim Starten Ihrer Ayakaleaf Pro-Instanz mit dem Befehl `bin/up` lädt das Toolkit automatisch alle in `ALL_TEX_LIVE_DOCKER_IMAGES` aufgeführten Images herunter.

Hier ein Beispiel, in dem für neue Projekte standardmäßig TeX Live 2026 verwendet wird und 2025 für ältere Projekte weiterhin im Einsatz bleibt.

<Tabs>
<Tab title="Minimale Installation">

Die folgende Konfiguration installiert alle vollständigen TeX Live-Docker-Images von 2025 bis 2026. Wir empfehlen, vor der Verwendung dieser Konfiguration mindestens **64 GB** freien Speicherplatz zur Verfügung zu haben.

```dotenv title="config/variables.env" wrap
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
```

### Verfügbare TeX Live-Images

Dies ist eine Reihe von TeX Live-Images, die speziell für Overleaf optimiert sind und auch in `TEX_LIVE_DOCKER_IMAGE` und `ALL_TEX_LIVE_DOCKER_IMAGES` eingetragen werden können:

* `ghcr.io/ayaka-notes/texlive-full:2026.1` (auch als Tag `latest`)
* `ghcr.io/ayaka-notes/texlive-full:2025.1`
* `ghcr.io/ayaka-notes/texlive-full:2024.1`
* `ghcr.io/ayaka-notes/texlive-full:2023.1`
* `ghcr.io/ayaka-notes/texlive-full:2022.1`
* `ghcr.io/ayaka-notes/texlive-full:2021.1`
* `ghcr.io/ayaka-notes/texlive-full:2020.1`

<Warning>

Es gibt ein striktes Schema dafür, wie Images getaggt werden **müssen** (es gilt der reguläre Ausdruck `^[0-9]+.[0-9]+`, wobei die erste Zahl das TeX Live-Jahr und die zweite die Patch-Version angibt).

</Warning>

### Kann ich eine andere Image-Registry verwenden?

> Manche fragen sich vielleicht, ob man `ghcr.io` durch eine andere Mirror-Seite ersetzen oder texlive auf ein anderes Image von Docker Hub umstellen kann.

Nein, das empfehlen wir nicht, da die Konfiguration relativ kompliziert ist. Wenn Sie von einer Mirror-Seite herunterladen, können Sie Ihr Image in `ghcr.io/ayaka-notes/texlive-full` umbenennen.

Wenn Sie aber wirklich Ihre eigene Image-Registry verwenden möchten, fügen Sie Folgendes hinzu:

```dotenv title="config/variables.env" wrap
IMAGE_ROOT=hub.your.com/your-repo
```

Anschließend müssen Sie sicherstellen, dass sich alle texlive-Images in `your-repo` befinden, zum Beispiel

* `hub.your.com/your-repo/texlive-full:2025.1`
* `hub.your.com/your-repo/texlive-full:2024.1`

Ausführliche Informationen erhalten Sie im folgenden Quellcode, der zeigt, wie Ihre Umgebungsvariablen ausgewertet werden:

```mjs title="sandboxed-compiles/index.mjs" wrap expandable
if (process.env.SANDBOXED_COMPILES === 'true') {
  // Set default image root if not provided
  let imageRootPath = process.env.IMAGE_ROOT || "ghcr.io/ayaka-notes";
  // Export imageRoot to Settings
  Settings.imageRoot = imageRootPath

  // allowedImageNames should be:
  // [
  //  { imageName: "texlive-2023:latest", imageDesc: "TeX Live 2023" },
  //  { imageName: "texlive-2022:latest", imageDesc: "TeX Live 2022" },
  // ]
  Settings.allowedImageNames = parseTextExtensions(process.env.ALL_TEX_LIVE_DOCKER_IMAGES)
    .map((texImage, index) => ({
      imageName: texImage.split("/")[texImage.split("/").length - 1],
      imageDesc: parseTextExtensions(process.env.ALL_TEX_LIVE_DOCKER_IMAGE_NAMES)[index]
        || texImage.split(':')[1],
    }))
  
  // In the end, imageName will be put together with imageRoot to form the full image path
  // The full name will be like: ghcr.io/ayaka-notes/texlive-2023:latest

  // Set default image name if not provided
  if(!process.env.TEX_LIVE_DOCKER_IMAGE) {
    process.env.TEX_LIVE_DOCKER_IMAGE = imageRootPath + "/" + Settings.allowedImageNames[0].imageName
  }

  // Export currentImageName to Settings
  // This is the new created projects' image name
  Settings.currentImageName = process.env.TEX_LIVE_DOCKER_IMAGE
}
```

Um nicht jedes Mal Ihre Instanz manuell mit `bin/up` aktualisieren zu müssen, können Sie die Aktualisierung Ihres TeX Live-Images automatisieren. Siehe [updating-tex-live-full-images-automatically.md](/de/on-premises/maintenance/updating-tex-live-full-images-automatically  "mention").

### Bekannte Probleme

Dies ist ein realer Fall aus der Overleaf-Community:

> Mit `6.0.1-ext-v3.3` habe ich diese Einstellungen in `variables.env`:
>
> ```dotenv
> TEX_LIVE_DOCKER_IMAGE=texlive/texlive:latest-full
> ALL_TEX_LIVE_DOCKER_IMAGES=texlive/texlive:latest-full
> ```
>
> Mit `texlive/texlive:latest-full` funktioniert das einwandfrei. Ich habe jedoch ein anderes texlive-Image `danteev/texlive:2025-10-15` heruntergeladen und beide Variablen auf den neuen Image-Namen geändert, aber es funktioniert nicht:
>
> ```dotenv
> TEX_LIVE_DOCKER_IMAGE=danteev/texlive:2025-10-15
> ALL_TEX_LIVE_DOCKER_IMAGES=danteev/texlive:2025-10-15
> ```
>
> In den Logs sehe ich Folgendes:
>
> ```text wrap
> {"name":"clsi","level":50,"err":{"message":"(HTTP code 404) no such container - No such image: texlive/texlive:latest-full ","name":"Error","stack":"Error: (HTTP code 404) no such container - No such image: texlive/texlive:latest-full ... 
> ```
>
> Es scheint, dass die geänderten Einstellungen in `variables.env` nicht wirksam werden. Die Kompilierung versucht weiterhin, das Image `texlive/texlive:latest-full` auszuführen, nicht das neue Image.
>
> Ich habe einen Neustart versucht, die Container gelöscht und neu gestartet, aber das Problem besteht weiterhin.
>
> Gibt es eine Lösung?

Aufgrund technischer Einschränkungen gilt: Wenn Sie nur ein einziges Docker-TeXLive-Image einrichten, etwa `texlive-fullA:latest`

```text
ALL_TEX_LIVE_DOCKER_IMAGES=texlive/texliveA:latest-full
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=TeXLiveA
TEX_LIVE_DOCKER_IMAGE=texlive/texliveA:latest-full
```

und nach einiger Betriebszeit Ihrer Overleaf-Instanz das TeXLive-Image auf `texlive-fullB:latest` ändern möchten, werden Sie feststellen, dass Ihre Benutzer keines ihrer Projekte mehr kompilieren können.

```text
ALL_TEX_LIVE_DOCKER_IMAGES=texlive/texliveA:latest-full
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=TeXLiveA
TEX_LIVE_DOCKER_IMAGE=texlive/texliveA:latest-full
```

Das liegt daran, dass der Name des TeXLive-Full-Images (für Sandbox-Kompilierungen) für jedes Projekt in der Datenbank gespeichert wird. _Nur wenn ein Benutzer die TeXLive-Version seines Projekts ändert, zum Beispiel von 2024 auf 2025, wird der Image-Name in der Datenbank geändert_.

Wenn CLSI ein Projekt kompiliert, verwendet es den in der Datenbank gespeicherten Container-Image-Namen direkt für die Kompilierung.

Wenn Sie nur ein Docker-Image bereitstellen, können Benutzer das zum Kompilieren des Projekts verwendete Image nicht ändern. In diesem Fall müssen Sie ein Skript schreiben, um das TeXLive-Image für alle Benutzerprojekte in MongoDB **manuell zu ändern**.

### Debugging und Fehlermeldung

Führen Sie den folgenden Befehl aus, um das clsi-Log über das Toolkit zu prüfen:

```bash wrap
bin/logs clsi
```

Wenn beim Kompilieren mit den TeX Live-Images Probleme auftreten, reichen Sie bitte hier ein Issue ein:

[https://github.com/ayaka-notes/texlive-full/issues/new?template=texlive-image-bug.yml](https://github.com/ayaka-notes/texlive-full/issues/new?template=texlive-image-bug.yml)

Um uns bei der Reproduktion und Fehlersuche zu helfen, werden Sie möglicherweise gebeten, Ihr Projekt auf Overleaf hochzuladen. Wir laden das Projekt dann herunter und führen Kompilierungstests mit GitHub Action durch.
