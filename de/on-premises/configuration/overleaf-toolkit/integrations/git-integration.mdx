Die Git-Integration ist derzeit unter [ayaka-notes/overleaf](https://github.com/ayaka-notes/overleaf) verfügbar.

<Info>

Diese Funktion wurde ursprünglich von [ayaka-notes/ayakaleaf-pro](https://github.com/ayaka-notes/ayakaleaf-pro) entwickelt.

</Info>

<Steps>
<Step title="git-bridge aktivieren (nur für Toolkit-Nutzer)">
Wenn Sie das Toolkit verwenden, aktivieren Sie die `git-bridge`, indem Sie Folgendes in Ihrer `config/overleaf.rc` festlegen:

```text title="config/overleaf.rc"
GIT_BRIDGE_ENABLED=true
```
</Step>

<Step title="git-bridge-Container hinzufügen (nur für Docker-Compose-Nutzer)">
Wenn Sie eine eigene `docker-compose.yml` verwenden, fügen Sie Ihrer Compose-Datei die folgende Container-Konfiguration hinzu:

```yaml title="docker-compose.yml (git-bridge service)" wrap
git-bridge:
    restart: always
    image: ghcr.io/ayaka-notes/overleaf-pro/git-bridge:6.3.2 # tag should match the `sharelatex` container tag
    volumes:
        - ~/git_bridge_data:/data/git-bridge
    container_name: git-bridge
    expose:
        - "8000"
    environment:
        GIT_BRIDGE_API_BASE_URL: "http://sharelatex:3000/api/v0/" 
        GIT_BRIDGE_OAUTH2_SERVER: "http://sharelatex"
        GIT_BRIDGE_POSTBACK_BASE_URL: "http://git-bridge:8000"
        GIT_BRIDGE_ROOT_DIR: "/data/git-bridge"
    user: root
    command: ["/server-pro-start.sh"]
```

Verwenden Sie dasselbe Tag wie für das `sharelatex`-Image. Der [MCP-Server](/de/on-premises/configuration/overleaf-toolkit/mcp-server) (v6.3.1 und neuer) ist Teil des `sharelatex`-Images und wird zusammen mit der Git-Integration aktiviert, sodass er keinen zusätzlichen Container benötigt.
</Step>

<Step title="Konfiguration des sharelatex-Containers aktualisieren">
Außerdem müssen Sie den Container `git-bridge` im Container `sharelatex` verlinken und die folgenden Umgebungsvariablen definieren. Achten Sie dabei besonders auf `V1_HISTORY_URL`:

```yaml title="docker-compose.yml (sharelatex service)"
sharelatex:
    links:
        - git-bridge
    environment:
         GIT_BRIDGE_ENABLED: true
         GIT_BRIDGE_HOST: "git-bridge"
         GIT_BRIDGE_PORT: "8000"
         # We use v1 now, if you used to set V1_HISTORY_URL, please update now
         V1_HISTORY_URL: "http://sharelatex:3100/api"
```
</Step>

<Step title="Authentifizierung">
Zur Authentifizierung eines Git-Clients benötigen Nutzerinnen und Nutzer ein Personal Access Token. Personal Access Tokens können über die Benutzeroberfläche der Anwendung verwaltet werden (siehe Dokumentation):

<Step title="Überwachung und Ressourcenbedarf">
Wir empfehlen, nach der Aktivierung der `git-bridge` die Ressourcen Ihres Hosts zu überwachen. Die zusätzliche Last hängt ab von:

* der Anzahl der Nutzerinnen und Nutzer, die die Funktion verwenden
* der Art der in Ihrer Instanz gehosteten Projekte (größere Projekte sind in der Regel ressourcenintensiver)

### Projekte nach S3 auslagern

Die Git-Integration speichert für jedes Projekt, das von einem Benutzer geklont wird, ein vollständiges Git-Repository auf der Festplatte. Wenn Ihr Speicherplatz begrenzt ist, können Sie einen Swap-Job aktivieren, der weniger genutzte Repositories nach AWS S3 verschiebt. Wird ein ausgelagertes Repository wieder benötigt, wird es zurück auf die Festplatte verschoben. Die folgenden Umgebungsvariablen steuern den Swap-Job:

| Name                                  | Beschreibung                                                                                                                                        |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GIT_BRIDGE_SWAPSTORE_TYPE`           | Setzen Sie diesen Wert auf "s3", um den Swap-Job zu aktivieren.                                                                                                         |
| `GIT_BRIDGE_SWAPSTORE_AWS_ACCESS_KEY` | Ihr AWS Access Key                                                                                                                                |
| `GIT_BRIDGE_SWAPSTORE_AWS_SECRET`     | Ihr AWS Secret                                                                                                                                    |
| `GIT_BRIDGE_SWAPSTORE_S3_BUCKET_NAME` | Dieser Bucket enthält die gezippten Git-Repositories                                                                                               |
| `GIT_BRIDGE_SWAPSTORE_AWS_REGION`     | Die Region des Buckets                                                                                                                                |
| `GIT_BRIDGE_SWAPJOB_MIN_PROJECTS`     | <p>Mindestanzahl der Projekte, die auf der Festplatte verbleiben.<br /><br /><strong>- Standard:</strong> 50</p>                                                      |
| `GIT_BRIDGE_SWAPJOB_LOW_GIB`          | <p>Untere Schwelle für das Auslagern. Der Swap-Job verschiebt Projekte, bis die Festplattennutzung unter diesem Wert liegt.<br /><br /><strong>- Standard:</strong> 128 GB</p> |
| `GIT_BRIDGE_SWAPJOB_HIGH_GIB`         | <p>Obere Schwelle für das Auslagern. Der Swap-Job beginnt mit dem Auslagern, wenn die Festplattennutzung diesen Wert erreicht.<br /><br /><strong>- Standard:</strong> 256 GB</p> |
| `GIT_BRIDGE_SWAPJOB_INTERVAL_MILLIS`  | <p>Zeitabstand zwischen der Prüfung der Festplattennutzung und der Ausführung des Swap-Jobs.<br /><br /><strong>- Standard:</strong> 3600000 ms = 1 Stunde</p>             |

### Fragen und Antworten

<Accordion title="Wie funktioniert das Berechtigungsmodell der Git Bridge, wenn ich mein Projekt mit anderen teile?">

Nutzerinnen und Nutzer mit Lesezugriff können dieses Projekt nur klonen; Nutzerinnen und Nutzer mit Lese- und Schreibzugriff können Projekte klonen und pushen. Hinweis: Nutzerinnen und Nutzer müssen angemeldet sein, um diesem Projekt beizutreten.

</Accordion>

<Accordion title="Wie klone ich ein Projekt, und welchen Benutzernamen und welches Passwort verwende ich?">

Öffnen Sie im Editor in der linken Leiste **Integrations** und klicken Sie auf **Git integration**. Dort wird der Clone-Befehl in folgender Form angezeigt:

```sh
git clone https://<your-overleaf>/git/<project_id>
```

Wenn Git nach Zugangsdaten fragt, geben Sie `git` als Benutzernamen und ein Personal Access Token als Passwort ein. Erzeugen Sie das Token unter **Account Settings**; es ist ein Jahr lang gültig. Ihr Kontopasswort funktioniert nicht.

Änderungen werden nicht automatisch synchronisiert: Verwenden Sie `git pull`, um die im Editor vorgenommenen Änderungen abzurufen, und `git push`, um Ihre eigenen zu übertragen. Der Pfad `/git` wird vom `sharelatex`-Container bereitgestellt, daher benötigt ein vorgeschalteter Reverse Proxy keine zusätzliche Regel.

</Accordion>

<Accordion title="`git push` schlägt mit `HTTP 413` oder `curl 55 Broken pipe` fehl">

Der Push ist größer als das Upload-Limit, das über `MAX_UPLOAD_SIZE` festgelegt wird (in Megabyte, standardmäßig `50`) und auch für Pushes gilt. Erhöhen Sie es in `config/variables.env`, zum Beispiel auf `MAX_UPLOAD_SIZE=200`, und führen Sie dann `bin/up -d` aus. Wenn Sie den [TLS-Proxy](/de/on-premises/configuration/overleaf-toolkit/tls-proxy) oder Ihren eigenen Reverse Proxy verwenden, erhöhen Sie auch dessen `client_max_body_size` (`50M` in der `config/nginx/nginx.conf` des Toolkits).

Die git-bridge lehnt außerdem Dateien größer als 50 MB und Projekte mit mehr als 2.000 Dateien ab. Diese Limits werden über `GIT_BRIDGE_REPOSTORE_MAX_FILE_SIZE` (in Byte) und `GIT_BRIDGE_REPOSTORE_MAX_FILE_NUM` in `config/variables.env` festgelegt.

</Accordion>
