title: Project-History-Chunks-Collection
icon: layer-group
---

`projectHistoryChunks` enthält ein Dokument pro Verlaufs-Chunk, einer Folge von Versionen im Verlauf eines Projekts. Mongo enthält nur die Metadaten des Chunks; der Chunk selbst (ein Snapshot plus die Änderungen danach) ist ein gzip-komprimiertes JSON-Objekt im Chunks-Bucket. Es gibt kein Mongoose-Schema: history-v1 schreibt die Collection in `services/history-v1/storage/lib/chunk_store/mongo.js`, das es für jede Verlaufs-ID aus 24 Hexadezimalzeichen verwendet, wie in CE (`services/history-v1/storage/lib/chunk_store/index.js:644-652`).

#### Felder {#fields}

| Feld | Typ | Bedeutung | Quelle |
| ----- | ---- | ------- | ------ |
| `_id` | ObjectId | Chunk-ID. Sie benennt auch das Chunk-Objekt im Bucket (siehe Hinweise). | `mongo.js:183-185` |
| `projectId` | ObjectId | Verlaufs-ID des Projekts, der Wert in `projects.overleaf.history.id`. In CE legt Web den Verlauf mit der eigenen `_id` des Projekts an (`services/web/app/src/Features/History/HistoryManager.mjs:51-55`). | `mongo.js:186` |
| `startVersion` | Number | Projektversion vor der ersten Änderung im Chunk. | `mongo.js:187` |
| `endVersion` | Number | Projektversion nach der letzten Änderung im Chunk. | `mongo.js:188` |
| `endTimestamp` | Date | Zeitpunkt der letzten Änderung im Chunk; `null`, wenn der Chunk keine Änderungen hat, wie der erste Chunk eines neuen Projekts (`libraries/overleaf-editor-core/lib/chunk.js:146-149`). | `mongo.js:189` |
| `state` | String | `pending`, `active`, `closed` oder `deleted`, siehe Hinweise. | `mongo.js:190`, `343`, `378`, `409` |
| `updatedAt` | Date | Wird beim Einfügen, beim Aktivieren und beim Löschen gesetzt. Das Schließen eines Chunks ändert es nicht. | `mongo.js:191`, `343`, `409`, `434`, `450` |

#### Wer schreibt {#who-writes-it}

| Code | Funktion |
| ---- | ------------ |
| `services/history-v1/storage/lib/chunk_store/mongo.js:179-194` | `insertPendingChunk`: fügt einen `pending`-Eintrag ein, bevor das Chunk-Objekt hochgeladen wird (`chunk_store/index.js:394-410`). |
| `mongo.js:331-359` | `activateChunk`: `pending` zu `active`, sobald der Upload abgeschlossen ist. Ein doppelter Schlüssel bedeutet hier, dass bereits ein anderer Chunk bei dieser Version beginnt. |
| `mongo.js:371-388` | `closeChunk`: `active` zu `closed`, wenn ein neuer Chunk folgt (`confirmCreate`, `mongo.js:206-227`). |
| `mongo.js:402-419` | `deleteActiveChunk`: `active` zu `deleted`, wenn ein längerer Chunk mit derselben Startversion ihn ersetzt (`confirmUpdate`, `mongo.js:295-321`). |
| `mongo.js:428-452` | `deleteChunk` und `deleteProjectChunks`: markieren Chunks als `deleted`. Die zweite läuft bei history-v1 `DELETE /projects/:project_id` (`services/history-v1/api/controllers/projects.js:361-373`). |
| `mongo.js:144-174` | `clone`: kopiert die Einträge eines Projekts unter eine neue Verlaufs-ID, für history-v1 `POST /projects/:project_id/clone`. Web hat einen Client für diese Route (`HistoryManager.mjs:63-72`), aber nichts in Web ruft ihn auf. |
| `mongo.js:497-502` | `deleteOldChunks`: entfernt alte `deleted`- und `pending`-Einträge. Läuft nur über `services/history-v1/storage/tasks/delete_old_chunks.js`. |

Neue Chunks kommen von project-history, das die eingereihten Bearbeitungen an history-v1 `POST /projects/:project_id/legacy_changes` sendet (`services/history-v1/api/routes/project_import.js:29-31`); history-v1 ruft dann `chunkStore.update` oder `chunkStore.create` auf (`services/history-v1/storage/lib/persist_changes.js:215`, `229`). Ein neues Projekt erhält seinen ersten Chunk von `chunkStore.initializeProject` (`chunk_store/index.js:54-80`).

#### Hinweise {#notes}

* Zustandsablauf: `pending` (Eintrag geschrieben, Upload läuft) → `active` (der neueste Chunk, kann noch erweitert werden) → `closed` (ein neuerer Chunk folgt) oder `deleted` (ersetzt, oder das Projekt wurde gelöscht). Lesevorgänge betrachten nur `active` und `closed`.
* Das Chunk-Objekt ist gzip-komprimiertes JSON (`services/history-v1/storage/lib/history_store.js:151-170`) unter dem Schlüssel `<project key>/<chunk id>` (`history_store.js:65-67`). Der Projektschlüssel ist die mit Nullen aufgefüllte Verlaufs-ID, umgekehrt und in 3/3/Rest Zeichen aufgeteilt (`libraries/object-persistor/src/ProjectKey.js:8-15`). Der Bucket ist `OVERLEAF_EDITOR_CHUNKS_BUCKET` (`services/history-v1/config/custom-environment-variables.json:53-56`): `/buckets/chunks` in der Entwicklungsumgebung (`develop/docker-compose.yml:90`) oder `overleaf-chunks` mit `S3_ENABLED=true` (`develop/s3/docker-compose.yml:51`).
* Einträge im Zustand `deleted` oder `pending` und ihre Bucket-Objekte werden nur von `delete_old_chunks.js` entfernt (`yarn delete_old_chunks`, `services/history-v1/package.json:79`). Das CE-Image hat dafür keinen Cron-Job (`server-ce/config/crontab-history`, `server-ce/config/crontab-deletion`), daher bleiben sie in CE erhalten.
* Wenn Web ein gelöschtes Projekt ablaufen lässt, ruft es history-v1 `DELETE /projects/:history_id` auf (`services/web/app/src/Features/Project/ProjectDeleter.mjs:385-391`, `HistoryManager.mjs:127-135`, `152-162`), was alle Chunks des Projekts als `deleted` markiert.
* Mit einem konfigurierten `backupStore` schreibt das Bestätigen eines Chunks außerdem `overleaf.history.currentEndVersion`, `currentEndTimestamp`, `updatedAt` und `overleaf.backup.pendingChangeAt` in das Projekt (`mongo.js:232-262`). CE konfiguriert `backupStore` nicht, daher kehrt `mongo.js:238-240` vorzeitig zurück.
