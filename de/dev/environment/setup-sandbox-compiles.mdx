Sandbox-Kompilierungen funktionieren in der Entwicklungsumgebung etwas anders als im Produktions-Image. Die Entwicklungsumgebung hat sie bereits eingerichtet; diese Seite erklärt die Einstellungen und drei Punkte, die Sie beachten sollten:

* Problem mit Dateiberechtigungen
* Gemeinsames Volume zwischen history-v1 und filestore
* Problem mit Unterverzeichnissen

### Sandbox-Kompilierung aktivieren {#enable-sandbox-compiles}

Sandbox-Kompilierungen sind standardmäßig aktiviert. `develop/docker-compose.yml` setzt `SANDBOXED_COMPILES=true` für `clsi`, und `develop/dev.env` enthält den Rest:

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

clsi lädt Images nicht selbst herunter, laden Sie die Images daher einmal mit `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1` (und `:2025.1`) herunter.

LaTeX läuft in den Geschwister-Containern als `TEXLIVE_IMAGE_USER`. In der Entwicklungsumgebung ist das `tex`, was auch der Standard von clsi ist (`services/clsi/config/settings.defaults.cjs:154`). Das Produktions-Image verwendet stattdessen `www-data`, wenn `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` gesetzt ist (`server-ce/config/env.sh:15-21`), weil dort die Dateien vom Benutzer `www-data` des Overleaf-Containers erstellt werden.

<Warning>

Bitte verwenden Sie kein selbst gebautes Image, da sonst eine Reihe von Fehlern auftreten kann.

</Warning>

### Dateiberechtigungen korrigieren {#fix-file-permissions}

Der clsi-Container startet als root, übergibt die Ordner `compiles`, `output` und `cache` an den Benutzer `node` (uid `1000`) und führt clsi dann als `node` aus (`services/clsi/entrypoint.sh`). Daher gehört `develop/compiles` auf dem Host der uid `1000`, derselben uid wie `tex` in der Entwicklungsumgebung (siehe den Kommentar in `develop/pandoc/Dockerfile`). Mit den obigen Einstellungen kompiliert die Entwicklungsumgebung ohne jede Änderung der Berechtigungen.

Wenn Sie stattdessen `TEXLIVE_IMAGE_USER=root` setzen, hat root (uid `0`) keine Berechtigung, in die Unterordner von `compiles` zu schreiben. Geben Sie in diesem Fall der Gruppe `root` den Besitz und Schreibrechte für `compiles` und setzen Sie `setgid`, damit neue Unterordner diesen Besitz erben:

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

Eine ausführliche Dokumentation finden Sie in `services/clsi/README.md`.

### Gemeinsames Volume zwischen history-v1 und filestore {#volume-share-between-history-v1-and-filestore}

<Info>

Die Einstellungen in diesem und dem nächsten Abschnitt sind bereits in `develop/docker-compose.yml` und `develop/dev.env` enthalten. Sie spielen nur mit `S3_ENABLED=false` in `develop/dev.rc` eine Rolle. Mit dem Standard `S3_ENABLED=true` legen filestore und history-v1 diese Dateien stattdessen in RustFS-Buckets ab (`develop/s3/docker-compose.yml`).

</Info>

Standardmäßig fungiert filestore als Brücke zwischen S3 und anderen Diensten in Overleaf. In Overleaf CE oder Server Pro werden jedoch standardmäßig alle Dateien lokal gespeichert. Daher hat Overleaf eine recht trickreiche Methode eingeführt.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

Gleichzeitig wird `data/history` auch vom History-Dienst verwendet. Auf diese Weise können verschiedene Microservices dieselben Daten gemeinsam nutzen. Deshalb bindet der filestore-Dienst in develop das Volume `history-v1-buckets` von history-v1 ein. Ohne dieses Volume **kann clsi keine Blob-Dateien vom filestore-Dienst abrufen**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

filestore findet die Buckets über diese Einstellungen in `dev.env`:

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### Unterverzeichnisse verwenden {#use-subdirectories}

filestore liest History-Blobs immer mit Unterverzeichnissen (`services/filestore/app/js/KeyBuilder.js:58`, `:70`). Das Produktions-Image schaltet `useSubdirectories` für history-v1 ein (`server-ce/config/production.json`), die Standardkonfiguration von history-v1 jedoch nicht, sodass history-v1 in der Entwicklung <strong>alle Daten flach ablegen würde.</strong> `dev.env` setzt daher `NODE_CONFIG` für history-v1:&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

Ohne diese Einstellung speichert history-v1 die `project_blobs`-Dateien so:

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

Wenn `useSubdirectories` auf `true` gesetzt ist, wird der `_` in diesen Namen zu `/`, sodass jeder Blob in Unterordnern gespeichert wird.
