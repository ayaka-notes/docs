## 摘要

自托管的 Overleaf 部署通常只按照一条经验法则来确定规格：每五到十个并发用户配备一个 CPU 核心和 1 GB 内存。我们证明，这条法则不仅不够精确，而且在结构上就是错误的：它假设容量只受单一资源维度支配，而实际上存在两堵相互独立的"墙"；此外，两个软件参数（都与硬件无关）对结果的影响可高达四倍。

我们在 QEMU/KVM 虚拟机中，以 21 种 CPU/内存配置测量了一个原版 Ayakaleaf Pro v6.2.2 部署（启用沙盒编译，TeX Live 2025），宿主机核心频率锁定在 3.0 GHz。工作负载是一篇真实的 63 页 XeLaTeX 学位论文，由多达数百个不同的用户账户同时编译。我们发现，当虚拟机内存低于 32 GiB 时，核心数几乎无关紧要——在 16 GiB 时，4、8 和 16 vCPU 虚拟机的实测容量相差不到 8%——容量反而受一堵超线性的内存墙支配，这堵墙源于 TeX Live 目录树上共享的页缓存。

为了检验这些规律在规模扩大一个数量级后是否仍然成立，我们在一台 64 核、995 GiB 内存的服务器上重复了这组测试。它能以 100% 的成功率承受 1024 个同时进行的冷编译——是其线程数的八倍——而我们始终没有触及它的上限。真正有用的数字并不是这个上限，而是其下方的拐点：在 $N=256$ 之前，尾延迟每翻倍增长 20–40%，而到 $N=512$ 时则增长 190%。因此，若以"不出错的最大并发数"来报告容量，会把实际可用的工作点高估四倍。在这台机器上，内存从来不是瓶颈资源；限制来自 CPU，以及容器守护进程接纳新沙盒的速率——无论请求多少编译，该速率都在 200 附近饱和。

我们还发现了两个容量规划无法察觉的实现层面效应。第一，CLSI 强制执行一个硬编码的上限：最多 65 个同时编译，且无法通过任何环境变量调整；超过该上限后，用户会立即收到 HTTP 503，而不是被放入队列。第二，Docker 运行器中的每容器内存限制自 2018 年引入以来一直无效，无论是数值大小还是设置位置都有问题，因此一次内存耗尽事件会拖垮整台主机，而不仅仅是单个编译。解除并发上限并将默认编译超时从 180 s 提高到 300 s 后，8 vCPU / 48 GiB 虚拟机的实测容量从 64 个并发编译提升到 268 个——在零硬件成本下提升了 4.2 倍。

最后，我们表明，该系统中的并发换来的只有分时，而工作负载仅受时钟频率限制。拟合得到的退化规律 $T(N)=T_1\max(1,N/C)^{b}$ 给出 $b=0.914$，接近完全按比例减速；而在该机器完整的 1.0–5.5 GHz 范围内进行的时钟扫描，将三十次测量结果归拢到 $T=(k/f)\max(1,N/C)$ 上，其中 $k=27.9 GHz·s$，残差离散度为 5.1%。5.5 倍的时钟频率带来 5.5 倍的加速，没有收益递减。这正是时钟与核心换来不同东西的含义：时钟让每个用户的编译更快，核心只是能接纳更多用户。

## 1. 引言

Overleaf 是占主导地位的协作式 LaTeX 编辑器，其本地部署版本被广泛用于那些不能把未发表稿件发送到第三方云的大学和研究团队。为这样的部署确定规格是一个反复出现的实际问题：在固定的硬件预算下，究竟能有多少人同时按下"重新编译"？

官方指南给出的是一条线性法则——大约每五到十个并发用户配备一个核心和 1 GB 内存——它假定容量在两种资源上平滑且联合地扩展。我们的测量从三个方面与之矛盾。

### 1.1 容量受两堵相互独立的墙支配，而不是一堵

一个配置失败的原因，要么是内存耗尽——此时 Overleaf 服务栈本身崩溃并返回 HTTP 502；要么是编译超过服务端超时——此时 CLSI 报告 `timedout`，而数 GB 内存仍然闲置。这两种状态的扩展行为完全不同，补救措施也不同。给受内存限制的配置增加核心不仅低效，有时甚至适得其反：我们测得某些配置在增加核心数后容量反而_下降_，因为更多的核心使并发编译齐步推进，导致它们的内存峰值需求同时出现，而不是交错出现。

### 1.2 软件参数比硬件更具决定性

编译超时是 MongoDB 中的一个按用户设置的字段，其默认值 180 s 会悄无声息地限制受 CPU 约束的配置。在硬件不变的情况下，将其提高到 300 s 可使实测容量提升至多 4.2 倍。另外，CLSI 通过一个硬编码常量拒绝超过 65 个同时编译。任何没有同时考虑这两点的容量研究——以及任何部署——测量的都是软件，而不是机器。

### 1.3 并发是分时，而不是并行

由于 LaTeX 编译是单线程的，在 $C$ 个核心上服务 $N$ 个同时用户并不会让系统更早完成；只会让每个用户按比例等待更久。因此，在确定用户愿意等待多长时间之前，"支持多少并发用户"这个问题本身就是不适定的。我们将这种依赖关系明确化并加以量化。

### 1.4 贡献

* 一个涵盖 21 种 CPU/内存配置的容量矩阵，在锁频、重复验证的条件下测得，并根据每种配置的失败特征识别出其约束条件。
* 两个拟合模型：一个将超线性内存墙与 CPU 上限区分开的容量模型，以及一个确立纯分时行为的延迟模型。
* 识别并通过实验确认了已部署系统中的两个实现问题，其中包括一个自 2018 年以来一直不起作用的容器内存限制。
* 量化了编译超时与容量之间的权衡，我们认为任何并发数字都必须同时注明这一点。

## 2. 背景

### 2.1 编译路径

Overleaf 的编译请求依次经过 `web` $\rightarrow$ `clsi` $\rightarrow$ 编译容器。在沙盒编译部署（`SIBLING_CONTAINERS_ENABLED=true`）中，CLSI 不会在进程内运行 `latexmk`；它通过绑定挂载的套接字请求宿主机的 Docker 守护进程，基于 TeX Live 镜像启动一个新容器，并将项目目录绑定挂载到 `/compile`。因此，一次编译就是一个运行单个 `latexmk` 进程的短生命周期容器。

由此产生三个结论，它们都影响着本文的测量。第一，工作单元是一个单线程进程：XeLaTeX 不会并行化。第二，每次编译的资源隔离完全取决于 Docker 运行器请求了什么——我们将在 §6.2 中表明，它实际上什么都没请求。第三，工作集的主体不是文档，而是 TeX Live 目录树——一个约 32 GiB 的只读语料库，每个并发编译都会读取它，因而通过宿主机页缓存共享它。这种共享正是我们观察到的超线性内存扩展的来源。

### 2.2 启用沙盒编译

社区版 Overleaf 在应用容器内部运行 `latexmk`。而 Ayakaleaf Pro 与 Overleaf Server Pro 一样，可以将每次编译放在一个_兄弟_容器中运行——这是由应用在_宿主机的_ Docker 守护进程上启动的容器，而不是嵌套在应用容器内部。两个 Toolkit 设置即可开启此功能：

```ini
# config/overleaf.rc
SERVER_PRO=true
SIBLING_CONTAINERS_ENABLED=true
DOCKER_SOCKET_PATH=/var/run/docker.sock

# config/variables.env
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2025.1
```

Toolkit 会将宿主机的 Docker 套接字绑定挂载到应用容器中，并把这些设置转换为 CLSI 读取的环境变量：`SANDBOXED_COMPILES=true`、`SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` 和 `SANDBOXED_COMPILES_HOST_DIR`，最后一个是编译目录在_宿主机_上的路径。这个路径很重要：因为启动编译容器的是宿主机的守护进程，所以传给它的绑定挂载路径必须能在宿主机的命名空间中解析，而不是在应用容器的命名空间中。在此模式下，Server-Pro 的 `config/env.sh` 还会强制设置 `TEXLIVE_IMAGE_USER=www-data`，以确保编译容器写入的文件属主一致。

验证方式很直接：编译期间，宿主机上会出现一个名为 `project-{projectId}-{userId}-{hash}` 的容器，它基于 TeX Live 镜像运行 `latexmk`，并以 0 退出。这就是本文通篇测量其数量的单元，我们将在 §6.2 中报告它完全没有资源限制。

**为什么这对本研究很重要。**

兄弟容器让测量变得干净——每次编译都是一个可观察、独立调度的操作系统实体——但这也意味着在编译之间仲裁 CPU 和内存的是虚拟机内核，而不是 Overleaf。因此，本文中的每条扩展规律都是 Linux 调度器作用于 $N$ 个单线程进程时的性质，这也是它们如此规律的原因。

### 2.3 两种失败模式

我们测量的每种配置都恰好以两种方式之一失败，而且这种区别可以直接从响应状态中看出，无需推断：

* **内存耗尽**——Overleaf 服务栈本身失去响应，请求返回 **HTTP 502**。在失败的并发级别下，虚拟机可用内存通常低于 500 MiB。
* **编译超时**——CLSI 在达到按用户设置的超时时间时终止编译，并报告状态 `timedout`。在失败的并发级别下，可用内存通常还有数 GB。

我们根据这种特征对每种配置进行分类，而不是依据资源比例的启发式规则，这使得"我们撞上了哪堵墙"这个问题可以直接从数据本身得到回答。

## 3. 方法

### 3.1 测试平台与时钟控制

所有虚拟机都运行在同一台 Intel Core i9-14900K 宿主机上的 QEMU/KVM 中，宿主机配有 62 GiB 内存和 NVMe 存储。虚拟机系统为 Ubuntu 24.04，搭配 Docker 29.7 和 Overleaf Toolkit，部署了启用沙盒编译的 Ayakaleaf Pro v6.2.2，使用 `texlive-full:2025.1`。

除非控制其时钟，否则普通桌面 CPU 很难代表服务器。KVM 没有提供设置虚拟时钟的机制：vCPU 就是一个宿主机线程，宿主机核心以什么频率运行，它就以什么频率运行。因此我们直接约束宿主机，在每个核心上禁用睿频并将 `scaling_max_freq` 固定在 3.0 GHz，同时使用 `taskset` 将虚拟机的 vCPU 绑定到物理 P 核上。在混合架构 CPU 上，这一区别很重要：该型号的 E 核基础频率为 2.4 GHz，禁用睿频后_无法_达到 3.0 GHz，因此一旦运行偏移到 E 核上，就会悄无声息地测量一台更慢的机器。在满负载下，我们验证了全部十六个绑定线程都精确运行在 3000 MHz。一个守护脚本会在每次基准测试前检查这一不变条件，否则拒绝启动；在研究期间，它捕获到一次调频策略被悄悄重置的情况。

### 3.2 第二个测试平台：一台大型运行器

QEMU 矩阵每次只隔离一个变量，但它最多只有十六个绑定线程。为了检验在高一个数量级时相同的规律是否依然成立，我们在一台大型服务器上重复了并发扫描：一颗 AMD EPYC 7773X（Milan-X，64 核 / 128 线程，768 MiB L3 缓存），配有 995 GiB 内存，运行相同的 Ayakaleaf Pro v6.2.2 镜像和相同的 `texlive-full:2025.1`。与 QEMU 虚拟机不同，这台机器没有锁频：它是一台生产级服务器，我们也按生产级服务器来测量它。

有两项操作上的预防措施是必要的，值得说明，因为如果没有它们，实验测量的就是测试工具而不是服务器。第一，每个容器都被限制在一个设置了 `MemoryMax=940 GiB` 的 `systemd` slice 中，这样失控的扫描只会耗尽一个 cgroup，而不是整台主机。第二，沙盒编译由宿主机守护进程创建，每个都会写脏自己的写时复制层——即使 20.6 GiB 的基础镜像是共享的，每个容器也测得 116 MiB——因此 Docker 数据根目录被迁移到了一块专用的 NVMe 设备上。在 $N=1024$ 时，一次扫描会写入约 119 GiB 的临时层，普通的根文件系统根本放不下。

### 3.3 工作负载

文档是一篇真实的 63 页硕士学位论文（SJTU 模板），通过 `latexmk` 使用 XeLaTeX 编译，包含 TikZ 图形、`biblatex` 参考文献处理和嵌入的 PDF 资源——也就是说，这是一个真实而非合成的负载。在所有配置下，空载虚拟机上的单次编译耗时 8.6–9.8 s，我们将其作为无负载基线 $T_1$。

### 3.4 负载生成

我们创建了 512 个真实用户账户，并为每个账户提供一份独立的项目副本，使并发编译完全像独立用户那样相互竞争，而不是共享同一个项目锁。请求从宿主机发往虚拟机的转发端口，因此负载生成不会消耗虚拟机的 CPU。

并发是_同时_的，而不是错开的。首先建立所有会话——登录、CSRF 令牌、编译器选择——然后每个线程都休眠，直到一个统一的挂钟时刻（只计算一次并共享），再发出各自的 `POST /project/:id/compile`。这种区别并非吹毛求疵。错开的逐步加压测量的是稳定队列下的吞吐量；同时爆发测量的是一整个阶梯教室的学生在同一个截止时间通知后按下同一个按钮时会发生什么，而这正是运维人员真正担心的情况。两者的差异不止一个常数因子，因为后者填充编译队列的速度比守护进程清空它的速度更快。

在能够如实地产生这种爆发之前，我们必须先排除四个实际障碍。每一个都值得记录，因为每一个都会悄无声息地把实验降级为对测试工具而非服务器的测量。

#### 3.4.1 两个限速器，而不是一个

Overleaf 按来源地址限制登录频率——每分钟 20 次尝试——而我们的所有流量都来自同一台主机。为每个模拟用户分配不同的 `X-Forwarded-For` 地址可以消除这一限制，但随即会撞上第二个更粗粒度的限制：每个子网每分钟约 200 次的配额。因此，把用户分布在一个连续地址块中会在第 201 个账户时失败。我们改为根据用户序号推导合成地址，使相邻用户落在不同的 `/24` 网段中，

$$
\texttt{203.}\;\big\lfloor i/250 \big\rfloor \bmod 100 + 1\texttt{.}\;
  i \bmod 250 + 1\texttt{.}\; i \bmod 200 + 10 ,
$$

这让两个限速器在全部 1024 个用户下都保持宽松。

#### 3.4.2 注入的请求头默认会被丢弃

仅设置请求头还不够。Express 只对被告知可信任的对端采纳 `X-Forwarded-For`，而 Overleaf 的 `trustedProxyIps` 默认为 `loopback`。由于负载生成器是通过容器的网桥而不是回环接口访问应用的，请求头会被解析然后丢弃，所有模拟用户又会归并回同一个地址。其症状是恰好在第二十次登录时出现一波 `HTTP 429`，这很容易被误读为服务器过载。必须将网关网络显式加入信任链；在 §4.3 的集群部署中，还必须加入 Pod 和 Service 的 CIDR。

#### 3.4.3 负载均衡器会覆盖它被要求保留的请求头

当实例位于代理之后时，常规的 `option forwardfor` 会把真实客户端地址_追加_到链中，这在生产环境中是正确的行为，在这里却恰恰是错误的：合成地址会被负载生成器自己的地址取代。必须将该指令限定为 `option forwardfor if-none`，使代理仅在客户端未提供该值时才添加。

#### 3.4.4 客户端在服务器容量耗尽之前就先耗尽了文件描述符

在 $N=1024$ 时，生成器同时持有一千多个套接字，默认 1024 个描述符的软限制在会话建立阶段而非测量阶段就已达到。这种失败是无声的：三个会话未能建立，运行结果报告 1021 而不是 1024；同时，一个通过调用 shell 统计容器数量的采样线程因 `EMFILE` 而终止，悄无声息地截断了遥测数据。必须在生成器上提高软限制——我们宿主机上的硬限制本来就是 1048576——然后重新运行。我们在 §4.3 中报告了两次运行：修正后的那次完成了 1024 个中的 1024 个，其中位数与被截断的那次相差不到 1.2 s，因此我们认为第一次运行可用但不具权威性。

### 3.5 测量规程

为了保证可复现性，以下几项方法上的选择被证明是必要的。

#### 3.5.1 预热

在刚启动的虚拟机上，页缓存是空的，最初的编译测量的是冷启动 I/O 而不是稳态容量：同样的 2 vCPU / 2 GiB 配置，冷启动时为 36.5 s，预热后为 9.8 s，相差 3.7 倍。因此，每种配置在启动后都会先进行两次单编译预热，其结果不计入。

#### 3.5.2 通过标准

只有当_每个_编译都成功且该并发级别在重复测试中依然通过时，该级别才算通过。这比成功率阈值更严格，而且很重要：在 4 vCPU / 16 GiB 下，并发级别 32 第一次以 80.2 s 的中位数通过，但重复时 32 个编译全部超时，因此我们报告的是 31。

#### 3.5.3 搜索

各并发级别的定位方式是：从模型预测的初始值出发进行指数式区间扩展，然后进行精确的整数二分。由于判定标准是全有或全无，一个级别在第一次失败时即可确定，因此一旦有一个失败，我们就放弃其余正在进行的请求——但在较小的级别上例外，因为被放弃的编译会严重拖住一台小型虚拟机，使其再也无法恢复。

#### 3.5.4 级别之间的隔离

在开始下一个级别之前，会先清空编译容器，并轮询 Web 应用直到它重新响应。否则，紧跟在一次崩溃之后的级别会记录一个虚假的零会话失败。

#### 3.5.5 宿主机清洁

宿主机上无关的虚拟机均已关闭：当有 24 GiB 宿主机内存被其他用途占用时，相同的虚拟机配置在相同并发下报告的负载均值是 11.7，而不是 3.2。宿主机的内存压力会传导到虚拟机中，使测量失效。

每个级别都以 100% 完成，包括 $N=1024$——线程数的八倍。我们没有找到这台机器的容量上限；在它耗尽余量之前，我们先耗尽了耐心。这是本研究中第一个约束条件不是内存的配置：在 $N=1024$ 时，编译 cgroup 的峰值为 184 GiB，仅为其 940 GiB 上限的五分之一，而 CPU 处于 100% 利用率，负载均值为 166。

#### 4.3.2 退化是次线性的，因为准入受到速率限制

朴素的分时模型预测，$8\times$ 的线程数意味着 $8\times$ 的延迟。实测代价相对于单次编译是 $9.7\times$，但相对于 $N=128$ 只有 $3.8\times$——而所施加的负载增加了八倍。原因可以在图 7(b) 和表 2 的最后一列中看到：尽管 1024 个请求是同时发出的，实际存活的沙盒数从未超过 205。守护进程创建容器的速度跟不上客户端请求的速度，因此请求在准入阶段排队，而不是在 CPU 内部争用。正是排队挽救了这里的尾延迟，而且这完全是意外。

#### 4.3.3 拐点在 512，而不在失败点

在 $N=256$ 与 $N=512$ 之间，负载翻倍使 $p_{95}$ 延迟上升了 $2.9\times$；而此前每次翻倍的代价都在 $1.2\times$ 到 $1.4\times$ 之间。如果以"不失败的最大 $N$"来表述容量，就会报告 1024，而这对运维人员毫无用处：在那个点上，尾部等待时间接近八分钟。

### 4.4 编译时间与时钟频率成反比

由于工作负载受 CPU 约束，其代价应当按 $1/f$ 变化。我们通过在机器的完整频率范围内（1.0–5.5 GHz，分十档）扫描宿主机时钟来直接检验这一点，其他条件保持不变（图 8）。单编译时间从 26.5 s 降至 4.8 s：5.5 倍的时钟频率带来 5.5 倍的加速，在整个范围内都没有收益递减。在全部十个频率下，乘积 $T\!\cdot\!f$ 的偏差都在 2% 以内。

按核心份额进行归一化后，全部三十次测量——十个频率下的三个并发级别——都归拢到一个常数上：

$$
T(N,f) \;=\; \frac{k}{f}\,\max\!\left(1,\frac{N}{C}\right),
  \qquad k = 27.9\ \mathrm{GHz\cdot s}
$$

在时钟本身变化 5.5 倍的范围内，残差离散度为 5.1%。没有任何曲率这一点本身就是结论：如果工作负载受内存带宽或 I/O 约束，那么随着 CPU 超过另一种资源，$T$ 会在高频时趋于平缓。

## 5. 分析

### 5.1 两堵墙，分别拟合

每种配置都根据其失败特征（§2.3）进行分类，然后只在实际撞上内存墙或 CPU 上限的配置上分别对两者进行拟合：

$$
N_{\max} = \min\left(A R^{p},\; k_c C\right)
$$

其中 $R$ 以 GiB 为单位，$C$ 以 vCPU 为单位。

内存墙的指数始终是超线性的，$p>1$：随着总内存增加，每多一个并发编译的边际内存成本反而_下降_，从 3 GiB 虚拟机上的每编译约 312 MiB 降至 32 GiB 虚拟机上的约 194 MiB。其机制就是 §2.1 中描述的 TeX Live 目录树上的共享页缓存：并发编译会读取相互重叠的字体和宏文件，因此更大的缓存会被更多编译分摊。这就是为什么朴素的"每五个用户 1 GB"法则会低估大型机器、高估小型机器。

### 5.2 更多核心反而更糟的情况

公式 (2) 是两项中的最小值，因此在 $C$ 上是单调的，但测量结果并非如此。我们观察到两次增加核心反而_降低_容量的反转：16 GiB 时（54 对 45）和 32 GiB 时（145 对 135）。两者都发生在受内存约束的状态下，机制也相同：核心更多时，并发编译齐步推进，在同一时刻达到其驻留内存峰值；而核心更少时，调度器会让它们交错运行，峰值也随之错开。在内存余量本已紧张的虚拟机上，正是这种错开让它得以存活。基于平均资源使用量构建的容量模型无法表达这一点；这是峰值_重合_的性质。

第三个表面上的反转出现在 2 GiB，我们现在不予采信。搜索记录显示 2 vCPU 时容量为 2，而 4 和 8 vCPU 时为 1，看起来像是同一效应。重新检查原始扫描数据后，我们发现情况更简单：在 2 GiB 时，级别 $N=2$ 在三种核心数下首次尝试都成功了，但在其中两种的确认运行中失败。这个级别并不代表容量，而是一次掷硬币，2 vCPU 那一项只是恰好掷中的那一次。因此，我们在三种核心数下都报告可复现的值 1，并且不从这一差异中得出任何结论。我们在这里记录这一修正，而不是悄悄改写表格，因为被舍弃的读数恰恰是那种本可以支撑一个有趣论断的读数。

## 6. 实现层面的发现

### 6.1 硬编码的并发上限

在足够大的虚拟机上，无论请求的并发数是多少，容量都恰好停在 65 个同时编译：在 $N=66,80,96,128$ 时，我们测得 $65$ 个成功，以及 $1,15,31,63$ 个立即返回的 `unavailable` 响应，容器数固定在 65，数 GB 内存未被使用，编译时间中位数稳定在 77 s——远低于任何超时值。

原因是 CLSI 中的一个常量：

```javascript
// services/clsi/config/settings.defaults.cjs:110
compileConcurrencyLimit: isSpotInstance ? 32 : 64,

// services/clsi/app/js/LockManager.js
if (LOCKS.size <= Settings.compileConcurrencyLimit) return   // <= admits 64+1
throw new Errors.TooManyCompileRequestsError(...)
```

该比较是非严格的，因此实际上限为 $64+1=65$，与测量结果完全一致。多出的请求会收到 **HTTP 503**——它们是被_拒绝_，而不是排队，因此从用户角度看，编译按钮直接失败了。与同一文件中的其他所有可调参数不同，这个参数不读取任何环境变量；它于 2024 年 8 月在上游引入，只能通过修改镜像来更改。提高该限制后，同一台 16 vCPU / 32 GiB 虚拟机在 $N=80$ 时的结果从 `success=65, unavailable=15` 变为 `success=80`。

### 6.2 不起作用的容器内存限制

检查一个运行中的编译容器，会发现它完全没有任何资源隔离：

```text
Memory=0  NanoCpus=0  CpuShares=0  CpuQuota=0  CpusetCpus=[]
Ulimits=[{Name:cpu Soft:305 Hard:310}]
```

没有 CPU 配额是有意为之，这也解释了为什么 §4.2 中的分时指数如此干净：没有任何东西扭曲编译之间的竞争。然而，没有_内存_限制并非有意为之。Docker 运行器确实请求了一个限制：

```javascript
// services/clsi/app/js/DockerRunner.mjs:262
Memory: 1024 * 1024 * 1024 * 1024, // 1 Gb
```

这里有两处错误。该值是 $1024^4=1 tebiB$，而注释本意是 $1024^3$；并且该字段放在创建选项的顶层，而不是 Docker API 所期望的 `HostConfig` 内部，因此被丢弃——观察到的 `Memory=0` 证实了这一点。这两个错误在引入该文件的提交（`9a519f0d3d`，2018 年 3 月）中就已存在，并在从 CoffeeScript 的转换、全仓库的重新格式化以及从 CJS 到 ESM 的迁移中保留了下来，而这些改动都没有重新审视语义。值得注意的是，同一提交中的 `MAX_OUTPUT = 1024 * 1024 // 1MB` 是正确的，说明这是一次笔误而非理解错误。

其后果在我们的低内存测量中清晰可见。由于编译没有限制，内存耗尽并不会表现为 Docker 终止某个违规容器；而是会拖垮整台虚拟机。在 2 vCPU / 2 GiB 配置上，我们观察到用于监控的 SSH 会话被阻塞了 300 s，两个核心上的负载均值达到 68，虚拟机最终自行重启。一个正常工作的每容器限制会让退化平缓得多：过大的编译会失败，而服务会存活下来。

唯一真正生效的限制是 `RLIMIT_CPU`，设置为 $\text{timeout}+5$ 秒。它限制的是 _CPU_ 时间而不是挂钟时间，而单次编译只消耗约 9 s 的 CPU，因此在任何并发下它都不会构成约束；它防范的是诸如失控宏之类的病态输入。不过，它是一个有用的判定依据：观察到 `Soft:305` 即可确认 300 s 的超时设置确实已传递到容器中。

### 6.3 编译超时是最主要的可调参数

按用户设置的字段 `features.compileTimeout` 默认为 180 s。对于任何受 CPU 约束的配置，这不是安全余量，而是一个容量设置，因为一台仍在正确计算的机器会被判定为失败。将其提高到 300 s——只需一次 MongoDB 更新——就能使实测容量变化多达 4.2 倍（表 3）。上限为 600 s，由 `RequestParser.MAX_TIMEOUT` 强制执行，超过该值会被悄悄截断。

| 4 vCPU / 48 GiB  |    63 |   143 | $2.27\times$ | CPU                   |
| 4 vCPU / 16 GiB  |    31 |    54 | $1.74\times$ | CPU                   |
| 2 vCPU / 8 GiB   |    15 |    21 | $1.40\times$ | CPU                   |
| 8 vCPU / 32 GiB  |   127 |   135 | $1.06\times$ | 下一步将撞上内存墙 |
| 8 vCPU / 16 GiB  |    56 |    45 | $0.80\times$ | 内存                |
| 16 vCPU / 32 GiB |   159 |   141 | $0.89\times$ | 内存                |

**表 3.** 编译超时对实测容量的影响。

最后两行是结果中违反直觉的那一半，也是我们在同一超时下重新测量每种配置的原因。对于受_内存_约束的配置，更长的超时反而会_降低_容量，因为每个编译持有其驻留内存的时间更长，相互重叠的编译也更多。因此，一个容量数字如果不注明测量时所用的超时，就毫无意义，而且两种超时下的数字不能混在同一张表中。

## 7. 相关工作

### 7.1 厂商指南

Overleaf 自己的硬件文档陈述了我们在此量化的定性事实：LaTeX 是单线程的，因此单核性能决定编译时间，而且"只有当你要编译的文档数超过空闲 CPU 核心数时，更多核心才会有帮助" \[1]。随后它给出了线性的规格法则——2 核/3 GiB 的基础配置，外加每五到十个并发用户一个核心和 1 GB 内存——这正是本研究的动机。我们的贡献在于把这些陈述变成可测量的规律（公式 (1) 和 (2)），并指出线性法则在何处失效：它没有考虑使内存墙呈超线性的共享页缓存，也没有考虑主导结果的两个软件参数。

### 7.2 构建与 CI 容量研究

在 LaTeX 之外，对并发下构建系统的测量已相当成熟。LightSys 报告称，在 Docker 容器内进行编译的传统 CI 系统，其 I/O 会随拉取请求到达率的上升而退化，瓶颈出现在约十一个并发请求附近 \[17]；TAOS-CI 观察到，编译在 CI 挂钟时间中占主导，在大型项目中占整个流水线时长的 60–67% \[18]。我们的系统在一个方面有所不同，而这一点被证明是决定性的：LaTeX 编译是交互式的。一个耗时翻倍的 CI 任务只是带来不便；而一次耗时翻倍的编译会被盯着预览窗格等待的用户直接感知，这就是为什么我们不把超时视为失败阈值，而是视为一个容量参数。

### 7.3 容器开销

近期的工作分解了 Docker 容器在不同存储层级上的启动延迟 \[19]，并刻画了边缘环境中的容器性能 \[20]。在我们的场景中，每次编译的容器启动开销被分摊了：相对于 9 s 的编译，它只是一个很小的常数，并被我们拟合的无负载时间 $T_1$ 吸收。真正重要的容器属性是资源限制的_缺失_（§6.2），它将单次编译的内存超限转变为整台主机的故障。

### 7.4 作为不可信输入的 LaTeX

沙盒编译之所以存在，是因为 TeX 是一门编程语言，而文档是不可信输入 \[21, 22]。正是这一设计选择使本研究成为可能——每次编译都是一个资源行为可观察的隔离容器——同时也让缺失的内存限制变得后果严重，因为部署它的运维人员会默认隔离是存在的。

### 7.5 作为研究对象的编译器

TeX 本身作为一门语言已有完善的文档 \[16]，但它作为_构建目标_的行为直到最近才受到关注。Tan 和 Rigger \[8] 使用不同的引擎和发行版版本编译了大量 arXiv 源文件，发现引擎选择不可互换：在 XeTeX 和 pdfTeX 下产生字节级相同输出的文档只占极小的比例。这一结果直接关系到我们的方法。容量是文档_和_引擎共同的属性，因此一个不同时固定两者的基准测试是不可复现的；所以我们自始至终固定同一份文档、同一个引擎和同一个发行版（`texlive-full:2025.1`），并在每个图注中注明引擎。这也限定了我们数据的普适性，值得明确指出：它们刻画的是 XeLaTeX 在这份文档上的表现，而不是抽象意义上的 TeX。

关于 LaTeX 构建_系统_的工作主要由实践者推动。LaTeX3 项目的 `l3build` \[13] 标准化了回归测试和打包，独立的基准测试则对比了各种封装工具——一项针对 26 个构建系统的调查发现，预编译导言区比普通运行快约 20%，比 `latexmk` 快约 40% \[14]。这些工作优化的是_单次_编译。它们与我们的测量相互正交且可以叠加：导言区缓存会缩短 $T_1$，而本文中的每个容量数字都随 $T_1$ 缩放。

### 7.6 编辑器中的并发控制，而非编译器中的

Overleaf 的协作部分建立在一条成熟的研究脉络之上。操作变换起源于 Ellis 和 Gibbs \[9]，并由 Jupiter 系统 \[10] 使其适用于高延迟客户端，其设计在 `document-updater` 中清晰可见：一个对操作排序的服务器，以及一个供客户端同步的每文档缓冲区。无冲突复制数据类型 \[11] 无需中央排序器即可解决同样的问题。正是这一区别让 §4.3 的拓扑得以成立：由于待处理更新的缓冲区位于共享的 Redis 中，而不是某个实例的内存中，路由到任意副本的编译都能看到最新的按键输入，因此编译亲和性可以出于缓存局部性来选择，而不必为了正确性。

### 7.7 容量模型

Amdahl 定律 \[24] 限定了并行带来的加速比，Little 定律 \[23] 将占用量与到达率和服务时间联系起来；两者在上文中都有使用。Gunther 的通用可扩展性定律 \[12] 在前者基础上增加了一个表示一致性延迟的退化项，预测吞吐量会先达到峰值然后下降。我们注意到，直到 $N=1024$，我们的系统都_没有_表现出这种退化状态：吞吐量饱和、延迟增长，但没有任何崩溃。原因是结构性的而非侥幸——编译之间没有需要保持一致的共享状态，因此该定律增加的那一项接近于零，而 §4.3 中的准入平台期在争用产生影响之前就将其限制住了。

## 8. 给运维人员的建议

<Steps>
<Step title="在购买硬件之前，先调整这两个软件参数">
两者都是免费的，而且都比我们测量过的任何单项硬件升级更有价值。将 `features.compileTimeout` 提高到用户实际能够容忍的值——CLSI 接受的最大值为 600 s——并且，如果你预计会超过 65 个同时编译，要么在派生镜像中提高 `compileConcurrencyLimit`，要么进行横向扩展。两者都不做，就意味着在为软件拒绝使用的核心付费。
</Step>

<Step title="按拐点而不是上限来确定单机规格">
大型运行器的扫描（§4.3）区分了两个经常被混为一谈的数字。_上限_——仍能返回每个 PDF 的最大并发数——在一台 64 核服务器上至少为 1024，我们始终没有触及。_拐点_——尾延迟不再平缓增长、开始成倍增长的那个点——位于 512，而它下方最后一个舒适的工作点是 256。在 $N=256$ 与 $N=512$ 之间，$p_{95}$ 等待时间从两分钟增加到将近六分钟；在 512 与 1024 之间则达到八分钟。按上限确定规格的运维人员交付的是一个技术上可用、但没人愿意用的系统。

因此，对于这台机器和这份文档，建议的工作点是 **256 个并发编译**，即物理核心数的 $4\times$、线程数的 $2\times$，可将 $p_{95}$ 保持在 120 s 左右。我们建议将 `compileConcurrencyLimit` 设为该值，而不是让它保持在较高的水平：一次接纳 1024 个编译会让所有人等待八分钟，而接纳 256 个并让其余的排队，则能让大多数用户在两分钟内得到结果。排队只会拖累晚到的人；争用则会拖累所有人。
</Step>

<Step title="将这些数字视为最坏情况">
表 2 中的每个级别都是同时发起的冷编译。这两个条件在生产环境中都不成立：同一份文档的热编译耗时 8.6 s，而冷编译为 28.3 s，相差 $3.3$ 倍；而且真实用户不会在同一秒按下按钮。因此，一个每两分钟重新编译一次、具有典型缓存命中率的稳态用户群，所能支撑的写作者数量会比单看并发数字所暗示的多得多——在 256 这个工作点上，大约可达一千名甚至更多活跃作者。并发数字是对瞬时爆发的限定，而不是座位数。
</Step>

<Step title="先确定延迟预算，再据此读出规格">
公式 (1) 可以直接反解。对于在 $C$ 个核心、时钟频率为 $f$ 时的目标等待时间 $T$，可容纳的并发数为 $N \le C\,fT/k$，对于这份文档 $k\approx28 GHz·s$。在 3 GHz 的 8 核上设定 60 s 预算，得到 $N\le51$；120 s 预算则使其翻倍。将预算与容量一同公布，是如实表述两者的唯一方式。
</Step>

<Step title="先买内存，再买核心，并确认你撞上的是哪堵墙">
在 32 GiB 以下，我们测得增加核心几乎没有收益。诊断成本很低：如果失败表现为 HTTP 502 且虚拟机内存不足，就增加内存；如果失败表现为 `timedout` 且内存仍有余量，就增加核心或提高超时。运维人员可以根据我们用来对配置进行分类的同一失败特征来判断。
</Step>

<Step title="为体验选时钟，为人数选核心">
由于 $T\propto 1/f$ 没有任何曲率（在 1.0–5.5 GHz 范围内偏差 2%），更快的时钟会让每个用户的每次编译都更快。更多的核心不会让任何单次编译变快；它们只能接纳更多并发编译。如果部署的抱怨是"编译太慢"，就应该购买时钟频率；如果抱怨是"截止时间前编译失败"，就应该购买内存和核心。
</Step>

<Step title="超过上限后横向扩展，而不是纵向扩展">
超过 65 个并发编译后，受支持的方式是横向扩展（图 2c 和图 10，详见 §9）：在带有 Cookie 会话亲和性的负载均衡器后面部署多个应用实例，共享集中式的 MongoDB、Redis 和 S3 兼容存储，`git-bridge` 保持单例。这会将单实例上限乘以实例数，而这正是 SaaS 部署达到其自身容量的方式。
</Step>

<Step title="不要依赖每次编译的隔离">
在 Docker 运行器的内存限制被修复（§6.2）之前，单个病态文档就可能耗尽整台主机，而不是只有它自己被终止。需要这一保证的运维人员应当自行施加限制，而不是等待修复。我们在大型主机上使用的机制是一个带有硬上限的 systemd slice，然后让 Docker 守护进程指向它，使其创建的每个容器都计入其中：

```ini
[Slice]
MemoryMax=940G
```

这里有一个细节，一旦忽略就会浪费一个下午。名为 `docker-capped.slice` 的 slice 并不位于 `docker.slice` 旁边，而是位于它_内部_，因为连字符是层级分隔符，而不是名称的一部分。一个看起来没有效果的上限，通常是被施加在了离容器实际所在位置差一层的地方。请在运行后从 `memory.max_usage_in_bytes` 读回峰值来验证，而不要轻信配置文件——在我们的主机上，即使在 1024 个同时编译时，编译 cgroup 也从未超过其上限的五分之一，这本身就证明了约束条件是守护进程而不是内存。
</Step>
</Steps>

## 9. 参考多机部署

上文的所有内容测量的都是单台机器。本节将以足以搭建的细节阐述分布式形态，并且——由于运维人员真正面对的问题不是_如何做_而是_是否要做_——首先说明在什么时候它值得付出这些麻烦。

### 9.1 何时需要分布式形态

在所有重要方面，单台机器的运维成本都更低：一个故障域，没有需要保持一致的共享状态，没有可能出错的路由。我们的数据给出了何时离开单机的三个阈值。

#### 9.1.1 低于 65 个并发编译时，不要这样做

单实例上限是一个软件常量，而不是硬件常量（§6.1）。在施加的负载接近它之前，第二台机器只会增加故障模式，而换不来任何东西。64 核主机只有在提高 `compileConcurrencyLimit` 之后，才能以完全成功的结果服务 256 个并发编译；一个还没有修改这一个值的运维人员并不受硬件约束，不应该去采购硬件。

#### 9.1.2 在 65 到大约 500 之间，先纵向扩展

纵向扩展在我们的整个测试范围内都保持线性，从未进入退化状态。一台大型主机以 100% 的成功率达到了 1024 个同时冷编译（§4.3）；延迟拐点出现在 512，而不是更早。在这个区间内，一台更大的机器严格来说比几台较小的机器更简单，而且根据 §4.4，一台更快的机器会改善每个用户的体验，而不仅仅是接纳更多用户。

#### 9.1.3 为了可用性而采用分布式，而不是为了吞吐量

在达到上限之前运行多个应用副本的真正理由是：一台机器就意味着一个电源、一个内核、一个升级窗口。这是一个正当的理由，也是我们会给出的理由；只不过它不是一个容量论据，而将两者混为一谈会让运维人员在需要内存的时候去购买副本。

### 9.2 各层级及其规格

图 10 展示了该拓扑。它有四个层级，各自按不同的量进行扩展——这正是将它们分开的全部意义所在。

#### 9.2.1 边缘层

一个负载均衡器，或者为了可用性使用两个。它终止 TLS，不做任何昂贵的工作；它随连接数而不是编译数扩展，对于本文研究的负载，一个小型实例就足够了。重要的是它的配置，而不是它的规格（§9.3）。

#### 9.2.2 应用副本

它们承担编译负载，是唯一随并发数扩展的层级。按照 §8 的规则确定每个副本的规格——先内存，后核心，然后是时钟——再将副本数设为峰值并发数除以单副本上限。副本不保存任何持久数据：其本地磁盘存放的是编译临时文件和输出缓存，两者都可以重建。正是这一点让它们可以安全地自由添加和移除，而这值得验证而不是想当然，因为一个配置错误的 `filestore` 路径就会悄无声息地把这一层变成有状态的。

#### 9.2.3 状态层

Redis、MongoDB 和 S3 兼容的对象存储，分别部署在不同的主机上。Redis 是承重的那个，也是最不显眼的：它保存会话存储和实时文档缓冲区，正是这一点让路由到任意副本的编译都能看到在另一个副本上键入的内容。把 Redis 当作缓存并按淘汰策略来确定规格的运维人员，会产生基于过时文档的编译，而这极难诊断，因为没有任何东西失败——只是输出是错的。MongoDB 随项目数量而不是编译速率扩展。对象存储在单副本时是可选的，在多副本时是必需的。

#### 9.2.4 单例

`git-bridge` 将仓库保存在本地磁盘上，维护一个本地索引，并且没有复制路径。它必须恰好运行一个实例，固定在一个指定副本旁边，它也是让整个部署无法做到完全无状态的组件。请据此规划它的主机：它的磁盘才是需要备份的那块。

| **层级**      | **数量**            | **扩展依据**          |
| ------------- | -------------------- | ------------------------ |
| 负载均衡器 | 1–2                  | 并发连接数   |
| 应用   | $\lceil N/C\rceil$ | 峰值并发编译数 |
| Redis         | 1（+副本）         | 活跃编辑会话数  |
| MongoDB       | 1（+副本）         | 存储的项目数          |
| 对象存储  | 1 个集群            | 项目总字节数      |
| `git-bridge`  | 恰好 1            | 磁盘上的仓库数     |

### 9.3 路由是最容易出错的部分

三类请求必须到达三个不同的地方，而默认的单规则配置最多只能满足其中两类。

`/project/` 下的编译流量应当按项目标识符进行一致性哈希分配，使项目的编译缓存始终留在同一个副本上。我们使用 HAProxy 的 `balance hash path,field(3,/)`，配合 `hash-type consistent` 和 `hash-balance-factor 150`。这一选择在横向扩容时很重要：使用 Cookie 亲和性时，已有会话会无限期地固定在原来的副本上，新增的副本只会接收新用户，因此运维人员刚刚付费购买的机器完全分担不到促使他购买它的那部分负载。在我们的配置中，横向扩容时一致性哈希重新分配了 35% 的项目，而 Cookie 方式为 0%。

会话流量则不同。当 WebSocket 升级失败、`socket.io` 回退到 XHR 轮询时，同一会话的连续轮询必须到达同一个副本，而路径中没有可供哈希的项目标识符。这类流量需要一个单独的、带有 Cookie 亲和性的后端。我们设计了这种拆分，但并未部署；我们将其标记为一个缺口，而不是声称已经实现。

最后，`/git/` 必须到达运行 `git-bridge` 的那个副本。它被路由到该副本而不是直接路由到 `git-bridge`，因为 bridge 会通过应用的 OAuth 端点验证其回调，并通过应用解析 blob URL；绕过副本只会破坏身份验证，而不会带来任何改善。

### 9.4 缩容需要排空缓冲期

移除副本与添加副本并不对称：正在进行的编译会丢失，用户会看到一个并非由他们造成的失败。可行的顺序是先停止新流量，等待，然后才终止。我们将其实现为一个 pre-stop 钩子，在负载均衡器将后端标记为排空状态期间，将 Pod 保持一个可配置的时长——测试时短到几分钟即可，而在生产环境中则长到足以让会话自然结束，以小时而不是秒计。这个时长就是决定弹性是无感还是令人恼火的调节旋钮。

还有一个约束是我们通过测量而非设计发现的：基于 CPU 的自动扩缩容对这一工作负载不起作用。应用 Pod 自身的利用率只有 22 m core，而节点总量为 3997 m core，因为编译工作发生在 Pod 不计入的兄弟容器中。用于扩缩这一层的任何信号，都必须统计正在运行的编译容器，而不是 Pod 的 CPU。

## 10. Overleaf 之外的启示

§4.2 和 §4.3 中的内容没有任何一处是 Overleaf 代码所特有的。测得的规律源于任何托管式 LaTeX 服务都具备的三个特性：工作单元是一个单线程进程，它被隔离在容器中，其工作集是一个必须由页缓存承载的大型只读目录树。由此得出的三个结论可以直接迁移到任何构建此类服务的人。

### 10.1 先配置内存，再配置核心

该矩阵最有力的结果是否定性的：在 16 GiB 以下，核心数几乎无关紧要，只有到 48 GiB 时，4、8 和 16 vCPU 的配置才拉开差距（143、268、331）。把常规法则理解为"每五个用户加一个核心"的运维人员买错了资源。其机制是发行版目录树上的共享页缓存，这是 TeX Live 体量的属性，而不是任何特定前端的属性。

### 10.2 准入速率是一种资源，而它通常被遗忘

在 $N=1024$ 时，尽管所有请求同时到达，我们的服务器上存活的沙盒从未超过 205 个（图 7b）。限制因素是容器创建，而不是编译——这与那些将容器启动成本归因于运行时开销而非镜像大小的测量研究一致 \[19, 20]。只按 CPU 和内存确定规格的服务，会发现其突发行为受一个从未测量过的量支配。其实际形式就是 §8 的建议：有意识地限制准入，因为你主动选择的队列，好过你事后才发现的队列。

### 10.3 比编译活得更久的沙盒会使模型失效

这里的每个容量数字都假设容器被创建、执行一次编译然后退出——生命周期为数十秒，并且只在运行时占空比接近一。最近的两种设计模式打破了这一假设，而且打破的方式相同。

第一种是每用户持久沙盒。为每个用户分配一个固定的私有环境，会把一个统计复用的资源池变成一组预留：一个通过分时可以在 64 个核心上服务 256 个并发编译的服务，如果给每个用户分配四个专用核心，就只能服务 16 个用户，在同样的硬件下少了一个数量级。我们的数据量化了这一选择的代价，而不是反对它——预留换来的是可预测性，在我们推荐的工作点上，兑换比例大约是 $16\times$。

第二种，也是更新的一种，是与编译器共享沙盒的 AI 智能体。在智能体辅助的写作平台中，运行 XeLaTeX 的同一个容器可能还承载着一个长期运行的编程智能体，因此它被持续占用，而不是突发占用。实践者报告的正是模型对此类部署所预测的症状——在用户数不多时就出现持续的迟缓 \[15]。这种相互作用值得精确表述，因为它并不只是"负载更多"。我们的三项发现会相互叠加。占用不再是突发的，因此 §4.2 的分时规律同时作用于整个用户群，而不只是当前正在编译的那一部分。页缓存——正是它带来了 §4.1 中超线性的内存回报——现在要与智能体自己的工作集共享，对 TeX 而言不再是热的。而 §6.2 中缺失的容器内存限制会变得危险得多，因为一个永不退出的容器永远不会归还它的内存。

我们没有测量过此类平台，也不对任何具体产品做出论断。我们能说的是我们的数据对设计意味着什么：一个为每个用户提供长生命周期多核沙盒的架构，应当按预留系统来确定规格，而不是依据本文报告的并发数字；它所能期望的容量，更接近其核心数除以每用户核心数，而不是表 1 中的任何数字。

## 11. 有效性威胁

### 11.1 单一文档

所有测量都使用同一份 63 页的 XeLaTeX 文档。对于其他文档，绝对容量会有所不同；但扩展规律作为比例关系，不应改变。一份驻留内存大得多的文档会移动内存墙的位置，但不会改变其超线性特征。

### 11.2 虚拟化宿主机

虚拟机运行在一台物理机器上的 KVM 中，因此绝对数值包含虚拟化开销，并且各虚拟机共享宿主机的页缓存和 NVMe 设备。在观察到宿主机内存压力会使相同并发下的虚拟机内负载均值膨胀超过 $3\times$ 之后，我们关闭了无关的虚拟机，从而缓解了最大的混杂因素。

### 11.3 同时到达

每个编译都在同一时刻发出，这是最坏情况。真实用户以随机过程到达，因此按照我们的数据确定规格的部署会有余量而不是不足——但提交截止时间前的峰值更接近我们的模型，而不是泊松模型。

### 11.4 边缘配置

在 2 GiB 时，系统已经接近崩溃，同一配置的重复运行结果可能相差一个编译。我们报告保守值，并且不从该状态下 $\pm 1$ 的差异中得出结论。

## 14. 结论

自托管 Overleaf 的容量规划并不是扩展单一资源的问题。有三项发现应当改变容量规划的做法。

第一，在虚拟机内存低于 32 GiB 时，核心数几乎无关紧要：在 16 GiB 时，4、8 和 16 vCPU 虚拟机的容量相差不到 8%。设定上限的是内存——通过 TeX Live 目录树上的共享页缓存；只有在内存充裕之后，核心才开始起作用。

第二，两个软件参数比硬件更重要。解除 CLSI 硬编码的 65 个编译上限并提高默认的 180 s 编译超时后，一台 8 vCPU / 48 GiB 虚拟机的并发编译数从 64 提升到 268——无需任何额外硬件即提升 4.2 倍。两者都无法从配置文档中发现；其中一个甚至根本无法配置。

第三，"这台机器支持多少并发用户"这个问题本身没有被充分定义。该系统中的并发是纯粹的分时，容量就是超时所能容纳的量。如实的回答应当同时说明两者：_如果用户愿意等待_ $T$ _秒，这台机器可以服务_ $N$ _个同时编译_，其中 $N$ 和 $T$ 通过公式 (1) 相关联。

我们还报告了一个潜在缺陷：Docker 运行器中的每容器内存限制自 2018 年以来一直无效，无论是数值大小还是设置位置都有问题。其实际影响是，小型部署上的内存耗尽会拖垮整个服务，而不只是导致问题的那一次编译。
