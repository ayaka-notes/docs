## 二进制文件迁移

Server Pro 和社区版即将发布的大版本 `6.0` 将把二进制文件的存储占用减少一半。版本 `5.5.7` 中包含一个在线迁移，可在升级过程中将停机时间降至最低。

自 Server Pro `4.x` 起，二进制文件会被存储两次：一次在 "filestore" 的活动文件存储中，另一次在完整项目历史系统中。今后，每个文件只会在完整项目历史系统中存储一份副本。

迁移到整合存储系统包含两个部分：一个用于控制迁移阶段的新标志，以及一个处理所有活动项目和软删除项目的脚本。

阶段：

* `OVERLEAF_FILESTORE_MIGRATION_LEVEL=0`（默认）：文件从 filestore 读取并写入 filestore，同时异步写入历史系统。
* `OVERLEAF_FILESTORE_MIGRATION_LEVEL=1`：文件从历史系统读取（回退到 filestore），并同时写入 filestore 和历史系统。可以降级到 `OVERLEAF_FILESTORE_MIGRATION_LEVEL=0`。
* `OVERLEAF_FILESTORE_MIGRATION_LEVEL=2`：文件只从历史系统读取和写入。无法降级到 `OVERLEAF_FILESTORE_MIGRATION_LEVEL=1`，除非迁移是以"离线"方式执行的。

如果你将数据存储在 [S3](https://docs.overleaf.com/on-premises/configuration/overleaf-toolkit/s3) 中，并为 filestore（`OVERLEAF_FILESTORE_S3_ACCESS_KEY_ID`）和 history（`OVERLEAF_HISTORY_S3_ACCESS_KEY_ID`）使用不同的服务账户：请为 filestore 用户授予对存放 blob 的历史存储桶 `OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET` 的读取权限。今后，filestore 服务将负责响应来自编译服务的读取请求。

<Warning>

强烈建议先在非生产/沙箱环境中执行二进制文件迁移。

</Warning>

<Check>

标准的 Server Pro 许可证允许你在一个生产环境以及一个非生产/沙箱环境中运行本应用；强烈建议你准备一个非生产环境用于测试。

</Check>

<Info>

如果你升级到 Server Pro/CE `6.0` 版本后又决定降级到早期版本，则应从完整的系统备份中恢复。

</Info>

<Steps>
<Step title="创建备份">
为你的实例创建一份完整的[备份](https://docs.overleaf.com/on-premises/maintenance/data-and-backups#performing-a-consistent-backup)，其中包含 **mongo**、**redis** 和 **sharelatex** 目录的一致性快照。
</Step>

<Step title="更新">
**Toolkit：** 使用 `$ bin/upgrade` 脚本将 **toolkit** 升级到最新版本。当出现提示时，**不要**确认 **Upgrade** image? 提示——而是手动编辑 **config/version** 文件，将其值设置为 `5.5.7`。

**旧版 docker-compose.yml：** 将 `sharelatex` 服务的版本更新为 `5.5.7`。
</Step>

#### 离线迁移

如果你想在二进制文件迁移脚本运行期间阻止用户登录，请按以下步骤操作：

* 使用管理员账户登录你的 Overleaf 实例
* 点击 **Admin** 按钮并选择 **Manage Site**
* 点击 **Open/Close Editor** 标签页
* 点击 **Close Editor** 按钮
* 点击 **Disconnect all users** 按钮

完成上述操作后，所有已登录的用户都将被重定向到维护页面，任何访问登录页面的新用户也会看到维护页面，并且**无法**登录。

重启实例时需要重复这些步骤。要重新开放站点，只需重启实例即可。

#### 在线迁移

可以在应用仍在运行时执行迁移脚本。需要考虑以下几点：

* 迁移过程是 IO 密集型的，脚本运行期间应监控资源使用情况。
* 如果处理并发度较高，`filestore` 服务的事件循环可能会出现阻塞，从而导致用户体验下降。我们建议从默认值 `--concurrency=10` 和 `--concurrent-batches=1` 开始。
* 你可以随时停止脚本。再次启动时，脚本会验证之前处理过的项目，并跳过已处理的文件。如果你希望在不太繁忙的时段（例如夜间）运行迁移，这一点会很有用。

我们的建议是：当项目数量少于 1000 个时（参见使用 `--report` 运行迁移脚本时的输出），关闭站点并在维护窗口内离线运行迁移。如果项目数量很多，你可以先运行脚本并监控其进度，然后根据具体情况决定继续在线运行还是改为离线运行。

#### 清理旧的二进制文件数据

完成迁移并确认项目仍能访问其所有文件后，可以删除 `/var/lib/overleaf/data/user_files` 中的旧文件存储。我们强烈建议将这些文件保留一段时间——你可以先重命名该文件夹，使其对应用不可访问。

#### 文件缺失

旧版本的 Server Pro/CE 会在用户上传完成之前就创建文件树条目，这可能导致上传失败时文件显示为缺失。在处理所有文件树时，你可能会发现少数此类情况被报告为错误。

如果缺失文件的数量较少，可以考虑手动检查这些情况，并在浏览器中通过编辑器将其删除。

如果缺失文件的数量较多，请考虑联系支持团队，参见上面的邮件模板。

#### 查找损坏的文件树

对于文件树格式错误的项目（例如文件名为空），迁移可能会失败。你可以使用 `find_malformed_filetrees` 脚本检查数据库中的所有项目，从而获取这些问题的列表：

```bash wrap
$ bin/docker-compose exec sharelatex /bin/bash -c "cd /overleaf/services/web && /sbin/setuser www-data node scripts/find_malformed_filetrees.mjs > /tmp/malformed-file-trees.json"
```

要修复无效路径，请使用 `fix_malformed_filetree` 脚本，对每个错误路径分别运行一次该命令：

```bash wrap
$ bin/docker-compose exec sharelatex /bin/bash -c "cd /overleaf/services/web && /sbin/setuser www-data node scripts/fix_malformed_filetree.mjs --logs=/tmp/malformed-file-trees.json"
```
