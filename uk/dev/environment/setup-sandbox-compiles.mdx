Компіляція в пісочниці в середовищі розробки працює трохи інакше, ніж у продакшн-образі. У середовищі розробки її вже налаштовано; на цій сторінці пояснено налаштування та три моменти, про які варто пам'ятати:

* Проблема з правами доступу до файлів
* Спільний том для history-v1 та filestore
* Проблема з підкаталогами

### Увімкнення ізольованої компіляції {#enable-sandbox-compiles}

Компіляцію в пісочниці ввімкнено за замовчуванням. `develop/docker-compose.yml` задає `SANDBOXED_COMPILES=true` для `clsi`, а `develop/dev.env` містить решту:

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

clsi не завантажує образи сам, тому завантажте їх один раз командою `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1` (і `:2025.1`).

LaTeX працює в сусідніх контейнерах від імені `TEXLIVE_IMAGE_USER`. У середовищі розробки це `tex`, що також є значенням за замовчуванням для clsi (`services/clsi/config/settings.defaults.cjs:154`). Продакшн-образ натомість використовує `www-data`, коли `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` (`server-ce/config/env.sh:15-21`), бо там файли створює користувач `www-data` контейнера Overleaf.

<Warning>

Будь ласка, не використовуйте власноруч зібраний образ — ви можете зіткнутися з низкою помилок.

</Warning>

### Виправлення прав доступу до файлів {#fix-file-permissions}

Контейнер clsi запускається від root, передає теки `compiles`, `output` і `cache` користувачеві `node` (uid `1000`), а потім запускає clsi від імені `node` (`services/clsi/entrypoint.sh`). Тому `develop/compiles` на хості належить uid `1000`, тому самому uid, що й у `tex` у середовищі розробки (див. коментар у `develop/pandoc/Dockerfile`). З наведеними вище налаштуваннями середовище розробки компілює без жодних змін прав.

Якщо натомість задати `TEXLIVE_IMAGE_USER=root`, root (uid `0`) не має права записувати в підтеки `compiles`. У такому разі надайте групі `root` володіння та право запису на `compiles` і встановіть `setgid`, щоб нові підтеки успадковували це володіння:

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

Докладну документацію див. у `services/clsi/README.md`.

### Спільний том для history-v1 та filestore {#volume-share-between-history-v1-and-filestore}

<Info>

Налаштування з цього й наступного розділу вже є в `develop/docker-compose.yml` і `develop/dev.env`. Вони мають значення лише за `S3_ENABLED=false` у `develop/dev.rc`. За значення за замовчуванням `S3_ENABLED=true` filestore і history-v1 зберігають ці файли в бакетах RustFS (`develop/s3/docker-compose.yml`).

</Info>

За замовчуванням filestore виконує роль мосту між S3 та іншими сервісами Overleaf. Однак в Overleaf CE або Server Pro всі файли за замовчуванням зберігаються локально. Тому в Overleaf запровадили доволі хитромудрий метод.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

Водночас `data/history` використовує й сервіс історії. Так різні мікросервіси можуть спільно використовувати ті самі дані. Тому сервіс filestore у develop монтує том `history-v1-buckets` сервісу history-v1. Без нього **clsi не зможе отримувати blob-файли із сервісу filestore**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

filestore знаходить бакети через ці налаштування в `dev.env`:

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### Використання підкаталогів {#use-subdirectories}

filestore завжди читає blob-об'єкти історії з підкаталогами (`services/filestore/app/js/KeyBuilder.js:58`, `:70`). Продакшн-образ вмикає `useSubdirectories` для history-v1 (`server-ce/config/production.json`), а типова конфігурація history-v1 ні, тому в розробці history-v1 <strong>зробив би всі дані пласкими.</strong> Тож `dev.env` задає `NODE_CONFIG` для history-v1:&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

Без цього history-v1 зберігає файли `project_blobs` так:

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

Коли `useSubdirectories` дорівнює `true`, символ `_` у цих назвах стає `/`, тож кожен blob зберігається у вкладених теках.
