Рекомендований спосіб розгортання та керування екземплярами Overleaf Server CE і Overleaf Pro — використання Toolkit.

Toolkit спрощує створення вашого екземпляра Overleaf завдяки набору спеціальних скриптів, які приховують оркестрацію необхідних мікросервісів. Достатньо запустити вбудований скрипт ініціалізації та вказати кілька параметрів конфігурації, як-от шляхи до постійного сховища, — і Toolkit сам подбає про розгортання та з'єднання мікросервісів, з яких складається ваш екземпляр Overleaf Server CE або Pro.

Це дає вам змогу зосередитися на налаштуванні користувацького досвіду та впровадженні конкретних функцій вашого локального екземпляра. Toolkit бере всю складність на себе, забезпечуючи спрощене розгортання вашого екземпляра Overleaf.

<Info>

З історичних причин основний контейнер Overleaf називається `sharelatex` і базується на Docker-образі `sharelatex/sharelatex`. Це пов'язано з тим, що технологія ґрунтується на кодовій базі ShareLaTeX, яку було об'єднано з Overleaf. Докладніше читайте в [цьому дописі в блозі](https://www.overleaf.com/blog/518-exciting-news-sharelatex-is-joining-overleaf). Колись у майбутньому його буде перейменовано відповідно до схеми найменувань Overleaf.

</Info>

#### Архітектура

Усередині контейнера Overleaf програмне забезпечення працює як набір мікросервісів, якими керує `runit`. Ось деякі з найцікавіших файлів усередині контейнера:

* `/etc/service/`: файли ініціалізації мікросервісів.
* `/var/log/overleaf/`: логи кожного мікросервісу.
* `/overleaf/services/`: код різних мікросервісів.
* `/var/lib/overleaf/`: точка монтування для постійних даних (відповідає каталогу, вказаному в `OVERLEAF_DATA_PATH` на хості).

#### Контейнери MongoDB і Redis

Overleaf залежить від двох зовнішніх баз даних: MongoDB і Redis. За замовчуванням Toolkit розгортає окремий контейнер для кожної з цих баз даних на додаток до контейнера Overleaf — разом три Docker-контейнери.

<Info>

Якщо ви бажаєте під'єднатися до наявного екземпляра MongoDB або Redis, це можна зробити, вказавши відповідні параметри в конфігураційному файлі [overleaf.rc](/uk/on-premises/configuration/overleaf-toolkit/files-and-locations#the-overleaf.rc-file).

</Info>

#### Редактор і процес компіляції

У цьому розділі наведено загальний огляд обробки документів і процесу компіляції.

<Info>

На цій сторінці описано процес компіляції із Sandboxed Compiles, доступний лише в Overleaf Pro. У Server CE процес компіляції використовує прості підпроцеси — замініть пункти, що стосуються **контейнера**, одним пунктом **запуск компіляції в підпроцесі**.

</Info>

Компоненти / учасники:

* `user` — користувач застосунку
* `editor` — клієнтський застосунок, що працює в браузері
* `clsi` — мікросервіс для компіляції PDF
* `document-updater` — мікросервіс для обробки оновлень документів
* `filestore` — мікросервіс для роботи з бінарними файлами
* `real-time` — мікросервіс для обробки вебсокетів
* `web` — (не такий уже й мікро) сервіс для обробки API-запитів

**Кешування в Redis**

* **user**: завантажує сторінку редактора
* **editor**: відкриває вебсокет
* **editor**: надсилає через вебсокет запит на відкриття документа
  * **real-time** -> **document-updater**: документ завантажується з MongoDB у Redis
* **editor**: надсилає оновлення документа через вебсокет
  * **real-time** -> **document-updater**: документ оновлюється в Redis
* **editor**: надсилає нові запити на компіляцію
  * Через 5 хвилин після останнього скидання (для кожного документа):
    * **document-updater**: скидає документ із Redis у MongoDB
* **editor**: надсилає нові оновлення
  * кожні 100 оновлень (для кожного документа):
    * **document-updater**: скидає історію документа з Redis у MongoDB
* **user**: залишає редактор/закриває вкладку браузера
  * через 5 хвилин
    * **real-time**: перевіряє наявність інших співавторів; якщо їх немає:
      * **real-time** -> **document-updater**: скидає документи з Redis у MongoDB

**Читання з MongoDB у Redis**

* **document-updater** -> **web** -> **docstore**: читання з MongoDB

**Скидання з Redis у MongoDB**

* **document-updater** -> **web** -> **docstore**: запис у MongoDB

**Компіляція — режим синхронізації "full"**

* **editor**: надсилає запит на компіляцію з режимом синхронізації "full"
* **web** -> **document-updater**: усі документи скидаються з Redis у MongoDB
* **web** -> **docstore**: усі документи завантажуються з MongoDB
* **web** -> **clsi**: до `clsi` надсилається запит на компіляцію, що містить:
  * режим синхронізації
  * хеш дерева файлів -> "стан проєкту"
  * усі документи з їхнім вмістом -> діє обмеження розміру тіла запиту 7MB
  * URL бінарних файлів для окремого завантаження
* **clsi**: перевіряє стан на диску з урахуванням режиму синхронізації та "стану проєкту"
  * це повна синхронізація, тому попередній стан на диску можна ігнорувати
* **clsi**: очищує каталог компіляції
* **clsi**: записує всі документи в каталог компіляції
* **clsi**: записує всі бінарні файли в каталог компіляції
  * `clsi` копіює файли з локального кешу проєкту
  * у разі промаху кешу:
    * **clsi** -> **filestore**: завантажує файли
* **clsi**: записує "стан проєкту"
* **clsi**: переконується, що Docker-контейнер існує з потрібною конфігурацією
  * формує параметри контейнера, зокрема версію texlive
  * хешує параметри
  * назва контейнера: `project-<project-id>-<user-id>-<hash>`
* **clsi**: запускає контейнер і передає stdout/stderr у пам'ять -> обмеження 2MB
* **clsi**: залишає зупинений контейнер -> його буде видалено через 24 години
* **clsi**: записує stdout/stderr на диск
* **clsi**: копіює вихідні файли в унікальний вихідний каталог
  * build-id складається з 8 випадкових байтів і мітки часу з точністю до мілісекунд
  * видаляє всі каталоги збірок, крім останніх 3 (анонімний користувач) / останнього 1 (користувач, що увійшов у систему)
* **clsi**: компіляція завершилася помилкою/тайм-аутом
  * видаляє кеш компіляції — він може містити неповні файли або бути пошкодженим
* **editor**: завантажує output.log і output.pdf

**Компіляція — режим синхронізації "incremental"**

* **editor**: надсилає запит на компіляцію з режимом синхронізації "incremental"
* **web** -> **document-updater**: отримує всі документи з Redis
  * хеш "стану проєкту" також зберігається в Redis
  * **web** надсилає хеш дерева файлів до `document-updater`, і `document-updater` може перетворити інкрементальну компіляцію на повну в разі невідповідності
    * див. процес компіляції, що виконується, коли редактор запитує компіляцію "full"
* **web** -> **clsi**: до `clsi` надсилається запит на компіляцію, що містить:
  * режим синхронізації
  * хеш дерева файлів -> "стан проєкту"
  * усі документи з Redis з їхнім вмістом -> діє обмеження розміру тіла запиту 7MB
  * без бінарних файлів
* **clsi**: перевіряє стан на диску з урахуванням режиму синхронізації та "стану проєкту"
  * це інкрементальна синхронізація, тому "стан проєкту" має збігатися
  * у разі невідповідності: відповідає кодом 409, і web повторює спробу із синхронізацією "full"
    * див. процес компіляції, що виконується, коли редактор запитує компіляцію "full"
* **clsi**: записує оновлені документи в каталог компіляції
* **clsi**: переконується, що Docker-контейнер існує з потрібною конфігурацією
  * формує параметри контейнера, зокрема версію texlive
  * хешує параметри
  * назва контейнера: `project-<project-id>-<user-id>-<hash>`
* **clsi**: запускає контейнер і передає stdout/stderr у пам'ять -> обмеження 2MB
* **clsi**: залишає зупинений контейнер -> його буде видалено через 24 години
* **clsi**: записує stdout/stderr на диск
* **clsi**: копіює вихідні файли в унікальний вихідний каталог
  * build-id складається з 8 випадкових байтів і мітки часу з точністю до мілісекунд
  * видаляє всі каталоги збірок, крім останніх 3 (анонімний користувач) / останнього 1 (користувач, що увійшов у систему)
* **clsi**: компіляція завершилася помилкою/тайм-аутом
  * видаляє кеш компіляції — він може містити неповні файли або бути пошкодженим
* **editor**: завантажує output.log і output.pdf

**Компіляція — перемикання між режимами**

* **editor**: фіксує невдалу компіляцію — наступна компіляція буде "full"
* **editor**: фіксує успішну компіляцію — наступна компіляція буде "incremental"
