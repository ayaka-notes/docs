<Accordion title="Запуск Overleaf із файловою системою NFS">

Монтування файлової системи NFS у контейнер Overleaf технічно можливе, але не рекомендоване і може призводити до різних проблем із продуктивністю.

Одна з поширених помилок, що виникає під час компіляції:

```text
EBUSY: resource busy or locked, unlink '/var/lib/overleaf/data/compiles/62f3d57bef7cf9005c364e75-62f3d57bef7cf9005c364e7a/.nfs573663533034825247625441'
```

Зокрема, ми не радимо використовувати файлові системи на основі NFS для тимчасових даних, наприклад для каталогів із даними компіляції. Для наведених нижче каталогів радимо використовувати локальний робочий диск, бажано локальний SSD.

Для інсталяцій на основі `docker-compose` пропонуємо просто перевизначити bind-mount з NFS, що дає змогу не змінювати шляхи в застосунку. Ось приклад фрагмента конфігурації `docker-compose` з використанням робочого диска, змонтованого в `/scratch`:

```yaml title="docker-compose excerpt"
services:
  sharelatex:
    environment:
      SANDBOXED_COMPILES_HOST_DIR: /scratch/compiles/
    volumes:
      - nfs:/var/lib/overleaf/data
      - /scratch/cache/:/var/lib/overleaf/data/cache
      - /scratch/compiles/:/var/lib/overleaf/data/compiles
      - /scratch/output/:/var/lib/overleaf/data/output
      - /scratch/tmp/:/var/lib/overleaf/tmp
```

Після оновлення немає потреби переносити наявні файли з NFS у нове місце. Компілятор LaTeX може повторно створити всі файли під час повної компіляції.

Докладніше див.: https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-with-an-nfs-filesystem

</Accordion>

<Accordion title="Під час запуску Overleaf у Windows або macOS служба `mongo` не запускається">

Якщо ви запускаєте Overleaf у Windows або macOS, служба `mongo` може не перезапуститися з такою помилкою:

```text title="Example error"
Failed to start up WiredTiger under any compatibility version.
Reason: 1: Operation not permitted
```

Це може статися, коли дані MongoDB підключено через bind mount з файлової системи, яка не забезпечує потрібної їй семантики, наприклад з каталогу, змонтованого з Windows. Для [Windows з WSL 2](/uk/on-premises/installation/using-docker-compose/windows) тримайте Toolkit у домашньому каталозі Linux в Ubuntu й використовуйте bind mount за замовчуванням. Див. [перевірки MongoDB](/uk/on-premises/installation/using-docker-compose/windows/troubleshooting#mongodb-fails-to-start) у посібнику для цієї платформи.

Для нової інсталяції, якій потрібне сховище під керуванням Docker, наведене нижче перевизначення використовує іменовані томи (див. [рекомендації щодо зберігання даних для образу MongoDB](https://github.com/docker-library/docs/blob/master/mongo/content.md#where-to-store-data)). У наявній інсталяції зміна точок монтування не переносить дані: перед перемиканням створіть резервну копію бази даних і кешу та відновіть їх, інакше сервіс побачить порожні томи. Додайте це до `config/docker-compose.override.yml`, об'єднавши з наявною конфігурацією:

```yaml title="config/docker-compose.override.yml"
volumes:
  mongo-data:
  redis-data:

services:
  mongo:
    volumes:
      - mongo-data:/data/db

  redis:
    volumes:
      - redis-data:/data
```

Докладніше див.: https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-on-windows-or-macos-results-in-the-mongoservice-not-starting

</Accordion>

<Accordion title="Оновлення до Redis 6.2 призводить до циклу перезапусків">

Скористайтеся командою `docker logs redis`, щоб вивести копію журналів.

Якщо ви бачите рядок `Fatal: Can't initialize Background Jobs`, повний вивід виглядатиме приблизно так:

```text title="Redis log example"
1:M 11 Feb 2024 15:19:22.609 # Server initialized
1:M 11 Feb 2024 15:19:22.609 # Fatal: Can't initialize Background Jobs.
1:C 11 Feb 2024 15:19:26.055 # oO0OoO0OoO0Oo Redis is starting oO0OoO0OoO0Oo
```

Це може бути пов'язано з версією Docker, що використовується. Оновлення до версії >= 20.10.10 має розв'язати цю проблему.

Докладніше див. відповідну проблему в Redis: https://github.com/redis/redis/issues/12362

Джерело: https://docs.overleaf.com/on-premises/support/troubleshooting#upgrading-to-redis-6.2-results-in-a-restart-loop

</Accordion>

<Accordion title="Неправильна орієнтація зображень попереднього перегляду/мініатюр у галереї шаблонів">

Іноді зображення попереднього перегляду/мініатюри, згенеровані Ayakaleaf Pro, можуть мати неправильну орієнтацію, і їх потрібно виправити вручну. Ці зображення зберігаються в `/var/lib/overleaf/data/template_files/`.

Перед внесенням будь-яких змін радимо створити резервну копію цієї папки.

Для кожного проблемного шаблону потрібно виконати наведені нижче кроки:

Знайдіть ID шаблонуПерейдіть до галереї шаблонів вашого екземпляра (/templates/all), відкрийте проблемний шаблон і скопіюйте ID з URL-адреси (наприклад: https://your-instance-url/templates/6645d346c224815e9460a695).Виконайте команду виправленняВиконайте наведену нижче команду на хості Docker (замініть ID шаблону на скопійований і за потреби оновіть шлях):docker exec sharelatex /bin/bash -c "mogrify -rotate 90 /var/lib/overleaf/data/template\_files/6645d346c224815e9460a695\_\*\{thumbnail,preview\}"

Джерело: https://docs.overleaf.com/on-premises/support/troubleshooting#incorrect-orientation-of-template-gallery-preview-thumbnail-images

</Accordion>

<Accordion title="Переконайтеся, що ви ввімкнули системні виклики. Для pdflatex це 'pdflatex -shell-escape'.">

Команду `\write18` у Community Edition за замовчуванням вимкнено, оскільки всі компіляції відбуваються в одному контейнері `sharelatex`; це безпечніше налаштування за замовчуванням.

Якщо ви хочете ввімкнути її для pdflatex, створіть у корені проєкту файл `latexmkrc` з таким вмістом:

```perl title="latexmkrc"
$pdflatex = 'pdflatex --shell-escape';
```

Потім спробуйте скомпілювати повторно.

Джерело: https://docs.overleaf.com/on-premises/support/troubleshooting#please-verify-that-you-have-enabled-system-calls.-for-pdflatex-this-is-pdflatex-shell-escape

</Accordion>

<Accordion title="`bin/up` завершується помилкою `unable to upgrade to tcp, received 409` або `OCI runtime exec failed` після «Initiating Mongo replica set...»">

Ці помилки означають, що контейнер `mongo` постійно аварійно завершується й перезапускається. `bin/up` запускає MongoDB, а потім виконує в ньому команду, яка не вдається, поки контейнер перезапускається. `bin/docker-compose ps` показує сервіс `mongo` у стані `Restarting`.

Щоб знайти справжню причину, прочитайте журнал MongoDB:

```sh
bin/logs mongo
```

Поширені причини:

* <strong>Процесор не підтримує AVX.</strong> MongoDB 5.0 і новішим версіям потрібна підтримка AVX на x86-64, а в журналі з'являється `MongoDB 5.0+ requires a CPU with AVX support`. У віртуальній машині встановіть тип процесора `host`, щоб AVX передавався до неї.
* <strong>Ядро Linux від 6.19 до 7.0.13.</strong> MongoDB відмовляється запускатися на цих ядрах. Обхідний шлях див. у розділі [Вимоги до програмного забезпечення](/uk/on-premises/installation/introduction#software-requirements).
* <strong>Дані створено старішою версією MongoDB.</strong> MongoDB 8.0 не може безпосередньо відкрити дані з 4.4 або 5.0. Оновлюйтеся на одну мажорну версію за раз, див. [Оновлення MongoDB](/uk/on-premises/maintenance/updating-mongodb).

</Accordion>

<Accordion title="Журнал показує «Running Overleaf Community Edition, skipping TexLive checks»">

Для Ayakaleaf Pro це очікувано, і це повідомлення можна ігнорувати. Воно виводиться, коли `OVERLEAF_IS_SERVER_PRO` не дорівнює `true`, що й має місце в образі Ayakaleaf Pro. Ayakaleaf Pro не потребує цієї змінної, тож залиште її незаданою.

</Accordion>

<Accordion title="Контейнер `sharelatex` постійно перезапускається">

Перш ніж Overleaf запуститься, контейнер виконує стартові перевірки й завершує роботу, якщо одна з них не проходить. Toolkit запускає його з `restart: always`, тож Docker знову запускає його, і та сама перевірка знову не проходить. У стартовому виводі зазначено, яка перевірка не пройшла:

```sh
bin/docker-compose logs --tail=100 sharelatex
```

Поширені причини:

* **`Missing required secrets`**: установіть `OVERLEAF_INVITE_TOKEN_SECRET` у `config/variables.env`, див. [Змінні середовища](/uk/on-premises/configuration/overleaf-toolkit/environment-variables).
* **`ShareLaTeX to Overleaf rebranding`**: конфігурація досі використовує змінні або шляхи `SHARELATEX_`; перейменуйте їх, як зазначено в повідомленні.
* **Помилка після `Checking can connect to mongo and redis`**: Overleaf не може підключитися до MongoDB або Redis. Перевірте `bin/logs mongo` і `bin/logs redis`.

Після усунення причини виконайте `bin/up -d`.

</Accordion>

<Accordion title="Контейнер зупиняється на `910_initiate_doc_version_recovery` або завершується з кодом 2">

Під час кожного запуску контейнер по черзі виконує свої стартові скрипти, і журнал називає кожен із них як `*** Running /etc/my_init.d/<script>...`. `910_initiate_doc_version_recovery` має що робити лише на екземплярах, які колись працювали на Overleaf 5.0.1. На будь-якому іншому екземплярі він виводить `No recovery of doc versions needed.`, і запуск продовжується. Його вивід також записується до `data/history/doc-version-recovery.log` в `OVERLEAF_DATA_PATH`.

Код завершення та кінець виводу `bin/docker-compose logs --tail=100 sharelatex` показують, що сталося:

* **Код завершення 2**, і журнал закінчується рядком `*** Init system aborted.`: контейнер було зупинено, наприклад командою `bin/stop`, `docker stop` або натисканням Ctrl+C під час `bin/up`. Скрипт в останньому рядку `Running` — це лише той, що виконувався в той момент, і він не завершився з помилкою. Запустіть контейнер знову за допомогою `bin/up -d` і дочекайтеся завершення запуску.
* **Код завершення 1**, і журнал показує `*** /etc/my_init.d/<script> failed with status <n>`: цей скрипт завершився з помилкою, і її текст наведено в рядках безпосередньо вище. Якщо `910_initiate_doc_version_recovery` завершився з помилкою `Detected unflushed changes while recovering doc versions`, екземпляр працював на 5.0.1 і досі має не збережені на диск (unflushed) зміни; дотримуйтеся офіційного посібника [Doc version recovery](https://docs.overleaf.com/on-premises/release-notes/release-notes-5.x.x/doc-version-recovery).

</Accordion>

<Accordion title="«Restricted, sorry you don’t have permission to load this page»">

Ця сторінка з'являється, коли ви ввійшли у свій обліковий запис, але не маєте дозволу відкривати цю сторінку, наприклад сторінку адміністратора, відкриту обліковим записом, що не є адміністратором, або проєкт, яким з вами не поділилися.

Щоб відкрити сторінки адміністратора, увійдіть з обліковим записом адміністратора. Наявний адміністратор може зробити інший обліковий запис адміністратором, або ви можете створити його командою `create-user --admin`, див. [Керування користувачами](/uk/on-premises/user-and-project-management/user-management). У середовищі розробки (`develop/`) для сторінок адміністратора також потрібно `ADMIN_PRIVILEGE_AVAILABLE=true` у `develop/dev.env`; в образі Ayakaleaf Pro це вже встановлено.

</Accordion>
