RHEL і його перезбірки (Rocky Linux, AlmaLinux) постачаються з Podman замість Docker, а деякі організації не дозволяють Docker на своїх серверах. Toolkit може запускати Ayakaleaf Pro на **rootless Podman**: контейнери працюють від імені звичайного користувача, компіляція, як і раніше, виконується в ізольованих контейнерах TeX Live, а SELinux залишається в режимі enforcing. Скрипт `bin/podman-setup` перевіряє хост і виправляє те, що може.

Наприкінці цього розділу у вас буде такий самий екземпляр, як у розділі [Використання Docker Compose](/uk/on-premises/installation/using-docker-compose): Ayakaleaf Pro з ізольованою компіляцією, MongoDB і Redis, яким ви керуєте звичними командами `bin/up`, `bin/doctor` і `bin/upgrade`.

<Info>

Підтримка Podman експериментальна. Вона походить з офіційного Overleaf Toolkit, який тестує її лише в RHEL 9 і новіших з rootless Podman, ізольованою компіляцією та SELinux у режимі enforcing. Ми перевірили ці сторінки на Rocky Linux 9.9 (Podman 5.8, SELinux enforcing) з Ayakaleaf Pro 6.3.4. Рекомендованим середовищем виконання контейнерів залишається Docker.

</Info>

### Що вам потрібно {#what-you-need}

* **RHEL, Rocky Linux, AlmaLinux або CentOS Stream 9 чи новіший** із SELinux у режимі enforcing. На будь-якому іншому дистрибутиві `bin/podman-setup` зупиняється. В Ubuntu або Debian використовуйте [Використання Docker Compose](/uk/on-premises/installation/using-docker-compose/linux).
* **Користувач без прав root з доступом до `sudo`**, якому належатимуть контейнери. Виконуйте всі команди цього розділу від імені цього користувача; `bin/podman-setup` відмовляється запускатися від `root`.
* **Чистий хост**: без Docker Engine і без наявної установки Toolkit. Перенесення наявного екземпляра на Docker у Podman тут не описано.

### Чим це відрізняється від Docker {#how-it-differs-from-docker}

|                                   | Docker                                  | Rootless Podman                                                                          |
| --------------------------------- | --------------------------------------- | ---------------------------------------------------------------------------------------- |
| Хто запускає контейнери           | Демон Docker від імені `root`           | Ваш користувач                                                                           |
| Сокет для запуску компіляції      | `/var/run/docker.sock`                  | `/run/user/<uid>/podman/podman.sock`                                                     |
| Порти                             | Будь-які, наприклад `80` і `443`        | `1024` і вище, наприклад `8080`                                                          |
| Брандмауер хоста (`firewalld`)    | Опубліковані порти його оминають        | Діє: відкрийте порт за допомогою `firewall-cmd`                                          |
| Запуск після перезавантаження     | Їх перезапускає демон Docker            | Служба користувача `podman-restart`                                                      |
| SELinux                           | Toolkit не налаштовує                   | Модуль політики `podman_socket_clsi` і `SELINUX_MODE=managed` у `config/overleaf.rc`      |
| Профіль seccomp для компіляції    | Вбудований в образ                      | Toolkit видобуває його в `config/seccomp/<version>/` і задає як `SECCOMP_PROFILE`        |

### Відомі обмеження {#known-limitations}

* <strong>Інтеграція з Git.</strong> В Ayakaleaf Pro 6.3.4 `git clone` на Podman завершується помилкою `502`: NGINX усередині образу шукає контейнер `git-bridge` через DNS-сервер Docker (`127.0.0.11`), якого в Podman немає. Виправлення ([1b911d1092](https://github.com/ayaka-notes/ayakaleaf-pro/commit/1b911d1092c80f7b0ff77c5e3805b40503d49964)) увійде до наступного випуску; доти залиште `GIT_BRIDGE_ENABLED=false`.
* <strong>IP-адреси клієнтів.</strong> Rootless Podman переспрямовує опублікований порт зсередини мережі контейнера, тому Ayakaleaf Pro бачить кожного відвідувача з внутрішньою адресою, наприклад `10.89.0.15`. [Журнали аудиту](/uk/on-premises/user-guide/administrators/user-management#audit-logs) користувача в панелі адміністратора показують цю адресу замість його IP-адреси.
