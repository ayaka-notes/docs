Ayakaleaf Pro потребує:

* **MongoDB 8** як **набір реплік** (він використовує транзакції). Три учасники, розподілені на три вузли, переживуть втрату вузла; один учасник також працює.
* **Redis 7**, один сервер з AOF-персистентністю. Redis зберігає правки, які ще не записано в MongoDB, сесії та повідомлення між службами Overleaf. Overleaf підключається до одного сервера Redis: Sentinel і Redis Cluster не підтримуються.

<Info>

Натомість можна використовувати керовані сервіси, як-от MongoDB Atlas або Redis вашої хмари. Пропустіть цю сторінку й вкажіть їх у `OVERLEAF_MONGO_URL` і `OVERLEAF_REDIS_HOST` на [кроці 4](/uk/on-premises/installation/using-kubernetes/4.-personalizing-your-instance).

</Info>

<Steps>
<Step title="MongoDB">
```yaml title="10-mongo.yaml" wrap
apiVersion: v1
kind: Service
metadata:
  name: mongo
  namespace: overleaf
spec:
  clusterIP: None                 # headless: gives mongo-0.mongo, mongo-1.mongo, ...
  publishNotReadyAddresses: true  # members must resolve each other before the set is initiated
  selector:
    app: mongo
  ports:
    - name: mongo
      port: 27017
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mongo
  namespace: overleaf
spec:
  serviceName: mongo
  replicas: 3
  selector:
    matchLabels:
      app: mongo
  template:
    metadata:
      labels:
        app: mongo
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app: mongo
              topologyKey: kubernetes.io/hostname
      containers:
        - name: mongo
          image: mongo:8.0
          args:
            - --replSet=overleaf
            - --bind_ip_all
            - --wiredTigerCacheSizeGB=0.25   # default is 50% of (RAM - 1 GB); size it for your nodes
          # env:
          #   - name: GLIBC_TUNABLES        # only on kernel 6.19+ (SERVER-121912)
          #     value: glibc.pthread.rseq=1
          ports:
            - containerPort: 27017
          readinessProbe:
            tcpSocket:
              port: 27017
          resources:
            requests:
              cpu: 100m
              memory: 384Mi
            limits:
              memory: 768Mi
          volumeMounts:
            - name: data
              mountPath: /data/db
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 5Gi
---
# Initiates the replica set once. Safe to re-run: it does nothing when the set exists.
apiVersion: batch/v1
kind: Job
metadata:
  name: mongo-init-replica-set
  namespace: overleaf
spec:
  backoffLimit: 20
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: init
          image: mongo:8.0
          command:
            - mongosh
            - --quiet
            - --host=mongo-0.mongo
            - --eval
            - |
              try {
                rs.status()
                print('replica set already initiated')
              } catch (e) {
                rs.initiate({
                  _id: 'overleaf',
                  members: [
                    { _id: 0, host: 'mongo-0.mongo.overleaf.svc.cluster.local:27017' },
                    { _id: 1, host: 'mongo-1.mongo.overleaf.svc.cluster.local:27017' },
                    { _id: 2, host: 'mongo-2.mongo.overleaf.svc.cluster.local:27017' },
                  ],
                })
              }
```

```bash
kubectl apply -f 10-mongo.yaml
kubectl -n overleaf rollout status statefulset/mongo
kubectl -n overleaf wait --for=condition=complete job/mongo-init-replica-set --timeout=5m
kubectl -n overleaf exec mongo-0 -- mongosh --quiet --eval 'rs.status().members.map(m => m.name + " " + m.stateStr)'
```

Через кілька секунд один учасник має бути `PRIMARY`, а решта — `SECONDARY`. Job повторює спроби, доки не відповідять усі учасники, тож кілька невдалих подів Job — це нормально.

* Headless Service потребує `publishNotReadyAddresses: true`: учасники мають знаходити один одного за іменем ще до того, як набір реплік буде створено.
* Учасників додано за їхніми стабільними іменами (`mongo-0.mongo.overleaf.svc.cluster.local`), а ніколи не за IP-адресами подів, які змінюються після кожного перезапуску.
* Для одного учасника встановіть `replicas: 1` і залиште в Job лише `mongo-0`.
</Step>

<Step title="Redis">
```yaml title="20-redis.yaml" wrap
apiVersion: v1
kind: Service
metadata:
  name: redis
  namespace: overleaf
spec:
  selector:
    app: redis
  ports:
    - name: redis
      port: 6379
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
  namespace: overleaf
spec:
  serviceName: redis
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis
          image: redis:7.4
          args: [--appendonly, "yes"]
          ports:
            - containerPort: 6379
          readinessProbe:
            tcpSocket:
              port: 6379
          resources:
            requests:
              cpu: 50m
              memory: 128Mi
            limits:
              memory: 512Mi
          volumeMounts:
            - name: data
              mountPath: /data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 2Gi
```

```bash
kubectl apply -f 20-redis.yaml
kubectl -n overleaf rollout status statefulset/redis
```
</Step>

### Q\&A

<Accordion title="MongoDB 8 аварійно завершується під час запуску на новому ядрі. Чому?">

<strong>Відповідь:</strong> MongoDB 8 не працює на ядрі Linux 6.19 і новіших ([SERVER-121912](https://jira.mongodb.org/browse/SERVER-121912)). Розкоментуйте змінну середовища `GLIBC_TUNABLES` у `10-mongo.yaml`.

</Accordion>

<Accordion title="Скільки пам'яті потрібно MongoDB?">

<strong>Відповідь:</strong> За замовчуванням MongoDB використовує для кешу половину пам'яті вузла мінус 1 ГБ, і бачить пам'ять вузла, а не обмеження пода. Налаштуйте `--wiredTigerCacheSizeGB` відповідно до своїх вузлів; `0.25` утримувало кожного учасника на рівні приблизно 200–260 МіБ на наших тестових вузлах із 4 ГБ.

</Accordion>
