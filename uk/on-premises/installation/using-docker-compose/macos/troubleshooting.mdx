### Ініціалізація завершується помилкою invalid command code {#initialization-fails-with-invalid-command-code}

`bin/init` повідомляє `sed: ... invalid command code`, коли знаходить BSD sed з macOS. Додайте GNU sed до `PATH`, як описано в розділі [1. Завантаження Toolkit](/uk/on-premises/installation/using-docker-compose/macos/1.-download-the-toolkit), і перевірте `sed --version`.

Невдала ініціалізація може залишити всі три файли в `config/` з порожнім `OVERLEAF_INVITE_TOKEN_SECRET`. Повторний запуск `bin/init` тоді повідомляє `Config files already exist`. Для нової інсталяції, яка ще жодного разу не запускалася, перемістіть ці три файли до каталогу резервних копій і знову виконайте `bin/init`. Для наявного екземпляра збережіть його конфігурацію та секрети й не видаляйте його файли лише для того, щоб `bin/init` запустився знову.

### MongoDB постійно перезапускається {#mongodb-keeps-restarting}

Перегляньте журнали MongoDB і версію ядра віртуальної машини Docker:

```bash
bin/docker-compose logs --tail=100 mongo
docker info --format '{{.KernelVersion}}'
```

Якщо журнал вказує на несумісність ядра Linux, виконайте кроки з розділу [Перевірте ядро Linux віртуальної машини Docker](/uk/on-premises/installation/using-docker-compose/macos/5.-personalizing-your-instance#check-the-docker-vms-linux-kernel) і знову запустіть `bin/up -d`. Сам лише код завершення `137` не доводить, що MongoDB забракло пам'яті: перевірте стан контейнера та журнали. Про старішу проблему MongoDB у Docker Desktop див. також [Усунення несправностей](/uk/on-premises/support/troubleshooting).

### Не вдається підключитися до демона Docker {#cannot-connect-to-the-docker-daemon}

Запустіть Docker Desktop і перевірте вибраний контекст Docker, див. [0. Налаштування Docker Desktop](/uk/on-premises/installation/using-docker-compose/macos/0.-setup-docker-desktop). Якщо `docker info` працює, але компіляції не можуть дістатися до Docker, перевірте налаштування сокета в `config/overleaf.rc` і перегляньте журнали `clsi`. Справний Docker CLI на Mac не доводить, що сокет у застосунку змонтовано правильно.

### Сторінка відкривається, але компіляція не вдається {#the-page-opens-but-compiles-fail}

Перевірте, що образ TeX Live є локально й відповідає архітектурі рушія Docker:

```bash
docker image inspect ghcr.io/ayaka-notes/texlive-full:2026.1 \
  --format '{{.Os}}/{{.Architecture}}'
bin/logs -f clsi
```

На Apple silicon образ має бути `linux/arm64`. Перевірте, що `SERVER_PRO` і `SIBLING_CONTAINERS_ENABLED` обидва мають значення `true`, а потім застосуйте зміни за допомогою `bin/up -d`. Якщо журнали повідомляють про відсутній каталог компіляції, перевірте спільний доступ до файлів у Docker Desktop і розташування `OVERLEAF_DATA_PATH`. Не вимикайте ізольовану компіляцію, щоб приховати помилку монтування.

### Not a directory, або відсутній bind mount {#not-a-directory-or-a-bind-mount-is-missing}

Файл на хості, який монтує перевизначення, міг бути видалений, або Docker міг створити каталог там, де мав бути файл. Перевірте вихідний шлях на хості та те, чого очікує монтування — файлу чи каталогу. Відновіть конфігураційний файл, перш ніж перестворювати контейнер. Інсталяція в `/tmp` може зіткнутися з цим після того, як macOS видалить тимчасові файли.

### Конфлікти портів або назв контейнерів {#port-or-container-name-conflicts}

Якщо порт `8080` зайнятий, виберіть інший порт у `config/overleaf.rc`, відповідно задайте `OVERLEAF_SITE_URL` і знову виконайте `bin/up -d`.

Toolkit дає своїм контейнерам фіксовані назви, як-от `sharelatex`, `mongo` і `redis`. Сама лише зміна `PROJECT_NAME` не робить дві інсталяції Toolkit незалежними. Перш ніж запускати другий екземпляр, перевірте `docker ps -a` і використайте інші назви контейнерів у перевизначенні Compose, інший порт і окремі каталоги даних. Не видаляйте контейнери чи дані наявного розгортання, щоб розв'язати конфлікт назв.

### Через деякий час екземпляр стає недоступним {#the-instance-is-unreachable-after-a-while}

Імовірно, Mac перейшов у режим сну або Docker Desktop було закрито. Див. [Підтримання доступності екземпляра](/uk/on-premises/installation/using-docker-compose/macos/6.-post-installation-tasks#keep-the-instance-available).

### `bin/doctor` повідомляє, що це не Linux, або просить увійти в Quay {#bin/doctor-says-this-is-not-linux-or-asks-for-a-quay-login}

Обидва попередження очікувані в macOS з публічним образом, див. [2. Ознайомлення з Toolkit](/uk/on-premises/installation/using-docker-compose/macos/2.-familiarize-yourself-with-the-toolkit). Натомість перевірте завантаження образів, стан сервісів і результати компіляції та не ігноруйте інші помилки у звіті.
