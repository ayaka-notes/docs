### Створення адміністратора та першого проєкту {#create-the-administrator-and-a-first-project}

Відкрийте [http://localhost:8080/launchpad](http://localhost:8080/launchpad) у **браузері Windows**, створіть перший обліковий запис адміністратора та увійдіть. Потім виконайте кроки з розділу [6. Завдання після встановлення](/uk/on-premises/installation/using-docker-compose/linux/6.-post-installation-tasks) посібника для Linux, використовуючи порт `8080` у прикладах URL.

### Перевірка компіляції {#verify-compilation}

Робоча сторінка входу не доводить, що окремі контейнери компілятора мають доступ до каталогу даних WSL. Створіть порожній проєкт і скомпілюйте цей `main.tex` за допомогою **pdfLaTeX**:

```latex
\documentclass{article}
\begin{document}
Ayakaleaf Pro on Windows WSL 2.
\end{document}
```

Попередній перегляд PDF має показати текст. Для базового образу за потреби виберіть **TeX Live 2026 Basic** у налаштуваннях проєкту.

Виберіть **XeLaTeX** і перевірте:

```latex
\documentclass{article}
\usepackage{fontspec}
\begin{document}
Ayakaleaf WSL XeLaTeX sandbox.
\end{document}
```

Обидва приклади працюють з базовим образом. Для китайських документів, перш ніж перевіряти наведене нижче за допомогою **XeLaTeX**, використайте образ, що містить `ctex` і потрібні шрифти, наприклад повний. Базовий образ їх не містить:

```latex
\documentclass{ctexart}
\begin{document}
你好，Ayakaleaf Pro。
\end{document}
```

Щоб переконатися, що використовується ізоляція, під час компіляції виконайте в **Ubuntu**:

```bash
docker ps -a --filter ancestor=ghcr.io/ayaka-notes/texlive-basic:2026.1
bin/logs -f clsi
```

Використайте у фільтрі назву вибраного вами образу. Короткі компіляції можуть завершитися ще до запуску `docker ps`; `-a` також показує зупинені контейнери до їх очищення. Контейнер компілятора має використовувати цей образ і bind mount `/compile` з каталогу даних Toolkit у WSL. Самі лише журнали застосунку не замінюють перевірки PDF.

### Перевірка збереження даних {#verify-persistence}

В **Ubuntu**, у каталозі Toolkit:

```bash
bin/stop
bin/start
```

Дочекайтеся запуску застосунку, знову відкрийте проєкт з Windows і скомпілюйте його ще раз. Ваш обліковий запис, вихідний код і файли проєкту мають залишитися на місці. За замовчуванням робочі дані зберігаються в `~/ayakaleaf-toolkit/data/` всередині Ubuntu. Зберігайте і `config/`, і `data/`; видалення або скасування реєстрації дистрибутива Ubuntu може їх знищити.

### Підтримання доступності екземпляра {#keep-the-instance-available}

Щоб екземпляр працював постійно, потрібні три умови: Windows не засинає, Docker Desktop працює, а контейнери перезапускаються разом із рушієм.

У **Settings → General** Docker Desktop увімкніть **Start Docker Desktop when you sign in to your computer**, див. [Docker Desktop settings](https://docs.docker.com/desktop/settings-and-maintenance/settings/). Це запускає Docker після входу, а не до нього. Після перезавантаження Windows увійдіть у систему, дочекайтеся повного запуску Docker Desktop, відкрийте Ubuntu й перевірте `docker ps` і сайт.

**Resource Saver** у Docker Desktop не пов'язаний зі сплячим режимом Windows. Зазвичай він активується лише тоді, коли не запущено жодного контейнера; запущені застосунок, MongoDB і Redis не допускають цього стану бездіяльності. На WSL 2 він призупиняє рушій Docker, а не вимикає спільну віртуальну машину WSL. Не призупиняйте Docker Desktop вручну за допомогою **Pause**, поки обслуговуєте користувачів. Вимикати Resource Saver лише для того, щоб цей стек працював, не потрібно; див. [документацію Docker про Resource Saver](https://docs.docker.com/desktop/use-desktop/resource-saver/).

Сервіси Toolkit використовують `restart: always`. Перевірте фактичне налаштування в **Ubuntu**:

```bash
docker inspect sharelatex mongo redis --format '{{.Name}} restart={{.HostConfig.RestartPolicy.Name}}'
```

Кожен сервіс має повідомити `always`. Щойно Docker запущено, він може перезапустити ці наявні контейнери без нового `bin/up`. Контейнер, зупинений вручну, залишається зупиненим, доки ви його не запустите або не перезапустите рушій; з `always` перезапуск рушія може знову його запустити. Див. [поведінку політик перезапуску Docker](https://docs.docker.com/engine/containers/start-containers-automatically/).

| Дія | Вплив на Ayakaleaf |
| --- | --- |
| Закрити термінал Ubuntu після `bin/up -d` | Контейнери працюють у фоновому режимі; термінал не керує ними. Docker Desktop і середовище WSL мають залишатися доступними |
| Закрити вікно Docker Dashboard | Вікно можна закрити, а Docker Desktop продовжить працювати в системному треї |
| Вибрати **Quit Docker Desktop** | Зупиняє рушій і робить сайт недоступним; щоб відновити роботу, знову відкрийте Docker Desktop |
| Виконати `wsl --shutdown` | Зупиняє всі дистрибутиви WSL і перериває роботу бекенда Docker WSL; перезапустіть Docker Desktop і знову відкрийте Ubuntu |
| Перевести Windows у сплячий режим, гібернацію або вимкнути | Сервіс недоступний; лише ввімкнений чи вимкнений екран цього не змінює |
| Виконати `bin/stop` | Зупиняє екземпляр зі збереженням його даних; щоб продовжити, використайте `bin/start` |

Для тривалої роботи від мережі відкрийте у Windows 11 **Settings → System → Power & battery → Screen, sleep & hibernate timeouts** (у деяких версіях — **Power** або **Screen and sleep**). Установіть для часу переходу в сплячий режим під час живлення від мережі значення **Never** і вимкніть автоматичну гібернацію, якщо її налаштовано. Дисплей при цьому може вимикатися. Дія під час закриття кришки ноутбука — окреме налаштування; закриття кришки може перевести ноутбук у сплячий режим, навіть якщо тайм-аут бездіяльності має значення Never. Див. [параметри живлення Windows](https://support.microsoft.com/en-us/windows/experience/power-battery/power-settings-in-windows-11).

Не виконуйте `wsl --shutdown` як звичайне очищення, поки сайт використовується. Якщо зміна налаштувань WSL цього потребує, спершу зупиніть екземпляр і заплануйте перерву в роботі. З цими налаштуваннями Windows може запускати екземпляр безперервно. Для спільного сервісу, який має переживати вихід із системи та перезавантаження без нагляду, ми рекомендуємо [посібник для Linux](/uk/on-premises/installation/using-docker-compose/linux).

### Перевірка відновлення після перезапуску Docker Desktop {#check-recovery-after-restarting-docker-desktop}

Після збереження роботи й завершення активних компіляцій виберіть **Restart Docker Desktop** у меню усунення несправностей Docker Desktop. Дочекайтеся запуску рушія, а потім перевірте в **Ubuntu**:

```bash
docker ps
curl -I http://localhost:8080/launchpad
```

Відкрийте наявний проєкт у Windows і скомпілюйте його ще раз. Переконайтеся, що обліковий запис і вихідний код досі на місці.

Якщо ви навмисно зупинили екземпляр за допомогою `bin/stop`, використайте `bin/start`. Якщо Docker працює, але сервіс не запускається, перегляньте його журнали, а не перестворюйте конфігурацію. Windows Update, оновлення Docker і втрата живлення все одно можуть перервати цілодобову роботу інсталяції; створюйте резервні копії та перевіряйте відновлення після планового обслуговування.

### Щоденне використання {#daily-use}

Запустіть Docker Desktop у Windows. Відкрийте **Ubuntu**:

```bash
cd "$HOME/ayakaleaf-toolkit"
```

| Завдання | Команда |
| --- | --- |
| Запустити наявні контейнери | `bin/start` |
| Зупинити контейнери й зберегти дані | `bin/stop` |
| Застосувати зміни конфігурації | `bin/up -d` |
| Перевірити стан | `bin/docker-compose ps` |
| Переглянути журнали запуску | `bin/docker-compose logs --tail=100 sharelatex` |
| Переглянути журнали MongoDB | `bin/docker-compose logs --tail=100 mongo` |
| Переглянути журнали компілятора | `bin/logs -f clsi` |

`bin/start` не застосовує зміни конфігурації: після зміни `config/` використовуйте `bin/up -d`. Перед оновленням, перенесенням або видаленням дистрибутива WSL дотримуйтеся інструкцій з розділу [Дані та резервні копії](/uk/on-premises/maintenance/data-and-backups). Копіювання робочих файлів MongoDB, поки база даних у них записує, не є узгодженою резервною копією.

Для локального використання залишайте `127.0.0.1`. Щоб обслуговувати інші комп'ютери, також потрібно свідомо налаштувати адресу прослуховування, URL сайту, брандмауер і мережу Windows та HTTPS; сама лише зміна `OVERLEAF_SITE_URL` не публікує порт.

Якщо щось не працює, див. [Усунення несправностей](/uk/on-premises/installation/using-docker-compose/windows/troubleshooting).
