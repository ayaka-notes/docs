## Prerequisites

Overleaf is a typical open-source project for microservice architecture, with all services running in Docker.&#x20;

* The Official Community Edition source code is on [GitHub Overleaf Official](https://github.com/overleaf/overleaf/tree).&#x20;
* The source code for Overleaf-CEP is available on [GitHub Yu-i-i/Overleaf](https://github.com/yu-i-i/overleaf-cep).
* Ayakaleaf Pro is available on [GitHub ayaka-notes/ayakaleaf-pro](https://github.com/ayaka-notes/ayakaleaf-pro).

To set up an Overleaf development environment, you'll need a powerful server; a configuration of at least 8 cores and 16GB of RAM is recommended, as you'll need to run more than 20 containers simultaneously.

<Info>

Since servers with 8 or more CPU cores are typically expensive, It's highly recommend using your local computer for development.

</Info>

Meanwhile, as a developer, we believe you should already be familiar with [Docker installation](https://docs.docker.com/engine/install/ubuntu/). We strongly suggest using a recent and stable Ubuntu LTS (e.g. Ubuntu 24.04 in 2025–2026) and the latest Docker for development, as this reduces the possibility of encountering unexpected errors.

In summary, you will need:

* [x] A powerful server/desktop to develop
* [x] A recent and stable Ubuntu LTS (e.g. Ubuntu 24.04)
* [x] Docker and Git environment

## Configuration Tutorial

Here, we use Ayakaleaf Pro to show how to set up an Overleaf development environment. All commands below run in the `develop` directory unless said otherwise.

<Steps>
<Step title="Pull the Source Code">
First of all let's clone the repo:

```bash title="bash"
git clone https://github.com/ayaka-notes/ayakaleaf-pro.git
cd ayakaleaf-pro/develop
```
</Step>

<Step title="Synchronize `yarn.lock`">
The repository uses Yarn 4 (`packageManager` in the root `package.json`), and its `yarn.lock` can be out of sync with the `package.json` files. Sync it after the first clone and after any `package.json` change:

```bash title="bash"
bin/sync
```

`bin/sync` runs `yarn install --mode=update-lockfile` in a `node:24.18.1` container, so you do not need Node.js on the host. Do not commit the changed `yarn.lock`.
</Step>

<Step title="Build Develop Image">
Build the services:

```bash title="bash"
bin/build
```

<Info>

If Docker is running out of RAM while building the services in parallel, create a `.env` file in this directory containing `COMPOSE_PARALLEL_LIMIT=1`.

</Info>
</Step>

<Step title="Apply the Translations">
The modules of Ayakaleaf Pro keep their translations in `services/web/locales/locales_patches/`, which the committed locale files do not contain. Apply them once before the first start, or the pages of these modules show keys such as `about_to_permanently_delete_accounts` instead of text:

```bash title="bash"
bin/i18n
```

It needs `jq` on the host. Run it again after adding a translation or changing branch, see [Update i18n Translations](/dev/environment/update-i18n-translations).
</Step>

<Step title="Start All Micro Services">
Then start the services:

```bash title="bash"
bin/up
```

Once the services are running, open [http://localhost/launchpad](http://localhost/launchpad) to create the first admin account. Add the port if you changed `OVERLEAF_PORT` (see below).

<Info>

LDAP is on by default (`LDAP_ENABLED=true` in `dev.rc`). The launchpad then shows the LDAP admin form: it only asks for an email, and that admin logs in through LDAP afterwards, for example as `professor` / `professor` (`professor@planetexpress.com`). The test users are listed in `develop/authentication/README.md`. Set `LDAP_ENABLED=false` and `SAML_ENABLED=false` to create a local admin with a password instead.

</Info>
</Step>
</Steps>

<Info>

`develop/dev.env` already sets `ADMIN_PRIVILEGE_AVAILABLE=true`, so admins can open the Admin panel without extra setup.

</Info>

### Configuration (`dev.rc`)

`develop/dev.rc`, next to `dev.env`, holds the switches of the dev environment, like `overleaf.rc` in the Overleaf Toolkit. Change a value and run `bin/dev` again to apply it; a feature that is turned off also stops its containers.

| Variable | Default | What it does |
| -------- | ------- | ------------ |
| `OVERLEAF_PORT` | `80` | Host port of the site. |
| `LDAP_ENABLED` | `true` | LDAP login with test users. |
| `SAML_ENABLED` | `true` | SAML login with test users. |
| `MAILPIT_ENABLED` | `true` | Catches every email from `web` in Mailpit. It also turns email confirmation on (`EMAIL_CONFIRMATION_DISABLED=false`). |
| `S3_ENABLED` | `true` | Keeps history and template files in RustFS (S3) instead of local volumes. |
| `HOPPSCOTCH_ENABLED` | `true` | Hoppscotch with a proxy into the Docker network, see [Setup Develop Tools](/dev/environment/setup-develop-tools). |
| `HOPPSCOTCH_PORT` | `9170` | Host port of Hoppscotch. |
| `GRAFANA_ENABLED` | `true` | Grafana on `/grafana/` of the site, with the state, metrics and logs of every service, see [Setup Develop Tools](/dev/environment/setup-develop-tools). |

Each feature keeps its `docker-compose.yml` and other files in its own folder: `authentication/ldap`, `authentication/saml`, `mail`, `s3`, `hoppscotch` and `grafana`. A feature that needs a `web` setting without an environment variable mounts a file into `/etc/overleaf/settings.d/`, and `develop/settings.dev-env.cjs` merges all of them. All `bin/*` scripts go through `bin/docker-compose`, which adds the files of the features that are on. Call `bin/docker-compose` instead of `docker compose` when you need a compose command yourself.

<Warning>

The local volumes and RustFS are separate stores: a project created with `S3_ENABLED=true` has no history or binary files after switching to `false`, and the other way round. To copy the files of an environment that ran before `S3_ENABLED` existed into RustFS, follow "Moving existing data into RustFS" in [develop/README.md](https://github.com/ayaka-notes/ayakaleaf-pro/blob/server-pro/develop/README.md).

</Warning>

### Ports

The site, the RustFS console and Hoppscotch listen on `127.0.0.1` of the host; on a remote machine, forward their ports first, for example `ssh -L 9001:localhost:9001 <host>`. The site uses `OVERLEAF_PORT` from `dev.rc`, so add the port to the addresses below if you changed it.

| Page | Address | Login |
| ---- | ------- | ----- |
| Site | [http://localhost](http://localhost) | The accounts of the site, or the test users |
| Email inbox (Mailpit) | [http://localhost/mailpit/](http://localhost/mailpit/) | None |
| Grafana | [http://localhost/grafana/](http://localhost/grafana/) | None, anonymous users are admins |
| Mongo Express | [http://localhost/mongo-express/](http://localhost/mongo-express/) | None |
| RedisInsight | [http://localhost/redis-insight/](http://localhost/redis-insight/) | None |
| S3 console (RustFS) | [http://localhost:9001/rustfs/console/](http://localhost:9001/rustfs/console/) | `rustfsadmin` / `rustfsadmin` |
| Hoppscotch | [http://localhost:9170](http://localhost:9170) (`HOPPSCOTCH_PORT`) | None |

Mailpit, Grafana, Mongo Express and RedisInsight are served by the site on their own paths, through webpack-dev-server, so they need no port of their own. Once you are logged in, the **Dev tools** menu in the navbar of the site links to them; a page whose feature is turned off in `dev.rc` is left out. [Setup Develop Tools](/dev/environment/setup-develop-tools) shows what each of them does.

The S3 API (port 9000) and SMTP (port 1025) are only reachable inside the Docker network. Mongo (27017) and Redis (6379) are published on `127.0.0.1` for debugging. Mongo Express (8081), RedisInsight (5540) and git-bridge (8000) are published on all interfaces of the host.

### TeX Live

Sandboxed compiles are on by default: `develop/dev.env` sets `SANDBOXED_COMPILES=true` and the images `ghcr.io/ayaka-notes/texlive-full:2026.1` and `ghcr.io/ayaka-notes/texlive-full:2025.1`. clsi does not pull images itself, so pull them once:

```bash
docker pull ghcr.io/ayaka-notes/texlive-full:2026.1
docker pull ghcr.io/ayaka-notes/texlive-full:2025.1
```

See [Setup Sandbox Compiles](/dev/environment/setup-sandbox-compiles) for the details.

<Warning>

A project created while `SANDBOXED_COMPILES` was off has no TeX Live image. It still compiles with the default image, but jumping between the code and the PDF fails with "That didn't work. Recompile and try again." Give such projects the image of `TEX_LIVE_DOCKER_IMAGE` once; without `--commit`, the script only shows what it would change:

```bash
bin/docker-compose exec web sh -c 'cd /overleaf/services/web && node scripts/backfill_project_image_name.mjs --commit'
```

</Warning>

`dev.env` also turns on Pandoc conversions with `PANDOC_IMAGE=overleaf-pandoc:local`. Build that image once, from the root of the repository:

```bash
docker build -t overleaf-pandoc:local develop/pandoc
```

To compile on a macOS host, you may need to override the path to the Docker socket by creating a `.env` file in the `develop` directory, containing `DOCKER_SOCKET_PATH=/var/run/docker.sock.raw`

### Development

To avoid running `bin/build && bin/up` after every code change, you can run Overleaf Community Edition in _development mode_, where services will automatically update on code changes.

To do this, use the included `bin/dev` script:

```text
bin/dev
```

This will start all services using `node --watch`, which will automatically monitor the code and restart the services as necessary. Run it again after changing `dev.rc`.

To improve performance, you can start only a subset of the services in development mode by providing a space-separated list to the `bin/dev` script:

```text
bin/dev [service1] [service2] ... [serviceN]
```

<Info>

Starting the `web` service in _development mode_ will only update the `web` service when backend code changes. In order to automatically update frontend code as well, make sure to start the `webpack` service in _development mode_ as well.

</Info>

If no services are named, all services will start in development mode.

After adding a translation or changing branch, run `bin/i18n`, see [Update i18n Translations](/dev/environment/update-i18n-translations).

### Debugging

When run in _development mode_ most services expose a debugging port to which you can attach a debugger such as the inspector in Chrome's Dev Tools or one integrated into an IDE. The following table shows the port exposed on `127.0.0.1` of the **host machine** for each service:

| Service                 | Port |
| ----------------------- | ---- |
| `web`                   | 9229 |
| `clsi`                  | 9230 |
| `chat`                  | 9231 |
| `docstore`              | 9233 |
| `document-updater`      | 9234 |
| `filestore`             | 9235 |
| `notifications`         | 9236 |
| `real-time`             | 9237 |
| `history-v1`            | 9239 |
| `project-history`       | 9240 |
| `linked-url-proxy`      | 9241 |
| `third-party-datastore` | 9242 |

To attach to a service using Chrome's _remote debugging_, go to chrome://inspect/ and make sure _Discover network targets_ is checked. Next click _Configure..._ and add an entry `localhost:[service port]` for each of the services you want to attach a debugger to.

After adding an entry, the service will show up as a _Remote Target_ that you can inspect and debug.

### Logging

The script `bin/logs` follows the logs and formats them with `bunyan`. It also needs `ggrep`, which is the name of GNU grep when installed with Homebrew on macOS; Ubuntu does not have a `ggrep` command.

```bash
sudo npm install -g bunyan
# Or sudo apt install node-bunyan 
```

Or, you can run directly with:

```text
bin/docker-compose logs -f [service name]
```

Use `bin/docker-compose` rather than `docker compose`, so that the services of the features in `dev.rc` (`mailpit`, `rustfs`, `ldap`, `saml`, `hoppscotch`, and `grafana` with Prometheus, Loki and the exporters) are found too.

With `GRAFANA_ENABLED=true`, the logs of every container are also in Grafana, where they can be filtered by service, level and text, see [Setup Develop Tools](/dev/environment/setup-develop-tools#grafana).
