Sandboxed compiles work a little differently in the dev environment than in the production image. The dev environment already has them set up; this page explains the settings and three things to keep in mind:

* File Permission Problem
* Volume Share Between history-v1 and filestore
* Subdirectories Problem

### Enable Sandbox Compiles

Sandboxed compiles are on by default. `develop/docker-compose.yml` sets `SANDBOXED_COMPILES=true` for `clsi`, and `develop/dev.env` holds the rest:

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

clsi does not pull images itself, so pull the images once with `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1` (and `:2025.1`).

LaTeX runs in the sibling containers as `TEXLIVE_IMAGE_USER`. In the dev environment this is `tex`, which is also clsi's default (`services/clsi/config/settings.defaults.cjs:154`). The production image uses `www-data` instead when `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` (`server-ce/config/env.sh:15-21`), because there the files are created by the `www-data` user of the Overleaf container.

<Warning>

Please don't use your self-built image, you may encounter a series of errors.

</Warning>

### Fix File Permissions

The clsi container starts as root, gives the `compiles`, `output` and `cache` folders to the `node` user (uid `1000`) and then runs clsi as `node` (`services/clsi/entrypoint.sh`). So `develop/compiles` on the host belongs to uid `1000`, the same uid as `tex` in the dev setup (see the comment in `develop/pandoc/Dockerfile`). With the settings above, the dev environment compiles without any permission change.

If you set `TEXLIVE_IMAGE_USER=root` instead, root (uid `0`) has no permission to write to the subfolders of `compiles`. In that case, give the `root` group ownership and write permission to `compiles`, with `setgid` set so that new subfolders inherit this ownership:

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

For detailed document, you can see `services/clsi/README.md`.

### Volume Share Between history-v1 and filestore

<Info>

The settings in this section and the next one are already in `develop/docker-compose.yml` and `develop/dev.env`. They only matter with `S3_ENABLED=false` in `develop/dev.rc`. With the default `S3_ENABLED=true`, filestore and history-v1 keep these files in RustFS buckets instead (`develop/s3/docker-compose.yml`).

</Info>

By default, filestore act as a bridge between s3 and other services in overleaf. However, in overleaf ce or server pro, all files are stored locally by default. So, overleaf introduced a very tricky method.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

And in the meantime, `data/history` is also used by history service. In this way, they can share the same data between different micro service. That is why the filestore service in develop mounts the `history-v1-buckets` volume of history-v1. Without it, **clsi will not be able to pull blob files from filestore service**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

filestore finds the buckets through these settings in `dev.env`:

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### Use Subdirectories

filestore always reads history blobs with subdirectories (`services/filestore/app/js/KeyBuilder.js:58`, `:70`). The production image turns `useSubdirectories` on for history-v1 (`server-ce/config/production.json`), but the default config of history-v1 does not, so in development history-v1 would <strong>flatten all the data.</strong> `dev.env` therefore sets `NODE_CONFIG` for history-v1:&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

Without it, history-v1 stores the `project_blobs` files like this:

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

With `useSubdirectories` set to `true`, the `_` in these names becomes `/`, so each blob is stored in subfolders.
