### Introductions

Before you delve into development, We hope you can understand the folloing things:

* Overleaf is developed in an [internal repository](http://github.com/overleaf/internal) officially, and the community edition is published in [overleaf/overleaf](https://github.com/overleaf/overleaf). A copybot is responsible for synchronizing code between the internal and public repositories.
* [Ayaka-notes/overleaf-pro](https://github.com/ayaka-notes/ayakaleaf-pro) is a forked version of overleaf community, We hope this project can be long-term, so please follow the rules before make contributions.

### Commit Rules

* Please do not make extensive modifications to the existing Overleaf code. Concentrate as much functionality as possible in the `services/web/modules` folder. This will minimize our workload when merging and updating the code later.
* Vibe coding is indeed very an easy way, but it can easily make a mess of our project, making it unmaintainable later on, so please use it with caution.
* Please do not add any translation-related content during development; use existing translations whenever possible.
* Avoid introducing environment variables unless absolutely necessary. If required, ensure they are as consistent as possible with those in the Overleaf toolkit or [docs.overleaf.com](https://docs.overleaf.com/).

### Branch Rules

We use the following branch for overleaf-pro development:

* `main`: This branch is used only for upstream code synchronize,  please **DO NOT** commit any external changes. In this branch, we will set some tags like `ce-v[X.x.x]`, which indecates this corresponds to `v[X.x.x]` in the Overleaf Official Community Edition. Notes: this tag is immutable!
* `server-pro`: This branch is the default branch for daily development.
* `feature-X`: This branch is used for development a specific feature.
* `release-vX.0.0`: The branch specific for release, we will do some hot-fix becore release.

### GitHub Action

[GitHub Action](https://github.com/ayaka-notes/ayakaleaf-pro/actions) is responsible for auto CI/CD. You don't need to build images on your own machine: every image below is built by a workflow, and the ones with a manual trigger can be built in one click.

| Workflow | Trigger | Source | Image |
| --- | --- | --- | --- |
| Sync Upstream Code | Daily, manual | `overleaf/overleaf` → `main` | — |
| Build Development Image | Daily, manual | `server-pro` | `ghcr.io/ayaka-notes/overleaf-pro/dev:<service>` |
| Build Operations Image | Push / PR to `server-pro`, manual | Pushed commit or PR head | `ghcr.io/ayaka-notes/overleaf-pro/ops:<YYYYMMDDHHMM>-<sha>`, `ops:latest` |
| Build Release Image | Manual | Latest `release-v*` branch | `ghcr.io/ayaka-notes/overleaf-pro:<version>`, `:latest`, and `overleaf-pro/git-bridge` |

* **Development images** hold one microservice each (`web`, `webpack`, `clsi`, ...) for `linux/amd64` and `linux/arm64`. The Codespace setup pulls them through `develop/docker-compose.image.yml` instead of running `bin/build`.
* **Operations images** are full single-container images (like `sharelatex/sharelatex`) for testing a change end to end. `ops:latest` only moves on pushes to `server-pro`; a PR gets a timestamped tag only. These images are kept for 7 days and are for testing only.
* **Release images** are what users deploy. The version comes from the branch name, so `release-v6.3.0` publishes `overleaf-pro:6.3.0`.

<Steps>
<Step title="Run A Workflow Manually">
Open the [Actions](https://github.com/ayaka-notes/ayakaleaf-pro/actions) tab, pick the workflow on the left, click **Run workflow**, and confirm. Build Operations Image also has a **Build without cache** option for when a cached layer is stale.
</Step>

<Step title="Build In Your Fork">
The same workflows run in a fork: enable Actions in your fork, then run them from its Actions tab. Images are pushed to `ghcr.io/<your-name>/overleaf-pro/...` with the built-in `GITHUB_TOKEN`, so no secrets are needed. Sync Upstream Code and the old image cleanup only run in `ayaka-notes`.

Build Release Image needs a `release-v*` branch in your fork.
</Step>
</Steps>

<Info>

To check which commit an image was built from: an operations image tag ends with the short commit hash, and a release image carries it in the `com.overleaf.pro.revision` label (see `docker inspect` in the Q\&A below).

</Info>

### Q\&A

<Accordion title="How to find the commit hash for Overleaf Community Edition `X.0.0` ?">

First of all, you need to pull the docker image and run with the following command to inspect labels in this docker image:

```shellscript title="bash" wrap
docker inspect --format='{{json .Config.Labels}}' sharelatex/sharelatex:6.0.0
{"com.overleaf.ce.revision":"b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f","org.opencontainers.image.ref.name":"ubuntu","org.opencontainers.image.version":"24.04"}
```

Then you can check if the [commit(b0d05c0)](https://github.com/overleaf/overleaf/commit/b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f) is present in upstream master branch.

</Accordion>

<Accordion title="Why the commit hash is the same in CE image between `6.0.0` and `6.0.1`?">

This is an expected behavior. The 6.0.1 release is a minor patch release built on top of the 6.0.0 image. The changes are applied by patching the existing 6.0.0 image, instead of rebuilding the image from a new commit. Therefore, the commit hash inside the image is identical between 6.0.0 and 6.0.1.

For detailed infomation, see [hotfix](https://github.com/overleaf/overleaf/tree/main/server-ce/hotfix).

</Accordion>
