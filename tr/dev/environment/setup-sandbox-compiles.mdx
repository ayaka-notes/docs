Korumalı alan derlemeleri geliştirme ortamında üretim imajından biraz farklı çalışır. Geliştirme ortamında bunlar zaten ayarlanmıştır; bu sayfa ayarları ve akılda tutulması gereken üç noktayı açıklar:

* Dosya İzinleri Sorunu
* history-v1 ile filestore Arasında Volume Paylaşımı
* Alt Dizinler Sorunu

### Sandbox Compiles'ı Etkinleştirme {#enable-sandbox-compiles}

Korumalı alan derlemeleri varsayılan olarak açıktır. `develop/docker-compose.yml`, `clsi` için `SANDBOXED_COMPILES=true` ayarlar ve geri kalanı `develop/dev.env` içindedir:

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

clsi imajları kendisi çekmez, bu yüzden imajları bir kez `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1` (ve `:2025.1`) ile çekin.

LaTeX kardeş konteynerlerde `TEXLIVE_IMAGE_USER` olarak çalışır. Geliştirme ortamında bu `tex`'tir ve aynı zamanda clsi'nin varsayılanıdır (`services/clsi/config/settings.defaults.cjs:154`). Üretim imajı ise `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` olduğunda `www-data` kullanır (`server-ce/config/env.sh:15-21`), çünkü orada dosyaları Overleaf konteynerinin `www-data` kullanıcısı oluşturur.

<Warning>

Lütfen kendi oluşturduğunuz imajı kullanmayın, bir dizi hatayla karşılaşabilirsiniz.

</Warning>

### Dosya İzinlerini Düzeltme {#fix-file-permissions}

clsi konteyneri root olarak başlar, `compiles`, `output` ve `cache` klasörlerini `node` kullanıcısına (uid `1000`) verir ve ardından clsi'yi `node` olarak çalıştırır (`services/clsi/entrypoint.sh`). Bu yüzden ana makinedeki `develop/compiles`, geliştirme ortamındaki `tex` ile aynı uid olan `1000`'e aittir (`develop/pandoc/Dockerfile` içindeki yoruma bakın). Yukarıdaki ayarlarla geliştirme ortamı hiçbir izin değişikliği olmadan derler.

Bunun yerine `TEXLIVE_IMAGE_USER=root` ayarlarsanız root (uid `0`) `compiles` alt klasörlerine yazma iznine sahip olmaz. Bu durumda `compiles` için `root` grubuna sahiplik ve yazma izni verin ve yeni alt klasörlerin bu sahipliği devralması için `setgid` ayarlayın:

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

Ayrıntılı dokümantasyon için `services/clsi/README.md` dosyasına bakabilirsiniz.

### history-v1 ile filestore Arasında Volume Paylaşımı {#volume-share-between-history-v1-and-filestore}

<Info>

Bu bölümdeki ve bir sonraki bölümdeki ayarlar zaten `develop/docker-compose.yml` ve `develop/dev.env` içindedir. Yalnızca `develop/dev.rc` içinde `S3_ENABLED=false` olduğunda önemlidir. Varsayılan `S3_ENABLED=true` ile filestore ve history-v1 bu dosyaları bunun yerine RustFS bucket'larında tutar (`develop/s3/docker-compose.yml`).

</Info>

Varsayılan olarak filestore, Overleaf'te s3 ile diğer servisler arasında bir köprü görevi görür. Ancak Overleaf CE veya Server Pro'da tüm dosyalar varsayılan olarak yerel olarak depolanır. Bu nedenle Overleaf oldukça dolambaçlı bir yöntem getirmiştir.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

Bu arada `data/history` geçmiş servisi tarafından da kullanılır. Böylece farklı mikroservisler aynı verileri paylaşabilir. Bu yüzden develop'taki filestore servisi, history-v1'in `history-v1-buckets` birimini bağlar. Bu olmadan **clsi, filestore servisinden blob dosyalarını çekemez**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

filestore, bucket'ları `dev.env` içindeki şu ayarlarla bulur:

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### Alt Dizinleri Kullanma {#use-subdirectories}

filestore geçmiş blob'larını her zaman alt dizinlerle okur (`services/filestore/app/js/KeyBuilder.js:58`, `:70`). Üretim imajı history-v1 için `useSubdirectories` ayarını açar (`server-ce/config/production.json`), ancak history-v1'in varsayılan yapılandırması açmaz; bu yüzden geliştirmede history-v1 <strong>tüm verileri düzleştirirdi.</strong> Bu nedenle `dev.env`, history-v1 için `NODE_CONFIG` ayarlar:&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

Bu olmadan history-v1, `project_blobs` dosyalarını şöyle saklar:

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

`useSubdirectories` `true` olarak ayarlandığında bu adlardaki `_` karakteri `/` olur, böylece her blob alt klasörlerde saklanır.
