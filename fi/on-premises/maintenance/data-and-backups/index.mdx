Overleafin kehittyessä tietokannan tietojen skeemaa on joskus muutettava, ja tämän prosessin automatisointiin käytetään siirtoskriptejä (migraatioita). Ne on ajettu ensin [overleaf.com](https://www.overleaf.com/)-palvelussa, joka on maailman suurin Overleaf-instanssi, joten useimmat mahdolliset tilanteet on todennäköisesti jo kohdattu. Emme kuitenkaan anna mitään takuita tietojesi suhteen. Varmista, että luot tiedoistasi **yhtenäisen** varmuuskopion **ennen** instanssisi päivittämistä.

<Info>

Kun päivität uuteen Docker-imageen, kaikki siirrot, joita **ei** ole vielä ajettu, suoritetaan automaattisesti. Tämä voi kestää jonkin aikaa tietomääräsi koosta riippuen, ja lokien seuraaminen kertoo edistymisestä. Lisätietoja on [Logging](/fi/on-premises/configuration/overleaf-toolkit/logging)-dokumentaatiossamme.

</Info>

### Tietojen tallennus

Ayakaleaf Pro tallentaa tietonsa kolmeen erilliseen paikkaan:

* <strong>MongoDB-tietokanta:</strong> Täällä sijaitsevat käyttäjä- ja projektitiedot.
* <strong>Redis:</strong> toimii suorituskykyisenä välimuistina käsittelyssä oleville tiedoille ja tallentaa pääasiassa projektien muokkauksiin ja yhteistyöhön liittyviä tietoja.
* <strong>Overleafin tiedostojärjestelmä:</strong> tallentaa projektien ei-muokattavat tiedostot (kuvat mukaan lukien) ja toimii myös väliaikaisena levyvälimuistina projektien käännösten aikana.

<Info>

Tämä voi olla `~/sharelatex_data` tai `~/overleaf_data` riippuen siitä, milloin instanssisi on otettu käyttöön.

</Info>

<Check>

Projektitiedostoille ja projektien täydelle historiatiedolle tuemme myös S3-yhteensopivia tallennustaustajärjestelmiä.

</Check>

Lisätietoja levyllä olevasta kansiorakenteesta on osiossa Kansiot yksityiskohtaisesti.

### Yhtenäisen varmuuskopion tekeminen

Yhtenäistä varmuuskopiota tehtäessä on otettava mukaan kolme tietovarastoa:

* MongoDB
* Redis
* Overleafin tiedostojärjestelmän tiedot

Yhtenäisen varmuuskopion tuottamiseksi on **välttämätöntä** estää käyttäjiä tuottamasta uusia tietoja varmuuskopioinnin aikana. Siksi suosittelemme huoltoikkunan ajoittamista, jonka aikana käyttäjät eivät pääse instanssiin eivätkä voi muokata projektejaan.

Ennen varmuuskopioinnin aloittamista sinun on otettava instanssisi pois käytöstä. Sammutusprosessi automatisoi sivuston sulkemisen ja käyttäjien yhteyksien katkaisemisen.

Sammuttaaksesi instanssin aja `bin/docker-compose stop sharelatex`, jos käytät Toolkit-käyttöönottoa, tai `docker compose stop sharelatex`, jos käytät Docker Composea.

Kun `sharelatex`-kontti on pysäytetty, voit aloittaa varmuuskopioinnin.

Kun varmuuskopiointi on valmistunut **onnistuneesti**, sinun on käynnistettävä `sharelatex`-kontti. Aja tätä varten `bin/docker-compose start sharelatex`, jos käytät Toolkit-käyttöönottoa, tai `docker compose start sharelatex`, jos käytät Docker Composea.

<Danger>

* Varmuuskopiot tulisi säilyttää eri palvelimella kuin se, jolla Overleaf-instanssisi toimii, mieluiten kokonaan eri sijainnissa.
* Tietokantojen replikointi useisiin MongoDB-instansseihin voi tarjota jonkin verran redundanssia, mutta se ei suojaa tietojen vioittumiselta.
* Varmuuskopioiden testaaminen on paras tapa varmistaa, että ne ovat täydellisiä ja toimivia.

</Danger>

### MongoDB

MongoDB:n mukana tulee komentorivityökalu [mongodump](https://docs.mongodb.com/manual/reference/program/mongodump/), jolla voi luoda varmuuskopion tietokantaan tallennetuista käyttäjä- ja projektitiedoista.

Kun `sharelatex`-kontti on pysäytetty ja `mongo`-kontti on edelleen käynnissä, vedosta `sharelatex`-tietokanta isäntäkoneen tiedostoon ja palauta se samalla tavalla (`--drop` korvaa olemassa olevat kokoelmat):

```bash wrap
# Toolkit
bin/docker-compose exec -T mongo mongodump --db sharelatex --archive --gzip > mongo-backup.gz
bin/docker-compose exec -T mongo mongorestore --archive --gzip --drop < mongo-backup.gz

# Docker Compose (container name mongo)
docker exec -i mongo mongodump --db sharelatex --archive --gzip > mongo-backup.gz
docker exec -i mongo mongorestore --archive --gzip --drop < mongo-backup.gz
```

### Overleafin tiedostojärjestelmän tiedot

Toolkit-käyttöönotoissa polku, johon ei-muokattavat tiedostot tallennetaan, määritetään tiedostossa `config/overleaf.rc` ympäristömuuttujalla `OVERLEAF_DATA_PATH`, mutta instanssin luontiajankohdasta riippuen se voi olla `data/sharelatex`.

Täydellisen varmuuskopion varmistamiseksi tämä hakemisto on kopioitava rekursiivisesti esimerkiksi **rsync**-työkalulla.

### Redis

Redis tallentaa käyttäjäistunnot ja odottavat asiakirjapäivitykset ennen kuin ne siirretään MongoDB:hen.

Append Only File (AOF) -pysyvyys on suositeltu määritys Redisin pysyvyydelle.

Toolkitin käyttäjillä AOF-pysyvyys on oletuksena käytössä **uusissa** asennuksissa. Nykyiset käyttäjät löytävät lisätietoja AOF:n käyttöönotosta [täältä](/fi/on-premises/configuration/overleaf-toolkit/redis#enabling-append-only-file-persistence).

Jos päätät jatkaa RDB-tilannevedosten käyttöä AOF-pysyvyyden rinnalla, voit kopioida RDB-tiedoston turvalliseen paikkaan varmuuskopioksi.

### Tietojen siirtäminen palvelimien välillä

Parhaassa tapauksessa uudessa instanssissa ei vielä ole arvokkaita tietoja. Meillä ei ole prosessia instanssien tietojen yhdistämiseen.

Olettaen, että uudessa instanssissa ei vielä ole tietoja, tässä on joitakin vaiheita, joita voit noudattaa. Yleisellä tasolla luomme `mongo`-, `redis`- ja `overleaf`-volyymeista tar-paketin, kopioimme sen uudelle palvelimelle ja purkamme sen siellä.

#### Toolkit

```bash
# Gracefully shutdown the old instance
old-server$ bin/stop

# Create the tar-ball
old-server$ tar --create --file backup-old-server.tar config/ data/

# Copy the backup-old-server.tar file from the old-server to the
# new-server using any method that fits

# Gracefully shutdown new instance (if started yet)
new-server$ bin/stop

# Move new data, you can delete it too
new-server$ mkdir backup-new-server
new-server$ mv config/ data/ backup-new-server/

# Populate config/data dir again
new-server$ tar --extract --file backup-old-server.tar

# Start containers
new-server$ bin/up
```

#### Docker Compose

```bash wrap
# Gracefully shutdown the old instance
old-server$ docker stop sharelatex
old-server$ docker stop mongo redis

# Create the tar-ball
old-server$ tar --create --file backup-old-server.tar ~/OVERLEAF_data ~/mongo_data ~/redis_data

# Copy the backup-old-server.tar file from the old-server to
# the new-server using any method that fits

# Gracefully shutdown new instance (if started yet)
new-server$ docker stop sharelatex
new-server$ docker stop mongo redis

# Move new data, you can delete it too
new-server$ mkdir backup-new-server
new-server$ mv ~/OVERLEAF_data ~/mongo_data ~/redis_data backup-new-server/

# Populate data dirs again
new-server$ tar --extract --file backup-old-server.tar

# Start containers
new-server$ docker start mongo redis
new-server$ docker start sharelatex
```

**docker-compose.yml**-tiedostostasi riippuen saatat joutua mukauttamaan `mongo`-, `redis`- ja `overleaf`-volyymien polkuja.

<Info>

Kun tar ajetaan root-käyttäjänä (tai sudolla), se säilyttää tiedostojen omistajan/ryhmän ja oikeudet, mikä on ratkaisevan tärkeää varmuuskopiota palautettaessa.

</Info>

### Kansiot yksityiskohtaisesti

<Info>

Seuraavilla kansioilla on lisämerkintöjä:

* (b) sisällytä varmuuskopioihin, mieluiten instanssin ollessa pysäytettynä yhtenäisyyden varmistamiseksi
* (d) voidaan poistaa
* (e) tilapäiset tiedostot, voidaan poistaa instanssin ollessa pysäytettynä

</Info>

1. `~/mongo_data` (b)
   * MongoDB:n datahakemisto
2. `~/redis_data` (b)
   * Redis-tietokannan datahakemisto
3. `~/overleaf_data`
   1. bin
      1. synctex (d)
         * ei käytössä uusimmassa julkaisussa; aiemmin käytettiin mukautettua synctex-binääriä (synctexiä käytetään lähdekoodin vastaavuuksiin .tex-tiedostojen ja pdf:n välillä)
   2. data
      1. cache (e)
         * käännösten binääritiedostovälimuisti
      2. compiles (e)
         * LaTeX-käännös tapahtuu täällä
      3. db.sqlite (d)
         * ei käytössä uusimmassa julkaisussa; tallensi aiemmin clsi-välimuistin tietoja (siirretty joko yksinkertaisiin muistinsisäisiin rakenteisiin tai levy skannataan)
      4. db.sqlite-wal (d)
         * ei käytössä uusimmassa julkaisussa, katso db.sqlite
      5. output (e)
         * LaTeX-käännösten tulosteiden tallennus asiakkaalle tarjoamista varten
      6. template\_files (b)
         * mallijärjestelmän kuvaesikatselut (vain Ayakaleaf Pro)
      7. user\_files (b)
         * projektien binääritiedostot
      8. history (b)
         * projektien täydet historiatiedostot
   3. tmp
      1. dumpFolder (e)
         * zip-tiedostojen käsittelyn väliaikaiset tiedostot
      2. uploads (e)
         * tiedostolatausten puskurointi (binääritiedoston / uuden projektin zip-latauksessa)
      3. projectHistories (e)
         * väliaikaiset tiedostot projektien täyden historian siirtoja varten

### Q\&A

<Accordion title="MongoDB-tiedot ovat vioittuneet tai osittain poistettu, eikä minulla ole varmuuskopiota. Mitä voin tehdä?">

<strong>Vastaus:</strong> `mongo`-kontti ei itse säilytä tietoja: tietokanta on hakemistossa `data/mongo` (`MONGO_DATA_PATH` tiedostossa `config/overleaf.rc`). Jos vain kontti on rikki, poista se komennolla `bin/docker-compose rm -sf mongo` ja luo se uudelleen suorittamalla `bin/up -d`.

Jos MongoDB ei käynnisty, koska sen tiedostot ovat vioittuneet tai puuttuvat, viimeinen keino on MongoDB:n oma [`mongod --repair`](https://www.mongodb.com/docs/v8.0/tutorial/recover-data-following-unexpected-shutdown/). Se hylkää vioittuneet tiedot ja luo puuttuvien tilalle tyhjiä tynkätiedostoja, joten varaudu tietojen menetykseen. Pysäytä kaikki ja kopioi datahakemisto ensin, ja suorita sitten korjaus samalla imagella kuin `mongo`-konttisi (`MONGO_IMAGE` ja `MONGO_VERSION` tiedostossa `config/overleaf.rc`, oletuksena `mongo:8.0`):

```bash
# In the Toolkit directory
bin/stop
sudo cp -a data/mongo data/mongo-original   # keep this copy untouched
docker run --rm -v "$PWD/data/mongo:/data/db" mongo:8.0 mongod --dbpath /data/db --repair
bin/up -d
```

Jos korjauksen piti muuttaa tietoja, MongoDB ei enää käynnisty replikajoukon jäsenenä, ja Toolkit ajaa sitä sellaisena (`--replSet overleaf`): `bin/logs mongo` näyttää viestin `This instance has been repaired and may contain modified replicated data`. Käynnistä tällöin korjatut tiedostot ilman `--replSet`-valitsinta, vedosta ne ja palauta vedos uuteen tietokantaan:

```bash
bin/stop
docker run -d --name mongo-repaired -v "$PWD/data/mongo:/data/db" mongo:8.0
# wait a few seconds for mongod to start
docker exec mongo-repaired mongodump --db sharelatex --archive --gzip > mongo-backup.gz
docker rm -f mongo-repaired
sudo mv data/mongo data/mongo-repaired
bin/up -d   # starts with a new, empty data/mongo
```

Palauta sitten `mongo-backup.gz` yllä olevan [MongoDB](#mongodb)-osion `mongorestore`-komennolla.

Jos MongoDB-tiedot ovat kadonneet kokonaan, Ayakaleaf Pro ei voi rakentaa projekteja uudelleen. Käyttäjät, projektiluettelo, kansiorakenteet, dokumenttien nykyinen teksti ja historian hakemisto on kaikki tallennettu MongoDB:hen. `data/overleaf/data/history` sisältää edelleen ladatut tiedostot ja historian sisällön sisältötiivisteiden alle tallennettuina (`overleaf-project-blobs`) sekä gzip-pakattuina JSON-historiapaloina (`overleaf-chunks`), mutta mitään työkalua niiden muuttamiseksi takaisin projekteiksi ei ole. Voit vain etsiä niistä käsin.

</Accordion>
