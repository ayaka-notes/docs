---
title: 1. Obtener las imágenes de Ayakaleaf Pro
description: Usa las mismas imágenes de Ayakaleaf Pro que el Toolkit.
icon: split
---

Kubernetes ejecuta las mismas imágenes que el Toolkit. No existe una imagen independiente para Kubernetes.

| Imagen                                               | Usada por                                                               |
| ---------------------------------------------------- | ----------------------------------------------------------------------- |
| `ghcr.io/ayaka-notes/overleaf-pro:6.3.2`             | el Deployment `overleaf`                                                |
| `ghcr.io/ayaka-notes/overleaf-pro/git-bridge:6.3.2`  | [Integración con Git](/es/on-premises/configuration/kubernetes/integrations/git-integration) (opcional), con la misma etiqueta que la anterior |
| `ghcr.io/ayaka-notes/texlive-*`                      | compilaciones, descargadas en Docker en los nodos en el [paso 0](/es/on-premises/installation/using-kubernetes/0.-prepare-the-nodes) |

Las imágenes son públicas en [ghcr.io](https://github.com/ayaka-notes/ayakaleaf-pro/pkgs/container/overleaf-pro/) para amd64 y arm64, por lo que el kubelet puede descargarlas sin credenciales.

<Warning>

Usa siempre una etiqueta de versión, como `6.3.2`, no `latest`. Las actualizaciones ejecutan migraciones de la base de datos y deben seguir [Actualizar en Kubernetes](/es/on-premises/maintenance/upgrading-on-kubernetes); una etiqueta móvil actualizaría un pod cada vez que se reprogramara.

</Warning>

### Preguntas y respuestas

<Accordion title="Nuestros nodos no pueden acceder a ghcr.io. ¿Qué hacemos?">

<strong>Respuesta:</strong> Copia las imágenes a un registro al que puedan acceder los nodos y usa ese nombre en los manifiestos, por ejemplo:

```bash
docker pull ghcr.io/ayaka-notes/overleaf-pro:6.3.2
docker tag ghcr.io/ayaka-notes/overleaf-pro:6.3.2 registry.example.com/ayakaleaf/overleaf-pro:6.3.2
docker push registry.example.com/ayakaleaf/overleaf-pro:6.3.2
```

Para un registro sin TLS, containerd necesita en cada nodo un `/etc/containerd/certs.d/<registry>/hosts.toml` con `server = "http://<registry>"`, y `config_path` configurado como en el [paso 0](/es/on-premises/installation/using-kubernetes/0.-prepare-the-nodes). Docker por sí mismo solo hace push por HTTP sin cifrar a `localhost`, así que haz push a través de `localhost:<port>` en el host del registro o añádelo a `insecure-registries`.

</Accordion>
