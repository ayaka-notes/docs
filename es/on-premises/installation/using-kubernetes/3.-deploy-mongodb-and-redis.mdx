Ayakaleaf Pro necesita:

* **MongoDB 8** como **replica set** (usa transacciones). Tres miembros repartidos en tres nodos sobreviven a la pérdida de un nodo; un solo miembro también funciona.
* **Redis 7**, un servidor con persistencia AOF. Redis contiene las ediciones que aún no se han escrito en MongoDB, las sesiones y los mensajes entre los servicios de Overleaf. Overleaf se conecta a un único servidor Redis: Sentinel y Redis Cluster no son compatibles.

<Info>

En su lugar, puedes usar servicios gestionados, como MongoDB Atlas o el Redis de tu nube. Omite esta página y establece `OVERLEAF_MONGO_URL` y `OVERLEAF_REDIS_HOST` con sus direcciones en el [paso 4](/es/on-premises/installation/using-kubernetes/4.-personalizing-your-instance).

</Info>

<Steps>
<Step title="MongoDB">
```yaml title="10-mongo.yaml" wrap
apiVersion: v1
kind: Service
metadata:
  name: mongo
  namespace: overleaf
spec:
  clusterIP: None                 # headless: gives mongo-0.mongo, mongo-1.mongo, ...
  publishNotReadyAddresses: true  # members must resolve each other before the set is initiated
  selector:
    app: mongo
  ports:
    - name: mongo
      port: 27017
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mongo
  namespace: overleaf
spec:
  serviceName: mongo
  replicas: 3
  selector:
    matchLabels:
      app: mongo
  template:
    metadata:
      labels:
        app: mongo
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app: mongo
              topologyKey: kubernetes.io/hostname
      containers:
        - name: mongo
          image: mongo:8.0
          args:
            - --replSet=overleaf
            - --bind_ip_all
            - --wiredTigerCacheSizeGB=0.25   # default is 50% of (RAM - 1 GB); size it for your nodes
          # env:
          #   - name: GLIBC_TUNABLES        # only on kernel 6.19+ (SERVER-121912)
          #     value: glibc.pthread.rseq=1
          ports:
            - containerPort: 27017
          readinessProbe:
            tcpSocket:
              port: 27017
          resources:
            requests:
              cpu: 100m
              memory: 384Mi
            limits:
              memory: 768Mi
          volumeMounts:
            - name: data
              mountPath: /data/db
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 5Gi
---
# Initiates the replica set once. Safe to re-run: it does nothing when the set exists.
apiVersion: batch/v1
kind: Job
metadata:
  name: mongo-init-replica-set
  namespace: overleaf
spec:
  backoffLimit: 20
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: init
          image: mongo:8.0
          command:
            - mongosh
            - --quiet
            - --host=mongo-0.mongo
            - --eval
            - |
              try {
                rs.status()
                print('replica set already initiated')
              } catch (e) {
                rs.initiate({
                  _id: 'overleaf',
                  members: [
                    { _id: 0, host: 'mongo-0.mongo.overleaf.svc.cluster.local:27017' },
                    { _id: 1, host: 'mongo-1.mongo.overleaf.svc.cluster.local:27017' },
                    { _id: 2, host: 'mongo-2.mongo.overleaf.svc.cluster.local:27017' },
                  ],
                })
              }
```

```bash
kubectl apply -f 10-mongo.yaml
kubectl -n overleaf rollout status statefulset/mongo
kubectl -n overleaf wait --for=condition=complete job/mongo-init-replica-set --timeout=5m
kubectl -n overleaf exec mongo-0 -- mongosh --quiet --eval 'rs.status().members.map(m => m.name + " " + m.stateStr)'
```

Al cabo de unos segundos, un miembro debería estar en `PRIMARY` y los demás en `SECONDARY`. El Job reintenta hasta que todos los miembros responden, así que es normal que fallen algunos pods del Job.

* El Service headless necesita `publishNotReadyAddresses: true`: los miembros deben encontrarse por nombre antes de que exista el replica set.
* Los miembros se añaden con sus nombres estables (`mongo-0.mongo.overleaf.svc.cluster.local`), nunca con las IP de los pods, que cambian en cada reinicio.
* Para un solo miembro, establece `replicas: 1` y conserva solo `mongo-0` en el Job.
</Step>

<Step title="Redis">
```yaml title="20-redis.yaml" wrap
apiVersion: v1
kind: Service
metadata:
  name: redis
  namespace: overleaf
spec:
  selector:
    app: redis
  ports:
    - name: redis
      port: 6379
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
  namespace: overleaf
spec:
  serviceName: redis
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis
          image: redis:7.4
          args: [--appendonly, "yes"]
          ports:
            - containerPort: 6379
          readinessProbe:
            tcpSocket:
              port: 6379
          resources:
            requests:
              cpu: 50m
              memory: 128Mi
            limits:
              memory: 512Mi
          volumeMounts:
            - name: data
              mountPath: /data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 2Gi
```

```bash
kubectl apply -f 20-redis.yaml
kubectl -n overleaf rollout status statefulset/redis
```
</Step>

### Preguntas y respuestas

<Accordion title="MongoDB 8 falla al arrancar con un kernel reciente. ¿Por qué?">

<strong>Respuesta:</strong> MongoDB 8 falla con el kernel de Linux 6.19 y posteriores ([SERVER-121912](https://jira.mongodb.org/browse/SERVER-121912)). Descomenta la variable de entorno `GLIBC_TUNABLES` en `10-mongo.yaml`.

</Accordion>

<Accordion title="¿Cuánta memoria necesita MongoDB?">

<strong>Respuesta:</strong> Por defecto, MongoDB usa para su caché la mitad de la memoria del nodo menos 1 GB, y ve la memoria del nodo, no el límite del pod. Ajusta `--wiredTigerCacheSizeGB` a tus nodos; `0.25` mantuvo cada miembro en unos 200 a 260 MiB en nuestros nodos de prueba de 4 GB.

</Accordion>
