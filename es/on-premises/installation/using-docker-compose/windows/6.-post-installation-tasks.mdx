### Crear el administrador y un primer proyecto {#create-the-administrator-and-a-first-project}

Abre [http://localhost:8080/launchpad](http://localhost:8080/launchpad) en tu **navegador de Windows**, crea la primera cuenta de administrador e inicia sesión. Después, sigue [6. Tareas posteriores a la instalación](/es/on-premises/installation/using-docker-compose/linux/6.-post-installation-tasks) de la guía de Linux, usando el puerto `8080` en sus URL de ejemplo.

### Verificar la compilación {#verify-compilation}

Que la página de inicio de sesión funcione no demuestra que los contenedores de compilación independientes puedan acceder al directorio de datos de WSL. Crea un proyecto en blanco y compila este `main.tex` con **pdfLaTeX**:

```latex
\documentclass{article}
\begin{document}
Ayakaleaf Pro on Windows WSL 2.
\end{document}
```

La vista previa del PDF debería mostrar el texto. Con la imagen basic, selecciona **TeX Live 2026 Basic** en la configuración del proyecto si es necesario.

Selecciona **XeLaTeX** y prueba:

```latex
\documentclass{article}
\usepackage{fontspec}
\begin{document}
Ayakaleaf WSL XeLaTeX sandbox.
\end{document}
```

Ambos ejemplos funcionan con basic. Para documentos en chino, usa una imagen que contenga `ctex` y las fuentes necesarias, como full, antes de probar lo siguiente con **XeLaTeX**. Basic no los incluye:

```latex
\documentclass{ctexart}
\begin{document}
你好，Ayakaleaf Pro。
\end{document}
```

Para confirmar que se usa el sandbox, ejecuta en **Ubuntu** mientras se compila:

```bash
docker ps -a --filter ancestor=ghcr.io/ayaka-notes/texlive-basic:2026.1
bin/logs -f clsi
```

Usa en el filtro el nombre de la imagen que hayas elegido. Las compilaciones cortas pueden terminar antes de que se ejecute `docker ps`; `-a` también muestra los contenedores detenidos hasta que se limpian. Un contenedor de compilación debería usar esa imagen y un bind mount `/compile` desde el directorio de datos de WSL del Toolkit. Los registros de la aplicación por sí solos no sustituyen a la comprobación del PDF.

### Verificar la persistencia {#verify-persistence}

En **Ubuntu**, desde el directorio del Toolkit:

```bash
bin/stop
bin/start
```

Espera a la aplicación, vuelve a abrir el proyecto desde Windows y compílalo de nuevo. Tu cuenta, el código fuente y los archivos del proyecto deberían seguir ahí. De forma predeterminada, los datos en uso están en `~/ayakaleaf-toolkit/data/` dentro de Ubuntu. Conserva tanto `config/` como `data/`; desinstalar o anular el registro de la distribución de Ubuntu puede eliminarlos.

### Mantener la instancia disponible {#keep-the-instance-available}

Mantener la instancia en funcionamiento tiene tres partes: Windows permanece activo, Docker Desktop se ejecuta y los contenedores se reinician con el motor.

En **Settings → General** de Docker Desktop, activa **Start Docker Desktop when you sign in to your computer**; consulta [la configuración de Docker Desktop](https://docs.docker.com/desktop/settings-and-maintenance/settings/). Esto inicia Docker después de iniciar sesión, no antes. Tras reiniciar Windows, inicia sesión, espera a que Docker Desktop termine de iniciarse, abre Ubuntu y comprueba `docker ps` y el sitio.

El **Resource Saver** de Docker Desktop es independiente de la suspensión de Windows. Normalmente solo se activa cuando no hay contenedores en ejecución; la aplicación, MongoDB y Redis en ejecución impiden esa condición de inactividad. En WSL 2 pausa el motor de Docker en lugar de apagar la máquina virtual WSL compartida. No uses manualmente **Pause** en Docker Desktop mientras das servicio a usuarios. No necesitas desactivar Resource Saver solo para mantener esta pila en funcionamiento; consulta [la documentación de Resource Saver de Docker](https://docs.docker.com/desktop/use-desktop/resource-saver/).

Los servicios del Toolkit usan `restart: always`. Verifica el ajuste real en **Ubuntu**:

```bash
docker inspect sharelatex mongo redis --format '{{.Name}} restart={{.HostConfig.RestartPolicy.Name}}'
```

Cada servicio debería indicar `always`. Una vez que Docker se ejecuta, puede reiniciar esos contenedores existentes sin un nuevo `bin/up`. Un contenedor detenido manualmente permanece detenido hasta que lo inicies o reinicies el motor; con `always`, un reinicio del motor puede volver a iniciarlo. Consulta [el comportamiento de las políticas de reinicio de Docker](https://docs.docker.com/engine/containers/start-containers-automatically/).

| Acción | Efecto en Ayakaleaf |
| --- | --- |
| Cerrar el terminal de Ubuntu después de `bin/up -d` | Los contenedores se ejecutan en segundo plano; el terminal no es su supervisor. Mantén disponibles Docker Desktop y el entorno WSL |
| Cerrar la ventana del Docker Dashboard | La ventana puede cerrarse mientras Docker Desktop continúa en la bandeja del sistema |
| Elegir **Quit Docker Desktop** | Detiene el motor y deja el sitio no disponible; vuelve a abrir Docker Desktop para recuperarlo |
| Ejecutar `wsl --shutdown` | Detiene todas las distribuciones de WSL e interrumpe el backend WSL de Docker; reinicia Docker Desktop y vuelve a abrir Ubuntu |
| Suspender, hibernar o apagar Windows | El servicio no está disponible; mantener solo la pantalla encendida o apagada no cambia esto |
| Ejecutar `bin/stop` | Detiene la instancia conservando sus datos; usa `bin/start` para reanudarla |

Para un uso prolongado con alimentación de corriente, abre en Windows 11 **Configuración → Sistema → Energía y batería → Tiempos de espera de pantalla, suspensión e hibernación** (algunas versiones muestran **Energía** o **Pantalla y suspensión**). Establece el tiempo de suspensión con el equipo enchufado en **Nunca** y desactiva la hibernación automática si está configurada. La pantalla puede seguir apagándose. La acción de la tapa de un portátil es un ajuste aparte; cerrar la tapa puede suspenderlo aunque el tiempo de suspensión por inactividad sea Nunca. Consulta [la configuración de energía de Windows](https://support.microsoft.com/en-us/windows/experience/power-battery/power-settings-in-windows-11).

No ejecutes `wsl --shutdown` como limpieza rutinaria mientras el sitio está en uso. Si un cambio en la configuración de WSL lo requiere, detén primero la instancia y planifica una interrupción. Windows puede ejecutar la instancia de forma continua con estos ajustes. Para un servicio compartido que deba sobrevivir a cierres de sesión y reinicios desatendidos, recomendamos la [guía de Linux](/es/on-premises/installation/using-docker-compose/linux).

### Comprobar la recuperación tras reiniciar Docker Desktop {#check-recovery-after-restarting-docker-desktop}

Después de guardar el trabajo y dejar que terminen las compilaciones activas, elige **Restart Docker Desktop** en el menú de solución de problemas de Docker Desktop. Espera al motor y, a continuación, comprueba en **Ubuntu**:

```bash
docker ps
curl -I http://localhost:8080/launchpad
```

Abre el proyecto existente en Windows y compílalo de nuevo. Confirma que la cuenta y el código fuente siguen existiendo.

Si detuviste la instancia intencionadamente con `bin/stop`, usa `bin/start`. Si Docker está en marcha pero un servicio falla, lee sus registros en lugar de volver a crear la configuración. Las actualizaciones de Windows, las actualizaciones de Docker y los cortes de corriente pueden seguir interrumpiendo una instalación que funcione las 24 horas; mantén copias de seguridad y comprueba la recuperación después del mantenimiento planificado.

### Uso diario {#daily-use}

Inicia Docker Desktop en Windows. Abre **Ubuntu**:

```bash
cd "$HOME/ayakaleaf-toolkit"
```

| Tarea | Comando |
| --- | --- |
| Iniciar los contenedores existentes | `bin/start` |
| Detener los contenedores y conservar los datos | `bin/stop` |
| Aplicar cambios de configuración | `bin/up -d` |
| Comprobar el estado | `bin/docker-compose ps` |
| Leer los registros de arranque | `bin/docker-compose logs --tail=100 sharelatex` |
| Leer los registros de MongoDB | `bin/docker-compose logs --tail=100 mongo` |
| Leer los registros del compilador | `bin/logs -f clsi` |

`bin/start` no aplica las ediciones de configuración: usa `bin/up -d` después de cambiar `config/`. Sigue [Datos y copias de seguridad](/es/on-premises/maintenance/data-and-backups) antes de actualizar, trasladar o eliminar la distribución de WSL. Copiar los archivos de MongoDB en uso mientras la base de datos escribe no es una copia de seguridad coherente.

Mantén `127.0.0.1` para uso local. Dar servicio a otros equipos también requiere establecer deliberadamente la dirección de escucha, la URL del sitio, la configuración de red y del firewall de Windows y HTTPS; cambiar solo `OVERLEAF_SITE_URL` no publica ningún puerto.

Si algo no funciona, consulta [Solución de problemas](/es/on-premises/installation/using-docker-compose/windows/troubleshooting).
