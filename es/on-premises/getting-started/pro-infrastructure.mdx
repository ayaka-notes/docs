#### Servicios

La infraestructura de Overleaf Pro consta de cuatro servicios principales: `sharelatex`, `git-bridge` (opcional), `mongo` y `redis`. El servicio `sharelatex`, que ejecuta la aplicación principal de Server Pro, depende de los servicios `mongo` y `redis` para su base de datos y para las funcionalidades de caché y tiempo real, y de `git-bridge` para gestionar la [integración con Git](/es/on-premises/configuration/overleaf-toolkit/git-integration) (opcional). El único puerto publicado en la máquina anfitriona es el puerto 80, que utiliza el contenedor `sharelatex`.

Server Pro también admite opcionalmente [almacenamiento compatible con S3](/es/on-premises/configuration/overleaf-toolkit/s3) para los archivos de proyecto y el historial completo de proyectos, además de poder hacer de proxy para el acceso al [sitio de documentación principal de Overleaf](https://www.overleaf.com/learn). Para más información, consulta nuestra guía sobre las páginas de [Añadir ayuda de LaTeX para usuarios](/es/on-premises/configuration/overleaf-toolkit/adding-latex-user-help).

<Info>

Si es necesario, MongoDB y Redis pueden externalizarse mediante variables de entorno que apunten a servicios externos. Para más información, consulta [Configurar Overleaf](/es/on-premises/configuration) si usas Docker Compose y [Ajustes del Toolkit](/es/on-premises/configuration/overleaf-toolkit/toolkit-settings) si usas el Overleaf Toolkit.

</Info>

#### Compilación

Para las [compilaciones en sandbox](/es/on-premises/configuration/overleaf-toolkit/sandboxed-compiles), el contenedor `sharelatex` orquesta la creación de nuevos contenedores para gestionar las compilaciones de los proyectos; lo hace a través del socket de Docker de la máquina anfitriona. Puedes leer más sobre el editor y el proceso completo de compilación y caché [aquí](/es/on-premises/getting-started/microservices#editor-and-compile-process).

#### Red

La comunicación entre contenedores se realiza mediante la resolución DNS interna de Docker a través de una red bridge dedicada, y no hay cortafuegos habilitados. Por defecto, los servicios anteriores usan sus respectivos puertos estándar, aunque pueden configurarse mediante variables de entorno. El contenedor `sharelatex` usa el puerto 80 para el acceso web externo (servido por Nginx), el contenedor `mongo` usa el puerto 27017 y `redis` usa el puerto 6379.

Si usas nuestra solución gestionada [Overleaf Toolkit](https://github.com/overleaf/toolkit), puedes [habilitar opcionalmente un proxy TLS](/es/on-premises/configuration/overleaf-toolkit/tls-proxy) para terminar las conexiones HTTPS con Nginx mediante una variable de entorno. Como alternativa, puedes usar tu proxy TLS existente.

<Info>

Puedes ver un diagrama que explica el flujo de las solicitudes [aquí](/es/on-premises/configuration/overleaf-toolkit/tls-proxy).

</Info>

#### Resumen

* Fuera de la red de Docker, solo el puerto 80 es accesible y está vinculado a Nginx. <strong>Nota:</strong> El contenedor `sharelatex` ejecuta muchos [servicios](https://github.com/overleaf/overleaf/tree/main/services) que se comunican entre sí mediante HTTP. Sin embargo, estos puertos **no** son accesibles desde fuera de la red de Docker.
* Dentro de la red de Docker, los servicios de Overleaf, MongoDB, Redis y Git Bridge pueden comunicarse libremente entre sí.
* Dentro de los contenedores de [compilaciones en sandbox](/es/on-premises/configuration/overleaf-toolkit/sandboxed-compiles) no hay red disponible.
