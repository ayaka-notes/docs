#### Servicios

La infraestructura de Overleaf Pro consta de cuatro servicios principales: `sharelatex`, `git-bridge` (opcional), `mongo` y `redis`. El servicio `sharelatex`, que ejecuta la aplicación principal de Server Pro, depende de los servicios `mongo` y `redis` para su base de datos y sus funciones de caché/tiempo real, y de `git-bridge` para gestionar la [integración con Git](/es/on-premises/configuration/overleaf-toolkit/git-integration) (opcional). El único puerto publicado en la máquina host es el puerto 80, que utiliza el contenedor `sharelatex`.

Server Pro también admite opcionalmente [almacenamiento compatible con S3](/es/on-premises/configuration/overleaf-toolkit/s3) para los archivos de proyecto y el historial completo de proyectos, además de poder hacer de proxy para el acceso al [sitio de documentación de Overleafarrow-up-right](https://www.overleaf.com/learn) principal. Para más información, consulta nuestra guía sobre las páginas de [Añadir ayuda de LaTeX para usuarios](/es/on-premises/configuration/overleaf-toolkit/adding-latex-user-help).

<Info>

Si es necesario, MongoDB y Redis pueden externalizarse mediante variables de entorno que apunten a servicios externos. Para más información, consulta [Configurar Overleaf](/es/on-premises/configuration) si utilizas Docker Compose y [Ajustes del Toolkit](/es/on-premises/configuration/overleaf-toolkit/toolkit-settings) si utilizas el Overleaf Toolkit.

</Info>

#### Compilación

Para las [compilaciones aisladas (Sandboxed Compiles)](/es/on-premises/configuration/overleaf-toolkit/sandboxed-compiles), el contenedor `sharelatex` orquesta la creación de nuevos contenedores para gestionar las compilaciones de los proyectos; lo hace a través del socket de Docker de la máquina host. Puedes leer más sobre el editor y el proceso completo de compilación/caché [aquí](/es/on-premises/getting-started/microservices#editor-and-compile-process).

#### Redes

La comunicación entre contenedores se realiza mediante la resolución DNS interna de Docker a través de una red puente dedicada, y no hay cortafuegos habilitados. De forma predeterminada, los servicios anteriores utilizan sus respectivos puertos estándar, pero estos se pueden configurar mediante variables de entorno. El contenedor `sharelatex` utiliza el puerto 80 para el acceso web externo (servido por Nginx), el contenedor `mongo` utiliza el puerto 27017 y `redis` utiliza el puerto 6379.

Los clientes que utilizan nuestra solución gestionada [Overleaf Toolkitarrow-up-right](https://github.com/overleaf/toolkit) pueden, opcionalmente, [habilitar un proxy TLS](/es/on-premises/configuration/overleaf-toolkit/tls-proxy) para terminar las conexiones HTTPS mediante Nginx a través de una variable de entorno. También puedes utilizar tu proxy TLS existente.

<Info>

Puedes ver un diagrama que explica el flujo de las solicitudes [aquí](/es/on-premises/configuration/overleaf-toolkit/tls-proxy).

</Info>

#### Resumen

* Fuera de la red de Docker, solo el puerto 80 es accesible y está vinculado a Nginx. **Nota:** el contenedor `sharelatex` ejecuta muchos [serviciosarrow-up-right](https://github.com/overleaf/overleaf/tree/main/services) que se comunican entre sí mediante HTTP. Sin embargo, estos puertos **no** son accesibles desde fuera de la red de Docker.
* Dentro de la red de Docker, los servicios de Overleaf, MongoDB, Redis y Git Bridge pueden comunicarse libremente entre sí.
* Dentro de los contenedores de [compilaciones aisladas](/es/on-premises/configuration/overleaf-toolkit/sandboxed-compiles), no hay red disponible.
