<Info>

Si nunca ejecutó Server Pro versión 5.0.1 o Community Edition versión 5.0.1, o si inició una instancia completamente nueva con la 5.0.1, no necesita ejecutar este proceso de recuperación.

</Info>

**Actualizaciones de esta página:**

* (2024-04-22 13:40 BST): Se añadió el paso "Detener la entrada de nuevas actualizaciones en el sistema y volcar todos los cambios a MongoDB".
* (2024-04-23 11:45 BST): Se tienen en cuenta los volcados fallidos en la 5.0.1 y se omiten los volcados cuando ya se había iniciado la 5.0.2.

La duración de la recuperación dependerá del número y del tamaño de los proyectos de su instancia y del backend de almacenamiento utilizado por el almacén de historial para los chunks (definido en `OVERLEAF_HISTORY_CHUNKS_BUCKET`).

El proceso de recuperación retrasará el inicio de la aplicación dentro del contenedor de Server Pro. Durante ese tiempo, el sitio aparecerá como fuera de línea. Solo admitimos ejecutar la recuperación desde una única instancia del contenedor de Server Pro; todos los demás workers de escalado horizontal deben estar desconectados.

Puede detener y reanudar el proceso de recuperación si es necesario.

Según nuestras pruebas de rendimiento, el proceso de recuperación puede procesar aproximadamente 10 000 proyectos pequeños por minuto en hardware moderno (CPU a 3 GHz y almacenamiento NVMe local). Por ejemplo, para una instancia con 100 000 proyectos, programe una ventana de mantenimiento que permita al menos 10+2 min de inactividad. Utilice la siguiente consulta para estimar el número de proyectos de su instancia:

```bash wrap
$ docker exec mongo mongosh sharelatex --quiet --eval 'db.projects.estimatedDocumentCount() + db.deletedProjects.estimatedDocumentCount()'
```

Lea por completo los siguientes pasos de recuperación antes de empezar. Los clientes de Server Pro pueden ponerse en contacto con [support@overleaf.com](mailto:support@overleaf.com) para cualquier pregunta.

### Proceso de recuperación

<Steps>
<Step title="Descargue las imágenes de la versión">
Descargue las imágenes de la versión `5.0.3`.
</Step>

<Step title="Identifique algunos proyectos">
Identifique por su id algunos proyectos a los que les falte el historial; lo ideal es que tenga permiso para realizar cambios en uno de ellos.
</Step>

<Step title="Programe el mantenimiento">
Programe una ventana de mantenimiento para el tiempo de inactividad.
</Step>

<Step title="Detenga todos los workers excepto uno">
Si utiliza una configuración de escalado horizontal, detenga todos los workers excepto uno.
</Step>

<Step title="Detenga las nuevas actualizaciones y vuelque todos los cambios a MongoDB">
Detenga la entrada de nuevas actualizaciones en el sistema y vuelque todos los cambios a MongoDB:

1. Cierre el editor y desconecte manualmente a todos los usuarios mediante el panel de administración en `https://my-server-pro.example.com/admin#open-close-editor`, en la pestaña "Open/Close Editor".
2.  Detenga el servicio Websocket/real-time.

    ```bash
    $ docker exec sharelatex sv stop real-time-overleaf
    ```
3.  Espere a que el servicio real-time finalice, lo que se indica con `down:`.

    ```bash
    $ docker exec sharelatex sv status real-time-overleaf
    run: real-time-sharelatex: (pid 394) 50s, want down, got TERM
    # wait a little longer...

    $ docker exec sharelatex sv status real-time-overleaf
    down: real-time-sharelatex: 7s, normally up
    ```
4.  Detenga el contenedor git-bridge si está habilitado.

    ```bash
    $ docker stop git-bridge
    ```
5.  Si nunca ejecutó la 5.0.2: lance un volcado manual de las actualizaciones de documentos y espere a que finalice correctamente.

    Puede repetir el comando en caso de error. Si ve un `failureCount` distinto de cero en ejecuciones sucesivas, detenga la migración (restaure los servicios mediante `docker restart git-bridge sharelatex`) y póngase en contacto con el soporte.

    ```bash wrap
    $ docker exec sharelatex bash -c 'source /etc/container_environment.sh && source /etc/overleaf/env.sh && cd services/document-updater && LOG_LEVEL=info node scripts/flush_all.js'
        ...
        {"name":"default","hostname":"...","pid":324,"level":30,"successCount":...,"failureCount":0,"msg":"finished flushing all projects","time":"...","v":0}
        Done flushing all projects
        
    ```
6.  Si nunca ejecutó la 5.0.2: asegúrese de que todos los cambios se hayan volcado fuera de redis.

    Si obtiene cualquier salida de `redis-cli`, detenga la migración (restaure los servicios mediante `docker restart git-bridge sharelatex`) y póngase en contacto con el soporte.

    ```bash wrap
    $ docker exec redis redis-cli --scan --pattern 'DocVersion:*'
        # no output from redis-cli indicates success, check exit code of redis-cli next, it should be zero
        $ echo $?
        0
        
    ```
7.  Intente volcar los cambios de historial pendientes.

    Este volcado se hará en la medida de lo posible, ya que algunos proyectos tienen historiales dañados debido a la migración defectuosa de la base de datos. Cualquier fallo se resolverá con una resincronización del historial al final del proceso de recuperación.

    ```bash wrap
    $ docker exec sharelatex bash -c 'source /etc/container_environment.sh && source /
        
    ```
</Step>

<Step title="Realice una copia de seguridad">
Considere realizar una [copia de seguridad coherente](https://docs.overleaf.com/on-premises/maintenance/data-and-backups#performing-a-consistent-backup) de la instancia.
</Step>

<Step title="Actualice">
Actualice a la versión `5.0.3`.
</Step>

<Step title="Recuperación automática">
El proceso de recuperación se ejecuta automáticamente al iniciarse el contenedor.
</Step>

<Step title="Siga el progreso">
Puede seguir el progreso del script consultando de forma continua el archivo de registro `/var/lib/overleaf/data/history/doc-version-recovery.log`. Mostrará el número total de proyectos al principio y un resumen cada 1000 proyectos procesados.

```bash wrap
$ docker exec sharelatex tail --retry --follow /var/lib/overleaf/data/history/doc-vers
```
</Step>

<Step title="Espere a que finalice el proceso de recuperación">
Espere a que finalice el proceso de recuperación, ya sea siguiendo el archivo de registro anterior hasta que aparezca una línea `Done.` o esperando a que se muestre `Finished recovery of doc versions.` en la salida estándar del contenedor de Server Pro.
</Step>

<Step title="Valide el proceso de recuperación">
Valide el proceso de recuperación abriendo el panel de historial de algunos de los proyectos a los que antes les faltaba el historial.

1.  Acelere la resincronización de los proyectos que va a probar (acabarán procesándose, pero no queremos esperar a que les llegue el turno).

    ```bash wrap
    $ docker exec sharelatex curl -X POST --silent "http://127.0.0.1:3054/project/000000000000000000000000/resync?force=true"
        
    ```

    (Repita la operación con cada uno de los id de proyecto que vaya a probar, sustituyendo `000000000000000000000000` por un id de proyecto cada vez).
2. Abra el editor de los proyectos `https://my-server-pro.example.com/project/000000000000000000000000`
3. Abra el panel "History" del proyecto y compruebe el contenido más reciente.
4. Opcional: cierre de nuevo el panel "History". Realice un cambio en el código, como añadir un comentario en el encabezado.
5. Opcional: vuelva a compilar para forzar el volcado del cambio local. Abra de nuevo el panel "History" y compruebe el cambio. Cuando termine, deshaga el cambio.
</Step>

<Step title="Para el escalado horizontal...">
Vuelva a iniciar los demás workers.
</Step>

<Step title="Mantenga la instancia en ejecución">
Mantenga en ejecución la instancia que ejecutó el proceso de recuperación. Resincronizará en segundo plano el historial de todos los proyectos con una concurrencia de 1, lo que provocará una carga base ligeramente mayor. (Puede reiniciar la instancia, pero tendrá que volver a empezar con las resincronizaciones).
</Step>

<Step title="Avísenos cuando haya terminado">
Clientes de Server Pro: informen al equipo de soporte cuando hayan completado el proceso de recuperación.
</Step>
</Steps>
