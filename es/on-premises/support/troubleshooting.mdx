<Accordion title="Ejecutar Overleaf con un sistema de archivos NFS">

Montar un sistema de archivos NFS en un contenedor de Overleaf es técnicamente posible, pero no se recomienda y puede provocar distintos tipos de errores de rendimiento.

Un error habitual que aparece en las compilaciones es:

```text
EBUSY: resource busy or locked, unlink '/var/lib/overleaf/data/compiles/62f3d57bef7cf9005c364e75-62f3d57bef7cf9005c364e7a/.nfs573663533034825247625441'
```

En particular, desaconsejamos usar sistemas de archivos basados en NFS para datos efímeros, como los directorios que se usan para los datos de compilación. Recomendamos usar un disco temporal local, preferiblemente un SSD local, para los siguientes directorios.

En las instalaciones basadas en `docker-compose`, sugerimos simplemente sobrescribir el bind-mount de NFS, lo que evita cambiar rutas en la aplicación. Este es un ejemplo de un fragmento de configuración de `docker-compose` que usa un disco temporal montado en `/scratch`:

```yaml title="docker-compose excerpt"
services:
  sharelatex:
    environment:
      SANDBOXED_COMPILES_HOST_DIR: /scratch/compiles/
    volumes:
      - nfs:/var/lib/overleaf/data
      - /scratch/cache/:/var/lib/overleaf/data/cache
      - /scratch/compiles/:/var/lib/overleaf/data/compiles
      - /scratch/output/:/var/lib/overleaf/data/output
      - /scratch/tmp/:/var/lib/overleaf/tmp
```

No es necesario migrar ningún archivo existente desde el NFS a su nueva ubicación tras la actualización. El compilador de LaTeX puede volver a crear todos los archivos con una nueva compilación completa.

Para más detalles, consulta: https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-with-an-nfs-filesystem

</Accordion>

<Accordion title="Al ejecutar Overleaf en Windows o macOS, el servicio `mongo` no se inicia">

Si ejecutas Overleaf en Windows o macOS, es posible que el servicio `mongo` no se reinicie y muestre el error:

```text title="Example error"
Failed to start up WiredTiger under any compatibility version.
Reason: 1: Operation not permitted
```

Esto puede ocurrir cuando los datos de MongoDB se montan mediante bind mount desde un sistema de archivos que no proporciona la semántica que necesita, como un directorio montado desde Windows. Para [Windows con WSL 2](/es/on-premises/installation/using-docker-compose/windows), mantén el Toolkit en el directorio personal de Linux de Ubuntu y usa los bind mounts predeterminados. Consulta las [comprobaciones de MongoDB](/es/on-premises/installation/using-docker-compose/windows/troubleshooting#mongodb-fails-to-start) de la guía de la plataforma.

Para una instalación nueva que necesite almacenamiento gestionado por Docker, el siguiente override usa volúmenes con nombre (consulta las [indicaciones de almacenamiento de la imagen de MongoDB](https://github.com/docker-library/docs/blob/master/mongo/content.md#where-to-store-data)). En una instalación existente, cambiar los montajes no migra los datos: haz una copia de seguridad y restaura la base de datos/caché antes del cambio, o el servicio verá volúmenes vacíos. Añade esto a `config/docker-compose.override.yml`, combinándolo con cualquier configuración existente:

```yaml title="config/docker-compose.override.yml"
volumes:
  mongo-data:
  redis-data:

services:
  mongo:
    volumes:
      - mongo-data:/data/db

  redis:
    volumes:
      - redis-data:/data
```

Para más información, consulta: https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-on-windows-or-macos-results-in-the-mongoservice-not-starting

</Accordion>

<Accordion title="Actualizar a Redis 6.2 provoca un bucle de reinicios">

Usa el comando `docker logs redis` para obtener una copia de los registros.

Si ves la línea `Fatal: Can't initialize Background Jobs`, la salida completa tendrá un aspecto similar a este:

```text title="Redis log example"
1:M 11 Feb 2024 15:19:22.609 # Server initialized
1:M 11 Feb 2024 15:19:22.609 # Fatal: Can't initialize Background Jobs.
1:C 11 Feb 2024 15:19:26.055 # oO0OoO0OoO0Oo Redis is starting oO0OoO0OoO0Oo
```

Esto puede estar relacionado con la versión de Docker que estás usando. Actualizar a una versión >= 20.10.10 debería resolver el problema.

Para más información, consulta la incidencia original de Redis: https://github.com/redis/redis/issues/12362

Referencia: https://docs.overleaf.com/on-premises/support/troubleshooting#upgrading-to-redis-6.2-results-in-a-restart-loop

</Accordion>

<Accordion title="Orientación incorrecta de las imágenes de vista previa/miniatura de la galería de plantillas">

En ocasiones, las imágenes de vista previa/miniatura generadas por Ayakaleaf Pro pueden crearse con una orientación incorrecta y requerir una intervención manual para corregirlas. Estas imágenes se almacenan en `/var/lib/overleaf/data/template_files/`.

Recomendamos hacer una copia de seguridad de esta carpeta antes de realizar cualquier cambio.

Tendrás que seguir los pasos siguientes para cada plantilla afectada:

Busca el ID de la plantillaVe a la galería de plantillas de tu instancia (/templates/all), abre una plantilla afectada y copia el ID de la URL (por ejemplo: https://your-instance-url/templates/6645d346c224815e9460a695).Ejecuta el comando de correcciónEjecuta el siguiente comando desde el host de Docker (sustituye el ID de la plantilla por el que copiaste y actualiza la ruta si corresponde):docker exec sharelatex /bin/bash -c "mogrify -rotate 90 /var/lib/overleaf/data/template\_files/6645d346c224815e9460a695\_\*\{thumbnail,preview\}"

Referencia: https://docs.overleaf.com/on-premises/support/troubleshooting#incorrect-orientation-of-template-gallery-preview-thumbnail-images

</Accordion>

<Accordion title="Please verify that you have enabled system calls. For pdflatex, this is 'pdflatex -shell-escape'.">

El comando `\write18` está deshabilitado de forma predeterminada en Community Edition, ya que todas las compilaciones se realizan dentro del mismo contenedor `sharelatex`; esta es la opción predeterminada más segura.

Si quieres habilitarlo para pdflatex, crea un archivo `latexmkrc` en la raíz de tu proyecto con el siguiente contenido:

```perl title="latexmkrc"
$pdflatex = 'pdflatex --shell-escape';
```

A continuación, vuelve a compilar.

Referencia: https://docs.overleaf.com/on-premises/support/troubleshooting#please-verify-that-you-have-enabled-system-calls.-for-pdflatex-this-is-pdflatex-shell-escape

</Accordion>

<Accordion title="`bin/up` falla con `unable to upgrade to tcp, received 409` u `OCI runtime exec failed` después de «Initiating Mongo replica set...»">

Estos errores significan que el contenedor `mongo` se bloquea y se reinicia continuamente. `bin/up` inicia MongoDB y después ejecuta un comando dentro de él, que falla mientras el contenedor se reinicia. `bin/docker-compose ps` muestra el servicio `mongo` como `Restarting`.

Para encontrar la causa real, lee el registro de MongoDB:

```sh
bin/logs mongo
```

Las causas habituales son:

* <strong>La CPU no admite AVX.</strong> MongoDB 5.0 y posteriores necesitan AVX en x86-64, y el registro muestra `MongoDB 5.0+ requires a CPU with AVX support`. En una máquina virtual, establece el tipo de CPU en `host` para que AVX se transfiera.
* <strong>Kernel de Linux 6.19 a 7.0.13.</strong> MongoDB se niega a iniciarse con estos kernels. Consulta [Requisitos de software](/es/on-premises/installation/introduction#software-requirements) para ver la solución alternativa.
* <strong>Los datos los creó una versión anterior de MongoDB.</strong> MongoDB 8.0 no puede abrir directamente datos de 4.4 o 5.0. Actualiza una versión principal cada vez; consulta [Actualizar MongoDB](/es/on-premises/maintenance/updating-mongodb).

</Accordion>

<Accordion title="El registro muestra «Running Overleaf Community Edition, skipping TexLive checks»">

Es lo esperado con Ayakaleaf Pro y puedes ignorarlo. El mensaje se muestra cuando `OVERLEAF_IS_SERVER_PRO` no es `true`, que es lo que ocurre en la imagen de Ayakaleaf Pro. Ayakaleaf Pro no necesita esta variable, así que déjala sin definir.

</Accordion>

<Accordion title="El contenedor `sharelatex` se reinicia continuamente">

Antes de que Overleaf se inicie, el contenedor ejecuta comprobaciones de arranque y se cierra cuando una de ellas falla. El Toolkit lo ejecuta con `restart: always`, por lo que Docker lo vuelve a iniciar y la misma comprobación vuelve a fallar. La salida de arranque indica la comprobación que ha fallado:

```sh
bin/docker-compose logs --tail=100 sharelatex
```

Las causas más comunes son:

* **`Missing required secrets`**: establece `OVERLEAF_INVITE_TOKEN_SECRET` en `config/variables.env`; consulta [Variables de entorno](/es/on-premises/configuration/overleaf-toolkit/environment-variables).
* **`ShareLaTeX to Overleaf rebranding`**: la configuración sigue usando variables o rutas `SHARELATEX_`; renómbralas como indica el mensaje.
* **Un error después de `Checking can connect to mongo and redis`**: Overleaf no puede conectarse a MongoDB o Redis. Revisa `bin/logs mongo` y `bin/logs redis`.

Después de corregir la causa, ejecuta `bin/up -d`.

</Accordion>

<Accordion title="El contenedor se detiene en `910_initiate_doc_version_recovery` o sale con el código 2">

En cada arranque, el contenedor ejecuta sus scripts de inicio uno tras otro, y el registro nombra cada uno como `*** Running /etc/my_init.d/<script>...`. `910_initiate_doc_version_recovery` solo tiene trabajo que hacer en instancias que alguna vez ejecutaron Overleaf 5.0.1. En cualquier otra instancia imprime `No recovery of doc versions needed.` y el arranque continúa. Su salida también va a `data/history/doc-version-recovery.log` en `OVERLEAF_DATA_PATH`.

El código de salida y el final de `bin/docker-compose logs --tail=100 sharelatex` indican lo que ocurrió:

* **Código de salida 2**, y el registro termina con `*** Init system aborted.`: el contenedor se detuvo, por ejemplo con `bin/stop`, `docker stop` o Ctrl+C en `bin/up`. El script de la última línea `Running` es solo el que se estaba ejecutando en ese momento; no falló. Vuelve a iniciar el contenedor con `bin/up -d` y deja que el arranque termine.
* **Código de salida 1**, y el registro muestra `*** /etc/my_init.d/<script> failed with status <n>`: ese script falló, y su error aparece en las líneas inmediatamente anteriores. Si `910_initiate_doc_version_recovery` falló con `Detected unflushed changes while recovering doc versions`, la instancia ejecutó la versión 5.0.1 y todavía tiene ediciones sin volcar; sigue la guía oficial de [recuperación de versiones de documentos](https://docs.overleaf.com/on-premises/release-notes/release-notes-5.x.x/doc-version-recovery).

</Accordion>

<Accordion title="«Restricted, sorry you don’t have permission to load this page»">

Esta página se muestra cuando tu cuenta ha iniciado sesión pero no tiene permiso para abrir la página, por ejemplo, una página de administración abierta por una cuenta que no es administradora o un proyecto que no se ha compartido contigo.

Para abrir las páginas de administración, inicia sesión con una cuenta de administrador. Un administrador existente puede convertir otra cuenta en administradora, o puedes crear una con el comando `create-user --admin`; consulta [Gestión de usuarios](/es/on-premises/user-and-project-management/user-management). En el entorno de desarrollo (`develop/`), las páginas de administración también necesitan `ADMIN_PRIVILEGE_AVAILABLE=true` en `develop/dev.env`; la imagen de Ayakaleaf Pro ya lo establece.

</Accordion>
