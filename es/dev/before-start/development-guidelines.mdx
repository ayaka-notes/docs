### Introducción

Antes de sumergirte en el desarrollo, esperamos que comprendas lo siguiente:

* Overleaf se desarrolla oficialmente en un [repositorio interno](http://github.com/overleaf/internal), y la edición comunitaria se publica en [overleaf/overleaf](https://github.com/overleaf/overleaf). Un copybot se encarga de sincronizar el código entre el repositorio interno y el público.
* [Ayaka-notes/overleaf-pro](https://github.com/ayaka-notes/ayakaleaf-pro) es una versión bifurcada (fork) de Overleaf Community. Queremos que este proyecto sea sostenible a largo plazo, así que sigue estas reglas antes de contribuir.

### Reglas de commits

* No realices modificaciones extensas en el código existente de Overleaf. Concentra tanta funcionalidad como sea posible en la carpeta `services/web/modules`. Así minimizaremos el trabajo al fusionar y actualizar el código más adelante.
* El vibe coding es realmente una forma muy sencilla de trabajar, pero puede desordenar fácilmente nuestro proyecto y hacerlo inmantenible más adelante, así que úsalo con precaución.
* No añadas contenido relacionado con traducciones durante el desarrollo; utiliza las traducciones existentes siempre que sea posible.
* Evita introducir variables de entorno salvo que sea absolutamente necesario. Si son necesarias, asegúrate de que sean lo más coherentes posible con las del Overleaf Toolkit o de [docs.overleaf.com](https://docs.overleaf.com/).

### Reglas de ramas

Usamos las siguientes ramas para el desarrollo de overleaf-pro:

* `main`: esta rama se usa solo para sincronizar el código upstream; **NO** hagas commit de ningún cambio externo. En esta rama crearemos etiquetas como `ce-v[X.x.x]`, que indican que corresponde a `v[X.x.x]` de la Community Edition oficial de Overleaf. Nota: ¡esta etiqueta es inmutable!
* `server-pro`: esta es la rama predeterminada para el desarrollo diario.
* `feature-X`: esta rama se usa para desarrollar una funcionalidad específica.
* `release-vX.0.0`: rama específica para una versión; en ella aplicaremos algunas correcciones urgentes (hot-fix) antes del lanzamiento.

### GitHub Action

[GitHub Action](https://github.com/ayaka-notes/ayakaleaf-pro/actions) se encarga del CI/CD automático. No necesitas compilar imágenes en tu propia máquina: cada una de las imágenes siguientes se compila mediante un workflow, y las que tienen activación manual se pueden compilar con un solo clic.

| Workflow | Activación | Origen | Imagen |
| --- | --- | --- | --- |
| Sync Upstream Code | Diaria, manual | `overleaf/overleaf` → `main` | — |
| Build Development Image | Diaria, manual | `server-pro` | `ghcr.io/ayaka-notes/overleaf-pro/dev:<service>` |
| Build Operations Image | Push / PR a `server-pro`, manual | Commit enviado o head del PR | `ghcr.io/ayaka-notes/overleaf-pro/ops:<YYYYMMDDHHMM>-<sha>`, `ops:latest` |
| Build Release Image | Manual | Rama `release-v*` más reciente | `ghcr.io/ayaka-notes/overleaf-pro:<version>`, `:latest` y `overleaf-pro/git-bridge` |

* Las **imágenes de desarrollo** contienen cada una un microservicio (`web`, `webpack`, `clsi`, ...) para `linux/amd64` y `linux/arm64`. La configuración de Codespace las descarga mediante `develop/docker-compose.image.yml` en lugar de ejecutar `bin/build`.
* Las **imágenes de operaciones** son imágenes completas de un solo contenedor (como `sharelatex/sharelatex`) para probar un cambio de principio a fin. `ops:latest` solo se actualiza con pushes a `server-pro`; un PR solo recibe una etiqueta con marca de tiempo. Estas imágenes se conservan durante 7 días y son solo para pruebas.
* Las **imágenes de versión** son las que despliegan los usuarios. La versión se obtiene del nombre de la rama, así que `release-v6.3.0` publica `overleaf-pro:6.3.0`.

<Steps>
<Step title="Ejecutar un workflow manualmente">
Abre la pestaña [Actions](https://github.com/ayaka-notes/ayakaleaf-pro/actions), elige el workflow a la izquierda, haz clic en **Run workflow** y confirma. Build Operations Image también tiene una opción **Build without cache** para cuando una capa en caché está obsoleta.
</Step>

<Step title="Compilar en tu fork">
Los mismos workflows se ejecutan en un fork: habilita Actions en tu fork y ejecútalos desde su pestaña Actions. Las imágenes se publican en `ghcr.io/<your-name>/overleaf-pro/...` con el `GITHUB_TOKEN` integrado, así que no se necesitan secretos. Sync Upstream Code y la limpieza de imágenes antiguas solo se ejecutan en `ayaka-notes`.

Build Release Image necesita una rama `release-v*` en tu fork.
</Step>
</Steps>

<Info>

Para comprobar a partir de qué commit se compiló una imagen: la etiqueta de una imagen de operaciones termina con el hash corto del commit, y una imagen de versión lo lleva en la etiqueta `com.overleaf.pro.revision` (consulta `docker inspect` en las preguntas y respuestas más abajo).

</Info>

### Preguntas y respuestas

<Accordion title="¿Cómo encontrar el hash del commit de Overleaf Community Edition `X.0.0`?">

En primer lugar, descarga la imagen de Docker y ejecuta el siguiente comando para inspeccionar las etiquetas de esa imagen:

```shellscript title="bash" wrap
docker inspect --format='{{json .Config.Labels}}' sharelatex/sharelatex:6.0.0
{"com.overleaf.ce.revision":"b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f","org.opencontainers.image.ref.name":"ubuntu","org.opencontainers.image.version":"24.04"}
```

Después puedes comprobar si el [commit (b0d05c0)](https://github.com/overleaf/overleaf/commit/b0d05c0cf0750714e1f467d20ed6c5f5e9467e8f) está presente en la rama master upstream.

</Accordion>

<Accordion title="¿Por qué el hash del commit es el mismo en la imagen CE entre `6.0.0` y `6.0.1`?">

Este es el comportamiento esperado. La versión 6.0.1 es un parche menor construido sobre la imagen 6.0.0. Los cambios se aplican parcheando la imagen 6.0.0 existente, en lugar de reconstruir la imagen a partir de un nuevo commit. Por lo tanto, el hash del commit dentro de la imagen es idéntico entre 6.0.0 y 6.0.1.

Para más información, consulta [hotfix](https://github.com/overleaf/overleaf/tree/main/server-ce/hotfix).

</Accordion>
