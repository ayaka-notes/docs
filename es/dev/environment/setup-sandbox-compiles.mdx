title: Configurar compilaciones en sandbox

Las compilaciones en sandbox funcionan un poco distinto en el entorno de desarrollo que en la imagen de producción. El entorno de desarrollo ya las tiene configuradas; esta página explica la configuración y tres cosas que hay que tener en cuenta:

* Problema de permisos de archivos
* Volumen compartido entre history-v1 y filestore
* Problema de subdirectorios

### Habilitar compilaciones en sandbox {#enable-sandbox-compiles}

Las compilaciones en sandbox están activadas por defecto. `develop/docker-compose.yml` establece `SANDBOXED_COMPILES=true` para `clsi`, y `develop/dev.env` contiene el resto:

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

clsi no descarga imágenes por sí mismo, así que descárgalas una vez con `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1` (y `:2025.1`).

LaTeX se ejecuta en los contenedores hermanos como `TEXLIVE_IMAGE_USER`. En el entorno de desarrollo es `tex`, que también es el valor por defecto de clsi (`services/clsi/config/settings.defaults.cjs:154`). La imagen de producción usa `www-data` en su lugar cuando `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` (`server-ce/config/env.sh:15-21`), porque allí los archivos los crea el usuario `www-data` del contenedor de Overleaf.

<Warning>

No uses tu propia imagen compilada; podrías encontrarte con una serie de errores.

</Warning>

### Corregir los permisos de archivos {#fix-file-permissions}

El contenedor de clsi arranca como root, asigna las carpetas `compiles`, `output` y `cache` al usuario `node` (uid `1000`) y luego ejecuta clsi como `node` (`services/clsi/entrypoint.sh`). Por eso `develop/compiles` en el host pertenece al uid `1000`, el mismo uid que `tex` en el entorno de desarrollo (consulta el comentario en `develop/pandoc/Dockerfile`). Con la configuración anterior, el entorno de desarrollo compila sin ningún cambio de permisos.

Si en cambio estableces `TEXLIVE_IMAGE_USER=root`, root (uid `0`) no tiene permiso para escribir en las subcarpetas de `compiles`. En ese caso, da al grupo `root` la propiedad y permiso de escritura sobre `compiles`, con `setgid` activado para que las nuevas subcarpetas hereden esta propiedad:

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

Para obtener documentación detallada, consulta `services/clsi/README.md`.

### Volumen compartido entre history-v1 y filestore {#volume-share-between-history-v1-and-filestore}

<Info>

La configuración de esta sección y de la siguiente ya está en `develop/docker-compose.yml` y `develop/dev.env`. Solo importa con `S3_ENABLED=false` en `develop/dev.rc`. Con el valor por defecto `S3_ENABLED=true`, filestore e history-v1 guardan estos archivos en buckets de RustFS (`develop/s3/docker-compose.yml`).

</Info>

De forma predeterminada, filestore actúa como puente entre S3 y los demás servicios de Overleaf. Sin embargo, en Overleaf CE o Server Pro, todos los archivos se almacenan localmente de forma predeterminada. Por ello, Overleaf introdujo un método muy ingenioso.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

Al mismo tiempo, `data/history` también lo usa el servicio de historial. De este modo, distintos microservicios pueden compartir los mismos datos. Por eso el servicio filestore en develop monta el volumen `history-v1-buckets` de history-v1. Sin él, **clsi no podrá obtener los archivos blob del servicio filestore**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

filestore encuentra los buckets mediante esta configuración en `dev.env`:

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### Usar subdirectorios {#use-subdirectories}

filestore siempre lee los blobs del historial con subdirectorios (`services/filestore/app/js/KeyBuilder.js:58`, `:70`). La imagen de producción activa `useSubdirectories` para history-v1 (`server-ce/config/production.json`), pero la configuración por defecto de history-v1 no, así que en desarrollo history-v1 <strong>aplanaría todos los datos.</strong> Por eso `dev.env` establece `NODE_CONFIG` para history-v1:&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

Sin ello, history-v1 guarda los archivos de `project_blobs` así:

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

Con `useSubdirectories` en `true`, el `_` de estos nombres se convierte en `/`, de modo que cada blob se guarda en subcarpetas.
