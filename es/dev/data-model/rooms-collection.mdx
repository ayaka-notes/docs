`rooms` guarda un documento por sala de chat de un proyecto: el chat del proyecto o un hilo de comentarios de revisión. Solo el servicio chat la escribe, en `services/chat/app/js/Features/Threads/ThreadManager.js`. No hay esquema de Mongoose. Los mensajes de una sala están en la colección [messages](/es/dev/data-model/messages-collection).

#### Campos {#fields}

| Campo | Tipo | Significado | Origen |
| ----- | ---- | ------- | ------ |
| `_id` | ObjectId | Id de la sala. `messages.room_id` apunta aquí. | `ThreadManager.js:57-61` |
| `project_id` | ObjectId | Proyecto al que pertenece la sala. | `ThreadManager.js:43-54` |
| `thread_id` | ObjectId | Solo en hilos de comentarios: el id del comentario, igual que `id` y `op.t` del comentario en `docs.ranges.comments` (consulta [docs](/es/dev/data-model/docs-collection)). No existe en la sala del chat del proyecto. | `ThreadManager.js:38-55`, `services/docstore/app/js/RangeManager.js:54-57` |
| `resolved` | Object | Se establece cuando el hilo se resuelve y se elimina cuando se reabre. Un hilo sin este campo está abierto. | `ThreadManager.js:94-123` |
| `resolved.user_id` | String | Id del usuario que resolvió el hilo. Se guarda como cadena, no como ObjectId: el cuerpo de la solicitud solo se comprueba como id válido, no se convierte. | `ThreadManager.js:103`, `services/chat/app/js/Features/Messages/MessageHttpSchemas.js:70` |
| `resolved.ts` | Date | Cuándo se resolvió el hilo. | `ThreadManager.js:104` |

#### Quién la escribe {#who-writes-it}

| Código | Qué hace |
| ---- | ------------ |
| `ThreadManager.js:31-63` `findOrCreateThread` | Hace un upsert de la sala. Se ejecuta en cada envío, lectura, edición y eliminación de mensajes (`services/chat/app/js/Features/Messages/MessageHttpController.js:183,204,227,236,245,280,301`), así que el primer mensaje de un comentario crea la sala de su hilo, y leer el chat del proyecto crea la sala del chat del proyecto. |
| `ThreadManager.js:94-109` `resolveThread` | Establece `resolved`. Lo llaman desde web el módulo track-changes (`services/web/modules/track-changes/app/src/TrackChangesController.mjs:142`), la restauración del historial (`services/web/app/src/Features/History/RestoreManager.mjs:276`) y el módulo mcp-server (`services/web/modules/mcp-server/app/src/CommentTools.mjs:159`). |
| `ThreadManager.js:111-123` `reopenThread` | Elimina `resolved`. Mismos llamadores: `TrackChangesController.mjs:160`, `RestoreManager.mjs:285`, `CommentTools.mjs:183`. |
| `ThreadManager.js:154-172` `duplicateThread` | Inserta una sala nueva con un `thread_id` nuevo, copiando `resolved`. Se usa cuando un doc se restaura desde el historial (`RestoreManager.mjs:233`). |
| `ThreadManager.js:12-29` `cloneThreads` | Copia cada sala de hilo de un proyecto a otro proyecto, con un `_id` nuevo y el mismo `thread_id`. Se usa cuando un proyecto se copia con sus rangos (`services/web/app/src/Features/Project/ProjectDuplicator.mjs:197`). |
| `ThreadManager.js:125-131` `deleteThread` | Elimina una sala de hilo; luego el controlador elimina sus mensajes (`MessageHttpController.js:167-175`). Lo llama el módulo track-changes (`TrackChangesController.mjs:173`). |

#### Notas {#notes}

* Un proyecto tiene como máximo una sala sin `thread_id`: el chat del proyecto. El servicio chat la encuentra con `thread_id: { $exists: false }` (`ThreadManager.js:38-45`).
* El estado resuelto de un comentario solo existe aquí. Docstore quita `op.resolved` antes de guardar los rangos (`services/docstore/app/js/RangeManager.js:59-61`).
* Después de copiar un proyecto, el mismo `thread_id` existe en dos proyectos. Consulta siempre por `project_id` y `thread_id` juntos, como hace el servicio chat.
* Las salas de un proyecto eliminado se mantienen hasta que caduca el proyecto eliminado.
