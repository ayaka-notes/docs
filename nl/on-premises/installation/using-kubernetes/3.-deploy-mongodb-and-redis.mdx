Ayakaleaf Pro heeft het volgende nodig:

* **MongoDB 8** als **replicaset** (het gebruikt transacties). Drie leden verdeeld over drie nodes overleven het uitvallen van een node; één lid werkt ook.
* **Redis 7**, één server met AOF-persistentie. Redis bevat de bewerkingen die nog niet naar MongoDB zijn geschreven, de sessies en de berichten tussen Overleaf-services. Overleaf maakt verbinding met één Redis-server: Sentinel en Redis Cluster worden niet ondersteund.

<Info>

Je kunt in plaats daarvan beheerde diensten gebruiken, zoals MongoDB Atlas of de Redis van je cloud. Sla deze pagina over en stel `OVERLEAF_MONGO_URL` en `OVERLEAF_REDIS_HOST` daarop in bij [stap 4](/nl/on-premises/installation/using-kubernetes/4.-personalizing-your-instance).

</Info>

<Steps>
<Step title="MongoDB">
```yaml title="10-mongo.yaml" wrap
apiVersion: v1
kind: Service
metadata:
  name: mongo
  namespace: overleaf
spec:
  clusterIP: None                 # headless: gives mongo-0.mongo, mongo-1.mongo, ...
  publishNotReadyAddresses: true  # members must resolve each other before the set is initiated
  selector:
    app: mongo
  ports:
    - name: mongo
      port: 27017
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mongo
  namespace: overleaf
spec:
  serviceName: mongo
  replicas: 3
  selector:
    matchLabels:
      app: mongo
  template:
    metadata:
      labels:
        app: mongo
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app: mongo
              topologyKey: kubernetes.io/hostname
      containers:
        - name: mongo
          image: mongo:8.0
          args:
            - --replSet=overleaf
            - --bind_ip_all
            - --wiredTigerCacheSizeGB=0.25   # default is 50% of (RAM - 1 GB); size it for your nodes
          # env:
          #   - name: GLIBC_TUNABLES        # only on kernel 6.19+ (SERVER-121912)
          #     value: glibc.pthread.rseq=1
          ports:
            - containerPort: 27017
          readinessProbe:
            tcpSocket:
              port: 27017
          resources:
            requests:
              cpu: 100m
              memory: 384Mi
            limits:
              memory: 768Mi
          volumeMounts:
            - name: data
              mountPath: /data/db
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 5Gi
---
# Initiates the replica set once. Safe to re-run: it does nothing when the set exists.
apiVersion: batch/v1
kind: Job
metadata:
  name: mongo-init-replica-set
  namespace: overleaf
spec:
  backoffLimit: 20
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: init
          image: mongo:8.0
          command:
            - mongosh
            - --quiet
            - --host=mongo-0.mongo
            - --eval
            - |
              try {
                rs.status()
                print('replica set already initiated')
              } catch (e) {
                rs.initiate({
                  _id: 'overleaf',
                  members: [
                    { _id: 0, host: 'mongo-0.mongo.overleaf.svc.cluster.local:27017' },
                    { _id: 1, host: 'mongo-1.mongo.overleaf.svc.cluster.local:27017' },
                    { _id: 2, host: 'mongo-2.mongo.overleaf.svc.cluster.local:27017' },
                  ],
                })
              }
```

```bash
kubectl apply -f 10-mongo.yaml
kubectl -n overleaf rollout status statefulset/mongo
kubectl -n overleaf wait --for=condition=complete job/mongo-init-replica-set --timeout=5m
kubectl -n overleaf exec mongo-0 -- mongosh --quiet --eval 'rs.status().members.map(m => m.name + " " + m.stateStr)'
```

Na enkele seconden zou één lid `PRIMARY` moeten zijn en de andere `SECONDARY`. De Job probeert het opnieuw totdat alle leden antwoorden, dus een paar mislukte Job-pods zijn normaal.

* De headless Service heeft `publishNotReadyAddresses: true` nodig: de leden moeten elkaar op naam kunnen vinden voordat de replicaset bestaat.
* De leden worden toegevoegd met hun stabiele namen (`mongo-0.mongo.overleaf.svc.cluster.local`), nooit met pod-IP's, die bij elke herstart veranderen.
* Voor één lid stel je `replicas: 1` in en houd je alleen `mongo-0` in de Job.
</Step>

<Step title="Redis">
```yaml title="20-redis.yaml" wrap
apiVersion: v1
kind: Service
metadata:
  name: redis
  namespace: overleaf
spec:
  selector:
    app: redis
  ports:
    - name: redis
      port: 6379
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
  namespace: overleaf
spec:
  serviceName: redis
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis
          image: redis:7.4
          args: [--appendonly, "yes"]
          ports:
            - containerPort: 6379
          readinessProbe:
            tcpSocket:
              port: 6379
          resources:
            requests:
              cpu: 50m
              memory: 128Mi
            limits:
              memory: 512Mi
          volumeMounts:
            - name: data
              mountPath: /data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 2Gi
```

```bash
kubectl apply -f 20-redis.yaml
kubectl -n overleaf rollout status statefulset/redis
```
</Step>

### Q\&A

<Accordion title="MongoDB 8 crasht bij het opstarten op een recente kernel. Waarom?">

<strong>Antwoord:</strong> MongoDB 8 faalt op Linux-kernel 6.19 en later ([SERVER-121912](https://jira.mongodb.org/browse/SERVER-121912)). Haal het commentaarteken weg bij de omgevingsvariabele `GLIBC_TUNABLES` in `10-mongo.yaml`.

</Accordion>

<Accordion title="Hoeveel geheugen heeft MongoDB nodig?">

<strong>Antwoord:</strong> Standaard gebruikt MongoDB de helft van het geheugen van de node min 1 GB voor zijn cache, en het ziet het geheugen van de node, niet de limiet van de pod. Stel `--wiredTigerCacheSizeGB` in op basis van je nodes; met `0.25` bleef elk lid op ongeveer 200 tot 260 MiB op onze testnodes van 4 GB.

</Accordion>
