Sandbox-compilaties werken in de ontwikkelomgeving iets anders dan in de productie-image. De ontwikkelomgeving heeft ze al ingesteld; deze pagina legt de instellingen uit en drie dingen om op te letten:

* Probleem met bestandsrechten
* Gedeeld volume tussen history-v1 en filestore
* Probleem met submappen

### Sandbox-compilaties inschakelen {#enable-sandbox-compiles}

Sandbox-compilaties staan standaard aan. `develop/docker-compose.yml` zet `SANDBOXED_COMPILES=true` voor `clsi`, en `develop/dev.env` bevat de rest:

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

clsi haalt zelf geen images op, dus haal de images één keer op met `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1` (en `:2025.1`).

LaTeX draait in de zustercontainers als `TEXLIVE_IMAGE_USER`. In de ontwikkelomgeving is dat `tex`, wat ook de standaard van clsi is (`services/clsi/config/settings.defaults.cjs:154`). De productie-image gebruikt in plaats daarvan `www-data` wanneer `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` (`server-ce/config/env.sh:15-21`), omdat de bestanden daar worden aangemaakt door de gebruiker `www-data` van de Overleaf-container.

<Warning>

Gebruik niet uw zelfgebouwde image, anders kunt u op een reeks fouten stuiten.

</Warning>

### Bestandsrechten herstellen {#fix-file-permissions}

De clsi-container start als root, geeft de mappen `compiles`, `output` en `cache` aan de gebruiker `node` (uid `1000`) en voert clsi daarna uit als `node` (`services/clsi/entrypoint.sh`). Daardoor is `develop/compiles` op de host van uid `1000`, dezelfde uid als `tex` in de ontwikkelomgeving (zie de opmerking in `develop/pandoc/Dockerfile`). Met de bovenstaande instellingen compileert de ontwikkelomgeving zonder enige wijziging van rechten.

Als je in plaats daarvan `TEXLIVE_IMAGE_USER=root` instelt, heeft root (uid `0`) geen recht om naar de submappen van `compiles` te schrijven. Geef in dat geval de groep `root` eigendom en schrijfrechten op `compiles`, met `setgid` ingesteld zodat nieuwe submappen dit eigendom erven:

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

Uitgebreide documentatie vindt u in `services/clsi/README.md`.

### Gedeeld volume tussen history-v1 en filestore {#volume-share-between-history-v1-and-filestore}

<Info>

De instellingen in deze en de volgende sectie staan al in `develop/docker-compose.yml` en `develop/dev.env`. Ze zijn alleen van belang met `S3_ENABLED=false` in `develop/dev.rc`. Met de standaardwaarde `S3_ENABLED=true` bewaren filestore en history-v1 deze bestanden in plaats daarvan in RustFS-buckets (`develop/s3/docker-compose.yml`).

</Info>

Standaard fungeert filestore als brug tussen S3 en andere services in Overleaf. In Overleaf CE of Server Pro worden alle bestanden echter standaard lokaal opgeslagen. Daarom heeft Overleaf een zeer slimme methode geïntroduceerd.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

Tegelijkertijd wordt `data/history` ook door de history-service gebruikt. Zo kunnen verschillende microservices dezelfde gegevens delen. Daarom koppelt de filestore-service in develop het volume `history-v1-buckets` van history-v1. Zonder dit volume **kan clsi geen blobbestanden ophalen bij de filestore-service**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

filestore vindt de buckets via deze instellingen in `dev.env`:

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### Submappen gebruiken {#use-subdirectories}

filestore leest history-blobs altijd met submappen (`services/filestore/app/js/KeyBuilder.js:58`, `:70`). De productie-image zet `useSubdirectories` aan voor history-v1 (`server-ce/config/production.json`), maar de standaardconfiguratie van history-v1 niet, dus in ontwikkeling zou history-v1 <strong>alle gegevens plat opslaan.</strong> Daarom zet `dev.env` `NODE_CONFIG` voor history-v1:&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

Zonder deze instelling slaat history-v1 de `project_blobs`-bestanden zo op:

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

Met `useSubdirectories` op `true` wordt de `_` in deze namen een `/`, zodat elke blob in submappen wordt opgeslagen.
