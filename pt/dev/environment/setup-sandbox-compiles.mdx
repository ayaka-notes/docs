As compilações em sandbox funcionam um pouco diferente no ambiente de desenvolvimento do que na imagem de produção. O ambiente de desenvolvimento já as tem configuradas; esta página explica as configurações e três pontos a ter em mente:

* Problema de permissões de arquivos
* Compartilhamento de volume entre history-v1 e filestore
* Problema de subdiretórios

### Habilitar o Sandbox Compiles {#enable-sandbox-compiles}

As compilações em sandbox vêm ativadas por padrão. `develop/docker-compose.yml` define `SANDBOXED_COMPILES=true` para o `clsi`, e `develop/dev.env` contém o restante:

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

O clsi não baixa imagens sozinho, então baixe as imagens uma vez com `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1` (e `:2025.1`).

O LaTeX roda nos contêineres irmãos como `TEXLIVE_IMAGE_USER`. No ambiente de desenvolvimento, esse usuário é `tex`, que também é o padrão do clsi (`services/clsi/config/settings.defaults.cjs:154`). A imagem de produção usa `www-data` quando `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` (`server-ce/config/env.sh:15-21`), porque lá os arquivos são criados pelo usuário `www-data` do contêiner do Overleaf.

<Warning>

Não use uma imagem construída por você mesmo, pois você pode encontrar uma série de erros.

</Warning>

### Corrigir permissões de arquivos {#fix-file-permissions}

O contêiner do clsi inicia como root, entrega as pastas `compiles`, `output` e `cache` ao usuário `node` (uid `1000`) e então executa o clsi como `node` (`services/clsi/entrypoint.sh`). Assim, `develop/compiles` no host pertence ao uid `1000`, o mesmo uid de `tex` no ambiente de desenvolvimento (veja o comentário em `develop/pandoc/Dockerfile`). Com as configurações acima, o ambiente de desenvolvimento compila sem nenhuma alteração de permissão.

Se, em vez disso, você definir `TEXLIVE_IMAGE_USER=root`, o root (uid `0`) não tem permissão para escrever nas subpastas de `compiles`. Nesse caso, dê ao grupo `root` a propriedade e permissão de escrita em `compiles`, com `setgid` definido para que as novas subpastas herdem essa propriedade:

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

Para a documentação detalhada, consulte `services/clsi/README.md`.

### Compartilhamento de volume entre history-v1 e filestore {#volume-share-between-history-v1-and-filestore}

<Info>

As configurações desta seção e da próxima já estão em `develop/docker-compose.yml` e `develop/dev.env`. Elas só importam com `S3_ENABLED=false` em `develop/dev.rc`. Com o padrão `S3_ENABLED=true`, o filestore e o history-v1 guardam esses arquivos em buckets do RustFS (`develop/s3/docker-compose.yml`).

</Info>

Por padrão, o filestore atua como uma ponte entre o S3 e os outros serviços do Overleaf. No entanto, no Overleaf CE ou no Server Pro, todos os arquivos são armazenados localmente por padrão. Por isso, o Overleaf introduziu um método bastante engenhoso.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

Ao mesmo tempo, `data/history` também é usado pelo serviço de histórico. Dessa forma, microsserviços diferentes podem compartilhar os mesmos dados. Por isso o serviço filestore em develop monta o volume `history-v1-buckets` do history-v1. Sem ele, **o clsi não conseguirá obter arquivos blob do serviço filestore**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

O filestore encontra os buckets por meio destas configurações em `dev.env`:

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### Usar subdiretórios {#use-subdirectories}

O filestore sempre lê os blobs do histórico com subdiretórios (`services/filestore/app/js/KeyBuilder.js:58`, `:70`). A imagem de produção ativa `useSubdirectories` para o history-v1 (`server-ce/config/production.json`), mas a configuração padrão do history-v1 não, então em desenvolvimento o history-v1 <strong>achataria todos os dados.</strong> Por isso o `dev.env` define `NODE_CONFIG` para o history-v1:&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

Sem isso, o history-v1 armazena os arquivos de `project_blobs` assim:

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

Com `useSubdirectories` definido como `true`, o `_` nesses nomes vira `/`, então cada blob é armazenado em subpastas.
