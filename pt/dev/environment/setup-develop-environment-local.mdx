## Pré-requisitos {#prerequisites}

O Overleaf é um projeto de código aberto típico com arquitetura de microsserviços, com todos os serviços executados no Docker.&#x20;

* O código-fonte oficial da Community Edition está em [GitHub Overleaf Official](https://github.com/overleaf/overleaf/tree).&#x20;
* O código-fonte do Overleaf-CEP está disponível em [GitHub Yu-i-i/Overleaf](https://github.com/yu-i-i/overleaf-cep).
* O Ayakaleaf Pro está disponível no [GitHub ayaka-notes/ayakaleaf-pro](https://github.com/ayaka-notes/ayakaleaf-pro).

Para configurar um ambiente de desenvolvimento do Overleaf, você precisará de um servidor potente; recomenda-se uma configuração de pelo menos 8 núcleos e 16 GB de RAM, pois será necessário executar mais de 20 contêineres simultaneamente.

<Info>

Como servidores com 8 ou mais núcleos de CPU costumam ser caros, recomendamos fortemente usar seu computador local para o desenvolvimento.

</Info>

Além disso, como desenvolvedor, acreditamos que você já esteja familiarizado com a [instalação do Docker](https://docs.docker.com/engine/install/ubuntu/). Sugerimos fortemente usar uma versão LTS recente e estável do Ubuntu (por exemplo, Ubuntu 24.04 em 2025–2026) e a versão mais recente do Docker para desenvolvimento, pois isso reduz a possibilidade de encontrar erros inesperados.

Em resumo, você precisará de:

* [x] Um servidor/desktop potente para desenvolver
* [x] Uma versão LTS recente e estável do Ubuntu (por exemplo, Ubuntu 24.04)
* [x] Ambiente com Docker e Git

## Tutorial de configuração {#configuration-tutorial}

Aqui, usamos o Ayakaleaf Pro para mostrar como configurar um ambiente de desenvolvimento do Overleaf. Todos os comandos abaixo são executados no diretório `develop`, salvo indicação em contrário.

<Steps>
<Step title="Obter o código-fonte">
Primeiro, vamos clonar o repositório:

```bash title="bash"
git clone https://github.com/ayaka-notes/ayakaleaf-pro.git
cd ayakaleaf-pro/develop
```
</Step>

<Step title="Sincronizar o `yarn.lock`">
O repositório usa Yarn 4 (`packageManager` no `package.json` raiz), e o seu `yarn.lock` pode ficar fora de sincronia com os arquivos `package.json`. Sincronize-o após o primeiro clone e após qualquer alteração em um `package.json`:

```bash title="bash"
bin/sync
```

`bin/sync` executa `yarn install --mode=update-lockfile` em um contêiner `node:24.18.1`, então você não precisa de Node.js no host. Não faça commit do `yarn.lock` alterado.
</Step>

<Step title="Construir a imagem de desenvolvimento">
Construa os serviços:

```bash title="bash"
bin/build
```

<Info>

Se o Docker ficar sem RAM ao construir os serviços em paralelo, crie um arquivo `.env` neste diretório contendo `COMPOSE_PARALLEL_LIMIT=1`.

</Info>
</Step>

<Step title="Aplicar as traduções">
Os módulos do Ayakaleaf Pro guardam suas traduções em `services/web/locales/locales_patches/`, que os arquivos de locales commitados não contêm. Aplique-as uma vez antes da primeira inicialização, ou as páginas desses módulos mostrarão chaves como `about_to_permanently_delete_accounts` em vez de texto:

```bash title="bash"
bin/i18n
```

Ele precisa de `jq` no host. Execute-o novamente depois de adicionar uma tradução ou trocar de branch, veja [Atualizar traduções i18n](/pt/dev/environment/update-i18n-translations).
</Step>

<Step title="Iniciar todos os microsserviços">
Em seguida, inicie os serviços:

```bash title="bash"
bin/up
```

Quando os serviços estiverem em execução, abra [http://localhost/launchpad](http://localhost/launchpad) para criar a primeira conta de administrador. Adicione a porta se você alterou `OVERLEAF_PORT` (veja abaixo).

<Info>

O LDAP vem ativado por padrão (`LDAP_ENABLED=true` em `dev.rc`). O launchpad então mostra o formulário de administrador LDAP: ele pede apenas um e-mail, e esse administrador faz login depois pelo LDAP, por exemplo como `professor` / `professor` (`professor@planetexpress.com`). Os usuários de teste estão listados em `develop/authentication/README.md`. Defina `LDAP_ENABLED=false` e `SAML_ENABLED=false` para criar um administrador local com senha.

</Info>
</Step>
</Steps>

<Info>

`develop/dev.env` já define `ADMIN_PRIVILEGE_AVAILABLE=true`, então os administradores podem abrir o painel de administração sem configuração extra.

</Info>

### Configuração (`dev.rc`) {#configuration-dev-rc}

`develop/dev.rc`, ao lado de `dev.env`, contém as chaves do ambiente de desenvolvimento, como o `overleaf.rc` no Overleaf Toolkit. Altere um valor e execute `bin/dev` novamente para aplicá-lo; um recurso desativado também para seus contêineres.

| Variável | Padrão | O que faz |
| --- | --- | --- |
| `OVERLEAF_PORT` | `80` | Porta do host para o site. |
| `LDAP_ENABLED` | `true` | Login LDAP com usuários de teste. |
| `SAML_ENABLED` | `true` | Login SAML com usuários de teste. |
| `MAILPIT_ENABLED` | `true` | Captura no Mailpit todo e-mail do `web`. Também ativa a confirmação de e-mail (`EMAIL_CONFIRMATION_DISABLED=false`). |
| `S3_ENABLED` | `true` | Guarda os arquivos de histórico e de templates no RustFS (S3) em vez de volumes locais. |
| `HOPPSCOTCH_ENABLED` | `true` | Hoppscotch com um proxy para a rede do Docker, veja [Configurar ferramentas de desenvolvimento](/pt/dev/environment/setup-develop-tools). |
| `HOPPSCOTCH_PORT` | `9170` | Porta do host para o Hoppscotch. |
| `GRAFANA_ENABLED` | `true` | Grafana em `/grafana/` do site, com o estado, as métricas e os logs de cada serviço, veja [Configurar ferramentas de desenvolvimento](/pt/dev/environment/setup-develop-tools). |

Cada recurso mantém seu `docker-compose.yml` e outros arquivos em uma pasta própria: `authentication/ldap`, `authentication/saml`, `mail`, `s3`, `hoppscotch` e `grafana`. Um recurso que precisa de uma configuração do `web` sem variável de ambiente monta um arquivo em `/etc/overleaf/settings.d/`, e `develop/settings.dev-env.cjs` mescla todos eles. Todos os scripts `bin/*` passam por `bin/docker-compose`, que adiciona os arquivos dos recursos ativados. Use `bin/docker-compose` em vez de `docker compose` quando precisar de um comando compose.

<Warning>

Os volumes locais e o RustFS são armazenamentos separados: um projeto criado com `S3_ENABLED=true` não tem histórico nem arquivos binários depois de mudar para `false`, e vice-versa. Para copiar para o RustFS os arquivos de um ambiente que rodava antes de `S3_ENABLED` existir, siga “Moving existing data into RustFS” em [develop/README.md](https://github.com/ayaka-notes/ayakaleaf-pro/blob/server-pro/develop/README.md).

</Warning>

### Portas {#ports}

O site, o console do RustFS e o Hoppscotch escutam em `127.0.0.1` do host; em uma máquina remota, encaminhe primeiro as portas, por exemplo `ssh -L 9001:localhost:9001 <host>`. O site usa `OVERLEAF_PORT` do `dev.rc`, então adicione a porta aos endereços abaixo se você a alterou.

| Página | Endereço | Login |
| --- | --- | --- |
| Site | [http://localhost](http://localhost) | As contas do site ou os usuários de teste |
| Caixa de entrada (Mailpit) | [http://localhost/mailpit/](http://localhost/mailpit/) | Nenhum |
| Grafana | [http://localhost/grafana/](http://localhost/grafana/) | Nenhum, usuários anônimos são administradores |
| Mongo Express | [http://localhost/mongo-express/](http://localhost/mongo-express/) | Nenhum |
| RedisInsight | [http://localhost/redis-insight/](http://localhost/redis-insight/) | Nenhum |
| Console S3 (RustFS) | [http://localhost:9001/rustfs/console/](http://localhost:9001/rustfs/console/) | `rustfsadmin` / `rustfsadmin` |
| Hoppscotch | [http://localhost:9170](http://localhost:9170) (`HOPPSCOTCH_PORT`) | Nenhum |

Mailpit, Grafana, Mongo Express e RedisInsight são servidos pelo site em seus próprios caminhos, por meio do webpack-dev-server, então não precisam de porta própria. Depois do login, o menu **Dev tools** na barra de navegação do site aponta para eles; uma página cujo recurso está desativado no `dev.rc` fica de fora. [Configurar ferramentas de desenvolvimento](/pt/dev/environment/setup-develop-tools) mostra o que cada um faz.

A API do S3 (porta 9000) e o SMTP (porta 1025) só são acessíveis dentro da rede do Docker. Mongo (27017), Redis (6379), Mongo Express (8081), RedisInsight (5540) e git-bridge (8000) são publicados apenas em `127.0.0.1` do host.

### TeX Live {#tex-live}

As compilações em sandbox vêm ativadas por padrão: `develop/dev.env` define `SANDBOXED_COMPILES=true` e as imagens `ghcr.io/ayaka-notes/texlive-full:2026.1` e `ghcr.io/ayaka-notes/texlive-full:2025.1`. O clsi não baixa imagens sozinho, então baixe-as uma vez:

```bash
docker pull ghcr.io/ayaka-notes/texlive-full:2026.1
docker pull ghcr.io/ayaka-notes/texlive-full:2025.1
```

Veja [Configurar Sandbox Compiles](/pt/dev/environment/setup-sandbox-compiles) para os detalhes.

<Warning>

Um projeto criado enquanto `SANDBOXED_COMPILES` estava desativado não tem imagem do TeX Live. Ele ainda compila com a imagem padrão, mas pular entre o código e o PDF falha com “That didn't work. Recompile and try again.” Atribua uma vez a esses projetos a imagem de `TEX_LIVE_DOCKER_IMAGE`; sem `--commit`, o script só mostra o que mudaria:

```bash
bin/docker-compose exec web sh -c 'cd /overleaf/services/web && node scripts/backfill_project_image_name.mjs --commit'
```

</Warning>

O `dev.env` também ativa as conversões do Pandoc com `PANDOC_IMAGE=overleaf-pandoc:local`. Construa essa imagem uma vez, a partir da raiz do repositório:

```bash
docker build -t overleaf-pandoc:local develop/pandoc
```

Para compilar em um host macOS, talvez seja necessário substituir o caminho do socket do Docker criando um arquivo `.env` no diretório `develop` com `DOCKER_SOCKET_PATH=/var/run/docker.sock.raw`

### Desenvolvimento {#development}

Para evitar executar `bin/build && bin/up` após cada alteração no código, você pode executar o Overleaf Community Edition em _modo de desenvolvimento_, no qual os serviços são atualizados automaticamente quando o código muda.

Para isso, use o script incluído `bin/dev`:

```text
bin/dev
```

Isso iniciará todos os serviços usando `node --watch`, que monitora automaticamente o código e reinicia os serviços conforme necessário. Execute-o novamente depois de alterar o `dev.rc`.

Para melhorar o desempenho, você pode iniciar apenas um subconjunto dos serviços em modo de desenvolvimento, fornecendo uma lista separada por espaços ao script `bin/dev`:

```text
bin/dev [service1] [service2] ... [serviceN]
```

<Info>

Iniciar o serviço `web` em _modo de desenvolvimento_ só atualizará o serviço `web` quando o código de backend mudar. Para atualizar automaticamente também o código de frontend, certifique-se de iniciar também o serviço `webpack` em _modo de desenvolvimento_.

</Info>

Se nenhum serviço for informado, todos os serviços serão iniciados em modo de desenvolvimento.

Depois de adicionar uma tradução ou trocar de branch, execute `bin/i18n`, veja [Atualizar traduções i18n](/pt/dev/environment/update-i18n-translations).

### Depuração {#debugging}

No _modo de desenvolvimento_, a maioria dos serviços expõe uma porta de depuração à qual você pode conectar um depurador, como o inspetor do Dev Tools do Chrome ou um integrado a uma IDE. A tabela a seguir mostra a porta exposta em `127.0.0.1` da **máquina host** para cada serviço:

| Serviço            | Porta |
| ------------------ | ---- |
| `web`                   | 9229 |
| `clsi`                  | 9230 |
| `chat`                  | 9231 |
| `docstore`              | 9233 |
| `document-updater`      | 9234 |
| `filestore`             | 9235 |
| `notifications`         | 9236 |
| `real-time`             | 9237 |
| `history-v1`            | 9239 |
| `project-history`       | 9240 |
| `linked-url-proxy`      | 9241 |
| `third-party-datastore` | 9242 |

Para se conectar a um serviço usando a _depuração remota_ do Chrome, acesse chrome://inspect/ e certifique-se de que _Discover network targets_ esteja marcado. Em seguida, clique em _Configure..._ e adicione uma entrada `localhost:[service port]` para cada serviço ao qual deseja conectar um depurador.

Depois de adicionar uma entrada, o serviço aparecerá como um _Remote Target_ que você pode inspecionar e depurar.

### Logs {#logging}

O script `bin/logs` acompanha os logs e os formata com `bunyan`. Ele também precisa de `ggrep`, que é o nome do GNU grep quando instalado com Homebrew no macOS; o Ubuntu não tem o comando `ggrep`.

```bash
sudo npm install -g bunyan
# Or sudo apt install node-bunyan 
```

Ou você pode executar diretamente:

```text
bin/docker-compose logs -f [service name]
```

Use `bin/docker-compose` em vez de `docker compose`, para que os serviços dos recursos do `dev.rc` (`mailpit`, `rustfs`, `ldap`, `saml`, `hoppscotch` e `grafana` com Prometheus, Loki e os exporters) também sejam encontrados.

Com `GRAFANA_ENABLED=true`, os logs de todos os contêineres também ficam no Grafana, onde podem ser filtrados por serviço, nível e texto, veja [Configurar ferramentas de desenvolvimento](/pt/dev/environment/setup-develop-tools#grafana).
