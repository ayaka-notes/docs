---
title: Coleção OAuth Applications
icon: id-badge
---

`oauthApplications` contém os clientes OAuth que o web conhece. Um documento é um cliente. No Ayakaleaf Pro, o único que escreve nela é o módulo web `git-bridge`, que cria um cliente chamado `Overleaf Git Bridge` quando o web inicia. O esquema é `services/web/app/src/models/OauthApplication.mjs`.

#### Campos {#fields}

| Campo | Tipo | Significado | Origem |
| ----- | ---- | ------- | ------ |
| `_id` | ObjectId | Id do documento do cliente. `oauthAccessTokens.oauthApplication_id` e `oauthAuthorizationCodes.oauthApplication_id` apontam para ele. | `OauthApplication.mjs:5` |
| `id` | String | Id do cliente: 64 letras minúsculas e dígitos aleatórios. | `OauthApplication.mjs:7`, `services/web/modules/git-bridge/index.mjs:25` |
| `clientSecret` | String | Segredo do cliente, gravado como `v1.` mais 32 caracteres aleatórios. Só `getClient` o lê, e nada chama `getClient` (veja Notas). | `OauthApplication.mjs:8`, `git-bridge/index.mjs:26` |
| `grants` | Array of String | Tipos de grant. O cliente do git-bridge tem `['password']`. Devolvido com o cliente quando um token é verificado (`services/web/modules/oauth2-server/app/src/OAuth2Model.mjs:67-72`). | `OauthApplication.mjs:9`, `git-bridge/index.mjs:27` |
| `name` | String | Nome do cliente. O módulo git-bridge e o código de tokens de acesso pessoal encontram o cliente pelo nome `Overleaf Git Bridge`. | `OauthApplication.mjs:10`, `git-bridge/index.mjs:15-16,28` |
| `redirectUris` | Array of String | URIs de redirecionamento permitidas. `[]` para o cliente do git-bridge. | `OauthApplication.mjs:11`, `git-bridge/index.mjs:29` |
| `scopes` | Array of String | Scopes que o cliente pode usar. `['git_bridge']` para o cliente do git-bridge. | `OauthApplication.mjs:12`, `git-bridge/index.mjs:30` |
| `pkceEnabled` | Boolean | Apenas no esquema: nenhum código deste repositório o grava, e só o `getClient`, que não é usado, o lê (`OAuth2Model.mjs:207`). | `OauthApplication.mjs:13` |

#### Quem escreve {#who-writes-it}

| Código | O que faz |
| ---- | ------------ |
| `git-bridge/index.mjs:9-35` (module `git-bridge`) | Quando `GIT_BRIDGE_ENABLED` é `true`, cria o cliente `Overleaf Git Bridge` na inicialização do web se não existir nenhum cliente com esse nome. |

#### Quem lê {#who-reads-it}

| Código | O que faz |
| ---- | ------------ |
| `services/web/modules/oauth2-server/app/src/OAuthPersonalAccessTokenManager.mjs:53-61` (module `oauth2-server`) | Encontra o cliente `Overleaf Git Bridge` pelo nome e guarda o seu `_id` em cada novo token de acesso pessoal. Sem o cliente, nenhum token é criado. |
| `OAuth2Model.mjs:31-39,67-72` (`getAccessToken`) | Carrega o cliente de um token por `oauthApplication_id` e devolve o seu `id` e `grants`. |
| `OAuth2Model.mjs:185-209,241,275` (`getClient`, `saveToken`, `saveAuthorizationCode`) | Procuram clientes por `id`. Nunca alcançados neste repositório, veja Notas. |

#### Índices {#indexes}

Apenas o índice padrão de `_id`. O índice único `id_1` vem de migrações marcadas `saas` (`20190912145016_create_oauthApplications_indexes.mjs`) e `server-pro` (`20230502180757_server_pro_oauth_indexes.mjs`), que o Community Edition não executa.

#### Notas {#notes}

* O web usa `@node-oauth/oauth2-server` apenas para verificar tokens bearer (`server.authenticate` em `services/web/app/src/Features/Authentication/AuthenticationController.mjs:409-450`), o que chama apenas `getAccessToken` e `verifyScope` do modelo. Nenhuma rota serve `/oauth/token` ou `/oauth/authorize`, por isso `getClient`, `saveToken` e `saveAuthorizationCode` nunca são chamados.
* O módulo procura o cliente pelo nome e depois cria-o, e o Community Edition não tem índice único em `name` ou `id`. Assim, nada impede um segundo cliente com o mesmo nome. O código que precisa do cliente usa aquele que `findOne` devolver.
