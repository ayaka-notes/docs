<Accordion title="Executar o Overleaf com um sistema de arquivos NFS">

Montar um sistema de arquivos NFS em um contêiner do Overleaf é tecnicamente possível, mas não é recomendado e pode resultar em diferentes tipos de erros de desempenho.

Um erro comum observado nas compilações é:

```text
EBUSY: resource busy or locked, unlink '/var/lib/overleaf/data/compiles/62f3d57bef7cf9005c364e75-62f3d57bef7cf9005c364e7a/.nfs573663533034825247625441'
```

Em particular, desaconselhamos o uso de sistemas de arquivos baseados em NFS para dados efêmeros, como os diretórios usados para dados de compilação. Recomendamos usar um disco temporário local, de preferência um SSD local, para os diretórios a seguir.

Em configurações baseadas em `docker-compose`, sugerimos simplesmente substituir o bind-mount do NFS, o que evita alterar caminhos na aplicação. Aqui está um trecho de exemplo de configuração do `docker-compose` usando um disco temporário montado em `/scratch`:

```yaml title="docker-compose excerpt"
services:
  sharelatex:
    environment:
      SANDBOXED_COMPILES_HOST_DIR: /scratch/compiles/
    volumes:
      - nfs:/var/lib/overleaf/data
      - /scratch/cache/:/var/lib/overleaf/data/cache
      - /scratch/compiles/:/var/lib/overleaf/data/compiles
      - /scratch/output/:/var/lib/overleaf/data/output
      - /scratch/tmp/:/var/lib/overleaf/tmp
```

Não é necessário migrar nenhum arquivo existente do NFS para o novo local após a atualização. O compilador LaTeX pode recriar todos os arquivos com uma nova compilação completa.

Para mais detalhes, consulte: https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-with-an-nfs-filesystem

</Accordion>

<Accordion title="Executar o Overleaf no Windows ou macOS faz com que o serviço `mongo` não inicie">

Se você estiver executando o Overleaf no Windows ou macOS, o serviço `mongo` pode falhar ao reiniciar, com o erro:

```text title="Example error"
Failed to start up WiredTiger under any compatibility version.
Reason: 1: Operation not permitted
```

Para evitar esse erro, os dados precisam ser armazenados em um volume, e não em um diretório montado via bind mount (consulte a documentação da imagem `mongo` para mais detalhes: https://github.com/docker-library/docs/blob/master/mongo/content.md#where-to-store-data). Para armazenar os dados em volumes Docker montados dentro dos contêineres do MongoDB e do Redis, adicione o seguinte ao `config/docker-compose.override.yml` (crie este arquivo se ele ainda não existir):

```yaml title="config/docker-compose.override.yml"
volumes:
  mongo-data:
  redis-data:

services:
  mongo:
    volumes:
      - mongo-data:/data/db

  redis:
    volumes:
      - redis-data:/data
```

Para mais informações, consulte: https://docs.overleaf.com/on-premises/support/troubleshooting#running-overleaf-on-windows-or-macos-results-in-the-mongoservice-not-starting

</Accordion>

<Accordion title="A atualização para o Redis 6.2 resulta em um loop de reinicialização">

Use o comando `docker logs redis` para obter uma cópia dos logs.

Se você vir a linha `Fatal: Can't initialize Background Jobs`, a saída completa será semelhante a esta:

```text title="Redis log example"
1:M 11 Feb 2024 15:19:22.609 # Server initialized
1:M 11 Feb 2024 15:19:22.609 # Fatal: Can't initialize Background Jobs.
1:C 11 Feb 2024 15:19:26.055 # oO0OoO0OoO0Oo Redis is starting oO0OoO0OoO0Oo
```

Isso pode estar relacionado à versão do Docker em uso. Atualizar para uma versão >= 20.10.10 deve resolver o problema.

Para mais informações, consulte o issue do Redis upstream: https://github.com/redis/redis/issues/12362

Referência: https://docs.overleaf.com/on-premises/support/troubleshooting#upgrading-to-redis-6.2-results-in-a-restart-loop

</Accordion>

<Accordion title="Orientação incorreta das imagens de pré-visualização/miniatura da galeria de modelos">

Ocasionalmente, as imagens de pré-visualização/miniatura geradas pelo Server Pro podem ser criadas na orientação errada e exigir intervenção manual para correção. Essas imagens são armazenadas em `/var/lib/overleaf/data/template_files/` (>= 5.0.3) e `/var/lib/sharelatex/data/template_files/` (versões anteriores).

Recomendamos fazer backup desta pasta antes de fazer qualquer alteração.

Você precisará seguir as etapas abaixo para cada modelo afetado:

Encontre o ID do modeloNavegue até a galeria de modelos da sua instância (/templates/all), abra um modelo afetado e copie o ID da URL (por exemplo: https://your-instance-url/templates/6645d346c224815e9460a695).Execute o comando de correçãoExecute o seguinte comando a partir do host Docker (substitua o ID do modelo pelo que você copiou e atualize o caminho, se necessário):docker exec sharelatex /bin/bash -c "mogrify -rotate 90 /var/lib/overleaf/data/template\_files/6645d346c224815e9460a695\_\*\{thumbnail,preview\}"

Referência: https://docs.overleaf.com/on-premises/support/troubleshooting#incorrect-orientation-of-template-gallery-preview-thumbnail-images

</Accordion>

<Accordion title="Verifique se você habilitou as chamadas de sistema. Para o pdflatex, isso é 'pdflatex -shell-escape'.">

O comando `\write18` é desabilitado por padrão no Community Edition porque todas as compilações acontecem dentro do mesmo contêiner `sharelatex`; esse é o padrão mais seguro.

Se quiser habilitá-lo para o pdflatex, crie um arquivo `latexmkrc` na raiz do seu projeto com o seguinte conteúdo:

```perl title="latexmkrc"
$pdflatex = 'pdflatex --shell-escape';
```

Em seguida, tente recompilar.

Referência: https://docs.overleaf.com/on-premises/support/troubleshooting#please-verify-that-you-have-enabled-system-calls.-for-pdflatex-this-is-pdflatex-shell-escape

</Accordion>
