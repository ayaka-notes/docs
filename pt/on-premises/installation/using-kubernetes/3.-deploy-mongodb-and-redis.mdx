title: 3. Implantar o MongoDB e o Redis
description: Execute o MongoDB como um replica set e o Redis com persistência, ou aponte para os seus próprios.
icon: database
---

O Ayakaleaf Pro precisa de:

* **MongoDB 8** como um **replica set** (ele usa transações). Três membros distribuídos em três nós sobrevivem à perda de um nó; um único membro também funciona.
* **Redis 7**, um servidor com persistência AOF. O Redis guarda as edições que ainda não foram gravadas no MongoDB, as sessões e as mensagens entre os serviços do Overleaf. O Overleaf se conecta a um único servidor Redis: Sentinel e Redis Cluster não são suportados.

<Info>

Você pode usar serviços gerenciados em vez disso, como o MongoDB Atlas ou o Redis da sua nuvem. Pule esta página e defina `OVERLEAF_MONGO_URL` e `OVERLEAF_REDIS_HOST` para eles na [etapa 4](/pt/on-premises/installation/using-kubernetes/4.-personalizing-your-instance).

</Info>

<Steps>
<Step title="MongoDB">
```yaml title="10-mongo.yaml" wrap
apiVersion: v1
kind: Service
metadata:
  name: mongo
  namespace: overleaf
spec:
  clusterIP: None                 # headless: gives mongo-0.mongo, mongo-1.mongo, ...
  publishNotReadyAddresses: true  # members must resolve each other before the set is initiated
  selector:
    app: mongo
  ports:
    - name: mongo
      port: 27017
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mongo
  namespace: overleaf
spec:
  serviceName: mongo
  replicas: 3
  selector:
    matchLabels:
      app: mongo
  template:
    metadata:
      labels:
        app: mongo
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app: mongo
              topologyKey: kubernetes.io/hostname
      containers:
        - name: mongo
          image: mongo:8.0
          args:
            - --replSet=overleaf
            - --bind_ip_all
            - --wiredTigerCacheSizeGB=0.25   # default is 50% of (RAM - 1 GB); size it for your nodes
          # env:
          #   - name: GLIBC_TUNABLES        # only on kernel 6.19+ (SERVER-121912)
          #     value: glibc.pthread.rseq=1
          ports:
            - containerPort: 27017
          readinessProbe:
            tcpSocket:
              port: 27017
          resources:
            requests:
              cpu: 100m
              memory: 384Mi
            limits:
              memory: 768Mi
          volumeMounts:
            - name: data
              mountPath: /data/db
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 5Gi
---
# Initiates the replica set once. Safe to re-run: it does nothing when the set exists.
apiVersion: batch/v1
kind: Job
metadata:
  name: mongo-init-replica-set
  namespace: overleaf
spec:
  backoffLimit: 20
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: init
          image: mongo:8.0
          command:
            - mongosh
            - --quiet
            - --host=mongo-0.mongo
            - --eval
            - |
              try {
                rs.status()
                print('replica set already initiated')
              } catch (e) {
                rs.initiate({
                  _id: 'overleaf',
                  members: [
                    { _id: 0, host: 'mongo-0.mongo.overleaf.svc.cluster.local:27017' },
                    { _id: 1, host: 'mongo-1.mongo.overleaf.svc.cluster.local:27017' },
                    { _id: 2, host: 'mongo-2.mongo.overleaf.svc.cluster.local:27017' },
                  ],
                })
              }
```

```bash
kubectl apply -f 10-mongo.yaml
kubectl -n overleaf rollout status statefulset/mongo
kubectl -n overleaf wait --for=condition=complete job/mongo-init-replica-set --timeout=5m
kubectl -n overleaf exec mongo-0 -- mongosh --quiet --eval 'rs.status().members.map(m => m.name + " " + m.stateStr)'
```

Após alguns segundos, um membro deve estar como `PRIMARY` e os outros como `SECONDARY`. O Job tenta novamente até que todos os membros respondam, então alguns pods do Job com falha são normais.

* O Service headless precisa de `publishNotReadyAddresses: true`: os membros precisam se encontrar pelo nome antes que o replica set exista.
* Os membros são adicionados com seus nomes estáveis (`mongo-0.mongo.overleaf.svc.cluster.local`), nunca com IPs de pods, que mudam a cada reinicialização.
* Para um único membro, defina `replicas: 1` e mantenha apenas `mongo-0` no Job.
</Step>

<Step title="Redis">
```yaml title="20-redis.yaml" wrap
apiVersion: v1
kind: Service
metadata:
  name: redis
  namespace: overleaf
spec:
  selector:
    app: redis
  ports:
    - name: redis
      port: 6379
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
  namespace: overleaf
spec:
  serviceName: redis
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis
          image: redis:7.4
          args: [--appendonly, "yes"]
          ports:
            - containerPort: 6379
          readinessProbe:
            tcpSocket:
              port: 6379
          resources:
            requests:
              cpu: 50m
              memory: 128Mi
            limits:
              memory: 512Mi
          volumeMounts:
            - name: data
              mountPath: /data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 2Gi
```

```bash
kubectl apply -f 20-redis.yaml
kubectl -n overleaf rollout status statefulset/redis
```
</Step>

### Q\&A

<Accordion title="O MongoDB 8 trava na inicialização em um kernel recente. Por quê?">

<strong>Resposta:</strong> O MongoDB 8 falha no kernel Linux 6.19 e posteriores ([SERVER-121912](https://jira.mongodb.org/browse/SERVER-121912)). Descomente a variável de ambiente `GLIBC_TUNABLES` em `10-mongo.yaml`.

</Accordion>

<Accordion title="Quanta memória o MongoDB precisa?">

<strong>Resposta:</strong> Por padrão, o MongoDB usa para seu cache metade da memória do nó menos 1 GB, e ele enxerga a memória do nó, não o limite do pod. Defina `--wiredTigerCacheSizeGB` de acordo com os seus nós; `0.25` manteve cada membro em cerca de 200 a 260 MiB nos nossos nós de teste de 4 GB.

</Accordion>
