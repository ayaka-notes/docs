---
title: 1. Obter as imagens do Ayakaleaf Pro
description: Use as mesmas imagens do Ayakaleaf Pro que o Toolkit.
icon: split
---

O Kubernetes executa as mesmas imagens que o Toolkit. Não existe uma imagem separada para o Kubernetes.

| Imagem                                               | Usada por                                                               |
| ---------------------------------------------------- | ----------------------------------------------------------------------- |
| `ghcr.io/ayaka-notes/overleaf-pro:6.3.2`             | o Deployment `overleaf`                                                 |
| `ghcr.io/ayaka-notes/overleaf-pro/git-bridge:6.3.2`  | [Integração com Git](/pt/on-premises/configuration/kubernetes/integrations/git-integration) (opcional), mesma tag acima |
| `ghcr.io/ayaka-notes/texlive-*`                      | compilações, baixadas no Docker dos nós na [etapa 0](/pt/on-premises/installation/using-kubernetes/0.-prepare-the-nodes) |

As imagens são públicas no [ghcr.io](https://github.com/ayaka-notes/ayakaleaf-pro/pkgs/container/overleaf-pro/) para amd64 e arm64, então o kubelet pode baixá-las sem credenciais.

<Warning>

Sempre use uma tag de versão, como `6.3.2`, e não `latest`. As atualizações executam migrações do banco de dados e precisam seguir [Atualizando no Kubernetes](/pt/on-premises/maintenance/upgrading-on-kubernetes); uma tag móvel atualizaria um pod sempre que ele fosse reagendado.

</Warning>

### Q\&A

<Accordion title="Nossos nós não conseguem acessar o ghcr.io. O que fazemos?">

<strong>Resposta:</strong> Copie as imagens para um registro que os nós consigam acessar e use esse nome nos manifestos, por exemplo:

```bash
docker pull ghcr.io/ayaka-notes/overleaf-pro:6.3.2
docker tag ghcr.io/ayaka-notes/overleaf-pro:6.3.2 registry.example.com/ayakaleaf/overleaf-pro:6.3.2
docker push registry.example.com/ayakaleaf/overleaf-pro:6.3.2
```

Para um registro sem TLS, o containerd precisa de um `/etc/containerd/certs.d/<registry>/hosts.toml` com `server = "http://<registry>"` em cada nó e de `config_path` definido como na [etapa 0](/pt/on-premises/installation/using-kubernetes/0.-prepare-the-nodes). O próprio Docker só faz push por HTTP simples para `localhost`, então faça o push por `localhost:<port>` no host do registro ou adicione-o a `insecure-registries`.

</Accordion>
