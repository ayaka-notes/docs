O RHEL e suas recompilações (Rocky Linux, AlmaLinux) vêm com o Podman em vez do Docker, e algumas organizações não permitem o Docker em seus servidores. O Toolkit pode executar o Ayakaleaf Pro no **Podman rootless**: os contêineres rodam sob um usuário comum, as compilações continuam rodando em contêineres TeX Live isolados e o SELinux permanece em modo enforcing. O script `bin/podman-setup` verifica o host e corrige o que puder.

Ao final desta seção, você terá a mesma instância que com [Usando Docker Compose](/pt/on-premises/installation/using-docker-compose): o Ayakaleaf Pro com compilações isoladas, MongoDB e Redis, gerenciado com os habituais `bin/up`, `bin/doctor` e `bin/upgrade`.

<Info>

O suporte ao Podman é experimental. Ele vem do Overleaf Toolkit oficial, que só o testa no RHEL 9 e posteriores com Podman rootless, compilações isoladas e SELinux em modo enforcing. Testamos estas páginas no Rocky Linux 9.9 (Podman 5.8, SELinux enforcing) com o Ayakaleaf Pro 6.3.4. O Docker continua sendo o runtime de contêineres recomendado.

</Info>

### O que você precisa {#what-you-need}

* **RHEL, Rocky Linux, AlmaLinux ou CentOS Stream 9 ou posterior**, com o SELinux em modo enforcing. O `bin/podman-setup` para em qualquer outra distribuição. No Ubuntu ou Debian, use [Usando Docker Compose](/pt/on-premises/installation/using-docker-compose/linux).
* **Um usuário não root com `sudo`** que será o dono dos contêineres. Execute todos os comandos desta seção como esse usuário; o `bin/podman-setup` se recusa a rodar como `root`.
* **Um host limpo**: sem Docker Engine e sem uma instalação existente do Toolkit. A migração de uma instância existente baseada em Docker para o Podman não é abordada.

### Como difere do Docker {#how-it-differs-from-docker}

|                                      | Docker                                     | Podman rootless                                                                          |
| ------------------------------------ | ------------------------------------------ | ---------------------------------------------------------------------------------------- |
| Quem executa os contêineres          | O daemon do Docker, como `root`            | O seu usuário                                                                            |
| Socket usado para iniciar compilações | `/var/run/docker.sock`                    | `/run/user/<uid>/podman/podman.sock`                                                     |
| Portas                               | Qualquer uma, por exemplo `80` e `443`     | `1024` ou acima, por exemplo `8080`                                                      |
| Firewall do host (`firewalld`)       | Ignorado pelas portas publicadas           | Aplica-se: abra a porta com `firewall-cmd`                                               |
| Iniciar após uma reinicialização     | O daemon do Docker os reinicia             | O serviço de usuário `podman-restart`                                                    |
| SELinux                              | Não configurado pelo Toolkit               | Módulo de política `podman_socket_clsi` e `SELINUX_MODE=managed` em `config/overleaf.rc`  |
| Perfil seccomp para compilações      | Embutido na imagem                         | Extraído para `config/seccomp/<version>/` e definido como `SECCOMP_PROFILE` pelo Toolkit |

### Limitações conhecidas {#known-limitations}

* <strong>Integração com Git.</strong> No Ayakaleaf Pro 6.3.4, `git clone` falha com `502` no Podman: o NGINX dentro da imagem procura o contêiner `git-bridge` com o servidor DNS do Docker (`127.0.0.11`), que o Podman não tem. A correção ([1b911d1092](https://github.com/ayaka-notes/ayakaleaf-pro/commit/1b911d1092c80f7b0ff77c5e3805b40503d49964)) virá na próxima versão; até lá, deixe `GIT_BRIDGE_ENABLED=false`.
* <strong>Endereços IP dos clientes.</strong> O Podman rootless encaminha a porta publicada a partir da rede do contêiner, então o Ayakaleaf Pro vê cada visitante com um endereço interno como `10.89.0.15`. Os [logs de auditoria](/pt/on-premises/user-guide/administrators/user-management#audit-logs) de um usuário no painel de administração mostram esse endereço em vez do endereço IP dele.
