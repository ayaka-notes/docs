### Criar o administrador e um primeiro projeto {#create-the-administrator-and-a-first-project}

Abra [http://localhost:8080/launchpad](http://localhost:8080/launchpad) no seu **navegador do Windows**, crie a primeira conta de administrador e faça login. Em seguida, siga [6. Tarefas pós-instalação](/pt/on-premises/installation/using-docker-compose/linux/6.-post-installation-tasks) do guia para Linux, usando a porta `8080` nas URLs de exemplo.

### Verificar a compilação {#verify-compilation}

Uma página de login funcionando não prova que os contêineres de compilação separados conseguem acessar o diretório de dados do WSL. Crie um projeto em branco e compile este `main.tex` com **pdfLaTeX**:

```latex
\documentclass{article}
\begin{document}
Ayakaleaf Pro on Windows WSL 2.
\end{document}
```

A pré-visualização do PDF deve mostrar o texto. Para a imagem basic, selecione **TeX Live 2026 Basic** nas configurações do projeto, se necessário.

Selecione **XeLaTeX** e teste:

```latex
\documentclass{article}
\usepackage{fontspec}
\begin{document}
Ayakaleaf WSL XeLaTeX sandbox.
\end{document}
```

Os dois exemplos funcionam com a imagem basic. Para documentos em chinês, use uma imagem que contenha o `ctex` e as fontes necessárias, como a full, antes de testar o seguinte com **XeLaTeX**. A basic não os inclui:

```latex
\documentclass{ctexart}
\begin{document}
你好，Ayakaleaf Pro。
\end{document}
```

Para confirmar o uso do sandbox, execute no **Ubuntu** durante a compilação:

```bash
docker ps -a --filter ancestor=ghcr.io/ayaka-notes/texlive-basic:2026.1
bin/logs -f clsi
```

Use no filtro o nome da imagem que você escolheu. Compilações curtas podem terminar antes de `docker ps` ser executado; `-a` também mostra contêineres parados até a limpeza. Um contêiner de compilação deve usar essa imagem e uma montagem bind `/compile` a partir do diretório de dados do Toolkit no WSL. Os logs da aplicação sozinhos não substituem a verificação do PDF.

### Verificar a persistência {#verify-persistence}

No **Ubuntu**, a partir do diretório do Toolkit:

```bash
bin/stop
bin/start
```

Aguarde a aplicação, reabra o projeto a partir do Windows e compile novamente. Sua conta, o código-fonte e os arquivos do projeto devem continuar lá. Os dados ativos padrão ficam em `~/ayakaleaf-toolkit/data/` dentro do Ubuntu. Guarde tanto `config/` quanto `data/`; desinstalar ou cancelar o registro da distribuição Ubuntu pode excluí-los.

### Manter a instância disponível {#keep-the-instance-available}

Manter a instância em execução envolve três partes: o Windows permanece ativo, o Docker Desktop está em execução e os contêineres reiniciam junto com o engine.

Em **Settings → General** do Docker Desktop, ative **Start Docker Desktop when you sign in to your computer**; consulte [Docker Desktop settings](https://docs.docker.com/desktop/settings-and-maintenance/settings/). Isso inicia o Docker após o login, e não antes dele. Após uma reinicialização do Windows, inicie sessão, aguarde o Docker Desktop terminar de iniciar, abra o Ubuntu e verifique `docker ps` e o site.

O **Resource Saver** do Docker Desktop é independente do repouso do Windows. Normalmente ele só é ativado quando não há contêineres em execução; a aplicação, o MongoDB e o Redis em execução impedem essa condição de inatividade. No WSL 2, ele pausa o engine do Docker em vez de desligar a VM compartilhada do WSL. Não use **Pause** manualmente no Docker Desktop enquanto estiver atendendo usuários. Você não precisa desativar o Resource Saver apenas para manter esta stack em execução; consulte a [documentação do Resource Saver do Docker](https://docs.docker.com/desktop/use-desktop/resource-saver/).

Os serviços do Toolkit usam `restart: always`. Verifique a configuração real no **Ubuntu**:

```bash
docker inspect sharelatex mongo redis --format '{{.Name}} restart={{.HostConfig.RestartPolicy.Name}}'
```

Cada serviço deve informar `always`. Quando o Docker estiver em execução, ele pode reiniciar esses contêineres existentes sem um novo `bin/up`. Um contêiner parado manualmente permanece parado até que você o inicie ou reinicie o engine; com `always`, uma reinicialização do engine pode iniciá-lo novamente. Consulte o [comportamento das políticas de reinicialização do Docker](https://docs.docker.com/engine/containers/start-containers-automatically/).

| Ação | Efeito no Ayakaleaf |
| --- | --- |
| Fechar o terminal do Ubuntu após `bin/up -d` | Os contêineres são executados em modo destacado; o terminal não é o supervisor deles. Mantenha o Docker Desktop e o ambiente WSL disponíveis |
| Fechar a janela do Docker Dashboard | A janela pode ser fechada enquanto o Docker Desktop continua na bandeja do sistema |
| Escolher **Quit Docker Desktop** | Para o engine e torna o site indisponível; abra o Docker Desktop novamente para recuperar |
| Executar `wsl --shutdown` | Para todas as distribuições WSL e interrompe o backend WSL do Docker; reinicie o Docker Desktop e reabra o Ubuntu |
| Colocar o Windows em repouso, hibernar ou desligar | O serviço fica indisponível; manter apenas a tela ligada ou desligada não altera isso |
| Executar `bin/stop` | Para a instância mantendo seus dados; use `bin/start` para retomar |

Para uso prolongado na energia elétrica, abra **Settings → System → Power & battery → Screen, sleep & hibernate timeouts** do Windows 11 (algumas versões mostram **Power** ou **Screen and sleep**). Defina o tempo limite de repouso quando conectado à energia como **Never** e desative a hibernação automática, se estiver configurada. A tela ainda pode se desligar. A ação da tampa de um notebook é uma configuração separada; fechar a tampa pode colocá-lo em repouso mesmo com o tempo limite de repouso por inatividade definido como Never. Consulte as [configurações de energia do Windows](https://support.microsoft.com/en-us/windows/experience/power-battery/power-settings-in-windows-11).

Não execute `wsl --shutdown` como limpeza de rotina enquanto o site estiver em uso. Se uma alteração nas configurações do WSL exigir isso, pare a instância primeiro e planeje uma interrupção. O Windows pode executar a instância continuamente com essas configurações. Para um serviço compartilhado que precisa sobreviver a logouts e reinicializações sem supervisão, recomendamos o [guia para Linux](/pt/on-premises/installation/using-docker-compose/linux).

### Verificar a recuperação após reiniciar o Docker Desktop {#check-recovery-after-restarting-docker-desktop}

Depois de salvar o trabalho e permitir que as compilações ativas terminem, escolha **Restart Docker Desktop** no menu de solução de problemas do Docker Desktop. Aguarde o engine e, em seguida, verifique no **Ubuntu**:

```bash
docker ps
curl -I http://localhost:8080/launchpad
```

Abra o projeto existente no Windows e compile-o novamente. Confirme que a conta e o código-fonte ainda existem.

Se você parou a instância intencionalmente com `bin/stop`, use `bin/start`. Se o Docker estiver ativo, mas um serviço falhar, leia os logs dele em vez de recriar a configuração. O Windows Update, as atualizações do Docker e quedas de energia ainda podem interromper uma instalação 24 horas; mantenha backups e verifique a recuperação após manutenções planejadas.

### Uso diário {#daily-use}

Inicie o Docker Desktop no Windows. Abra o **Ubuntu**:

```bash
cd "$HOME/ayakaleaf-toolkit"
```

| Tarefa | Comando |
| --- | --- |
| Iniciar os contêineres existentes | `bin/start` |
| Parar os contêineres e manter os dados | `bin/stop` |
| Aplicar alterações de configuração | `bin/up -d` |
| Verificar o status | `bin/docker-compose ps` |
| Ler os logs de inicialização | `bin/docker-compose logs --tail=100 sharelatex` |
| Ler os logs do MongoDB | `bin/docker-compose logs --tail=100 mongo` |
| Ler os logs do compilador | `bin/logs -f clsi` |

`bin/start` não aplica edições de configuração: use `bin/up -d` depois de alterar `config/`. Siga [Dados e backups](/pt/on-premises/maintenance/data-and-backups) antes de atualizar, mover ou remover a distribuição WSL. Copiar arquivos ativos do MongoDB enquanto o banco de dados está gravando não é um backup consistente.

Mantenha `127.0.0.1` para uso local. Atender outros computadores também exige definir intencionalmente o endereço de escuta, a URL do site, a configuração de firewall/rede do Windows e o HTTPS; alterar apenas `OVERLEAF_SITE_URL` não publica uma porta.

Se algo não funcionar, consulte [Solução de problemas](/pt/on-premises/installation/using-docker-compose/windows/troubleshooting).
