title: Nastavení kompilací v sandboxu

Kompilace v sandboxu fungují ve vývojovém prostředí trochu jinak než v produkčním image. Vývojové prostředí je už má nastavené; tato stránka vysvětluje nastavení a tři věci, na které je třeba pamatovat:

* Problém s oprávněními souborů
* Sdílení svazku mezi history-v1 a filestore
* Problém s podadresáři

### Povolení kompilací v sandboxu {#enable-sandbox-compiles}

Kompilace v sandboxu jsou ve výchozím stavu zapnuté. `develop/docker-compose.yml` nastavuje `SANDBOXED_COMPILES=true` pro `clsi` a `develop/dev.env` obsahuje zbytek:

```dotenv title="develop/dev.env" wrap
#################
#   Sandbox     #
#################
SANDBOXED_COMPILES=true
SANDBOXED_COMPILES_HOST_DIR_COMPILES=${PWD}/compiles
SANDBOXED_COMPILES_HOST_DIR_OUTPUT=${PWD}/output
TEXLIVE_IMAGE_USER=tex
ALL_TEX_LIVE_DOCKER_IMAGES=ghcr.io/ayaka-notes/texlive-full:2026.1, ghcr.io/ayaka-notes/texlive-full:2025.1
ALL_TEX_LIVE_DOCKER_IMAGE_NAMES=Texlive 2026, Texlive 2025
TEX_LIVE_DOCKER_IMAGE=ghcr.io/ayaka-notes/texlive-full:2026.1
```

clsi sám image nestahuje, proto je jednou stáhněte příkazem `docker pull ghcr.io/ayaka-notes/texlive-full:2026.1` (a `:2025.1`).

LaTeX běží v sesterských kontejnerech jako `TEXLIVE_IMAGE_USER`. Ve vývojovém prostředí je to `tex`, což je také výchozí hodnota clsi (`services/clsi/config/settings.defaults.cjs:154`). Produkční image místo toho používá `www-data`, když je `SANDBOXED_COMPILES_SIBLING_CONTAINERS=true` (`server-ce/config/env.sh:15-21`), protože tam soubory vytváří uživatel `www-data` kontejneru Overleaf.

<Warning>

Nepoužívejte prosím vlastní sestavený image, mohli byste narazit na řadu chyb.

</Warning>

### Oprava oprávnění souborů {#fix-file-permissions}

Kontejner clsi se spouští jako root, předá složky `compiles`, `output` a `cache` uživateli `node` (uid `1000`) a pak spustí clsi jako `node` (`services/clsi/entrypoint.sh`). Proto `develop/compiles` na hostiteli patří uid `1000`, stejnému uid jako `tex` ve vývojovém prostředí (viz komentář v `develop/pandoc/Dockerfile`). S výše uvedeným nastavením vývojové prostředí kompiluje bez jakékoli změny oprávnění.

Pokud místo toho nastavíte `TEXLIVE_IMAGE_USER=root`, root (uid `0`) nemá oprávnění zapisovat do podsložek `compiles`. V takovém případě dejte skupině `root` vlastnictví a právo zápisu ke `compiles` a nastavte `setgid`, aby nové podsložky toto vlastnictví zdědily:

```bash title="bash"
sudo chown -R 1000:root compiles
sudo chmod -R g+w compiles
sudo chmod g+s compiles
```

Podrobnou dokumentaci najdete v `services/clsi/README.md`.

### Sdílení svazku mezi history-v1 a filestore {#volume-share-between-history-v1-and-filestore}

<Info>

Nastavení v této a následující sekci už jsou v `develop/docker-compose.yml` a `develop/dev.env`. Mají význam jen při `S3_ENABLED=false` v `develop/dev.rc`. S výchozím `S3_ENABLED=true` ukládají filestore a history-v1 tyto soubory místo toho do bucketů RustFS (`develop/s3/docker-compose.yml`).

</Info>

Ve výchozím nastavení slouží filestore jako most mezi S3 a ostatními službami Overleafu. V Overleaf CE nebo Server Pro se však všechny soubory ve výchozím stavu ukládají lokálně. Overleaf proto zavedl velmi důmyslný postup.

```javascript title="server-ce/config/settings.js" wrap
switch (process.env.OVERLEAF_FILESTORE_BACKEND) {
  case 's3':
    // s3 case...
  default:
    settings.filestore = {
      backend: 'fs',
      stores: {
        template_files: Path.join(DATA_DIR, 'template_files'),

        // NOTE: The below paths are hard-coded in server-ce/config/production.json, so hard code them here as well.
        // We can use DATA_DIR after switching history-v1 from 'config' to '@overleaf/settings'.
        project_blobs:
          process.env.OVERLEAF_HISTORY_PROJECT_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-project-blobs',
        global_blobs:
          process.env.OVERLEAF_HISTORY_BLOBS_BUCKET ||
          '/var/lib/overleaf/data/history/overleaf-global-blobs',
      },
    }
}
```

Zároveň `data/history` používá i služba historie. Takto mohou různé mikroslužby sdílet stejná data. Proto služba filestore v develop připojuje svazek `history-v1-buckets` ze služby history-v1. Bez něj **clsi nebude moci stahovat blob soubory ze služby filestore**.

```yml title="develop/docker-compose.yml" wrap
  filestore:
    build:
      context: ..
      dockerfile: services/filestore/Dockerfile
    env_file:
      - dev.env
#    environment:
#      - ENABLE_CONVERSIONS=true
    volumes:
      - filestore-public-files:/overleaf/services/filestore/public_files
      - filestore-template-files:/overleaf/services/filestore/template_files
      - filestore-uploads:/overleaf/services/filestore/uploads
      - history-v1-buckets:/buckets
```

filestore najde buckety pomocí těchto nastavení v `dev.env`:

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
```

### Použití podadresářů {#use-subdirectories}

filestore vždy čte bloby historie s podadresáři (`services/filestore/app/js/KeyBuilder.js:58`, `:70`). Produkční image zapíná `useSubdirectories` pro history-v1 (`server-ce/config/production.json`), ale výchozí konfigurace history-v1 ne, takže ve vývoji by history-v1 <strong>všechna data zploštil.</strong> Proto `dev.env` nastavuje `NODE_CONFIG` pro history-v1:&#x20;

```dotenv title="develop/dev.env"
OVERLEAF_EDITOR_PROJECT_BLOBS_BUCKET='/buckets/project_blobs'
OVERLEAF_EDITOR_BLOBS_BUCKET='/buckets/blobs'
NODE_CONFIG='{"persistor":{"useSubdirectories":true}}'
```

Bez toho history-v1 ukládá soubory `project_blobs` takto:

```bash wrap
node@43eb5dac5b1b:/buckets/project_blobs$ ls
169_609_71360f687c431b9796_5b_889ef3cf71c83a4c027c4e4dc3d1a106b27809  
94e_655_88cb5cc77ab70c9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
169_609_71360f687c431b9796_a0_e21c740cf81e868f158e30e88985b5ea1d6c19
94e_655_88cb5cc77ab70c9796_fd_3c0326302e49486d3ea86c833edf9b88320c41
169_609_71360f687c431b9796_fd_3c0326302e49486d3ea86c833edf9b88320c41 

```

S `useSubdirectories` nastaveným na `true` se `_` v těchto názvech změní na `/`, takže každý blob se uloží do podsložek.
